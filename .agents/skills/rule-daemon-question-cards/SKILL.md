# Question cards

- A standing `ask_user_question` card belongs to the TURN, not the MCP call (`utils/standing-questions.ts`). An abandoned call DETACHES, an identical re-ask ADOPTS, an early answer is HELD for the next ask, and a reworded question is a new card.
- A CLI that holds the call open can still end a turn while the call waits (codex's code mode yields an MCP call back to the model after `yield_time_ms`, and the model may give up polling and end the turn; measured on 0.170.0). On a COMPLETED turn of a chat or of a member's own conversation, the newest unanswered card is HANDED OVER (`StandingQuestions.handOver`) to the deferred store under its own id, with no second row: the chat's `Run.pendingQuestion` (`ChatService.keepQuestionStanding`), a member's `Run.pendingMemberQuestions` (`MemberQuestionCards.ask` with `onScreen`). Its parked call is answered with the store's outcome (`posted`), and the verdict starts a turn as any deferred card's does. Released from the registry before the turn's sweeps run; refused while another card stands (closed `unanswerable`). A stopped or failed turn, the card's other siblings, and a callee conversation keep the turn's close.
- For a CLI whose client will not hold a call open (`AdapterConfig.hostQuestionDeferredReason`, cursor): the tool answers `posted` at once and the answer arrives as the next message. Do not reintroduce polling.
  - The card outlives the turn (`sweepNode` skips `deferred`) and is retired by a new turn (`sweepDeferred` → `unanswerable`).
  - Write the verdict row and clear `Run.pendingQuestion` BEFORE the answer message goes out.
  - One per run, rehydrated at boot (`rehydrateDeferredQuestions`); a different second question is refused. Every row names its `kind` (`question`, `plan`, `project`); a row that names none, or a kind no longer raised (`patch`), is unreadable and cleared at boot. No compatibility readers.
  - `propose_plan` and `save_project_instructions` take the same deferral, column and one-card rule (`PendingCardSnapshot`); a project card's Apply runs `ProjectInstructionsChangeService.write`, and its failures after Apply are `stale`, never `unavailable` (the user did see the card). Approve or Reject starts a turn whose message is the verdict, a plan's note included. Their listing says the call returns at once (`register(…, { answersAtOnce })`, read by `PlanBroker` / `ProjectInstructionsBroker.answersAtOnce`).
- cursor's own `cursor/ask_question` is not used for `ask_user_question` (option ids only).
- **Attachments.** Every writer of a question row (one carrying `questions`: the solo blocking and deferred host-tool paths, the solo in-turn and between-turn CLI events, the team host-tool and CLI-event paths, a member's deferred card) spreads `QuestionAttachmentsService.cardFields` into it: `attachments` and `moreAttachments` (always 0 now). Only explicit pages, ever (user decision): exactly the pages `ask_user_question`'s `artifacts` named, each once at its newest version, at most `MAX_QUESTION_ATTACHMENTS`; nothing is discovered for the agent — no page named in the words, none of its turn, none published since — so a question without `artifacts` (every CLI's own question tool, claude's AskUserQuestion included) writes `attachments: []`. Resolved once when the row is written and never rewritten: a hand-over writes no row, and a reboot rehydrate keeps the row as it is. An entry names a page's `artifactId`, title and version, never its serving key. A failed read attaches nothing and never refuses the question; `artifacts` naming a page this run never published refuses the call, naming the run's pages. `StandingQuestions.keyFor` stays title + questions, so an identical re-ask adopts the card with the attachments it was first written with. The command-center relay copies both fields onto `ThreadQuestionCardInput`. Rows an earlier build wrote with automatically picked pages keep them on disk; the renderer draws stored attachments only for a question asked through `ask_user_question` (`.claude/rules/ui-chats-cards.md`).
- **Team runs.** Every member turn whose CLI hands its model no question tool (`hostQuestionToolReason`) is offered `ask_user_question`: `beginAgentTurn` registers the sink under `callerKey(member, conversation)` and drops it with the turn (the tool keys its listing and call the same way, so a chat's bare member id is unchanged); claude keeps its own AskUserQuestion, so one question never draws two cards.
  - Own conversation, a CLI that holds the call open: one card in the member's flow, tracked as a question and closed with the turn like the turn's other cards (`openCards`).
  - Own conversation, `hostQuestionDeferredReason`: answered `posted`; `TeamCardsService` keeps the card in `Run.pendingMemberQuestions` (one per member, same words adopt, others `QUESTION_ALREADY_STANDING`), rehydrates it at boot, retires it on a user message (`TeamExecutorService.sendMessage`, not awaited, so the message still beats a scheduled wake) and on archive (`ChatService.retireStandingCard`); its verdict leaves the column first, then wakes that member's own conversation with `deferredAnswerMessage` (`StageWakeService.wakeLead` with the member).
  - Callee conversation: parked on its caller (`CallBroker.parkQuestion`), as a claude callee's is. A deferred one (`deferred: true`) blocks nobody, holds the call once the callee's turn ends (`owesHold`, `answerOwed`) and continues the callee inside it with the caller's answer — or, past the TTL or with no caller turn left, with word that none came, never failing the call.
