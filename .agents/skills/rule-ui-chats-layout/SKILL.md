# Chats — layout, thread UI memory and the command center

**Thread UI memory** (`chats/thread-ui-memory.ts`):

- Folds are remembered per thread, keyed by the row they belong to (`tools:<group id>`, `tool:<call id>`, …), never by an index.
- Only a press writes.
- Which hook remembers a boolean, in a thread or outside one: `.claude/rules/renderer-components.md` → _The one home for…_.
- Two things are deliberately not per thread: the context readout's drill-downs and the builder palette.
- The agents panel is always rendered when a chat is open and starts folded per thread. Nothing but its per-thread fold shows or hides it: no show/hide toggle, no header button, no auto-open on an artifact.
- The browser pane (`chats/browser/`) is a column of its own between the transcript and the agents panel, opened per thread by the agents panel's globe; it never takes the agents panel's place. It draws a placeholder that main covers with the chat's active tab (`browserSetBounds`), so every overlay primitive (`Dialog`, `Menu` — and `ContextMenu` and `Select` through it — and `Popover`) reports while it is open (`components/browser-occlusion.ts`), and while any is open anywhere the pane swaps the view for a still (`browserCapture`) — a new overlay that skips this is drawn under the page. The one exception is the pane's own full-screen view (`BrowserColumn`), a `Dialog` with `coversBrowser={false}` that hosts the view itself while the column's pane steps aside. Open in new window moves the whole browser into a window of its own whose renderer draws only `BrowserPane` with `windowed` (`chats/browser/browser-window-root.tsx`, chosen in `main.tsx` before `App` loads); the docked pane keeps the tab strip and says the browser is in its own window, with Show window and Dock back. It opens by itself only for a tab an agent just opened (`BrowserStateEvent.agentOpenedTabId`), once, and when the browser docks back from its own window (`dockedBack`, so a column closed during the pop-out comes back); later agent actions only mark the globe. Every chat link (`useChatLink`, `ChatLink`, `ChatPanelLinkRow` in `chats/browser/chat-link.tsx`) opens an `http(s)` address in that pane on a plain click only while the pane is open, else in the system browser; its right-click menu offers both browsers and Copy link. A tab shows its name (`BrowserTabState.name`, else the page title, which stays in its tooltip) beside a colour dot that opens its colour and Rename menu (`components/color-rename-menu.tsx`, shared with the terminal's tabs; double-click the name renames too, through `TabStrip`'s `leading`, `editor` and `onDoubleClick`); the user's rename or recolour goes through `browserLabelTab` and main keeps it from every later agent label, field by field. On a paired device there is no pane and the globe says "The browser runs on your Mac". Tabs and cookies are each thread's own; the pane holds no browser state of its own beyond what main reports (`onBrowserState`).
- The agents panel's column holds only what belongs to the thread: its agents, teams, pull requests and pages. The run waterfall, the processes readout and the notes open in popups from its control row (and rail), never as sections in the column; the waterfall's and processes' reads are gated on that popup being open (`onPopupChange`), never on the panel being unfolded.
- The progress popup (`chats/progress-dialog.tsx`: a team run's stages, the goals with the user's add, edit, close and reopen, and the thread's outcome) is the chat screen's too: the shelf's Progress chip and the agents panel's Goals row open it. The chip stands whenever the thread has stages, goals or an outcome, or the user can add a goal, and reads "Set goals" — the one status counter with words — while the user can add one and none is set; moving a stage stays in the panel's Stages section.
- The notes popup (`chats/notes-dialog.tsx`: the user's own notes, then a team run's team notes) is the chat screen's, not the panel's: the control row's notes button, the shelf's Team notes chip and a `team_note` row in the transcript (`TeamNoteOpenContext`) all open it, the last two on the pressed note.
- Read the MCP listing only when its disclosure opens (`mcpOpen`).

**Looks redundant, is not.** Check here before cutting:

- The task list renders in both the transcript and the agents panel. The user confirmed they want both.
- The shelf's Tasks, Sub-agents and Terminals chips restate panel counts on purpose.
- The chat-list row is four lines. Do not delete one.
- The tail `ResizeObserver` watches the scroller itself as well as its children, because a shrinking viewport fires nothing else.
- The composer shelf reserves its height (`min-h-7`). Anything thread-produced worth reaching is another chip there, never a new band — with one exception (user decision): messages other threads sent that still wait for this thread's turn are drawn above the composer as `chats/waiting-messages-strip.tsx` (sender, why it waits, first lines, Deliver now and Remove), because a counter alone went unnoticed; the Waiting messages chip lists them all. The working-agents card floats over the transcript instead, holding what a chip cannot: a row per agent and its messages. Content chips (changes, pull requests, buttons, teams) run durable to volatile from the left; the status counters (Terminals, Monitors, Sub-agents, Waiting messages, Team notes, Tasks, Progress) are glyph + figure only in `ComposerShelf`'s right-anchored `status` cluster, volatile to durable so the right edge stays put.

**Do not reintroduce:**

- Landing-view centring on the window.
- The run's folder in the composer: it belongs in the header.
- A horizontal timeline strip on the chat screen, on a command center card, or a timeline inside `subagent-block.tsx` (user decision: the cards carry none). The command center's timeline is one page-level panel in its right sidebar (`command-center/timeline-panel.tsx`, read from `GET /v1/command-center/timeline`), with no filters (user decision). Its Needs you panel (`command-center/needs-you-panel.tsx`) draws each waiting thread's open cards with the thread's own `ApprovalCard`, read from that run's state and answered through `sendVerdict` — never a second card or answer path.
- A second view of the command center's threads (cards grid, board columns): the page is the manager's chat, the graph, or both — the graph on top, the chat below (`commandCenter.view` in localStorage, the graph's height `commandCenter.graphHeight`) — with a full-height right sidebar showing Needs you or the timeline — chosen only by the header buttons, no switch inside it — user decision. Its motion (flowing wires, a breathing glow on working and waiting nodes) is the `cc-*` classes in `styles/global.css`, all off under reduced motion. The graph is React Flow, the team graph's library, laid out by `command-center/graph-layout.ts` — the manager on top, the threads under it in attention bands (`attentionOf` in `card-view.ts`, top to bottom by `ATTENTION_ORDER`: blocked, question (only threads asking the user), working (threads the manager awaits a reply from included, chip "Awaiting reply"), quiet, inactive after a day — user decision; working threads stand newest started first, every other band newest activity first, so a running thread never moves its card), each band on rows of its own (`bandRows`, `perLineFor`), every other row shifted half a card, each card as tall as what it shows; one indented column on a phone. A card's board card (`CommandCenterCard.task`, the card it works, nothing else) is a label on it. A card's head is the shared `ThreadHead` (`components/thread-head.tsx`, the same head the manager chat's thread cards wear), with a quiet Show chat icon and an Open in Chats icon at its end; Open in Chats, and the off-board toast's button, are the only controls on the page that leave it (user decision); the manager node opens nothing. Each project on the graph has a colour (`project-colors.ts`: the app palette in project-name order over every project on the board, so the project filter never recolours one), worn as a dot on its cards' project label and keyed, for the projects shown, in a legend in the graph's corner. The phone column's flow pane yields vertical panning to the page (`.cc-touch-scroll` in `styles/global.css`, unlayered so it beats xyflow's unlayered `touch-action: none`; a Tailwind utility in a layer cannot), or a finger cannot scroll it. A thread opened on the graph is not a second view of it: its node turns into one card in its own place, the node's head on top and the thread's chat under it (user decision: the node becomes the chat's header, one width, resized as a whole). The node becomes a `slot` node as big as the card at zoom 1, so the layout leaves room (`layoutRows` gives each box its own width) and the wire still ends on it; the card itself is drawn by `command-center/thread-card-layer.tsx`, a sibling of `<ReactFlow>` inside `GraphView`'s provider and never inside a node, a `NodeToolbar` or the transformed viewport (a non-portalled `Dialog` or `Popover` would be captured there), placed on its slot's top-left corner through refs from one subscription to the flow's transform, at its own pixel size at every zoom (user decision: it does not scale), its chat (`thread-card-chat.tsx`: `Chats` with `hosted`, the existing run read by id from both listings through `chats/read-run.ts`, its queue under `command-center-thread:<runId>`, drawn with no chat header of its own — `hideHeader`, since the node's head is the card's one header, user decision) behind `memo`, so a pan draws no chat again. It resizes from its corner and bottom edge, never past the graph pane, and keeps its size per thread on this device (`commandCenter.cardSizes`, pruned to the board's threads); its collapse chevron turns it back into the node and unmounts the chat. Any number may be open (user decision), held in renderer memory (`command-center/open-cards.ts`); an open card's thread keeps the band and order it had when it opened, always has a node even past the "+N more" cap, and opening or closing one never refits the view. A thread's node, and an open card by its head, can be dragged once a press travels `DRAG_THRESHOLD` (`thread-card-layer.tsx`; a shorter press stays a click), never on a phone. The drop is kept per thread on this device as an offset from the manager node's top-left (`commandCenter.nodePositions`, `command-center/node-positions.ts`, pruned to the board's threads; `run-records.ts` is the per-thread localStorage map it shares with the card sizes). `layoutRows` stands each pinned box there and moves a row that would touch one down past it, keeping band order; it centres the manager on the width of the graph with every card closed and every box in its row (`frame`), so neither a pin nor an open card moves the manager and with it every pinned node; a pinned node's wire is an elbow from the manager's bottom (user decision: a moved node stays put and the rest lays out around it). Reset layout, in the zoom controls while any place is stored, forgets them all. The view refits itself on a canvas resize, and on a change of the graph's width only until the user pans or zooms — a drag, a new thread or a band change never overrides the user's own view. On a phone the open card fills the graph pane, one at a time, with a back control and a phone back entry. A card closes when its thread leaves the board. Every in-page way to a thread — a node's title or Show chat, the answer popover, Needs you, the timeline, a thread link in the manager chat or in an open card, the working-threads card — goes through `CommandCenter`'s `showThread`: it switches the Chat view to Both (Graph on a phone), switches the project filter to the thread's project, opens its card, pans to it and flashes it (`.cc-flash`); a thread no longer on the board raises a toast whose Open in Chats is the way out. Its pan is marked as the view's own, so it does not close the answer popover. A card's Answer opens `command-center/answer-popover.tsx`: a `Popover` (`anchor="viewport"`, drawn outside the flow, whose transformed viewport would capture a fixed panel) hung from the pressed button, holding that run's cards through `NeedsYouPanel`'s own `RequestCard` and answer path — never a window (user decision: a window looked crude for it). It closes once the run holds nothing to answer, on a press outside it and when the view pans or zooms (`onViewportMove`), since a transform leaves it behind. Its nodes get `onNodeClick`, or React Flow sets `pointer-events: none` on them and no card answers the mouse.
- Always-visible controls for an absent axis.
