# Host tools — team proposals and the lead's cards

- `read_teams` / `propose_team` (`TeamProposalBroker` gates them to every chat — ordinary, a team's builder, a project's own, an analysis — and to a team run's LEAD in its own conversation, never another member and never the lead answering a call; user decisions: any of them may read and change any team or project, each behind the same card, and in a team run only the lead the user talks to may — 2026-11-12): the write is `TeamProposalService`'s in `v1/teams`, never the agent's. Every chat takes one form (`readProposeTeamArgs`): `team` whole (with `replaces`, a whole replacement), else `edits` + `replaces`, `overlay` + `overlayProjectId` and `project`, together on one card, with a required `summary` and `reason`. What a call leaves unnamed is the chat's own (`proposalTargetOf`, over the sinks): edits naming no team are a builder chat's team (`TeamBuilderBroker`, refused elsewhere), an overlay naming no project is a project chat's project or a builder chat's older binding (`ProjectChatBroker`, `TeamBuilderBroker.projectId`), and an overlay alone that names its project is that project's default team's, whichever team the chat edits. The chat's own team goes through `proposeChange`; any other through `proposeEdits`, held to `assertRunnable`. The brief of each such chat names all of this (`ANY_TEAM_OR_PROJECT`, `agents/utils/any-team-or-project.ts`).
  - A team's builder chat (`Run.editsTeamSlug`) is also offered `save_team_change`, through a `TeamBuilderBroker` sink `ChatService` registers per turn carrying that slug — the slug is never the model's. Every change goes on a `propose_team` card first (user decision: the user sees what changes, why, and the exact diff before anything is written): edits plus a required one-line `summary` and `reason`, and optionally `project` — a change to the instruction blocks of a project whose default team this is, so text moves between the team and the project on ONE card (user request: four approvals for one move were the cost of routing it through an analysis card) — or `overlay` + `overlayProjectId`, the same move into a project's overlay, which `TeamProposalService.prepareChange` applies to the file as it stands (`editTeam`, the save's own edit, schema, team and `configDir`-token checks — never `assertRunnable`, since a team is built up over several changes) into an ordinary `replace` card pinned to that file's hash; its `project` half (`TeamProposalProject`) is filled in and checked by `checkedProjectChange` — the write's own rules, the 20 000-character total among them — before the card, and pinned to the instructions revision. Approve writes it as any replacement is written (hash re-checked, backup, store save), the project's blocks first through `ProjectsService.update` (logged as the chat's change, revision-guarded) and put back when the team write fails (`writeProjectWithTeam`, as `writeWithTeam` does for an overlay); an editor save after the card went up, a moved revision, a project that left the team or was deleted makes it `not-saved` / `changed`. The builder's `save_team_change` is a check only: it always runs as a dry run and takes no `dryRun` argument. Its brief (`teams/utils/team-chat-instructions.ts`) routes every change through the card and advises no rehearsal, since a proposal refuses without raising one; the agent writes the YAML itself only to repair a file a proposal or check refused `TEAM_UNREADABLE` (it cannot be loaded — its YAML or the schema; the refusal carries the parser's first line only, since the rest quotes the file), and the turn's next check then takes the repaired file as it stands (`TeamBuilderSink.acceptsAnyVersion`). It READS its own team through `read_teams`, never with its file tools: a library team runs to 280KB, past what one tool result carries, so `slug` alone answers the whole team only while it fits a page (`PAGE_BYTES`, `teamOrOutlineText`) and its outline otherwise (every member, block and stage with each text sized, `teams/utils/team-reading.ts`); `members`, `blocks` and `stages` write those parts out with each text between `=== <path> ===` markers naming the path an edit's `path` takes, `search` answers every paragraph holding one of its words under its field's path, `full` the whole team, `overlays` the project overlays of the team it names, and `projects` the projects that run it by default — every long answer paged by `offset` on line breaks, each page naming the hash, the same in every chat. `configDir` reads as a token there too (overlay YAML through `redactOverlaySource`). `propose_team` words its listing per chat for what naming no target means there (`instructions(context)`). `isHostBuilderTeamCall` approves the builder's read and check in every mode (neither writes a change); the proposal is approved by `isHostTeamProposalCall`, its card being the gate. A builder chat also holds the analysis tools while its team has runs (`.claude/rules/daemon-thread-analysis.md` → builder chats).
  - A chat proposes a NEW team whole (`team`), and changes a library team by EDITS (`replaces` + `edits` + a required `summary` and `reason`; `team` beside a change is refused): `TeamProposalService.prepareEdits` applies them through `prepareChange`, with an overlay or project half when they carry one, then holds the result to `assertRunnable` as a whole team from a chat is held, into the same `replace` card pinned to the file's hash (`TEAM_NOT_FOUND` for a slug the library lacks). A whole `team` with `replaces` still replaces one, but its listing steers to edits: a library team runs to 280KB, past what one tool call can carry. It changes a project's overlay alone with `overlay` + `overlayProjectId` + a required `summary` and `reason`: `TeamProposalService.prepareOverlay` reads the project's default team itself (`PROJECT_GONE`, `PROJECT_HAS_NO_TEAM`) and raises the same card, through `prepareChange` with no edits. It reads the overlays first with `read_teams` `slug` + `overlays`.
  - An analysis keeps `save_team_change` and the Apply for what the user applied from its card; `propose_team` is for a change the user asks for in their own words (`.claude/rules/daemon-thread-analysis.md`). Its verdict reaches it like any chat's.
  - In an ordinary chat `read_teams` is not auto-approved (a read of the user's data outside the chat, like the history tools; a project chat's and an analysis's are, `isHostLibraryReadCall`, a builder chat's through `isHostBuilderTeamCall`) and shows every `configDir` as a token naming it (`configDirToken`, `<set:` + a short hash of the path), so neither tool hands a profile path to the provider (`read_analyzed_thread`'s team view still does). A proposal that keeps a token gets the path back from the team it replaces, matched by the token alone — never by member id or pool position, which an edit moves — and only for an agent of a CLI that profile served there; any other token refuses the proposal (`CONFIG_DIR_UNKNOWN`, `restoreConfigDirs`), never a guess. A refusal after the restore shows each path as its token (`redactConfigDirText`), and a library file's YAML error reaches the agent as its first line only (`firstLineOf`: the rest quotes the file).
  - A proposal is checked with the strict `TeamSchema` (never `TeamYamlSchema`, whose default would make an agent `approval: 'auto'`) and `TeamExecutorService.assertRunnable`; one that fails raises no card. A new team's slug (`freeDerivedSlug`, which writes nothing) and a replacement's `baseHash` are fixed when the card is raised.
  - The card is DEFERRED (`ChatService.raiseOwnedCard`): the tool answers at once and the verdict reaches the agent as the run's next message, so no CLI tool-call deadline expires it. One per run in `Run.pendingTeamProposal`, retired only by a newer proposal, an archive or the run's teardown (a new turn retires every other deferred card — a question, plan or project card — never this one: `PendingApproval.standing`), rehydrated at boot.
  - On Approve: clear the column, then write (hash re-checked BEFORE the backup, `TEAM_CHANGED` / `TEAM_EXISTS` from the store as the final guard), then the verdict row, then the message. The note the user typed is kept on the verdict row and in the message, on either button. An approval's row also carries its `outcome` (`saved` + slug, or `not-saved` + a `cause` code — `TeamProposalOutcome`, twin of the renderer's `readProposalOutcome`), because the message can wait for a turn to end and the card must not.
  - The card counts as `awaiting` only while no turn runs (`ChatService.awaitingOf`, the `ignore` of `ApprovalRegistry.awaitingFor`): every status write carries it (`writeRunStatus`'s `announce.awaiting`), so the badge follows the turns around a card that outlives them. The boot reconcile never writes it off, nor the standing question, plan or project card (`standingProposalCardId`, `readPendingQuestion`); rehydration drops a column whose card the transcript already closed, and closes one whose proposal no longer parses.
  - The card lists every `approval: 'auto'` agent (`autoAgents`, pool members included; not `acceptEdits`), worked out by the daemon; the agent's `summary` is its own capped line and its `reason` its own capped text (line breaks kept, hidden characters refused).
  - A verdict pressed while a turn runs is HELD and sent when that turn ends, however it ends (`ChatService.heldVerdicts`, in memory, released from the finalizer's `finally` and the start-failure path), and only as a turn of its own (`sendMessage`'s `ownTurn`, refused `RUN_BUSY` and held again rather than delivered into a turn). Archiving a chat closes its standing card from the column as it stands after the stop (`retireStandingCard`), and an archived chat refuses a new one (`raiseOwnedCard` throws `RUN_ARCHIVED`, re-checked after the column write; the tool answers `CARD_NOT_SHOWN`), since an archived chat refuses the verdict's message. A verdict is held, too, while a deferred question, plan or patch stands, and a chat being deleted or archived drops what it holds.

- A team run's lead (user decision 2026-11-12: only the lead, the member the user talks to) also gets `read_teams`, `propose_team`, `save_project_instructions` and `save_plugin` (`.claude/rules/plugins.md`; `TeamExecutorService.registerLeadCardSinks`, for every member `possibleLeadsOf` names, re-registered each pass and dropped with the run), and is the one member that writes the run's goals (`GoalWritersBroker`, registered there for every member on the same `offeredTo`; `goals` below): each sink carries `HostSinkOptions.offeredTo`, read live at every listing and call, which holds it to the member leading NOW (`isLeadNow`: the trigger's member in `lead` mode, `StageService.cached`'s lead in `relay`) in its own conversation (`conversationId` null) while a turn of that conversation runs (the pass's live conversations), so between its turns all four are refused as an idle chat's are. `save_project_instructions` and `save_plugin` are offered whatever CLI the lead or its pool members run, cursor included: their team cards are deferred, so no CLI has to hold the call open. The proposal, project and plugin cards are DEFERRED and owned by `TeamCardsService` (`v1/teams`, the team twin of `ChatService.raiseOwnedCard` & co. behind the `OwnedCardHost` interface): the row is written in the lead's flow, the card is tracked `deferred` + `standing` under the lead, the tool answers at once (its receipt names the team card's Approve or Deny, `HostProjectInstructionsOutcome.buttons`), and the verdict row is written and the verdict reaches whoever leads at the press as a host wake in its own conversation (`StageWakeService.wakeLead`, key `card:<runId>:<requestId>`). `TeamProposalService` picks the host by run kind (`cardsOf`: `run.teamId`). The lead's project card stands one per run in `Run.pendingTeamProjectCard` (never `Run.pendingQuestion`, whose boot rehydration is a chat's): an identical change adopts it, another is refused (`QUESTION_ALREADY_STANDING`), the column is cleared before Apply writes through `ProjectInstructionsChangeService.write` (source `chat`, the team run's id), it is rehydrated at boot (`TeamCardsService.rehydrate`), and archiving retires it with the proposal card (`ChatService.retireStandingCard`). The executor auto-approves the lead's `propose_team` and `save_project_instructions` calls in every mode (their card is the gate); its `read_teams` and `save_plugin` stay the user's to allow outside `auto`, as in an ordinary chat.
