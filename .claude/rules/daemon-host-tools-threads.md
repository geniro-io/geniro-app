# Host tools — thread messages, the command center and host wakes

- Thread messages (`list_threads`, `message_thread`): `ThreadInboxService` (`v1/agents`) writes the row first, in `thread_messages`, under per-target limits; `ThreadDeliveryService` (`v1/teams`, it needs both the chat service and the executor) routes it to one of three outcomes. **Joined**: a running turn on a CLI whose `followUp` neither is unavailable nor interrupts takes it through `sendMessage` `joinOnly` or `joinThreadMessage`, flipped `delivered` before the write so a `follow_up_dropped` finds it; a dropped one goes back to waiting under one info row, never a "not sent" row. A turn parked on the lead's or the chat's own question takes nothing, because it reads nothing until the user answers: the row waits with reason `question`, where Remove reaches it. Past `THREAD_JOINS_PER_HOUR` per target, counted from the rows (`status: delivered` with a `deliveryId`, which only a join stamps), a message that could join waits with reason `wake_limit` and wakes nobody, so two threads answering each other while the other's turn is alive run out. **Woken**: past stopped, failed, not started, a question card, `wake: false`, cold-and-large and `THREAD_WAKES_PER_HOUR`, a wake opens a turn on the fixed `THREAD_WAKE_PROMPT`, and that turn's drain carries the text: a wake never carries a message, so a message has one path into a prompt whichever way its turn opened. A chat's wake is a `HostWake` with `note: null` and a `stale` check, so it leaves memory unsettled and the row keeps the debt; a team goes through `wakeLeadForThreadMessage`, which walks a run again only when it `completed`. **Waiting**: the row carries its reason and the next turn drains it, at most `THREAD_MESSAGES_TURN_MAX_CHARS` a turn. The user's **Deliver now** (`POST /v1/threads/:runId/waiting-messages/:messageId/deliver`, `ThreadDeliveryService.deliverNow`) sets the row's `wake` and routes it again with `pressed`, which passes the join budget, cold-and-large and `THREAD_WAKES_PER_HOUR` (they hold back agents, not the user) but not stopped, failed, not started or a question card; it answers the outcome and reason. Owed rows (`wake` true, reason null, `running_turn` or `question`) are released on `bus.allStatuses()`, not on a settled turn, because a thread working off-turn settles none, on the lead's `onConversationTurnEnded`, and once at boot. Agent text, and the sender's title and member name, reach a prompt only through `threadMessagesPrompt`'s fence, never `<geniro-note>`; a not-delivered note names the thread by id for the same reason. The approval is the sender's ordinary card, so neither tool may join `autoApproves` or the team memory arm, and nothing reads the receiver's mode. `tools/call` skips `isOffered`, so the tools also refuse from the sender's run row. `claude` turns withhold `ListAgents` and set `crossSessionInbound: refuse` (`claudeSettingsArgs`), and keep `SendMessage`.
- The command center's manager (`v1/command-center`, `Run.commandCenter`, hidden from the sidebar and `list_threads` like a project chat but still a messageable thread, so replies reach it) reaches threads through its own tools only, each offered while `CommandCenterBroker` holds its turn and refused from any other run by the row: `tell_threads` (1–12 roster threads per call, resolved by handle, id or exact title — a name two titles share, exactly or as a part of each, is ambiguous — and nothing sent while any name is ambiguous or unknown — `AMBIGUOUS_TARGET`, `THREAD_NOT_FOUND`, `NOT_MANAGED` with candidates; each send is an ordinary `ThreadDeliveryService.send` with the manager as sender), `note_thread` (its note per roster thread), `archive_threads` (1–12 roster threads, resolved like `tell_threads` and nothing archived while any name is unresolved; each through `ChatService.archive`, the sidebar's own archive, never a delete; an already archived thread is reported, the manager's own run is refused `OWN_RUN`; an archived thread leaves the roster at once) and `start_thread` (a backlog card plus a start request on the task row; a deferred Start card raised through `ChatService.raiseOwnedCard` and re-tracked at boot from the task's columns, or approved at once in `auto`; Electron main's `ThreadStartConductor` starts approved cards with `startedBy: 'manager'` and no approval of its own, and the manager is woken when it started or failed). `list_threads` and `message_thread` are withheld from it (`isAppOwnChat` reads the sink; `senderTarget` refuses the row). `tell_threads`, `note_thread` and `start_thread` are auto-approved in the manager's chat only (`isHostCommandCenterCall`, user decision), so a manager start asks the user once, on its Start card; `archive_threads` is not — it follows the manager chat's approval mode — and `message_thread` keeps its card everywhere. A manager send with `expect_reply` carries `replyCreditUntil` (2 h): the receiver's first reply spends every live credit it holds and routes past the join and wake budgets once, never past `cold_and_large`; a spent credit is announced on the bus (`publishReplyCreditSpent`) so the replying thread's card stops awaiting at once. The roster (`command_center_roster`, handles never reused) is synced to the board's active set before each manager turn — additions at once, removals beside an addition or at most every 6 h — and written as the manager's `teamInstructions`, byte-identical while it does not change, closed by the user's standing instructions for the manager (`Settings.commandCenterInstructions`, pushed by Electron main to the desktop-only `PUT /v1/command-center/instructions` and held in memory by `CommandCenterChatService`) when there are any; the per-turn status table rides the prompt instead.
- A thread's last activity is the creation time of its newest transcript row, read only through `utils/run-activity.ts` (`newestItemAt`): `RunWire.lastActivityAt` (`ItemDao.latestItemAtPerRun`), the list routes' `activeSince` / `activeUntil` window (`RunDao.listPage`), `list_threads` (`RunDao.listThreads`: the window, `includeArchived`, `project` and its `page` / `nextPage`, ordered own project first, then by last activity, then id) and `search_chats`. The window's start is inclusive and its end exclusive (`windowBounds`); a run with no rows falls in no window. Never date a thread by `Run.updatedAt`, which bookkeeping writes have moved.
- Host wakes (`services/host-wake.bus.ts`): something geniro did for an agent outside its turn (a share that waited on the user's sign-in, a message from another thread) wakes it like a monitor's output, but on its own deliveries — `HostWakeChatDelivery` (held while a turn runs or a card waits, sent after listen, `RUN_BUSY` holds it again, other failures retried 3 × 30 s, then a run-level warning row says why) and `HostWakeGraphDelivery` (`wakeConversation` with opener `host`: its settle is news, announced without `hostTurn`, never counted toward `MAX_MONITOR_WAKES`, and a callee conversation is refused — only a monitor reopens a held call). What cannot be delivered (archived chat, the user's Stop — also one pressed while the wake was being sent — a refused wake, a run no pass has driven since the daemon started) becomes `oweKeyNote` for the conversation's next turn, which settles the wake (a note refused because the daemon is shutting down settles nothing, so the next boot sends it again). A wake whose `withdrawn()` answers true is dropped unsent at every attempt (a share link once agents may not share). A wake with `note: null` leaves memory unsettled when it cannot go, because a durable row holds the debt, and `stale()`, which `HostWakeChatDelivery` alone asks, drops it right before a turn would start. The opening row is a `HostRowWire` (`monitors`, `shares` or `threadWake`), whose prompt alone carries a share's link.
