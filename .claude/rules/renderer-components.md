# Renderer components — reuse & structure

Every styled element goes through the layers in order: token → primitive → shared component → feature screen. Never duplicate a component or pattern.

## Layers

1. Token — see `renderer-design-system.md`.
2. Primitive in `components/ui/`: token-driven, shadcn-v4 style (`data-slot`, `cva` variants, `cn()`).
3. App-level shared component in `components/`, composed from primitives.
4. Feature screen: one directory per screen (`chats/`, `settings/`, `teams/`, …). App shell (`App.tsx`, `main.tsx`) and daemon clients sit at the renderer root: REST through `createDaemonApis(handle)` (`daemon-api.ts`) over the generated `autogenerated/`, WS through `daemon-client.ts`.

## Reuse

- Before adding UI, browse `components/ui/` and `components/` for an existing piece.
- A pattern that appears in a second place becomes a shared component, imported everywhere.
- New primitive → `components/ui/`; app-specific composition → `components/`; feature-only pieces stay in the feature directory.
- Import directly (`./ui/button`); no barrel `index.ts` files.
- Screens are layout + state wiring; visual building blocks come from the shared layers.
- Every component in `components/` and `components/ui/` gets a co-located `*.stories.tsx` in the same commit (enforced by `components/catalog-coverage.spec.ts`; how to write one is in `renderer-stories.md`).

## The one home for…

- Control-chip look: `chip`. `select`'s `ghost` variant is built from it; a trailing `ChipChevron` marks a picker, so never put one on a static chip.
- Dropdowns: `select`, never a native `<select>` (its macOS menu ignores tokens and is invisible to the DOM). Pass `groups`, not `<option>` children; tests open `[data-menu-trigger]` and read `[role="option"]`.
- Always-visible mutually exclusive options: `segmented-control` — only when the choice is the screen's subject. A filter that narrows what is already shown goes behind a trigger (`Menu`).
- Images the user looks at: `image-viewer` (built on `dialog`, portalled). Use `ZoomableImage`; a caller that controls which picture shows renders `ImageViewer` with `ZOOMABLE_TRIGGER_CLASS` on its opener. A bare `<img>` is only for chrome. Never add a second lightbox.
- Command output: `ansi-text` over the `ansi.ts` parser. Colours come from `--ansi-*` tokens (brightness → `--ansi-bright-*`), never from the stream or computed in TypeScript.
- Pickable answer options: `option-list`, whose `arity` (`many` / `one` / `none`) decides the drawing. Never `chip` (labels can be sentences).
- Dismissible error strip: `error-banner`. `error-text` alone is for a form field, where typing clears it.
- Clipboard: `copy-button`, which owns the write and the copied feedback.
- Asking before an action: a modal question, `confirm-dialog` — or `confirm-action-button`, the button that opens one and runs the action from it. Never a second press on the same button for a new surface.
- A card that is clickable takes its hover from `card-hover.ts` (`NAV_CARD_CLASS` on a `NavListItem` card, `CARD_BUTTON_CLASS` on a card that is itself the button): a background tint only, never a translate, a shadow or a ring change; never restate it.
- A long free text in a header or row: `clamped-text` (`ClampedText`), which folds it and offers Show more only when it overflows.
- A panel opened by hovering (a submenu, a `hover-popover`, a menu a hover reveals): `use-pointer-grace` (`usePointerGrace`) keeps it while the pointer travels to it and closes it once the pointer strays or stops short. Never a close timer of its own.
- Tooltips: a plain `title` attribute. `TooltipLayer` (`components/ui/tooltip.tsx`, mounted once in `boot-app.tsx`) draws every one in the design system instead of the OS; never build a per-control hover tip for plain text. A tip that holds controls or a reading is a `hover-popover`.
- Reaching an MCP listing: `mcp-dialog-button` (opens `mcp-section` in a `dialog`); its open state belongs to the caller.
- Memoized callbacks: `use-latest-callback` (`useLatestCallback`), never `useCallback` (eslint bans it). A kept `useCallback` function holds its render's whole scope, which holds the other kept callbacks and their renders, so every earlier render stays in memory until the renderer runs out of heap. A `useMemo` whose value holds a function made inline is the same link: build that function with `useLatestCallback`.
- Remembering a boolean the user set: `use-persisted-flag`. Inside a chat thread use `chats/thread-ui-memory.ts` (`useThreadFlag` / `useThreadOverride` / `useThreadFlags`) instead, so the choice stays with that thread.
- Side-panel blocks and outward links: `panel-section` + `panel-link-row`.
- Sidebar rows: `nav-list-item`; set `suspendActivation` while a nested control owns the row's clicks and focus.
- Prompt-length fields: `expandable-textarea`, except where the surrounding component must close the field itself (its ⤢ modal cannot be dismissed from outside — see `chats/queued-strip.tsx`).
- Opening a long text in a window: `markdown-editor-dialog` (`MarkdownEditorDialog` to edit it, `MarkdownViewerDialog` for the same window locked). Never a second text window.
- A long text that is edited somewhere else (a team's text on a project's page, a shared stage text, a block another screen owns): `read-only-text` (`ReadOnlyText`), its first lines with Open full text into `MarkdownViewerDialog`. Never the whole text printed in full, and never a disabled or `inert` editor standing in for a read-only one. What this scope adds to that text is a field only once it holds text or its Add was pressed: the Add sits beside Open full text through `ReadOnlyText`'s `actions`, styled `TEXT_ACTION_CLASS`.
- A setting a narrower scope can override (a project over its team): `teams/overridable-row.tsx` (`OverridableRow`, `OverridableGroup`). The control stays live and changing it is the override; the row then carries the accent edge, the scope's name and a reset back to the inherited value, a quiet Team tag before. Never an Override button that unlocks a faded or `inert` control.
- A text that may run long on a card or row: `clamped-text`. A list that grows with use (history, devices, analyses) shows its newest few with Show all, or moves behind a button into a dialog; never every entry inline.

## Daemon types

- Never restate a daemon wire type; import it from `autogenerated/`. `shared/contracts.ts` is Electron-internal and holds no daemon shapes, except the one twin recorded in `apps/ui/src/main/AGENTS.md` (`ShareDestination`).
- A renderer-only concept over daemon data is derived from a generated type (`TeamMeta = Pick<Team, …>`, `Pick<TeamMember, 'id'>`), so a daemon change surfaces as a type error. These derivations live in `teams/member-schema.ts` and `teams/team-doc.ts`.

## Test helpers

- A helper only specs use lives in `renderer/__tests__/`, never in a production directory such as `components/ui/`.
- `__tests__/stub-resize-observer.ts` is called by the specs that need it, not installed suite-wide — other specs rely on the global being absent.
