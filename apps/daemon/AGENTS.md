# apps/daemon

Guidance for coding agents working in `apps/daemon` — the NestJS loopback daemon. Claude Code loads it automatically when this directory is touched and Cursor reads nested `AGENTS.md` files as well; Codex loads it only when started inside this directory; see the root `AGENTS.md` for project-wide overview, commands, conventions and constraints.

### Module layout

A standalone NestJS engine the UI spawns as a child process, laid out like Geniro's `apps/api/src`: `main.ts` (bootstrapper + extensions → `init()`) and `app.module.ts` at the root, then feature/infra dirs:
- `auth/` — `runtime.ts` (per-launch `RuntimeInfo` + DI token, incl. the bound `port`) + global `runtime.module.ts` (also hosts `CallTokenRegistry`, so the guard and the graph executor share it without a module cycle); `mint-token.ts` (the one source of loopback credentials — the launch token AND the per-caller-node MCP call tokens); `token.guard.ts` + `safe-equal.ts` (loopback bearer-token gate); `ws-auth.ts` (`enforceWsHandshakeAuth` — the ONE Socket.IO handshake gate, shared by every gateway, since the handshake bypasses Nest guards; gateway MESSAGES do run the global guards, which is why `LoopbackTokenGuard` passes `ws` contexts); `call-token.registry.ts` (per-`(runId, nodeId)` MCP call tokens, minted through `ensure` — see below).

**A call token is minted ONCE per RUN, and `CallTokenRegistry.ensure` is the only way a run start may ask for one.** A node's CLI process is kept between passes and presents the token it spawned with, so a fresh token locks that process out of its own endpoint for the rest of the run: every `call_agent`, `await_agent` and board-tool call answered 403 by the guard, with nothing in the transcript explaining it. The idempotence lives in the registry rather than at the call sites (the caller loop and the board-task loop both start a run), because a call site that forgets a `get(...) === null` guard re-mints.
- `environments/` — `environment.{prod,dev,test}.ts` + `index.ts` (picks by `NODE_ENV`, loads `.env` via dotenv), laid out like the sibling api's: prod is the base, dev spreads prod, **test spreads DEV**, and each is one object literal closed with `as const satisfies Record<string, string | number | boolean | null>` — the shape is INFERRED, so there is no hand-written interface to keep in step and a new field is typed at every read site without a second edit. An env file holds environments and nothing else: `readDaemonVersion` lives in `utils/daemon-version.ts`, and the strict parsers in `utils/handshake.ts` beside the rest of the UI→daemon contract. Three fields deliberately bypass `getEnv` and say so at their own line — it boolean-coerces `'0'`/`'1'`/`'on'`/`'off'`, which is wrong for `GENIRO_USER_DATA` (a path), `GENIRO_PORT` (must be a bindable 1..65535) and `GENIRO_IDLE_EXIT_MS` (malformed ⇒ feature OFF, never a guessed number). `host` is a CONSTANT rather than an env knob — the one deliberate departure from the sibling's env-everything shape, because "binds 127.0.0.1 only" is a hard v1 constraint and an env var is how it would come to be broken.
- `utils/` — `handshake.ts` (pidfile `DaemonInfo` shape + loopback bind defaults + `isValidPort`/`parsePort`); `stop-cause.ts` (reads and removes the UI's `daemon-stop-cause` note at boot, and the cause vocabulary and sentences the interrupted rows and the board use — see *An interrupted card is continued only when the app stopped on purpose*); `interrupted-runs.ts` (`closeInterruptedRuns` — the boot's one order for it: read the note once, both orphan reconciles, then the board settle); `pidfile.ts` (write/remove — `mintToken` moved to `auth/mint-token.ts`); `pidfile.lifecycle.ts` (Nest `OnApplicationShutdown` → removes the pidfile); `atomic-file.ts` (stage-then-rename writes: `atomicWrite`, its `Sync` sibling for callers that cannot yield, and `atomicCreate`, the exclusive form the instance lock claims with); `process-identity.ts` — the ONE answer to "is pid N still the process I recorded", `ps`-reported start time within a 2s tolerance, shared by the two things that act on a pid they do not hold a handle to (a bare `kill(pid, 0)` cannot tell a recycled pid from the original, and both readers below would then SIGKILL or refuse to boot on a stranger); `instance-lock.ts` + `instance-lock.lifecycle.ts` — **one daemon per userData dir**. The port fallback stays (a FOREIGN process on 47615 must not block a start), but a second GENIRO daemon is refused: it would share the SQLite file and overwrite the pidfile (a stray `pnpm daemon:dev` beside the app's own daemon). The lock records the holder's process start time, so a SIGKILLed daemon's leftover lock is self-healing with no staleness window to tune — the next launch cannot confirm a dead holder and takes over at once. The takeover is ATOMIC: a stale lock is RENAMED to a name only this launch knows and the file it actually took is judged again, standing down (and linking a live holder's lock back) if a faster launch got there first — never delete-then-claim, which lets a second launch delete the lock the first had just written. Released on Nest's shutdown hook, NOT `process.on('exit')`: Nest re-raises the signal after its hooks and default signal termination never runs `exit` listeners. It is released only after every in-flight turn is drained and every kept agent process signalled (`ProcessRegistry.drain`, memoized, and `AgentSessionRegistry.closeAll`): Nest runs the root module's shutdown hooks before `AgentsModule`'s, so the lock and pidfile hooks start both themselves rather than waiting for the hooks that would; `idle-shutdown.lifecycle.ts` — the daemon exits ITSELF after `GENIRO_IDLE_EXIT_MS` with no connected WS client **and** no in-flight turn. Two conditions, not one: no client is what makes it unused, no turn is what makes it safe to stop, and a workflow keeps running after its window closes. "No turn" counts work BETWEEN turns too (`AgentSessionRegistry.workingOffTurn`: a kept process that wrote an off-turn row in the last `OFF_TURN_ACTIVE_MS`, or holds a detached command) — otherwise it kills claude's own continuation turns, cursor delegates still out, and a `pnpm dev` the agent left running. It exists for the launches the UI supervisor can never clean up after — it only terminates the daemon it OWNS, and a force-quit or crash leaves one it does not. SIGTERM at itself rather than a direct exit, so the `ProcessRegistry` drain and pidfile cleanup still run. **Disabled unless the environment names a window**, which only `DaemonSupervisor.spawnDaemon` does (10 min): `pnpm daemon:dev` and the throwaway `pnpm generate:api` daemon have no client by design and must not read that as being unwanted; `crash-guards.ts` — the process-level `unhandledRejection`/`uncaughtException` handlers, installed before Nest so a stray rejection logs instead of crashing past the `ProcessRegistry` drain. An uncaught exception SIGTERMs the daemon at ITSELF so the shutdown hooks still run — first writing its pid to `<userData>/daemon-crashed` (`DAEMON_CRASH_MARK_NAME`, twinned in the UI's `daemon-pidfile.ts`), because that SIGTERM makes a crash exit exactly like the idle exit, and the mark is how the supervisor tells a death it must respawn from a stop it must not — and that is the one thing here with a trap in it: **Nest runs those hooks inside its own SIGTERM listener**, so a hook that throws comes straight back as another uncaught exception. It is latched (`shuttingDown`) for exactly that reason — unlatched, every re-entry re-sends SIGTERM and re-runs the hooks, each arming its own failsafe timer, until the process aborts on memory (the macOS "Electron quit unexpectedly" dialog). Every handler body is also wrapped so it cannot throw out of itself — the debug sink writes to a file, and a stream the shutdown already closed is the same loop reached through the logger.
- `db/mikro-orm.config.ts`, running on `db/nul-safe-sqlite.driver.ts` and switched to WAL at boot (`main.ts`). **MikroORM 7 binds no parameters**: every statement is rendered with its values pasted in (`AbstractSqlConnection.prepareQuery` → `Platform.formatQuery`) and run as raw SQL, and SQLite ends a string literal at a NUL byte, so the stock driver fails any write whose text holds one with `unrecognized token`, losing transcript rows. The driver's platform renders such a string as `('a' || char(0) || 'b')` instead. WAL is there so a process READING `geniro.db` (an agent's own `sqlite3` query, a DB browser) cannot hold the rollback-journal lock past better-sqlite3's 5s and fail the daemon's writes with `database is locked`; a failed switch is logged and retried next launch, never fatal. Copying the database therefore means copying `geniro.db-wal` with it, or stopping the daemon first.
- `v1/runs/` — `runs.module.ts` + `entity/{run,item,node-state,call-context,run-group}.entity.ts` + `runs.types.ts` (status/kind enums). `run_groups` is the sidebar's own folders — runtime state, not a definition, so it sits in SQLite beside the runs it holds rather than in YAML (which is reserved for the workflows a user authors and exports). `Run.contextTokens` / `contextWindowTokens` are runtime state of the same kind: the last context reading the CLI reported, written from every `context_progress` (`ChatService.rememberContext` → `RunDao.rememberContext`) and again from the `turn_complete` that carries the window, since claude names one on its result line and on no assistant line. Neither half is ever cleared by a READING that omits it — silence says nothing about a figure — while a COMPACTION clears the count outright (`RunDao.forgetContext`, called from the carried-compaction commit and from a CLI compaction that did not say what it left behind), because the conversation it measured is gone; it exists because the transcript can only carry a figure per SETTLED turn. See *The RING is drawn from three sources* in `apps/ui/AGENTS.md` for the reading order. `NodeState` carries the per-node twin of that pair, and the renderer READS it — `GET /v1/workflows/runs/:runId/nodes` on run open and on reconnect (`chats/use-node-context.ts`), which is what gives a workflow node's ring a durable source instead of only the ephemeral live plane. `CallContext` is the twin ONE level further down, keyed `(runId, callId)`: a node is the wrong grain for a reading, because a node can hold several agent-to-agent calls at once and `node_state` collapses them to whichever wrote last. It rides the same route (nested under each node's row as `calls[]`) and the same teardown. The same route also answers SPEND over the whole run (`totals`, `mainTotals`, `calls[].totals`), summed at read time from the run's `turn_complete` rows grouped by node and by the payload's `callId` — nothing new is stored, and a call that spent without ever reporting a context reading is listed too, within the same cap. Two properties of that listing are not obvious from the shape. It is CAPPED (`CALL_CONTEXT_SNAPSHOT_LIMIT`, newest first and returned oldest-first): a row is written per call and never deleted until the run is, while the route is read WHOLE on every reconnect, so a long-lived workflow that fans out on a loop would make every reconnect pay for its entire history — and a reading older than the oldest loaded transcript thread has no ring to be drawn on anyway. And the DAO creates a row only when the calling node still has a `node_state` row: unlike its node twin, which is a bare `nativeUpdate` that harmlessly matches nothing, this one INSERTS, so a reading straggling past a teardown would orphan a row. The node is the right thing to ask about rather than the run, on two counts — `purge` destroys node states BEFORE call contexts, so there is a window where the `runs` row still stands and a row written against it is already dead; and `getNodeStates` builds its response by mapping over node states and looking calls up beside them, so a call whose node has no state row is unreachable BY CONSTRUCTION. It narrows rather than closes: `Item.runId` has no FK either, and closing it properly means a transaction spanning both writes, not a longer guard. `NodeState.workedMs` / `toolCalls` are the per-node TOTALS beside that pair, and the difference between the two kinds is why they need their own writer. A context reading is a LEVEL — the newest one is the whole truth, so `rememberContext` replaces and a write that never lands costs nothing. These are TOTALS, where every write is a fraction of the answer, so `NodeStateDao.rememberWork` SUMS and a lost write is a figure permanently short. It is a read-modify-write rather than a SQL increment, which is safe only because the executor funnels both figures through the one serialized `enqueue()` chain it already uses for the readings and the DAG gives a node one turn at a time; a second writer reaching that row from another path would need a real increment. `workedMs` comes from `turn_complete`'s `usage.durationMs` and `toolCalls` from counting `tool_call` events whose `parentToolUseId` is absent — the daemon-side twin of the renderer's `subagentIdOf` exclusion, so a delegate's toolbelt is never folded into its launcher's. Both are written at the `turn_complete` site ALONE, unlike the context pair's two sites, because a duration exists only on that line. `Run.workedMs` / `toolCalls` are the CHAT twin of the same pair, written by `ChatService` through `RunDao.rememberWork` — the same split `contextTokens` follows, since a chat's readings live on the run row rather than a node row. Written at EVERY ending of a turn geniro started, not only the clean one: a `turn_complete` contributes both figures, and a `turn_cancelled` or an `error` contributes the tools already called and no duration, neither terminal carrying a `usage` — counting only the clean ending loses every stopped or failed turn's tools. What is still NOT counted is what the CLI does OFF-TURN (`handleBetweenTurnEvent` has no terminal arm), so a claude process opening a continuation turn of its own when a delegate reports back writes to the transcript and not to these columns; closing that needs a per-RUN counter and is deliberately not built. They ride `RunWire`, so the renderer reads them off the run it already holds instead of a second route — and, because a TOTAL cannot be derived from the event that moved it and nothing else refreshes a run row between full listings, the SETTLE announce carries them too (`RunStatusEvent.workedMs` / `.toolCalls`, read back by `writeRunStatus` through `RunDao.readWork`); without it the renderer's copy freezes at fetch time, and since a durable total outranks the client's windowed fold past `HISTORY_PAGE` items, the agent card's clock drops back at the settle. On a settle ALONE — an activity announce fires on every tool call and must not pay a query — and omitted when both are null, these columns only ever growing, which is what keeps every workflow run off the field. Null means never measured, never zero, and the two are independently nullable: every ACP agent reports no timing while still using tools. `NodeState.polledSpend` is the other runtime column here and belongs to a different subject: a per-EVENT ledger of what each polled CONVERSATION has cost (`utils/polled-spend-ledger.ts`) for a CLI whose money is POLLED from the vendor rather than reported per turn (`AdapterConfig.usage.polledSpend` — cursor today, via `CursorAcpAdapter.fetchAccountSpend`, driven by the generic `PolledSpendService`). Per event, not a watermark, because the vendor REVISES a charge after listing it: a long agent request is listed early and its cost grows as it runs, so a watermark that counts each event at first sight undercounts badly. Every poll re-reads each conversation from its oldest still-open event and REPLACES the figure held under each event's key; an event older than a day (`SETTLE_AFTER_MS`), on a poll that read its whole window, is folded into a settled sum. A conversation never priced starts an hour before its node was created (bounded by the account's thirty days); a node priced before the ledger existed whose start the account no longer covers keeps its old total as settled. The conversations a node answers for are THREE sets, claimed by one node each: every session in `NodeState.sessionIds` (appended by `saveSessionId`, the one seam every turn saves through, since `agentSessionId` is overwritten by each), every `call_result` row's `sessionId` naming it as callee (the only record on runs older than that history column), and every DELEGATE any of those spawned (`AgentAdapter.spawnedConversations` — cursor reads the CLI's own `Agent ID: <id>` task-result sentence out of the parent's `store.db`; a delegate is billed under its own conversation id). `NodeState.polledCostCents` / `polledCostEvents` are that same bill per NODE — the ledger's sum, rewritten whole on every poll — because a workflow mixes CLIs: a workflow run ADDS the polled bill to the other nodes' turn costs (`addPolledSpendToTotals`), and a polled node's card and readout state its own share (`nodePolledSpend`), so one node's polled bill is never shown as the run's whole total.
- `v1/auth/` — CLI account sign-in: `controllers/cli-auth.controller.ts` (`@Controller('v1/auth')`) exposes `POST /login`, `GET /login/:id`, `POST /login/:id/code`, `POST /login/:id/cancel`, `POST /logout`, `POST /mcp-login`. An ended sign-in is dropped 10 minutes after it settles, only the last 64K of its output is kept, and once a code is submitted only NEW output can ask for another (an old prompt still in the buffer must not reopen the code field). The pty those flows run in is `/usr/bin/script`, which gives the CLI a session and process group of its OWN, so the reap re-confirms each of `script`'s children (same pid, same command) and terminates that child's group too; killing `script`'s group alone left a SIGHUP-ignoring CLI reparented to launchd.

### The agent-execution substrate

- `v1/agents/` — the shared agent-execution substrate (M2): `agents.module.ts` + `chat.types.ts` at the root, then `adapters/`, `controllers/`, `services/`, `dao/`, `dto/`, `utils/`.
  - `adapters/` — the abstract `AgentAdapter` base + `adapter.types.ts` (the CLI-agnostic contract, incl. `AdapterConfig`/`AdapterQuestion`/`TurnDriver`/`HandoffResult`) + `utils/skill-scan.utils.ts` (the shared on-disk walk, free of any one CLI's paths), then one directory per PROTOCOL several CLIs could speak and one per CLI — see `.claude/rules/agent-adapters.md`. **Every static fact about a CLI is one `AdapterConfig`**, assembled by that adapter's own `getConfig()`, so `listSkills`, `listEfforts`, `listReportedCommands`, `supportsLiveStream`, `resolveApprovalMode`, `handoffTarget`, `runLogin`/`runLogout`/`runMcpLogin` and `errorRecovery` are CONCRETE on the base over config; only `getConfig`, `buildArgs`, `mapMessage` and `listModels` are abstract. The `auth` block sits beside `mcp` and `configDir`: that CLI's own sign-in argv, the reason it has none, and the wording that marks a failed turn as a lapsed ACCOUNT session (evidence-gated — a CLI whose such failure has never been observed declares `[]`, as cursor does, rather than a cure invented from `--help`).
    - `acp/` — the agent-agnostic **Agent Client Protocol** client, one file per protocol concern (not an exhaustive list): `acp.types.ts` (wire shapes; the JSON-RPC framing itself is shared with codex in `adapters/utils/json-rpc.utils.ts`, and so is the reply correlation, in `adapters/utils/json-rpc-pending.utils.ts`), `acp-content.ts` (attachments → `image` content blocks), `acp-session.ts` (ONE process and the turns run on it — the transport, the replies it is still owed (`PendingRequests`, with ACP's deadlines on top), the negotiated capabilities, the session id; this is the `TurnDriver` an ACP adapter returns), `acp-driver.ts` (the per-TURN state machine, one built per turn), `acp-sessions.ts` (`session/list` — the protocol's own answer to "what conversations do you hold", plus the `session/load` handshake that makes an agent replay one, and the readers for both), `acp-models.ts` (per-session model selection — see the `CursorAcpAdapter` paragraph below). It knows nothing about cursor; a second ACP-capable CLI composes it rather than copying the protocol.
    - `claude/` — `claude.adapter.ts`, `claude.const.ts` (ALL of that CLI's constants), `claude.types.ts`, `claude-probe.service.ts` (the `--permission-mode` support probe — a round that could not settle is held for `CLAUDE_MODE_PROBE_RETRY_MS` per `--version` rather than re-run by every read), and `utils/` (`claude-message` — `mapClaudeMessage` + the two stream-partial mappers; `claude-usage`; `claude-models` — the account models the CLI caches in `~/.claude.json`; `claude-images` — base64 content blocks; `claude-question` — the one defensive reading of an AskUserQuestion input, `claudeCardQuestions` (the card, which the caller's envelope is then built from by the shared `adapterQuestionOf`), and `withResponse`, which picks the answer channel by question COUNT — `updatedInput.answers` (a map keyed by question text) for a lone question, `updatedInput.response` (one free-text reply, which REPLACES the structured list) for several; `claude-mcp-config` — the per-turn 0600 `--mcp-config` file, its boot sweep, and the geniro-key collision check; `claude-mcp-folder` — what claude's OWN config files say about a folder (which servers are project-scope, which the user disabled themselves); `claude-mcp-list` — `parseMcpList`, the prose `claude mcp list` output turned into rows; `claude-mcp-ready` — the `mcp_status` request line and the reply reader behind the readiness gate below; `claude-context-usage` — the SECOND undocumented control request this adapter drives, `get_context_usage`, the wire behind that CLI's own `/context`. The reader projects the large reply down to what a readout can use, and three facts shape it — an `isDeferred` row is OUTSIDE `totalTokens` (the non-deferred rows sum exactly to it), `Free space` is the remainder rather than a category and is dropped so nothing double-counts it, and the per-tool rows are folded into one per SERVER because which server holds the context is invisible until they are summed; `claude-tasks` — that CLI's own task list read off BOTH directions of a tool call, since the `TaskCreate` id is only in the result and the `TaskUpdate` status only in the input; `claude-sessions` — the conversations this profile holds, listed and read off `<configDir>/projects/<flattened cwd>/<id>.jsonl`; `claude-commands` — the reload/announce dialogue that gets the command list WITH a sentence per entry: `system/init` names every command and describes NONE of them (an array of plain strings). One `reload_skills` control request makes the CLI push `system/commands_changed` carrying `{name, description, argumentHint, aliases}` — the reload's answer, never a startup announcement (an ordinary turn that asks nothing emits none), and it lands BEFORE `init`. The request rides `AgentTurnInput.commandListProbe` — a flag that says what the turn IS, never what a CLI should do about it — and ONLY the command probe sets it: `reload` re-reads the user's own skills and plugins, which is free in a throwaway temp directory and rude on a live chat), plus `claude-turn.driver.ts` — that gate.

      **A claude session's FIRST prompt is held until the CLI's MCP servers have finished dialling.** The CLI dials its servers when the PROCESS starts and does NOT wait for them before running a turn, so a prompt written too early can find some servers still `pending` and lose their tools for the rest of the conversation — nothing is permanently missing (the surface GROWS mid-turn), so the damage is entirely in what the model concludes once and never re-checks. The oracle is `mcp_status`, an undocumented client-initiated control request on the same stdin dialogue as `can_use_tool`: it answers BEFORE any prompt has been written, with one row per server under `mcpServers` (not `servers` — reading the obvious name returns an empty list from every healthy reply, which is indistinguishable from "discovery has not started"). The gate polls it and releases on two IDENTICAL readings with nothing `pending`, never one: discovery is gradual, so a single quiet moment is also what a half-discovered list looks like. Only `pending` blocks — waiting for `needs-auth` to become `connected` would hold every first message for the full deadline on any machine with one signed-out server. Three exits bound it: an empty reading is believed for a 2s grace (a machine with no servers), a `refused` reply releases at once (a renamed subtype costs the fix and never the turn), a CLI that has answered NO poll for 5s (`CLAUDE_MCP_READY_SILENCE_MS`) releases with a `notice` saying the surface is unconfirmed (a cold start is shorter, and the CLI answers an unknown subtype with an error reply, so longer silence is a CLI that stopped answering); silence is NOT timed while one of the CLI's own hooks is running, since it reads no control request until its SessionStart hooks finish and reports them on stdout (`system/hook_started` / `hook_response`, paired by `hook_id`) — and a 15s deadline releases with a `notice` NAMING the servers still starting, because a turn must never silently run on a partial surface. The seam is agent-agnostic — `TurnDriver.awaitPromptReady` awaited by `CliTurnOptions.holdPrompt` in `spawn-cli.ts`, FIRST turn only (the wait belongs to the process, and by turn two the servers have been up for a whole turn) — and cursor defines neither, so its opening write stays synchronous. Two claude turns are outside it as well: one carrying `isolateMcpServers` loads no server by construction, and one naming no approval mode is a geniro-internal probe that never reaches a tool. A cancel during the hold DROPS the prompt rather than writing it into a turn the user already stopped, and a gate that throws is logged and the prompt sent anyway — losing the user's message would be worse than the defect being fixed.
    - `cursor-acp/` — `cursor-acp.adapter.ts` (binary name, env re-injection, the approval policy, the session-mode mapping, and a `getConfig()` whose single-reader facts are written INLINE), `cursor-acp.const.ts` (the values that are NOT single-reader: the `mcp list` argv and the probed row markers its parser and its adapter both spell) and `utils/` (one file per concern, not an exhaustive list here — `cursor-mcp-list.utils.ts` — `parseCursorMcpList`; `cursor-todos.utils.ts` — `parseCursorTodos`, the `cursor/update_todos` payload; `cursor-context-store.utils.ts` — **that CLI's own context accounting, read off disk**; see the directory for the rest). It still has no `.types.ts` — the wire shapes live in `acp/`. Its `mapMessage` throws by construction: an ACP adapter has no line mapper, `createTurnDriver` returns an `AcpSession` (the `TurnDriver`), which builds an `AcpTurnDriver` per turn, and `acp/acp-driver.spec.ts` is what drives the protocol without a process.
    - `codex/` — OpenAI's Codex CLI, driven over its own **`codex app-server`** (stdio JSON-RPC, one process per conversation; codex ships no ACP server). `codex.adapter.ts` (the config fact sheet, the one-shot listings — `model/list`, `thread/list`, `thread/read`, `skills/list`, `config/read`, `config/value/write` — each asked of a fresh app-server with the handshake and the request written back to back, and the plan limits asked of the RUNNING process with `account/rateLimits/read` so they are that run's account), `codex.const.ts`, `codex.types.ts`, `codex-session.ts` (the PROCESS: transport, its `PendingRequests` (shared with ACP), the thread, and everything keyed by an id codex mints per thread — items, parked approval requests, sub-agent threads) and `codex-turn.driver.ts` (one per TURN: `turn/start` carrying that turn's own approval policy, sandbox, model and effort — codex keeps a turn's overrides for the turns after it, so every turn sends all of them — `turn/steer` for a follow-up, which JOINS the turn (a refusal of it never goes unsaid: the driver posts a notice quoting the message and asking the user to send it again, even when the reply lands after the next turn has opened — the one stale reply `PendingRequests` delivers), `turn/interrupt` for Stop, and `thread/compact/start` for `/compact`), over pure mappers in `utils/`. The composed instruction block is the thread's `developerInstructions`; geniro's MCP endpoint rides the thread's config overrides as ONE dotted key (`mcp_servers.<name>`, so the user's own servers stay), bearer token in `http_headers`, with a day-long `tool_timeout_sec` on geniro's entry alone. Approval modes: `auto` = `never` + no sandbox, `ask` = `untrusted` + workspace-write, `acceptEdits` = `ask` with file-change requests answered `accept` by the driver only while the change stays inside the folder (`fileChangeStaysIn` — no `grantRoot`, and every path AND every move destination, `kind.move_path`, inside `cwd`, each judged by the shared `utils/write-containment.ts`, the same check `applyHostPatch` uses, which must find codex's raw path inside under both the as-written and the resolved reading, since how codex's own writer reads it is not geniro's to rely on — and no target that shares its inode with another name (`hasOtherHardLinks`, asked under both readings of the path like the containment check, and answered as shared for a path it cannot examine), which no judgement of a path can see; anything else is a card — and inside the folder the trust is WHOLE: a file that runs commands later (git's own config, an MCP or editor task file) is accepted like any other, by decision, since no path policy is built around the mode), `plan` = codex's plan collaboration mode (sent only on the way into plan mode and back out, since a collaboration mode's settings outrank the thread's own) under a read-only sandbox.     **A turn does not end on its CLI's turn-end line while a DELEGATE it started is still out** (`spawn-cli.ts`, `TurnState.openWork`/`deferredTerminal`, fed by the agent-agnostic `background_work` event). The turn-end line is the end of what the agent was SAYING, never of what its process is DOING: a claude turn that launched a delegate prints its `result` while the delegate still runs, and the CLI then runs a whole FURTHER turn of its own accord as the delegate reports (that continuation's result line carries `origin:{kind:"task-notification"}`). Settling on the first `result` ends geniro's turn mid-work and hands everything after it to nobody — assistant messages dropped, permission requests answered with no card shown. So a `turn_complete` is HELD while `openWork` is non-empty, and the hold ends one of three ways: RELEASED with its held result when the last unit reports, or — bound by the turn's existing silence deadline — when the outstanding work is given up on, rather than overwriting a finished turn with "produced nothing…"; or DISCARDED with no result ever emitted when the turn demonstrably continues before either of those fires, because the main thread speaks again (`RESUMES_A_HELD_TURN`, main-thread events only) or a follow-up is delivered into the held turn — releasing the stale result there would settle the turn in the middle of the agent's next answer, so the turn instead runs on to its NEXT terminal. Only a `turn_complete`, and only on a `session` stdin lifetime: a cancel is the user asking to stop now, an `error` is a turn that failed rather than finished, and a turn whose process ends with it has no "after" to wait for. Claude reports the lifecycle on `system/task_started` + `task_updated`/`task_notification` (both terminal channels mapped — they spell one outcome `killed` and `stopped`); a CLI that reports none simply never emits the event and its turns settle exactly as before, so this is not a capability an adapter must declare.

    **The last delegate REPORTING is not the end of the turn — the CLI says when it is, and nothing here waits on a clock** (`announcesSessionState` / `onSessionState` in `spawn-cli.ts`, fed by the agent-agnostic `session_state` event). The hold ends when the last delegate reports, and that is precisely when the CLI is about to speak again: the way it LEARNS a delegate finished is a task notification, which opens a whole further turn of its own. So a release on the report settles one breath ahead of the continuation and posts a false "done" notification into that gap. A fixed grace period after the report was tried and rejected (it delays every genuine ending); do not reintroduce a timer. The answer is the CLI's own statement: claude announces `system/session_state_changed` under `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS`, and its schema calls `idle` the "authoritative turn-over signal" — a turn that launched a background delegate emits no `idle` with its first `result`, only after the continuation's. So for a CLI that has announced its state, a report settles nothing: the continuation's main-thread output DISCARDS the held terminal (`RESUMES_A_HELD_TURN`) and the turn ends on the continuation's result, and when no continuation follows, `idle` ends it. `idle` is also trusted over this layer's own bookkeeping — a unit still listed in `openWork` when the CLI goes idle is a report that was missed, and is written off the way the silence deadline writes off its own. A CLI that has never announced its state is released on the report itself, since nothing else would ever say the turn is over; the off-turn twin follows the same two rules.

**Nor does a turn end on a `result` while a follow-up written INTO it has not been taken** (`TurnState.unconsumedFollowUps` / `supersededTerminal` in `spawn-cli.ts`, fed by the agent-agnostic `user_message_consumed` event and gated on `AdapterConfig.followUp.consumptionReported`). A message delivered mid-turn joins the turn, but joining is not being answered in it. claude's `--replay-user-messages` echoes each stdin message as a `user` line carrying `isReplay: true` at the moment the CLI TAKES it: a message written while a tool ran is echoed at the tool boundary and answered inside the same `result`, while one written as the model produces its final words is echoed only after that `result`, under a fresh `system/init`, and answered by a `result` of its own. Settling on the first line ends the turn (and a workflow run, whose `call_agent` calls are then refused `RUN_NOT_ACTIVE`) under a message the agent is about to answer. So each follow-up written on the stdin-line path is recorded, crossed off by an echo carrying its text (the turn's own prompt is echoed too and matches nothing), and a `turn_complete` arriving while any is outstanding is HELD; the turn then settles on its next `result`, with the held segment's usage FOLDED in (`utils/fold-turn-complete.ts`) so its bill is not lost — the adapter already reports each `result` as that segment's own figures. The held result is NOT the prompt being answered, so `promptAnswered` stays false and a continuation arriving meanwhile is still routed around the turn. An echo that never matches is bounded the way every other hold is: the CLI announcing `idle` settles on the held result, and a CLI that never says `idle` settles on it at the silence deadline rather than being failed as having produced nothing. A CLI that declares no acknowledgement keeps settling on the first `result`, since nothing could ever cross its messages off; cursor needs none, its follow-up being a `session/prompt` whose own reply is the only one that ends the turn.

**A backgrounded COMMAND is deliberately not among them, and that carve-out is the whole of `unit === 'agent'` in `trackBackgroundWork`.** A delegate's completion makes the CLI open a whole further turn of its own, which needs a turn to land in; a backgrounded `pnpm dev` reports nothing, ever, so holding on it runs to the 30-minute silence deadline above an agent that has finished. A shell is covered elsewhere: its end is a durable `shell_info` row, the command is a first-class row in the running-shells panel with its own terminal behind it, and anything the CLI says once it lands rides `handleBetweenTurnEvent` — which is what makes the carve-out safe. An unclassified unit (`'other'`) counts as a shell, which is the reading `announceDelegateWork` already takes, so a CLI that names no kinds cannot get delegate treatment through one path and not the other.

    **A unit the agent WAITS on is not background work until the CLI says it has become some** (`background_work.foreground` and the `backgrounded` phase; `foregroundUnits` in `spawn-cli.ts`). claude's `task_started` fires for a SYNC sub-agent too, and — once a foreground command has run a few seconds — for that command, so that either CAN be moved to the background; both carry `is_backgrounded: false`, which the CLI's schema defines as "in the foreground with the spawning tool call blocking on it". Read as background, a sync sub-agent would raise `subagentsOut` and a long `pnpm test` `shellsOpen`, and the composer reads either count as "the agent is free" (see `apps/ui/AGENTS.md` → *When a message queues*). So a foreground unit is announced to NOBODY as background work: no `backgroundOpen: true`, no `shell_open`, and at its settle no `shell_info` for a command that never detached (its end is its own tool result). A later move — the CLI's auto-background timer, or a queued message it moved the work aside to deliver — arrives as `task_updated patch.is_backgrounded: true`, which the mapper turns into a `backgrounded` phase (never a settle; a patch that also ends the unit is a settle alone), and only then is the announcement made. A foreground delegate still enters `openWork`: whether the turn may end is a different question from whether the agent is free. cursor needs none of this — its `cursor/task` states `isBackground` and a foreground delegate is already announced `backgroundOpen: null`.

    **A background SHELL's OPEN is a transcript row too** (`shell_open` items). The tool call that detached a command is in the transcript; the DETACHMENT is not, and that is the fact a reader needs. It is read here off the CLI's own structured frames, so the renderer never has to recover it by matching the CLI's English (`readLaunchHandle`, deliberately strict), and `Run.shellsOpen` — which counts exactly these events — and the transcript stay two views of one set. It doubles nothing (the reader marks the call it names and never adds a command), and it belongs in `restatesRunAsWorking`: an open really is work beginning, but a backgrounded command deliberately does not hold a turn (`trackBackgroundWork`'s `unit === 'agent'` carve-out), so reading it as the AGENT working would latch the spinner with no further row until the close to take it down. The badge it earns is `held`, which `shellsOpen` already drives.

    **A background SHELL's end is a transcript row, because nothing else records it** (`shell_info` items; `AgentEvent`'s `shell_info`, `spawn-cli`'s `announceShellWork`). A detached command's launching tool call is answered within the second (`Command running in background with ID: …`) and the command runs on for minutes — so the transcript holds a start and no end, and a client folding "what is running" out of tool calls lists it forever. claude reports the completion to the MODEL as a `system/task_notification` frame (parsed as `background_work`) and to the conversation only as a sentence the agent writes. `announceShellWork` is the twin of `announceDelegateWork` for the units on that channel that are NOT delegates, and the two are told apart by what the `started` line said, never guessed. Three details are load-bearing. It runs BEFORE the delegate twin, because it decides "is this a delegate?" by asking `delegateWork`, which that twin deletes from on the settle carrying figures — the other order announces every delegate as a shell as well. It announces ONCE per unit (`settledShells`): claude reports the same ending on `task_updated` AND `task_notification`, and the row is durable, so a duplicate would be stored for the life of the transcript. And it is a `shell_info` rather than a `subagent_info`, since announcing a shell as a delegate is exactly the phantom sub-agent the delegate twin refuses to create in the other direction. **It also belongs in `restatesRunAsWorking`**: a settled run producing a row goes back to `running`, and a `pnpm dev` finishing minutes after a chat settled would otherwise put that chat's badge back with nothing able to take it down.

    **A CLI that reports a backgrounded command FINISHED is answered by the operating system** (`utils/process-descendants.ts`; `sweepDetachedShells` in `spawn-cli.ts`, gated by `AdapterConfig.shells.unreportedDetachReason`). Everything above rests on the CLI bracketing its own background work. cursor does not, and it says the opposite: a backgrounded command's tool call is answered `status: "completed"`, `rawOutput: {exitCode: 0, …}` within seconds while the process runs on. Believing it loses the command entirely — no row, no count, no chip, and a chat that looks idle while it works. No other channel carries it: no `cursor/*` extension method is about backgrounding, nothing is written to disk, and the CLI never calls the ACP `terminal/*` client methods (`createTerminal`), so declaring a `terminal` client capability changes nothing.

    The process table can answer because the command is OURS: it runs under the CLI child this module spawned (`command → /bin/zsh → cursor-agent → the daemon`). So a settling turn takes ONE `ps` reading and asks, of every execute call the CLI has ANSWERED, whether a descendant is still running it. Three things keep that honest. It looks only at ANSWERED calls — an unanswered one is an ordinary foreground command the transcript already draws as running, and opening a row for it too would list it twice. It matches on a normalized PREFIX of the command rather than an equality, because the CLI wraps what it runs in a long zsh preamble ending `-- <command>`. And the result is fed back through `announceShellWork` as an ordinary `background_work` bracket, so a shell found this way is the same row, the same `shellsOpen` count and the same chip as one a CLI reported itself — there is no second kind of shell anywhere downstream. The poll that closes it exists only while something IS out (`DETACHED_SHELL_POLL_MS`), so an ordinary session never runs one, and the process ending closes whatever is left.

    **Stopping a terminal reaches a FOREGROUND command too** (`ChatShellsService.killForeground`, `utils/process-descendants.ts` → `commandNeedles`). The panel lists a command call the CLI has not answered as running, so Stop must reach it, not only DETACHED commands (`shell_open` rows). The written command is usually not in the process table at all: a shell given one simple command EXECS it, as does `env`, so `/bin/zsh -lc 'env -u FOO BAR=1 sleep 37 > log 2>&1'` is one row reading `sleep 37`. So the lookup is ATTRIBUTION first — only processes under this run's own live CLI (`AgentSessionRegistry.processRoots`), never the CLI itself — and matching second, over needles derived from the written text (the `sh -c` body unwrapped, `env` options and assignments dropped, redirections cut, builtins skipped). The whole TREE under each match is signalled (a foreground command shares its CLI's group, so a group kill would leave its children), and nothing is written: the CLI answers the call itself once the command exits.

What the CLI DOES write is the delegate's own transcript, `~/.cursor/projects/<cwd, non-alphanumerics → ->/agent-transcripts/<id>/<id>.jsonl`, whose first line wraps the delegate's brief verbatim (`<user_query>\n{prompt}\n</user_query>`) and whose last line, once it is over, is `{"type":"turn_ended","status":"success|error|aborted"}`. The `<id>` is NOT `cursor/task`'s `agentId`, so the transcript is located by the BRIEF: born after the launch, unclaimed by another delegate, opening with that prompt. The ACP session watches every background delegate's transcript while the process is alive (`DELEGATE_ENDING_POLL_MS`, only while one is out) and writes the close with the outcome it states (`completed` / `failed` / `stopped`) and the duration measured from the launch, in-turn or through the off-turn sink. `utils/cursor-delegate-transcript.utils.ts` is the reader; `cursor-acp.const.ts`'s `Background sub-agents` block says what to re-check on a CLI upgrade.

    **A TURN ending closes nothing it can watch.** A turn-settle closer that closed every delegate still out when a cursor turn COMPLETED was removed — it drew still-working delegates as `completed`; do not reintroduce it. The fallback survives only where nothing can watch: a delegate whose announcement carries no brief, or whose transcript never turns up (`DELEGATE_RECORD_MISS_LIMIT` reads, logged), is closed with no outcome ahead of the COMPLETED turn's `turn_complete` (`AcpSession.onTurnCompleted`) — or at once, if that turn is already over when the watch gives up.

    **And the turn itself WAITS for the delegates it can watch, then the agent is woken — geniro does what cursor's ACP server never does** (`AcpDelegateProtocol.wakePrompt`, `AcpTurnDriver.holdForDelegates`, `AcpSession.awaitDelegates`, `cursor-acp/utils/cursor-delegate-wake.utils.ts`). Without it a callee that launched background delegates ends its turn "they are finishing now", and its caller gets that sentence as the result (`delegates_still_running`). So a turn whose prompt ends `end_turn` with WATCHED background delegates out THAT IT LAUNCHED ITSELF (`AcpTurnDriver.launchedHere` — session-wide, a delegate an earlier turn stopped waiting on would hold every later message of the conversation again) emits no `turn_complete`: it posts one `info` notice and holds. When the last one ends, the session is prompted with each delegate's description, outcome, duration, report (the last assistant line of its own transcript — the parent holds no result, since the `task` call returned at launch) and transcript path, and the turn settles on THAT prompt's answer — its `finalText` starts at the wake, so a caller is not handed "finishing now" glued in front of the review — which may launch more and hold again, up to `MAX_DELEGATE_WAKES`. While held there is no prompt out, like the transient-resume pause: Stop is answered by `withdrawHeldPrompt` (no frame, `turn_cancelled`), and a message carries the turn on through `sendFollowUp` and ends the hold. A hold nothing has moved for in `DELEGATE_HOLD_IDLE_MS` (25 min, restarted by each ending, under `spawn-cli`'s 30-minute silence deadline so that never fires on a turn with an answer) settles on the answer it had. A delegate nothing can watch never holds anything, nor does a probe turn. Known limit: delegates that END before the prompt does are not reported — the agent may have polled for them already, and a wake would replace its real answer with a reply to the wake. On a workflow call the executor counts an open background delegate as an open tool call (`delegate:<id>`) for the call broker's silence watchdog, which otherwise read the hold as a wedged callee.

    **A RESUMED delegate writes no new transcript** (`locateCursorDelegateTranscript`): cursor continues a cut-off delegate by APPENDING the new brief to its existing transcript, which opens with the original brief. So a transcript born before the launch is also matched when it was written to since the launch and its LATEST user message carries the brief, and only delegates still OUT hold a claim on a transcript. A claim is handed over when the brief written LAST is no longer the claimant's — a cut-off delegate never writes `turn_ended`, so it stays out, and its continuation takes the transcript while it is closed `stopped`. The rule is tried only 15s after the launch (a new transcript appears ~6s in) and never against the parent's own conversation, which can quote the brief. A delegate is cut off when its own cursor stream drops (`decision=THROW RetriableError … enableAgentRetries:false` in cursor's debug log; the ACP server offers no retry flag); a parent's stream dropping does not stop its sub-agents.

    **codex reports a sub-agent as `subAgentActivity`, not as a collab call — and reports its ending after the turn.** A `spawn_agent` call arrives on the PARENT thread as `{type:"subAgentActivity", kind:"started", agentThreadId, agentPath:"/root/<name>"}` and no `collabAgentToolCall` at all (`subAgentActivityOf` in `codex/utils/codex-items.utils.ts`, `CodexTurnDriver.trackSubAgentActivity`). The sub-agent's own thread streams on the same connection (its items nest under the launch via `parentToolUseId`), and its ending arrives twice — its thread's `turn/completed` and a parent-side `subAgentActivity` `kind:"completed"` — both after the parent's turn has ended; `closeSubagent` takes whichever comes first — so codex, too, has no turn-settle closer.

    **A BRACKETED delegate's off-turn steps are not the run working** (`ChatService.leaseOnDelegateRow`, `GraphExecutorService`'s `onOffTurnEvent`, over `BackgroundWorkCounts.isDelegateOut`). The delegate-row lease and the node's off-turn badge exist for delegates nothing brackets; a delegate announced open is already on the badge through `subagentsOut`, and its close — which is no terminal event — is what ends that. Read as the run or node working, a codex sub-agent's streamed steps would keep a chat `running` for the whole lease and latch a workflow node `running` for good.

What CAN also end it is the PROCESS. Such a delegate runs INSIDE the ACP process that launched it — its own permission requests arrive on the parent's session, and killing that group two seconds after a turn left one unable to finish writing its file — so when the session closes, everything still out has demonstrably stopped. The close is written there (`AgentSessionRegistry.onClosed` → `settleAfterSessionClosed`, ahead of the off-turn badge restore, which returns early on exactly the runs this is about), and again at BOOT for the closes a SIGKILLed daemon never got to write — no session can exist that early, so every open delegate on disk is stranded by construction. The outcome is `stopped` rather than `completed`: the delegate never reported, so claiming it finished its work would be a figure nothing measured.

    Three details. The open set is folded from the run's OWN `subagent_info` rows rather than kept only in memory, so one durable source serves both the session close and the boot sweep — an in-memory tally is right for the first and empty for the second. The ranking inside that fold mirrors the renderer's `subagentBlockStatus` (a stated `backgroundOutcome` outranks `backgroundOpen`, and a row claiming neither says nothing), because the two form one contract: the renderer does not read a TURN's ending as a delegate's, which is what lets a fan-out stay visible while it works, and it is safe to do that only because this always eventually says otherwise. And the count rides the run ROW (`RunWire.subagentsOut`, announced on `run_status`), the delegate twin of `shellsOpen` and for its reason — derived from the open thread's transcript it is knowable for one chat and no other.

    **A WORKFLOW run's endings are the EXECUTOR's to write** (`GraphExecutorService` → `closeStrandedWork`, over `utils/open-delegates.ts`, `utils/open-shells.ts` and `ItemDao.shellRows`). `ChatService`'s session-close hook keys by RUN while the executor's sessions are keyed per turn (`<runId>::call:call-7`), so it cannot reach them; and the shell closes a dying process announces arrive through `onOffTurnEvent` after `runFinished`, where they are dropped by design. The executor writing them is forced rather than chosen: it numbers its run's rows with its own counter, so a close from `ChatService`'s allocator into a live workflow run could take a seq the executor is about to use. At run end it closes every delegate and detached command still out, AHEAD of the terminal row; when the registry closes one of a LIVE run's sessions on its own account (unused, evicted, stale) it closes that session's delegates alone, scoped by call id or by node — its shells need nothing there, since the process exit's own announcements still reach a live run's sink. Every close carries its open row's node AND call id (`ownerFields`): a callee's rows are claimed into its call block by the payload's `callId`, so a close without one lands in the main flow while the delegate sits in the block (the renderer also claims a callId-less delegate row into the call its launch was made in). `reconcileStrandedShells` is the boot sweep's shell twin, for the closes a SIGKILLed daemon never heard.

    **A dynamic WORKFLOW's fleet is a transcript row too, and for a stronger reason than the shell's: nothing about it reaches the conversation at all** (`workflow_info` items; `AgentEvent`'s `workflow_info`, `CLAUDE_TASK_PROGRESS_SUBTYPE`). Claude's `Workflow` tool is ONE tool call that fans out into dozens of agents running inside its own orchestrator with transcripts of their own — so without it a long workflow is one opaque tool call. The launch is a `system/task_started` carrying `task_type:'local_workflow'` and the workflow's NAME, and progress rides `system/task_progress` on the same `tool_use_id` — running totals every time (`usage.total_tokens` is the SUM over the roster, so it is the workflow's own bill and not the turn's), and the full agent roster whenever one of them changes state. Three details are load-bearing. `task_progress` is SHARED with delegates, so the roster's presence is the discriminator — a delegate's line names a `subagent_type` and carries none, and mapping those would card every Task call. Only the roster-bearing lines become rows, which is what keeps the channel from writing a transcript row every few milliseconds: the CLI attaches the roster on a state change or at most every ten seconds, and since an agent's tokens are reported as it FINISHES, every line that moves the totals carries the roster with it. And the launch line is the only one that ever states the workflow's name — every line after it reports the description instead — which is why the anchor is emitted at `task_started` rather than waiting for the first roster.

**Every compaction the CLI FINISHES is one transcript row, whether or not it reported a summary** (`utils/compaction-rows.ts` → `CompactionRows`, run beside `mapEventToItem` by the chat turn, the chat's between-turn handler, and the graph executor's in-turn and off-turn sinks). The boundary line carries the figures and no text; the CLI's injected summary carries the text and no figures. When the summary follows, the figures are stamped onto its row. When none does, a row of the daemon's own (`COMPACTED_WITHOUT_SUMMARY`, `severity: 'info'`, the same `compaction` marker including `trigger`) is written ahead of whatever the stream produces next. The second case is the COMMON one: claude builds its synthetic summary line only on the local-command path (a typed `/compact`), so an AUTOMATIC compaction — the window filling mid-turn — would otherwise leave no trace in any transcript. A delegate's compaction is left out, since it is not the conversation the user reads. The renderer checks the marker BEFORE the author, so the daemon-written row reads as the same event (`conversation compacted automatically`).

### Workflow passes and off-turn work

**A workflow run's agent processes outlive each reply, as a chat's do** (`GraphExecutorService`'s pass `finally`, `AgentSessionRegistry.closeRun`, `CliSession.shellsRunning`). Each message to a workflow run is a PASS. What an agent started in the background (`run_in_background` dev servers) lives inside its process, so a pass must never close the run's processes at its end:
- **A pass leaves its processes running.** The next message reuses each one under the same key: its session key does not change between passes, and a caller's call token is minted once per RUN rather than per pass, since a kept process presents the token it spawned with.
- **The registry reaps an unused process on the ordinary idle rules, never while it holds a detached command** (`shellsRunning > 0`, also exempt from eviction).
- **Archive and delete end every process of the run** (`closeRun`, matching `<runId>` and `<runId>::…`).

With it:
- **Between passes, a kept process is still recorded.** Its closers and its off-turn sink go on writing after the pass, refusing only a run being deleted. That writing is why a workflow run's rows take their seq from the shared `ItemSeqAllocator`: the pass that spawned a process and a later pass can both be writing.
- **An unattended node's between-turn permissions are still granted after its pass**, now that what follows is recorded.
- **The endings of work inside a process are written when that process goes, not at the pass's end.**

**The pass-end `skipped` sweep skips a node that already has a status** (`GraphExecutorService`, before `setStatus(skipped)`). `skipped` is decided off the PASS's own bookkeeping, and a call-only node — or any node a call ran inside this pass — has none, so a finished node would be rewritten `skipped`. Only a node still `pending` is skipped.

**A follow-up pass resets to `pending` only the nodes the DAG schedules** (`prepareNextPass`, `onDemandNodeIds`). A CALL-ONLY node that already has a `node_state` row keeps its status: no pass schedules such a node, so `pending` would promise a turn that never comes and erase how the node's last call ended. A node added to the workflow since still gets its pending row.

**A turn geniro started never settles on the result of a continuation the CLI ran by itself** (`AgentEvent`'s `turn_complete.continuation`, set by claude's mapper from `CLAUDE_CONTINUATION_ORIGIN_KIND`; honoured in `spawn-cli`'s terminal branch). A message written while the CLI is mid-continuation is answered only AFTER the continuation's own `result` line, which carries `origin:{kind:"task-notification"}`; settling on the first result would hand the new turn the continuation's text (the call runtime's "wrong result text" case too, since a `thread:` continuation is a turn on a kept process). The marked result is handed to the between-turn path instead (`handleOrphanEvent`), so its row and usage are still written, and the turn waits for its own. The flag is a fact the line states about itself, never inferred from timing or from zero figures. **The exception is a continuation that ABSORBED the prompt** (`TurnState.promptTaken`): a prompt written while the continuation runs a TOOL is taken at the next tool boundary — the CLI echoes it (`isReplay`) and logs `absorbed_mid_turn` in its session file — and answered inside the continuation's ONE result, with no result of its own ever following (routed around, the turn would settle twice). So once the CLI has echoed this turn's own prompt (matched by text, `CliTurnOptions.promptText`), a continuation's result or failure is the turn's ending; the order of the echo against the result is what separates the two cases. The idle settle (`answeredByContinuation`, a row the renderer draws no footer for) stays as the fallback for a CLI that never echoes.

**What the CLI does AFTER its turn settles belongs to the run, not to nobody** (`ChatService.handleBetweenTurnEvent`). A turn's `result` line ends the turn geniro started; it does not stop the CLI, which routinely opens a further turn of its own accord when a delegate reports back — that continuation's own result names itself `origin:{kind:"task-notification"}`. `spawn-cli` has no turn to hand that output to, so it arrives on `onBetweenTurnEvent`, and every event type is kept, never only tool calls. The rule is the in-turn rule: whatever `mapEventToItem` yields a row for is persisted in arrival order, the live signals feed the same partial stream, the self-reports feed the same harvest stores, and the continuation's own terminal event settles the run again. A settled run producing rows goes back to `running` with `offTurnActivity` naming it as the CLI carrying on by itself rather than as a fresh turn. A `notice` is the exception (`restatesRunAsWorking`): it says something about the CLI, and a steered message the CLI refuses after its turn had ended arrives as one with no terminal event behind it — restated as `running`, it would latch a finished run's badge on. Two runs are exempt: one the user CANCELLED (Stop is final — a straggling result flipping `cancelled` back to `completed` says their Stop did not take, though the rows are still written, because a transcript that hides work is lying the other way), and one whose `running` this path did not write, which `offTurnRuns` is what distinguishes — the handler is async, so a real turn can have opened in between, and settling THAT turn's run on the previous one's tail is the defect `cancelledTurnMayStillEmit` exists to stop. **A ROW is not the only evidence that the run is working again** (`restatusAfterOffTurnSignal`): an agent that is THINKING has emitted none, and on a long think it will not for minutes. A main-thread `text_delta` or `thinking_progress` from a SETTLED run therefore flips it back too, on the same terms as a row (a delegate's is not the run's, and Stop is still final). Its own method rather than another caller of the row path, for two reasons: a delta fires many times a second and the phrase never changes, so `offTurnRuns` short-circuits the rest of the burst before it reaches the database, and a run whose `running` belongs to a REAL turn is left entirely alone instead of having that turn's activity phrase restated — a row is worth re-announcing for, an unfinished word is not. `context_progress` is deliberately excluded: it measures the WINDOW rather than asserting that anything is being produced, and it is also emitted synthetically once a compaction has FINISHED. **And a DELEGATE'S own rows are evidence too, under a lease rather than a latch** (`leaseOnDelegateRow`, `closedDelegates`): a delegate whose launching `Task` call has already returned has nothing holding the turn open for it — `spawn-cli` holds only on `background_work`, which is the CLI's own `task_started` bracket, and a delegate it never brackets is invisible to that mechanism — so the `result` line settles the run while the delegate's steps go on arriving. Such a row flips the run back too — but it CANNOT go through the row path, whose `running` is ended by a terminal event that a delegate never produces, so restating a delegate's trailing rows there latches the spinner on with nothing able to take it down. The lease is that missing off-switch, renewed free by each further row and expiring after `DELEGATE_ROW_LEASE_MS` back to the status it took over. The two cases are told apart by EVIDENCE, not by timing: a bracketed delegate reports its own end, `spawn-cli` relays that as the `backgroundOpen: false` announcement that closes its block, and `closedDelegates` records it from BOTH handlers — in-turn for a delegate whose whole life fits inside its turn, off-turn for one that outlives it — so a named delegate's tail restates nothing while an un-bracketed one's stream takes the lease. In the happy path the expiry is never reached: a delegate that reports back makes the CLI open a continuation turn, and that turn's own `result` settles the run through the ordinary path.

**An off-turn `running` has a SECOND ending, and without it the badge could outlive everything that could take it down** (`ChatService.settleAfterSessionClosed`, over `AgentSessionRegistry.onClosed`). The latch a main-thread row takes ends only on a terminal event; the lease at least expires. Close the PROCESS that owed that terminal event and neither can happen, leaving the run `running` for good. So a close hands the badge back, and it is a different fact from the expiry rather than a shorter clock: the expiry is a GUESS that a quiet delegate has finished, a close is the CERTAINTY that nothing more can arrive. The status to restore lives on `offTurnRuns` itself (a `Map`, not a `Set`), since both kinds need restoring on identical terms. Nothing is announced during SHUTDOWN — every session is closed on the way out, and the next boot's reconcile owns those runs. A process that DIES on its own — a crash, an OOM kill, a `pkill` — is a close too (`forgetWhenClosed` must not drop it silently): it tells the same listeners, with `exited` set so the transcript note says the process ended rather than that geniro closed it.

**And the idle window measures a chat going UNUSED, which a CLI writing rows is not** (`AgentSessionRegistry.touchOffTurn`). `session.idle` means "alive with no turn of OURS in flight" — true of a CLI running flat out between turns — so the window armed at the last settle would run out underneath live work. An off-turn event refreshes the timer, the same reading the `parked` exemption beside it already applies. It refreshes rather than arms, and only when a window is already running: with a turn in flight there is deliberately no timer, and `track` arms the next one when that turn settles. It rides the caller's `onBetweenTurnEvent` sink, so a caller that supplies none keeps `spawn-cli`'s "dropped an event arriving between turns" warning instead.

**The ceiling itself is DERIVED from the machine, not a constant** (`sessionCeilingFor`, `MAX_LIVE_SESSIONS`). An evicted session costs the next message a cold start (every MCP server rebooted), so a flat constant is wrong on large machines. Total memory × ⅛ ÷ ~1GB per session, clamped to [2, 16]; the per-session cost is the heavy case (a CLI with many MCP servers dialled), so it over-estimates in the safe direction. Three choices in it are worth keeping: TOTAL memory rather than free, because free depends on what the machine was doing at boot and the same computer would otherwise get a different ceiling on each launch; a ⅛ SLICE rather than a share of what is available, because these processes are a cache (any of them re-opens with `--resume`, costing latency and nothing else) and the user's editor and browser announce themselves nowhere here; and a CAP at 16 that is not about memory at all — past a dozen the constraint is the person, since these are conversations somebody is meant to be following. The registry takes the ceiling as an `@Optional()` constructor argument purely so its specs can pin one: an eviction case asserting which of three sessions went means something different at a ceiling of 2 and of 16, and the derivation is pinned separately on the pure function.

**EVICTION must not kill an agent working off-turn** (`AgentSessionRegistry.OFF_TURN_ACTIVE_MS`, `worksOffTurn`). `evictIfFull` exempts a turn in flight and a parked question and takes the least-recently-used of the rest — and a CLI carrying on between turns is `idle` by that reading. So an entry that produced an off-turn row within the last five minutes is exempt on the same terms `parked` is — `offTurnActiveAt` is its OWN field rather than `lastUsedAt`, which a settling turn also refreshes, because "recently used" and "working right now" are different questions and only the second is worth a process. The window matches `ChatService`'s `DELEGATE_ROW_LEASE_MS` deliberately: both answer "how long do we go on believing a quiet stretch is still work", and two numbers is how the badge and the process come to disagree about whether a chat is busy. It can only push the registry OVER the ceiling, never refuse a turn — the all-busy arm, with a wider meaning of busy.

**And a close that INTERRUPTED work owes the transcript a sentence** (`AgentSessionRegistry.onClosed`'s `interrupted` argument → `ChatService.noteInterruptedSession`). Restoring the badge is right on every close, but the status it restores is the one the off-turn stretch took over — routinely `completed`, from a turn that ended before the agent carried on — so without a row the run reports a clean completion over unfinished work with nothing naming the cause. The registry is the only place that can tell the two apart (it knows whether the process was working when it closed), so it says which, and the row is written for that case ALONE: every session is closed eventually, and a warning on each would put a red row in every conversation the user owns about nothing. The sentence names the recovery, because there is one and it is not obvious — the conversation is intact, so the next message resumes it.

    **That silence deadline does not run at all while the turn is blocked on a verdict** (`TurnState.outstanding` non-empty), and that is the absence of a window rather than a longer one. The deadline's premise is that silence is UNEXPLAINED — it exists to catch a CLI nobody can account for. A turn parked on an approval card is the opposite: geniro raised the request, knows the CLI is blocked on it, and is itself the thing withholding the answer, so the clock would be timing a HUMAN — and would fail the run and rewrite an `AskUserQuestion` card the user is coming back to as `unanswerable`. `respondApproval` rearms on DELIVERY, and from that moment rather than from when the card went up, so answering late does not leave the turn moments from being abandoned; a second still-open card keeps it suspended. Two consequences are deliberate: Stop is then the only bound on a parked turn (which is correct — it is waiting for its user, who is the only one who can end the wait), and a parked turn keeps `ProcessRegistry.activeCount` non-zero, so `IdleShutdownLifecycle` will not fire while a question is on screen.

    **A KILL is not a cancellation, and only `cancelRequested` can tell them apart** (`settleFromTermination`'s signal branch). `turn_cancelled` is right only for the terminations geniro ASKS for — Stop and the shutdown reap both reach `cancel()`, a retired session reaches `close()`, and both set the flag — and wrong for every other way a process dies: an OOM kill, a crash, a `pkill`, a supervisor taking the group down. `cancelled` is deliberately the ONE ending the app never notifies about, so a killed agent settled that way fails silently under a badge blaming the user. Only a requested cancel (`cancelRequested`) settles `cancelled`; any other signal settles `failed` and posts `The turn failed.`. The signal is NAMED in the error message (`… was terminated by SIGKILL`), with the stderr tail beside it, since "the process ended" is not a diagnosis.
    **A findings REPORT is a transcript row too, and the only place its findings exist** (`report_findings` items; `HOST_FINDINGS_TOOL` in `chat.types.ts`, `v1/mcp/tools/report-findings/`, `utils/host-findings.ts` (its permission predicate), `services/findings-report.broker.ts`). A host tool on geniro's own MCP server beside `ask_user_question`: an agent hands over a typed list of code-review findings and the transcript draws them, instead of printing markdown a transcript can only show as prose. The ARGUMENT shape deliberately mirrors claude's own `ReportFindings`, snake_case included, so an agent that knows that tool needs to learn nothing new; `readHostFindingsReport` is the one place that naming seam is crossed. The tool result is a RECEIPT — `10 findings recorded and shown to the user.` — never the findings, which is what keeps them out of the model's window twice; the row is therefore the only copy, and it is persisted rather than streamed for `task_list`'s reason. Every CHAT is handed the endpoint for it (the question tool is still registered only where a CLI has none of its own), and the call auto-approves, because what the agent is asking permission for is the act of drawing in this app's own transcript — a gate there is a press with nothing behind it. Every call-capable GRAPH node holds the endpoint too (`holdsEndpoint` in `GraphExecutorService`), but nothing registers a reporter outside `ChatService`, so a graph node sees the endpoint and no findings tool. The one render tool a graph node IS offered is the page (`show_artifact`, below).

    **A render card is stamped with the DELEGATE that drew it, when the turn can say which one** (`ChatService.attributeCard`, over `AgentTurnHandle.attributableDelegate`). The drawing tools write their rows through the host-tool sinks rather than through `mapEventToItem`, which is where every OTHER row gets its `parentToolUseId` — so without this a delegate's card arrives looking like the main thread's own work and the renderer files it there (`subagentIdOf` → `ownerOf`). The identity cannot come from the REQUEST: the endpoint is addressed `(runId, nodeId)` and a delegate calls the very same one, so the turn has to INFER it, and the whole judgment lives behind that one handle method rather than at each call site. Three conditions: The turn must be HELD — the agent has said its piece and the process is alive only for the delegates still reporting; while it is still talking the card is as likely to be its own, which `spawn-cli` states itself on the release path ("the main thread is talking again with N unit(s) still out"). Exactly one delegate must be open, counted over `openWork` rather than over the ids that RESOLVED, since one the CLI announced with no launching call is still a second delegate. And that delegate's own launching call must be known. Anything else answers null and the row goes out unattributed — deliberately: a card filed under the wrong delegate reads exactly like a correct attribution, which is worse than the unattributed row it replaces. Cursor therefore attributes nothing today, its delegates being unbracketed, and that is the honest answer rather than a gap.

    **A CHART is another row of the same RENDER family** (`show_chart` items; `HOST_CHART_TOOL` in `chat.types.ts`, `v1/mcp/tools/show-chart/`, `utils/host-chart.ts` (its permission predicate), `services/chart.broker.ts`). An agent hands over typed numbers and the transcript plots them, instead of spending its output on an ASCII bar chart or a table the reader has to hold in their head. Everything above holds unchanged — the payload is the card, the result is a receipt (`Chart drawn for the user: 2 series over 30 points.`), the row is the only copy, every chat is handed it, it auto-approves, no graph node registers one. What is its OWN: **the payload is POSITIONAL.** Every series carries one value per entry of `labels`, matched by index, and a `null` is a GAP rather than a zero. Nothing on either side of the wire may drop or reorder one list independently of the other — that failure does not throw, it silently re-attributes every measurement after the edit and still looks like a chart. Which is why `readHostChart` **blanks** an unreadable label instead of removing it, re-aligns every series to `labels.length` (padding short, cutting long), and why the renderer's twin re-does that alignment over stored rows. Three kinds and no pie (`CHART_KINDS`): a pie encodes magnitude as angle, the hardest encoding to compare by eye, and what it gets reached for reads better as the bar chart already there. The five-series cap is the PALETTE (`--chart-1..5`, and `categoryToken` wraps): on a multi-series plot colour is the only thing tying a curve to its legend entry, so a sixth would claim the first one's colour. A call with nothing plottable is answered as INVALID_ARGS rather than as a drawn chart — unlike an empty findings report, which is a real review outcome, a chart of nothing is only ever a mistake.

    **A SCORECARD is another drawing of the family** (`show_metrics` items; `HOST_METRICS_TOOL` in `chat.types.ts`, `v1/mcp/tools/show-metrics/`, `utils/host-metrics.ts` (its permission predicate), `services/metrics.broker.ts`). A handful of headline figures with their changes — what an agent reaches for when it has measured a few things and would otherwise write them into a sentence nobody can scan. Everything the chart's paragraph says about the bargain holds: the payload is the card, the result is a receipt (`Scorecard drawn for the user: 4 figures.`), the row is the only copy, every chat is handed it, it auto-approves, no graph node registers one. **The line against `show_chart` is in both tools' descriptions**, because an agent with numbers in hand has to choose: several readings of ONE thing is a chart, one current reading each of SEVERAL unrelated things is this — they share no axis, so a chart of coverage-plus-bundle-size-plus-test-count is one enormous bar and two invisible ones. Two facts about the shape are load-bearing. **Every figure arrives ALREADY FORMATTED, as a string** — only the agent knows whether `0.82` reads `82%` and whether `1258291` is `1.2 MB` or `1,258,291`, so this row displays and never computes, and neither reader may "help" by coercing a number (both sides pin that with a test that goes red independently; the failure would look like the model's mistake and be the host's). There is no `unit` field for the same reason: a unit is part of how a figure reads. **The sentiment is STATED, never derived** — whether a change is good news is not a property of its sign, since `−40ms` is good and `−4 pts` of coverage is bad, and a `higherIsBetter` flag only moves the same guess one step away. An unrecognised sentiment falls back to ABSENT rather than to `bad`, so a misspelling cannot paint a good result red. A call with no readable figure is answered as INVALID_ARGS, on the chart's rule rather than the findings tool's: an empty review is a real outcome, an empty scorecard is only ever a mistake.

    **A COMPARISON is the family's DECISION TABLE** (`show_comparison` items; `HOST_COMPARISON_TOOL` in `chat.types.ts`, `v1/mcp/tools/show-comparison/`, `utils/host-comparison.ts` (its permission predicate), `services/comparison.broker.ts`). Several options judged against the same criteria, with a recommendation — what an agent reaches for when asked which of these to use. **Alone in this family it has to justify itself against markdown**, because a markdown table RENDERS in this transcript: an agent can already draw three columns of prose and it looks fine. So it earns its place on exactly two things a table cannot hold — a per-cell VERDICT (the shared `SENTIMENTS` vocabulary), which is what makes the winning option's column visibly greener where a table forces the reader through every cell to work out the same answer, and a NAMED, reasoned RECOMMENDATION, because a comparison that does not answer the question has handed the deciding back to the person who delegated it. The tool description says both out loud, and says that a call with every cell neutral and no recommendation should have been a markdown table — so a model can tell the two apart. **The cells are POSITIONAL** against `options`, the chart's hazard again and handled the same way: an unreadable cell is BLANKED rather than dropped (dropping shifts every later cell one column left, filing each option's answer under its neighbour's name — a failure that does not throw and still looks like a comparison), and both readers re-align every row to the option count rather than trusting the model to have counted. TWO options is a real floor, not a formality: a one-column "comparison" is the shape a model produces when it has decided before it has compared, and drawing it would dress that up as an analysis. The recommendation is matched to a column **by name**, case- and whitespace-insensitively — a model writing `SQLite` is far more reliable than one writing `1`, a name matching nothing costs only the column highlight while the reason still reads, and an index pointing at the wrong column would be silently wrong. Half a recommendation is dropped whole: a named option with no reason is an assertion the reader cannot weigh, a reason naming no option is a paragraph.

    **A GALLERY is the family's PICTURES** (`show_gallery` items; `HOST_GALLERY_TOOL` in `chat.types.ts`, `v1/mcp/tools/show-gallery/`, `utils/host-gallery.ts` (its permission predicate), `services/gallery.broker.ts`). Several images shown together as a thumbnail grid that opens into the full-screen viewer, where the reader can zoom and step between them. It carries a class of answer none of the others can: screenshots before and after a change, the frames of a flow, charts some other tool wrote to disk. Without it an agent's only move is a markdown image per picture — a column of full-width images with no way to step between them and nothing saying they are ONE set. The ordinary bargain holds: the payload is the card, the result is a receipt (`Gallery shown to the user: 3 images.`), the row is the only copy, every chat is handed it, it auto-approves. **What is its OWN, and it is the sharpest difference in the family: this payload names FILES where every other one carries its own content.** Nothing is embedded — each entry is a PATH the RENDERER later resolves through the same `GET /v1/chats/:runId/image?path=` route a markdown image already uses, under that route's own guards (extension allowlist, real regular file, canonicalized before the stat, byte ceiling). So it adds no reach an agent did not already have: it could write `![](x.png)` today and the renderer would fetch it identically. What it adds is N at once, which is what `MAX_GALLERY_IMAGES` bounds — a cap on how many file reads ONE call can trigger, rather than on how much a card can readably hold. The daemon never opens any of them, so a path that has since moved costs one broken tile rather than a failed call, and the agent is still told the row landed, which is the only thing the call actually did. Unreadable entries are DROPPED where the chart's cells are blanked, and the two are not inconsistent: a chart is positional, so removing a cell re-attributes every later measurement, while a gallery is a SET and a tile naming no file has nothing to draw. Its line is against MARKDOWN rather than against a sibling tool — ONE picture is a markdown image and reads better inline; this is for a set, and its value is that the reader can step between them. Both halves are pinned in `mcp-server.service.spec.ts`'s description audit.

    **An ARTIFACT is the family's PAGE, and its only revisable row** (`show_artifact` items; `HOST_ARTIFACT_TOOL` in `chat.types.ts`, `v1/mcp/tools/show-artifact/`, `utils/host-artifact.ts` (its permission predicate), `utils/artifact-page.ts`, `services/artifact.broker.ts`, `services/artifact-store.service.ts`). The agent writes one HTML document — its own CSS and script inline, libraries only from the fixed CDNs — and the app shows it beside the conversation, openable full-screen — a layout the agent DESIGNED, with working interaction. What it carries that its siblings cannot is exactly that: each of them draws ONE fixed shape from typed arguments, which is their strength and their ceiling. Two things are its own, and both follow from the payload being CODE rather than data. **It never runs in this app's origin**: the page is written to a file, served by the route above, and framed with `sandbox="allow-scripts"` and NO `allow-same-origin`, so it lands in an opaque origin — no reach into the app's DOM, its storage, or the loopback token the renderer holds — while its own response CSP leaves it no network of its own: scripts, stylesheets and fonts may come from a fixed list of public library CDNs (the root `AGENTS.md` → *Constraints*, third shape), and nothing else — no fetch, no socket, no remote image. What makes those libraries look native is geniro's **page runtime** (`utils/artifact-runtime.ts`), spliced in FRONT of the agent's document because the page's own script calls it: `geniro.chart(el, option)` builds an ECharts chart in the app's palette, Chart.js is themed the moment its UMD build assigns `window.Chart` (an accessor on that global, since a body script builds a chart before DOMContentLoaded), Mermaid, Lucide and highlight.js are themed and drawn on DOMContentLoaded, and a `:where()` component kit (`g-card`, `g-stat`, `g-badge`, `g-table`, `g-kanban`, …) styles a page with zero specificity so the page's own rules always win. The frame wrapper fires `geniro:theme` once it has written the host's tokens, and the runtime re-themes on that event — deduped by the theme's own value, since the host posts the theme on ready, on load and on every switch. Never an `<iframe srcdoc>`: a srcdoc document INHERITS the embedder's policy, and this renderer's is `default-src 'self'` with no `script-src`, so the agent's script would simply never run. **And it is REVISABLE**: the row is addressed by an `artifact_id`, and publishing the same id again supersedes the page with a new version rather than adding a second card — which is what lets an agent open a plan early and keep it current, the whole reason the tool exists rather than a second gallery. The transcript keeps EVERY row (each opens the version it announced, and only the newest opens itself, since every open card frames a live document); the PANEL lists each artifact once, at its current version. Its caps REFUSE rather than truncate, on `propose_patch`'s rule: the first N bytes of an HTML document is not a smaller document, it is a broken one. **A WORKFLOW node publishes pages too** (`GraphExecutorService.registerArtifactPublishers`): the executor registers a publisher per call-capable agent node on every pass and files the row under that node, which is why every such node holds the MCP endpoint rather than callers alone. The publishers are not disposed at a pass's end (a kept process goes on working between passes) and are dropped with the run. The key the route authenticates on is registered with `registerSecret` at its mint site, the rule `CallTokenRegistry.issue()` follows — it rides the item payload, and the debug sink writes a preview of every payload into a log the user is invited to paste into a bug report.

    **A picture the page names is stored WITH the page** (`ArtifactStoreService.preparePage`, `utils/artifact-image-policy.ts`, `utils/artifact-html-images.ts`). A local `<img>` source is read through the one image policy and copied to `images/<sha256>.<ext>`, so the page outlives the original file, and a revision writes nothing for a picture it keeps. A tag that does not close, a `>` inside a quoted value, or any refused picture refuses the whole page, with nothing written. The caps refuse rather than truncate: 10 MB a picture, 64 MB of pictures counted per reference, 64 distinct pictures. `withInlineImages` writes each stored picture back in as a `data:` URI, so no route hands a picture to the page. The scanner is one bounded pass over the tags, not an HTML parser: a `src=` inside another attribute's quoted text is taken for the attribute, which leaves that picture unshown, and the policy still judges the path it names.

    **A PROPOSED PATCH is the family's side effect** (`HOST_PATCH_TOOL` in `chat.types.ts`, `v1/mcp/tools/propose-patch/`, `utils/host-patch.ts` (its permission predicate), `utils/apply-patch.ts`, `services/patch.broker.ts`). The agent proposes a change it has NOT made; the transcript shows the diff with Apply and Reject; geniro writes the file if the user accepts. Three ways it is not like its siblings, each load-bearing. **It PARKS** — and rides an ordinary `approval_request` row carrying `toolName`, exactly as `ask_user_question` does, so the card, the verdict route, the WS gateway and the settle-time sweep all serve it unchanged (its own `outstandingPatches` set exists only so the sweep can say "before the patch was answered" rather than "the question"). **It carries a real gate, and exactly ONE.** The tool CALL auto-approves like its siblings' (the `autoApproves` arm) — calling the tool writes nothing, so a call gate would be a meaningless card before the real one. The write is behind Apply on the diff, and THAT card appears even in `auto` mode: mode governs `autoApproves`, which is the path the CLI's request to call the tool takes, and the proposal card does not go through it. **Its caps REFUSE rather than truncate**: every other cap in this family truncates because a model that found forty things still did the work, but the first N characters of a file body is a TRUNCATED FILE. The arguments are `Edit`'s own names (`file_path`/`old_string`/`new_string`) so the renderer's `editDiffOf` draws the diff with no second diff renderer, and an omitted `old_string` falls through to `Write`'s additions-only shape. `applyHostPatch` is the only place the family touches disk: the write must land inside the run's cwd, as judged by `utils/write-containment.ts` — the one containment check shared with codex's `acceptEdits` auto-accept, so a hardening lands in both. It is lexical AND real-path, because a lexical check alone is satisfied by a symlink sitting inside the folder and pointing anywhere, and it follows the TARGET itself, one component at a time as the kernel does, rather than only its directory: a file that is itself a link out and a dangling link are each an escape a parent-only check waves through. A path is judged under BOTH readings a writer may take — as written, where a `..` after a link steps out of the link's target (`link/..`, `link/./..`, `link/sub/../..`), and resolved first, which is what `path.resolve` and codex's own patch applier do — and `applyHostPatch` hands it the resolved path it actually writes, so a `link/..` that lands inside is written rather than refused. The check is made AGAIN at the moment of the write, because awaits separate it from the write and a background command the agent started can plant a link meanwhile: the file is then opened at its real path with `O_NOFOLLOW` (a link inside the folder is still written through, one planted at the last moment refuses the open), and a file with other hard links is refused, since every containment check reads a hard link as an ordinary file inside (asked of the open file here, and of the path by `hasOtherHardLinks` for a writer that only decides beforehand). Each shape is pinned by a test that goes red on its own. An `oldString` must match **exactly once**: zero means the file moved on, more than one means picking the first is a coin flip on which occurrence the user actually read in the diff. Outcomes are four, and `stale` earns its place — the user said YES and the write still could not happen, so telling the agent "declined" would have it argue when the right move is to re-read the file. Filesystem errors travel as their `code` alone: an `ENOENT` message carries an absolute path, and that string goes to a model whose provider is off this machine.

    **A PROPOSED PLAN is a gate BEFORE the work** (`HOST_PLAN_TOOL` in `chat.types.ts`, `v1/mcp/tools/propose-plan/`, `utils/host-plan.ts` (its permission predicate), `services/plan.broker.ts`). The agent shows how it means to carry a request out — a title and a short ordered list of steps — and the call blocks until the user answers. What that buys is the cheapest correction there is: a plan is redirected in one sentence, while the same misunderstanding found after the edits costs a revert. Structurally it is the patch tool's twin — parks on an ordinary `approval_request` row, its own `outstandingPlans` set so the sweep says "before the plan was answered", `question: false` so the badge reads *waiting for approval*, and the CALL auto-approves because proposing changes nothing. Three things are its own. **Approving performs NO action**, so there is no `stale` arm: nothing can have moved underneath a decision that touches nothing, and the verdict IS the answer. **Both verdicts carry an optional NOTE**, and that is where most of the value is — a bare "no" tells an agent nothing and costs a round trip to ask what the user would rather have, while "no — leave the parser alone, just fix the cap" redirects it in the same press. It rides the `answer` field the approval channel already carries for questions (unconditionally, all the way from the WS `verdict` handler), and it is normalized to absent when blank, so the agent is never handed silence to quote back. `hostPlanResultText` puts the note INSIDE the sentence for the same reason: an approval carrying a caveat must not read as a plain yes, and a refusal carrying a redirection must not read as a wall. **Its caps TRUNCATE**, on the findings tool's rule rather than the patch tool's — a plan that overran is still a plan, and `MAX_PLAN_STEPS` is where one stops being readable at a glance, which is the only thing this card is better at than prose. Deliberately NOT a live to-do list: nothing is ticked off as the agent works, because a checklist is a different feature with its own update channel and pretending this one is that would leave every plan frozen at step one.

    **`notify_user` is the host tool that draws NOTHING: the agent's own notification** (`HOST_NOTIFY_TOOL` in `chat.types.ts`, `v1/mcp/tools/notify-user/`, `utils/host-notify.ts` (its permission predicate), `services/notify.broker.ts`). The renderer announces every finished turn by itself, but one that ends with a background command still running only PROVISIONALLY — the banner says a command is still running and is withdrawn if the run goes back to work — because an agent routinely ends its turn waiting on one and carries on when it reports, and nothing on the CLI's wire separates that wait from an agent that has finished and left a dev server up (`session_state_changed` reports `idle` in both, and the task frames carry only the command; see *System notifications* in `apps/ui/AGENTS.md`). So saying the task is DONE, and what is ready, is the agent's to state, the shape of Claude Code's own `PushNotification`; its banner replaces the plain one. The description says exactly when: finished, with something left running — and NOT when nothing is running (the app already announces that), when pausing on a test run or a build, or for progress. It writes no row: the sink publishes `{status: null, notify}` on the client-wide `run_status` broadcast, because the thread it is about is usually not the one on screen, and the call auto-approves like the render family. Every chat is handed it; no graph node registers one.

    **The DESCRIPTIONS are the routing logic, and are audited as a SET** (`McpServerService — what the descriptions tell a model` in `mcp-server.service.spec.ts`, asserting on the `tools/list` response, which is the text a model actually receives). Near-neighbours share this listing — the render tools, plus the board and history tools, whose writers must also tell themselves apart from the CLI's own checklist tools (`TaskCreate`) — and a model reads them together rather than one at a time, so a description written in isolation (`show_chart` describing the scorecard case without naming `show_metrics`; `propose_patch` omitting its `unavailable` outcome) misroutes. The spec pins: both sides of an overlapping pair name the other; every outcome a description counts is spelled; every drawing tool says ONCE and "do not also"; every tool has a **when**, and every card tool a **when NOT**. **Two of these tools collide with claude's own** — `ReportFindings` and `ExitPlanMode`, the latter REACHABLE since `plan` is one of the `CHAT_APPROVAL_MODES` a chat can run under. So `report_findings` says it is the same job as claude's and asks to be preferred (only this one draws in the app the user is watching), and `propose_plan` says to use either its own plan mode or this, never both, since two approval cards for one plan is a gate answered twice.

    **The rendezvous under every host tool is one base class** (`services/host-sink.broker.ts` → `HostSinkBroker<TSink>`). Every `HostSinkBroker` subclass (`UserQuestionBroker`, `FindingsReportBroker`, `ChartBroker`, `MetricsBroker`, `ComparisonBroker`, `GalleryBroker`, `PatchBroker`, `PlanBroker`, `NotifyBroker`, …) adds only the public verb (`canAsk`/`ask`, `canReport`/`report`, `canDraw`/`draw`), the sentence said when no turn is running, and the sink's signature. The two subtle parts are written exactly once there — the disposer is IDENTITY-CHECKED (settle paths run late and out of order, so a keyed `unregister` would tear down the sink a LATER turn of the same run had installed) and `deliver` NEVER throws (an undeliverable call is an outcome the agent carries on from; a throw crosses MCP as a tool error and reads to the model as its own call being malformed). The logger is `new Logger(this.constructor.name)`, so a failure still names which tool failed.

### Question cards

**A question CARD outlives the CALL that raised it, because the caller's deadline is 60 seconds** (`StandingHostQuestion` in `chat.types.ts`; the protocol itself in `utils/standing-questions.ts` — a per-turn `StandingQuestions` owning the map and its four transitions, OPEN / ADOPT / DETACH / CLOSE, with `ChatService` keeping the persistence and the registry. It is its own module so those transitions can be driven directly: the case that matters is two agent calls racing over one card, including ADOPT settling the resolver it displaces). An MCP client puts a hard wall-clock deadline on every `tools/call`, and `ask_user_question` is the one host tool that waits on a PERSON. Nothing can move it from this side: cursor-agent calls the SDK's `callTool({name, arguments})` with no `RequestOptions` at all, so the SDK default stands and `resetTimeoutOnProgress` is false, meaning progress notifications would not extend it either. (claude's own client is configurable — its bundle documents a per-server `timeout` in the MCP config and `MCP_TOOL_TIMEOUT` — but claude is never offered this tool, having its own.)

Closing the card when the client gives up would make the deadline the USER's — a card carrying two questions cannot be answered inside a minute. So the card belongs to the TURN and the call is only a collection channel: an abandoned call is DETACHED (its promise released so the turn's bookkeeping is not left waiting) while the row, the registry entry and the badge stand. A re-ask carrying the IDENTICAL title and questions ADOPTS that card rather than raising a second, disconnected one, and the tool description says so in as many words, pinned by the description audit. An answer given while no call is in flight is HELD and handed to the next ask at once, so the user's own answer is never thrown away for having arrived a moment late. A REWORDED question is a new card, which is the honest reading: the person is being asked something else.

**For a CLI whose client will not hold a call open, the answer is to stop blocking on the call at all** (`AdapterConfig.hostQuestionDeferredReason`, `ChatService`'s deferred-card block beside `announceAwaiting`, `Run.pendingQuestion`). The standing card survives the CALL; it does not survive the TURN, and the turn is what the agent ends when it gives up after the deadline — leaving the user a minute to notice, switch apps and answer.

So for such a CLI, `ask_user_question` **answers `posted` at once** and the agent is told to stop and wait (`POSTED_QUESTION_RESULT`); the card stands until it is answered, and the answer reaches the agent as the run's NEXT message. No polling, no retry loop, no clock. A polling shape (return before the deadline, have the model call again) was rejected by the user: an LLM request every minute to wait for a human is the cost this removes. Do not reintroduce it.

Which CLI does which is an adapter fact, and the reason field says why (cursor: no `RequestOptions`, `resetTimeoutOnProgress` false, no timeout field on the ACP HTTP server entry or in `~/.cursor/mcp.json`, no `MCP_*TIMEOUT*` env var). claude declares null — its ceiling is geniro's own to set and is a day — so the blocking machinery above is its arm and is pinned as such (`holdsCallsOpen` in `chat.service.spec.ts`, since claude is never handed this tool and no harness adapter would otherwise reach that path).

Four properties replace what a parked promise would hold. The card **outlives the turn**: `ApprovalRegistry.sweepNode` skips a `deferred` entry, since every other pending card is a parked call while this one has none by construction. It is **retired when a new turn supersedes it** (`sweepDeferred` → an `unanswerable` row), because the user typing something else means the agent has moved on. Answering it **starts a turn** rather than resolving anything, and the verdict row and the cleared column are written BEFORE that message goes out, or the answer's own turn would write the card off as superseded. And there is **one per run**, durably (`Run.pendingQuestion`, re-tracked by `rehydrateDeferredQuestions` from `main.ts`) — which is not belt-and-braces but the common case: a deferred card leaves no turn in flight, so `IdleShutdownLifecycle` exits the daemon ten minutes after the last window closes, long before somebody who meant to answer later comes back. A second, DIFFERENT question while one stands is refused rather than stacked; an identical re-ask answers `posted` again without raising anything.

Not taken for `ask_user_question`: cursor's own `cursor/ask_question` (beside `cursor/create_plan` and `cursor/generate_image`), whose ACP request has no deadline — its reply is `answers[{questionId, selectedOptionIds}]`, option ids only, so a typed answer cannot travel it and the card has a text field.

### Pull requests and task lists

**Which pull requests a thread OPENED is read out of its own transcript** (`Run.pullRequests` + `pullRequestsScannedSeq`; `utils/pull-request-capture.ts`, `services/pull-request-capture.service.ts`, called from `ChatService.listChats`). Never key it by the branch the run's folder has checked out — that MISSES a thread that moved the checkout back or worked in sibling repositories (`cd ../mobile-app && gh pr create`), and LIES by presenting whatever somebody else opened on that branch as this thread's work.

The signal is the CREATION, which is the only thing that identifies a pull request as this conversation's: a `tool_result` carrying a `…/pull/<n>` URL whose paired `tool_call` ran `gh pr create`. Everything about that pairing is load-bearing. A URL ALONE is not evidence — `gh pr view` puts one in a tool result too, and that pull request belongs to whoever opened it, which is the branch query's own mistake reached from the other side. `\d+` in the pattern is what excludes `…/pull/new/<branch>`, the hint `git push` prints in the SAME result as the real URL. And the command is matched against the whole serialized tool input rather than a named field, so it stays one rule across every transport's tool shapes (`.claude/rules/agent-adapters.md`).

The pass is INCREMENTAL and its marker is what makes the backfill free: `pullRequestsScannedSeq` null means "never scanned", so the first listing reads the whole transcript once — no migration. After that each pass reads `seq > marker`, which the `(run_id, seq)` index serves directly, so a settled conversation costs one `max(seq)` read however long it is. The marker ADVANCES even when nothing was captured, or a conversation with no pull requests would be re-read from the beginning forever. It runs inside the chat list, so every error is logged and swallowed per run: one unreadable transcript costs that thread its pull-request row and never the listing.

**"Ran `gh pr create`" is decided by WHERE the words stand, and "printed the URL" by the URL standing ALONE on its line** (`runsPullRequestCreate`, `PULL_REQUEST_URL_LINE`). Never a substring match: a `grep -n 'gh pr create\|pull/5639' file` uses the marker as a search PATTERN and its output can quote another thread's URL mid-line. So the marker has to sit where a shell would execute it (the start of a string, after `;`/`&&`/`|`/`(`/`{`/a newline, inside a named shell's `-c` argument, or after a wrapper's `--`), and a URL counts only as the whole of a trimmed line, which is the one shape `gh pr create` prints. **The words that only LEAD UP to a command are walked back over** (`COMMAND_PREFIX_WORDS`, `ASSIGNMENT_WORD`, `PREFIX_ARGUMENT`): an assignment (`GH_REPO=o/r gh pr create`), a body keyword (`then`, `do`), a wrapper that runs its argument (`time`, `env`, `timeout 60`, `xargs -I{}`), and `gh` named by its path — without the walk-back, each of those shapes opens real pull requests no chip shows. A word that TAKES the marker as its arguments (`echo -n gh pr create`) still stops the walk. The capture is incremental and there is deliberately no sweep to re-read already-scanned rows (a one-time reset was built and removed under the no-migrations rule). **A result's text is read whatever shape the CLI gave it** (`resultText`): claude's is a string, while cursor's ACP `execute` answers `{exitCode, stdout, stderr}`.

What is stored is the IDENTITY only — owner, repo, number, url. No title and no state: those change on GitHub's side after the capture, and a copy here would be a stale second answer beside the live one the UI reads with `gh`. The URL is also self-sufficient (`gh pr view <url>` resolves from any working directory), which is what makes a multi-repository thread answerable at all — geniro cannot know where the agent was standing, since it `cd`s inside its own shell commands.

**The agent's OWN task list is a transcript row, not a tool call** (`task_list` items; `AgentEvent`'s `task_list`, `adapters/claude/utils/claude-tasks.utils.ts`, `adapters/cursor-acp/utils/cursor-todos.utils.ts`, the agent-agnostic `AcpTodoProtocol` seam in `acp-driver.ts`). Every shipped CLI keeps a checklist while it works a multi-step job, and its tool rows alone do not show it (cursor's `Update TODOs` row discloses NO arguments: `rawInput:{_toolName:"updateTodos"}`). **`mode` is the load-bearing field**: some shapes on the wire are PATCHES naming only the rows that moved (claude's `TaskUpdate` sends `{taskId,status}` and no text at all; cursor's `merge:true` frames), so a consumer reading any announcement as the whole list loses tasks. It is never inferred from the contents — a patch that happens to name every row is indistinguishable from a snapshot — the CLI says which it sent, and cursor says so literally. Absent, it reads as a patch: the direction that leaves a stale row rather than deleting every task it did not name. **Claude's half is read off BOTH directions of a tool call**, which the CLI forces rather than geniro choosing it: a created task's id exists only in the result (`Task #1 created successfully: …`), an update's status only in the input, and `TaskList`'s result is the one place the whole list is stated — so the result parsers match the CLI's own anchored sentences, a `tool_result` block carrying `tool_use_id` and no tool name. There is no pull channel to ask instead: the task-shaped control subtypes answer other questions (`background_tasks` takes a `tool_use_id`, `get_plan` returns the plan-mode file), and `system/background_tasks_changed` goes to the CLI's remote-control bridge, never stdout. **Cursor's half is the vendor extension `cursor/update_todos`**, handled through the agent-agnostic seam (so another CLI's channel is a config rather than a branch) rather than declined via `CURSOR_SILENTLY_DECLINED_METHODS`. Baseline ACP's `plan`/`plan_update` updates are NOT what either agent sends. The event carries the producing `toolCallId` so the renderer shows the list INSTEAD of that opaque row, and it is a DURABLE row rather than a live signal because the list is only ever the fold of its announcements — a reopened chat has to replay them all. The run row's fold (`utils/task-list-fold.ts` → `RunTaskGroup`) is keyed by node AND by `callId` (read off the payload, where the executor tags a callee sub-turn's rows): a node called several times keeps one checklist per call, each numbering from 1 (keyed by node alone, one call's task `1` patches over another's). A row stored before the key existed reads as the node's own conversation. A delegate's list is its own: the announcement carries whatever origin its line carried, so the MAPPING knows nothing about sub-agents — and the run-row FOLD does, deliberately (`utils/task-list-fold.ts` skips a row stamped `parentToolUseId`): it is keyed per node and per call, and a delegate carries its launcher's ids, so its task `1` would otherwise rename and complete the agent's own in the list the side panel draws and the transcript's cards take their titles from. (claude does not currently hand task tools to a delegate, so that path is unexercised on the wire.)

What `v1/agents` exports to the graphs module is whatever `agents.module.ts`'s own `exports` array currently names — read that array rather than a hand-kept list.

A `call_agent` on the SYNC arm has no deadline and cancels nothing (a request that goes away ends only the reply, leaving the result await-collectable) — so without it a wedged callee leaves the caller waiting with nothing saying so. Bounded by SILENCE rather than duration (an agent turn legitimately runs for many minutes), re-armed by every callee row through `noteCalleeActivity` — which the EXECUTOR calls at its own callee persist seam, the only place a callee's output is visible from — and it writes ONE `system` row per call carrying `stalledCall: true`, `severity: 'info'` and its sentence under `message` (the key `transcript-item.tsx` reads; any other key persists a row that renders nothing). It is SUSPENDED while the callee has a tool call of its own in flight (`ActiveCall.openToolCalls`, fed by `noteCalleeToolStarted` / `noteCalleeToolFinished` at the same executor seam), and restarts when the last one answers (a callee waiting on its own `Task` sub-agents is silent, not wedged). Cleared on the settle AND in `unregisterRun`, and `announceStall` re-reads `this.runs` rather than a captured state, because a wedged callee is exactly what makes the delete's own settle wait time out — two independent guards against the orphan-row write `Item.runId`'s missing foreign key would otherwise make permanent. **A callee's kept process is keyed by its CONVERSATION, not by its call** — `<runId>::call:<first call id>`, which every `thread:` continuation shares — so a continuation is handed to the process that already holds the conversation, and `--resume` spawns a fresh one only once that process is gone; the broker refuses a continuation while a call on that conversation is live (`THREAD_BUSY`), which is what keeps the registry's one-turn-per-key premise true (otherwise several `claude -p --resume <same id>` children edit one worktree at once). Two things follow from one process serving several calls. The process's CLOSER closes the stranded delegates of EVERY call it served (`callsBySessionKey`), not only the latest one, and it is installed AFTER `startTurn` — a kept process that cannot serve the turn is replaced inside that call and its close fires synchronously, so a closer installed first is consumed by the replacement. And the registry's off-turn sink is REBOUND on every turn (`SessionEntry.offTurn`) — bound once at spawn, it would file a later call's off-turn work under the first call. **A parked question's 30-minute TTL is SUSPENDED while its OWNER is blocked** (`noteCallerBlocked` / `noteCallerUnblocked`, called from the executor's approval seam beside the callee twin): a caller inside its own AskUserQuestion cannot `answer_agent`; the callee's silence watchdog stands down while it is parked, for the same reason. An owner's blockers are a SET of named cards (`<sessionKey>#<request id>`), not a count, because spawn-cli re-offers a request its turn settled without an answer to the next turn of the same process (a count would need two answers for one card). And any node can be an owner: a callee turn's card blocks that node too, and a callee PARKED on its own caller is a blocker of the calls it owns (`parkBlocker`, released on every way out of the park through `unpark`) — Manager → Engineer → Researcher, where an Engineer waiting on its Manager cannot answer its Researcher either. **Call state survives a daemon restart through the transcript** (`v1/agents/utils/call-seed.ts` → `RunCallSeed`, folded by the follow-up path from `ItemDao.callRecordRows`; it lives in agents because the context readout reads it too, and agents never imports graphs): call ids continue past the highest one already persisted instead of re-minting `call-1` over the old rows, every settled call is a thread again with the session its `call_result` recorded (conversations rebuilt through the `thread` parents), and an `UNKNOWN_CALL` for an id from before the restart says so and names the thread that survives; `capabilities` — composes `GET /v1/capabilities` from the adapter-owned probes AND each adapter's own `configDir.unavailableReason` and `handoffTarget` verdict, iterating the adapter registry rather than naming CLIs, and owning only the wire shape), `controllers/` (`workflows` + `capabilities` — thin routes delegating to their services; the MCP endpoint that serves the call tools is `v1/mcp/`, below), `dto/`. The **call runtime**: a claude caller node gets `call_agent`/`await_agent` over a loopback MCP endpoint delivered as a per-turn `--mcp-config` file (the token rides the 0600 file, never argv), and a cursor caller gets the same endpoint in its ACP `session/new` frame (an HTTP header inside a stdin frame — never argv, never a file in the user's worktree). Every adapter hands its own CLI the endpoint, so **having outgoing call edges is the whole admission predicate** — there is no per-machine capability gate that can shut a caller out (a cursor trust probe, a `.cursor/mcp.json` merge and a `cursorCalls` capability field were removed; do not reintroduce them). **The Q&A bridge (M4)**: a call-initiated callee's AskUserQuestion parks in the broker and returns to the CALLER as a `{status:'question', call_id, question, options}` envelope — the caller answers via `answer_agent(call_id, answer)` (delivered as `control_response` with `updatedInput.response`) or escalates to the user through its own question card, then collects the final result with `await_agent`. Because headless claude strips AskUserQuestion under `--dangerously-skip-permissions` (the tool is wired by the presence of a permission-prompt CHANNEL, `--permission-prompt-tool stdio`, which the bypass removes), question-capable claude turns — call-initiated callees AND caller nodes — spawn in the CLI's ask mode with the DAEMON auto-approving plain permission requests at the executor seam (unattended semantics preserved; an explicit `approval: 'ask'` node keeps the human card for permissions); the `requires_user_interaction` flag + tool name discriminate questions from permissions, and DAG-scheduled questions keep the card path (answerable: the WS `verdict` payload carries an optional `answer` that rides `updatedInput.answers` for a lone question and `updatedInput.response` for several — `withResponse` owns that choice, so no caller picks a field). Transcript kinds `call_question`/`call_answer` record the exchange under the caller's node. **A question reaches a BUSY caller too**: parked while the caller is blocked waiting on a DIFFERENT call of its own, it diverts that wait (the envelope carries `still_running: <the awaited call>`, which stays await-collectable); parked while the caller waits on nothing, it is handed to the next wait the caller starts (once — `envelopeDelivered`), and — only for a CLI whose follow-up joins the turn rather than interrupting it (`AdapterConfig.followUp.interrupts`) — pushed into the running turn through `RunCallCapability.tellLiveNode`. A wait that timed out or was abandoned releases its waiter, or it would swallow the next question. **A USER message releases a caller's waits too** (`CallBroker.interruptWaits`, called by the executor after it delivers a follow-up into a running turn, or a message into a running call's callee): claude takes a mid-turn message only at the next tool boundary, and an `await_agent` or sync `call_agent` is one tool call lasting as long as the callee. The wait answers `pending` with `interrupted: 'user_message'` and a note, consuming nothing. A message delivered while no wait is open is remembered (`unreadUserMessages`) so the next wait returns at once, until the CLI reports it consumed (`user_message_consumed`) or the node's turn ends. Not for a CLI whose follow-up interrupts (cursor): its new prompt already replaces the one waiting. **Callers are steered to ASYNC calls.** `call_agent`, its `mode` and `await_agent` descriptions, and the "May call" block say to prefer async, keep working or end the turn, and expect to be started again (a CALLEE is told its call stays open meanwhile — see *A call waits for the calls its callee made*): the broker already wakes a caller whose call finishes or asks after its turn ended (`wakePrompt`, recorded by `wakeNotice` as a system row whose `wake` field names the calls — the renderer draws it as a divider linking to their cards), the geniro counterpart of a CLI's background-task notification. The default mode stays `sync` for an agent that names none. **A caller that fanned out can wait on ALL of its calls at once**: `await_agent` with no `call_id` (`CallBroker.awaitAny`) answers at once with an unseen question or an uncollected result, else races one waiter per open call and returns the FIRST question or finished result, stamped with its `call_id` (an error envelope gains a root `call_id` for this), leaving the rest collectable; a `timeout_ms` answers `pending` with `waiting_on` listing every open call. **No wait is unbounded over the endpoint**: an omitted `timeout_ms` is `DEFAULT_AWAIT_TIMEOUT_MS` (the 240s ceiling), because the caller's HTTP client cuts a request that has received nothing for five minutes and hands the model `The operation timed out.`. The call tools also REFUSE an argument they do not read rather than ignoring it (a guessed `timeout_seconds` would otherwise be an unbounded wait), and carry `ALWAYS_LOADED_TOOL_META` so claude never defers their schemas (a compaction can unload a deferred schema, leaving the model guessing argument names). A question is returned once — a wait whose waiter took a question but lost the race puts it back unseen. Known limit of the in-turn push: a message that lands while a scheduled node is writing its final answer (or held for delegates) can become that node's output for downstream nodes. A cursor callee CAN raise a question, over the vendor extension `cursor/ask_question` (baseline ACP has no open-ended question call). It must never be declined (`-32601`): cursor's handler then replays each single-select question as a bare `session/request_permission` with options as `allow_once` entries, which `auto` would approve — answering the user's question with option #1 and no human involved. The lifecycle (park the JSON-RPC id → surface an `approval_request` → answer with the adapter's encoder) lives in the agent-agnostic driver; the method name, the params shape and the reply shape are values the adapter injects as an `AcpQuestionProtocol`, so a second agent's channel is a config, not a branch. The contract is transcribed from the CLI's own source (`ask-question-handler.ts`), which is why `allowMultiple` is answerable here and not through cursor's fallback. Two guards remain: a payload that does not read as a question falls through to the old decline, and a free-text answer naming no offered option is sent as `skipped` with the text as its `reason` rather than as an invented `selectedOptionIds`. Whether a CLI's question channel COSTS the ask posture is its own adapter fact (`questionsCostAskPosture`) — true for claude, false for cursor, since an ACP request arrives whatever session mode the agent is in, so an unattended cursor node stays on `auto` instead of parking every permission on a verdict nobody is there to give.

- `v1/stats/` — **what the app has spent, and the ledger that remembers it.** `usage_events` is an append-only table carrying one row per finished turn (its token counts, cost and timings, plus the agent / model / folder DENORMALIZED at write time). It stores nothing new — every figure is already inside a `turn_complete` payload, or the `error` payload of a turn that failed after spending (`USAGE_ITEM_KINDS`) — what it changes is the LIFETIME: `RunTeardownService` hard-deletes a run's `items`, so a lifetime total computed from the transcript shrinks whenever a user tidies a chat away, and the dimensions are copied rather than joined because the rows holding them are destroyed with the run. The one row that is NOT a turn is a POLLED-spend CLI's bill (cursor today): that bill exists only as a figure the account reports (see `polled-spend.service.ts`), stored on the run and node rows a delete destroys, so each priced run also keeps its own ledger rows — ONE PER LOCAL DAY AND MODEL the account billed it under (`Run.polledSpendBuckets`, summed from the nodes' per-event ledgers; `polledSpendRows`), keyed `(runId, seq ≤ POLLED_SPEND_SEQ = -1)` and replaced as a SET whenever the poll announces a new total (`spendUpdatedAt`) — its agent the run's own for a chat, or for a workflow the CLI of the node holding the largest polled share (`polledAgentKind`). A run priced before buckets were kept still carries one undated-model row. A run's unpriced turns are credited to its FIRST row only, so cost per turn does not divide one bill by the same turns once per row. A boot sweep seeds or repairs them. Stats reads polled spend from that row alone and never from `runs`, so a live run is not counted twice and a deleted one keeps its bill. Ledger writes are native inserts rather than a flush, because flushing a fork that has loaded runs re-stamps their `updated_at`. The module OBSERVES the agent plane and never drives it, exactly as `v1/diagnostics/` does: it subscribes to `AgentEventBus`, which is where both execution paths converge on the one `persistItemAndEmit`, so a chat turn and a graph node are covered by the same subscription and nothing in `v1/agents` imports `v1/stats`. The dependency is one-way, NOT zero: the sweep added `ItemDao.allUsageRows` and `Item`'s `kind` index, and both exist for this module alone. A boot sweep (`services/usage-backfill.service.ts`) seeds history from existing rows and repairs the one gap the subscriber cannot — a daemon that dies between the item write and the ledger write — and is safe to run every launch because a turn is keyed by `(runId, seq)` with a unique index behind it. **What the threads did is a sibling ledger, `usage_activity`** (`UsageActivityDao`), kept beside `usage_events` for the same lifetime reason: a thread's creation, the pull requests it opened, and cumulative snapshots of its own changes. One table, three kinds, and a `dedupKey` that refuses a second thread or pull request row. The daemon cannot count lines, because every git call belongs to the Electron main process, so the desktop app measures a FOLDER after each finished or settled turn of a thread working in it, and posts the total (`POST /v1/stats/line-snapshots`). Lines are counted PER FOLDER, not per thread, so threads sharing one checkout do not count one edit once each. A repository and branch is measured against ONE baseline commit, `line_baselines` (`LineBaselineDao`, keyed by `folderKeyOf(root, branch)`), set the first time any of its threads is measured — that thread's start commit — and fetched through `POST /v1/stats/line-baselines`. The ROOT is the repository top level the client read, honoured only when it is a plain absolute path containing the thread's own folder — compared without case, since macOS paths are case-insensitive, while the key keeps git's own spelling (`measuredFolder`, else the thread's folder): the totals cover the whole repository, so a thread in a subfolder and one at the root are one series. A snapshot names its baseline, branch and root and is filed under `lineKeyOf(root, branch, baseSha)`; a row written before baselines existed is its thread's own series (`snapshotLineKey` → `run:<runId>`). A baseline the folder has left (a rewritten history, a checkout no longer descending from it) is reported stale by the client once, and replaced with the asking thread's start commit by a conditional update, so two windows reporting it together replace it once. A day's lines are the growth past the highest total its series had reached (`linesIncrements`, against `peakLinesBefore` for a period's baseline), never a delta a client sent: a total that falls back and rises again counts its lines once. The agents module announces the facts it creates on `AgentEventBus` (`RunCreatedEvent`, `PullRequestsCapturedEvent`) and this module records them, because `v1/stats` imports `v1/agents` and not the reverse. A boot sweep (`UsageBackfillService.backfillActivity`, started behind the boot rather than awaited by it, since it reads every run on every launch) fills the same two kinds for history — a thread per run, a pull request per capture the run row holds, each dated by its own transcript row (or by the run's creation when that row is gone) — under the same `dedupKey`s, so a repeat sweep writes nothing. Line history cannot be backfilled: a thread's first measurement counts every change it has made so far, on the day it was taken. The activity fold lives in `utils/activity-fold.ts`. The SPEND fold is NOT here: `emptyTotals`/`addUsage`/`usageFiguresFrom` live in `v1/agents/utils/usage-figures.ts`, shared with the per-chat metrics panel, because two copies of the null-means-not-measured rule is how the panel and the page come to disagree about the same turns.
  **A claude turn's cost is a STEP of the session's running total, and the base of that step must survive a restart** (`ClaudeSessionCostLedger`, `utils/claude-cost-totals.utils.ts` → `<userData>/claude-session-costs.json`, `utils/claude-cost-state.utils.ts`). `result.total_cost_usd` is the session's cumulative figure, and a gracefully ending process appends a `cost-state` line to the transcript that `--resume` restores. The ledger subtracts the last total it saw, and keeps the totals on disk — in memory only, a daemon restart bills the first result of every resumed process whole (a `/compact` reports no tokens, so the token-priced guard cannot bound it). A session the ledger has never seen (an imported terminal conversation) is seeded from the transcript's last `cost-state` when argv is built for its process (`seedForResume`): a session the ledger does not know, or knows ABOVE the restored total (the previous process was killed before writing one), starts from the restored total; one it knows at or below it keeps its own figure, which also bills what the previous process spent after its last result (a stopped turn, background sub-agents); one that restores nothing starts from zero. A step off that known base that did not go DOWN is trusted whole — the token-priced clip is kept only for an unknown base or a total that dropped (two processes on one session), because it would cut legitimate background sub-agent spend.

  **A turn its CLI does not price is priced at LIST price, from a public catalog rather than a table here** (`services/model-price-catalog.service.ts` → `ModelPriceCatalog`, the pure half in `utils/model-prices.ts`). codex prices nothing on its wire. The catalog is models.dev's `api.json` (an allowed outbound-call shape under the root `AGENTS.md`'s *Constraints*), held in memory, persisted to `<userData>/model-prices.json` and loaded from it at boot, refreshed at most every 12h behind the boot; lookups are SYNCHRONOUS and exact-id. Which catalog provider a CLI's models are priced under is an adapter fact (`AdapterConfig.usage.listPrice` — claude `anthropic`, codex `openai`, cursor `unavailable`, since its bill is read from the account), read by the base's `listPriceOf`, and handed in through `AdapterDaemonDeps.prices`. codex bills a turn's token DELTA: `uncached × input + cached × cache_read + cache-write × cache_write + output × output` (reasoning is a share of output on that wire and is not added again; cache reads AND writes are details of its input), at the context tier the turn's LAST prompt fell in — an approximation that can only over-bill a turn that crossed the tier mid-way (`turnUsageOf`). claude's own turn cost is the CLI's `total_cost_usd`; the catalog (never a hand-written price table) backs its DELEGATE calibration (`ClaudeDelegateCostLedger`), where a model the catalog does not list prices to null. No price ⇒ `costUsd: null`, never $0.
- `v1/projects/` and `v1/tasks/` — **the tasks board's storage, and the services that act on it.** A `Project` carries the standing answers for the work done on its board — a DEFAULT folder, the run configuration, and the autopilot policy (`autopilotEnabled`, `autopilotIntakeStatus`, `autopilotMaxConcurrent` — accepted by `createProjectSchema` / `updateProjectSchema`, written by `ProjectsService`, read by `ProjectQueueService` and `TaskQueueService`; only `autopilotFailureStreak` is server-owned, reset through `POST /v1/projects/:projectId/rearm`); a `Task` is one card, with a status, labels, a source, a folder of its OWN and its branch / worktree / run / report links. **`Task.folder` is the default overridden, and null means INHERIT rather than "none"** — one board routinely holds work across several checkouts. The split also refuses a WORKFLOW-targeted card while the autopilot is armed (`resolveRunTarget`'s `workflow-unattended`): a workflow carries `approval` per node, so there is no single field to force the way an agent run's is forced, and a node that asks would park an unattended run forever. Asked as a USER on a disarmed board, so a project nobody is auto-running does not report its whole intake column as unstartable. Both are plain CRUD over `BaseDao` with no relations and no cascades, so `ProjectsService.remove` deletes a project's tasks itself. The two modules need each other's DAO — a project delete removes tasks, a task create checks its project exists — which is a cycle; it runs one way only, `TasksModule` importing `ProjectsModule` while `ProjectsModule` PROVIDES `TaskDao` rather than importing back, on the reading `RunGroupsService`'s own doc block records for the same trap. `Task.position` orders a column and is allocated past the column's live maximum (`TaskDao.nextPositionIn`), never from its count: a soft-deleted card keeps its position but leaves the count, so counting hands a live card's slot out twice. It is unique within a column and not contiguous: a new card or a move takes the column's live maximum + 1, and only `POST /v1/tasks/reorder` renumbers — `0..n-1` over exactly the cards a drag names, each written by a conditional UPDATE on its status (`TaskDao.setPositionIfInStatus`), so a card moved to another column mid-reorder keeps the position its move gave it; a drag on one project's board leaves other projects' cards alone, while a drag on the every-project board sends — and so renumbers — the whole mixed column, its ties settled by creation order. **Label instructions** (`label_instructions`, `LabelInstructionsService`) are text attached to a label, globally (`projectId` null) or for one project: every task run composes the rows matching its card's labels, followed by the report ask, into `Run.taskInstructions` (`TaskRunsService.composeTaskInstructions`), every row sent whole with no length limit, like the executor's instruction blocks, and a project delete removes its own rows (`ProjectsModule` provides `LabelInstructionDao` on `TaskDao`'s terms). That is a column of its own rather than a join into `customInstructions`, for two reasons: `POST /v1/chats/forget-custom-instructions` purges the USER's text and must not take a card's label block and report ask with it, and a card continued in its existing thread RE-RESOLVES its label rows and rewrites the column before the continuation is sent (`TaskRunsService.resume`, through the same `ChatService.updateSettings` patch as the card's other settings — the key is absent from the HTTP settings DTO), so an instruction edited, added or removed since the first press reaches it; changed text respawns the thread's kept CLI process, which `AgentAdapter.sessionKey` hashes. The turn still reads the user's own text first, then the card's, because `composeTurnInstructions` ranks `taskInstructions` directly after `customInstructions`. The run↔task edge has TWO ends — `Task.runId` and `Run.taskId`, the latter a plain nullable id mirroring `groupId` with no FK — and they are written together or not at all: `TaskRunsService.abandon` deletes the run it created as it clears the card, because a chat naming a card that does not name it back is the disagreement nothing here is allowed to leave. `TaskRunsService` starts an agent on a card, and it starts an ordinary CHAT rather than a second execution path — `ChatService` called with a worktree as its cwd, which is why this module imports `AgentsModule` and never the reverse (the same direction `GraphsModule` already takes). It runs no git at all: the worktree and the branch arrive already made from the Electron main process, since every git call this app makes belongs there. `TaskSettleService` is the other half and it OBSERVES rather than drives — an `AgentEventBus` subscriber on `v1/stats`' reading, so one subscription covers every way a run can settle and nothing in `v1/agents` learns that tasks exist. **A run COMPLETING moves nothing and writes no report — the agent does both, through the board tools.** **The board tools (`HOST_BOARD_TOOLS`: `list_projects`, `board_vocabulary`, `list_tasks`, `get_task`, `create_task`, `update_task`) are served to EVERY agent holding the MCP endpoint** — every chat and every call-capable workflow node, not only a run working a card — so an ordinary chat can file a ticket without reading `daemon.json` and curling the REST API. The tasks module owns all of it: `utils/board-tools.ts` writes the names, descriptions and JSON schemas (every column and priority with its meaning, every bound and default, the INHERIT rule for the run-configuration fields, and the AUTOPILOT hazard — a card landing in an armed project's intake column starts an agent within ~20s, so new cards default to `backlog`), and `TaskBoardToolService` answers them, installed behind `graphs/services/task-board.broker.ts` because `GraphsModule` may not import this module; the MCP host lists whatever the broker offers and dispatches by name. Machine-owned values (labels in use and which carry instructions, workflows, CLIs with their approval modes, a CLI's models and efforts, config directories in use) come from `board_vocabulary` (`TaskBoardVocabularyService`); saved config PROFILES live in Electron's `settings.json`, which the daemon never opens, so only directories already recorded on projects and cards are listed. Every write goes through `TasksService` (validation by the HTTP DTOs' own `createTaskSchema` / `updateTaskSchema`, the status compare-and-set, the `task_changed` broadcast); the run-owned fields are refused by name and there is no delete tool. The chat permission gate auto-approves them (`isHostBoardCall`) — a card is on the board in front of the user and one click to undo — with the exceptions enforced by the board itself, since the gate sees only a tool name: anything that hands an agent's own text to UNATTENDED work is refused to any chat not already running in `auto` (`refuseUnattended`) — on a board whose autopilot is ARMED, putting a card in its intake or changing ANY existing card (a working card returns to the intake by itself when its run is interrupted or deleted, and the autopilot then starts it as it stands with `auto` approval, so a column check is not enough; only the run working a card may still write its report and move it to a non-intake column), setting a card's `approval` to `auto`, and changing an EXISTING card's run configuration at all (folder, agent, model, effort, approval, config directory, workflow) — which agent and approval a person's next Run press uses is decided as much by inheritance as by the value sent (clearing a card's own `ask` under an `auto` project, or dropping its workflow, raises it without naming `auto`), so the whole set is refused rather than resolved case by case. A NEW card merely inheriting an `auto` project's approval is the user's own policy and allowed. It is keyed on the column the card ENDS UP in rather than on a move, since guarding only the move leaves an edit-in-place bypass; an open failure breaker does not exempt the intake, since it only delays the start. Without it an agent in an `ask` or `plan` chat could hand text of its own to an ungated agent with no card in between. A workflow node's board calls follow that node's own approval mode — the executor auto-approves no host tool. An answer that put a card in an armed intake says so. A run that WORKS a card keeps its defaults: `get_task` / `update_task` target that card when no `task` is named, and it may move it only to `TASK_AGENT_OWN_STATUSES`. `update_task` writes `Task.report` (markdown, stored ON the card with `reportedAt`, so it outlives the thread) and moves the card through `moveStatus`, report first; an agent may pick `in_progress`, `in_review`, `done` or `failed`, never the intake columns the autopilot hands out. Never automate it from the settle (`completed` → `in_review`, a report read out of the transcript): a thread's last message is whatever the agent happened to say last, and a run ending is not the task being finished. The instructions (`utils/task-prompt.ts`) name the tool and what each column means. What the settle still does is what an agent cannot do for itself: `failed` → `failed` (a dead process calls no tool) and `cancelled` → back to `todo` (a user stopping their own agent did not fail at anything). The report may reference SCREENSHOTS as markdown images with absolute paths — the instructions ask for them in the report AND in the agent's chat message, since the card and the thread are each read on their own and "either" let an agent show the pictures on the card alone (`utils/task-prompt.ts` → `REPORT_SCREENSHOTS`); `update_task` COPIES each one the REPORT names onto the card's files (`utils/report-images.ts`, `TaskAttachmentService.adopt`) and points the report at the copy (`rewriteReportImages`) — a copy, unlike every user-attached file, because an agent's screenshot lives in a scratch directory that is routinely reaped; one that cannot be copied is named in the tool's receipt and never costs the report. A path that already IS one of the card's own copies is kept as it is (a report read back with `get_task` and re-sent must not attach every picture again, into the 20-file cap), the rewrite replaces the image DESTINATION by position rather than the first matching text (which can be the alt text, and must not expand `$&` in a file name), and a copy path holding spaces is written in `<…>` form — the data directory is under `Application Support`, and a bare destination with a space is not an image. That return to `todo` is also the autopilot's INTAKE, so while a project is armed `TaskQueueService` reports a card whose last run was CANCELLED as blocked rather than handing it out (`STOPPED_BY_USER_REASON`, off `ProjectQueueRaw.stoppedTaskIds`) — otherwise the timer restarts a card the user just stopped and re-sends its brief into the same thread. The stop is a mark on the CARD (`Task.stoppedAt`, stamped by the cancel settle), not a reading of the run's CURRENT status: a user who stops a card and then carries its thread on themselves turns that run `running` and then `completed`, and a status check would hand the card straight back out (`continuation()` re-sending the whole brief). Only a Run press that actually STARTS the card clears the mark, the start route refuses an autopilot start on a marked card (`TASK_STOPPED_BY_USER`), and an intake card whose run is still LIVE is never handed out at all. The live path and the app-was-closed reconcile are ONE piece of code, reading the run ROW's status. A card is moved only while it still reads `in_progress`: the run is an ordinary chat, so a follow-up message after review settles it again, and a card the agent or the user already moved must stay where they put it — which is also why a failure is counted against the autopilot's breaker only on a card that was being worked, while a success clears the streak whatever column the agent had already moved the card to. A card that IS in `done` when its run settles is instead announced as FINISHED (the `work-finished` reason on `task_changed`), which is what lets the board collect its worktree — and an ordinary settle announces no such thing, since a card in review is a conversation the user is still having in that directory. The one card that rule would strand is lifted back out: a card in `failed` whose SAME run announces `running` again goes back to `in_progress` (`reviveFailedCard`), because a run that errored is routinely carried on in the chat itself — which never passes through `TaskRunsService`, the path that moves a card when the panel's Follow up is pressed. Only `failed` is lifted; a card in review is being continued deliberately. It also LETS GO: `run_deleted` is a run's own teardown announcement, and a task's run is an ordinary chat that can be deleted from the chat sidebar like any other — so `TaskSettleService` subscribes and clears the edge on the card holding it, sending one that was being WORKED back to `todo` and keeping its report, which is the card's own rather than a pointer into the deleted transcript (otherwise the card sits in `in_progress` for good with Run disabled, since the button asks the RUN); the worktree is deliberately untouched, since the branch and the directory outlive the conversation and the agent's work is in them.

**An interrupted card is continued only when the app stopped on purpose** (`utils/stop-cause.ts`, twinned with the UI's `writeStopCause` in `daemon-pidfile.ts`). The boot reconcile cannot tell a quit from a crash by itself — both leave a turn `running` — so Electron main writes one word to `<userData>/daemon-stop-cause` right before every signal it sends the daemon (`quit` from `before-quit`, `self-update` when an update's relaunch is that quit, `restart` from a Settings restart or a stale-build replacement) — only for a daemon it has seen serving, since one still booting has not read the previous note yet — and `crash` when it respawns a serving daemon that left a crash mark, and `main.ts` reads and deletes it once, before both reconciles. Those reconciles run before `TaskSettleService` subscribes to the bus, so `main.ts` then settles every board's cut-off cards itself (`settleCutOffCards(null)`), rather than leaving them `in_progress` until a board is opened. No note is `unknown` (a SIGKILL, an OOM kill, a power cut). The cause rides the `interrupted` error row as `interruptCause` and names the sentence (`run interrupted — the daemon crashed while this turn was running`). `TaskSettleService` sends every interrupted card back to the intake column, and for `crash` and `unknown` also marks it stopped (`Task.stoppedAt` + `Task.interruptedBy`), so the armed autopilot leaves it to a person with the reason on the board (`interruptedReason`) and the start route refuses an autopilot start (`TASK_INTERRUPTED`), until a Run press clears both; `quit`, `self-update` and `restart` continue unattended. The agent may have been halfway through an edit after a crash, and re-sending the brief over what it left is the duplicate work this guards. A row written before the cause existed reads as `unknown`.
- `v1/handoff/` — **handing a conversation to the user**. A live PTY mirror (`TerminalSessionsService`, a `/terminals` Socket.IO namespace, `TurnMirrorService`, the daemon's `node-pty` dependency) was built and removed — do not reintroduce it: an open `claude --resume` TUI does not grow while another process writes the session, and **two interactive CLIs on one session do not see each other either**. (The SHELL app carries its own node-pty for the unrelated in-app terminal panel, see `apps/ui/AGENTS.md` → *Terminal panel*.) The CLI is started when the button is pressed and renders the conversation as it stands then. So the daemon RESOLVES and never RUNS — `HandoffService` maps a run (or one workflow node, or one call thread) to `AgentAdapter.handoffTarget`, telling it whether geniro's own kept process may still hold the conversation (`mayHold`, read off the session registry — which a CLI allowing one process per conversation needs, see `handoff.heldFlag` and the `codex/` bullet), and the Electron main process opens the user's terminal with it (`main/open-terminal.ts` writes a 0700 `.command` script and `open`s it, so LaunchServices routes it to whatever the user set as their terminal — there is no macOS API for a default terminal, only that file association). `utils/shell-line.ts` renders the SAME invocation as one pasteable line, which the button shows on hover with a copy control, so a terminal geniro cannot launch (a remote host, an open tmux pane) is never a dead end. ONE route, and one thing: sign-in (`/login`, `/logout`, `/mcp-login`) belongs to `v1/auth`, which allocates a pty itself. Layout: `handoff.module.ts` + `handoff.types.ts` at the root, then `services/`, `controllers/`, `dto/`, `utils/`.

### Importing CLI conversations

**Finding one of those conversations is a question for the DAEMON, not a filter over its answer** (`AgentSessionsInput.query`, `AdapterConfig.sessions.contentSearchUnavailableReason`, `adapters/utils/session-search.utils.ts`). A client-side filter can only match the fields a row DISPLAYS, and a claude row's title is the conversation's opening prompt (often a bare `/command <url>`). Every adapter must apply the query ITSELF — the shared matcher over title+cwd is agent-agnostic, and what differs is whether there is anything more to read — or a search would silently widen back to the whole list on whichever CLI forgot. claude reads its own JSONL and answers with a `snippet`, the line that matched, WINDOWED on the term (never truncated from the start, which can cut the match out); cursor declares `contentSearchUnavailableReason`, since `session/list` takes no search parameter and its transcripts are behind `session/load`, one spawn per conversation. The search is bounded twice and SAYS so through the listing's own dynamic `partialReason` — `CLAUDE_SESSION_SEARCH_FILE_LIMIT` (newest files) and `CLAUDE_SESSION_SEARCH_BUDGET_BYTES` (per file) — the per-file budget is large on purpose, because the long sessions are the ones worth searching. Only what was SAID is searched (user and assistant text): a session's tool inputs and outputs are most of its bytes, so including them makes ordinary words match nearly every conversation. The CLI's own injected envelopes (e.g. a `<task-notification>` carrying tool-use ids) are excluded by the same reader the titles use.

**Taking over a conversation the user already had** (`AgentAdapter.listSessions` / `prepareSessionImport` / `readSessionHistory`, composed by `CliSessionsService`, offered by the sidebar's own control beside `+`). The ask was to continue an existing terminal session inside the app rather than start blank, and the CLIs answer it through completely different mechanisms — which is the whole reason it is three adapter methods and not one. (codex is the third mechanism: `thread/list` for the listing and `thread/read` for the transcript, each a one-shot `codex app-server`; its threads live in its own home and resume by id, so nothing is copied. Its own search matches a thread's title and opening message only, so the query is matched here, over title and folder, and `sessions.contentSearchUnavailableReason` says so.)

**claude is READ off disk.** Every conversation it has ever held is `<configDir>/projects/<flattened cwd>/<sessionId>.jsonl`, one append-only file per session **in exactly the envelope its `-p --output-format stream-json` writes to stdout** — so the import needs no protocol at all, and an imported row is built by `mapClaudeMessage`, the same mapper a live turn's rows come from, rather than by a second reader that could disagree with it about what a message is. Nothing has to be moved for the resume: `--resume <id>` finds it in the profile the run already carries. Scale is what shapes the reader — a real profile can hold thousands of sessions across gigabytes, with individual sessions many megabytes each — so the listing stats every candidate and opens each only as far as its first user message rather than reading any of them whole. Two rules in it: the folder filter compares **canonicalized** paths, because the CLI records `cwd` as its process saw it (`/private/var/…`) while this app canonicalizes every folder it holds (`/var/…`); and a turn that is nothing but slash-command envelopes is re-rendered as `/name args` rather than shown as markup or dropped, since dropping it leaves a session whose every turn is a command with no name at all.

**cursor is ASKED over ACP, and its sessions must be brought across.** `session/list` is a real protocol method this agent advertises and answers with `{sessionId, cwd, title, updatedAt}` — including a title the AGENT generated, which no disk scan could produce. It is **profile-scoped, not a global index** (a fresh empty config dir answers with zero rows), so the listing is taken under a throwaway profile linked at the USER's `acp-sessions` while geniro's turns run against its own store — which is why importing one is a **copy** (not found before it, loads and replays its whole transcript after). The transcript comes back the same way: `session/load` streams the entire prior conversation as `session/update` notifications before it replies, so `readSessionHistory` spawns that handshake and reads the replay. Reading it at CREATION rather than on the thread's first turn is what keeps the order right — a turn's replay arrives after the user's new message is already persisted, which would file the imported history BELOW the message that continued it.

What this CLI cannot offer is stated rather than left as a short list: `sessions.listingPartialReason` says that only ACP sessions are listed, because the chats started by the interactive `cursor-agent` live in `~/.cursor/chats/` — a separate namespace the same server answers `Session … not found` for. Without the reason a user whose terminal history is all in that store reads a correct short list as a broken feature.

Two rules the daemon side follows. The import is **prepared before the run row exists**, so a refusal leaves no half-made thread and the user gets the CLI's own sentence instead of a chat whose first message dies on a session nobody can find. And the happy path writes **no system row at all**: the transcript is its own evidence that the import worked, so only what the transcript cannot show by itself earns a line — history left out, or a record that could not be read (`severity: 'info'`, never the failure chrome every other daemon notice wears).

### ACP and cursor transport

**The cursor transport (ACP)** — every cursor turn runs under its **own throwaway `CURSOR_CONFIG_DIR`**, seeded with a copy of the user's `cli-config.json` and nothing else (`adapters/cursor-acp/utils/cursor-profile.utils.ts`, materialized by `prepareTurn` and swept at boot). Not hygiene — a correctness rule: applying a model or an effort over ACP PERSISTS into that directory (`session/set_config_option` rewrites `model`, `selectedModel` and `modelSelectionHistory` in `cli-config.json`), so sharing the user's directory would change what their own `cursor-agent` opens with. The copy keeps their permissions and default model, and their approval mode on an `auto` turn alone: every other turn writes `approvalMode: "allowlist"` and `autoAcceptWebSearch: false` over it (`CursorProfileSeed.askForApprovals`), because under the user's own `unrestricted` the CLI runs tools with no `session/request_permission`, and with web-search auto-accept on it searches with none, so geniro never shows a card; a profile that cannot be written that way fails the turn. The mode is read once per process, so whether a turn asks is part of cursor's `sessionKey`: switching a chat between `auto` and `ask`/`plan`, either way, respawns its process (and stops what it started in the background). `mcp.json` is deliberately NOT copied or symlinked — it is 0600 and holds their own server credentials, and it is unnecessary: the CLI resolves that file from the user's home either way. A handshake under a fresh directory costs no extra latency. The model listing takes its own profile for the same reason (a parameterized handshake can migrate a persisted variant selection, which writes). **The one thing that must NOT be per turn is the CONVERSATION**: the CLI keeps each ACP thread at `<configDir>/acp-sessions/<sessionId>/` — inside the directory the disposer removes — so a per-turn store makes every second message's `session/load` answer `-32602 Invalid params {"message":"Session … not found"}`. So that ONE name is a symlink to `<userData>/cursor-sessions`, shared by every turn, while the settings the isolation exists for stay per turn (the CLI writes the store THROUGH the link, and `node:fs` `rm -r` unlinks the symlink rather than descending into it). The store is deliberately NOT nested inside `cursor-profiles`, which the boot sweep removes wholesale. A `session/load` the agent REFUSES is a degrade rather than a dead end — a `notice` naming the loss and a fresh `session/new`, because every later turn resumes the same id, so a hard failure would make the chat unusable for good (`'session_load'` is a pending kind of its own in `acp-driver.ts` for exactly this).

**ACP instruction delivery** — on ACP the WHOLE composed instruction block is sent once per SESSION, never once per turn: prompt text is part of the conversation there, so a block one turn carries stays in the window for every turn after it. `AcpTurnDriver.composePrompt` sends the block only when its TEXT differs from `AcpSession.deliveredInstructions`, which the two ways a session can already hold a block keep current: a prompt WRITTEN on this kept process records what it carried, and a successful `session/load` reads the newest `<host-context>` block back out of the replay (`readHostContext` — cursor-agent replays each prior user message whole as one `user_message_chunk`, read in its own `replayAgentTurn`). Compared as text rather than flagged, so a block that CHANGED — a call surface this process was not granted, forgotten custom instructions, re-resolved label instructions — is still delivered and supersedes the older one; a replay that cannot be parsed, or a refused load that fell back to `session/new`, re-sends. A `/compact` needs nothing: this CLI's compaction replaces the session, and a fresh session holds nothing. claude needs none of this — its block rides `--append-system-prompt`, outside the conversation, and a turn's stdin carries only the user's words.

**The CONTEXT WINDOW is a per-model parameter, and picking one is a real setting rather than a label.** It rides the same `configOptions` machinery the effort chip uses (`context`, category `model_config`, `CURSOR_CONTEXT_WINDOW_PARAMETER_ID`), so it is stored per run (`Run.contextWindow`), per workflow node and per saved run configuration, and it reaches the turn through `cursorModelSelection` (which also applies a `context=` pair carried inside a legacy composed id). It is per MODEL: only some models have the axis and their values differ (`300k|1m`, `272k|1m`, `200k|1m`). The numbers are never mapped here — `1m` is the CLI's own word, and what it produces is read back out of that CLI's own accounting, which is what the meter draws. And the frame must be AWAITED: this CLI binds the window when the turn BEGINS, so a frame pipelined with the prompt leaves the turn on the model's default while the agent still reports `context = 1m`. Hence `AcpModelParameter.applyBeforePrompt`, which the driver honours by holding the prompt (and releasing it on a refusal, so a turn is never stranded behind a setting that could not land). It is set on this axis alone: the effort axis is not known to bind at turn start, and the hold costs latency per turn.

**The model and parameter frames go out ONE AT A TIME, each after the reply to the one before** (`AcpTurnDriver.configSteps`). Never pipeline them: cursor runs each `session/set_config_option` as its own async read-modify-write of the model's WHOLE parameter list, so frames in flight together overwrite each other with stale lists (the CLI logs `Invalid parameter combination for <model>; falling back to default variant`). The prompt still follows the LAST frame straight down the pipe unless a parameter asks to be in force first, so the added cost is one round-trip per frame beyond the first. Two things follow from waiting: a parameter is resolved and checked against the MODEL frame's own reply (the new model's option list) rather than the session reply describing the model being switched away from, and a model the agent REFUSES drops the parameters queued behind it, on the rule the local refusal already followed.

**Max Mode is the user's own switch, defaulting ON, and it is the whole of the second context axis.** Models without the `context` parameter take their window from **Max Mode**, a top-level boolean in `cli-config.json` (`CURSOR_MAX_MODE_CONFIG_KEY`), and geniro writes it explicitly on every turn (`CursorProfileSeed.maxMode`), from the `maxMode` switch cursor declares in `AdapterConfig.options` → `Settings.agentOptions['cursor-agent']` → the wire (`agentOptions`) → `Run.agentOptions` → `AgentTurnInput.agentOptions` (read with `agentOption(input, CURSOR_MAX_MODE_OPTION)`), falling back to the option's own default (`CURSOR_MAX_MODE`, true) for a turn that says nothing. It travels the `customInstructions` road exactly — the client sends it because settings live in the Electron process, and it is SNAPSHOTTED onto the run, so flipping the switch changes the next chat rather than moving an open conversation between a 200k and a 1M window mid-thread. A NULL column reads as the DEFAULT, never as OFF — reading absence as a decline would quietly shrink every such run's window. It can only ever widen, which is why ON is the default — a model that HAS the `context` parameter obeys the parameter and ignores the flag, and a model that has neither is unchanged. So every model runs at the largest window it has, the choice where there is one stays the CLI's own answer read from its own handshake, and geniro holds no table of anybody's context sizes. Written EXPLICITLY, ON and OFF alike, rather than inherited: the per-turn profile is a copy of the user's own config, so an untouched key means "however their terminal was last left". What it COSTS is why there is a switch at all: on some Cursor plans Max Mode bills at a premium, and which plan a user is on is not something this app can read.

### Auto-compaction

**AUTO-COMPACTION is asked of the CLI where it HAS a control, and performed by the daemon between turns where it does not.** A chat run carries `autoCompactPercent` (10–95, `AutoCompactPercentSchema`; null = never) and a workflow node carries its own; both rules read that one number.

**The native route on claude is `--autocompact`** (`AdapterConfig.autoCompact`, `AgentAdapter.autoCompactArgs`, `AgentTurnInput.autoCompact`). Not `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, which changes nothing a driven session does. `--autocompact <auto|tokens>` is a documented flag ("Auto-compact window size", 100k–1M, with `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and the `autoCompactWindow` setting as its env and user twins). It names a WINDOW, and the CLI compacts a fixed 33k short of it — its `/context` calls that reserve the "Autocompact buffer" — so geniro asks for `threshold + buffer` and the compaction lands on the percent the user chose, mid-turn (`compact_boundary` with `trigger: "auto"`). `modelUsage.contextWindow` still reports the model's real 200,000, so the meter and the between-turn arithmetic below are untouched by the flag.

**Why that matters more than tidiness: geniro's own rule can only ever fire at a turn BOUNDARY, and one turn can cross the threshold and keep going.** A long turn can climb far past the threshold without ever ENDING above it, and nothing here can run in between: `/compact` is itself a turn and the CLI is busy. So where a CLI can hold the threshold itself, it is handed the threshold; where it cannot, the between-turn rule is all there is and that limit stands.

The window handed over is the CONVERSATION's own last reading — live plane first, then the row (`ChatService.turnAutoCompact`; the executor keeps the per-node twin in `nodeWindows`, fed from the same two sites that write `nodeStateDao.rememberContext`) — the same pair the between-turn rule judges on, so the two can never disagree about how full the window is. It is null until some turn has reported one, so a conversation's FIRST turn runs unflagged and the between-turn rule covers it — the executor seeds `nodeWindows` from `node_state` at every pass (`RunContext.nodeWindows`), since every user message starts a pass and a map filled only in memory would leave nearly every root-node turn unflagged; the value joins `AgentAdapter.sessionKey`, because on a kept process the window is learned from the turn that just settled and a threshold that never reached argv would otherwise silently never apply. A window smaller than the CLI's own floor costs the flag rather than the turn — argv outside 100k–1M is refused before the turn starts.

**cursor has no such control** (`cursor-acp`'s `autoCompact: {kind: 'unavailable'}`): its `--help` names no compaction or context-window flag, and ACP's `session/new` has no field for one. So a cursor conversation keeps the between-turn rule as its only threshold, with the limit above.

**The between-turn rule itself** (`utils/auto-compact.ts`, `ChatService.autoCompactIfDue`) is what every CLI falls back on. Its mechanism is the one a user already has — `AgentAdapter.geniroCommandFor('/compact')`, claude's in-place compaction and cursor's summary-and-carry — and there is no per-CLI branch. With the flag in play it becomes a no-op in practice rather than a second compaction: the CLI compacts mid-turn, so the reading at the settle is far below the threshold. The check runs after a turn SETTLES `completed` (off the finalizer, once its claim is released) and after an off-turn continuation settles `completed`, against `RunContextRegistry` falling back to the run row; it sends `/compact` through `sendMessage` exactly as if typed, and only once that has taken the run writes the `info` row naming the reading — a message the user sent first simply wins the claim, and no row announces a compaction that never ran. Three guards keep it from costing more than it reclaims. A geniro-command turn never re-arms it. While one runs, `sendMessage` refuses every follow-up `RUN_BUSY` (`compactingRuns`) instead of delivering it: on a `replacesSession` CLI a follow-up interrupts the summary prompt, and its reply would be committed as the summary. That flag holds a per-turn token and is cleared only by the turn that set it, because the registry frees the run before the finalizer finishes and the next compaction can claim it in between. And the first context READING after a compaction records a BASELINE (`compactionBaselines`, taken in `rememberContext` whether or not a threshold is set; the workflow twin takes the next turn's opening reading, `NodeTurnResult.firstTokens`): nothing compacts again until the conversation regrows past it by `AUTO_COMPACT_REGROWTH_FRACTION` of the window, since a threshold below what a fresh conversation already holds would otherwise buy a paid `/compact` after every turn. The baseline is the FIRST reading after the compaction, never a later settle's (which measures what a whole turn grew to), and it is taken even with no threshold set, so switching one on later judges from the right base. **A carried compaction also RETIRES the kept process** (`AgentSessionRegistry.retire`). Clearing the session id is not enough on a kept process: `AcpSession.openTurn` opens a later turn on the session it already holds, so the summary would be sent into the very conversation it replaced. A mark rather than a close, so what the process started in the background runs on until the conversation is actually continued.

**WORKFLOW agent nodes auto-compact too** (`WorkflowAgentNode.autoCompactPercent`, `GraphExecutorService`'s `compactIfDue`), and WHEN is the whole design. Never compact before a node is RESUMED (a callee called again, a follow-up, a wake) — that races every resume path. A node compacts RIGHT AFTER the turn that filled it, inside the unit that still owns its session key, at the three places a node's turn ends (`launchNode`, `launchCalleeTurn`, `continueNode`): between `handle.done` and the settle, so nothing else can open a turn on that key meanwhile — a callee's call is still active (`THREAD_BUSY`), and a node's turn is still retained and unsettled. The cost is deliberate and was the user's pick: a sync caller's result, and a DAG node's downstream, wait for the compaction. Four details carry it: It is NEVER run inside `enqueue`: the compaction's own events are enqueued, so awaiting them from a queued callback would wait forever. A follow-up to a compacting root is refused `RUN_BUSY` (`compactingNodes`) rather than delivered into it. A WAKE needs no guard: the retained turn makes the broker read the caller as live, and the wake `drainCaller` issues at the settle is queued behind that settle. And the run's cancel reaches the compaction (`compactionHandles`). For a CLI whose compaction replaces the session (cursor) the summary is kept per SESSION KEY (`carriedSummaries`), the key is retired, and the next turn on that key opens without resuming and with the summary prepended — in memory only, so a daemon restart before that turn leaves the node resuming its old, intact session, merely uncompacted. Baselines are per session key as well, so a node's own conversation and each call conversation are judged apart.

**On a CLI with no in-turn control, the BETWEEN-TURN threshold governs turn boundaries only**, and a turn that crosses it mid-flight is caught by that CLI's own compaction if it has one. Never write a `/compact` into a RUNNING turn's stdin — that interrupts a working agent (the user chose to keep compaction at turn boundaries).

### cursor context, streaming and failures

**Do not rebuild learned Max Mode window sizes.** Two invented picker rows (`standard` / `max mode`) whose SIZES were learned from turns and overlaid onto the listing were built and removed: Max Mode is a MODE rather than a context window, and a learned size is wrong from the moment the vendor changes a number. The capability has no answer on this transport — `supports_max_mode`, `context_token_limit` and `context_token_limit_for_max_mode` live on the CLI's own server model message, a `session/new` reply carries `modes`/`models`/`configOptions` with `{modelId, name}` model entries and nothing more, no model table is cached on disk, and `maxModeAutoEnabled` is the CLI's own bookkeeping for models whose catalog entry says `requiresMaxMode` (setting it by hand changes nothing). Always-on sidesteps the question.

**`ContextWindowStore`'s key carries the window CHOICE as a third component** — without it a chat at `context=300k` and one at `1m` on the same model share an entry and overwrite each other's figure. And the ACP transport ANNOUNCES its model (`AcpSession.currentModelId` → a `turn_model` event), so a cursor chat can scale its meter before a turn COMPLETES and the cross-run window cache — which files a measurement under the model that reported it — can be written from this transport, cursor's session store naming no model. The id is the agent's OWN (`models.currentModelId` from the session reply), replaced by the one the agent CONFIRMS on its `set_model` reply — never by the one a turn merely requested, which `turn_model` announces instead. The two must stay separable because `rememberWindow`'s anti-poisoning guard compares exactly them: with the requested id written into the session field, both operands are the same value and a refused model's window is cached under the requested one. The offers check cannot stand in for the reply — it reads the vocabulary the agent ENUMERATED, and a refusal is reachable past it. `buildUsage`'s `contextModel` falls back to it and keeps its existing guard — a model id is a label ON a denominator, never a name offered with nothing being measured.

**That session store is also where this CLI's context accounting lives** (`utils/cursor-context-store.utils.ts`), and reading it is the whole reason a cursor chat can show a breakdown at all. Over ACP the agent says NOTHING about its window (no usage in any `sessionUpdate` or in the `{"stopReason":"end_turn"}` reply; the "context"-shaped keys are `embeddedContext`). The figures are off-protocol: the CLI writes a full breakdown per turn into `<sessionId>/store.db`, which is what its own TUI renders, and geniro already owns that directory because the per-turn profile symlinks into it. So this needs no new access, only a parser: `meta` holds one hex-JSON header carrying `latestRootBlobId`, `blobs` is content-addressed, and the root blob is protobuf — `{1: used, 2: window, 3: repeated {1: key, 2: label, 3: tokens, 4: chars}}`. Three things keep it honest. It is opened READ-ONLY through node's OWN `node:sqlite` (this file has nothing to do with geniro's ORM, and the built-in costs neither a dependency nor a rebuild against Electron's ABI) — geniro owns the directory but not the format, and nothing may write to another program's store. The block is found BY SHAPE rather than by field number, walking the message tree for rows of (string, string, varint), so a vendor adding a field still parses. And the arithmetic is re-checked rather than trusted: the categories must sum EXACTLY to the stated total, which rejects a different block whose rows merely look alike — a genuinely changed encoding then yields null and no breakdown, never a number read out of unrelated bytes. Never ESTIMATE from the transcript instead: the window is dominated by tool and skill listings a transcript cannot see, so an estimate is wrong by orders of magnitude. The header also carries an unused `blobEncryptionKey`, the most likely way this stops working — and it stops by returning null. **The same reading feeds the meter's RING, and it has to reach the durable row to do it.** The reading is taken at the turn's two BOUNDARIES (at the session reply, so a resumed chat is scaled before its prompt goes out, and again just ahead of `turn_complete`) and published as `context_progress` — the ephemeral live plane, which the client drops the moment the run settles, so it alone would leave the ring blank between turns. `AcpTurnDriver` therefore KEEPS the last reading and `buildUsage` writes it into the turn's own `turn_complete` (`contextTokens`, `contextWindowTokens`, and the model only where there is a window for it to label), which is the durable half every other CLI's ring is drawn from. The wire's own `usage_update.used` still outranks it — a figure the agent SENT beats one read out of its files — while `inputTokens`, which measures one request rather than the window, ranks below both.

**A THIRD reading moment, taken WHILE the turn runs, is what a first turn depends on** (`CONTEXT_REREAD_MS` in `acp-driver.ts`). Both boundaries above are useless to a conversation the agent has never held: `session/new` writes no store at all — a brand-new chat's directory holds `meta.json` and nothing else — while the store IS rewritten several times within a turn (`latestRootBlobId` moves). So an ordinary `session/update` notification also takes a reading, floored at two seconds and published only when the figure has MOVED — the read is cheap, but each new figure is a socket emission to every client watching the run, and a turn streams its answer a word at a time. Notifications are the carrier because a turn that is working always has them; during a `session/load` replay `sessionId` is not yet set, so the mid-turn reading cannot fire against the previous turn's figures.

**A message CAN be handed to a running cursor turn — and doing it INTERRUPTS** (`TurnDriver.sendFollowUp`, `AcpTurnDriver.latestPromptId`, `AdapterConfig.followUp.interrupts`). The ACP SPEC suggests one `session/prompt` per turn, but cursor ACCEPTS a second against a live session (the binary, not the spec, decides — see `.claude/rules/agent-adapters.md`). It does not ADD to the prompt in flight, it REPLACES it — the first answers `{"stopReason":"cancelled"}`, the second runs to `end_turn`, and the agent still holds the conversation. So the channel exists and what differs from claude is WHAT A PRESS COSTS, which is its own config field rather than a shared sentence: claude's message joins the turn and is picked up at the next tool boundary, cursor's drops the tool call in flight. The renderer says which BEFORE the press, there being nothing to undo after it. **The frame is the DRIVER's, not the adapter's** — it needs the session id and has to be recorded to make sense of the reply — hence a second delivery hook (`CliTurnOptions.sendFollowUp`) beside `buildFollowUpPayload`, taking the same settle guard and preferred over it; a driver that writes for itself also keeps the existing "unregister a frame whose write failed" path, so an unwritten frame cannot leave the turn waiting on a reply that never comes. **The message STOPS the running prompt first, and is sent only once the agent confirms** (`session/cancel` → the stopped prompt's reply → the new `session/prompt`; `AcpTurnDriver.interruptedPromptId`). Never send the second prompt straight away: a prompt that was itself sent to interrupt another can never be stopped — not by the next prompt, not by `session/cancel`, so Stop is dead too — and runs on to `end_turn` beside the prompt that replaced it, every step done twice. Three things ride the wait: a message arriving while the cancel is in flight JOINS the waiting one rather than interrupting a prompt not yet sent; every request still parked is answered `cancelled` as the protocol requires and withdrawn (`approval_withdrawn`), since the agent drops it anyway and its card would be left on screen with nothing behind a verdict; and every tool call still open when the confirmation lands is closed as interrupted (`INTERRUPTED_TOOL_RESULT`) — nothing new has been sent by then, so everything open was the stopped prompt's, and the agent aborts those calls without a word. The wait is bounded (`INTERRUPT_ACK_DEADLINE_MS`): past it the message goes out anyway with a warning row, and the stopped prompt's late reply settles nothing, matched by id rather than by counting what is outstanding. A Stop pressed during the wait ends the turn on that reply and sends nothing. The interrupted output survives as its own transcript row, and the run settles once. Known limit: that row is filed BELOW the message that interrupted it, because a turn's events persist through a serialized chain while the follow-up reserves its seq directly — closing that needs an ordering seam on the turn handle.

**A CLI that DISCLOSES its thinking streams it live, and cursor does** (`AgentEvent.reasoning_delta`, `PartialStreamService.reasoning`, `RunDeltaEvent.thinkingText`). The driver buffers an `agent_thought_chunk` into the block it will close later (`appendPending`) and also emits it live, so a pure reasoning stretch is never silent on the wire. It is a SECOND channel rather than a widened `thinking_progress`, because the two are alternatives decided by the CLI: headless claude redacts the block and can only ever report a token COUNT, cursor sends the words and reports no count. Both open the same stretch (`isReasoning` asks about either, or a chunk after the token path would open a second one), both are EPHEMERAL — `mapEventToItem` answers null and the durable `reasoning` row is the same words — and words WINNING over thinking is what keeps them from racing for one row. It also joins `RESUMES_A_HELD_TURN` and `restatusAfterOffTurnSignal` on the same terms as its two siblings: it cannot arrive without the model having authored something. The renderer draws the streaming words (`thinkingTokens: null` beside them) in the bubble the durable row becomes.

**A model WRITING a tool call is the live plane's third channel, and the only one that could see the longest silence in a turn** (`AgentEvent`'s `tool_compose`, `mapClaudeStreamEvent`, `PartialStreamService.composing`, `RunDeltaEvent.composingTool` / `.composingBytes`). `text_delta` covers the agent talking and `thinking_progress` / `reasoning_delta` cover it thinking; between them sits a stretch where it is doing neither — serializing a tool's arguments, with nothing reaching the transcript until the whole call has been written. For a `Bash` that is milliseconds. For a host tool whose ARGUMENT is the deliverable (`show_artifact` carries a whole HTML document) it is minutes, and the renderer hides the raw tool row by design. Under `--include-partial-messages` the wire carries one `content_block_start` with `{type:'tool_use', name}`, many small `input_json_delta` frames, then `content_block_stop`. Three things keep it cheap and honest. The NAME is the load-bearing half — a client uses it to decide whether the wait is worth drawing a card skeleton for — while the ARGUMENTS never cross this wire, only their BYTE COUNT, which is why `input_json_delta`'s text is still dropped exactly as it always was. The count is published in STEPS (`COMPOSE_PUBLISH_STEP`), since those frames are a few bytes each and a large artifact would otherwise be thousands of socket broadcasts; the published figure therefore LAGS by less than one step. And a DELEGATE's frames are dropped in the mapper rather than downstream, because this drives a placeholder in the MAIN thread's transcript. It is EPHEMERAL like its two siblings (`mapEventToItem` answers null), it joins `RESUMES_A_HELD_TURN` (the model cannot be serializing a call it did not just decide to make), it ends an open reasoning stretch the way words arriving do, and it is cleared by the CLI's own `content_block_stop`, by words, by `retire` and by the turn boundary. CHAT ONLY today: `streamPartials` is `ChatService`'s, so a workflow node's nodes get no composing signal — the loader simply does not appear there.

**A failure this CLI reports about ITSELF settles the turn as one** (`AcpAgentFailureProtocol` in `acp/acp-driver.ts`, read by `cursor-acp/utils/cursor-agent-failure.utils.ts`). `cursor-agent` catches its own transport failure (e.g. `Error: RetriableError: [unavailable] PING timed out`), writes the sentence out as an ordinary `agent_message_chunk` and answers `stopReason: "end_turn"` regardless — its `handlePrompt` returns `end_turn` on every path that is not a cancel, so there is no protocol field to read. What IS readable is that the chunks are the CLI's own literals: `` `\n\nError: ${String(e)}` `` where `String(e)` names one of four error CLASSES (`RetriableError`/`NonRetriableError`/`ActionRequiredError`/`CancelledError`, each a `get kind()` getter in `index.js`), one hardcoded `Error: [unauthenticated] …`, and four fixed `ActionRequiredError` sentences. Requiring BOTH anchors — the chunk-opening prefix AND a class name — is what keeps it off an agent WRITING about an error, which is the commonest thing a coding agent does; the four bare English sentences are matched as the WHOLE chunk for the same reason, and that arm's own `e.message` fallback is deliberately not matched at all. The turn then settles on an `error` **instead of** its `turn_complete` (not as well as, or the run settles twice and the success badge goes back), the words the agent produced before it died are still flushed as a row, and the failure never reaches `finalText` — a downstream graph node must not be handed the transport error as this node's answer. The recognition is the ADAPTER's, as one predicate over one chunk, so an agent whose failures reach the protocol declares nothing and is untouched.

**A failure that is only a DROPPED CONNECTION is resumed rather than reported** (`AcpAgentFailureProtocol.resume`, cursor's `CURSOR_TRANSIENT_FAILURE_PATTERN`). A failure such as `RetriableError: [canceled] http/2 stream closed with error code CANCEL (0x8)` is not geniro misusing the CLI: its interactive client runs a user message with `enableAgentRetries` (reconnect and resume from the last checkpoint), while its ACP server calls the same `agentClient.run` without it (its debug log, `$TMPDIR/cursor-agent-logs-<uid>/`, says `decision=THROW RetriableError … enableAgentRetries:false`). So the driver answers a transient failure with a continuation prompt on the same session, at most three times per turn, with one `info` notice each time and the raw sentence in the debug log; a server answer such as `[internal] Input token limit exceeded` is not transient and still ends the turn.

**What the failed request left open is closed, and a sub-agent it was waiting on is ADOPTED rather than relaunched** (`AcpTurnDriver.settleCutOffToolCalls`, `AcpSession.adoptCutOffDelegate`, `AcpResumeContext`, `cursor-acp/utils/cursor-transient-resume.utils.ts`). When the ACP parent's run throws it writes `Error: …` and answers `end_turn` with NO `tool_call_update` for anything still open; a sub-agent's context is cancelled only by an abort or a user cancel, never by the parent's stream failing (and it retries its OWN stream — `enableAgentRetries` is off only for the ACP parent); and the conversation a resumed prompt continues is the server's last checkpoint, so results that came back after the agent's last step are gone. Telling the agent its delegates were stopped makes it relaunch work that is still running or already done. So on a failed request: every open tool call is closed as `CUT_OFF_TOOL_RESULT` — what ACP's v2 draft asks of the agent and what Zed does as a client — EXCEPT a delegation that can be watched, which is closed the way a background launch is (its call answered, its block left `backgroundOpen`) and from then on is a background delegate of this turn: its record says when it ends, the turn HOLDS for it after the resumed prompt, and the wake hands the agent its report. Its brief comes off the call's own input (`AcpDelegateProtocol.readLaunchInput`) because a delegate the call waits on is announced only as it returns, and its launch time is recorded for EVERY delegation (`noteDelegateLaunch`) so its transcript is matched by the born-after-launch rule. The resume prompt is BUILT per attempt from that (`resume.prompt(context)`): the adopted delegates by name with "do NOT launch these again", and the reports of delegates that finished after the agent last spoke or thought (`unconsumedDelegates` — a step is generated from the results before it, so speaking or thinking clears the set; a step of tool calls alone does not, which errs toward re-sending a report), read off their transcripts during the pause.

**A sub-agent runs as a SESSION of its own when the agent can run it that way** (`acp/acp-subagents.ts`, `AcpTurnDriver.onSubagentFrame` / `onChildUpdate`, `AcpDelegateProtocol.subagentToolCallId`, `CURSOR_ACP_CLIENT_META.subagents`). This is the first draft of ACP's unstable "Subagent Sessions" RFD, which cursor-agent speaks once the client declares `clientCapabilities._meta.subagents` — `_meta` and nowhere else, because the ACP SDK it bundles parses `initialize` with a zod object that drops unknown top-level keys (the reply then carries `sessionCapabilities.subagents: {}`). On the wire: a `subagent_spawned` on the parent whose `_meta.cursor.toolCallId` is the `task` call's own id, every step of the sub-agent — its thinking, its messages, its tool calls and their output — as ordinary `session/update`s under the sub-agent's own session id, and one `subagent_state_update` (`completed` / `failed` / `cancelled` / `disconnected`) the moment it ends. Five things follow. **Routing**: an update under an ANNOUNCED child's id is drawn inside its delegate's block — every event carries the launching call as `parentToolUseId`, the field claude's delegates already use, so the renderer, the tool counts and the held-turn rules need nothing new — and only an announced id is routed: the driver has never matched an update's session id, and an id nothing announced is still the parent's. A child announced with no readable launching call is DROPPED (`unplacedChildSessions`) rather than drawn as the parent. A child's words are durable rows block by block, never live deltas, which belong to the parent's working row. **Endings**: the wire closes a background delegate immediately (`AcpSession.endDelegateOnWire`, the same close the transcript watch writes; whichever lands first wins), and a child's still-open steps are closed `SUBAGENT_ENDED_TOOL_RESULT`. The transcript watch stays as the fallback for a CLI without the capability. **The agent continues ITSELF**: with the capability the CLI holds its prompt open while background sub-agents run and then continues the parent on their results inside the same prompt — the wakeup its interactive client always ran — so geniro's own hold/wake never triggers (nothing is still out when the prompt ends), and the parent's words either side of a background ending are split into two rows. **Messages QUEUE while a background sub-agent runs**: anything that ends the held prompt cancels every sub-agent in it, so `sendFollowUp` answers false (the caller's RUN_BUSY, which queues the message until the turn ends) and says so once per turn (`QUEUED_FOR_SUBAGENTS_NOTICE`). That was the user's choice over cancelling as Cursor does. **A failed request**: the CLI holds a failed prompt open until its sub-agents end too, so a delegate cut off by a dropped stream has usually ENDED on the wire by the time the failure is read; `settleCutOffToolCalls` closes it with its stated outcome and hands its result (its last words, `childReports`) to the resume. The merged RFD uses a different shape (`subagent_update`); no agent this client drives sends it yet, and it is a reader change in `acp-subagents.ts` when one does.

**A tool call announced before its arguments exist is not written until they do** (`AcpTurnDriver.heldToolCalls` / `refineToolCall`). cursor-agent opens an MCP call while the model is still writing it — `tool_call` titled `MCP: tool`, `status: pending`, `rawInput: {}` — and sends the server, the tool and the arguments in a status-less `tool_call_update` (its `refreshToolCall`) moments later, then `in_progress`. So a `pending` call with no arguments is HELD, updates refine its name and input, and it is written when the agent starts it, settles it, sends any request, says anything or ends the turn — so nothing is lost, and a call that opens with its arguments is written at once. ACP's own definition of `pending` ("the input is either streaming or we're awaiting approval") is what makes this protocol-general rather than a cursor branch. The RESULT body is not improved: cursor's MCP `rawOutput` is `{success: true}` and nothing else.

### The ACP process lifecycle

`CursorAcpAdapter` drives `cursor-agent acp`, Cursor's first-party Agent Client Protocol server, over JSON-RPC on stdio via the agent-agnostic `adapters/acp/` client (`acp.types.ts` wire shapes, `adapters/utils/json-rpc.utils.ts` framing, `json-rpc-pending.utils.ts` reply correlation, `acp-session.ts` the process, `acp-driver.ts` the per-turn state machine). **ONE PROCESS PER CONVERSATION**, like claude's: spawn → `initialize` → `session/new`|`session/load` → then, per turn, optional `session/set_mode` → optional `session/set_config_option`|`session/set_model` → `session/prompt` → stop reason, with the process kept between turns by `AgentSessionRegistry` (`canHostSession` → `keepStdinOpen`, as for claude). `ProcessRegistry`, cancel and the executor's fan-out work the same for every CLI.

**Never go back to one process per TURN**: the kept process is what keeps background delegates alive (a one-turn process is terminated `TURN_END_EXIT_GRACE_MS` after its terminal event, killing every sub-agent it left running). An instruction block telling the agent not to background work was built as a workaround and REMOVED on the user's instruction; do not reintroduce it.

**The SESSION/TURN SPLIT is what makes a kept process safe.** A per-turn field kept across turns would re-send the first turn's state (`imageBlocks`, the turn's own `input`: its attachments and its prompt). Rather than reset per-turn fields between turns — which makes "remember to reset" the invariant, and the next field added breaks it in silence — `AcpSession` holds the handful that genuinely outlive a turn (the transport, its `PendingRequests` — the request-id counter and the map of replies still owed —, the negotiated capabilities, the session id, the granted MCP servers, the current model, the session reply, and the instruction block the conversation already holds) and builds a FRESH `AcpTurnDriver` per turn from that turn's own input. A field is per-turn by default; surviving a turn is a deliberate move to the other class.

Three consequences are worth knowing. A later turn opens through **`TurnDriver.openTurn`** rather than a stdin payload — `AgentAdapter.buildNextTurnPayload` has nothing to return for a protocol whose next prompt is a frame, and without the hook `startTurn` refuses the turn outright. That hook also owns the turn's SETTINGS: `startTurn` skips its own approval-mode delivery for such a driver, because the mode here is a `session/set_mode` frame and asking for a stdin line would refuse the turn over a change the CLI can in fact be told about. And the mode, the model and the model's parameters are **re-applied per turn** off the stored session reply — `AgentAdapter.sessionKey` covers `model` and `effort` (so either respawns) and nothing else this transport can set, so a context window changed between two messages would otherwise keep the first turn's value for the life of the conversation. (Cursor's own key adds whether the turn asks; see *The cursor transport*.)

**Two pieces of state outlive a turn on a kept process.** **(1) Everything keyed by a PROTOCOL id lives on the session**, which is that id's actual namespace — `parkedPermissions`/`parkedQuestions`, `toolNames`/`toolInputs` and the delegate sets: `spawn-cli` re-holds a request its turn settled without an answer and re-offers it to the NEXT turn, so a verdict routinely arrives while a different turn is current, and `buildApprovalResponse` must still find it. **(2) The session MODE is restored.** A mode is session state the client sets and nothing resets, so a chat switched from `plan` back to `auto` would otherwise go on running read-only. `AcpSession` records the mode the agent OPENED in and the one it is in NOW, and a turn that names none asks to be put back to the default.

**Every turn on a kept process names its session, not only the one that opened it** (`AcpTurnDriver.openOnLiveSession` emits `session`). A workflow call records its turn's session as the handle a later `thread:` resumes, so a call served by a process that was already open would otherwise record none and fail to continue (`THREAD_UNAVAILABLE`).

**STOP is `session/cancel`, not a kill** (`AcpTurnDriver.buildInterruptPayload`). It is a NOTIFICATION — no id, no reply — and what ends the turn is the pending `session/prompt` answering `stopReason: "cancelled"` (promptly, on cursor). `spawn-cli` arms a 5s deadline behind the write and kills the group only if that reply never comes: the group holds the whole conversation and every delegate still out. It is a DRIVER hook rather than an adapter one because the frame names the session id.

The process still has to be made to go away when the SESSION ends, and it does not go quietly: `cursor-agent acp` ignores EOF and lives on (with a `worker-server` grandchild, reparented to launchd if orphaned). The registry's own `close()` — idle window, LRU eviction, staleness replacement, shutdown — terminates the group. Permission requests are real (`session/request_permission` is an ACP baseline): `auto` auto-approves in the driver to keep unattended semantics, `acceptEdits` is not offered (`cursorAutoDecision`, `approval.modes`): a request naming it is refused, a mode stored where nobody just picked it — a board card, the builder dock's default — falls back to the new-chat default through `ChatService.offeredApproval`, and a run or workflow node already holding it asks: per cursor-agent's `shouldBlockWrite`, an ordinary write inside the workspace is made with no permission request in every approval mode that CLI has, so the only write requests that reach geniro are writes outside the workspace and writes to its protected config files — git config and hooks, JSON under `.claude`, `mcp.json` under `.cursor`, anything under `.vscode` — each able to make a later command run code, with nothing on the request saying which of the two it is; deletes are asked about too. An edits-only mode would therefore be `ask` under another name; `ask` and `plan` park what reaches geniro on a user verdict. A caller node's MCP endpoint travels in `session/new`, so the call token rides an HTTP header inside a stdin frame — never argv, never a file on disk. `session/load` resume suppresses the agent's transcript replay so a resumed turn cannot duplicate history. Pasted images ride as `image` content blocks in `session/prompt`, gated on the agent's own `promptCapabilities.image`. **Per-session model selection has TWO carriers**, because ACP replaced one with the other: `configOptions[]` (the entry of category `model`, ACP 1.0, applied with `session/set_config_option {sessionId, configId, value}` — `configId`, not the `configOptionId` the docs' prose uses, which the agent rejects) and the pre-1.0 `models.currentModelId` + `models.availableModels`, applied with the spec-removed `session/set_model`. cursor-agent sends both blocks and answers both methods, so `acp-models.ts` reads whichever the reply carries (configOptions wins) and the driver picks the frame from what the agent ITSELF advertised — never from a version number. `listModels` runs a two-frame handshake and the driver applies the model BEFORE the prompt. The ids are the handshake's own namespace: `cursor-agent models` prints a DIFFERENT spelling for the same model that the agent answers `-32602 Invalid model value`, so the subcommand can never be the picker's source. A `session/load` reply carries `modes`, `models.currentModelId` AND a full `configOptions` list with each option's `currentValue`, so a resumed turn reads the same fields as a fresh one. Silence is not a refusal: nothing is refused locally on a reply that enumerated nothing. **Background sub-agents are real on this transport too**: a delegation arrives as an ordinary `tool_call` whose `rawInput` is `{_toolName:"task"}` (its title is the placeholder `Task: Subagent task`, the description not yet known), and a `cursor/task` REQUEST then carries the description, the full brief, the type, the model and the duration. The lifecycle is an agent-agnostic `AcpDelegateProtocol` (method + launch marker + params reader + the two facts below), so a second CLI's delegate channel is a config rather than a branch; the driver emits `subagent_info` twice per delegate — an anchor at launch, so the block opens and the run reads busy while it works, then the facts — and the renderer merges them last-non-null. Two adapter facts carry what is NOT there: `subagents.stepsUnavailableReason` (nothing the delegate itself did crosses the base wire — it runs as its own conversation in the CLI's private per-project store, so the block opens onto the brief and the duration and SAYS why) and `resultIsBookkeeping` (the `task` call returns `{durationMs, isBackground}`, which the block framed as `Result from <delegate>` — dropped, with the duration kept on the announcement). Known ACP gaps, surfaced as `notice` events (→ `system` items) rather than dropped: an unavailable session mode, a withheld call surface, images an agent never said it could read, and the FIRST unimplemented agent→client request per turn — Cursor's other blocking `cursor/*` extension requests (`create_plan`, `generate_image`) are declined in-protocol with `-32601`, and the notice flag is per-turn, not per-method; `cursor/ask_question`, `cursor/task` and `cursor/update_todos` are answered instead. A legacy one-shot `-p --output-format stream-json` cursor adapter, its `.cursor/mcp.json` merge machinery and its MCP-trust probe were removed with this transport; do not reintroduce them.

### Workflow call runtime

**An agent node can be a POOL of configurations, and a call picks among them** (`WorkflowAgentNode.pool`, `utils/agent-pool.ts`, `CallBroker.selectPoolMember`, the attempt loop in `GraphExecutorService`'s `launchCalleeTurn`). The node's own CLI settings — agent, model, effort, context window, model parameters, config directory — are member 1, and `pool` lists members 2, 3, … (at most `MAX_AGENT_POOL_EXTRA_MEMBERS`), each REPLACING those six fields whole, plus `autoCompactPercent` (a member that names none never compacts) and `mcpDisabled` (a member's own switched-off MCP servers — one naming none switches nothing off, since member 1's list names another profile's servers); `approval` is the member's own when it names one and the node's otherwise, since the node requires one, and `nodesThatAsk` therefore counts a node whose pool holds a member that asks; `role` and `description` stay the node's. Only CALLS run on the pool — the node's own conversation (a DAG turn, a message to it) is always member 1. A NEW conversation tries members in priority order (member 1 first), with members that last failed `rate_limited` (until the reset `resetInstantFrom` can place, else 30 min) or `auth_expired` tried last, and an attempt that fails on a limit or a lapsed sign-in — or fails before calling any tool of its own — is handed to the next member as a fresh conversation (`fallsThroughPool`; never on a cancel, and never mid-work otherwise, since that could repeat what it already did). A caller may pin one at the user's request with `call_agent`'s `member` (no handing on); a `thread:` continuation stays on the member whose session it is (`ThreadRecord.member`, restored after a restart from the `call_result` row's `member`), and a member disagreeing with it is refused `THREAD_MEMBER_MISMATCH`, an absent one `UNKNOWN_MEMBER`. The envelope names the `member` that answered and the members it passed over (`pool_skipped`), and `calleeSummary` lists the members by number — a member on a profile of its own as `separate profile`, never the directory's name, since that line goes to the caller's model provider. Five things keep the members apart, each a defect without it: a handed-on attempt writes no terminal status row (the transcript reads a call's first one as its ending) and does not report the call settling or its turn ended (a cancel meanwhile must stop the hand-on), while an attempt that did NOT fail reports its turn ended the moment its terminal event arrives (`endedAs`), so a cancel landing during its bookkeeping cannot stamp CALLEE_CANCELLED over finished work; the conversation's kept process is RETIRED on a hand-on, since a session judges whether it fits a turn by its own CLI's key; `node_state` is member 1's alone — its stamp, its resume handle, its context reading — so a member other than 1 records its sessions in the node's history only — its auto-compaction turn included, which runs as that member — and every row carrying its spend (in its turn and off it) names its own `agentKind` and `agentModel` (`turnMemberOf`), which is what Stats, the run's totals and the node's own totals file that spend under, a polled bill standing for the turns a polled member ran and added to the rest; the terminal handoff of a call thread and the call readout resolve the member from the call records and the run's own snapshot (`sessionMember`, `snapshotMemberProfile`) — the readout of a call still running from the process that holds it (`AgentSessionRegistry.agentOf`) — while transcript deletion and polled spend look under EVERY member's CLI and profile (`snapshotNodePoolProfiles`), a node's recorded polled bill counting whatever its stamp says. Whatever was said into the call while a failed attempt ran is carried into the next member's opening message (`poolHandOffPrompt`).

**A node switches MCP servers off for ITS turns alone** (`WorkflowAgentNode.mcpDisabled`, a member field — `MEMBER_FIELDS` — so each pool member carries its own; `AgentTurnInput.mcpDisabled`, set in `beginAgentTurn` from the member-resolved node, so a DAG turn, a callee sub-turn, a continuation and the node's own compaction turn all carry it; chats never set it). It writes no config of the CLI's — nothing changes in the user's terminal or in a chat — and joins `AgentAdapter.sessionKey` (sorted, de-duplicated), so a kept process is never reused under another set. geniro's own server is never switched off, and a name the CLI does not load is ignored. Each CLI applies it in its own adapter: **claude** passes `--disallowedTools mcp__<server>` (`claude-mcp-tool-name.utils.ts`, mirroring the CLI's own server-name normalizer — `claude.ai Booking.com` → `claude_ai_Booking_com`, `plugin:playwright:playwright` → `plugin_playwright_playwright`); the CLI still dials the servers, the model never sees their tools. **codex** reads its config first (`config/read {cwd}`, pending kind `config_read`, only when something is switched off) and merges thread overrides beside geniro's own endpoint (`codexTurnMcpOverrides`): a server its config defines gets `mcp_servers.<name>.enabled = false`, the built-in `codex_apps` gets `features.apps = false`; a plugin's server is reachable only by switching the whole plugin off (`plugins.<id>.enabled = false`), so its row says so (`turnToggleUnavailableReason`) and the turn leaves it on — and NOTHING is written for a name the config does not define, because an `enabled = false` override for such a name fails the whole `thread/start` (`invalid transport in mcp_servers.<name>`). **cursor** gets a throwaway `CURSOR_DATA_DIR` (`cursor-data-dir.utils.ts`, materialized in `prepareTurn` beside the per-turn profile and removed with it): the CLI reads a workspace's disabled servers, MCP sign-ins and approvals from `<data dir>/projects/<key of the git root>/`, so that directory is real, every entry symlinked into the user's own store (without the links an OAuth server reads `requires_authentication`), with its own `mcp-disabled.json` holding the user's list plus the node's; names the CLI writes and that do not exist yet are linked anyway, and the cwd's own key (delegate transcripts, terminal output) is linked whole. The listing's rows carry `turnToggleUnavailableReason` (adapter-wide `AdapterConfig.mcp.turnToggleUnavailableReason`, null for all three, else the row's own), which is what the builder draws its switches from.

**A failed callee tells its caller WHY, and in a vocabulary the caller can act on** (`utils/callee-failure.ts`, `AgentAdapter.failureFrom`, `CalleeTurnOutcome.failureClass` / `.resetsAt`). A constant failure message leaves the caller retrying blind into, say, a usage limit with hours left on it. The envelope reads `CALLEE_FAILED[<class>]: <message>`, the message being the CLI's own words passed through `redactSecrets` (this is the one seam where a callee's text crosses to a caller, whose provider is off this machine). Four classes, because they are four different things to DO: `rate_limited` (wait — `resetsAt` says until when, verbatim, never parsed into an instant), `auth_expired` (only the user can cure it), `daemon_restart` (geniro's own side failed or went away — a turn that could not start, a bookkeeping write that failed — so retry once) and `crashed` (the honest default). WHICH wording means which is a per-CLI fact and stays one: `AdapterConfig.auth.rateLimitPatterns` / `resetsAtPatterns`, patterns rather than substrings because claude spells one event several ways (`hit your session limit`, `hit your usage limit`, `hit your monthly limit`, `hit your monthly spend limit`, `hit your fast limit`) and a list of nouns would be a release behind. cursor declares `[]` on its `expiredMarkers` evidence gate. A pattern must not carry the `g` flag, which `agent-adapter.spec.ts` fails the suite over: these literals are read on EVERY failure, and `RegExp.test` advances `lastIndex`, so the second matching failure of a run would silently not match.

**And a caller may STOP a call it no longer wants** (`cancel_agent`, `CallBroker.cancelAgent`, `RunCallCapability.cancelCalleeTurn`). A caller that has LEARNED its call is pointless must not have to let it run on spending (the only other stop is the run-wide Stop, which needs a person). Three properties are deliberate. There is **no confirmation card**: a card would park an overnight run on a verdict nobody is there to give while the unwanted call goes on spending. **Ownership is enforced by the BROKER**, not asked of the tool's caller — a callee holds the same endpoint shape as its caller, so without the check a nested agent could stop a sibling's work; a call the asker does not own reads as `UNKNOWN_CALL` on `answerAgent`'s rule, a caller having no business learning that such a call exists. And the **reason is required**, stamped onto the envelope the caller collects (`CALLEE_CANCELLED: <agent> was stopped by <caller> — <reason>`) and onto the `call_result` row, because otherwise the whole record of a call ending early is its absence. `cancelCalleeTurn` both MARKS the call and cancels its turn, and the mark is what reaches the commonest case: a depth-1 call queues on the sub-turn pool (`parallelAgentsFor` — sized from total RAM on the live-session curve, never below 4), so the call past it of a fan-out has no process to signal — it settles `cancelled` when its slot comes up, without ever spawning. Known limit of that half: the semaphore has no cancellable wait, so a queued call's cancellation is collected only once the pool drains; a live call settles at once.

**A caller may also STEER a call without stopping it** (`message_agent`, `CallBroker.messageAgent`, `RunCallCapability.messageCallee`). Without it a correction waits for the call to END — `thread:` on a live call is refused `THREAD_BUSY` and `answer_agent` only answers a parked question. The message goes through the callee turn's own mid-turn channel, exactly as the user's `POST …/calls/:callId/messages` does, and is recorded as a `call_answer` row with `outcome: 'message'` under the caller. Ownership is the broker's, on `cancel_agent`'s rule (`UNKNOWN_CALL` for a call the asker does not own); a PARKED callee is refused `CALLEE_PARKED` and pointed at `answer_agent`, since a message is not an answer to the question it is blocked on. A message the callee cannot take YET is HELD on the call (`ActiveCall.pendingMessages`, offered again every `PENDING_MESSAGE_RETRY_MS`, in order) and the caller is told `state: 'queued'` — never refused. That is the commonest case, not an edge: a caller steers right after it dispatches, when the sub-turn may still be queued on the pool and a claude turn still holds its own prompt for MCP readiness, refusing follow-ups so one cannot overtake it (refusing there, `MESSAGE_REFUSED`, would lose the correction). What is still held when the call settles is written as a `call_answer` with `outcome: 'undelivered'` carrying the message, so a correction that never landed is not read as one the callee ignored. The receipt says whether the CLI's channel INTERRUPTS (`followUp.interrupts`), because on cursor the message replaces the step in flight. It is on `GENIRO_MCP_CALL_TOOLS`, so cursor auto-approves it like its siblings.

**A call whose callee ended its turn with sub-agents still out says so** (`CalleeTurnOutcome.delegatesStillOut`, the envelope's `delegates_still_running` + `note`), so a caller does not read a partial answer as the result. Counted from the call's own `subagent_info` rows (`strandedDelegates`) on the write chain after the turn's own rows, and only on a `completed` call — the envelope tells the caller to continue the thread rather than treat the result as final.

**A caller sees each callee conversation's prompt cache, and a cold, large one is not resumed by default** (`list_agent_threads` in `v1/mcp/tools/list-agent-threads/`, `CallBroker.listThreads`, the `CACHE_EXPIRED` refusal in `openCall`, `utils/prompt-cache-standing.ts`). A caller checks, before following up with a callee it last called long ago, whether that conversation's cache has lapsed — a lapsed cache re-bills the whole conversation on the next turn, and past half a window a fresh instance with a brief costs less. The figures move with the clock, so they are a TOOL's answer and never part of the "May call" block, which is hashed into the caller's `sessionKey` (a change respawns the caller and busts its own cache); that block carries only the static rule (`COLD_RESUME_RULE`). Each conversation lists its newest continue handle, whether a call runs on it, its last context reading and its cache standing (`warm` until an instant, `expired`, or `unknown` for a CLI that states no lifetime — never guessed), plus `advice`. The facts ride `CalleeTurnOutcome` (`promptCacheTtlMs`, `contextTokens`, `contextWindowTokens`, from the call's own turn; the reading is withheld once a compaction started, since it described the replaced conversation) onto `ThreadRecord.cache` and the `call_result` row, which `readCallSeed` restores with the row's time as the turn's end. A `call_agent` with `thread` on a conversation whose cache expired AND whose window is over `COLD_RESUME_CONTEXT_PERCENT` (50) is refused `CACHE_EXPIRED` unless the caller passes `resume_cold: true`; geniro's own continuations (a wake, a picked-back-up question, a held call continued) are never refused, since there is no brief to start over from. A call that recorded no session (cancelled while queued, restored without a result) is neither offered nor judged by. A turn the callee's kept process runs after its call settled moves that call's facts too (`noteConversationTurnEnded`, from the executor's off-turn sink); a restart re-reads them from the `call_result` row alone, so such a turn is forgotten across one. A lifetime a cache-only turn did not state falls back to the conversation's, then to the same callee and pool member's last stated one. The nodes route's `promptCacheExpiresAt` (per call and per node) falls back per node AND CLI instead, since usage rows name a pool member's CLI rather than its number — the two can differ only for two pool members on one CLI with different cache lifetimes.

**A rate-limited call WAKES its caller at the reset** (`CallBroker.scheduleResetWake`, `utils/reset-instant.ts`). `resetsAt` stays verbatim on the envelope; `resetInstantFrom` is the one reader that turns claude's own reset wording (`6:10pm (Asia/Almaty)`, `Sep 25, 6pm (TZ)`, `Jan 2, 2027, 9:30am (TZ)` — transcribed from its formatter, zone via `Intl`, DST-safe in two passes) into an instant, and answers null for anything it cannot place exactly, which schedules nothing. Without the wake a caller sleeps in a background shell or sits idle. The wake is grouped per instant, fires a minute after the reset (`RESET_WAKE_GRACE_MS`), is bounded at two days, uses `tellLiveNode` for a caller that is working and `wakeNode` for one that is not, and writes a system row naming the calls it continued. Only a call with a session to continue is scheduled, and the error envelope says so, so the caller waits instead of polling. **The promise is also the USER's, and it survives a restart** (`Run.resetWakes`, `CallBroker.useResetWakeHooks` / `restoreResetWakes` / `cancelResetWakes`, `GraphExecutorService.rehydrateResetWakes`). A daemon timer alone is invisible to the user and dies with a restart. So the schedule writes a `system` row (`resetWake: {phase: 'scheduled', …}`) and the run row's JSON column, which rides `RunWire.resetWakes` and the `run_status` announce, so the composer shelf shows "Continues at HH:MM" with a way to call it off (`POST /v1/workflows/runs/:runId/reset-wakes/cancel`). The column is written off when the promise is kept, cancelled, or fires into a stopped run. At boot the promises are armed again, and one whose reset passed while the daemon was down fires at once. A restored promise fires through the run's next pass when one has registered since. When none has, the executor walks the run again with geniro's prompt as the seed, filed as a `system` row rather than as the user's message. That walk reaches only trigger-fed agents, so a promise to an agent that answers only inside a call is written down as a note saying so, never kept silently. So is a promise whose walk would ALSO start agents that were not waiting — another trigger-fed agent, or a DAG node downstream that would re-run on what its producer says next: the walk is taken only when the agents it schedules are exactly the ones promised.

**A call waits for the calls its callee made** (`CallBroker.holdCall` / `reviewHold`, the HELD loop in `GraphExecutorService.launchCalleeTurn`). A call is the callee's whole job and the calls it makes are part of it, so a callee turn that ends COMPLETED while async or sync calls of its own conversation are still running (fire-and-forget excepted — nobody collects it) does not settle: it writes no ending, posts one `system` row carrying `heldCall: {waitingOn}` (folded into the call card's `heldOn` reading — TWIN PARSER in the renderer's `transcript-groups.ts`), and gives its sub-turn SLOT back while it waits; as the calls it waits for finish, a `heldCall` row with no `message` moves the card's count down and draws nothing. When the last of those calls settles, or one parks a question, the callee is continued inside the SAME call — the same session resumed, with `wakePrompt`'s items plus a line saying its next reply is the call's result — and the call settles on THAT turn's answer. Any wake aimed at a held conversation is routed there by `wakeOwner`; continuing it as a new call would defer to the held call and deadlock. A message to a held call — the caller's `message_agent` or the user's own into its block — wakes it with that message, behind any the caller had queued; one sent once it is woken but still waiting for a slot joins the prompt of the turn that continues it (the executor's `waitingCalls`; the caller's queued messages first, via `takeQueuedMessages`), ahead of the wake's closing `note` that the reply is the result, which is always said last — and if the call is stopped before that turn, each such user message gets a `Not delivered` row. A sub-call stopped by a usage limit keeps the call held (`owesHold` counts a promised continue), and the reset continues the callee inside it (`deliverResetWake` routes a held conversation to its hold); a reset that fires while the call's turn is ending, not yet held — the conversation still reading as live and refusing it, or its call not free — waits as owed work (`pendingResetDeliveries`, carried across passes like `resetWakes`) and is delivered when the hold starts or the call settles; a cancel or the user calling the continues off drops it with a `resetWake: {phase: 'cancelled'}` row. Bounded by `MAX_CALL_WAKES` (10): past it the call settles on the answer it has with `calls_still_running` and a note, and what is still out is delivered as before. `cancel_agent` on a call CASCADES: a running one stops the calls made inside it and silences what those left behind (`ActiveCall.madeIn`, kept on each settled call's thread record — a conversation's earlier calls' work is left alone), while one whose turn has ended — or that was ever held — stops every call its hold waits for, an earlier call's leftovers included, and then SILENCES the conversation (`silenceConversation`: results it was not woken for are marked told, a usage-limit continue promised to it is dropped with a `resetWake: {phase: 'cancelled'}` row saying why), since any of them would otherwise reopen the conversation just cancelled as a call made for the caller; finished work is never stamped cancelled, though its result is marked told all the same (collectable, never a wake); whether the call still owed work is recorded when the cancel is accepted (`ActiveCall.cancelledOwing`), because the cascade silences that work before the executor writes the call's ending, and a call that owed it ends `cancelled` rather than handing over its partial answer; calling off a promised continue (`cancelResetWakes`) re-reviews any call held only for it; a run Stop and `unregisterRun` release every hold as cancelled. The silence watchdog is suspended while held. A callee is told this up front: the "May call" block (`ANSWERING_A_CALL`, `utils/callee-text.ts`) and `call_agent`'s description on a conversation route say that ending its turn while its calls run does not hand back its result. A resumed wake turn that reports no session of its own is still in the one it resumed.

**A CALLER is a conversation, not a node** (`utils/caller-key.ts` → `callerKey(nodeId, conversationId)`). Keyed by node alone, two conversations of one node calling out would collect each other's results (`await_agent()` in one returning the other's, which then gets `UNKNOWN_CALL`). A turn answering a call is handed `/v1/mcp/<run>/<node>/<conversationId>`, the node's own conversation keeps the two-segment route, and the broker keys ownership, threads, waits, blockers, depth and wake targets by that pair; the node's existing call token opens both routes and nothing else. `call_started`/`call_result` carry `callerConversationId`, which `call-seed.ts` reads back after a restart. The WAKE follows the same key: a result or question owed to a callee that is itself a caller reaches it IN the conversation it is answering in — pushed into that call's own sub-turn while it works, and — once its turn has ended — continued INSIDE the same call while that call is held (see *A call waits for the calls its callee made*). Only for a call that SETTLED with its own calls still out (a failed turn, one past its wake limit) is it delivered by continuing that conversation as a new async call on the original caller's behalf ("Picked back up — …"), whose result wakes that caller as usual — never by waking the node in a fresh process with no session and no call. When that conversation already has a call QUEUED on it (waiting for a slot of the sub-turn pool, or inside a reopen) the wake is DEFERRED to that call (`startOwnerTurn` → `'deferred'`, `drainWhenFree`) rather than read as unreachable (which would orphan the question and cancel the callee who asked it), and a continuation resumes the newest point of the conversation that HAS a session, not a call cancelled before it ran. A reset wake takes the same path. Known limit: a deferred question's 30-minute TTL keeps running while the queued call waits for its slot.

**No call-tool wait outlasts the caller CLI's own tool-call deadline** (`AdapterConfig.mcp.toolCallDeadlineMs`: cursor 60s; claude 300s). `await_agent` and a sync `call_agent` are bounded at 80% of it and answer `pending` with the `call_id`, the result staying collectable — cursor gives up on an MCP call at 60s but keeps the socket open, so a waiter left registered would swallow the next question or the sync result into a reply nobody reads. Both tools also run under `whileCancellable`, so a client's `notifications/cancelled` releases the waiter as abandoned.

**Three smaller races in the same runtime.** A `cancel_agent` that lands after the callee's turn ENDED (the executor tells the broker, `noteCalleeTurnEnded`, before its post-turn bookkeeping, which can be a whole compaction turn) stops nothing and answers `already_finished` — never `CALLEE_CANCELLED` stamped over finished work — unless that conversation is still owed work (a call of its own running, a result it was not woken for, a usage-limit continue): such a call is held or about to be, so it is cancelled like a running one and ends `cancelled`. A follow-up that claims the run while a kept process's call is waking it makes the finished pass SUPERSEDED: a call arriving through it is refused `RUN_BUSY` before any id is minted, one already waking the run yields and ends `CALLEE_FAILED[daemon_restart]`, and call numbering continues past every id already issued (never two passes both running and re-minting `call-1`). And a callee turn that ends while its node has other live turns retires its OWN unanswered cards and their blockers, which otherwise suspended every question TTL of that node until its last turn ended.

Binding, the pidfile handshake and the config env are in the root `AGENTS.md` → *The daemon (`apps/daemon`)*.

### Plan limits

**Plan limits are the ACCOUNT's, so the metrics route serves the best reading any of its chats took** (`utils/plan-limits-ledger.ts`, held by `ChatMetricsService`, keyed by CLI + the ACCOUNT's config directory: the folder's pin (`ConfigDirPinService`) when there is one, else the run's own profile — a node's off the run's workflow copy — canonicalized. The pin matters because claude re-points its account to a project settings file's `env.CLAUDE_CONFIG_DIR` after startup, the same call the renderer's `accountConfigDir` makes; keyed by `run.configDir` alone, a default-profile chat in a pinned folder would serve its team-plan figures to every unpinned default chat). claude's `get_usage` does not always ask its usage endpoint: when that call fails it answers a "seeded" reading built from the process's own last request headers or a persisted snapshot, and strips `limits[]` from the reply. The reader marks such a reply `estimated`; the ledger prefers a real reading over a newer estimate for 30 minutes, otherwise the newest, forgets an account that answered with no windows, and serves a chat whose agent is closed another chat's reading. `planTakenAt` dates whatever is served, since it may be another thread's; `takenAt` dates the breakdown alone. In memory only — a restart costs the sharing until the next reading.

### Daemon endpoints (loopback)
The generated OpenAPI document (`/swagger-api`, the source of `pnpm generate:api`) is authoritative for every route and shape; this table is a map of what each route is for and the rules it carries.

| Route | Purpose | Auth |
|---|---|---|
| `GET /health/check` | readiness probe (`{status, version}`) | public |
| `GET /metrics` | Prometheus metrics | bearer token (`LoopbackTokenGuard`) |
| `GET /swagger-api` · `/swagger-api-json` · `/swagger-api-yaml` · `/swagger-api/reference` | OpenAPI spec (the source for `pnpm generate:api`) + Scalar UI | launch token, checked by `@packages/http-server`'s `swagger.guard` — raw Fastify routes and middleware that `LoopbackTokenGuard` never sees |
| `/ws` (Socket.IO) | renderer ⇄ daemon channel: `join`/`leave` run rooms, streamed `item` events, approval `verdict` → `verdict_ack`, plus `run_status`, a client-wide broadcast that carries no room so every chat's badge stays live, not just the focused run's. Its `status` is **nullable**, and that is what separates a status change from an activity announce: the announce fires from inside a turn's event stream on every tool call and never reads the run, so it must not assert a status (a straggler after a cancel would flip the badge back). A null status says only "this is what the run is DOING" and leaves the badge alone. Its `activity` has two consumers, not one: the sidebar badge, and the transcript's own live row through `RunActivityContext` (`chats/live-row.tsx`), so the two can never name different work for the same run — and it is **three-state like `awaiting`** (absent asserts nothing, `null` clears), which `ChatTitleService` is the first producer to need: an announce that never read the run has no honest activity to send, and `null` there blanks the phrase of a turn that is running. The event also carries an optional `title`, the name that service just gave a run — a broadcast for the same reason the status is, since a chat is named a second after its turn ends, typically once the user has moved on. ### Agent caches and MCP configuration

**What a CLI says about itself is cached ACROSS LAUNCHES, and invalidated by three separate mechanisms** (`services/model-vocabulary.store.ts`, `<userData>/model-vocabularies.json`). `utils/model-vocabulary-cache.ts` stops ONE process asking twice; the store stops every restart and TTL lapse re-paying a real `cursor-agent acp` handshake (seconds each) for answers that have not changed. Both readers consult the store first — `ModelsService` under the NULL model key, `CursorAcpAdapter.probeModelConfigOptionsShared` under the model's own — and the store holds opaque JSON with the caller supplying the shape guard, so a value whose shape has since moved costs a re-ask rather than a picker full of rows it cannot render. **Staleness is answered by three mechanisms because the three causes differ.** The CLI was UPGRADED → the `--version` lives in the ENTRY and is compared on every read (exact, no clock; in the entry rather than the key so an upgrade REPLACES a row instead of spending the entry budget on versions nobody can run). The ACCOUNT changed through geniro → `CacheResetService.forgetAgent(agent)` from `CliAuthService`, on a completed account sign-in or sign-out, since a subscription decides which models exist and none of that moves the version — every cache for that CLI, in memory as well as on disk, and an answer whose request began BEFORE the forget is discarded rather than stored (`ModelVocabularyStore.epoch()`), so a refresh already in flight cannot write the old account's list back; NOT on an MCP-server sign-in, which changes tools rather than models and is answered by retiring that folder's sessions. Anything else — a plan change, an entitlement flipped server-side, a `cursor-agent login` in the user's own terminal — cannot be observed here, so past an hour an entry is SERVED AND REFRESHED BEHIND THE ANSWER (`StoredAnswer.stale`), with a seven-day hard expiry as the backstop for a refresh that never succeeds. And beside the three, a MANUAL one: `POST /v1/agents/caches/clear` (View → Clear Agent Cache). The refresh is joined through each caller's existing single-flight (`ModelsService.inFlight`, `handshakeProbeCache`), so it cannot race a cold ask or spawn a second process group. An answer that could not actually be obtained is never filed — an empty model list, a probe reply that enumerated nothing — or one transient failure becomes a week of "this CLI has no models".

**MCP config writes** — the deliberate exception to "geniro writes only its own files": MCP configuration, plus claude's needs-auth record. Sharing the CLI's own state is the point: a switch flipped in geniro is the switch the user sees in their terminal, and the reverse.
- **Toggles** (`PUT /v1/agents/mcp`, `AgentAdapter.setMcpServerEnabled`). **claude** edits `projects[<project key>].disabledMcpServers` in `~/.claude.json` — the CLI's OWN key (`claude-project-key.utils.ts`: the cwd's real path walked up to its `.git`, a worktree's `.git` file followed back to the MAIN repository; keyed by the raw cwd the switch would do nothing in a subfolder or a task worktree) — the only mechanism that reaches servers of every scope. The write is a read-modify-write under `proper-lockfile` at `~/.claude.json.lock` — the SAME lock the CLI takes, whose `onCompromised` logs rather than throwing from a timer — then tmp+rename the way the CLI writes it: the file's existing mode kept (0600 for a new one), through a symlink rather than over it, fsynced before the rename (`atomicWrite`'s opt-in `preserveTarget` + `fsync`, the shared `rewriteHomeConfig`); it REFUSES an unparseable config rather than replacing a file that holds the user's whole CLI state. **cursor**'s toggle writes nothing directly: geniro runs that CLI's own `mcp enable|disable` IN the folder and lets it own the file (`~/.cursor/projects/<key>/mcp-disabled.json`, whose path also depends on `CURSOR_DATA_DIR`/`XDG_CONFIG_HOME` and on which of the CLI's two project-dir functions applies). **codex**: a one-shot `codex app-server` writes `config/value/write` `mcp_servers.<name>.enabled` into its own `config.toml` — per profile, so it covers every folder — and ONLY for a server that file defines (checked with `config/read` first); for its built-in `codex_apps` and plugins' servers the row says why there is no switch instead of geniro writing a stray table.
- **Plugin copy** — cursor's direct writes are all presses (`CursorAcpAdapter.copyPluginMcpServer`, `POST /v1/agents/mcp/plugin-servers`): Add on a plugin server writes an entry into `~/.cursor/mcp.json`. Plugin servers load in Cursor's own app and never in the ACP sessions geniro runs, which read only the two `mcp.json` files, and no CLI subcommand adds an entry — so a file write is the only route. claude's discipline minus the lock (cursor takes none on that file): a strict re-read, a refusal on an unparseable file or a name already used for something else, no write when the identical entry is there, and an atomic fsynced replace that keeps the file's mode (0600 for a new one). It carries NO credential: a plugin variable that is write-only or named like a key is never asked for, a header that needs one is left out (the server signs in with OAuth instead), and nothing bound for the plugin's host — a header or the URL — may read the user's environment (`${env:…}`) under any name.
- **Server definitions**, only on an explicit press in the MCP dialog's Add (`components/mcp-add-dialog.tsx`; `GET/PUT /v1/agents/mcp/config`, `POST /v1/agents/mcp/servers`; `AgentAdapter.readMcpConfigDocument` / `writeMcpConfigDocument` / `addMcpServer`): an "Add a server" form and an "Edit JSON" editor, both on the listing's PROFILE at USER scope, never a folder — claude's top-level `mcpServers` of the profile's `.claude.json` and nothing else in it (Add = `claude mcp add -s user`), cursor's `mcpServers` of `~/.cursor/mcp.json` under the plugin copy's discipline (Add = a direct write, that CLI having no `mcp add`), codex's `[mcp_servers]` table of its user `config.toml` through its OWN app-server writer (`config/batchWrite`, never TOML by hand; Add = `codex mcp add` for stdio and the same writer for http, since its `--url` form starts an OAuth flow nobody is there to finish). A save carries the version it was read at and is refused if the document moved; geniro keeps no copy, and every env/header value of an Add is registered for redaction before the CLI runs. Per-CLI details are in the route row above.
- **claude's needs-auth record is the one CLI cache geniro edits** (`ClaudeAdapter.forgetMcpNeedsAuth`): the CLI keeps `<profile>/mcp-needs-auth-cache.json` and skips any claude.ai connector listed there for up to 4h (15 min for other remote servers) at every session start, and `claude mcp login` exits before the user has authorized in the browser, so a re-check polled during the browser flow writes the entry back — the connector then reads Connected in `claude mcp get` and is withheld from every new session. When a re-check, a switch-on probe or a fresh listing sees a server `connected`, `AgentMcpService` deletes that server's key and retires the CLI's kept sessions (below); an unreadable record is left alone.

**An MCP change retires the KEPT agent sessions it reaches** (`AgentMcpService.retireSessionsReachedBy` over `AgentSessionRegistry.markStaleWhere`, called from `AgentMcpService.setEnabled` and once a SERVER sign-in is SEEN connected). A CLI reads its MCP configuration once, when it starts, so a server switched on or signed in to reaches the config and not a process a chat is already holding. It MARKS rather than closes — the flag is read at the start of the next turn — because a change can land while a turn is in flight (closing there kills work the user asked for) and because a folder may hold a dozen idle chats whose respawn would re-launch the user's own MCP servers for turns nobody sent. Matched per agent, and as far as that CLI keeps the state (`AdapterConfig.mcp.changeReach`, one answer for a toggle and one for a sign-in): claude's switch is per repository per profile (`claudeProjectKey`, so a subfolder or a task worktree is reached), its sign-ins per profile; cursor keeps both per project root outside any profile; codex keeps both per profile. A session records the profile it was spawned under for this. **A server sign-in is not `succeeded` when its CLI exits** — claude's claude.ai connectors exit about a second after opening the browser — but `verifying`: `CliAuthService` re-checks the server through `AgentMcpService.recheckServerHealth` — one server dialled per tick, never the folder's listing — (at once, then backing off to 10s, for up to `LOGIN_TIMEOUT_MS`) and reports `succeeded`, and retires sessions, only once it sees the server connected; a server that never connects is an honest `failed`. A connect seen there also corrects every other cached reading the sign-in reaches that still says `needs_auth`. And a TURN that reports a server as needing sign-in while geniro's own current reading of that folder says connected gets a transcript note, with the CLI's needs-auth record cleared and the session retired (`AgentMcpService.observeTurnServers`). A server SEEN connected by a re-check, a switch-on probe or a fresh listing retires the kept sessions its sign-in reaches (`changeReach.signIn`) when the CLI still held a needs-auth record for it (`AgentMcpService.forgetNeedsAuthOnceConnected` over `AgentAdapter.forgetMcpNeedsAuth`): the record made those sessions start without the server, so the CLI exiting `mcp login` is not the moment the connector becomes usable — the observed connect is. A turn whose own report misses a server geniro saw connected retires them too, record or not (`observeTurnServers`), since a process started before a sign-in made outside geniro holds no record to clear. A connect is carried to other folders' readings only for a same-named server pointing at the same place (`target`), or where either side does not say.
