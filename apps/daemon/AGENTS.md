Project-wide commands, conventions and constraints are in the root `AGENTS.md`; the module layout is in `.claude/rules/daemon-module-structure.md`, adapters in `agent-adapters.md`, the codex adapter in `codex-adapter.md`, MCP tools in `mcp-tools.md`, share links in `shares.md`, queries in `database-queries.md`. This file holds only what those do not: the daemon's non-obvious invariants, by area.

### Boot, process and storage

- `auth/` holds the launch token, the per-node call tokens (`mint-token.ts` is their one source), `LoopbackTokenGuard` and `enforceWsHandshakeAuth` (the one Socket.IO handshake gate for every gateway).
- A call token is minted once per RUN, only through `CallTokenRegistry.ensure`. A kept CLI process presents the token it spawned with, so a re-mint locks it out of its own endpoint (silent 403s).
- `environments/`: prod is the base, dev spreads prod, test spreads dev; each is one `as const satisfies …` literal. `GENIRO_USER_DATA`, `GENIRO_PORT` and `GENIRO_IDLE_EXIT_MS` bypass `getEnv` (it boolean-coerces). `host` is a constant, never an env knob (127.0.0.1-only is a hard rule).
- `utils/process-identity.ts` is the one answer to "is pid N still the process I recorded" (ps start time). Never act on a bare `kill(pid, 0)`; a recycled pid is a stranger.
- One daemon per userData dir (`instance-lock.ts`). Takeover of a stale lock is rename-then-recheck, never delete-then-claim. Release on Nest's shutdown hook (not `process.on('exit')`), and only after `ProcessRegistry.drain` and `AgentSessionRegistry.closeAll`.
- Idle self-exit (`idle-shutdown.lifecycle.ts`) needs no WS client AND no in-flight turn, counting off-turn work (`workingOffTurn`). It SIGTERMs itself so hooks run, and is off unless `GENIRO_IDLE_EXIT_MS` is set (only `DaemonSupervisor` sets it).
- `utils/sleep-watch.ts`: node's timers count through a macOS sleep, so a deadline that ran out with the lid shut fires at the wake. A silence, idle or waiting deadline uses `awakeTimeout`, which restarts it in full from the wake (`retime` changes a pending one's length, keeping its start). `RunProcessSweep` reads the watch too: a run's idle class counts from the last wake as well as its newest row. A deadline that names an instant (a usage-limit reset, a retry) stays on `setTimeout`, as do two windows that may harmlessly fire at the wake: the badge lease (`DELEGATE_ROW_LEASE_MS`, `chat.service`) only decides a word on the run and never abandons work, and `await_agent`'s bound (`untilDeadline`) only returns `pending` early, as the CLI's own tool-call deadline also counts through a sleep. The watch is a module-level singleton (`sleepWatch`); specs rely on its reset in `src/__tests__/setup.ts`.
- `crash-guards.ts` installs before Nest. An uncaught exception writes `<userData>/daemon-crashed` (twin of the UI's `daemon-pidfile.ts`), then SIGTERMs itself. Keep it latched (`shuttingDown`) and keep every handler body non-throwing; Nest runs hooks inside its SIGTERM listener, so a throwing hook re-enters.
- `db/nul-safe-sqlite.driver.ts`: MikroORM 7 inlines values into SQL and SQLite ends a literal at NUL, so the driver renders NUL as `char(0)`. Do not swap back to the stock driver. WAL is on; copying `geniro.db` needs `geniro.db-wal` too.
- better-sqlite3 is synchronous: every statement holds the event loop for its whole length, and awaits resume on microtasks, so a chain of statements holds it too. A request path never reads a whole run's payloads: it reads a kind through its index, a promoted column, or `RunKindRowsCache`; a walk over every row (the waterfall's spine, `ItemDao.timelineSpine`) reads a payload-free projection in seq windows with a yield between them. Until the boot sweep stamps an older run, its lookups fall back to the payload (Runs and runtime columns). Every statement, the ORM's and `getKysely()`'s alike, is timed at the Kysely driver (`db/slow-statement-log.ts`, `TimedSqliteConnection`): one at or past `SLOW_STATEMENT_MS` is logged by its shape only (`valueFreeSql`, never a value). `EventLoopWatchdogService` (diagnostics) logs any block of `EVENT_LOOP_BLOCK_WARN_MS` or more. The ORM's own `slowQueryThreshold` never sees a Kysely query; do not move the timing back there.
- **Seeding** (the command is in the root `AGENTS.md` → *Commands*):
  - Fills a database with chats in hard-to-reach UI states. Seeders live in `apps/daemon/src/db/seeders/`.
  - Seeds are idempotent and scoped: every fixture id starts `seed-fixture-`, and a run deletes exactly those before writing. Never `deleteAll`. Keep the `em.clear()` after that delete.
  - Never touch runtime-owned tables (`usage_events`, `node_state`) from a seed.
  - It refuses a real profile (`~/Library/Application Support/Geniro`, `~/.geniro`); `GENIRO_SEED_FORCE=1` overrides.
  - Dev-only: `db/seed.ts` and `db/seeders/` are excluded from the build, and `SeedManager` is registered in the seed entry point, never in `mikro-orm.config.ts` (`@mikro-orm/seeder` is a devDependency stripped from the packaged daemon).
- An adapter spawns only through `start()` / `runCommand()`.

### Run processes

`utils/run-process-scan.ts`, `services/run-process-attribution.service.ts`.

- Every run-scoped CLI, and every command action a user runs, is spawned with `runTagEnv` — `GENIRO_RUN_ID=<runId>` plus `GENIRO_RUN_OWNER=<currentRunOwner()>` (a hash of userData) — merged last so no adapter or caller env replaces it. `RunProcessAttribution` (over `attributeRunProcesses`) is the ONE answer to "which processes are this run's": tagged processes (this owner only; the env is the text AFTER the argv in `ps -E`) plus their descendants, each process in exactly one run. The one exception is what a CLI left running when it died, found by the groups its session recorded (Left commands below). The usage readout (`RunProcessesService`: `detached`, then app-wide `leftover`), the reaper and the sweep all ask it, so what a thread shows as detached is what archiving it ends; its kept CLI trees end with `closeRun`. Readouts may share a reading up to `READOUT_SCAN_MAX_AGE_MS` old; kills always take a fresh one.
  - What is never attributed is decided by STRUCTURE, never by a program's name: the daemon and its ancestors, a run the daemon itself carries the tag of, pid ≤ 1, another uid, a process on a terminal (and what it runs) while that terminal is open, and `isOutsideAnyRun` (executables under `/System`, `/usr/libexec`, `/Applications`, `~/Applications`, and the container VM — matched by lima's own `/_lima/` directory under any home — the one named exception). Never the HOST of a terminal: codex runs commands on a pseudo-terminal, and a whole agent must not vanish behind one. Do not add name lists here: macOS offers no process containment to apps (no cgroups; coalitions are launchd's), and a name decides nothing reliably.
  - Known limits: a tmux an agent started is its thread's, so ending the thread ends it, shells the user opened in it included; a shared helper an agent first started (gpg-agent, watchman, a Gradle daemon) stops with that thread and restarts on demand; a job the user orphans from a session an agent started, after its terminal closed, carries the run's tag and is stopped with it. Nothing in the process table tells these from what the agent detached. A system binary (`sh`, `zsh`, `sleep`, `tail`) whose parent is gone shows no tag — macOS withholds the env of `cs_restricted` processes — so it is a run's only through the left-command stop below. A command that starts yet another session after its last recording escapes that stop; so does one whose CLI dies before a reading finds it, and a claude command that dies with claude in its first seconds, before claude reports it as a task.
  - Kills (`RunProcessReaper`): explicit pids only, each re-confirmed by start time before TERM and KILL; nothing over `RUN_PROCESS_CAP` or when `ps` fails. Archive/sweep never reap a run the registry holds a live agent under, asked after the scan. A confirmed process-panel stop may stop selected detached pids while an agent is live, but excludes every registry-held CLI tree, including orphaned group members, after fresh attribution and usage scans; any selected pid outside the run's detached set refuses the entire request. An agent's stop action (`stopCandidates` / `stopRecorded`) is the one path that may stop a process under a LIVE CLI: it excludes only each registry-held CLI and the members of a CLI's own process group (its MCP servers and helpers; a backgrounded command runs in a group of its own), records each target's start time at publish from the fresh scan, and at the press stops the targets still the same process and still a candidate, plus their current candidate descendants (what they have started by the press) — a target gone or whose pid was reused is `gone`, one alive but no longer a candidate refuses the whole press (`PROCESS_CHANGED`). Both stop paths share one fresh reading (`freshReading`). A reap the sweep queued for a gone run re-asks the database that the run is still gone (`stillGone`); an idle reap re-asks nothing but `held`; queued reaps share one scan; logs name the executable, never the argv.
  - Left commands (`stopLeftGroups`): every CLI runs its detached commands in sessions of their own and stops them only on its own shutdown, so a CLI that dies without one (crash, OOM, Force Quit, a close whose escalation cut it short) leaves them running, and a system binary among them no longer shows the run tag once its parent is gone. From the moment the CLI reports a command running until it reports it ended, its session records, from the CLI's own tree, the process groups the command's own processes run in and their members' start times (`recordCommandGroups` over `commandWork`): background shells, delegates' commands, commands the agent waits on (claude's foreground tasks, every command codex runs) and, for a CLI that reports no units (cursor), its execute calls until the turn's sweep finds them gone or detached — once cursor answers a call, only what still runs in its tree. One reading per burst of starts, answers and allowed approvals, `COMMAND_GROUP_READ_DELAY_MS` after the first (a call can be reported before its command spawns), one more that long after it when the burst went on, then every `COMMAND_GROUP_REFRESH_MS` while any runs. A reading that finds nothing of a command drops it. Never the CLI's own group, which claude's MCP servers share; codex gives each MCP server a group of its own, recorded only if the agent ran that same command line. When the process ends, whatever ended it but shutdown, `AgentSessionRegistry.onLeftCommands` hands `endedRunning.groups` to the reaper (`createRunProcessReaper` wires it). After the kill grace, a group is acted on only while a recorded member is still alive in it with its recorded start time (a pgid cannot be reused while a member lives), never the daemon's own group; then its current members as explicit pids, minus `daemonChain`, `fencedPids` without the terminal fence, and every registry-held tree (`processTreeOf`). The terminal fence is skipped because the groups were the agent's by structure when recorded and codex runs its commands on a pseudo-terminal.
  - Archive and delete reap through `RunTeardownService.endProcesses` (the run's command actions aborted and monitors stopped, `closeRun`, then the reaper). `RunProcessSweep` (15 s after boot, then every 5 min) reaps what runs that are gone or archived in THIS database still run, never a run the registry holds a process for.
  - Monitors (the `monitor` tool) are daemon-owned and found by `MonitorRegistry`, never by attribution: a tagged `/bin/sh` root is invisible to `ps -E`, and a wrapper of the packaged daemon's own runtime would be fenced as an installed-app executable. `RunProcessesService` reports each as one `monitors` row with its whole process group (`processTreeOf` from the shell's pid), claimed out of `detached` and the app-wide `leftover`; Stop stops it through the registry. A running monitor holds its run like a command action (`held`). Known limit: a child that calls `setsid` leaves the group and shows as an ordinary detached process, which the detached Stop and the reaper still reach.
  - Idle (`RunIdleReapService`): once a run has sat unused for the kept-session window, what its agents left running outside any CLI is stopped too, whatever the run is (chat, card, workflow) and whatever column its card is in. Two ways in: the registry's idle close, once the CLI has EXITED and its group kill's grace has passed (`AgentSessionRegistry.onIdleClosed`: never for an eviction, a stale replacement, a teardown or shutdown; withdrawn when a teardown or shutdown escalates the close; and not while another conversation of the run was used within the window, `runUsedAt`), and the sweep, for a live run the registry holds no process for whose newest transcript row (`ItemDao.latestItemAtPerRun`, the run's `lastActivityAt`: its last turn's end, its last message, its off-turn rows — the one time only the conversation moves) is older than the window, counted from the last wake too and only once Electron has pushed the user's window (`hasUserIdleWindow`) — after a restart or an eviction. The reap is `RunProcessReaper.reapIdle`: unconditional but for `held` asked after the scan, since a run used again always holds a kept CLI, a command action the user is running (`ActionCommandRegistry.isRunning`) or a monitor (`MonitorRegistry.isRunning`) — archive and delete end those first; two asking for one run in the same reap share it and only the first is handed what it stopped; the sweep skips a run whose CLI exited within the kill grace (`awaitingGrace`), when its own MCP servers may still be stopping. When it stopped anything it writes one run-level `warning` row naming the commands that started the rest (`maskedCommand`) and owes the run's next turn a prompt line naming only their executables, since an argv read from the process table can carry a credential no agent typed (`oweRunNote`; in a workflow the first conversation to take a turn carries it); an archived or deleted run gets neither. The row is the run's newest, so the chat rises in the sidebar as for any event. Accepted: a dev server the user keeps using in a browser without writing to the chat for the window is stopped; the agent restarts it on the next message. It reaches only what attribution reaches (Known limits above): an orphaned system binary (`/bin/sleep`, `tail`, an `sh` loop) shows no tag and is neither stopped nor named, as with archive. A command the CLI tracks (`shellsRunning`) keeps the session, and so the run, from going idle at all.
  - `ps` reads go through `runPs` (`LC_ALL=C`); the boot-time identity probe in `utils/process-identity.ts` pins the locale itself. `lstart` follows the locale, and an unparsed table reads as unreadable. macOS hides the env of its own platform binaries, and turbo's strict env mode strips the tag from its tasks, which is why descendants are included.

### Runs and runtime columns

- `run_groups` (sidebar folders) are runtime state in SQLite, not YAML.
- Context readings (`Run.contextTokens` / `contextWindowTokens`, `NodeState`, `CallContext`) are LEVELS: a reading that omits a figure never clears it; a compaction clears it (`RunDao.forgetContext`).
- `CallContextDao` inserts only while the calling node still has a `node_state` row (an insert after teardown would orphan a row).
- `workedMs` / `toolCalls` are TOTALS, written by real increments (`NodeStateDao.rememberWork`), never a read-modify-write. The `node_state` / `runs` column holds the CLI-reported time only. Delegate tool calls (`parentToolUseId`) are not counted. A node turn's tools are added however it ends: at `turn_complete`, else when the turn finishes (error, cancel, or an exit with no terminal).
  - The node total is the agent's whole run. A call card draws its CONVERSATION's tools instead: the nodes route's `callFigures[].toolCalls`, counted from the rows (`ItemDao.ownToolCallsByCall`, after `ensureIndexed`) with `toolCallsThroughSeq`, the newest seq counted; the renderer adds only its own rows above it (`ownToolCallSeqsByCall`, twin). A sub-agent card's tools: run state's `delegates[].toolCalls` (`ItemDao.delegateToolCallCounts`, rows naming it as `parentToolUseId`, through `throughSeq`), plus its rows above (`daemonSubagentReadings`, twin).
  - A turn the CLI did not time (ACP), node or 1:1 chat, is measured by the wall clock from the agent's durable rows (`utils/wall-worked.ts`, twin of the renderer's `scanTurns`) and recorded one row per turn in `wall_turns` (`(runId, seq)` key, insert-or-ignore, never updated) by `WallWorkService`: live after each such `turn_complete` row (a chat's before its settle announce), and by a boot sweep retired by a versioned marker. No high-water mark: every catch-up records whatever its agent has unrecorded, so a turn durable late is still counted. `error` / `turn_cancelled` turns are not measured.
  - What is SERVED (nodes route `workedMs`, `RunDto.workedMs`, the settle announce) is CLI total + `wall_turns` sum (`servedWorkedMs`). `ChatTotals.workedMs` adds the run's whole `wall_turns` sum (`WallTurnDao.runSum`); the waterfall lanes and Stats stay CLI-only by contract. `wall_turns` is dropped with the run by `RunTeardownService`.
- `Run.workedMs` / `toolCalls` are written at every ending (complete, cancelled, error) and carried on the settle announce, never on activity announces. Null means not measured, never zero. A stretch the CLI runs by itself adds its own at its ending (`ChatService.countOffTurnWork`; a node's in `onOffTurnEvent`).
- A stretch the CLI runs by itself is dated by `off_turn_started` (raised by `runCliSession` ahead of its first output: the later of the waking report and the last result when a report came since the CLI last went idle, else the first output). A chat's open turn's holds and that start (`RunHoldRegistry`) are served on run state (`turnHeldMs`, `turnHeldSince`, `turnStartedAt`), since neither leaves a row. A turn of ours starting, a stretch starting and a settle start them over.
- `NodeState.polledSpend` is a per-EVENT ledger (the vendor revises charges): each poll replaces each event's figure; never a watermark. A node answers for its `sessionIds`, its callee `call_result` sessions, and their delegates (`spawnedConversations`).
- `Run.notes` is the user's alone and is never composed into a turn's instructions.
- Promoted payload columns (`Item.payloadId`, `toolNameLower`, `parentToolUseId`, `callId`, `utils/payload-refs.ts`) are filled only by `Item.stampPayloadRefs` (`@BeforeCreate`), so never write an item around the entity hooks (a native insert leaves them NULL and its run's lookups miss it). A run reads them only once `Run.payloadRefsVersion` equals `PAYLOAD_REFS_VERSION` (new runs are created stamped through `onCreate`, never a property initializer, which the schema sync would turn into a column default that marks every older run stamped); until then `ItemDao.payloadRef` falls back to the payload. `PayloadRefsSweepService` fills older runs after listen, in small batches. A change to `PAYLOAD_REF_KEYS` or the rule bumps `PAYLOAD_REFS_VERSION`. An older build writing the same profile after this one leaves its rows unstamped in a stamped run; that is unsupported (no downgrade).
- `RunKindRowsCache` holds a run's rows of kinds whose payload is never rewritten (`turn_complete`, `subagent_info`, `call_started`, …) and reads only past what it holds, capped at `ItemSeqAllocator.writtenThrough`; a run's deletion evicts it. `acknowledgeUserMessage` rewrites user messages, so `message` never goes through it. Two columns are filled in after insert: `inCall` (the cache reads a run that can hold calls only after `ItemCallIndexService.ensureIndexed`, and again from the start whenever `stampEpoch` moves) and the promoted payload columns (no reader of the cache may use them). A set is a `KindRowsView` (kinds, optionally a row filter); call records are `CALL_RECORDS` (`utils/call-seed.ts`), read `'fresh'` by every reader. The budget is payload characters across every set, never a count of sets.
- `Item.inCall` is which call's card a row is drawn in (`utils/call-membership.ts`, twin of the renderer's claim pass): `''` is the run's own flow, NULL is not stamped yet. It is stamped at the one insert seam (`persistItemAndEmit`, through `ItemCallIndexService`). Older rows are stamped per run before a conversation read (`ensureIndexed`) and by a boot sweep off the ready path, retired by a versioned marker: a change to the rule bumps `CALL_MEMBERSHIP_VERSION`.
- `GET /v1/chats/:runId/items` serves every row, page and anchors alike, with its base64 image blocks collapsed to a line naming them (`utils/collapse-image-blocks.ts`): the transcript draws a tool result's image block as JSON, and one page of a long run carried megabytes of them. The stored row keeps them.
- `GET /v1/chats/:runId/items` pages one conversation with `conversation=root` or `call=<id>` (a workflow run only). A root page also anchors, for each call it shows or that runs across it, the call's `CARD_READS` rows (per-kind caps), task lists since the newest whole one, an open turn's tool calls, its newest row, own message and named tool calls, and what closes them (those tool calls' replies, its shells and delegates) — the twin of the renderer's folded call card and pairing readers — plus the `unanswerable` rows of its approval cards.

### Agents: adapters

- Every static CLI fact is one `AdapterConfig`; see `agent-adapters.md`. Lapsed-account markers are evidence-gated (`[]` until observed).
- claude, first-prompt MCP gate (`claude-turn.driver.ts`, `TurnDriver.awaitPromptReady`): the first prompt of a process waits on `mcp_status` until two identical readings show nothing `pending`. Read `mcpServers`, not `servers`. Only `pending` blocks. Exits: 2s empty grace, `refused` releases, 5s silence (`CLAUDE_MCP_READY_SILENCE_MS`, not timed while hooks run), 15s with no change in the readings (`CLAUDE_MCP_READY_STALL_MS`, restarted on every change and while hooks run) under a 60s hard ceiling (`CLAUDE_MCP_READY_MAX_WAIT_MS`), then a notice naming the servers. A cancel during the hold drops the prompt; a throwing gate sends it anyway.
- claude `reload_skills` is sent only by the command-list probe (`commandListProbe`), never on a live chat.
- `withResponse` picks the AskUserQuestion answer field by question count; no caller picks it.
- cursor-acp's `mapMessage` throws by construction; `AcpSession` is its `TurnDriver`.
- codex (`codex app-server`, one process per conversation): `.claude/rules/codex-adapter.md`.
- `services/agent-session.registry`: kept CLI processes, one per run key, separate from `ProcessRegistry` (which tracks turns). It must subscribe to `session.closed` (a dead session is not idle and would hold a slot).
  - Idle window: the user's `Settings.keptSessionIdleMinutes` (bounds, default and push: `apps/ui/AGENTS.md` → *Settings*), arriving through the desktop-only `PUT /v1/agents/sessions/config` and held in memory only; `SESSION_IDLE_MS` (1 h) until the first push. One window for every run: a card's run is kept like any chat, whatever its column. A change re-times every waiting entry to its last use plus the new window on awake time (`AwakeTimer.retime`); one already past it goes through the ordinary idle close (parked, detached commands and off-turn work still re-arm).
  - The idle close alone is graceful (`SessionCloseOptions`): stdin first, then SIGTERM to the CLI's own group when it exits, or 2 s on (`TURN_END_EXIT_GRACE_MS`) for a CLI that ignores EOF, then SIGKILL. Eviction, staleness, teardown and shutdown stay immediate. Until it exits the process sits in the `closing` map: `processRoots` (so `held` and the sweep) still report it, and `closeRun` and `closeAll` escalate it. The close records its `SessionCloseCause` before it returns, because the exit it waits for is what settles the delegates still out.
  - Ceiling `sessionCeilingFor`: total memory / 8 / ~1GB, clamped [2, 16].
  - Eviction never takes a turn in flight, a parked card, or an entry with off-turn activity within `OFF_TURN_ACTIVE_MS`. That window must equal `DELEGATE_ROW_LEASE_MS`.
  - Off-turn events refresh (never arm) the idle timer (`touchOffTurn`).
  - A close that interrupted work writes one row at the close (`noteInterruptedSession`). A close that stopped detached commands (`detachedRunning`: a command a delegate still waits on is not one) — any close but `closeRun` and shutdown, a process ending on its own included (`endedRunning`) — also owes the key's next turn a `warning` row and a `<geniro-note>` after the prompt naming them (`runningCommands`, `utils/session-replacement-notes.ts`); the prompt line waits for a turn that carries a prompt (not a probe, resume-only or slash command) and a live process. Other closes write nothing. What the CLI left running is stopped separately (Run processes → Left commands).
- MCP harvest is age-bounded (it shadows the live listing); skill harvest is keyed `(agent, cwd, configDir)` — the profile is the account. MCP listing cache key includes `configDir`, the read runs under that profile's env, with a keyed single-flight (it launches the user's servers).
- `chat-metrics` composes only: it hands the adapter `{live, sessionId, configDir}` and each adapter answers from its own channel (`UsageReadChannel`; `account` needs neither a process nor a session).
- `chat-title`: writes a title only while it is still exactly what this service derived (manual renames are permanent); checks ownership before any spawn. Do not reintroduce asking cursor for a title. claude's title ask is a throwaway `haiku` turn, MCP withheld, temp cwd, once per conversation.
- `run-teardown` is the ONE delete teardown (cancel, wait, revoke tokens, purge rows with `softDelete` off, drop attachments and artifacts, announce `runDeleted`), shared by chat and workflow delete.
  - It never touches the tables exempt from teardown (root `AGENTS.md` → *Storage split*).
  - Only an ARCHIVED run's own CLI transcripts are deleted with it (`session-transcripts.service.ts`). It keeps a session another run names, or one that began before the run (an import). It never throws.
- `utils/`: nothing is named after a CLI. `CliSession.ask` must stay additive (control replies and events never consume each other's lines).

### Agents: turns and off-turn work

In `utils/spawn-cli.ts` unless noted.

- A `turn_complete` is HELD while a delegate it launched is out (`openWork`), in a turn of ours and in a stretch the CLI runs by itself (`deferredOffTurnTerminal`) alike, and both holds are announced as `turn_held` (off-turn only while no turn of ours is open). A report from a unit it waits on, or a main-thread detached command ending, ends the hold's announcement at once (`wakeOnReport`): claude starts working on a report immediately. Release the held result on the last report, at `idle`, or at the silence deadline. When the main thread speaks again (`RESUMES_A_HELD_TURN`) or a follow-up is delivered it ends nothing, but its segment is folded into whatever ending comes (`continuedSegment`, `offTurnContinued`) and counts on the live cost until then, never dropped: claude's cost is a step of its session ledger, so a dropped segment loses its money for good. A held off-turn result a turn of ours releases is stamped `insideTurn`. Only on a `session` stdin lifetime.
- For a CLI that announces session state, `idle` (claude `session_state_changed`) ends a held turn and writes off missed units. Do not reintroduce a grace timer after the last report.
- A follow-up written into a turn holds the turn until the CLI echoes it (`unconsumedFollowUps`, gated on `followUp.consumptionReported`). The held segment's usage is folded (`fold-turn-complete.ts`).
- Backgrounded commands never hold a turn; only `unit === 'agent'` does, and `'other'` counts as a shell.
- These holds (and cursor's `holdForDelegates`, below) are what each adapter's `backgroundWork.agentNote` promises the agent: change a hold, re-check its note. Never put a hold's bounds in the note.
- Every user-facing claude turn runs on a kept (`session`) process, an `auto` one without the permission dialogue included (`canHostSession`), so every one is held. Never send one back to a stdin-closed process: there claude holds back its own first result, waits on background commands too, and stops its agents after 10 idle minutes. A process spawned without the dialogue is never re-moded into another mode; the base respawns it (`spawnedOnDialogue`).
- A foreground unit (`is_backgrounded: false`) is never announced as background work until a `backgrounded` patch arrives. A delegate one still enters `openWork`; a command one holds nothing, and is recorded where it runs (Run processes → Left commands).
- `shell_open` / `shell_info` rows record detach and end. `announceShellWork` runs BEFORE `announceDelegateWork` and announces once per unit (`settledShells`). A settle for a shell this process never opened writes nothing: an earlier process closed it as it ended, and claude, resumed after a crash, reports its task `stopped` again.
- A command call the CLI never answered when its process died under the turn (not a Stop) is answered `CUT_OFF_COMMAND_RESULT` ahead of the turn's ending (`cutOffCommands`).
- A delegate's own detached command (`ownedByDelegate`) gets no shell row, but it is filed under its delegate through its launching call's `parentToolUseId` (either arrival order). While one runs, the delegate's `completed` settle is held, not announced: claude reports a delegate completed at each turn end and restarts it when the command reports. The held settle is announced when the delegate's last command ends; if claude then restarts the delegate, it reopens at once (deliberate: waiting for the restart could leave it working for good). If the process ends first, the held settle is announced as `stopped`, figures kept. If the delegate is started again while its settle is held, the held settle is dropped. A never-ending command keeps its delegate working. These commands count in `shellsRunning`, so the process is not reaped under them.
- A follow-up written into a CLI's stdin (claude) and not yet echoed as taken (`TurnState.unconsumedFollowUps`, with its `deliveryId`) dies with the process: claude queues it and, after an interrupt, runs it as a turn of its own only while the process lives (probed on 2.1.295), and a chat's Stop closes the session. So `spawn-cli` reports it `follow_up_dropped` when the process ends under the turn, and in `finishTurn` once the group has been signalled (`groupKilled`) — claude prints its cancel result inside the SIGTERM's window. A turn asked to stop (`cancelRequested`) refuses every further follow-up (`sendUserMessage` → false, the RUN_BUSY the composer queues on; otherwise a message sent right after Stop is steered into the stopping turn and lost).
- `restatesRunAsWorking` excludes `shell_open`, `shell_info`, `notice`, `follow_up_dropped`, a `tool_result` marked `endsBackgroundWork` (a background command's end, codex) and every `subagent_info` but an announced start (`backgroundOpen: true`) — a close, or a facts-only row such as claude's delegate price, which can land after its continuation settled; anything else from a settled run flips it back to `running`.
- `late_work_ended` (no row) says every call the CLI started or left open after its turn ended has ended or gone to the background, and ends that off-turn stretch the way a terminal event does (`endsOffTurnStretch`): the chat hands back the badge (`ChatService.settleLateWork`; a held delegate lease keeps it until expiry, a send that has claimed the run keeps it), a workflow node its own (`onOffTurnEvent`). Both read it ahead of their row gate, and the chat runs it only after the run's between-turn handlers already in flight (`offTurnInFlight`), since it would otherwise settle before the late result ahead of it restates the run, and drops it when a main-thread tool call arrives after it (`offTurnLateCalls`, counted on arrival): that is new late work, which ends with its own. Inside a turn the chat ignores it. Only the adapter knows its turn ended, so only it emits it.
- **A CLI that reports a backgrounded command FINISHED** (cursor) is checked against the process table (`sweepDetachedShells`, gated by `shells.unreportedDetachReason`). Only ANSWERED execute calls, prefix match, fed back through `announceShellWork`; poll only while something is out.
- Stopping a foreground command (`ChatShellsService.killForeground`): attribute first (only processes under this run's live CLI, never the CLI itself, and of those the ones its session recorded running that call's command when it did — `AgentSessionRegistry.recordedGroupsOf` — since two commands written alike cannot be told apart by text), then match. Signal the whole tree; write nothing. A detached command's Stop (`ChatShellsService.kill`) narrows its whole-table match to the recorded processes the same way while the session lives.
- A shell whose call codex has not answered is stopped from the process panel as a foreground command (`ChatShellsService.kill` → `stopForeground`): its written `/bin/zsh -lc '…'` is exec'd away. One found nowhere among the agent's processes is closed as already stopped once codex no longer reports it running (`recordedGroupsOf` answers null); while codex still does, the match missed a program that exec'd under another name, so Stop says it cannot tell which process it is and keeps the row.
- **A background DELEGATE's ending** for cursor is written by the daemon. The ACP session watches the delegate's own transcript, located by its brief, born after launch, unclaimed (`cursor-delegate-transcript.utils.ts`).
  - A turn ending closes nothing it can watch. Do not reintroduce a turn-settle closer. Unwatchable delegates become `untracked` ahead of the completed turn's `turn_complete`.
  - A turn with watched background delegates it launched holds, then wakes the agent with their reports (`holdForDelegates`, `MAX_DELEGATE_WAKES`). `DELEGATE_HOLD_IDLE_MS` must stay under spawn-cli's 30-min silence deadline. The hold is announced like spawn-cli's (`turn_held` with the count, then `open: 0` from `endHold`), so the composer sends straight in. While held, Stop is `withdrawHeldPrompt` and a message ends the hold.
  - A resumed delegate appends to its old transcript; the claim moves to the newest brief. The delegate it continues is closed `stopped` with recovery off (`recovery: null`).
  - A session close marks every delegate still out `untracked` with `trackingLost: 'process-ended'` (`processEndedCloseEvent`); the boot sweep, the workflow executor's `closeStrandedWork` and spawn-cli's exit flush do the same. Its work is over and only its outcome is unknown, so it is drawn as settled. A close that is the user's Stop says so (`SessionCloseCause` `'user-stop'`): the chat Stop passes it to `AgentSessionRegistry.close`, a workflow Stop or archive marks the run's kept processes first (`noteUserStop`). The session itself holds the cause (`AgentSession.noteCloseCause`, withdrawn by its next turn), so however the process then ends — a later close or its own kill after a refused interrupt — every writer above closes the delegates still out `stopped`. The open set is folded from durable `subagent_info` rows, ranked like the renderer's `subagentBlockStatus` (twin).
  - codex sub-agents (`subAgentActivity`) close on whichever ending arrives first; no turn-settle closer.
- An outcome-less ending reads `untracked` only for a delegate whose recovery ref still stands; without one (every row from before refs) it keeps its old reading: a close or a reply reads `completed` (`failed` on an error reply), and a turn that ended without a reply reads `cancelled`. A delegate the user's Stop cut off reads `cancelled` either way. The delegate's OWN turn ending decides (`turn_cancelled` is a Stop); the run's status is read only when no ending of its turn exists, since a chat settles after every turn and its status describes only the latest one.
- `SubagentRecoveryService` reconciles durable untracked children on a run's WebSocket join (open/reconnect), on new loss evidence, and — 5 s after boot, off the listen path — for runs that recorded a ref in the last 24 h. Each reconciliation has at most three attempts; duplicate joins share that budget and recovered terminal rows never restart it. A delegate settled by its rows, or still unknown when a round ran out, is retired at its row version: no later trigger reads it again until a newer `subagent_info` row of its own appears — or, for one given up while it may still run (not process-ended), until a 10-minute cooldown passes — and the run's tool rows are read only for delegates the declarations leave unresolved. Retired delegates are remembered for the newest 500 runs. `AgentAdapter.recoverSubagent` reads existing state through the CLI's read API or an adapter-local record reader; missing evidence and legacy rows without a reference stay unknown. Recovery preserves node/call ownership, never starts work, defers to live subordinate-command holds and rechecks racing live outcomes. Resumed child identities belong only to their newest launch.
- A bracketed delegate's off-turn steps are not the run working (`BackgroundWorkCounts.isDelegateOut`).
- A workflow run's stranded delegates and shells are closed by the EXECUTOR (`closeStrandedWork`), ahead of its terminal row. Every close carries its open row's node AND call id (`ownerFields`).
- `workflow_info` rows come only from roster-bearing `task_progress` lines; the anchor is emitted at `task_started` (the only line carrying the name).
- Every finished compaction is one row; with no summary the daemon writes `COMPACTED_WITHOUT_SUMMARY` (`compaction-rows.ts`). Delegate compactions are skipped.
- A turn never settles on a continuation's result (`turn_complete.continuation`), unless the continuation absorbed this turn's prompt (echo matched, `promptTaken`).
- Between-turn events (`handleBetweenTurnEvent`) are persisted exactly like in-turn ones, and a settled run goes back to `running`.
  - Exceptions: a CANCELLED run stays cancelled (rows still written); a run whose `running` this path did not write is left alone (`offTurnRuns`).
  - Main-thread `text_delta` / `thinking_progress` / `reasoning_delta` also flip it back (`restatusAfterOffTurnSignal`); `context_progress` never does.
  - An unbracketed delegate's rows take a lease (`DELEGATE_ROW_LEASE_MS`), not a latch.
  - A session close restores the badge (`settleAfterSessionClosed`), except during shutdown. A process dying on its own is a close too.
- The silence deadline does not run while a verdict is outstanding; `respondApproval` rearms on delivery.
- Only `cancelRequested` settles `cancelled`. Any other signal settles `failed`, naming the signal.

- `move_stage` (`StageService`, `v1/graphs` — it reads the run's snapshot through `RunWorkflowService`, which `v1/agents` may not import): offered to every agent node of a run whose snapshot has walkable stages (`Workflow.stages`, rules in `graphs/utils/stage-validate.ts`, twin of the renderer's). `StageService` is the ONE writer and needs no sink: a move is checked against the progress folded from every `stage_change` row (`graphs/utils/stage-fold.ts`), then written as a run-level `stage_change` row (seq reserved here, like `noteOnRun`), then folded into `Run.stageProgress`, then announced as `run_status.stages` (read back through the wire's parser) — all in one chain per run (`RunWriteQueue`, which archiving also goes through, so a move never lands on a run archived mid-move; deleting does not, so a move and a nudge re-read that the run still exists before writing), so two agents finishing the same stage cannot both succeed (`STAGE_NOT_CURRENT`). A refusal names its fix (`NEXT_REQUIRED` lists the branches, `NOT_REOPENABLE` the stages that can be). The listing is synchronous, so the executor registers each run it drives (`StageService.register`) and forgets it with the run (`disposeHostPublishers`); a CLI lists its tools only when a pass or wake starts it. What an agent knows: the static stage map is an instruction part (`stageMapPrompt`, from the snapshot, gated on the MCP tools like the call surface — it joins `sessionKey` and never changes mid-run), and the CURRENT stage rides each turn's prompt, after the user's words (`stageNotice`, on the delivery notice's turns — never a compaction, a geniro command or a slash command, which carry neither the stage line nor the delivery notice; a carried compaction summary still leads one), every call-tool reply (`stage`, beside the envelope like `unread_team_notes`), every call-broker wake (`RunCallCapability.currentStage`) and every `move_stage` reply — never the system prompt. A follow-up written into a live turn carries none (it reaches `beginAgentTurn` only on the next turn). A staged run's row is created with its starting progress (`initialStageProgress`, the one write outside `StageService`, so the first projection every client is handed already carries it); `StageService.current` folds the rows on a cache miss and rewrites the column when its rev differs (an older run with none, or a column write that failed); a move whose column write fails still counts and stays cached, and the column is written again by its own retry (`STAGE_COLUMN_RETRY_MS`) or the run's next `StageService.current` or move (`unsynced`), each revision announced once — until then a listing, the board card and `get_task` read its older rev. A held nudge is also withdrawn when the run is archived (`StageService.generation`). `Run.stageProgress` and the rows go with the run's teardown. No auto-approval (the executor auto-approves no host tool but the shared memory's).
  - The user's own moves (`POST /v1/workflows/runs/:runId/stages`, `StageWakeService.userMove`): the same `StageService.move`, actor `user` with `via` from `cameViaRemote`, `expectedRev` refused `409 STAGE_PROGRESS_CHANGED` when stale, any other refusal 400 with its code, an archived run `409 RUN_ARCHIVED`. The run's LEAD (`leadAgentId`: the first agent the trigger feeds, node order) is then woken in its own conversation with the move and the user's reason through `HostWakeBus` — held while its turn runs, a host turn when it ends. A run no pass has driven since the daemon started, or whose pass the user stopped, has no waker that takes a wake (`GraphExecutorService.canWake`): when its next pass would start the lead and no other agent, it is continued with the wake under geniro's own row (`continueAsHost`, never a user message, never throwing — the move is already written); otherwise the bus owes the lead a note for its next turn and the route answers `woke: false`; a run whose trigger starts no agent has no lead, and the route says so (`hasLead: false`). Each move and each nudge is its own wake key (`stage:<runId>:<rev>`, `stage:<runId>:nudge:<rev>`), so moves made while the lead works join one turn rather than replace each other; a held nudge is withdrawn once a move changes the revision. Never `walkAgain` a run whose pass would start other agents for a stage wake.
  - The nudge (`StageWakeService.nudgeIfStalled`, on `GraphExecutorService.onRunSettledCompleted` — the pass roll-up and a woken run's settle, `completed` only, never a shutdown's): a run idle with a stage still current, not archived, with no usage-limit reset scheduled (`Run.resetWakes`) and no monitor of its still running — waits the status cannot show —, gets ONE `nudge` row and a lead wake per (stage, revision); a second settle at the same point — or the first, when the run has no lead — writes `stalled` and `run_status.notify` instead, and nothing more until a move changes the revision. Both are `stage_change` rows (actor `system`), so a restart re-reads them; the fold ignores them.
- `team_note` / `team_notes` (`TeamNoteBroker`, workflow runs only — a chat registers no sink): one run-wide store every agent of the run reads, wired to the others or not. A note is an append-only `team_note` row in its author's transcript, filed in the call its conversation answers (`callAnsweredBy`); a correction is a newer note naming the old seq in `supersedes`, folded by `utils/team-note-fold.ts` for the tool and for `GET /v1/chats/:runId/team-notes` alike. Writes of one run are serialized so the per-run cap (`TEAM_NOTES_PER_RUN`, counted from the table) holds under racing writes; caps refuse, never truncate. Which notes each conversation was shown is in memory, and only a shown note counts as read, so a narrowed read leaves the rest unread; a superseded note never counts (its replacement is the note to read); after a restart every other note it did not write counts as unread again (over-reports, never hides). The unread figure rides `team_note` / `team_notes` replies, every call envelope (`unread_team_notes`, beside the envelope, not an arm of it) and the call broker's wake text (`RunCallCapability.unreadTeamNotes`) — never the system prompt or the May-call block, which `sessionKey` hashes.
- `monitor` / `stop_monitor` / `list_monitors` (`MonitorBroker` over the leaf `MonitorRegistry`): an agent's shell command (`/bin/sh -c`, deliberately a shell — the CLI's permission prompt shows the line) whose output wakes it. Spawned by `startManagedStream` (`utils/managed-stream.ts`: detached group, journaled, `buildChildEnv` then `runTagEnv`, ProcessRegistry key `monitor:<runId>:<id>` — never the bare run id, which would read as a busy run — stdin closed, stdout and stderr together, an `awakeTimeout` deadline, group TERM then KILL; the group is ended the moment the shell exits — TERM at once, KILL after the grace only while a member seen at the exit still lives in it with its start time (`isGroupAnchored`), since an emptied group's id can be reissued — and never signalled otherwise after it). `MonitorBatcher` (`utils/monitor-batcher.ts`, chord's limits): ANSI stripped, a carriage-return redraw keeps what a terminal shows (also across chunks), registered secrets masked before lines are cut at 1000 characters, a 200 ms window, at most 100 lines or 16 KiB per message (the rest counted), stopped as `flooded` past 1000 lines or 256 KiB in 10 s; timeout 1 s–1 h, default 10 min; 8 per run. Out-of-range arguments are refused, never clamped. Ids `mN` count per run; `stop_monitor` and `list_monitors` see only the calling conversation's. Offered only where a geniro tool call is put to the user first or the turn is `auto` (`offersMonitorTools` over `AdapterConfig.hostToolCallUngatedReason`, null on every CLI: measured per CLI beside its config; a workflow node only when every pool member passes). Never auto-approved: no `isHost<Name>Call`. The permission card keeps the CLI's remember choices, which remember the TOOL, so it says that remembering approves every later monitor command (user decision; `namesGeniroMonitor` in the renderer).
  - Delivery never enters a running turn, on any CLI. Output arriving while the conversation works is held, one message per monitor with later batches merged in, and goes out when the turn ends: a chat through `MonitorChatDelivery` → `ChatService.sendMessage(…, {ownTurn, hostRow})`, whose opening row is the monitor `system` row instead of a user message (released from `onTurnSettled` and only once the daemon listens (`startDelivering`, from `onListening`), held while `hostTurnHold` says a turn runs or a question/plan/patch card waits, held again on `RUN_BUSY`; an archived chat stops the run's monitors; a send that fails before its opening row is written (a folder gone, a failed write) is tried again at the chat's next settled turn — never the failed send's own settle — or after `MONITOR_SEND_RETRY_MS`, never on new output, and a thread Stop while it is out cancels the retry; the `MONITOR_SEND_ATTEMPTS`th failure in a row, or one after the row was written (a model refused — a retry would show the output twice), stops the run's monitors and owes the chat's next turn a note naming them, and a failed host turn settles quietly (`hostTurn`); dropped by the thread's Stop (`onStopped`); its settle announces `hostTurn`, so no banner is posted for it); a workflow conversation through `MonitorGraphDelivery` → `GraphExecutorService.wakeConversation` (Workflow call runtime). The text sits in a `monitor-output-<random>` fence after a line saying it is the command's output, under chord's `<message from="<description> · monitor[ · <end>]" monitor="mN">` header.
  - Rows (`monitors[]` on a `system` payload, `woke` true for a delivered message — twin of the renderer's `chats/monitor-payload.ts`): the start and an unannounced end are written by `MonitorRowWriter`; a delivered batch or end is the opening row of the turn it starts, and a delivery that drops a message carrying an end writes that end (`writeEnds`) unless its opening row was already written (`onHostRowWritten`), so no start is left without one and no end is written twice. A stop by the agent, the thread's Stop or teardown ends `stopped` and wakes nobody; the panel's Stop (`processes/stop` `monitorIds`) ends `stopped` and wakes the agent, telling it the user stopped it. `MonitorOutcomeSweep` (boot, after `ActionOutcomeSweep`, handed the stop cause `closeInterruptedRuns` read) ends every monitor whose newest row is not an end as `interrupted`: a chat's wake is handed to `MonitorChatDelivery` (sent after listen, under its holds) unless the stop was `crash`/`unknown`, when its next turn is owed a note instead; a workflow conversation is owed a note under its own session key (`oweKeyNote`: the node's, or the callee conversation's, read off the monitor's first row — its start, which carries `conversationId`); an archived run gets neither. The run's ids seed the registry's counter (`noteUsedIds`), which is per launch, so a new monitor never reuses one. A workflow stretch reopened by monitor output, with no other turn and no user message in it, announces `hostTurn` too. A monitor is never started again.

### Thread analysis

"Analyze thread": `ThreadAnalysisService`, `POST /v1/chats/:runId/analyses`.

- An analysis is an ordinary chat whose `Run.analysisSourceRunId` / `analysisSourceSeq` name the thread it reads and the seq its reads stop at (the source's newest row when it was started). Its method is `taskInstructions` (`utils/thread-analysis-guide.ts`), never a plugin skill at run time. Its approval mode is the dialog's, else `ANALYSIS_DEFAULT_APPROVAL` (`auto`), never `CHAT_DEFAULT_APPROVAL`: it works unwatched in its popup.
- It belongs to its source, like the builder's chat to its workflow: `listChats` and chat search (`ChatSearchIndexDao.match` / `run`) never return it, `GET /v1/chats/:runId/analysis` finds it (`{analysis: null}` for none, newest wins), and there is one per thread.
  - A start replaces exactly the analyses that existed BEFORE it created its own, and only AFTER the new one has its brief: a failed start keeps the old one, and two racing starts never delete each other's.
  - Deleting the source deletes it (`ThreadAnalysisService` on `bus.allDeleted()`, whichever route deleted the source); what that misses (a daemon stopped before the announce, a failed delete) is swept at boot (`sweepOrphans`).
- Its four tools (`read_analyzed_thread`, `report_recommendations`, `mark_recommendations`, `save_workflow_change`) are offered only while an analysis turn runs: `ChatService` registers an `AnalysisBroker` sink per turn only when the run has a source — or is a workflow's builder chat (below). (`save_workflow_change` is also a builder chat's — *Host tools*.) The sink carries the source and snapshot, so no tool takes a run id from the model.
- **Builder chats** (`Run.editsWorkflowSlug`) get the workflow analysis's reader and card too (user decision: the dock has the same tools and information as "Analyze & improve"). Each turn snapshots the workflow's `BUILDER_CHAT_ANALYSED_RUNS` newest unarchived runs as it begins (`ChatService.builderAnalysisTurn` over `utils/run-snapshots.ts`, the snapshot `ThreadAnalysisService` takes too), read before any host tool registers; a workflow with no run, or a failed read (logged), leaves the turn without the analysis tools. Nothing is stored on the run. Its brief carries the workflow analysis's method (`builderChatAnalysisGuide`, the same sections as `workflowAnalysisGuide`) in a `<workflow-analysis>` block, with two differences: repo items point at the runs' own repository (each run's `cwd`), since the builder works in the library, and a selected `W-` item goes on a `propose_workflow` card, never a save (its `save_workflow_change` stays a dry run), and is marked once that card's verdict arrives. The Apply route takes a builder chat's card (`RecommendationsApplyService`). Known limit: the builder runs in the library directory, which a workflow analysis is kept out of, so an agent reading run output there sits beside every workflow file under the builder's `acceptEdits` default.
- `read_analyzed_thread` pages ~22KB (codex cuts a tool result near 10k tokens): timing from `ThreadTimelineService` (the waterfall's UNCAPPED fold plus id-paired tool durations and the critical path, cached per `(runId, snapshotSeq, working)`, after the run's call membership is stamped), rows clipped at 2KB, one row in chunks. Images are collapsed (`collapse-image-blocks.ts`, twin of the renderer's export) and secrets masked before any cut; every answer leads with `HISTORY_RESULT_PREFACE`.
- `report_recommendations` refuses an evidence seq that does not exist at or below the snapshot, a workflow item for a plain chat, a memory item while the shared memory is off (the guide then leaves the memory target out too), a duplicate id, an id whose `W-`/`R-`/`U-`/`M-` prefix contradicts its target, and an item with no `territory`. Each item keeps to one territory, `process` (how the agents work) or `domain` (what the work itself needs to know), and the card tags it; the guide has a finding that needs both filed as two items. The card's timing strip is measured by the daemon, never taken from the agent.
- A `user` item edits an agent's own standing-instructions file, which reaches every project that agent works in. Its path is an adapter fact (`AdapterConfig.userInstructions`, resolved by `AgentAdapter.userInstructionsFile` under the run's `configDir`), listed to the analysis in the overview's `source.userInstructions` (chat) and in view=workflow's `userInstructions` (every node and pool member the run's snapshot ran), each with its size as it stands now (`sizedUserInstructionFiles`: its own length, not what it imports; `exists` false for a missing file, null for one it could not stat or a CLI that keeps none). Never spell a path in the guide.
- view=workflow's `instructionSizes` is every agent node's always-on block (`InstructionSizesService`, the inspector's measure) composed from the library's copy with the read run's own `customInstructions`, `memoryIndex`, `taskInstructions` and `replyLanguage` (`AnalysedWorkflowRef.instructions`; none when that run is gone), plus `inThisRun` where the run's own copy composes a block of another length.
- The overview counts failed tool calls (a `tool_result` with `isError`, paired in `pairToolCalls`) and sums the tokens and cost the CLI reported; a figure no turn reported stays null.
- An Apply (`POST /v1/chats/:runId/recommendations/apply`) is a user message carrying the selected items in full and `payload.apply: {cardSeq, ids}`; it is refused `RUN_BUSY` while a turn runs, never delivered mid-turn, and `ALREADY_APPLIED` for a card that already has one (the renderer reads "applied" from its window only). `save_workflow_change` (`WorkflowChangeService`, in `v1/graphs`) writes only `W-` ids in the NEWEST Apply (user messages read in seq order), refuses a hash drift, a deleted file and an invalid graph, and writes a timed backup first. It is not auto-approved.
- A builder chat's `save_workflow_change` runs under `WorkflowChangeService`'s `builder` authority, always as a dry run (its change is written behind `propose_workflow`'s card — *Host tools*): no Apply and no `ids`, `baseHash` or `dryRun` argument (all refused), the same edit and graph checks, and its edits apply to the file as it stands. Its version check is per turn: the sink records when the turn began, and the turn's first check is refused (`HASH_DRIFT`) when the file was written after that — the canvas does not save while the chat works, so something else wrote it; every later check is held to the hash the last one read or a refusal reported (`WorkflowBuilderBroker.noteVersion`). A `configDir` it wrote back as a `read_workflows` token is restored (`restoreConfigDirs`, `CONFIG_DIR_UNKNOWN` for one naming no profile of this workflow). `backup_workflow` (`WorkflowChangeService.backUp`, which answers the newest backup instead of copying a file unchanged since it) is the user's to ask for: an approved card already backs the file up.
- `save_workflow_change` takes EDITS (`graphs/utils/workflow-edits.ts`: unique `find`/`replace` in a string value, `path` set or remove), applied to the library copy as it stands (an analysis's at the hash it quotes). A `path` walks own keys only and refuses `__proto__`, `constructor` and `prototype`: the model writes it. Never take the whole workflow back: a library workflow runs to 250KB, and re-emitting it as tool arguments was minutes of silent generation per save.
- Timeline spans are clipped to the read's `[from, to]`; the critical path takes, at each step, the work still going latest before the cursor (an interval running past the cursor counts up to it); tool calls pair by node, call and id (ACP ids restart per session). Whether the source was working at the snapshot is recorded at the start (`Run.analysisSourceWorking`) and every read folds with it, so one snapshot always folds the same.
- **Workflow analysis** ("Analyze & improve", `WorkflowAnalysisService` in `v1/graphs` over `ThreadAnalysisService.startWorkflow`, `GET /v1/workflows/:slug/analysis`, `POST /v1/workflows/:slug/analyses`): the same chat, tools, card and Apply, reading a workflow's `runs` newest unarchived runs (at most `MAX_ANALYSED_WORKFLOW_RUNS`) instead of one thread. `Run.analysisWorkflowSlug` names the workflow and `Run.analysisRuns` (`utils/analysed-runs.ts`) each run with its own snapshot seq and working flag; `analysisSourceRunId` stays null, so every "is this an analysis" check reads both columns (`listChats`, chat search, the proposal gate, Apply, `ANALYSIS_OF_ANALYSIS`). The runs are chosen by the daemon from every run of the slug, never from a client's list; a run with no rows is skipped, none left is `ANALYSIS_NO_RUNS`.
  - It belongs to the workflow: deleting one of its runs keeps it, deleting the workflow deletes it (`WorkflowChatService.deleteWorkflow`), and a boot sweep deletes those whose library file is gone (`WorkflowAnalysisService.sweepOrphans`). One per workflow, replaced on the same terms as a thread's. It runs in the folder the dialog sent, else the newest read run's; with neither it is refused `ANALYSIS_FOLDER_GONE` and the dialog asks — never the library directory, which would put an agent reading untrusted run output beside every workflow file.
  - `AnalysisTurn.workflow` carries the runs; `sourceRunId` is the newest of them. Every `read_analyzed_thread` view takes `runId`, limited to those runs (`analysedSourceOf`, `NOT_ANALYSED` otherwise; a thread analysis takes none but its own). `view=runs` answers each run's totals and outcome (`Run.runOutcomes`) with every node's work in that run (`runs[].nodes`, `runNodeFigures`: the lane's turns, tools and bill, its working time — the CLI's own plus the `wall_turns` ledger through the run's snapshot (`servedWorkedMs`), as in `nodes` — and from the timeline its busy and blocked wall time and its share of the critical path, null for a node with a completed turn its CLI did not time, whose span the waterfall draws from the lane's previous row and which measures nothing; `models` times only measured turns, `timedTurns`), every node's totals (`nodes`, from the waterfall's lanes: the true turn count and a polled-spend CLI's bill), every caller→callee edge's calls over the runs (`calls`, `callFigures`, from the waterfall's call spans), and every node's turns per CLI and model (`models`, from the turn spans; a turn that reported no model — a failure, a Stop — is counted on the model its node last reported in that run; one before any report is filed apart under the model the run's own frozen copy configured (`configuredModels`, never the live `node_state.model`), `modelSource: 'configured'`. A pooled node is followed per member: every waterfall turn carries `member` — the CLI and configured model its own usage row (`turn_complete`, or a failed turn's `error` / `turn_cancelled`) names, member 1 when the row names none (`ChatWaterfallService`, `poolMemberOf`). A pool hand-off (`ItemDao.poolHandOffRows`, the executor's `nodePoolHandOff` row) splits the open turn: the attempt handed on is drawn as a failed turn of its member, and the rest goes on as the member the row names, so a member that keeps hitting its limit counts its failures. A pooled turn no row names a member for is left `model: null`, `modelSource: 'unreported'`), each over every row of each run up to its snapshot (`utils/workflow-runs-fold.ts`) — what the guide (`workflowAnalysisGuide`) compares models and the graph's structure from, and what its report (`WORKFLOW_REPORT`: a scorecard, the versions and a verdict on each earlier change, time per run and per agent, calls, models, instruction size and a graded instruction quality, section by section in the reply before the card) copies its figures from. It is masked whole, then paged like `view=workflow` (`pagedAnswer`, `offset`), never cut; a read from offset 0 folds afresh and keeps its text per run set for five minutes after its last read, so every later page is cut from that text; a later page asked after it lapsed is refused `RUNS_CHANGED` (read again from 0).
  - Versions: `view=runs` names each run's graph version (`snapshotVersion` over its own frozen copy, the hash the workflow ledger stamps) with its number and whether it is the library's now, and folds the analysed runs per version (`versions`, `versionFigures`). The numbers are the stats module's (`WorkflowHistoryService.versionIndex`), handed to `ThreadReaderService.read` by the tool, since `v1/agents` may not import `v1/stats`; a failed read names versions by hash alone.
  - History (`view=history`, answered by the tool from `WorkflowHistoryService` in `v1/stats`, masked whole, then paged like `view=workflow`): every recorded version newest first with its diff (`WorkflowVersionsService`) and figures over EVERY run the ledgers kept, deleted ones included (runs, cost, turns, the CLIs' own worked time, pull-request outcomes — `foldWorkflowHistory`); the change log; and every recommendation filed about the workflow with its status (`applied` / `skipped` / `failed` as marked, `selected` in an Apply but never marked, `open` while its chat exists, else `not-selected`), linked to the logged change that carried it out. Offered to any analysis with a workflow (`analysedWorkflowOf`): a workflow analysis, a builder chat, a thread analysis of a workflow run.
  - The change log (`workflow_change_log`, `WorkflowChangeLogService` in `v1/graphs`, teardown-exempt) gets one entry per library write geniro makes on someone's say-so, AFTER the file is written (a failed log write is logged and never refuses the save): an analysis's applied save (`source: 'analysis'`, the Apply's ids and card seq, the items' titles), an approved `propose_workflow` card (`'builder'` when the chat edits that workflow — its ids read from the card's summary and reason, which the builder's brief has name them — else `'chat'`, with the user's note), and a version restore (`'restore'`). Each carries the graph versions it moved between. A canvas save is not logged: a version no entry made reads as edited by hand.
  - The recommendation ledger (`workflow_recommendations`, `RecommendationLedgerService` in `v1/stats`, teardown-exempt) copies every `recommendations` card a workflow analysis or builder chat files, every Apply selecting from one and every `recommendation_outcome` mark, off `bus.all()`, serialized per chat, with a boot sweep over the chats that still exist; a card is filed once, the first selection stands, and a mark moves forward only by its row's seq. A new analysis deletes the chat it replaces, so this copy is the only record of what was recommended before.
  - Evidence names its `runId` and is checked against that run's snapshot. The card carries no timing strip (one run's would pass for the workflow's). `view=workflow` and `save_workflow_change` act on the analysis's own slug (`ThreadReaderService.analysedWorkflowOf`); `view=workflow runId=…` sets the library against that run's own copy. Every "is this an analysis" check on a row is `utils/analysed-runs.ts` `isAnalysisRun`.

### Question cards

- A standing `ask_user_question` card belongs to the TURN, not the MCP call (`utils/standing-questions.ts`). An abandoned call DETACHES, an identical re-ask ADOPTS, an early answer is HELD for the next ask, and a reworded question is a new card.
- For a CLI whose client will not hold a call open (`AdapterConfig.hostQuestionDeferredReason`, cursor): the tool answers `posted` at once and the answer arrives as the next message. Do not reintroduce polling.
  - The card outlives the turn (`sweepNode` skips `deferred`) and is retired by a new turn (`sweepDeferred` → `unanswerable`).
  - Write the verdict row and clear `Run.pendingQuestion` BEFORE the answer message goes out.
  - One per run, rehydrated at boot (`rehydrateDeferredQuestions`); a different second question is refused. Every row names its `kind` (`question`, `plan`, `patch`); a row that names none is unreadable and cleared at boot. No compatibility readers.
  - `propose_plan` and `propose_patch` take the same deferral, column and one-card rule (`PendingCardSnapshot`). Approve or Reject starts a turn whose message is the verdict, a plan's note included. Apply runs `applyHostPatch` from `resolveValidCwd(run.cwd)` when that message is sent, after a restart too. A missing folder, or an `old_string` no longer matching exactly once, comes back `stale` and nothing is written. Whole-file patches capture the contained target's byte SHA-256 or absence before raising the card, carried in the blocking closure or `PendingPatchSnapshot.fingerprint`; Apply checks the opened file before truncation, and an absent target is created exclusively. Changed, created or deleted targets are `stale`. A stored patch without the fingerprint field is unreadable and cleared at boot; null records that no fingerprint could be taken, so whole-file Apply refuses it. Every failure after Apply is `stale`, never `unavailable` (the user did see the card). Their listing says the call returns at once (`register(…, { answersAtOnce })`, read by `PlanBroker` / `PatchBroker.answersAtOnce`).
- cursor's own `cursor/ask_question` is not used for `ask_user_question` (option ids only).

### Pull requests and task lists

- A thread's pull requests are read from its own transcript (`pull-request-capture`). Never key them by branch.
  - `Run.pullRequests` holds the ones it OPENED. Only these end a card on merge (`TaskMergeService`), count in Stats (`announceOpened`, the backfill) and stand as a card's result.
  - `Run.touchedPullRequests` holds the ones a conversation's CLI record names (`AgentAdapter.readSessionPullRequests`: claude's `pr-link` lines — created, pushed to, checked out, commented on, merged). Shown on the chat surfaces only: `readDisplayedPullRequests` merges both for the run wire and the run-status announce, marking each `opened`. A task card and `get_task` show the opened ones (`RunDao.pullRequestsOf`; the board reads them with each card's stage line in one read, `RunDao.boardFactsOf`).
  - A CLI record is kept only when the run opened that pull request or its own rows name it (`textNamesPullRequest` over `ItemDao.pullRequestNamingCandidates`: its URL or API path, or a `gh pr <verb>` naming its number). claude answers every push with `gh pr view` in its own folder, so in a shared checkout its record names whatever pull request that folder's branch has. An unnamed record is re-checked only over rows written since (`unnamed`, in memory); a from-start pass re-checks the carried ones too, and a list that shrinks is announced (empty included).
  - Transcript signal: a `…/pull/\d+` URL that ENDS a line (alone, or after whitespace or `=`; never a bare `:`, which is `grep -n`) in a `tool_result` whose paired call ran `gh pr create` in command position (prefix words walked back). A URL mid-line is a quotation.
  - A record has no row of ours: it takes the seq of the tool result its time falls on (`ItemDao.toolResultSeqAt`), so ordering stays seq-based.
  - Incremental: the marker advances even when nothing was captured. Errors are swallowed per run. No repeating re-scan sweep; a rule change bumps `PULL_REQUEST_SCAN_VERSION`, and a run scanned under another version is re-read from the start once, by the boot sweep (`rescanOutdatedQuietly`) or its own turn end, never by a listing (a listing's re-read announced every run it re-read, and the renderer re-listed for each).
  - One pass per run at a time (`syncSerialized`), each over the row as this service last wrote it, so overlapping listings and a turn end never announce one change twice. A listing never waits on a pass in flight.
  - The marker stops at `ItemSeqAllocator.writtenThrough` (a reserved seq is not on disk yet); a pass reads candidates in seq windows with a yield between them and looks up their calls in one `rowsByPayloadId`, never a per-result `LIKE` over the history.
  - Store identity only (owner, repo, number, url), never title or state.
  - Every list the run wire or a run-status announce carries attaches each pull request's newest recorded outcome (`Run.runOutcomes`, read fresh by the capture pass), since the renderer replaces the whole list from each announce.
- Worktrees a thread worked in (`RunNamedPathsService`, `POST /v1/chats/:runId/named-paths`): of the candidate folders the desktop app lists, the ones a `tool_call` of the run names — the path or its run-folder-relative form (two segments or more), followed by a path boundary; a relative form must also begin one (a shell word boundary, a quote, an escaped newline or tab, or `./`), so it is never found inside another repository's path. Never the run's folder or one holding it. Each run's reading is remembered in memory (scanned seq, clamped to `writtenThrough`, + verdicts), so a later ask reads only newer rows — a folder asked about for the first time reads the whole history once, in seq windows that yield the event loop. Asks for one run are serialized.
- `task_list` rows: `mode` says snapshot vs patch and is never inferred; absent means patch. The run fold is keyed by node AND `callId` and skips delegate rows (`parentToolUseId`).

`v1/graphs/` (library: `*.geniro.yaml` under `<userData>/workflows/`).

- `calleeSummary` (`utils/callee-text.ts`) is the one line a caller sees about a callee: label plus `description`, never `role`.
- Every turn that answers a call carries `ANSWERING_A_CALL` as its own instruction part (`answeringACallPrompt`, not gated on the call tools), so a callee with no callees hears it too; `ANSWERING_WITH_CALLS_OUT` follows it in the "May call" block and in `call_agent`'s description, which must agree.

### Workflow call runtime

- The call token reaches a CLI in an HTTP header in `session/new` (ACP) or thread config (codex); claude's 0600 `--mcp-config` file is in `.claude/rules/agent-adapters.md`. Never argv, never a file in the worktree.
- Admission is "has outgoing call edges". Do not reintroduce a cursor trust probe, a `.cursor/mcp.json` merge or a `cursorCalls` capability.
- No cap on a run's total calls (depth cap only).
- Active-turn cap (`Workflow.maxActiveTurns`, never above `MAX_PARALLEL_AGENTS`, which `GET /v1/capabilities` serves as `maxActiveTurnsCeiling`): one gate per pass (`utils/turn-semaphore.ts`) counts callee turns at every depth. Only a FRESH call waits, writing a `queuedCall` system row (twin of the renderer's `CallBlockEntry.queued`; run state serves it over the whole run as `RunCallState.queued`, ended by the call's first `status` row or its settle); a cancel or Stop takes it out of the queue, and its silence watchdog is suspended while it waits (`CallBroker.noteCalleeQueued`). A turn blocked in `call_agent` / `await_agent`, on its own parked question or on a card stops counting (`RunCallCapability.turnBlocked`, reported by the broker off `waitingOwners` ∪ `blockedOwners`), and is counted again WITHOUT waiting when it unblocks; a wake (`startOwnerTurn`'s `wake`, a held call's wake) never waits either. Never make a blocked or returning turn re-acquire through the queue: a turn holding or awaiting a slot while waiting on turns that need one deadlocks the run, and a failed re-acquire after `handToWaiter` loses the question it delivered.
- Silence watchdog (`CALL_SILENCE_DEADLINE_MS`): surfaces, never settles. It writes one `stalledCall` system row with its text under `message`. Suspended while the callee has a tool call open, is parked, or is held. Cleared on settle and in `unregisterRun`.
- A callee's kept process is keyed by its CONVERSATION (`<runId>::call:<first call id>`). A continuation while a call on it is live is refused `THREAD_BUSY`. Install the process closer after `startTurn`; rebind the off-turn sink every turn.
- A parked question's 30-min TTL is suspended while its owner is blocked; blockers are a set of named cards, not a count.
- Call state survives a restart via the transcript (`v1/agents/utils/call-seed.ts`). Ids continue past the highest persisted; never re-mint `call-1`.
- claude question-capable turns (callees and callers) spawn in ask mode with the daemon auto-approving plain permissions (bypass mode strips AskUserQuestion) — only for an `auto` node; an explicit `ask` node keeps the human card.
- cursor `cursor/ask_question` must never be declined `-32601` (cursor would replay it as permissions that `auto` approves). A free-text answer naming no option is sent as `skipped`.
- Waits: `await_agent` / sync `call_agent` are bounded at 80% of `mcp.toolCallDeadlineMs` and by `DEFAULT_AWAIT_TIMEOUT_MS`; never unbounded. A user message releases waits (`interruptWaits`). `awaitingCalls` counts only the message targets (`RunCallCapability.messageTargets`, the trigger-fed agents, in their own conversations) inside a wait or in the GAP after one: `AWAIT_GAP_GRACE_MS` after a wait returns, ended by main-thread reply text (`noteOwnerReplying`), a message the CLI took or the turn ending (`forgetUserMessage`); a wait a user message released or the CLI abandoned opens none, and teardown clears the timers. The gap is kept apart from `waitingOwners`, which still means "inside a wait" (`tellWorkingOwnerFinished` reads it). Unknown arguments are refused. Call tools carry `ALWAYS_LOADED_TOOL_META`.
- **Agent pool** (`WorkflowAgentNode.pool`): calls and DAG node turns can hand work to another member.
  - Hand-on only on a limit, a lapsed sign-in, or a failure before any tool call; never on cancel or an unclassified failure mid-work.
  - A continued call follows the same rule as a node's conversation (`conversationStartMember`, below; the kept process asked through `RunCallCapability.conversationHoldsWork`), unless the caller pinned the thread by naming its `member` (`ThreadRecord.memberPinned`, carried on `call_result` as `memberPinned` for a restart): then it stays on that member. A move is decided by the broker (`CalleePoolPlan.sessionMember` names whose session `resumeSessionId` is) and carried out by the executor: it retires the kept process, writes the same `callId` + `member` system row a hand-on does, and opens the new member with the transcript; a refusal before any tool call returns the call to the session's member, resuming its session. On hand-on, recent history from that conversation and its original brief go into a fresh session; another conversation's rows never do. An explicit `member` selection disables fallback.
  - Spent members are one daemon-wide record (`PoolCooldowns`, `graphs/services/pool-cooldowns.store.ts`, a provider of the graphs module held as `CallBroker.poolCooldowns`), keyed by the account a member runs on — `effectiveAccountKey`, the plan-limits ledger's key (folder pin first, then `configDir`, canonicalized) — plus model, never by run or node. The executor is its only writer (node turns and callee attempts, each attempt as it is handed on); the broker only reads it. A member is spent until the instant its limit names (`resetInstantFrom`), else `POOL_COOLDOWN_FALLBACK_MS`; answering clears it. `limit` (a limit or lapsed sign-in) is filed by account and seen by every run; `unavailable` (any other failure it was handed past, a turn that could not start included) is filed only for the run and node that met it (`PoolSite`). In memory only.
  - Order (`poolAttemptOrder`): unspent members, then `unavailable`, then `limit`, each in pool order. A new call and every node turn (DAG, follow-up, new pass) start on the first; a conversation that has a session (`conversationStartMember`: a node's own, or a continued call's) moves only off a `limit`-spent member, or back to an earlier one PROVEN to work again (`PoolCooldowns.proven`: its account answered since the daemon started, or the reset instant its CLI named passed — never a guessed `POOL_COOLDOWN_FALLBACK_MS` lapsing, nor a member nothing is known about after a restart, either of which would meet the same limit on every message) while its process does not `holdsWorkFor` (a running command or a parked card would be stopped). A move writes the same `nodePoolHandOff` row a hand-on does (what later passes read) and carries the transcript into a fresh session; if the earlier member refuses again, the turn returns to the member it left and resumes that member's session (a fresh session with the transcript when the refusing attempt already made tool calls). With every member spent the node stays where it is. Transcript replays pass `redactSecrets`.
  - A handed-on attempt writes no terminal row and retires the kept process.
  - `node_state` belongs to member 1; spend rows name their own member's agent and model.
  - `calleeSummary` never names a member's config directory (it goes to the caller's provider).
- `mcpDisabled` per node/member writes no CLI config and joins `sessionKey`; geniro's own server is never switched off.
  - claude: `--disallowedTools mcp__<normalized>`, in the one variadic flag that always carries `Monitor` (`CLAUDE_WITHHELD_TOOLS`: geniro's `monitor` replaces claude's own, so every CLI has one mechanism).
  - codex: overrides only for names its config defines (an unknown name fails `thread/start`).
  - cursor: throwaway `CURSOR_DATA_DIR` with symlinks into the user's store.
- `CALLEE_FAILED[<class>]` (`rate_limited` / `auth_expired` / `daemon_restart` / `crashed`): the message passes through `redactSecrets`. `resetsAt` stays verbatim. Patterns are per-CLI config and must never carry the `g` flag.
- `cancel_agent`: no card, ownership enforced by the broker (`UNKNOWN_CALL` otherwise), reason required. It cascades to calls made inside; finished work is never stamped cancelled. After the turn ended it answers `already_finished` unless work is still owed.
- `message_agent`: ownership as above; `CALLEE_PARKED` when parked; a message not yet takeable is queued, never refused. Undelivered messages are written as `outcome: 'undelivered'`.
- A call the asker owns that has already finished is refused `CALL_FINISHED` (`CallBroker.finishedCall`) by `message_agent`, `cancel_agent` and `answer_agent`, naming `await_agent` and `thread:` as the next moves; only ownership reads as `UNKNOWN_CALL`. A caller still working when its async call settles is told inside its turn (`tellWorkingOwnerFinished`), never while it waits on its own calls, and `told` stays false so `drainCaller` still wakes it. Its note, and the question twin's (`tellWorkingOwner`), carry the call that conversation answers (`inAnsweredCall`); without it the row is drawn in the run's own flow as a stray block.
- Cache facts (`list_agent_threads`) are a tool answer, never part of the "May call" block (it is hashed into `sessionKey`). `CACHE_EXPIRED` refuses a cold, >50% resume unless `resume_cold`; geniro's own continuations are never refused.
- Reset wakes (`scheduleResetWake`) schedule only from an instant `resetInstantFrom` can place exactly. They are persisted on `Run.resetWakes` and re-armed at boot. A walk is taken only when it schedules exactly the promised agents; otherwise a note is written.
- Monitor output reaches a workflow conversation through `GraphExecutorService.wakeConversation`, installed by every pass whether or not the workflow can call (`wakeNode` exists only where it can): `busy` while the conversation's turn runs (held for `onConversationTurnEnded`), a node's own conversation continued as `continueNode` (reopening a finished run) with the monitor row as its opening row, never into a live turn — scheduled by `scheduleOwnTurn`, the pass's one copy of the bookkeeping `wakeNode` shares; a wake it took and then drops before its turn starts is handed back through `onDropped`: the delivery records its ends when the run was stopped, and holds the output again for that conversation's next turn end when a user's message started the run's next pass first. The workflow Stop (`cancel`) stops the run's monitors.
- A callee turn ending while its own calls run is HELD inside the same call (`holdCall`). The `heldCall` row is a twin of the renderer's `transcript-groups.ts`. Wakes for a held conversation go to the hold (`wakeOwner`). `MAX_CALL_WAKES` bounds it.
- A callee turn ending while its monitors still run, or while their output waits to be delivered, IS held inside the same call, like one whose own calls are out — a monitor is bounded (1 h at most), a detached command is not. `owesHold` and `reviewHold` read `RunCallCapability.monitorsOwed`. The output wakes the callee inside the call (`CallBroker.wakeHeldCallee`, a wake marked `monitor`), counted against its own `MAX_MONITOR_WAKES` (50), never `MAX_CALL_WAKES`; past it its monitors are stopped and the call settles on the answer it has. Output that waited for the turn to end goes out once the hold begins (`callHeld`). Cancelling the call stops its monitors, and so does a call that settles without being held.
- A callee turn ending while commands it detached still run is NOT held (a dev server never ends). The call settles, and its envelope counts them (`commands_still_running`), lists them (`running_commands`) and says in its `note`, as fact, never as an instruction, that the work may not be finished and where their output arrives. They are read from the CONVERSATION's shell rows (`shellsOutOfConversation`): an earlier call's on the same thread count and are tagged with that call (`CallBroker.recordedCallsOf`); another conversation's never do. Words come from the launching call (`launchingCallOf` — node, call and id, since ACP ids restart per session — then `shellCommandOf`) through `quotedCommand` (every env assignment's value shown as `…`, wherever it is set, then registered secrets masked; one line, `LEFT_RUNNING_COMMAND_MAX`). A held call re-reads them when it settles. A failed read is logged and names none, never costing the call its result. `nohup` servers are not CLI shells and are not listed.
- A caller is a conversation (`callerKey(nodeId, conversationId)`); everything the broker keys uses that pair. Never wake a node in a fresh process with no session.
- A superseded pass refuses calls `RUN_BUSY` before minting ids, and numbering continues.
- `rootsWorking` (what decides whether a workflow message queues) stops counting a trigger-fed agent while its own turn is HELD for background sub-agents (`turn_held` open > 0) and counts it again when the hold ends (`open: 0`): its reply is over, and a message delivered into it ends the hold. A held downstream DAG node still counts — it is a step of the walk.

Keyed on the column the card ends in. The executor auto-approves no host tool but the shared memory's (*Shared memory*).
- A working run may move its card only to `TASK_AGENT_OWN_STATUSES`.
- Report screenshots are copied onto the card; rewrite the image destination by position. Keep existing copies (20-file cap).
- A cancelled card is marked `Task.stoppedAt` and never auto-restarted (`TASK_STOPPED_BY_USER`); only a Run press that starts it clears the mark.

While armed, `TaskQueueService` holds a mark younger than `PREPARE_FAILURE_RETRY_MS` (5 min) in `blocked` BEFORE the cap, so it never takes the slot of the card behind it; an older one is handed out again (retry), a repeat failure re-stamps it, and any successful start clears it.

The worktree hold is asked last, so a card with a run-settings problem is reported as that.

- Stop cause (`utils/stop-cause.ts`, twin of the UI's `writeStopCause`): `main.ts` reads and deletes it once, before both reconciles, then runs `settleCutOffCards(null)`. `crash` / `unknown` mark interrupted cards stopped (`TASK_INTERRUPTED`); `quit` / `self-update` / `restart` continue unattended.

### Shared memory

`v1/memory` — one memory every agent shares, whatever its CLI, read and written through geniro's own tools (`memory_search`, `memory_read`, `memory_save`, `memory_forget`; base `MemoryMcpTool`, `.claude/rules/mcp-tools.md`).

- `memories` rows are teardown-exempt (root `AGENTS.md` → *Storage split*); provenance (`sourceActor`, `sourceAgentKind`, `sourceModel`, `sourceRunId`) is a plain copy, never a foreign key. `memories_fts` is the second recorded FTS exception (`.claude/rules/database-queries.md`), repaired at boot by `MemoryTextIndexService.ensure()` beside the chat index.
- Every write goes through `MemoryService.save` / `forget` with a `MemoryActor`, serialized so a handle (`m<n>`, one past the highest, never reused) and the near-duplicate check see a table no other write is changing. The service, not the approval, holds the limits: one-line title ≤ `MEMORY_TITLE_MAX_CHARS`, body ≤ `MEMORY_BODY_MAX_BYTES` (8 KB, so the CLIs' own notes import — user decision), refusal when `redactSecrets` would change the text (registered secrets only — an unregistered key is not caught, accepted), a near-duplicate title in the target scope (word overlap over FTS candidates; `notDuplicateOf` vouches past it), and a stale `rev`.
- Review mode (`agentWrites: pending`, user decision): an agent's — or an analysis chat's — NEW entry lands `pending`, and its update or forget of an existing entry is refused `UNDER_REVIEW`, so reviewed text is never replaced unseen. A near-duplicate refusal quotes only `active` entries; a match among `pending` ones is named by handle (`near_duplicate.pending`), never quoted, and blocks only an agent — the user is the reviewer. `notDuplicateOf` vouches past either. A forget keeps the writer's provenance. `setStatus` (approve, restore, forget) takes an actor and refuses an agent (`USER_ONLY`). Forgetting records what the entry was (`statusBeforeForget`) and keeps its `approvedAt`; a restore puts it back there, so a pending entry waits for review again and only an Approve press approves (user decision).
- Only `active` entries are searched or read by an agent; `pending` waits for the user's review and `forgotten` is restorable. An agent sees global entries plus its run's project's. Every tool result is masked with `redactSecrets` (a secret registered after an entry was saved never leaves), and a whole body is quoted inside a fence with a random name per reply, so a body cannot forge another entry's header.
- The project is the daemon's (`MemoryService.scopeOf`): the run's task card's project, else the live project whose folder `ProjectRootsService.rootsOf` resolves the run's folder to (a task worktree to its repository), else global only. The caller is `actorOf`: a workflow node's own `NodeState` agent and model, else the run's; an analysis run writes as `analysis`. Known limit: a pooled node's member that took over is recorded as member 1 (`node_state` holds member 1's agent).
- Reading stamps `lastUsedAt` through the builder, never a flush (a flush would move `updatedAt`).
- A new run snapshots the memory once, in the two Run builders (`createChat`, the executor's `startRun`), before its row exists: `MemoryService.runSnapshot` over `scopeFor({taskId, cwd})` (what `scopeOf` asks of a row) writes `Run.memoryIndex` and `Run.nativeMemoryOff`, and every turn reads both off the row like `customInstructions`, since both join `sessionKey` — a note saved or the switch flipped mid-run restarts nothing and reaches the next run. Until Electron's first push it snapshots nothing (the default is not the user's choice). A failed read starts the run without an index, never refuses it.
- The index (`memoryIndexText`) lists only entries the user wrote or imported, or approved by hand (`Memory.approvedAt`, stamped by the user's `setStatus` to `active` and cleared by any later save): an agent's unreviewed entry is reached only through `memory_search` (user decision, after research: a note an agent was steered into saving must not speak in every later run's instructions). Active entries the run may see, its project's first, most recently used first, one line each (handle, type, masked title, scope, last use), cut on whole lines at `MEMORY_INDEX_MAX_BYTES` with a `+N more` footer; null when empty or memory is off.
- Each CLI's own memory can be switched off per run (`Run.nativeMemoryOff` → `AgentTurnInput.nativeMemoryOff`): claude through `CLAUDE_CODE_DISABLE_AUTO_MEMORY` in its env, codex through `features.memories = false` in every thread config (endpoint or not); cursor-agent keeps none. Each switch is measured beside its constant. `runSnapshot` sets it only while the shared memory is on and the user switched the CLIs' own memory off (`MemoryConfig.nativeMemoryOff`, off by default and turned on by a successful import in Settings → Memory — user decision, so the CLIs' notes are never hidden before they are brought over).
- Settings arrive by push only (`PUT /v1/memories/config`, desktop only, `MemoryConfigSchema`, twin of the UI's `memorySchema`); until the first push the daemon holds `DEFAULT_MEMORY_CONFIG` (on, writes active) — the kept-session pattern, not the share one. Off removes the tools from every listing and refuses a kept CLI's call `MEMORY_DISABLED`. A run's prompt prefix never moves with the memory: entries saved, edited, approved or imported reach only new runs' instructions, and the review policy (read at each write) and the CLIs'-own-memory switch leave it as it is (the index and `nativeMemoryOff` are the run's snapshot, and the tools' descriptions are fixed text). Only the on/off switch itself moves it — no `list_changed` is sent, so a live CLI keeps the list it was spawned with, and a process of an existing run spawned after the switch lists the tools anew, costing that thread its prompt cache once (user decision: accepted rather than freezing the tool set per run).
- Auto-approved in a chat (`autoApproves`, in-turn and between turns) and in a workflow node at every approval level, in-turn and between turns (`isHostMemoryCall`, the executor's one host-tool approval), because a card per search would make memory unusable; every entry keeps who wrote it, and the user sees every entry in Settings → Memory.
- Each write publishes `memory_changed` (`MemoryEventBus`) to EVERY client, paired devices included (the user reads and edits memory from the phone); the event names the entry (`memoryId` null for a `bulk` change: forget-all, an import) and what the write did (`created`, `updated`, `forgotten`, `restored`, `approved`, `bulk`), never its text.
- The user's own routes (`MemoriesController`, `/v1/memories`) are open to paired devices (user decision); the config push (`MemoryConfigController`) and the import (`MemoryImportController`) are desktop only, each its own class because `DesktopOnlyGuard` sits on the class. A user's edit (`MemoryService.edit`, by id at the `rev` it read) makes the entry the user's own — a pending agent entry edited by the user is active and no longer waits on review; a forgotten one must be restored before it is edited. A near-duplicate refusal is `409 MEMORY_NEAR_DUPLICATE` whose message lists the handles (`NEAR_DUPLICATE_PREFIX`, twin of the pane's `nearDuplicateHandles`), so the pane vouches past exactly those. Forget-all is one statement over `active` and `pending` (each stays restorable); export is every active and pending entry as Markdown (`utils/memory-export.ts`).
- Import (`MemoryImportService`, in `v1/agents` because it walks `AgentAdapterRegistry`; its routes are `MemoryImportController`, desktop only): it only READS each CLI's own memory, through the adapter hook `readNativeMemory(configDir | null)` (null = the CLI's default profile; a CLI that keeps none answers null) and `nativeMemoryProjectKey(folder)` — claude's `<profile>/projects/*/memory/*.md` (not `MEMORY.md`), codex's `memories/MEMORY.md` task groups, never a symlinked directory or file, never codex's `memories_1.sqlite`. It never writes, moves or deletes a file there. Every profile the renderer names is read beside each CLI's default. A note's project is the live project whose key matches; two projects claiming one key leave it Global (`ambiguous`). A preview key names the note's text (a hash of title and body), so apply re-reads the files and skips a note edited or rewritten since the preview instead of storing text nobody saw; a second copy of one note (`sameAs`) and a key ticked twice are written once. Ticking a note is the user's review (user decision): imported entries land active with `approvedAt` stamped, in one flush, announced as one `bulk` change. Each row names its `profile` and the `folder` the note was written for (claude: read from a session filed beside the note, kept only when it flattens back to that directory; codex: none), home shown as `~`. The AI sort (`POST /v1/memories/import/triage`, `MemoryImportService.triage`) is advice only: it writes nothing, takes the notes' text from the client, masks it (`redactSecrets`) and puts one batch to the chosen CLI through `AgentAdapter.askOnce` (a throwaway turn isolated like the title ask; the model, effort, context window, model parameters and profile are the user's pick, checked as a chat's are — `EffortsService.accepts`, the CLI's `configDir.unavailableReason`, `resolveValidConfigDir` — and the cheap model at low effort on the default profile when none is picked; `AdapterConfig.oneShotAskUnavailableReason` says which CLIs cannot, served as the preview's `triageAgents`); the prompt and its reader are `utils/memory-triage.ts`, and a note the answer skipped simply has no verdict.
- Module direction: `MemoryModule` imports only `ProjectsModule` and provides the run, node and task DAOs it reads, so `AgentsModule` and `GraphsModule` (the run snapshot), `McpModule` and `NotificationsModule` import it, never the reverse.

### Stats

- `usage_events` and `usage_activity`: ledgers that outlive teardown (root `AGENTS.md` → *Storage split*). Append-only, with two exceptions, both `usage_activity`:
  - A `run_outcome` row (one per run and pull request, keyed `outcome:<runId>:<owner>/<repo>#<n>`) is UPDATED to a newer outcome, only ever forward by its source item's seq, in one `INSERT … ON CONFLICT … DO UPDATE … WHERE` (`UsageActivityDao.upsertRunOutcome`). `RunOutcomeLedgerService` copies each `run_outcome` item off `bus.all()` and, behind the boot, sweeps every outcome row the ledger lacks or holds older; `UsageActivityDao.runOutcomes` is the read a per-workflow-version outcome fold will use; the versions table does not read it yet.
  - A workflow run's `thread` row carries the workflow version ledger's version stamp, UPDATED in place (below).
- Workflow version ledger (`WorkflowLedgerService`): a workflow run's `thread` row is stamped with its workflow and graph version (`workflowVersionOf`, `graphs/utils/workflow-version.ts`: nodes, edges without their label, `maxActiveTurns` and the stages in their authored order, an empty list counting as none; never the workflow's name, description or layout) at `run_created`.
  - Each version's graph is recorded once in `workflow_versions`, keyed by (slug, version), teardown-exempt like the ledgers; `first_seen_at` keeps the earliest run, and versions are numbered by it.
  - A run with no graph copy it can read is stamped with its workflow alone and stays so, even after a later read freezes the library's graph into it. A run created before `SNAPSHOT_AT_CREATION_SINCE` is `inferred` (its copy was frozen later) and its graph is never registered, so it gets no number and no change summary.
  - The versions table (`GET /v1/stats/workflow-versions`) serves per version only the dates used, the run count, the cost and its average per priced run, and the graph's unified diff against the version numbered before it (`canonicalGraphYaml` of both, `utils/version-diff.ts` over jsdiff) with its added and removed line counts. A version's diff never changes, so `WorkflowVersionsService` keeps it in memory. Run status, failed nodes, turns, pull requests, lines and work time are deliberately not shown (user decision).
  - `POST /v1/stats/workflow-versions/restore` (`WorkflowVersionsService.restore`) writes a recorded version back as the library file's graph: its nodes, edges, `maxActiveTurns` and stages, under the file's own name and description, the places of the nodes it still has and the labels of the edges it still has. It backs the file up first (`.backups/`, as an applied change does), refuses a `baseHash` the file has moved past (`WORKFLOW_CHANGED`, checked before the backup and again by the store's save), and refuses a version with no recorded graph (`WORKFLOW_VERSION_NOT_FOUND`: an inferred one never has one). Restoring writes no new version: the next run stamps the restored one. The graph it replaces is recorded, numbered as of the restore, when no run has stamped it (an edit not run yet), so the table keeps it and it can be restored back; one a run stamped already has its row.
  - What is current is always the library file's graph (`currentVersion`), so a restore or an edit moves the current mark at once. When no version records that graph yet (edited since its last run, or never run), the table still shows it as its first row (`recorded: false`, unnumbered, no dates), diffed against the newest recorded version; its first run numbers it. A recorded version no run has stamped is a row with no dates.
  - The archive sweep deletes archived WORKFLOW runs too (`sweepArchived` → `purgeArchived`), so `WorkflowLedgerService.sweep()` is awaited in `main.ts` before listen — every boot, selecting only runs with no version stamp yet.
  - Every read by `workflow_slug` filters `kind = 'thread'`: `run_outcome` rows carry the slug too.
- `v1/stats` observes `AgentEventBus` and never drives; nothing in `v1/agents` imports it. `McpModule` imports it for one read, a workflow's history (`WorkflowHistoryService`, with the recommendation ledger it reads: *Thread analysis* → workflow analysis).
- Ledger writes are native inserts, not flushes (a flush re-stamps loaded runs' `updated_at`).
- Boot backfills must stay idempotent (`(runId, seq)` unique, `dedupKey`).
- Polled spend: Stats reads it only from the ledger rows (`seq ≤ POLLED_SPEND_SEQ`), never from `runs`.
- The spend fold is `v1/agents/utils/usage-figures.ts`, shared; never copy it. No price means `costUsd: null`, never $0.
- Lines are measured by the desktop app per folder against one `line_baselines` commit. Day lines are growth past the series peak, never a client delta.
- `ClaudeSessionCostLedger` persists session totals to disk (`claude-session-costs.json`). A resume's seed is registered at spawn and read from the transcript's last `cost-state` at the new process's `system/init`, never at spawn (the replaced process writes its line as it exits). A read that finds no line keeps a known total, and leaves the process's first result untrusted.
- List prices come only from `ModelPriceCatalog` (models.dev, persisted to `model-prices.json`); never a hand-written price table. Provider is an adapter fact (`usage.listPrice`).

### Agent instructions

- Every turn's instruction block is composed at one seam: `AgentAdapter.composeSystemPrompt` joins `AgentAdapter.turnInstructionParts` → `turnInstructionParts` (`v1/agents/utils/agent-instructions.ts`). Adapters never join the parts themselves (`.claude/rules/agent-adapters.md`).
- Order, general → specific (`TURN_INSTRUCTION_SOURCES`): host preamble (`GENIRO_UI_PREAMBLE`), the CLI's background-work note (`AdapterConfig.backgroundWork.agentNote`), the user's reply language (`replyLanguageInstruction`, from `Settings.replyLanguage`), the user's custom instructions, the shared memory's index (`Run.memoryIndex`), a board card's `taskInstructions`, the builder chat's `workflowInstructions`, wired `instructionBlocks`, the run's stage map (`stageMapPrompt`), the node's `role`, the callee sentence (`ANSWERING_A_CALL`, on every turn that answers a call, a leaf callee included), then the "May call" block.
- The preamble's tools section names each host tool by the situation it is for and leaves the how to the tool's description: claude lists MCP tools by name only, so a description is unread until the agent decides to load the tool. Name a tool by its `HOST_*_TOOL` wire name, conditionally (the text is not gated on the MCP endpoint, and a workflow node is offered only some), and name no CLI. Every new tool is named there in the same change, or exempted with its reason in `PREAMBLE_EXEMPT` (`mcp-server.service.spec.ts`, which fails on a listed tool that is neither; `.claude/rules/mcp-tools.md` → *Adding a tool*). Each of claude's own tools geniro withholds (`CLAUDE_WITHHELD_TOOLS`) is named there beside the tool that replaces it, since claude's own prompt still sends the model to it.
- The background-work note is per CLI because the truth differs: a claude or cursor turn (and the call it answers) is held while its background sub-agents run and the agent is started again with their reports, so it is told to end its turn rather than poll; a codex turn is not held, so it is told to `wait_agent`. Every sentence must stay true of its adapter's hold; never inject a reminder mid-turn instead (it arrives as a user message).
- Delivery: claude on `--append-system-prompt`; codex as the thread's `developerInstructions`; ACP inside the prompt text, after the user's words, wrapped in `<host-context>` (`HOST_CONTEXT_TAG`). Never lead the ACP prompt with it: the CLI names the chat from the prompt text.
- On ACP the block is sent once per session and re-sent only when its text changes (**ACP instruction delivery**, below).
- `internalProbe` turns get no preamble, no background-work note and no reply-language line.
- The reply language is snapshotted onto `Run.replyLanguage` like custom instructions (it joins `sessionKey`). claude also gets it as its own `language` setting, in the turn's own `--settings` object (`claudeSettingsArgs`). A later `--settings` replaces an earlier one, so the last one carries every key — fast mode, the language, and a repeat of the Ollama env the base's env-only flag carries ahead of it.
- Custom instructions are one global value, `Settings.customInstructions`, sent on chat create and workflow start under `CustomInstructionsSchema` (no length limit; refuses C0 control characters other than tab, LF and CR, since a NUL in argv makes `spawn` throw on every turn).
- They are snapshotted onto `Run.customInstructions`, never read live: `AgentAdapter.sessionKey` hashes them, so a live read would respawn the kept CLI and its MCP servers mid-conversation. Editing them affects the next chat.
- A node's `role` outranks them; keep them as peer fields, not one joined string.
- The memory index carries only entries the user wrote, imported or approved (*Shared memory*): it opens with `MEMORY_INDEX_PREFACE` (data, not instructions), carries titles only (bodies stay behind `memory_read`), is masked again on every turn (`redactSecrets`), and is composed only where the turn's MCP tools were delivered, since it names them.
- `POST /v1/chats/forget-custom-instructions` (an explicit Settings button) purges the snapshot from existing runs.

### ACP and cursor transport

- **The cursor transport**: each turn runs under a throwaway `CURSOR_CONFIG_DIR` seeded from the user's `cli-config.json` only (ACP model/effort changes persist into it).
  - Non-`auto` turns write `approvalMode: "allowlist"` and `autoAcceptWebSearch: false`; failing to write that fails the turn. Whether a turn asks is part of `sessionKey`.
  - Never copy or symlink `mcp.json`.
  - `acp-sessions` is a symlink to `<userData>/cursor-sessions`, never nested in `cursor-profiles` (swept at boot).
  - A refused `session/load` degrades to a notice plus `session/new`.
- **cursor named configurations** (`utils/cursor-account.utils.ts`): the CLI keeps its default login in the Keychain under fixed names, so `CURSOR_CONFIG_DIR` never moves the account.
  - Sign-in, sign-out and the Electron login probe run with `HOME=<dir>` and `AGENT_CLI_CREDENTIAL_STORE=file`: the CLI's own file store, `<dir>/.cursor/auth.json`. MCP sign-in never takes the profile (MCP stays the real home's).
  - A run never moves `HOME` (the agent's commands inherit it). It gets `AGENT_CLI_CREDENTIAL_STORE=memory` plus that file's access token as `CURSOR_AUTH_TOKEN`, never the token alone: outside the memory store the CLI writes it over the Keychain login. A signed-out profile still gets the memory store, so it fails "Authentication required" instead of borrowing the default account.
  - The token is registered as a secret, but the agent's own commands see it in their environment.
  - The seeded `cli-config.json` takes the profile's `authInfo` (or none). Per-model parameter probes and the account-spend poll stay on the default account; plan limits are read under the run's profile.
- **ACP instruction delivery** — the composed block is sent once per SESSION, re-sent only when its text differs from `AcpSession.deliveredInstructions`. `deliveredInstructions` is updated from the prompt written, or read back from the `session/load` replay (`readHostContext`).
- Model and parameter frames go ONE AT A TIME, each after the previous reply (`configSteps`); never pipeline. cursor binds the model and every parameter when the prompt arrives, so its prompt waits for the last frame's reply (`AcpSessionOptions.promptAwaitsConfig`, one switch per CLI, never per parameter), released on refusal or deadline. Never map window sizes in geniro.
- cursor opts into `AcpSessionOptions.skipUnchangedParameters`: at send time, resolve the parameter's option id against the turn's model, then skip only an equal reported `currentValue`. Read the latest session/new, session/load or accepted config reply; a model switch must use its own reply, never the previous model's options. A reply without current values invalidates the earlier snapshot. Settings do not necessarily survive the per-turn profile: compare THIS reply, never the preceding turn's request; a non-default effort can still need a frame every turn. Other ACP agents keep sending parameters unless they opt in after measurement.
- Max Mode is written explicitly every turn (ON and OFF) from the snapshotted `Run.agentOptions`; null reads as the default (ON). Do not rebuild learned Max Mode window sizes.
- `ContextWindowStore` keys include the window choice. `AcpSession.currentModelId` is the agent's own or confirmed model, never the requested one.
- cursor context (`cursor-context-store.utils.ts`): open `store.db` read-only via `node:sqlite`, never write it. Find the block by shape; categories must sum exactly, else null. Never estimate from the transcript. Persist the last reading into `turn_complete`. Mid-turn re-reads are floored at 2s and published only on change.
- Mid-turn follow-up on cursor interrupts: the cancel → await → prompt sequence is in `.claude/rules/agent-adapters.md`; the stopped prompt is tracked as `interruptedPromptId`. Parked requests are answered `cancelled` and withdrawn; open tool calls close as interrupted. The wait is bounded (`INTERRUPT_ACK_DEADLINE_MS`).
  - A follow-up accepted in that window already has its row (the owner wrote it on `true`), so the driver never drops one silently: every path that empties `queuedFollowUps` without sending (a Stop's turn end, an error reply, a failed write, the process ending — `TurnDriver.onProcessEnded`, asked by `spawn-cli` on the kill fallback, a crash, a process `error` and a broken stdin) emits `follow_up_dropped` with the messages' `deliveryId`s, AHEAD of the turn's terminal. It becomes a `system` row (`unsentMessages`) the renderer pairs with the user row; a `message_agent` id is recorded undelivered by the broker instead (`markMessageDropped`), its row carrying the `followUpId` of the "delivered" row it retracts. A broker tell or a wake handed to a working turn (`tellLiveNode`, `wakeNode`) rides its own id too; a dropped one is never a user row, and is delivered again once that turn has ended when it carries a `redeliver` (a reset wake, a wake) — a question or a result needs none, since the drain wakes the conversation with what it was not told. A workflow follow-up tells each root under its own id, and its row reads not sent only once every root it went to dropped it; a partial drop is a note naming the root. That marker is written at run level, where the follow-up's own row is: written under the root that answered last, it opened an empty node block, since the marker draws itself on the message.
- `reasoning_delta` and `tool_compose` are ephemeral (`mapEventToItem` → null). `tool_compose` carries the tool name and a byte count only, never arguments; delegate frames are dropped in the mapper.
- Self-reported cursor failures (`AcpAgentFailureProtocol`) need both anchors (prefix and error class). They settle `error` INSTEAD of `turn_complete` and never reach `finalText`. Transient drops resume up to 3 times. A latest `session/prompt` that answers an error reply takes the same path (`onPromptFailed`): cursor's background-task drain runs after the catch block that writes `Error: …`, so a drop there arrives as `-32603` with its cause in `data.details`. A reported failure the agent then talks past is forgotten (`forgetOutlivedFailure`).
- On a failed request, open tool calls close `CUT_OFF_TOOL_RESULT`; watchable delegations are adopted, not relaunched ("do NOT launch these again").
- Sub-agent sessions: declare `clientCapabilities._meta.subagents` only under `_meta`. Route only ANNOUNCED child ids; drop a child with no readable launching call. Messages queue while a background sub-agent runs (`sendFollowUp` → false).
- A `pending` tool call with empty arguments is held until refined (`heldToolCalls`).
- An agent closes a call whose permission geniro refused as `completed` (cursor: no body for an execute call, `{rejected:true}` for an MCP call). Every answer that is not a selected allow option — a Deny, an auto-deny, a request released `cancelled`, an allow the agent offered no option for — marks its `toolCallId` (`AcpSession.refusedToolCalls`, session-scoped like `parkedPermissions`), and a later allow clears it; that call's result is `isError` with `REFUSED_TOOL_RESULT` when the agent sent no body.
- One process per conversation. Never go back to one process per turn; do not reintroduce an instruction telling agents not to background work.
- `AcpSession` holds only state that outlives a turn (transport, pending replies, capabilities, session id, MCP servers, model, session reply, latest config reply, delivered instructions, and everything keyed by a protocol id). Everything else lives on a fresh `AcpTurnDriver` per turn.
  - Mode, model and parameters are checked per turn; a turn naming no mode restores the default. Only an opted-in agent skips parameters confirmed current.
  - Every turn emits its `session`.
- Stop is `session/cancel` with a 5s kill fallback. `cursor-agent acp` ignores EOF; the registry's `close()` kills the group.
- cursor offers no `acceptEdits`: a stored `acceptEdits` asks exactly like `ask` (`cursorAutoDecision` → null); never auto-approve under it.
- Model selection reads `configOptions` (`configId`, not `configOptionId`) or the legacy `models`. Pick the frame from what the agent advertised, never a version. `cursor-agent models` ids are never the picker source.
- `create_plan` / `generate_image` are declined `-32601`; `ask_question`, `task` and `update_todos` are answered. `create_plan` is READ before the refusal: its todos carry the ids the baseline `plan` update lacks and later `update_todos` patches key on, so it (not the held `plan` update) is the plan's `task_list` snapshot (`AcpTodoProtocol.plan`). Do not reintroduce the legacy `-p` cursor adapter, its `.cursor/mcp.json` merge or its trust probe.

### Auto-compaction

- **AUTO-COMPACTION** — asked of the CLI where it has a control, performed by the daemon between turns where not. One number: `autoCompactPercent` (10–95, null = never) per chat or node.
- claude: `--autocompact <threshold + 33k buffer>` (not `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`). The window is the conversation's last reading (live, then row; the executor seeds `nodeWindows` from `node_state` each pass), and before any reading the turn's model's known window (`utils/first-turn-window.ts`), so the flag is there from turn one: the id the CLI runs the name as under that profile (`AgentAdapter.resolveModel`; claude asks its own `initialize`, cached per profile and version), then that id's measured window at the window choice, then the catalog's (models.dev `limit.context`) only where the adapter declares `listPrice.catalogWindows` (claude yes, codex no) and never for a `[1m]`-style variant. Never a number parsed from the window choice. A reading whose model is not the one the turn announced (a delegate out-spending it in `modelUsage`) is not the conversation's window and is never stored as one, in a turn or between turns (`PartialStreamService.isOwnReading`). It joins `sessionKey`; outside 100k–1M the flag is dropped. cursor has none.
- Between-turn rule (`utils/auto-compact.ts`): after a `completed` settle, it sends `/compact` through `sendMessage` and writes its row only once that has taken.
  - A geniro-command turn never re-arms it.
  - `compactingRuns` refuses follow-ups `RUN_BUSY` with a per-turn token.
  - Baseline: the first reading after a compaction; no re-compaction until regrowth (`AUTO_COMPACT_REGROWTH_FRACTION`).
  - A carried compaction retires (marks) the kept process.
- Workflow nodes compact right after the filling turn, inside the unit owning the session key (`launchNode` / `launchCalleeTurn` / `continueNode`), never before a resume and never inside `enqueue`. `compactingNodes` refuses follow-ups. cursor's carried summary is held per session key in memory.
- Never write `/compact` into a running turn's stdin.

### Agent caches and MCP configuration

- `ModelVocabularyStore` (`model-vocabularies.json`) is invalidated by `--version` in the entry, `forgetAgent` on account sign-in/out (with an epoch so in-flight answers are discarded), stale-after-1h refresh, and a 7-day expiry. Never file an answer that could not be obtained (empty list).
- **MCP config writes** — one of the two exceptions to "geniro writes only its own files" (the other: deleting an archived run's own CLI transcripts, under `run-teardown` in *Agents: adapters*). Always through the CLI's own key, lock or mechanism:
  - claude toggle: `projects[<claudeProjectKey>].disabledMcpServers` in `~/.claude.json`, under `proper-lockfile` at `~/.claude.json.lock`. Atomic, mode-preserving, fsynced (`rewriteHomeConfig`); refuse an unparseable file.
  - cursor toggle: the CLI's own `mcp enable|disable` in the folder.
  - codex toggle: `config/value/write`, only for servers its user `config.toml` defines.
  - Plugin copy (cursor, `~/.cursor/mcp.json`): strict re-read, refuse unparseable or conflicting names, atomic fsynced write. No credential; nothing host-bound may read `${env:…}`.
  - Server definitions (`/v1/agents/mcp/config`, `/servers`): user scope of the listing's profile only. claude touches only top-level `mcpServers`; codex through `config/batchWrite` (HTTP servers) or its own `codex mcp add` (stdio servers), never TOML by hand. Saves carry the read version and are refused if it moved. Add values are registered with `registerSecret` before the CLI runs; nothing in a body is logged. `codex mcp add` is refused when the name exists.
  - claude's `mcp-needs-auth-cache.json` is the one CLI cache geniro edits: delete a server's key once it is seen connected; leave an unreadable record alone.
- An MCP change MARKS the kept sessions it reaches stale (`markStaleWhere`, scope per `mcp.changeReach`); never close them mid-turn.
  - A stale mark has a cause (`mcp` / `account` / `conversation`, merged by `mergeStale`). Only `mcp` waits while the process `holdsWork` (a detached command, a parked card, off-turn work): the turn runs on the old process with an `info` row and a prompt note (once per set of reasons) saying the change applies later and that switched-off servers are still loaded (user decision). An account change, a compaction or a pool hand-off never waits, and outranks an `mcp` mark.
- A server sign-in is `succeeded` only once the server is seen connected (`verifying` until then).
- The toggle's profile is part of the address; the write lands in the file the read came from.
- Clear Agent Cache (`POST /v1/agents/caches/clear`) forgets cached answers only: never the harvest stores or `ContextWindowStore` (measurements nobody can re-take), and it never re-probes a CLI.
- codex MCP config is read from the USER layer of `config/read {includeLayers: true}`, never the effective config (which adds defaults and plugin servers that would then be written into the user's `config.toml`).

### Daemon endpoints (loopback)

The OpenAPI document at `/swagger-api` (source of `pnpm generate:api`) is authoritative for every route and shape; read the controllers for behaviour.

Bind, shutdown and config:

- Binds `127.0.0.1` only, via the http-server extension's `host` / `portFallback` / `onListening` options. Preferred port `47615` (`DAEMON_PREFERRED_PORT`), falling back to a free port.
- Shutdown is Nest-owned (`enableShutdownHooks`); `utils/pidfile.lifecycle.ts` clears the pidfile. Do not add signal handling to `main.ts`.
- Config env, set by the UI: `GENIRO_USER_DATA` (fallback `~/.geniro`), `GENIRO_PORT`, `GENIRO_IDLE_EXIT_MS` (absent = never exit). The userData dir holds `geniro.db`, `daemon.json`, `daemon.lock`, `children.json`.

Auth by prefix (`auth/token.guard.ts`): every route needs `Bearer <launch token>` except the public prefixes `/health` and `/v1/artifacts` (`PUBLIC_PREFIXES`, matched at segment boundaries).

- Public: `/health`; `/v1/artifacts` is gated by a per-artifact 256-bit key in the URL (the `key` query), because an `<iframe src>` cannot send a header: one uniform 404 for every failure, `Referrer-Policy: no-referrer`, `?raw=1` matched as the literal `1`, `@ApiExcludeController`. `ArtifactStoreService.read` requires the key and compares it in constant time. Never put the launch token in a URL.
- Launch token (`LoopbackTokenGuard`): every other `/v1/*`, `/metrics`; `/swagger-api*` stays token-gated through `swagger.guard`.
- `/ws`: one Socket.IO gateway; the token rides the handshake `auth` payload. The handshake bypasses Nest guards, so every gateway authenticates in `handleConnection` through the shared `enforceWsHandshakeAuth` (`auth/ws-auth.ts`); never write a second copy. `LoopbackTokenGuard` lets `ws` message contexts through and refuses any other non-HTTP transport.
- `/v1/mcp/<runId>/<nodeId>[/<conversationId>]`: that node's own call token, keyed by `(runId, nodeId)` and revoked at run teardown, or the launch token. No other route accepts a call token.

Rules when adding or changing routes:

- Declare static segments (`forget-custom-instructions`, `sweep-archived`, `reorder-pinned`, `processes`, `reconcile`, `awaiting-merge`, `reorder`, `instruction-sizes`) before `:param` routes. Workflow slugs `runs`, `import` and `instruction-sizes` are reserved (`RESERVED_WORKFLOW_SLUGS`).
- Take query filters through a Zod DTO, never a bare `@Query` (an absent value lists everything; `fastify-qs` parses operators). List `scope` is an enum, never a boolean.
- `configDir` is snapshotted onto the run (as are `customInstructions` and `replyLanguage`: *Agent instructions*), travels as env, never argv, and must exist; a CLI without the mechanism refuses it (`CONFIG_DIR_UNSUPPORTED`). Text reaching a spawned CLI refuses control characters by field: custom instructions, label instructions and an instruction node's text refuse C0 control characters other than tab, LF and CR (`CustomInstructionsSchema`, `hasControlCharacters`, `chat.types.ts`), and `replyLanguage` is one bounded line without control, invisible or bidirectional characters (`ReplyLanguageSchema`); the agent-node text that reaches a spawned CLI (`role`, `id`, `name`, `description`, `model`, `effort`, and `configDir` as env) and a stage's text (`title`, `instructions`, `doneWhen`, `ownerHint`, which reach every agent's instructions) refuse NUL only, because the same schema also reads saved YAML and every run's own graph copy (`argvSafe`, `graphs.types.ts`); a server name in `mcpDisabled` refuses every control character (`mcpServerNameIsClean`).
- A mid-turn message is told to the CLI first and written only once delivered; else `409 RUN_BUSY`.
- `archivedAt` is its own column, never `deletedAt` (root `AGENTS.md` → *Storage split*). Archive cancels only a `running` turn; an archived run refuses messages (`RUN_ARCHIVED`).
- `PATCH /v1/tasks/:taskId` never accepts `runId` / `worktreePath` / `branch`. Status moves are a database compare-and-set (`TaskDao.compareAndSetStatus`).
- One live project per folder, enforced in the service, not a unique index (soft delete).
- `GET /v1/chats/:runId/image` stays an image channel: extension checked first, regular file, size cap, canonicalized before stat, URLs refused.
- Retry refuses a working run BEFORE closing its session, and requires a session id.
- `shell-output` names a tool call, never a path.
- Run snapshot (`Run.workflowSnapshot`): unreadable is `409 WORKFLOW_SNAPSHOT_UNREADABLE`, never re-frozen.
- Never store merged/open state for pull requests; never date them by capture time.
- `/ws` counts (`holdingFor`, `shellsOpen`, `subagentsOut`) are announced on transitions; every path that ends one must announce. `run_status.status` is nullable (activity announces assert none). `runs_changed` rows carry 0 for `rootsWorking` / `awaitingCalls`. `task_changed` is a twin of the UI's `parseTaskChanged`; the renderer collects worktrees only off `reason: 'work-finished'`.

Destructive or irreversible routes (and one that only looks it — `DELETE /v1/tasks/:taskId/files/:attachmentId` drops a reference, never the file):

- `DELETE /v1/chats/:runId` — hard-deletes a chat run through `RunTeardownService` (chat runs only; reached from the archive).
- `DELETE /v1/shares/:shareId` — revokes one shared page: its remote object, Keychain key and row (a failed remote delete keeps both).
- `POST /v1/shares/revoke-all` — deletes the named shared pages' remote objects, Keychain keys and rows (a failed remote delete keeps both).
- `POST /v1/chats/sweep-archived` — deletes chats archived ≥ `olderThanDays` (1 day–10 years) from `archivedAt`; one at a time, failures logged and skipped. The policy is the client's.
- `DELETE /v1/workflows/runs/:runId` — one workflow run's history (never the library workflow).
- `DELETE /v1/workflows/:slug` — removes the library workflow's YAML file.
- `POST /v1/stats/workflow-versions/restore` — replaces a library workflow's graph with a recorded version's (the file is backed up first).
- `DELETE /v1/workflows/:slug/chat` — discards the builder chat.
- `DELETE /v1/projects/:projectId` — the project AND its tasks.
- `DELETE /v1/tasks/:taskId` (soft delete), `DELETE /v1/label-instructions/:instructionId` — remove a card or a label instruction.
- `POST /v1/chats/forget-custom-instructions` — drops the snapshot from every run (leaves `taskInstructions`).
- `POST /v1/chats/:runId/archive` — cancels a running turn and closes its session.
- `POST /v1/chats/:runId/retry` — closes the kept session (refused while working).
- `POST /v1/chats/:runId/shells/kill` — signals the agent's command tree.
- `POST /v1/chats/:runId/processes/stop` — stops the selected detached processes and monitors (explicit pids only; one outside the run's detached set refuses the whole request).
- `PUT /v1/agents/mcp`, `PUT /v1/agents/mcp/config`, `POST /v1/agents/mcp/servers`, `POST /v1/agents/mcp/plugin-servers` — write the user's own CLI config (see MCP config writes).
- `DELETE /v1/groups/:groupId` releases its runs and the projects bound to it; it never deletes chats or boards.
