# apps/daemon

Guidance for Claude Code when working in `apps/daemon` — the NestJS loopback daemon. Loaded automatically when this directory is touched; see the root `CLAUDE.md` for project-wide overview, commands, conventions and constraints.

---

A standalone NestJS engine the UI spawns as a child process, laid out like Geniro's `apps/api/src`: `main.ts` (bootstrapper + extensions → `init()`) and `app.module.ts` at the root, then feature/infra dirs:
- `auth/` — `runtime.ts` (per-launch `RuntimeInfo` + DI token, incl. the bound `port`) + global `runtime.module.ts` (also hosts `CallTokenRegistry`, so the guard and the graph executor share it without a module cycle); `mint-token.ts` (the one source of loopback credentials — the launch token AND the per-caller-node MCP call tokens); `token.guard.ts` + `safe-equal.ts` (loopback bearer-token gate); `ws-auth.ts` (`enforceWsHandshakeAuth` — the ONE Socket.IO handshake gate, shared by every gateway, since engine.io bypasses Nest guards); `call-token.registry.ts` (per-`(runId, nodeId)` MCP call tokens).
- `environments/` — `environment.{prod,dev,test}.ts` + `index.ts` (picks by `NODE_ENV`, loads `.env` via dotenv), laid out like the sibling api's: prod is the base, dev spreads prod, **test spreads DEV**, and each is one object literal closed with `as const satisfies Record<string, string | number | boolean | null>` — the shape is INFERRED, so there is no hand-written interface to keep in step and a new field is typed at every read site without a second edit. An env file holds environments and nothing else: `readDaemonVersion` lives in `utils/daemon-version.ts`, and the strict parsers in `utils/handshake.ts` beside the rest of the UI→daemon contract. Three fields deliberately bypass `getEnv` and say so at their own line — it boolean-coerces `'0'`/`'1'`/`'on'`/`'off'`, which is wrong for `GENIRO_USER_DATA` (a path), `GENIRO_PORT` (must be a bindable 1..65535) and `GENIRO_IDLE_EXIT_MS` (malformed ⇒ feature OFF, never a guessed number). `host` is a CONSTANT rather than an env knob — the one deliberate departure from the sibling's env-everything shape, because "binds 127.0.0.1 only" is a hard v1 constraint and an env var is how it would come to be broken.
- `utils/` — `handshake.ts` (pidfile `DaemonInfo` shape + loopback bind defaults + `isValidPort`/`parsePort`); `pidfile.ts` (write/remove — `mintToken` moved to `auth/mint-token.ts`); `pidfile.lifecycle.ts` (Nest `OnApplicationShutdown` → removes the pidfile); `atomic-file.ts` (stage-then-rename writes: `atomicWrite`, its `Sync` sibling for callers that cannot yield, and `atomicCreate`, the exclusive form the instance lock claims with); `process-identity.ts` — the ONE answer to "is pid N still the process I recorded", `ps`-reported start time within a 2s tolerance, shared by the two things that act on a pid they do not hold a handle to (a bare `kill(pid, 0)` cannot tell a recycled pid from the original, and both readers below would then SIGKILL or refuse to boot on a stranger); `instance-lock.ts` + `instance-lock.lifecycle.ts` — **one daemon per userData dir**. The port fallback stays (a FOREIGN process on 47615 must not block a start), but a second GENIRO daemon is refused: it would share the SQLite file and overwrite the pidfile, which is exactly what a stray `pnpm daemon:dev` did for 19 hours beside the app's own daemon. The lock records the holder's process start time, so a SIGKILLed daemon's leftover lock is self-healing with no staleness window to tune — the next launch cannot confirm a dead holder and takes over at once. Released on Nest's shutdown hook, NOT `process.on('exit')`: Nest re-raises the signal after its hooks and default signal termination never runs `exit` listeners (observed — the pidfile was cleared while the lock file was not); `idle-shutdown.lifecycle.ts` — the daemon exits ITSELF after `GENIRO_IDLE_EXIT_MS` with no connected WS client **and** no in-flight turn. Two conditions, not one: no client is what makes it unused, no turn is what makes it safe to stop, and a workflow keeps running after its window closes. It exists for the launches the UI supervisor can never clean up after — it only terminates the daemon it OWNS, and a force-quit or crash leaves one it does not. SIGTERM at itself rather than a direct exit, so the `ProcessRegistry` drain and pidfile cleanup still run. **Disabled unless the environment names a window**, which only `DaemonSupervisor.spawnDaemon` does (10 min): `pnpm daemon:dev` and the throwaway `pnpm generate:api` daemon have no client by design and must not read that as being unwanted; `crash-guards.ts` — the process-level `unhandledRejection`/`uncaughtException` handlers, installed before Nest so a stray rejection logs instead of crashing past the `ProcessRegistry` drain. An uncaught exception SIGTERMs the daemon at ITSELF so the shutdown hooks still run, and that is the one thing here with a trap in it: **Nest runs those hooks inside its own SIGTERM listener**, so a hook that throws comes straight back as another uncaught exception. It is latched (`shuttingDown`) for exactly that reason — unlatched it re-sent SIGTERM and re-ran the hooks on every re-entry, each arming its own 6.5s failsafe timer, so the live timers piled up until the process aborted on memory. That abort is the macOS **"Electron quit unexpectedly"** dialog a user reported seeing periodically. Every handler body is also wrapped so it cannot throw out of itself — the debug sink writes to a file, and a stream the shutdown already closed is the same loop reached through the logger.

      **A claude session's FIRST prompt is held until the CLI's MCP servers have finished dialling.** The CLI dials its servers when the PROCESS starts and does NOT wait for them before running a turn, so a prompt written too early can find some servers still `pending` and lose their tools for the rest of the conversation — nothing is permanently missing (the surface GROWS mid-turn), so the damage is entirely in what the model concludes once and never re-checks. That is also why it is intermittent. The oracle is `mcp_status`, an undocumented client-initiated control request on the same stdin dialogue as `can_use_tool`, found by enumerating the shipped binary's subtypes and then driven live: it answers BEFORE any prompt has been written, with one row per server under `mcpServers` (not `servers` — reading the obvious name returns an empty list from every healthy reply, which is indistinguishable from "discovery has not started"). The gate polls it and releases on two IDENTICAL readings with nothing `pending`, never one: discovery is gradual, so a single quiet moment is also what a half-discovered list looks like. Only `pending` blocks — waiting for `needs-auth` to become `connected` would hold every first message for the full deadline on any machine with one signed-out server. Three exits bound it: an empty reading is believed for a 2s grace (a machine with no servers), a `refused` reply releases at once (a renamed subtype costs the fix and never the turn), and a 15s deadline releases with a `notice` NAMING the servers still starting, because a turn that silently runs on the old surface is the bug report again. The seam is agent-agnostic — `TurnDriver.awaitPromptReady` awaited by `CliTurnOptions.holdPrompt` in `spawn-cli.ts`, FIRST turn only (the wait belongs to the process, and by turn two the servers have been up for a whole turn) — and cursor defines neither, so its opening write stays synchronous. Two claude turns are outside it as well: one carrying `isolateMcpServers` loads no server by construction, and one naming no approval mode is a geniro-internal probe that never reaches a tool. A cancel during the hold DROPS the prompt rather than writing it into a turn the user already stopped, and a gate that throws is logged and the prompt sent anyway — losing the user's message would be worse than the defect being fixed.

Reaching that name is where the two shipped CLIs diverge, and it takes two adapter methods rather than one because the two acts cost different things. cursor WRITES a generated title into `<sessionId>/meta.json`, so `AgentAdapter.readSessionTitle` reads it for free and is re-read on a few later turns (a cursor conversation is named only after an exchange). Without it a chat opened with a pasted URL was named after that URL for good, which is what got reported. Order and budgets are the service's: ownership is checked FIRST (one indexed query is now what stands between a renamed chat and a spawn), reading is bounded by `CHAT_TITLE_UPGRADE_TURNS`, and asking is one-shot — separate sets, so a CLI whose null means "no such mechanism" keeps its full read budget. What the ending decides is only whether the CLI may be ASKED, since a read is a file open while an ask spawns a process and bills a model call, and a turn that died has nothing to name the derived title does not already say. It only ever writes a title that is still exactly what this service derived, which is what makes a manual rename permanent and is why the run row needs no "who named this" column; `run-teardown` — the ONE delete teardown (cancel → wait for the caller's in-flight work to stop writing → revoke call tokens, purge `runs`/`items`/`node_state` with the `softDelete` filter disabled, drop attachments, announce `runDeleted`), shared by the chat delete and the graph executor's `deleteRun` so neither can drift out of clearing a store.

    **A turn does not end on its CLI's turn-end line while a DELEGATE it started is still out** (`spawn-cli.ts`, `TurnState.openWork`/`deferredTerminal`, fed by the agent-agnostic `background_work` event). The turn-end line is the end of what the agent was SAYING, never of what its process is DOING: probed on claude 2.1.231, a turn told to launch a delegate and not wait for it printed its `result` while the delegate was still running, and the CLI then ran a whole FURTHER turn of its own accord as the delegate reported — that continuation's own result line says so, `origin:{kind:"task-notification"}`. Settling on the first `result` therefore ends geniro's turn mid-work and hands everything after it to nobody — whole assistant messages dropped for want of a turn to put them in, and permission requests answered with no card ever shown — while the run reported `completed` and its delegates rendered `stopped`. So a `turn_complete` is HELD while `openWork` is non-empty, and the hold ends one of three ways: RELEASED with its held result when the last unit reports, or — bound by the turn's existing silence deadline — when the outstanding work is given up on, rather than overwriting a finished turn with "produced nothing…"; or DISCARDED with no result ever emitted when the turn demonstrably continues before either of those fires, because the main thread speaks again (`RESUMES_A_HELD_TURN`, main-thread events only) or a follow-up is delivered into the held turn — releasing the stale result there would settle the turn in the middle of the agent's next answer, so the turn instead runs on to its NEXT terminal. Only a `turn_complete`, and only on a `session` stdin lifetime: a cancel is the user asking to stop now, an `error` is a turn that failed rather than finished, and a turn whose process ends with it has no "after" to wait for. Claude reports the lifecycle on `system/task_started` + `task_updated`/`task_notification` (both terminal channels mapped — they spell one outcome `killed` and `stopped`); a CLI that reports none simply never emits the event and its turns settle exactly as before, so this is not a capability an adapter must declare.

    **The release of a hold is not the end of the turn — it is the moment before the CONTINUATION** (`HELD_TERMINAL_GRACE_MS` in `spawn-cli.ts`). The hold ends when the last delegate reports, and that is precisely when the CLI is about to speak again: the way it LEARNS a delegate finished is a task notification, which opens a whole further turn of its own. So the release fired one breath ahead of the continuation and geniro settled the turn, painted `completed` and posted a system NOTIFICATION into that gap. REPORTED as "Тред запускает какую-то фоновую задачу, выполняет её, говорит мне «done», но потом сразу продолжает работать… я получаю фейковую нотификацию и фейковый статус". TRACED in the reporter's own daemon log on run `309e0822`: held at 13:00:45, `releasing the held 'turn_complete' — its background work has reported` at 13:02:48, badge `completed` in the same second, the agent writing "Explorer returned with substantial findings" ten seconds later and working on for thirteen more minutes. The mechanism to prevent it already existed and was one step out of reach — a main-thread event DISCARDS a held terminal (`RESUMES_A_HELD_TURN`), so a turn that visibly continues runs on to its NEXT terminal — but it only ever ran BEFORE the release, and the continuation lands just after. A released hold therefore waits ten seconds before settling, which is all the existing rule needs to see it. The number is a measurement, not a guess: across the 22 releases in that log the agent was producing again within 4s of eighteen and within 8.3s of twenty, the two stragglers (15.3s, 39.2s) having the shape of a fresh user message. The grace costs nothing in the common case — the turn does continue, so the settle was never due — and in the genuine-ending case it delays a badge and a notification by ten seconds, which is the right way round: a late "done" is a wait, an early one is a lie. **The timer re-reads `deferredTerminal` rather than closing over the event it was armed with**, and that re-read is the whole cancellation mechanism: a discard nulls the field and the timer finds nothing due, so there is no second `clearTimeout` to keep in step with every future way a hold can end. The off-turn twin gets the same grace AND, newly, the same discard — without the second half the grace would only have delayed a wrong answer.

**A backgrounded COMMAND is deliberately not among them, and that carve-out is the whole of `unit === 'agent'` in `trackBackgroundWork`.** Every unit on that channel used to hold, on the reading that the turn plumbing "only cares about identity" — but the two ends are not alike. A delegate's completion makes the CLI open a whole further turn of its own, which is the incident above and needs a turn to land in; a backgrounded `pnpm dev` reports nothing, ever, so the hold ran to the 30-minute silence deadline and the thread read `working · waiting on 1 background task` above an agent that had finished and was waiting for its user — REPORTED against a screenshot of exactly that, three passes after the badge's own wording had been argued over twice. What the hold bought for a shell is now bought better elsewhere: its end is a durable `shell_info` row, the command itself is a first-class row in the running-shells panel with its own terminal behind it, and anything the CLI says once it lands rides `handleBetweenTurnEvent` — which did not exist when the hold was written and is what makes the carve-out safe. An unclassified unit (`'other'`) counts as a shell, which is the reading `announceDelegateWork` already takes, so a CLI that names no kinds cannot get delegate treatment through one path and not the other.

    **A background SHELL's OPEN is a transcript row too, and it was not for one release** (`shell_open` items). It mapped to null on the reasoning that a command's start is already in the transcript as the tool call that detached it. The CALL is; the DETACHMENT is not — and that is the fact a reader needs. Which calls this CLI put in the background is read here off its own structured frames, and the renderer was left to recover the same fact by matching the CLI's ENGLISH (`readLaunchHandle`), a match that is deliberately strict and therefore misses by design. Every miss put `Run.shellsOpen` — which counts exactly these events — over a transcript naming fewer commands than the count, and the two are read by DIFFERENT surfaces: REPORTED as a sidebar row saying `working · waiting on background work` beside a header counting zero shells. The row makes them two views of one set. It doubles nothing (the reader marks the call it names and never adds a command), and it had to join `restatesRunAsWorking` — renamed from `closesWork`, which stopped being an accurate name once a non-close belonged in it: an open really is work beginning, but a backgrounded command deliberately does not hold a turn (`trackBackgroundWork`'s `unit === 'agent'` carve-out), so reading it as the AGENT working would latch the spinner with no further row until the close to take it down. The badge it earns is `held`, which `shellsOpen` already drives.

    **A background SHELL's end is a transcript row, because nothing else records it** (`shell_info` items; `AgentEvent`'s `shell_info`, `spawn-cli`'s `announceShellWork`). A detached command's launching tool call is answered within the second (`Command running in background with ID: …`) and the command runs on for minutes — so the transcript holds a start and no end, and a client folding "what is running" out of tool calls lists it forever. Measured 2026-08-24 on claude 2.1.237: a 45-second `sleep` reported its completion to the MODEL as a `system/task_notification` frame and to the conversation as a sentence the agent wrote, with no probe anywhere in the transcript. The frames were already parsed (`background_work`) and thrown away for want of anywhere to put them; `announceShellWork` is the twin of `announceDelegateWork` for the units on that channel that are NOT delegates, and the two are told apart by what the `started` line said, never guessed. Three details are load-bearing. It runs BEFORE the delegate twin, because it decides "is this a delegate?" by asking `delegateWork`, which that twin deletes from on the settle carrying figures — the other order announced every delegate as a shell as well. It announces ONCE per unit (`settledShells`): claude reports the same ending on `task_updated` AND `task_notification` 7ms apart, and the row is durable, so a duplicate is stored for the life of the transcript — measured, two identical rows per background command, before the guard. And it is a `shell_info` rather than a `subagent_info`, since announcing a shell as a delegate is exactly the phantom sub-agent the delegate twin refuses to create in the other direction. **It also had to join `closesWork`** (renamed from `closesADelegate`): a settled run producing a row goes back to `running`, and a `pnpm dev` finishing minutes after a chat settled would otherwise put that chat's badge back with nothing able to take it down — the same latched spinner the delegate half of that predicate exists to prevent.

    **A dynamic WORKFLOW's fleet is a transcript row too, and for a stronger reason than the shell's: nothing about it reaches the conversation at all** (`workflow_info` items; `AgentEvent`'s `workflow_info`, `CLAUDE_TASK_PROGRESS_SUBTYPE`). Claude's `Workflow` tool is ONE tool call that fans out into dozens of agents running inside its own orchestrator with transcripts of their own — so the whole of what geniro could say about a twenty-minute, half-million-token workflow was `running Workflow · 20m 34s`. Probed live on 2.1.251 (a two-agent script under `-p --output-format stream-json --verbose`): the launch is a `system/task_started` carrying `task_type:'local_workflow'` and the workflow's NAME, and progress rides `system/task_progress` on the same `tool_use_id` — running totals every time (`usage.total_tokens` is the SUM over the roster, 13779 + 13780 = 27559 on the probe, so it is the workflow's own bill and not the turn's), and the full agent roster whenever one of them changes state. Three details are load-bearing. `task_progress` is SHARED with delegates, so the roster's presence is the discriminator — a delegate's line names a `subagent_type` and carries none, and mapping those would card every Task call. Only the roster-bearing lines become rows, which is what keeps the channel from writing a transcript row every few milliseconds: the CLI attaches the roster on a state change or at most every ten seconds, and since an agent's tokens are reported as it FINISHES, every line that moves the totals carries the roster with it. Measured through the app rather than estimated — a 90-second, six-agent workflow wrote 12 rows totalling 10KB, so the twenty-minute one this was built for costs a few hundred KB for the only record its fleet ever ran. And the launch line is the only one that ever states the workflow's name — every line after it reports the description instead — which is why the anchor is emitted at `task_started` rather than waiting for the first roster.

**What the CLI does AFTER its turn settles belongs to the run, not to nobody** (`ChatService.handleBetweenTurnEvent`). A turn's `result` line ends the turn geniro started; it does not stop the CLI, which routinely opens a further turn of its own accord when a delegate reports back — that continuation's own result names itself `origin:{kind:"task-notification"}`. `spawn-cli` has no turn to hand that output to, so it arrives on `onBetweenTurnEvent`, which used to keep only the two halves of a tool call on the argument that those carry an id pairing them while a stray message has no anchor — dropping every other event type the CLI produced off-turn. What the user sees is what was reported — a run badged `completed` with more work appearing under it, and the agent's own messages after that point simply not arriving. The rule is now the in-turn rule: whatever `mapEventToItem` yields a row for is persisted in arrival order, the live signals feed the same partial stream, the self-reports feed the same harvest stores, and the continuation's own terminal event settles the run again. A settled run producing rows goes back to `running` with `offTurnActivity` naming it as the CLI carrying on by itself rather than as a fresh turn. Two runs are exempt: one the user CANCELLED (Stop is final — a straggling result flipping `cancelled` back to `completed` says their Stop did not take, though the rows are still written, because a transcript that hides work is lying the other way), and one whose `running` this path did not write, which `offTurnRuns` is what distinguishes — the handler is async, so a real turn can have opened in between, and settling THAT turn's run on the previous one's tail is the defect `cancelledTurnMayStillEmit` exists to stop. **A ROW is not the only evidence that the run is working again** (`restatusAfterOffTurnSignal`): an agent that is THINKING has emitted none, and on a long think it will not for minutes, so a live `Thinking… 500 tokens · 6s` line sat directly under a `✓ done` footer with the badge still reading `completed` — the reported "It show as completed, but its actually thinking". A main-thread `text_delta` or `thinking_progress` from a SETTLED run therefore flips it back too, on the same terms as a row (a delegate's is not the run's, and Stop is still final). Its own method rather than another caller of the row path, for two reasons: a delta fires many times a second and the phrase never changes, so `offTurnRuns` short-circuits the rest of the burst before it reaches the database, and a run whose `running` belongs to a REAL turn is left entirely alone instead of having that turn's activity phrase restated — a row is worth re-announcing for, an unfinished word is not. `context_progress` is deliberately excluded: it measures the WINDOW rather than asserting that anything is being produced, and it is also emitted synthetically once a compaction has FINISHED. **And a DELEGATE'S own rows are evidence too, under a lease rather than a latch** (`leaseOnDelegateRow`, `closedDelegates`): a delegate whose launching `Task` call has already returned has nothing holding the turn open for it — `spawn-cli` holds only on `background_work`, which is the CLI's own `task_started` bracket, and a delegate it never brackets is invisible to that mechanism — so the `result` line settles the run while the delegate's steps go on arriving. Reproduced against the real renderer: two sub-agent blocks climbing from 0 to 7 tool calls, every row persisted, under a header reading `✓ completed`. That is the reported «выполняются какие-то внутренние процессы, но он показывается как Completed». Such a row now flips the run back too — but it CANNOT go through the row path, whose `running` is ended by a terminal event that a delegate never produces: restating a delegate's trailing rows there is exactly what latched a `still working` spinner on with nothing able to take it down. The lease is that missing off-switch, renewed free by each further row and expiring after `DELEGATE_ROW_LEASE_MS` back to the status it took over. The two cases are told apart by EVIDENCE, not by timing: a bracketed delegate reports its own end, `spawn-cli` relays that as the `backgroundOpen: false` announcement that closes its block, and `closedDelegates` records it from BOTH handlers — in-turn for a delegate whose whole life fits inside its turn, off-turn for one that outlives it — so a named delegate's tail restates nothing while an un-bracketed one's stream takes the lease. In the happy path the expiry is never reached: a delegate that reports back makes the CLI open a continuation turn, and that turn's own `result` settles the run through the ordinary path.

**An off-turn `running` has a SECOND ending, and without it the badge could outlive everything that could take it down** (`ChatService.settleAfterSessionClosed`, over `AgentSessionRegistry.onClosed`). The latch a main-thread row takes ends only on a terminal event; the lease at least expires. Close the PROCESS that owed that terminal event and neither can happen — REPORTED twice, as "seems like its stuck" and "It finished but stucked - i have to ask about a status to continue". Reconstructed from the author's own `geniro.db` and debug log, run `1fb3a9f5` on 2026-08-22: the last off-turn row landed at 11:33:52, the session was reaped at 11:33:55, and nothing was announced again — the row read `running · still working` and the composer refused to send until the user typed a message, which is exactly what the second report describes doing. So a close now hands the badge back, and it is a different fact from the expiry rather than a shorter clock: the expiry is a GUESS that a quiet delegate has finished, a close is the CERTAINTY that nothing more can arrive. The status to restore therefore moved onto `offTurnRuns` itself (a `Map`, not a `Set`), since both kinds need restoring on identical terms and the lease's private copy was the second place that fact could drift. Nothing is announced during SHUTDOWN — every session is closed on the way out, and the next boot's reconcile owns those runs.

**And the idle window measures a chat going UNUSED, which a CLI writing rows is not** (`AgentSessionRegistry.touchOffTurn`). `session.idle` means "alive with no turn of OURS in flight" — true of a CLI running flat out between turns — so the window armed at the last settle simply ran out underneath live work. Same run, and the timing is exact: armed at the 11:03:55 settle, thirty minutes of continuous off-turn output touching nothing here, reaped at 11:33:55, three seconds after the last row. An off-turn event now refreshes the timer, the same reading the `parked` exemption beside it already applies. It refreshes rather than arms, and only when a window is already running: with a turn in flight there is deliberately no timer, and `track` arms the next one when that turn settles. It rides the caller's `onBetweenTurnEvent` sink, so a caller that supplies none keeps `spawn-cli`'s "dropped an event arriving between turns" warning instead.

**The ceiling itself is DERIVED from the machine, not a constant** (`sessionCeilingFor`, `MAX_LIVE_SESSIONS`). It was a flat `3`, which is defensible on a 16GB laptop and absurd on the 128GB desktop it was reported from — there the fourth chat paid a cold start (~6.5s, every MCP server rebooted) while 110GB sat free, and REPORTED as "что за max live session… это очень мало!". Total memory × ⅛ ÷ ~1GB per session, clamped to [2, 16]: 8–16GB → 2, 32GB → 4, 64GB → 8, 128GB → 16. The per-session cost is a MEASUREMENT (2026-08-25, the daemon's own four claude processes: 1202/1129/905/897MB) of the heavy case — a CLI with ten MCP servers dialled — so it over-estimates in the safe direction. Three choices in it are worth keeping: TOTAL memory rather than free, because free depends on what the machine was doing at boot and the same computer would otherwise get a different ceiling on each launch; a ⅛ SLICE rather than a share of what is available, because these processes are a cache (any of them re-opens with `--resume`, costing latency and nothing else) and the user's editor and browser announce themselves nowhere here; and a CAP at 16 that is not about memory at all — past a dozen the constraint is the person, since these are conversations somebody is meant to be following. The registry takes the ceiling as an `@Optional()` constructor argument purely so its specs can pin one: an eviction case asserting which of three sessions went means something different at a ceiling of 2 and of 16, and the derivation is pinned separately on the pure function.

**EVICTION had to learn the same thing, and until it did the ceiling could kill a working agent outright** (`AgentSessionRegistry.OFF_TURN_ACTIVE_MS`, `worksOffTurn`). `evictIfFull` exempted a turn in flight and a parked question and took the least-recently-used of the rest — and a CLI carrying on between turns is `idle` by that reading, so it was in the pool. Measured on the reporter's run `309e0822` (2026-08-25, reconstructed from `geniro.db` and the debug log): a claude thread settled its turn at 13:02:48, ran on by itself for thirteen minutes writing a twelve-task plan, said "Starting T1", and its last row landed at 13:16:09 — one second before the ceiling was reached for another chat and this session was chosen as the oldest idle one. `closed the agent session … the session ceiling was reached` and `run completed`, in the same second. The chat then sat 22 minutes showing `completed · worked 26s` over eleven pending tasks until the user typed "status?" to restart it, which is the whole of the report "Тред сам по себе остановился … я должен писать ему какое-то сообщение, чтобы он продолжил". So an entry that produced an off-turn row within the last five minutes is exempt on the same terms `parked` is — `offTurnActiveAt` is its OWN field rather than `lastUsedAt`, which a settling turn also refreshes, because "recently used" and "working right now" are different questions and only the second is worth a process. The window matches `ChatService`'s `DELEGATE_ROW_LEASE_MS` deliberately: both answer "how long do we go on believing a quiet stretch is still work", and two numbers is how the badge and the process come to disagree about whether a chat is busy. It can only push the registry OVER the ceiling, never refuse a turn — that arm already existed for the all-busy case and this widens what counts as busy.

**And a close that INTERRUPTED work owes the transcript a sentence** (`AgentSessionRegistry.onClosed`'s `interrupted` argument → `ChatService.noteInterruptedSession`). Restoring the badge is right on every close, but the status it restores is the one the off-turn stretch took over — routinely `completed`, from a turn that ended before the agent carried on — so the run above reported a clean completion over unfinished work with nothing anywhere naming the cause. The registry is the only place that can tell the two apart (it knows whether the process was working when it closed), so it says which, and the row is written for that case ALONE: every session is closed eventually, and a warning on each would put a red row in every conversation the user owns about nothing. The sentence names the recovery, because there is one and it is not obvious — the conversation is intact, so the next message resumes it. With the eviction fixed this is the net under what remains rather than the fix itself.

    **That silence deadline does not run at all while the turn is blocked on a verdict** (`TurnState.outstanding` non-empty), and that is the absence of a window rather than a longer one. The deadline's premise is that silence is UNEXPLAINED — it exists to catch a CLI nobody can account for. A turn parked on an approval card is the opposite: geniro raised the request, knows the CLI is blocked on it, and is itself the thing withholding the answer, so the clock would be timing a HUMAN, and a human who steps away for lunch has not wedged. Before this exemption, an `AskUserQuestion` card left unanswered while nothing could arrive would eventually settle the turn as `error`, mark the run failed, and rewrite the card the user was coming back to answer as `unanswerable` — a sentence false in every clause, since the CLI had produced both an answer and a question and had given up on nothing. `respondApproval` rearms on DELIVERY, and from that moment rather than from when the card went up, so answering late does not leave the turn moments from being abandoned; a second still-open card keeps it suspended. Two consequences are deliberate: Stop is then the only bound on a parked turn (which is correct — it is waiting for its user, who is the only one who can end the wait), and a parked turn keeps `ProcessRegistry.activeCount` non-zero, so `IdleShutdownLifecycle` will not fire while a question is on screen.

    **A KILL is not a cancellation, and only `cancelRequested` can tell them apart** (`settleFromTermination`'s signal branch). A child that exits on a signal used to settle `turn_cancelled` unconditionally, which is right for the terminations geniro ASKS for — Stop and the shutdown reap both reach `cancel()`, a retired session reaches `close()`, and both set the flag — and wrong for every other way a process dies: an OOM kill, a crash, a `pkill`, a supervisor taking the group down. The damage is not the word but what the word suppresses. `cancelled` is deliberately the ONE ending the app never notifies about (announcing a Stop tells the user what they just did), so a killed agent settled quietly under a badge saying the user had stopped it — a run that failed, told nobody, and blamed them for it. Only a requested cancel (`cancelRequested`) settles `cancelled`; any other signal now settles `failed` and posts `The turn failed.`. The signal is NAMED in the error message (`… was terminated by SIGKILL`), with the stderr tail beside it, since "the process ended" is not a diagnosis.
    **A findings REPORT is a transcript row too, and the only place its findings exist** (`report_findings` items; `HOST_FINDINGS_TOOL` in `chat.types.ts`, `utils/host-findings.ts`, `services/findings-report.broker.ts`). geniro's own MCP server carries a second host tool beside `ask_user_question`: an agent hands over a typed list of code-review findings and the transcript draws them, instead of printing markdown a transcript can only show as prose. The ARGUMENT shape deliberately mirrors claude's own `ReportFindings`, snake_case included, so an agent that knows that tool needs to learn nothing new; `readHostFindingsReport` is the one place that naming seam is crossed. The tool result is a RECEIPT — `10 findings recorded and shown to the user.` — never the findings, which is what keeps them out of the model's window twice; the row is therefore the only copy, and it is persisted rather than streamed for `task_list`'s reason. Every CHAT is handed the endpoint for it (the question tool is still registered only where a CLI has none of its own), and the call auto-approves, because what the agent is asking permission for is the act of drawing in this app's own transcript — a gate there is a press with nothing behind it. Graph nodes keep today's caller-only grant: nothing registers a reporter outside `ChatService`, so a graph caller sees the endpoint and no findings tool.

    **A CHART is the second row of the same RENDER family** (`show_chart` items; `HOST_CHART_TOOL` in `chat.types.ts`, `utils/host-chart.ts`, `services/chart.broker.ts`). An agent hands over typed numbers and the transcript plots them, instead of spending its output on an ASCII bar chart or a table the reader has to hold in their head. Everything above holds unchanged — the payload is the card, the result is a receipt (`Chart drawn for the user: 2 series over 30 points.`), the row is the only copy, every chat is handed it, it auto-approves, no graph node registers one. What is its OWN: **the payload is POSITIONAL.** Every series carries one value per entry of `labels`, matched by index, and a `null` is a GAP rather than a zero. Nothing on either side of the wire may drop or reorder one list independently of the other — that failure does not throw, it silently re-attributes every measurement after the edit and still looks like a chart. Which is why `readHostChart` **blanks** an unreadable label instead of removing it, re-aligns every series to `labels.length` (padding short, cutting long), and why the renderer's twin re-does that alignment over rows written by older builds. Three kinds and no pie (`CHART_KINDS`): a pie encodes magnitude as angle, the hardest encoding to compare by eye, and what it gets reached for reads better as the bar chart already there. The five-series cap is the PALETTE (`--chart-1..5`, and `categoryToken` wraps): on a multi-series plot colour is the only thing tying a curve to its legend entry, so a sixth would claim the first one's colour. A call with nothing plottable is answered as INVALID_ARGS rather than as a drawn chart — unlike an empty findings report, which is a real review outcome, a chart of nothing is only ever a mistake.

    **A SCORECARD is the family's other drawing** (`show_metrics` items; `HOST_METRICS_TOOL` in `chat.types.ts`, `utils/host-metrics.ts`, `services/metrics.broker.ts`). A handful of headline figures with their changes — what an agent reaches for when it has measured a few things and would otherwise write them into a sentence nobody can scan. Everything the chart's paragraph says about the bargain holds: the payload is the card, the result is a receipt (`Scorecard drawn for the user: 4 figures.`), the row is the only copy, every chat is handed it, it auto-approves, no graph node registers one. **The line against `show_chart` is in both tools' descriptions**, because an agent with numbers in hand has to choose: several readings of ONE thing is a chart, one current reading each of SEVERAL unrelated things is this — they share no axis, so a chart of coverage-plus-bundle-size-plus-test-count is one enormous bar and two invisible ones. Two facts about the shape are load-bearing. **Every figure arrives ALREADY FORMATTED, as a string** — only the agent knows whether `0.82` reads `82%` and whether `1258291` is `1.2 MB` or `1,258,291`, so this row displays and never computes, and neither reader may "help" by coercing a number (both sides pin that with a test that goes red independently; the failure would look like the model's mistake and be the host's). There is no `unit` field for the same reason: a unit is part of how a figure reads. **The sentiment is STATED, never derived** — whether a change is good news is not a property of its sign, since `−40ms` is good and `−4 pts` of coverage is bad, and a `higherIsBetter` flag only moves the same guess one step away. An unrecognised sentiment falls back to ABSENT rather than to `bad`, so a misspelling cannot paint a good result red. A call with no readable figure is answered as INVALID_ARGS, on the chart's rule rather than the findings tool's: an empty review is a real outcome, an empty scorecard is only ever a mistake.

    **A COMPARISON is the family's DECISION TABLE** (`show_comparison` items; `HOST_COMPARISON_TOOL` in `chat.types.ts`, `utils/host-comparison.ts`, `services/comparison.broker.ts`). Several options judged against the same criteria, with a recommendation — what an agent reaches for when asked which of these to use. **Alone in this family it has to justify itself against markdown**, because a markdown table RENDERS in this transcript: an agent can already draw three columns of prose and it looks fine. So it earns its place on exactly two things a table cannot hold — a per-cell VERDICT (the shared `SENTIMENTS` vocabulary), which is what makes the winning option's column visibly greener where a table forces the reader through every cell to work out the same answer, and a NAMED, reasoned RECOMMENDATION, because a comparison that does not answer the question has handed the deciding back to the person who delegated it. The tool description says both out loud, and says that a call with every cell neutral and no recommendation should have been a markdown table — so a model can tell the two apart. **The cells are POSITIONAL** against `options`, the chart's hazard again and handled the same way: an unreadable cell is BLANKED rather than dropped (dropping shifts every later cell one column left, filing each option's answer under its neighbour's name — a failure that does not throw and still looks like a comparison), and both readers re-align every row to the option count rather than trusting the model to have counted. TWO options is a real floor, not a formality: a one-column "comparison" is the shape a model produces when it has decided before it has compared, and drawing it would dress that up as an analysis. The recommendation is matched to a column **by name**, case- and whitespace-insensitively — a model writing `SQLite` is far more reliable than one writing `1`, a name matching nothing costs only the column highlight while the reason still reads, and an index pointing at the wrong column would be silently wrong. Half a recommendation is dropped whole: a named option with no reason is an assertion the reader cannot weigh, a reason naming no option is a paragraph.

    **A GALLERY is the family's PICTURES** (`show_gallery` items; `HOST_GALLERY_TOOL` in `chat.types.ts`, `utils/host-gallery.ts`, `services/gallery.broker.ts`). Several images shown together as a thumbnail grid that opens into the full-screen viewer, where the reader can zoom and step between them. It carries a class of answer none of the other five can: screenshots before and after a change, the frames of a flow, charts some other tool wrote to disk. Without it an agent's only move is a markdown image per picture — a column of full-width images with no way to step between them and nothing saying they are ONE set. The ordinary bargain holds: the payload is the card, the result is a receipt (`Gallery shown to the user: 3 images.`), the row is the only copy, every chat is handed it, it auto-approves. **What is its OWN, and it is the sharpest difference in the family: this payload names FILES where every other one carries its own content.** Nothing is embedded — each entry is a PATH the RENDERER later resolves through the same `GET /v1/chats/:runId/image?path=` route a markdown image already uses, under that route's own guards (extension allowlist, real regular file, canonicalized before the stat, byte ceiling). So it adds no reach an agent did not already have: it could write `![](x.png)` today and the renderer would fetch it identically. What it adds is N at once, which is what `MAX_GALLERY_IMAGES` bounds — a cap on how many file reads ONE call can trigger, rather than on how much a card can readably hold. The daemon never opens any of them, so a path that has since moved costs one broken tile rather than a failed call, and the agent is still told the row landed, which is the only thing the call actually did. Unreadable entries are DROPPED where the chart's cells are blanked, and the two are not inconsistent: a chart is positional, so removing a cell re-attributes every later measurement, while a gallery is a SET and a tile naming no file has nothing to draw. Its line is against MARKDOWN rather than against a sibling tool — ONE picture is a markdown image and reads better inline; this is for a set, and its value is that the reader can step between them. Both halves are pinned in `mcp-server.service.spec.ts`'s description audit.

    **A PROPOSED PATCH is the family's third tool and its first side effect** (`HOST_PATCH_TOOL` in `chat.types.ts`, `utils/host-patch.ts`, `utils/apply-patch.ts`, `services/patch.broker.ts`). The agent proposes a change it has NOT made; the transcript shows the diff with Apply and Reject; geniro writes the file if the user accepts. Three ways it is not like its siblings, each load-bearing. **It PARKS** — and rides an ordinary `approval_request` row carrying `toolName`, exactly as `ask_user_question` does, so the card, the verdict route, the WS gateway and the settle-time sweep all serve it unchanged (its own `outstandingPatches` set exists only so the sweep can say "before the patch was answered" rather than "the question"). **It carries a real gate, and exactly ONE.** The tool CALL auto-approves like its siblings' — that was got backwards first, and a live turn showed why it matters: without the `autoApproves` arm the user saw a meaningless "allow propose_patch?" card and *then* the patch card, and answering the first decided nothing, because calling the tool writes nothing. The write is behind Apply on the diff, and THAT card appears even in `auto` mode: mode governs `autoApproves`, which is the path the CLI's request to call the tool takes, and the proposal card does not go through it. **Its caps REFUSE rather than truncate**: every other cap in this family truncates because a model that found forty things still did the work, but the first N characters of a file body is a TRUNCATED FILE. The arguments are `Edit`'s own names (`file_path`/`old_string`/`new_string`) so the renderer's `editDiffOf` draws the diff with no second diff renderer, and an omitted `old_string` falls through to `Write`'s additions-only shape. `applyHostPatch` is the only place the family touches disk: the write must land inside the run's cwd, checked **twice** — lexically, and again on the REAL path of the containing directory, because a lexical check alone is satisfied by a symlink sitting inside the folder and pointing anywhere (both halves are pinned by tests that go red independently). An `oldString` must match **exactly once**: zero means the file moved on, more than one means picking the first is a coin flip on which occurrence the user actually read in the diff. Outcomes are four, and `stale` earns its place — the user said YES and the write still could not happen, so telling the agent "declined" would have it argue when the right move is to re-read the file. Filesystem errors travel as their `code` alone: an `ENOENT` message carries an absolute path, and that string goes to a model whose provider is off this machine.

    **A PROPOSED PLAN is the family's fourth tool: a gate BEFORE the work** (`HOST_PLAN_TOOL` in `chat.types.ts`, `utils/host-plan.ts`, `services/plan.broker.ts`). The agent shows how it means to carry a request out — a title and a short ordered list of steps — and the call blocks until the user answers. What that buys is the cheapest correction there is: a plan is redirected in one sentence, while the same misunderstanding found after the edits costs a revert. Structurally it is the patch tool's twin — parks on an ordinary `approval_request` row, its own `outstandingPlans` set so the sweep says "before the plan was answered", `question: false` so the badge reads *waiting for approval*, and the CALL auto-approves because proposing changes nothing. Three things are its own. **Approving performs NO action**, so there is no `stale` arm: nothing can have moved underneath a decision that touches nothing, and the verdict IS the answer. **Both verdicts carry an optional NOTE**, and that is where most of the value is — a bare "no" tells an agent nothing and costs a round trip to ask what the user would rather have, while "no — leave the parser alone, just fix the cap" redirects it in the same press. It rides the `answer` field the approval channel already carries for questions (unconditionally, all the way from the WS `verdict` handler), and it is normalized to absent when blank, so the agent is never handed silence to quote back. `hostPlanResultText` puts the note INSIDE the sentence for the same reason: an approval carrying a caveat must not read as a plain yes, and a refusal carrying a redirection must not read as a wall. **Its caps TRUNCATE**, on the findings tool's rule rather than the patch tool's — a plan that overran is still a plan, and `MAX_PLAN_STEPS` is where one stops being readable at a glance, which is the only thing this card is better at than prose. Two rules the daemon side follows. The import is **prepared before the run row exists**, so a refusal leaves no half-made thread and the user gets the CLI's own sentence instead of a chat whose first message dies on a session nobody can find. And the happy path writes **no system row at all**: the transcript is its own evidence that the import worked, so only what the transcript cannot show by itself earns a line — history left out, or a record that could not be read (`severity: 'info'`, never the failure chrome every other daemon notice wears).

**The cursor transport (ACP)** — every cursor turn runs under its **own throwaway `CURSOR_CONFIG_DIR`**, seeded with a copy of the user's `cli-config.json` and nothing else (`adapters/cursor-acp/utils/cursor-profile.utils.ts`, materialized by `prepareTurn` and swept at boot). Not hygiene — a correctness fix: applying a model or an effort over ACP PERSISTS into that directory, so before this a chat's model choice silently changed what the user's own `cursor-agent` opens with (measured: one `session/set_config_option` rewrote `model`, `selectedModel` and `modelSelectionHistory` in the real `~/.cursor/cli-config.json`). The copy keeps their permissions, approval mode and default model; `mcp.json` is deliberately NOT copied or symlinked — it is 0600 and holds their own server credentials, and it is unnecessary, which had to be measured rather than hoped: under a directory holding only `cli-config.json` an ACP session still loaded the folder's MCP servers and `mcp list` still reported all of them, because the CLI resolves that file from the user's home either way. Cost was measured too: a handshake under a fresh directory is no slower than one under the default profile, so the CLI cache it writes per turn buys no latency penalty. The model listing takes its own profile for the same reason (a parameterized handshake can migrate a persisted variant selection, which writes). **The one thing that must NOT be per turn is the CONVERSATION**, and missing that shipped a build where every cursor chat's second message died: the CLI keeps each ACP thread at `<configDir>/acp-sessions/<sessionId>/` — inside the directory the disposer removes — so `session/load` answered `-32602 Invalid params {"message":"Session … not found"}` and the turn failed before its prompt (probed both ways on 2026.08.11-e8db854: the same load under the profile that created the session succeeds). So that ONE name is a symlink to `<userData>/cursor-sessions`, shared by every turn, while the settings the isolation exists for stay per turn — measured through as well: the CLI writes the store THROUGH the link, a second throwaway profile resumes the session and answers a codeword only turn 1 was told, and `node:fs` `rm -r` unlinks the symlink rather than descending into it. The store is deliberately NOT nested inside `cursor-profiles`, which the boot sweep removes wholesale. A `session/load` the agent REFUSES is now a degrade rather than a dead end — a `notice` naming the loss and a fresh `session/new`, because every later turn resumes the same id, so a hard failure made the chat unusable for good (`'session_load'` is a pending kind of its own in `acp-driver.ts` for exactly this).

**The CONTEXT WINDOW is a per-model parameter, and picking one is a real setting rather than a label.** REPORTED as "у курсора есть еще размер модели, то есть 1 миллион, 300к … Я должен быть способен его выбрать везде". It rides the same `configOptions` machinery the effort chip uses (`context`, category `model_config`, `CURSOR_CONTEXT_WINDOW_PARAMETER_ID`), so it is stored per run (`Run.contextWindow`), per workflow node and per saved run configuration, and it reaches the turn through `cursorModelSelection` — which already applied a `context=` pair carried inside a legacy composed id, so the mechanism is not new, only reachable. Three measurements decided the shape. It is per MODEL: swept across all 34 models an account offers, twelve have the axis and their values differ (`300k|1m`, `272k|1m`, `200k|1m`). The numbers are never mapped here — `1m` is the CLI's own word, and what it produces is read back out of that CLI's own accounting, which is what the meter draws. And the frame must be AWAITED: this CLI binds the window when the turn BEGINS, so the driver's ordinary pipelining (frame and prompt sent back to back, on the reasoning that one ordered stream already orders them) leaves the turn on the model's default — measured on identical frames, `1m` awaited gives a 1,000,000-token window and `1m` pipelined gives 300,000, with the agent's reply confirming `context = 1m` either way. Hence `AcpModelParameter.applyBeforePrompt`, which the driver honours by holding the prompt (and releasing it on a refusal, so a turn is never stranded behind a setting that could not land). It is set on this axis alone: nothing has measured the effort axis to bind at turn start, and the deferral was priced at ~1.4s per turn when it was considered for the model frame.

**Max Mode is the user's own switch, defaulting ON, and it is the whole of the second context axis.** The paragraph above describes the `context` parameter, which twelve of thirty-four models carry. The other twenty-two — `kimi-k3` among them — were reported as "runs at one fixed context window", and the size was wrong: they take their window from **Max Mode**, a top-level boolean in `cli-config.json` (`CURSOR_MAX_MODE_CONFIG_KEY`), and geniro writes it explicitly on every turn (`CursorProfileSeed.maxMode`), from `Settings.cursorMaxMode` → the wire → `Run.cursorMaxMode` → `AgentTurnInput.cursorMaxMode`, falling back to `CURSOR_MAX_MODE` (true) for a turn that says nothing. It travels the `customInstructions` road exactly — the client sends it because settings live in the Electron process, and it is SNAPSHOTTED onto the run, so flipping the switch changes the next chat rather than moving an open conversation between a 200k and a 1M window mid-thread. A NULL column is a run created before the setting and reads as the DEFAULT, never as OFF: every such run has always used Max Mode, and reading absence as a decline would quietly shrink them all. Measured 2026-08-25 on 2026.08.11-e8db854 over ACP with the flag as the only difference: `kimi-k3` reports `maxTokens` **200,000** off and **1,048,576** on. It can only ever widen, which is why ON is the default — a model that HAS the `context` parameter obeys the parameter and ignores the flag (`gpt-5.6-sol` at `context=272k` reports 272,000 either way), a model that has neither is unchanged (`composer-2.5`, 200,000 both ways). So every model runs at the largest window it has, the choice where there is one stays the CLI's own answer read from its own handshake, and geniro holds no table of anybody's context sizes. Written EXPLICITLY rather than inherited: the per-turn profile is a copy of the user's own config, so an untouched key means "however their terminal was last left" — the same chat ran at 200k or 1M according to a switch flipped in another app. What it COSTS is why there is a switch at all: Cursor bills Max Mode at the model's API rate plus 20% on LEGACY request-based plans, while on current token-based plans it is the billing mode several models are already on — and which of the two a user is on is not something this app can read. OFF is written as explicitly as ON, for the same reason ON is: an untouched key means "however their terminal was last left".

**A rejected design worth not rebuilding.** The middle case first shipped as two rows of geniro's own invention in the context-window picker (`standard` / `max mode`) whose SIZES were learned from turns that had run, accumulated in `ContextWindowStore` under a per-setting key and overlaid onto the listing. It was rejected on two grounds, both right: Max Mode is a MODE rather than a context window, and a learned size is a cache that is wrong from the moment the vendor changes a number until the user next runs a turn. Neither is answerable by a better cache. The capability question that made it tempting is real and has no answer on this transport — `supports_max_mode`, `context_token_limit` and `context_token_limit_for_max_mode` are fields on the CLI's own server model message, a `session/new` reply carries `modes`/`models`/`configOptions` and nothing else with `{modelId, name}` model entries, no model table is cached on disk, and `maxModeAutoEnabled` is bookkeeping the CLI writes itself for models whose catalog entry says `requiresMaxMode` (measured: setting it by hand changes nothing). Always-on sidesteps the question entirely.

**Two fixes from that attempt were kept, both independent of it.** `ContextWindowStore`'s key gained the window CHOICE as a third component — without it a chat at `context=300k` and one at `1m` on the same model share an entry and each turn overwrites the other's figure, which is the "1M shown as 200k" class of defect from a new direction. And the ACP transport now ANNOUNCES its model (`AcpDriver.currentModelId` → a `turn_model` event): only claude emitted one, so a cursor chat had nothing to scale its meter against until a turn COMPLETED, and the cross-run window cache — which files a measurement under the model that reported it — could never be written from this transport, since cursor's session store records a full breakdown and names no model. The id is the agent's OWN (`models.currentModelId` from the session reply), replaced by the requested one when this turn switches; a refusal is not silent, so the attribution is knowably approximate rather than invented. `buildUsage`'s `contextModel` falls back to it and keeps its existing guard — a model id is a label ON a denominator, never a name offered with nothing being measured.

**That session store is also where this CLI's context accounting lives** (`utils/cursor-context-store.utils.ts`), and reading it is the whole reason a cursor chat can show a breakdown at all. Over ACP the agent says NOTHING about its window — re-measured 2026-08-15 against a raw frame capture of a real tool-using turn, five `sessionUpdate` variants and a bare `{"stopReason":"end_turn"}`, with all three "context"-shaped keys being `embeddedContext` — so the adapter recorded "no usage" and the panel said so, which is what got reported ("Курсор должен как-то нам давать какие-то значения"). The figures were never absent, only off-protocol: the CLI writes a full breakdown per turn into `<sessionId>/store.db`, which is what its own TUI renders, and geniro already owns that directory because the per-turn profile symlinks into it. So this needs no new access, only a parser: `meta` holds one hex-JSON header carrying `latestRootBlobId`, `blobs` is content-addressed, and the root blob is protobuf — `{1: used, 2: window, 3: repeated {1: key, 2: label, 3: tokens, 4: chars}}`. Three things keep it honest. It is opened READ-ONLY through node's OWN `node:sqlite` (this file has nothing to do with geniro's ORM, and the built-in costs neither a dependency nor a rebuild against Electron's ABI) — geniro owns the directory but not the format, and nothing may write to another program's store. The block is found BY SHAPE rather than by field number, walking the message tree for rows of (string, string, varint), so a vendor adding a field still parses. And the arithmetic is re-checked rather than trusted: the categories must sum EXACTLY to the stated total, which is what the probe found to hold and what rejects a different block whose rows merely look alike — a genuinely changed encoding then yields null and no breakdown, never a number read out of unrelated bytes. An ESTIMATE was the obvious alternative and was measured to be unusable: 346 characters of transcript against claude's 23,575 `Messages` tokens on a comparable thread, ~250× wrong, because the window is dominated by tool and skill listings a transcript cannot see. Same expiry warning as every probe block in this adapter — the header also carries an unused `blobEncryptionKey`, which is the most likely way this stops working, and it stops by returning null. **The same reading feeds the meter's RING, and it has to reach the durable row to do it.** The reading is taken at the turn's two BOUNDARIES (at the session reply, so a resumed chat is scaled before its prompt goes out, and again just ahead of `turn_complete`) and published as `context_progress` — the ephemeral live plane, which the client drops the moment the run settles. That alone left the ring filled for the length of a turn and blank between turns, which is when anybody looks at it: reported as "кружочек не синхронизируется с контекстом", against a chat whose panel read 140.7k of 200k beside an empty circle. `AcpTurnDriver` therefore KEEPS the last reading and `buildUsage` writes it into the turn's own `turn_complete` (`contextTokens`, `contextWindowTokens`, and the model only where there is a window for it to label), which is the durable half every other CLI's ring is drawn from. The wire's own `usage_update.used` still outranks it — a figure the agent SENT beats one read out of its files — while `inputTokens`, which measures one request rather than the window, now ranks below both. Measured end to end on a real cursor turn: `{contextTokens: 42970, contextWindowTokens: 200000}` in the row against `inputTokens: null` beside it, and the composer's ring reading `Context 21% full — 43k of 200k` against the panel's `43k of 200k · 21%`.

**A THIRD reading moment, taken WHILE the turn runs, is what a first turn depends on** (`CONTEXT_REREAD_MS` in `acp-driver.ts`). Both boundaries above are useless to a conversation the agent has never held: `session/new` writes no store at all — a brand-new chat's directory holds `meta.json` and nothing else — so the opening turn ran to completion under an empty ring and filled it only as it ended. REPORTED as a chat that "still hadn't loaded any context, and loaded it only later". The store is not written once per turn, which is what makes the fix available: probed 2026-08-25 on a fresh cursor chat, `latestRootBlobId` moved at 17.2s, 18.7s, 21.2s, 21.7s and 24.2s of the opening turn, and the blob at 18.2s already parsed to a complete `47,221 of 272,000`. So an ordinary `session/update` notification now also takes a reading, floored at two seconds and published only when the figure has MOVED — the read is 0.14ms, but each new figure is a socket emission to every client watching the run, and a turn streams its answer a word at a time. Notifications are the carrier because a turn that is working always has them; during a `session/load` replay `sessionId` is not yet set, so the mid-turn reading cannot fire against the previous turn's figures. Verified in the running app on a new chat with the identical prompt: the composer's ring absent for the whole turn before (5.5s → the 39.9s settle), and `Context 17% full — 47.2k of 272k` at 20.6s after, moving to 47.5k at 24.7s with the turn still going.

**A message CAN be handed to a running cursor turn — and doing it INTERRUPTS** (`TurnDriver.sendFollowUp`, `AcpTurnDriver.latestPromptId`, `AdapterConfig.followUp.interrupts`). REPORTED as "в курсоре не работает мгновенная отправка сообщения из очереди", and the control was inert because this adapter declared it had no channel — a declaration made from the ACP SPEC (`session/prompt` is one request per turn) rather than from the binary, which is the exact failure `.claude/rules/agent-adapters.md` warns about. Probed on 2026.08.11-e8db854: a second `session/prompt` against a live session is ACCEPTED. It does not ADD to the prompt in flight, it REPLACES it — the first answers `{"stopReason":"cancelled"}`, the second runs to `end_turn`, and the agent still holds the conversation (told "STOP counting, reply BANANA" mid-count, it replied `BANANA`). So the channel exists and what differs from claude is WHAT A PRESS COSTS, which is now its own config field rather than a shared sentence: claude's message joins the turn and is picked up at the next tool boundary, cursor's drops the tool call in flight. The renderer says which BEFORE the press, there being nothing to undo after it. **The frame is the DRIVER's, not the adapter's** — it needs the session id and has to be recorded to make sense of the reply — hence a second delivery hook (`CliTurnOptions.sendFollowUp`) beside `buildFollowUpPayload`, taking the same settle guard and preferred over it; a driver that writes for itself also keeps the existing "unregister a frame whose write failed" path, so an unwritten frame cannot leave the turn waiting on a reply that never comes. **Two prompts in flight is what the turn had to learn**: the superseded one's reply must NOT settle the run — that would end the turn in the middle of answering the message the user just pushed through, under a `cancelled` reading as a Stop nobody pressed — so only the reply whose id matches the most recent prompt emits a terminal. Matched by id rather than by counting what is outstanding: nothing orders the two replies, so a count settles the turn on whichever arrives second, which is the cancel whenever the agent is the slower half. Measured end to end through the daemon: `POST /messages` mid-turn now answers 201 instead of 409, the interrupted output survives as its own transcript row, and the run settles once. One wart stands: that row is filed BELOW the message that interrupted it, because a turn's events persist through a serialized chain while the follow-up reserves its seq directly — closing that needs an ordering seam on the turn handle.

**A CLI that DISCLOSES its thinking streams it live, and cursor does** (`AgentEvent.reasoning_delta`, `PartialStreamService.reasoning`, `RunDeltaEvent.thinkingText`). REPORTED as a cursor chat showing `Working… · 3m 8s` with nothing happening. The driver buffers an `agent_thought_chunk` into the block it will close later (`appendPending`) and, until this event existed, returned NOTHING for it — so a pure reasoning stretch put not one signal on the wire and the transcript drew the row it draws for an agent that has produced nothing at all. Captured on a real turn: thought chunks at 16.8–20.0s and again at 32.1–34.4s of a 28.5s turn, none of it visible until the block closed. It is a SECOND channel rather than a widened `thinking_progress`, because the two are alternatives decided by the CLI: headless claude redacts the block and can only ever report a token COUNT, cursor sends the words and reports no count. Both open the same stretch (`isReasoning` asks about either, or a chunk after the token path would open a second one), both are EPHEMERAL — `mapEventToItem` answers null and the durable `reasoning` row is the same words — and words WINNING over thinking is what keeps them from racing for one row. It also joins `RESUMES_A_HELD_TURN` and `restatusAfterOffTurnSignal` on the same terms as its two siblings: it cannot arrive without the model having authored something. Verified end to end through the daemon — 23 `thinkingText` events on one stretch, `thinkingTokens: null` beside them — and in the renderer, which draws the streaming words in the muted italic bubble the durable row becomes, with a spinner and a clock under them.

**A failure this CLI reports about ITSELF settles the turn as one** (`AcpAgentFailureProtocol` in `acp/acp-driver.ts`, read by `cursor-acp/utils/cursor-agent-failure.utils.ts`). `cursor-agent` catches its own transport failure, writes the sentence out as an ordinary `agent_message_chunk` and answers `stopReason: "end_turn"` regardless — so the turn used to be recorded `completed` with that sentence as its output and its `finalText`. REPORTED with a screenshot: `Error: RetriableError: [unavailable] PING timed out` sitting in the transcript as the agent's own prose under a `✓ done · 1m 14s` footer, having earlier been reproduced twice on 2026.08.11-e8db854 (once after 1m 29s, once after 16m 10s of silence). This paragraph previously ended "there is no protocol-level signal to read: telling it from a successful turn would mean matching that vendor's prose, which is why nothing here does" — the first clause is confirmed and the second was a judgement made without reading the CLI. Its shipped `2996.index.js` wraps the whole run in ONE catch whose every arm writes a message chunk, with `handlePrompt` around it returning `end_turn` on every path that is not a cancel, so there is no field to read and no stricter client that fixes it. What IS readable is that the chunks are the CLI's own literals: `` `\n\nError: ${String(e)}` `` where `String(e)` names one of four error CLASSES (`RetriableError`/`NonRetriableError`/`ActionRequiredError`/`CancelledError`, each a `get kind()` getter in `index.js`), one hardcoded `Error: [unauthenticated] …`, and four fixed `ActionRequiredError` sentences. Requiring BOTH anchors — the chunk-opening prefix AND a class name — is what keeps it off an agent WRITING about an error, which is the commonest thing a coding agent does; the four bare English sentences are matched as the WHOLE chunk for the same reason, and that arm's own `e.message` fallback is deliberately not matched at all. The turn then settles on an `error` **instead of** its `turn_complete` (not as well as, or the run settles twice and the success badge goes back), the words the agent produced before it died are still flushed as a row, and the failure never reaches `finalText` — a downstream graph node must not be handed the transport error as this node's answer. The recognition is the ADAPTER's, as one predicate over one chunk, so an agent whose failures reach the protocol declares nothing and is untouched.

`CursorAcpAdapter` drives `cursor-agent acp`, Cursor's first-party Agent Client Protocol server, over JSON-RPC on stdio via the agent-agnostic `adapters/acp/` client (`acp.types.ts` wire shapes, `acp-jsonrpc.ts` framing, `acp-session.ts` the process, `acp-driver.ts` the per-turn state machine). **ONE PROCESS PER CONVERSATION**, like claude's: spawn → `initialize` → `session/new`|`session/load` → then, per turn, optional `session/set_mode` → optional `session/set_config_option`|`session/set_model` → `session/prompt` → stop reason, with the process kept between turns by `AgentSessionRegistry`. What is unchanged is the machinery around it: `ProcessRegistry`, cancel and the executor's fan-out work the same for both CLIs.

**It was one process per TURN for two milestones, and what that cost is the reason it is not any more.** `canHostSession` answered false on an honest ground — ACP has the shape for a kept process, but no signed-in multi-turn ACP session had been OBSERVED here, and a second prompt on a session the agent considers finished would be answered with the previous turn's context, which is a wrong turn rather than a slow one. The measurement that settled it (2026-09-01): turn 1 told the agent to remember `BANANA-7731` and ended `end_turn` at 12676ms; turn 2 on the SAME process answered `BANANA-7731` in 7122ms, with no sign of the feared re-run. What the flip FIXES is not latency. `TURN_END_EXIT_GRACE_MS` arms only for a `turn` stdin lifetime, so a one-turn process was terminated ~2s after its terminal event — killing every sub-agent the turn had left running in the background. REPORTED against a turn that launched eleven reviewers and said "I'll be notified as they complete", every one of which rendered `cancelled`; measured both ways on a delegate given a 20-second shell command, which asked permission at 28.5s and wrote its file at 49.0s with the process kept, and never wrote it at all under a control run that killed the group 2s after the turn. The user's objection is what drove it — "in the Cursor UI this all works fine" — and it was correct: Cursor keeps one process, and the limitation was geniro's own. An instruction block telling the agent not to background work was built as a workaround and REMOVED on their instruction; do not reintroduce it.

**The flip needed the SESSION/TURN SPLIT first, and that split is the substance of the change.** Nearly every field of the old `AcpTurnDriver` was per-TURN and said so in its own doc comments — harmless only while a session was exactly one turn. `imageBlocks` and the turn's own `input` were the sharpest: both fixed at construction, so a second turn would have re-sent the first turn's attachments and its prompt. Rather than reset ~20 fields between turns — which makes "remember to reset" the invariant, and the next field added breaks it in silence — `AcpSession` now holds the handful that genuinely outlive a turn (the transport, the request-id counter and its pending map, the negotiated capabilities, the session id, the granted MCP servers, the current model, the session reply, and whether the host preamble has been said) and builds a FRESH `AcpTurnDriver` per turn from that turn's own input. A field is per-turn by default; surviving a turn is a deliberate move to the other class.

Three consequences are worth knowing. A later turn opens through **`TurnDriver.openTurn`** rather than a stdin payload — `AgentAdapter.buildNextTurnPayload` has nothing to return for a protocol whose next prompt is a frame, and without the hook `startTurn` refuses the turn outright, which is what confined ACP to one turn per process. That hook also owns the turn's SETTINGS: `startTurn` skips its own approval-mode delivery for such a driver, because the mode here is a `session/set_mode` frame and asking for a stdin line would refuse the turn over a change the CLI can in fact be told about. And the mode, the model and the model's parameters are **re-applied per turn** off the stored session reply — `AgentAdapter.sessionKey` covers `model` and `effort` (so either respawns) and nothing else this transport can set, so a context window changed between two messages would otherwise keep the first turn's value for the life of the conversation.

**TWO regressions the flip introduced, both invisible before it, both fixed.** Each is a piece of state that outlives a turn and that one process per turn hid completely. **(1) A parked approval could not be answered by the turn that inherited it.** `spawn-cli` re-holds a request its turn settled without an answer and re-offers it to the NEXT turn, so a verdict routinely arrives while a different turn is current — and with `parkedPermissions`/`parkedQuestions` on the turn, `buildApprovalResponse` found nothing, answered undefined, and the card read as answered while the agent stayed parked for good. Everything keyed by a PROTOCOL id — those two maps plus `toolNames`/`toolKinds`/`toolInputs` and the delegate sets — now lives on the session, which is that id's actual namespace. **(2) The session MODE was never restored.** A mode is session state the client sets and nothing resets, so a chat run under `plan` and then switched back to `auto` sent nothing on its next turn (there being no mode to ask for) and went on running read-only, with the composer chip and the run row both reading `auto`. `AcpSession` now records the mode the agent OPENED in and the one it is in NOW, and a turn that names none asks to be put back to the default.

**STOP is now `session/cancel`, not a kill** (`AcpTurnDriver.buildInterruptPayload`). It is a NOTIFICATION — no id, no reply — and what ends the turn is the pending `session/prompt` answering `cancelled`. The spec requires that, and the BINARY was measured rather than trusted (the adapter rules being explicit that a declared presence is not evidence): probed on 2026.08.11-e8db854, a cancel sent 8s into a counting turn completed the pending prompt in **2ms** with `stopReason: "cancelled"`. `spawn-cli` arms a 5s deadline behind the write and kills the group only if that reply never comes. Killing was acceptable while the process died with its turn and is not now: the group holds the whole conversation and every delegate still out. It is a DRIVER hook rather than an adapter one because the frame names the session id.

The process still has to be made to go away when the SESSION ends, and it does not go quietly: `cursor-agent acp` ignores EOF and lived on (measured: alive at 163MB with a `worker-server` grandchild 3m25s after reporting `end_turn`, and four such groups found reparented to launchd 1.5 days old). `TURN_END_EXIT_GRACE_MS` was the answer while a turn was a process; the registry's own `close()` — idle window, LRU eviction, staleness replacement, shutdown — is the answer now, and it terminates the group. Permission requests are real (`session/request_permission` is an ACP baseline): `auto` auto-approves in the driver to keep unattended semantics, `acceptEdits` auto-approves `edit`-kind tool calls only, `ask`/`plan` park on a user verdict. A caller node's MCP endpoint travels in `session/new`, so the call token rides an HTTP header inside a stdin frame — never argv, never a file on disk. `session/load` resume suppresses the agent's transcript replay so a resumed turn cannot duplicate history. Pasted images ride as `image` content blocks in `session/prompt`, gated on the agent's own `promptCapabilities.image`. **Per-session model selection is real** and was mis-recorded as absent until probed, and it has TWO carriers because ACP replaced one with the other: `configOptions[]` (the entry of category `model`, ACP 1.0 / schema v1.16.0, applied with `session/set_config_option {sessionId, configId, value}` — `configId`, not the `configOptionId` the docs' prose uses, which the agent rejects) and the pre-1.0 `models.currentModelId` + `models.availableModels`, applied with the now-removed `session/set_model`. Removal from the SPEC is not removal from the BINARIES: cursor-agent 2026.08.04-aaa8809 sends both blocks and answers both methods, so `acp-models.ts` reads whichever the reply carries (configOptions wins) and the driver picks the frame from what the agent ITSELF advertised — never from a version number. `listModels` runs a two-frame handshake and the driver applies the model BEFORE the prompt. The ids are the handshake's own namespace: `cursor-agent models` prints a DIFFERENT spelling for the same model that the agent answers `-32602 Invalid model value`, so the subcommand can never be the picker's source. A resumed session is asked unconditionally, and the reason recorded here — "a `session/load` reply is not observed to list models" — was REFUTED once resume could actually succeed: measured on 2026.08.11-e8db854, a load reply carries `modes`, `models.currentModelId` AND a full `configOptions` list with each option's `currentValue`, so a resumed turn reads the same fields as a fresh one (`model=claude-opus-5` then `effort=xhigh` both ACCEPTED on a loaded session). It went mis-recorded because the reply could not be observed at all while the session store was being deleted with each turn's config directory. What stands is the CONCLUSION: silence is not a refusal, so nothing is refused locally on a reply that enumerated nothing. **Background sub-agents are real on this transport too**, and the adapter declared for two milestones that they were not — on a measurement that read geniro's own `acp.types.ts` and concluded something about cursor. Refuted on the wire 2026-08-13 (2026.08.11-e8db854): a delegation arrives as an ordinary `tool_call` whose `rawInput` is `{_toolName:"task"}` (its title is the placeholder `Task: Subagent task`, the description not yet known), and a `cursor/task` REQUEST then carries the description, the full brief, the type, the model and the duration — the method the adapter had listed as "the single most suggestive artifact found" and was declining on every delegating turn. The lifecycle is an agent-agnostic `AcpDelegateProtocol` (method + launch marker + params reader + the two facts below), so a second CLI's delegate channel is a config rather than a branch; the driver emits `subagent_info` twice per delegate — an anchor at launch, so the block opens and the run reads busy while it works, then the facts — and the renderer merges them last-non-null. - Binds **`127.0.0.1` only**. Assembled exactly like Geniro's `apps/api` (`buildBootstrapper(…)` → `addExtension(buildHttpServerExtension(…))` → `init()`); the loopback specifics ride on the extension's `host` / `portFallback` / `onListening` options — bind 127.0.0.1, negotiate a free port if the preferred one is taken, and write the pidfile from `onListening` after a healthy listen (the `http-server`'s own listen still defaults to `0.0.0.0`, preserving Geniro's behavior). Shutdown is Nest-owned (`enableShutdownHooks`); `utils/pidfile.lifecycle.ts` clears the pidfile on the way out, so `main.ts` needs no signal handling.
- Writes the pidfile (`daemon.json`: `pid`, `host`, `port`, per-launch `token`, `version`, `entry` and `startedAt`) **only after** the schema is synced and the server is listening, then prints `GENIRO_DAEMON_READY {port}` to stdout. The UI never assumes the host/port — it reads the bound values back from the pidfile (so it no longer passes `GENIRO_PORT`; the daemon owns that default).
- Config env (set by the UI): `GENIRO_USER_DATA` (userData dir; fallback `~/.geniro`), `GENIRO_PORT` (preferred port; default `47615` per `DAEMON_PREFERRED_PORT` in `utils/handshake.ts`, falling back to a free port if taken) and `GENIRO_IDLE_EXIT_MS` (self-shutdown window; absent = never, which is the default for every launch the supervisor did not spawn). DB is `geniro.db`, pidfile `daemon.json`, instance lock `daemon.lock`, child journal `children.json`, all in the userData dir.

**What a CLI says about itself is cached ACROSS LAUNCHES, and invalidated by three separate mechanisms** (`services/model-vocabulary.store.ts`, `<userData>/model-vocabularies.json`). `utils/model-vocabulary-cache.ts` stops ONE process asking twice, which is not what a user feels: measured against a cold daemon, cursor's model LISTING costs 6.9s and one model's settings another 6.3s, and every app restart plus every ten-minute TTL lapse paid both again — for answers that had not changed in weeks. REPORTED as "это очень долго! Так долго не должно быть. Это должно быть практически мгновенно." Instant is not something geniro can ask the CLI for (those seconds ARE a real `cursor-agent acp` handshake); what it can stop doing is asking again for an answer it already has. Both readers now consult the store first — `ModelsService` under the NULL model key, `CursorAcpAdapter.probeModelConfigOptionsShared` under the model's own — and the store holds opaque JSON with the caller supplying the shape guard, so a value whose shape has since moved costs a re-ask rather than a picker full of rows it cannot render. Measured end to end across a full app restart: models 6.9s → 0.3s, `gpt-5.5`'s settings 6.3s → 0.3s, byte-identical payloads; in the running app, switching the composer to cursor-agent went from ~25s to ~1s. **Staleness is answered by three mechanisms because the three causes differ.** The CLI was UPGRADED → the `--version` lives in the ENTRY and is compared on every read (exact, no clock; and in the entry rather than the key so an upgrade REPLACES a row instead of spending the entry budget on versions nobody can run). The ACCOUNT changed through geniro → `ModelVocabularyStore.forget(agent)` from `CliAuthService`, on a completed account sign-in or sign-out, since a subscription decides which models exist and none of that moves the version; NOT on an MCP-server sign-in, which changes tools rather than models and is already answered by retiring that folder's sessions. Anything else — a plan change, an entitlement flipped server-side, a `cursor-agent login` in the user's own terminal — cannot be observed here, so past an hour an entry is SERVED AND REFRESHED BEHIND THE ANSWER (`StoredAnswer.stale`): the user waits for nothing and the answer is at most one interaction behind, with a seven-day hard expiry as the backstop for a refresh that never succeeds. And beside the three, a MANUAL one: `POST /v1/agents/caches/clear` behind the menu bar's Clear Agent Cache, for the case none of them reaches — the user has looked at the screen, believes it is wrong, and would rather pay the handshakes than argue with a cache. The refresh is joined through each caller's existing single-flight (`ModelsService.inFlight`, `handshakeProbeCache`), so it cannot race a cold ask or spawn a second process group. An answer that could not actually be obtained is never filed — an empty model list, a probe reply that enumerated nothing — because storing the stand-in is what would turn one transient failure into a week of "this CLI has no models".

**A folder's MCP change retires that folder's KEPT agent sessions** (`AgentSessionRegistry.markStale`, called from `AgentMcpService.setEnabled` and from `CliAuthService.settle` on a completed SERVER sign-in). A CLI reads its MCP configuration once, when it starts, so a server switched on or signed in to reaches the config and not a process a chat is already holding. It MARKS rather than closes — the flag is read at the start of the next turn — because a change can land while a turn is in flight (closing there kills work the user asked for) and because a folder may hold a dozen idle chats whose respawn would re-launch the user's own MCP servers for turns nobody sent. Matched on (agent, cwd): one folder is routinely used by both CLIs and they read different files, and a change is about one directory. **Which CLI this actually bites is worth stating, because the report that prompted it was about the other one.** It was written when only `claude` kept a process across a run's turns (`canHostSession` → `keepStdinOpen`, probe-verified on 2.1.223) and `CursorAcpAdapter.canHostSession` returned false. BOTH keep one now, so this staleness marking is what cursor needs too — and the measurement below was taken under the old behaviour, where every cursor turn was a fresh process that re-read the config by construction. Measured on 2026.08.11-e8db854 against this daemon: a cursor chat created BEFORE a server was added to the folder's `.cursor/mcp.json` answered `YES` to "is a tool named zzprobemarker available to you right now?" on its very next turn. The WS channel is a NestJS Socket.IO gateway (`@WebSocketGateway({ path: '/ws' })`) installed via the `IoAdapter` in `main.ts`; the renderer (`socket.io-client`) sends the per-launch token in the Socket.IO handshake `auth` payload (browsers can't set headers on a WS handshake). The HTTP `LoopbackTokenGuard` doesn't see Socket.IO traffic (engine.io intercepts `/ws` before Nest routing), so each gateway owns its own WS auth — via the one shared `auth/ws-auth.ts` → `enforceWsHandshakeAuth` (constant-time `safeEqual`, disconnects on mismatch), called from `handleConnection` in the notifications gateway.
