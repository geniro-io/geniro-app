# apps/daemon

Guidance for Claude Code when working in `apps/daemon` — the NestJS loopback daemon. Loaded automatically when this directory is touched; see the root `CLAUDE.md` for project-wide overview, commands, conventions and constraints.

---

A standalone NestJS engine the UI spawns as a child process, laid out like Geniro's `apps/api/src`: `main.ts` (bootstrapper + extensions → `init()`) and `app.module.ts` at the root, then feature/infra dirs:
- `auth/` — `runtime.ts` (per-launch `RuntimeInfo` + DI token, incl. the bound `port`) + global `runtime.module.ts` (also hosts `CallTokenRegistry`, so the guard and the graph executor share it without a module cycle); `mint-token.ts` (the one source of loopback credentials — the launch token AND the per-caller-node MCP call tokens); `token.guard.ts` + `safe-equal.ts` (loopback bearer-token gate); `ws-auth.ts` (`enforceWsHandshakeAuth` — the ONE Socket.IO handshake gate, shared by every gateway, since engine.io bypasses Nest guards); `call-token.registry.ts` (per-`(runId, nodeId)` MCP call tokens).
- `environments/` — `environment.{prod,dev,test}.ts` + `index.ts` (picks by `NODE_ENV`, loads `.env` via dotenv), laid out like the sibling api's: prod is the base, dev spreads prod, **test spreads DEV**, and each is one object literal closed with `as const satisfies Record<string, string | number | boolean | null>` — the shape is INFERRED, so there is no hand-written interface to keep in step and a new field is typed at every read site without a second edit. An env file holds environments and nothing else: `readDaemonVersion` lives in `utils/daemon-version.ts`, and the strict parsers in `utils/handshake.ts` beside the rest of the UI→daemon contract. Three fields deliberately bypass `getEnv` and say so at their own line — it boolean-coerces `'0'`/`'1'`/`'on'`/`'off'`, which is wrong for `GENIRO_USER_DATA` (a path), `GENIRO_PORT` (must be a bindable 1..65535) and `GENIRO_IDLE_EXIT_MS` (malformed ⇒ feature OFF, never a guessed number). `host` is a CONSTANT rather than an env knob — the one deliberate departure from the sibling's env-everything shape, because "binds 127.0.0.1 only" is a hard v1 constraint and an env var is how it would come to be broken.
- `utils/` — `handshake.ts` (pidfile `DaemonInfo` shape + loopback bind defaults + `isValidPort`/`parsePort`); `pidfile.ts` (write/remove — `mintToken` moved to `auth/mint-token.ts`); `pidfile.lifecycle.ts` (Nest `OnApplicationShutdown` → removes the pidfile); `atomic-file.ts` (stage-then-rename writes: `atomicWrite`, its `Sync` sibling for callers that cannot yield, and `atomicCreate`, the exclusive form the instance lock claims with); `process-identity.ts` — the ONE answer to "is pid N still the process I recorded", `ps`-reported start time within a 2s tolerance, shared by the two things that act on a pid they do not hold a handle to (a bare `kill(pid, 0)` cannot tell a recycled pid from the original, and both readers below would then SIGKILL or refuse to boot on a stranger); `instance-lock.ts` + `instance-lock.lifecycle.ts` — **one daemon per userData dir**. The port fallback stays (a FOREIGN process on 47615 must not block a start), but a second GENIRO daemon is refused: it would share the SQLite file and overwrite the pidfile, which is exactly what a stray `pnpm daemon:dev` did for 19 hours beside the app's own daemon. The lock records the holder's process start time, so a SIGKILLed daemon's leftover lock is self-healing with no staleness window to tune — the next launch cannot confirm a dead holder and takes over at once. Released on Nest's shutdown hook, NOT `process.on('exit')`: Nest re-raises the signal after its hooks and default signal termination never runs `exit` listeners (observed — the pidfile was cleared while the lock file was not); `idle-shutdown.lifecycle.ts` — the daemon exits ITSELF after `GENIRO_IDLE_EXIT_MS` with no connected WS client **and** no in-flight turn. Two conditions, not one: no client is what makes it unused, no turn is what makes it safe to stop, and a workflow keeps running after its window closes. It exists for the launches the UI supervisor can never clean up after — it only terminates the daemon it OWNS, and a force-quit or crash leaves one it does not. SIGTERM at itself rather than a direct exit, so the `ProcessRegistry` drain and pidfile cleanup still run. **Disabled unless the environment names a window**, which only `DaemonSupervisor.spawnDaemon` does (10 min): `pnpm daemon:dev` and the throwaway `pnpm generate:api` daemon have no client by design and must not read that as being unwanted; `crash-guards.ts` — the process-level `unhandledRejection`/`uncaughtException` handlers, installed before Nest so a stray rejection logs instead of crashing past the `ProcessRegistry` drain. An uncaught exception SIGTERMs the daemon at ITSELF so the shutdown hooks still run, and that is the one thing here with a trap in it: **Nest runs those hooks inside its own SIGTERM listener**, so a hook that throws comes straight back as another uncaught exception. It is latched (`shuttingDown`) for exactly that reason — unlatched it re-sent SIGTERM and re-ran the hooks on every re-entry, each arming its own 6.5s failsafe timer, so the live timers piled up until the process aborted on memory. That abort is the macOS **"Electron quit unexpectedly"** dialog a user reported seeing periodically. Every handler body is also wrapped so it cannot throw out of itself — the debug sink writes to a file, and a stream the shutdown already closed is the same loop reached through the logger.

      **A claude session's FIRST prompt is held until the CLI's MCP servers have finished dialling.** The CLI dials its servers when the PROCESS starts and does NOT wait for them before running a turn, so a prompt written too early can find some servers still `pending` and lose their tools for the rest of the conversation — nothing is permanently missing (the surface GROWS mid-turn), so the damage is entirely in what the model concludes once and never re-checks. That is also why it is intermittent. The oracle is `mcp_status`, an undocumented client-initiated control request on the same stdin dialogue as `can_use_tool`, found by enumerating the shipped binary's subtypes and then driven live: it answers BEFORE any prompt has been written, with one row per server under `mcpServers` (not `servers` — reading the obvious name returns an empty list from every healthy reply, which is indistinguishable from "discovery has not started"). The gate polls it and releases on two IDENTICAL readings with nothing `pending`, never one: discovery is gradual, so a single quiet moment is also what a half-discovered list looks like. Only `pending` blocks — waiting for `needs-auth` to become `connected` would hold every first message for the full deadline on any machine with one signed-out server. Three exits bound it: an empty reading is believed for a 2s grace (a machine with no servers), a `refused` reply releases at once (a renamed subtype costs the fix and never the turn), and a 15s deadline releases with a `notice` NAMING the servers still starting, because a turn that silently runs on the old surface is the bug report again. The seam is agent-agnostic — `TurnDriver.awaitPromptReady` awaited by `CliTurnOptions.holdPrompt` in `spawn-cli.ts`, FIRST turn only (the wait belongs to the process, and by turn two the servers have been up for a whole turn) — and cursor defines neither, so its opening write stays synchronous. Two claude turns are outside it as well: one carrying `isolateMcpServers` loads no server by construction, and one naming no approval mode is a geniro-internal probe that never reaches a tool. A cancel during the hold DROPS the prompt rather than writing it into a turn the user already stopped, and a gate that throws is logged and the prompt sent anyway — losing the user's message would be worse than the defect being fixed.

    **A turn does not end on its CLI's turn-end line while background work it started is still out** (`spawn-cli.ts`, `TurnState.openWork`/`deferredTerminal`, fed by the agent-agnostic `background_work` event). The turn-end line is the end of what the agent was SAYING, never of what its process is DOING: probed on claude 2.1.231, a turn told to launch a delegate and not wait for it printed its `result` while the delegate was still running, and the CLI then ran a whole FURTHER turn of its own accord as the delegate reported — that continuation's own result line says so, `origin:{kind:"task-notification"}`. Settling on the first `result` therefore ends geniro's turn mid-work and hands everything after it to nobody — whole assistant messages dropped for want of a turn to put them in, and permission requests answered with no card ever shown — while the run reported `completed` and its delegates rendered `stopped`. So a `turn_complete` is HELD while `openWork` is non-empty and released when the last unit reports; the bound is the turn's existing silence deadline, which releases the held result rather than overwriting a finished turn with "produced nothing…". Only a `turn_complete`, and only on a `session` stdin lifetime: a cancel is the user asking to stop now, an `error` is a turn that failed rather than finished, and a turn whose process ends with it has no "after" to wait for. Claude reports the lifecycle on `system/task_started` + `task_updated`/`task_notification` (both terminal channels mapped — they spell one outcome `killed` and `stopped`); a CLI that reports none simply never emits the event and its turns settle exactly as before, so this is not a capability an adapter must declare.

    **What the CLI does AFTER its turn settles belongs to the run, not to nobody** (`ChatService.handleBetweenTurnEvent`). A turn's `result` line ends the turn geniro started; it does not stop the CLI, which routinely opens a further turn of its own accord when a delegate reports back — that continuation's own result names itself `origin:{kind:"task-notification"}`. `spawn-cli` has no turn to hand that output to, so it arrives on `onBetweenTurnEvent`, which used to keep only the two halves of a tool call on the argument that those carry an id pairing them while a stray message has no anchor — dropping every other event type the CLI produced off-turn. What the user sees is what was reported — a run badged `completed` with more work appearing under it, and the agent's own messages after that point simply not arriving. The rule is now the in-turn rule: whatever `mapEventToItem` yields a row for is persisted in arrival order, the live signals feed the same partial stream, the self-reports feed the same harvest stores, and the continuation's own terminal event settles the run again. A settled run producing rows goes back to `running` with `offTurnActivity` naming it as the CLI carrying on by itself rather than as a fresh turn. Two runs are exempt: one the user CANCELLED (Stop is final — a straggling result flipping `cancelled` back to `completed` says their Stop did not take, though the rows are still written, because a transcript that hides work is lying the other way), and one whose `running` this path did not write, which `offTurnRuns` is what distinguishes — the handler is async, so a real turn can have opened in between, and settling THAT turn's run on the previous one's tail is the defect `cancelledTurnMayStillEmit` exists to stop.

    **That silence deadline does not run at all while the turn is blocked on a verdict** (`TurnState.outstanding` non-empty), and that is the absence of a window rather than a longer one. The deadline's premise is that silence is UNEXPLAINED — it exists to catch a CLI nobody can account for. A turn parked on an approval card is the opposite: geniro raised the request, knows the CLI is blocked on it, and is itself the thing withholding the answer, so the clock would be timing a HUMAN, and a human who steps away for lunch has not wedged. Before this exemption, an `AskUserQuestion` card left unanswered while nothing could arrive would eventually settle the turn as `error`, mark the run failed, and rewrite the card the user was coming back to answer as `unanswerable` — a sentence false in every clause, since the CLI had produced both an answer and a question and had given up on nothing. `respondApproval` rearms on DELIVERY, and from that moment rather than from when the card went up, so answering late does not leave the turn moments from being abandoned; a second still-open card keeps it suspended. Two consequences are deliberate: Stop is then the only bound on a parked turn (which is correct — it is waiting for its user, who is the only one who can end the wait), and a parked turn keeps `ProcessRegistry.activeCount` non-zero, so `IdleShutdownLifecycle` will not fire while a question is on screen.

    **A KILL is not a cancellation, and only `cancelRequested` can tell them apart** (`settleFromTermination`'s signal branch). A child that exits on a signal used to settle `turn_cancelled` unconditionally, which is right for the terminations geniro ASKS for — Stop and the shutdown reap both reach `cancel()`, a retired session reaches `close()`, and both set the flag — and wrong for every other way a process dies: an OOM kill, a crash, a `pkill`, a supervisor taking the group down. The damage is not the word but what the word suppresses. `cancelled` is deliberately the ONE ending the app never notifies about (announcing a Stop tells the user what they just did), so a killed agent settled quietly under a badge saying the user had stopped it — a run that failed, told nobody, and blamed them for it. Only a requested cancel (`cancelRequested`) settles `cancelled`; any other signal now settles `failed` and posts `The turn failed.`. The signal is NAMED in the error message (`… was terminated by SIGKILL`), with the stderr tail beside it, since "the process ended" is not a diagnosis.
    **The agent's OWN task list is a transcript row, not a tool call** (`task_list` items; `AgentEvent`'s `task_list`, `adapters/claude/utils/claude-tasks.utils.ts`, `adapters/cursor-acp/utils/cursor-todos.utils.ts`, the agent-agnostic `AcpTodoProtocol` seam in `acp-driver.ts`). Every shipped CLI keeps a checklist while it works a multi-step job, and geniro showed neither the list nor its progress: a multi-step job on claude produced only anonymous `Used 1 tool` rows, and on cursor-agent a `Update TODOs` row that discloses NO arguments (`rawInput:{_toolName:"updateTodos"}`) — so the list existed nowhere in the app. **`mode` is the load-bearing field**: two of the three shapes on the wire are PATCHES naming only the rows that moved (claude's `TaskUpdate` sends `{taskId,status}` and no text at all; cursor sent three `merge:true` frames carrying two of its three rows), so a consumer reading any announcement as the list shows one task where there are seven. It is never inferred from the contents — a patch that happens to name every row is indistinguishable from a snapshot — the CLI says which it sent, and cursor says so literally. Absent, it reads as a patch: the direction that leaves a stale row rather than deleting every task it did not name. **Claude's half is read off BOTH directions of a tool call**, which the CLI forces rather than geniro choosing it: a created task's id exists only in the result (`Task #1 created successfully: …`), an update's status only in the input, and `TaskList`'s result is the one place the whole list is stated — so the result parsers match the CLI's own anchored sentences, a `tool_result` block carrying `tool_use_id` and no tool name. There is no pull channel to ask instead: the 2.1.232 control subtypes were enumerated the way `mcp_status` was found, and the two task-shaped ones answer other questions (`background_tasks` takes a `tool_use_id`, `get_plan` returns the plan-mode file); the push channel that DOES carry the full list (`system/background_tasks_changed`) goes to the CLI's remote-control bridge and never appeared on stdout across a five-task probe. **Cursor's half was a vendor extension being declined in the quietest possible way** — `cursor/update_todos` is on `CURSOR_SILENTLY_DECLINED_METHODS`, so it was refused in-protocol with the transcript notice deliberately withheld; the third such method found to be REAL after `cursor/ask_question` and `cursor/task`, and the seam is agent-agnostic so a fourth CLI's channel is a config rather than a branch. Baseline ACP's `plan`/`plan_update` updates are NOT what either agent sends. The event carries the producing `toolCallId` so the renderer shows the list INSTEAD of that opaque row, and it is a DURABLE row rather than a live signal because the list is only ever the fold of its announcements — a reopened chat has to replay them all. A delegate's list is its own: the announcement carries whatever origin its line carried, so nothing about tasks knows about sub-agents. That path is measured but unproven on the wire — told explicitly to keep one, a claude delegate searched its own toolset three times and found no task tools, so the CLI does not hand them to a delegate.

Whether a CLI's question channel COSTS the ask posture is its own adapter fact (`questionsCostAskPosture`) — true for claude, false for cursor, since an ACP request arrives whatever session mode the agent is in, so an unattended cursor node stays on `auto` instead of parking every permission on a verdict nobody is there to give.

- `v1/handoff/` — **handing a conversation to the user**, which replaced the live PTY mirror and its whole plane (`TerminalSessionsService`, the `/terminals` Socket.IO namespace, `TurnMirrorService`, xterm.js in the renderer, and the `node-pty` dependency — one of the two native modules is gone). The mirror was a SECOND process rendering the same transcript, and it could not follow a running turn: an open `claude --resume` TUI does not grow while another process writes the session, and **two interactive CLIs on one session do not see each other either** (A was told a codeword by B and answered "NOTHING-HERE"). Keeping it in step therefore meant re-spawning the CLI on a cadence — a cold render per re-read, and a full repaint, because the new render is not an extension of the old (the conversation grows ABOVE the fixed input block). What the mirror was reached for was never "watch a copy" but "let me carry this on myself", and that needs no syncing at all: the CLI is started when the button is pressed and renders the conversation as it stands then. Layout: `handoff.module.ts` + `handoff.types.ts` at the root, then `services/`, `controllers/`, `dto/`, `utils/`.

**Taking over a conversation the user already had** (`AgentAdapter.listSessions` / `prepareSessionImport` / `readSessionHistory`, composed by `CliSessionsService`, offered by the sidebar's own control beside `+`). The ask was to continue an existing terminal session inside the app rather than start blank, and the two CLIs answer it through completely different mechanisms — which is the whole reason it is three adapter methods and not one.

**claude is READ off disk.** Every conversation it has ever held is `<configDir>/projects/<flattened cwd>/<sessionId>.jsonl`, one append-only file per session **in exactly the envelope its `-p --output-format stream-json` writes to stdout** — so the import needs no protocol at all, and an imported row is built by `mapClaudeMessage`, the same mapper a live turn's rows come from, rather than by a second reader that could disagree with it about what a message is. Nothing has to be moved for the resume: `--resume <id>` finds it in the profile the run already carries. Scale is what shapes the reader — a real profile can hold thousands of sessions across gigabytes, with individual sessions many megabytes each — so the listing stats every candidate and opens each only as far as its first user message rather than reading any of them whole. Two things in it are corrections rather than choices: the folder filter compares **canonicalized** paths, because the CLI records `cwd` as its process saw it (`/private/var/…`) while this app canonicalizes every folder it holds (`/var/…`) and a string compare therefore rejected every session in the folder the user was sitting in; and a turn that is nothing but slash-command envelopes is re-rendered as `/name args` rather than shown as markup or dropped, since dropping it leaves a session whose every turn is a command with no name at all.

**cursor is ASKED over ACP, and its sessions must be brought across.** `session/list` is a real protocol method this agent advertises and answers with `{sessionId, cwd, title, updatedAt}` — including a title the AGENT generated, which no disk scan could produce. Probed 2026-08-16 on 2026.08.11-e8db854: it is **profile-scoped, not a global index** (a fresh empty config dir answers with zero rows), so the listing is taken under a throwaway profile linked at the USER's `acp-sessions` while geniro's turns run against its own store — which is why importing one is a **copy** (not found before it, loads and replays its whole transcript after). The transcript comes back the same way: `session/load` streams the entire prior conversation as `session/update` notifications before it replies, so `readSessionHistory` spawns that handshake and reads the replay. Reading it at CREATION rather than on the thread's first turn is what keeps the order right — a turn's replay arrives after the user's new message is already persisted, which would file the imported history BELOW the message that continued it.

What this CLI cannot offer is stated rather than left as a short list: `sessions.listingPartialReason` says that only ACP sessions are listed, because the chats started by the interactive `cursor-agent` live in `~/.cursor/chats/` — a separate namespace the same server answers `Session … not found` for (probed, with the id under its own recorded cwd). A user whose terminal history is all in that store would otherwise read a correct four-row list as a broken feature.

Two rules the daemon side follows. The import is **prepared before the run row exists**, so a refusal leaves no half-made thread and the user gets the CLI's own sentence instead of a chat whose first message dies on a session nobody can find. And the happy path writes **no system row at all**: the transcript is its own evidence that the import worked, so only what the transcript cannot show by itself earns a line — history left out, or a record that could not be read (`severity: 'info'`, never the failure chrome every other daemon notice wears).

**The cursor transport (ACP)** — every cursor turn runs under its **own throwaway `CURSOR_CONFIG_DIR`**, seeded with a copy of the user's `cli-config.json` and nothing else (`adapters/cursor-acp/utils/cursor-profile.utils.ts`, materialized by `prepareTurn` and swept at boot). Not hygiene — a correctness fix: applying a model or an effort over ACP PERSISTS into that directory, so before this a chat's model choice silently changed what the user's own `cursor-agent` opens with (measured: one `session/set_config_option` rewrote `model`, `selectedModel` and `modelSelectionHistory` in the real `~/.cursor/cli-config.json`). The copy keeps their permissions, approval mode and default model; `mcp.json` is deliberately NOT copied or symlinked — it is 0600 and holds their own server credentials, and it is unnecessary, which had to be measured rather than hoped: under a directory holding only `cli-config.json` an ACP session still loaded the folder's MCP servers and `mcp list` still reported all of them, because the CLI resolves that file from the user's home either way. Cost was measured too: a handshake under a fresh directory is no slower than one under the default profile, so the CLI cache it writes per turn buys no latency penalty. The model listing takes its own profile for the same reason (a parameterized handshake can migrate a persisted variant selection, which writes). **The one thing that must NOT be per turn is the CONVERSATION**, and missing that shipped a build where every cursor chat's second message died: the CLI keeps each ACP thread at `<configDir>/acp-sessions/<sessionId>/` — inside the directory the disposer removes — so `session/load` answered `-32602 Invalid params {"message":"Session … not found"}` and the turn failed before its prompt (probed both ways on 2026.08.11-e8db854: the same load under the profile that created the session succeeds). So that ONE name is a symlink to `<userData>/cursor-sessions`, shared by every turn, while the settings the isolation exists for stay per turn — measured through as well: the CLI writes the store THROUGH the link, a second throwaway profile resumes the session and answers a codeword only turn 1 was told, and `node:fs` `rm -r` unlinks the symlink rather than descending into it. The store is deliberately NOT nested inside `cursor-profiles`, which the boot sweep removes wholesale. A `session/load` the agent REFUSES is now a degrade rather than a dead end — a `notice` naming the loss and a fresh `session/new`, because every later turn resumes the same id, so a hard failure made the chat unusable for good (`'session_load'` is a pending kind of its own in `acp-driver.ts` for exactly this).

**That session store is also where this CLI's context accounting lives** (`utils/cursor-context-store.utils.ts`), and reading it is the whole reason a cursor chat can show a breakdown at all. Over ACP the agent says NOTHING about its window — re-measured 2026-08-15 against a raw frame capture of a real tool-using turn, five `sessionUpdate` variants and a bare `{"stopReason":"end_turn"}`, with all three "context"-shaped keys being `embeddedContext` — so the adapter recorded "no usage" and the panel said so, which is what got reported ("Курсор должен как-то нам давать какие-то значения"). The figures were never absent, only off-protocol: the CLI writes a full breakdown per turn into `<sessionId>/store.db`, which is what its own TUI renders, and geniro already owns that directory because the per-turn profile symlinks into it. So this needs no new access, only a parser: `meta` holds one hex-JSON header carrying `latestRootBlobId`, `blobs` is content-addressed, and the root blob is protobuf — `{1: used, 2: window, 3: repeated {1: key, 2: label, 3: tokens, 4: chars}}`. Three things keep it honest. It is opened READ-ONLY through node's OWN `node:sqlite` (this file has nothing to do with geniro's ORM, and the built-in costs neither a dependency nor a rebuild against Electron's ABI) — geniro owns the directory but not the format, and nothing may write to another program's store. The block is found BY SHAPE rather than by field number, walking the message tree for rows of (string, string, varint), so a vendor adding a field still parses. And the arithmetic is re-checked rather than trusted: the categories must sum EXACTLY to the stated total, which is what the probe found to hold and what rejects a different block whose rows merely look alike — a genuinely changed encoding then yields null and no breakdown, never a number read out of unrelated bytes. An ESTIMATE was the obvious alternative and was measured to be unusable: 346 characters of transcript against claude's 23,575 `Messages` tokens on a comparable thread, ~250× wrong, because the window is dominated by tool and skill listings a transcript cannot see. Same expiry warning as every probe block in this adapter — the header also carries an unused `blobEncryptionKey`, which is the most likely way this stops working, and it stops by returning null.

`CursorAcpAdapter` drives `cursor-agent acp`, Cursor's first-party Agent Client Protocol server, over JSON-RPC on stdio via the agent-agnostic `adapters/acp/` client (`acp.types.ts` wire shapes, `acp-jsonrpc.ts` framing, `acp-driver.ts` the per-turn state machine). One turn is one process — spawn → `initialize` → `session/new`|`session/load` → optional `session/set_mode` → optional `session/set_config_option`|`session/set_model` → `session/prompt` → stop reason → exit — and `CursorAcpAdapter.canHostSession` DECLARES that, with the reason beside it: ACP has the shape for a kept process (`session/prompt` can be sent again on a loaded session), but no signed-in multi-turn ACP session has been observed here, and a second prompt on a session the agent considers finished is answered with the previous turn's context — a wrong turn, not merely a slower one. Claude, by contrast, now keeps its process BETWEEN turns (`AgentSessionRegistry`), so the two CLIs genuinely differ here. What is unchanged either way is the machinery around the process: `ProcessRegistry`, cancel and the executor's fan-out work the same for both. The "→ exit" at the end of that line had to be MADE true: a one-turn turn settles when its process ENDS, and closing stdin only asks — `cursor-agent acp` ignores EOF and lived on (measured: alive at 163MB with a `worker-server` grandchild 3m25s after reporting `end_turn`, and four such groups found reparented to launchd 1.5 days old). Two symptoms, one cause: the run's `ProcessRegistry` slot was never released, so every later message in that chat answered `RUN_BUSY` and sat in the composer's queue with the spinner still running, and each turn leaked a process group. So the terminal event now arms a short exit deadline (`TURN_END_EXIT_GRACE_MS` in `utils/spawn-cli.ts`) after which the group is terminated — a CLI that does exit on EOF is gone long before it fires, and the turn still settles on the process actually ending, so `done` still implies drained stdout. Permission requests are real (`session/request_permission` is an ACP baseline): `auto` auto-approves in the driver to keep unattended semantics, `acceptEdits` auto-approves `edit`-kind tool calls only, `ask`/`plan` park on a user verdict. A caller node's MCP endpoint travels in `session/new`, so the call token rides an HTTP header inside a stdin frame — never argv, never a file on disk. `session/load` resume suppresses the agent's transcript replay so a resumed turn cannot duplicate history. Pasted images ride as `image` content blocks in `session/prompt`, gated on the agent's own `promptCapabilities.image`. **Per-session model selection is real** and was mis-recorded as absent until probed, and it has TWO carriers because ACP replaced one with the other: `configOptions[]` (the entry of category `model`, ACP 1.0 / schema v1.16.0, applied with `session/set_config_option {sessionId, configId, value}` — `configId`, not the `configOptionId` the docs' prose uses, which the agent rejects) and the pre-1.0 `models.currentModelId` + `models.availableModels`, applied with the now-removed `session/set_model`. The legacy one-shot `-p --output-format stream-json` adapter, its `.cursor/mcp.json` merge machinery, and the MCP-trust probe were deleted with this transport.

- Binds **`127.0.0.1` only**. Assembled exactly like Geniro's `apps/api` (`buildBootstrapper(…)` → `addExtension(buildHttpServerExtension(…))` → `init()`); the loopback specifics ride on the extension's `host` / `portFallback` / `onListening` options — bind 127.0.0.1, negotiate a free port if the preferred one is taken, and write the pidfile from `onListening` after a healthy listen (the `http-server`'s own listen still defaults to `0.0.0.0`, preserving Geniro's behavior). The public allowlist is **`/health` alone** (`PUBLIC_PREFIXES` in `auth/token.guard.ts`), matched at segment boundaries so a sibling route like `/health-debug` doesn't inherit it. `/metrics` and `/swagger-api` are **token-gated**: with a deterministic default port, any web page could otherwise read the daemon's Prometheus internals and full API schema cross-origin. Every non-allowlisted route requires the `Bearer <token>` header — the launch token, or, **only** on `/v1/mcp/<runId>/<nodeId>`, that caller node's own per-node call token (minted when the run starts, revoked when it settles, keyed by `(runId, nodeId)` so one callee child can't open another node's route). The WS channel is a NestJS Socket.IO gateway (`@WebSocketGateway({ path: '/ws' })`) installed via the `IoAdapter` in `main.ts`; the renderer (`socket.io-client`) sends the per-launch token in the Socket.IO handshake `auth` payload (browsers can't set headers on a WS handshake). The HTTP `LoopbackTokenGuard` doesn't see Socket.IO traffic (engine.io intercepts `/ws` before Nest routing), so each gateway owns its own WS auth — via the one shared `auth/ws-auth.ts` → `enforceWsHandshakeAuth` (constant-time `safeEqual`, disconnects on mismatch), called from `handleConnection` in the notifications gateway. It stays extracted precisely so a second gateway cannot reintroduce a divergent copy of the check.
