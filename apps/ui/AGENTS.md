### Main process

`src/main/`:

- `index.ts` — app lifecycle. `daemon-supervisor.ts` — spawn/adopt/health-poll/orphan-sweep. `daemon-pidfile.ts` — reads + validates the daemon's pidfile.
- `settings.ts` — `settings.json` (see *Settings keys* below). `purge-legacy-secret.ts` — deletes the one Keychain entry earlier versions wrote (see *Storage split* in the root `AGENTS.md`).
- `agents/` — one DESCRIPTOR per CLI (`claude.ts`, `cursor-agent.ts`, `codex.ts`), collected in `agent-descriptors.ts` as a total `Record<CliKind, …>` so a CLI added without one is a compile error (`CLI_KINDS` in `shared/contracts.ts` is built the same way, from a `satisfies Record<CliKind, true>` object, since settings validation keys on it). A descriptor holds the CLI's env names, how to ask whether it is signed in, how (or why not) to ask for a newer version, its updater argv, and its vendor's `installer` (the script URL its docs lead with, the shell it is piped into, any switch that keeps it from waiting on a prompt). Nothing in `cli-detect.ts`, `cli-update.ts`, `cli-install.ts`, `probe-env.ts` or `settings.ts` names a CLI; the daemon's twin of each fact is that CLI's `AdapterConfig`.
- `cli-install.ts` — the agent cards' **Install** button (Onboarding and Settings): runs `curl -fsSL <installer url> | <shell>` and calls it installed only once the binary detection now resolves answers `--version`. A second press joins the running install; a pinned binary path that does not run, shadowing the fresh install, is NAMED rather than reported as a failed install. The renderer half, `use-cli-install.ts`, re-detects afterwards and, when the fresh CLI is signed out and no sign-in is running, goes straight to its in-place sign-in on both screens — which is why Onboarding reads the daemon handle itself (main starts the daemon at launch whatever the onboarding state).
- `cli-detect.ts` — per-CLI binary + version + signed-in state. `loggedIn` is three-state and `null` means UNKNOWN, never signed-out: a failed probe must not tell a signed-in user to sign in. Read the CLI's STRUCTURED reply where it has one (`cursor-agent status --format json` → `isAuthenticated`; its human output has a third `partially-authenticated` state that matches neither wording), otherwise exit code AND wording together (codex's `login status` answers on STDERR: `Logged in using …` exits 0, `Not logged in` exits 1).
- `probe-env.ts` — the main-side twin of the daemon's `child-env.ts`: a probe child gets its OWN agent's credentials and never another's (`detectClis` runs an authenticated `status` call). `neutralEnv()` applies the same rule to a child that is not an agent (`gh`), which keeps none.
- `git-info.ts` — the composer's branch chip (repo/branch/branches/dirty). Every call runs under the same `SAFE_CONFIG` as `git-changes.ts`, because the folder's `.git/config` is untrusted input: `core.fsmonitor` names a program git runs on any command that reads the index (pinned against a real hook, with a control case proving git runs one). A branch switch is GUARDED by a re-read dirty check and uses `git switch`, never `git checkout` (which resolves a branch name as a pathspec and restores a file). `pullBranch` is stash → `git pull --ff-only` → stash pop: `--ff-only` because a fast-forward is the only pull that cannot leave a merge commit or half-finished rebase for the user to resolve, and a divergence is not a composer button's decision. The stash goes back on EVERY path INCLUDING a failed pull, and a failed stash push aborts the pull rather than running it unprotected. `pullStashIsOurs` decides the tip is this pull's entry from the stash ref having MOVED *and* the tip's subject ending with `geniro: pull` — neither alone (git's prose is locale-dependent, a push on a not-really-dirty tree exits 0 having created nothing, and a concurrent `git stash` moves the ref). `BranchSwitchResult.dirty` tells the renderer the refusal is the guard working (amber tone, Pull offer). `BranchSwitchResult.worktree` OUTRANKS it: git will not check one branch out into two worktrees, so a Pull offer could not work. It is decided from `git worktree list --porcelain` (also read into `GitInfo.worktrees`, which marks those rows in the picker), never from git's translated `fatal: '<branch>' is already used by worktree at …`. The renderer answers it with an offer to point the run at the worktree that holds the branch — except on the saved-configuration path, which names its own folder, where the sentence states the path and stops.
- `worktree-service.ts` — the worktree and branch a task's agent works in: `git worktree add` under `<userData>/worktrees/<taskId>` on a `geniro/task-<id>` branch derived from the task's ID, never its title (user text, which would have to answer for every character git refuses and for two cards sharing a title). It lives in main because every git call this app makes belongs to main: same `SAFE_CONFIG` + argv-array `execFile` as `git-info.ts`, plus `--` ahead of the path (an argv array stops a shell reading a leading dash, not git). `<userData>/worktrees.json` is its registry and the ONLY thing that authorizes the recursive delete, so the SINK is bounded rather than the file trusted: a row naming a path outside the worktrees directory is dropped and nothing is removed, compared segment-wise so a sibling whose name merely begins with the root's is not admitted (the daemon's twin predicate is `v1/agents/utils/path-within.ts`, restated because main imports no daemon source). `reapFinishedWorktrees`, called from `index.ts` each time a daemon comes up, removes only worktrees whose card's work the DAEMON calls finished (`readFinishedTasks` → `POST /v1/tasks/finished`; an unanswered question collects nothing) and CONFIRMS each row against `git worktree list --porcelain` first, leaving an unconfirmable one where it is (mirroring `stranded-child-reaper.service.ts`). Never remove every clean registered worktree at launch: a worktree outlives its run, and that would take the cwd out from under every reviewed conversation. `prepareWorktree` CONTINUES in the task's standing worktree on a second press — its branch, uncommitted work and all, reported as `reused` — and a caller whose start is then refused leaves a reused one alone. Anything ELSE in the slot is cleared when empty and otherwise REFUSED with the path named unless git says it holds nothing; an existing task branch is reused, and removing a worktree keeps its branch. `settleWorktreeForTask` is the one path allowed to clear a DIRTY tree, and only because it commits first (`git add -A` onto the task's own branch, so the repository's `.gitignore` decides) and removes the directory afterwards; a commit that could not be made (hooks refused, no git identity) KEEPS the worktree. Hooks are run, never skipped — `--no-verify` is refused project-wide. Reached over three IPC channels and no others: `geniro:prepareTaskWorktree`, which SHAPES its failure into `TaskWorktreeResult` rather than throwing (an exception crossing IPC arrives as a string, and the board must tell a made worktree from a failed one before starting a run against it); `geniro:pruneTaskWorktree`, keyed by TASK and looked up in the registry, so a caller can only reach a path this app recorded creating; and `geniro:settleTaskWorktree`, its committing counterpart, fired by the board off the DAEMON's `work-finished` reason (card Done and no run working in it) — never off a card's column, which is written optimistically on drag, nor off its run settling, which takes a live conversation's cwd away.
- `github-prs.ts` — the live state of the **pull requests** a thread OPENED: `readPullRequestsByRef`, one `gh pr list --repo <owner/name> --state all` per repository plus `gh pr view <url>` for anything older than that page, run from the user's home because the refs name their repository. Its own file because `git-info.ts` reads local refs on a 5s budget and this is a network client on 15s. It FAILS CLOSED: every failure (no `gh`, a logged-out `gh`, not a GitHub checkout, the query erroring) is ONE outcome, the empty list, and every surface draws nothing. There is deliberately no "did it work" flag on the wire; the reason is written at the guard (a half-answer reads as confident and wrong).
- `resolve-binary.ts` — the PATH ∪ well-known-dirs lookup `cli-detect.ts` and `github-prs.ts` share: a packaged app launched from Finder runs under launchd's `/usr/bin:/bin:/usr/sbin:/sbin`, where `git` resolves and a Homebrew `gh` does not, so a bare-name spawn works in `pnpm dev` and is a silent ENOENT in every shipped build.
- `ipc.ts`; `ipc-schemas.ts` — the zod shapes every IPC argument is validated against before main acts on it (the renderer is the untrusted side of that boundary).
- `context-menu.ts` — the right-click menu. Electron provides none: a packaged app has no context menu unless it builds one.
- `navigation-policy.ts` — keeps the top frame on the renderer document; `URL.origin` cannot decide it in a packaged build, where every `file:` URL has the opaque origin `null`.
- `native-appearance.ts` — tells macOS which appearance the app is painting, from the stored theme — the ONE write that themes both the OS chrome and, through `prefers-color-scheme`, the page (see *Design system*).
- `open-terminal.ts` — the handoff OUT of geniro: a 0700 `.command` script and `open`, so LaunchServices routes it to the user's own terminal.
- `terminal-sessions.ts` — the shells behind the in-app terminal panel: one node-pty PTY per tab running the user's login shell (`-l`, the shell read from the user RECORD since a Finder launch may have no `SHELL`) in the requested folder; see *Terminal panel* below.
- `reveal-path.ts` — shows the daemon's log in Finder. It REVEALS rather than opens, so a path it is talked into taking cannot become a program that runs.
- `daemon-ready-notify.ts` — pushes the freshly started daemon's handle to the renderer, tolerating a window destroyed between the daemon becoming healthy and the send.
- `window-diagnostics.ts` — what MAIN saw happen to a window, written into the daemon's log; the `ui` channel carries only what the renderer catches, so a window that never ran the renderer could report nothing.
- `app-menu.ts` — the macOS menu bar: Electron's own default restated through role menus, with **Toggle Developer Tools** hidden (hidden rather than deleted, so ⌥⌘I stays bound; `Menu.getApplicationMenu()` over `electron --inspect` is the only way to read the running menu). Geniro's own rows: **Clear Agent Cache**, always, beside the two Reloads (Reload drops what the window holds; this drops what the daemon holds about the CLIs). It carries no accelerator, and does its work in the RENDERER over `IPC.onClearAgentCaches` to the FOCUSED window, which holds the daemon client. It clears and then RELOADS: `useAgentVocabulary` caches per hook INSTANCE, so there is no one cache to empty, and the reload is its own confirmation (it costs the composer's unsent text). Do not reintroduce a confirmation strip or a `vocabulary-epoch` cache key. ORDER is load-bearing: reload only AFTER the daemon answered (reloading first refills from a daemon that has not cleared), never on a failure (which would hide it), which goes to the daemon's log instead. **Component Catalog**, in development only: gated on `isDev` — `Boolean(process.env.ELECTRON_RENDERER_URL)`, passed IN to `installApplicationMenu` so the template stays a pure function of its arguments and both arms are spec-testable — and OMITTED rather than disabled when false. It PROBES before it opens and, when nothing listens, shows a dialog naming `pnpm storybook`; this app neither starts nor supervises that dev server, and spawning it was rejected (a long-lived child to own for a convenience). The port is a TWIN with `apps/ui/package.json`'s `storybook` script, and `app-menu.spec.ts` reads that script to check they agree.
- `updater.ts`, `update-installer.ts`, `update-service.ts` — **app self-update**: `updater.ts` reads the GitHub Releases feed, `update-installer.ts` downloads/verifies/stages the bundle and puts it in place at quit, `update-service.ts` owns the one state and the schedule; see *App updates* below.
- `login-shell-path.ts` — packaged Finder launches inherit launchd's minimal PATH; resolves the login-shell PATH for the daemon.
- `notifications/` — **system notifications**: `notifier.ts`, the ONE file that touches a notification API, and `notifications.service.ts` over it.

**The AUTOPILOT is two files in main, and neither has an IPC channel of its own.** `autopilot-conductor.ts` is a recurring tick modelled on `update-service.ts` — created in `start()` after a `stop()`, `unref`'d so it never keeps this process alive, its period injected so a spec drives it without a clock. Each tick reads `GET /v1/projects/:id/queue` for every armed project and starts exactly what that route handed out, forcing `approval: 'auto'` and naming itself `startedBy: 'autopilot'`. The daemon's `AUTOPILOT_APPROVAL` (`v1/tasks/utils/run-target.ts`) is the copy that ENFORCES that, and states why `acceptEdits` cannot serve: it still routes every Bash call to the approval seam, so an unattended run parks on its first command. It lives in MAIN because a renderer timer dies with the window and is throttled in the background, the daemon runs no git and every task needs a worktree, and main already runs a surviving interval. It DECIDES nothing about capacity — the cap and the breaker are enforced daemon-side at the route that makes the run (a conductor counting for itself is defeated by two open windows). A refusal is the ORDINARY case (another window got there first, the card moved), so the worktree is given back. One tick at a time, every failure logged and stepped over, so one bad project cannot end the sweep. Arming is an ordinary project PATCH through the generated client — no channel. `daemon-keepalive.ts` is the other half: ONE authenticated Socket.IO client held open while any project is armed, because `IdleShutdownLifecycle` exits the daemon after its window with no connected client AND no turn in flight — the gap being the app running with every window closed, a project armed, and a task just finished. It holds a CLIENT rather than changing the daemon's idle rule. It must authenticate: `enforceWsHandshakeAuth` disconnects an unauthenticated client and a disconnected one is not counted. It cannot keep a daemon alive past the APP — `before-quit` disposes it — and a relaunched daemon has a different token, so the socket MOVES rather than reconnecting.

**The MERGE WATCHER is the autopilot's counterpart: the conductor starts a card's work, this ends it** (`pull-request-merge-watcher.ts`). A card reaches `in_review` when its agent stops, and only a merge or a drag takes it out. Every five minutes, and on window focus behind the same five-minute floor (`sweepIfStale`, the trade `useThreadPullRequests` makes on its own focus listener), it reads `GET /v1/tasks/awaiting-merge`, asks GitHub about those pull requests through `readPullRequestsByRef` (the same batched-per-repository resolve the chat surfaces use) and reports each merge to `POST /v1/tasks/:taskId/pull-request-merged`. It lives in main for the conductor's reasons plus one: `gh` runs in this process and the daemon holds no login. It DECIDES nothing — it reports a fact (which pull request merged, and GitHub's `mergedAt`) and the daemon moves the card, so a card the user dragged elsewhere stays where they put it. A previous ROUND's merge never ends a card: the listing carries each card's `lastDoneAt`, and only a merge strictly after it counts (`endsCard`, the twin of the daemon's `mergedSince`), taking the FIRST pull request merged since. The listing is read as untrusted JSON (`readAwaitingMerge`, TWIN PARSER of `TaskAwaitingMergeSchema`), and a card whose boundary it cannot read is dropped rather than read as never Done. A sweep that finds no card in review spawns no `gh`. The board redraws off the ordinary `task_changed` broadcast — no IPC channel, no renderer change.

**The LAN GATEWAY is this process's second listener, and the whole of the app's network surface** (`main/remote/`). It serves the app's OWN renderer bundle to a phone on the same Wi-Fi, so the same live sessions are reachable from a second device — the carve-out is written in full in the root `AGENTS.md` → *Constraints*, and what matters here is why the code sits in MAIN rather than in the daemon. Two things a phone needs exist only on this side: the renderer bundle (`out/renderer`, an artifact of this app) and `window.geniro`, which IS main-process IPC and has no daemon side at all. Putting it here is also what keeps the daemon's own "binds 127.0.0.1 only" rule literally true rather than merely mostly true. **The phone's page is NOT a secure context** — the gateway serves plain http on the LAN — so every secure-context-only browser API is missing there and throws or reads `undefined`: ids come from `renderer/random-id.ts` (never `crypto.randomUUID`), copies go through `renderer/clipboard.ts` (never `navigator.clipboard`), and eslint bans both direct uses in the renderer. Every test environment and the Electron shell are secure contexts or stub the API, so a new secure-context-only API can pass every check and fail only on the phone.

- `gateway.ts` — the listener, styled on `terminal-sessions.ts` (options-as-test-seams, explicit `start`/`stop`, no module-level singleton). Binds `0.0.0.0` on `REMOTE_PREFERRED_PORT` (47616, one above the daemon's) with a free-port fallback, and **IPv4 only**: the Host guard refuses globally-routable IPv6, and not binding `::` means such a request cannot arrive to be refused. Routing order is its own routes → `/v1/*` and `/health` proxied → `/ws` upgraded → everything else from the bundle, behind ONE path-traversal guard. In development `out/renderer` does not exist and it proxies vite instead.
- `host-guard.ts` — the Host-header gate, applied to ordinary requests AND to upgrades. It answers "is this a Host WE would ever hand out", never "is this address reachable", and it has two jobs rather than one: stopping DNS rebinding, and keeping the gateway a LAN feature at all. The second is why it refuses global unicast IPv6 — a Mac routinely holds a SLAAC address. A `*.suffix` entry is the ONE shape that admits a name outside the LAN, and it exists for `tunnel.ts` below: it is checked before the port (a tunnel's port is its own 443, not this listener's), matched at a LABEL boundary so `evilngrok-free.app` cannot pass for `*.ngrok-free.app`, and refused outright for a bare `*` or a one-label suffix — a whole TLD is a zone a stranger can register inside and rebind through, while a provider's own zone is not.
- `tunnel.ts` — the child process that gives the gateway an INTERNET address, opened by a press in Settings and never on geniro's own initiative (the carve-out is in the root `AGENTS.md` → *Constraints*). Providers are a TABLE in preference order and nothing about one is branched on elsewhere (the adapter rule one directory over). cloudflared leads: its quick tunnel needs no account or config, while ngrok needs an authtoken on disk, shows a browser interstitial and puts the user's public IP in the hostname. The mask handed to the guard is DERIVED from the URL the client actually printed, never stored per provider (a paid ngrok account is served from a different zone). The client's output is re-read on every line because ngrok reassigns its subdomain mid-session, and it is spawned with `PATH`/`HOME` alone.
- `pairing.ts` — the 6-digit code, constant-time compared. Bounded per address AND globally; the global ceiling exists because picking a new source address is free on a LAN, so a per-address lockout bounds nothing, and tripping it ROTATES the code so the guessed space stops existing.
- `device-registry.ts` — `<userData>/remote-devices.json`, atomic 0600 writes, entry-by-entry salvage on `settings.ts`'s `salvageList` rule. It stores a token HASH: the file sits beside `daemon.json` and a readable token would be a standing key.
- `daemon-proxy.ts` — the forwarding. It injects `Authorization` itself and STRIPS whatever the browser sent, so the daemon's token never reaches the phone; on a `/ws` upgrade it rewrites the `token` query param, which is why `enforceWsHandshakeAuth` also reads that carrier (a proxy can rewrite an upgrade URL, not a frame). **The upgrade is matched as `/ws` OR `/ws/…`**: engine.io requests the trailing-slash form and the daemon answers only that form, so an exact `'/ws'` match breaks live streaming while every unit test passes — the symptom shows only from a real client (a phone that lists chats and starts runs but never watches one).
- `remote-routes.ts` — session / pair / bridge / events. A bridge call answers through the SAME `ipc-registry.ts` table the IPC channel uses, so the two cannot drift about what a channel does; a channel whose policy is `deny` answers a typed refusal rather than running. The `IpcMainInvokeEvent` a handler expects does not exist here, so it is handed a Proxy that THROWS on any read — safe only because `allow` is reserved for handlers that ignore the event, and a spec drives a handler that reads `event.sender` to prove the throw is what happens.

**Two limits worth knowing before building on it.** The `on*` push channels are subscriptions, not request/response, so in a browser they are no-ops: the SSE route carries keep-alives and nothing else yet. This does NOT touch chat streaming, which rides the daemon's `/ws` through the proxy — what a remote client misses is main-process events (a daemon restart, update state, a notification click). And `filePath` answers `null`, the honest browser answer: a page is never given a `File`'s real filesystem path.

**Revoking a device ENDS what it has open, and a phone tab outlives the build it loaded.** Pairing is checked at the `/ws` handshake, so an upgraded socket would otherwise outlive a revoke and switching remote access off (`closeAllConnections()` leaves upgraded sockets alone while `server.close()` waits for them). The gateway records every proxied upgrade against the device its handshake resolved: `stop()` destroys them all and `disconnectDevice` (called by `revokeDevice`) destroys that device's. The `/v1/*` and `/health` proxy applies the same Origin check the upgrade does, and an Origin on its scheme's default port is compared WITH that port (`new URL(origin).host` omits it). A phone keeps its tab open across the Mac's updates, so its next screen change asks for a lazy chunk of the OLD build ("Failed to fetch dynamically imported module" / "Importing a module script failed."). Two halves answer it. **The gateway 404s a missing FILE and never stores the page**: only a NAVIGATION — no extension, not under `/assets/` — falls back to `index.html` (`serveStatic` must never answer a missing chunk with HTML at 200, which WebKit refuses as a module and a tunnel's edge would cache under a `.js` URL); the page is served `no-store`, content-hashed `/assets/*` are `immutable`, and anything else is `no-cache`. **The renderer reloads once, from whichever place sees the failure first** (`renderer/stale-bundle.ts`): vite's `vite:preloadError` event, the root `ErrorBoundary`, and the boot's own `import('./App')` in `boot-app.tsx`. All three share one `reloadForNewBundle`, whose `sessionStorage` stamp records WHICH page asked: the same page asking again reads as "reloading" (the boundary shows "Loading the updated app…"), while the NEXT page failing the same way within 30s shows the error instead of looping. `isStaleBundleError` also matches vite's `Unable to preload CSS for …`, since vite preloads a lazy view's stylesheet before its module.

**A task's worktree, and the chat that outlives it.** A task runs in `<userData>/worktrees/<taskId>`, so the header must not name it by its last component: `GitInfo.worktreeOf` (the first block of `git worktree list --porcelain`, when it is not this folder's own root) lets `chats/use-worktree-origin.ts` name the REPOSITORY on the header chip of a task's run, with the worktree and the repository both in its panel. A task's chat outlives its worktree (the board collects it once the card is Done and nothing is working in it), so a turn refused `INVALID_CWD` in a task's chat puts the worktree back from the branch that holds the work and sends ONCE more (`chats/task-worktree.ts`, reached from `startTurn` and from Retry, the two paths every send takes); that turn settling under the still-Done card makes the daemon announce the work finished again, and the board collects it again. The task panel's Folder row elides its path from the FRONT (`shortenPath`, so the part naming the directory survives), shows the whole path on hover (`HoverPopover`'s `onPress`, which lets a trigger be a control of its own), and opens the picker INSIDE the folder it holds (`pickProjectFolder(defaultPath)` — without a default macOS reopens wherever the last dialog was).

**The New task dialog STAGES what only a card id could carry.** A pasted picture is written under its card's directory and a file is bound by the card's id, and a draft has neither. `useStagedDescriptionPaste` writes a `![name](staged-image:<n>)` reference at the caret at once and keeps the bytes, the Files row holds a list of paths, and `useBoard.createTask` creates the card WITHOUT the staged references (so an upload that never happens leaves no dead link), writes each picture the text still references, repoints those references in one description update, then binds the files. After the create a failure costs one picture or one file, never the card. The dialog's reset on open clears the phone's staged uploads too — it is hidden rather than unmounted, so otherwise a file picked for one task is uploaded again onto the next.

**A card's edits are OPTIMISTIC** (`useBoard.updateTask`) — never build the panel's fields from the saved card alone (two presses inside one round trip would send two whole arrays, the second dropping the first). An edit shows at once; edits still in flight are re-applied over any reload or other write's answer; an answer older than a newer edit's is ignored; a refused edit is undone field by field, only where the field still holds what that edit wrote. The Due row is a local draft saved on blur, Enter or unmount, and only when the date changed.

`src/shared/contracts.ts` holds the Electron-internal contracts only — IPC/Settings/CLI + `DaemonHandle` — shared across main/preload/renderer; it deliberately holds **no daemon wire types** (those are generated, see *The daemon API client* in the root `AGENTS.md`). `src/preload/index.ts` exposes a typed `window.geniro` via `contextBridge`.

### Renderer shell

`src/renderer/` — React app: `App.tsx`, `onboarding/`, then the feature directories below (`chats/`, `workflows/`, `tasks/`, `stats/`, `settings/`), plus `autogenerated/`, `daemon-api.ts` and `daemon-client.ts` (see *Settings* below for those).

**`stats/` is what the app has SPENT and what the THREADS did.** Totals, a per-day series and per-agent/model/project breakdowns over the daemon's usage ledger, drawn with **recharts** (a direct dependency) under `stats/charts/`, whose `chart-theme.tsx` is the one place series colours and axis styling are read off the design tokens; plus threads created, pull requests opened, lines added and removed, and average working time per thread. Its per-day switch (`stats/daily-metrics.ts`, the one table naming each choice's fields, unit and shape) plots those beside the spend. The line figures are measured here, not by the daemon, per REPOSITORY and branch rather than per thread: `stats/use-line-snapshots.ts` reads the folder's repository root and branch (`getGitHead` — `main/git-info.ts` `readGitHead`, which runs no `git status`), asks the daemon for that repository and branch's BASELINE commit (`resolveLineBaseline` — the start commit of the first of its threads to be measured), and posts the total `main/git-changes.ts` `readChangesTotals` (IPC `getChangesTotals`) measures against it. Keyed by the ROOT, not the folder, because the totals cover the whole repository; so every thread in one checkout posts one series (a shared edit counts once), and the settle window is per folder — the newest thread is asked for the baseline, and one that cannot set it (no start commit, or deleted meanwhile) hands the question to the next. Both reads are `denyRemotely`. It measures after each finished turn (a turn's `usage_recorded`, never a snapshot's announcement) and after a run SETTLES (`run_status`), since a stopped or failed turn writes no usage row and may still have changed files; each read is stamped with the moment it started. `readChangesTotals` sums `git diff --numstat` against the baseline (no cap — numstat reads no bodies) plus the untracked files read off disk: at most 2,000, each under 4MB, opened `O_NOFOLLOW`, read only up to the size checked, within a 5s budget; anything past those is left out and the total is marked `partial`, a floor. A baseline git SAYS the folder no longer has, or no longer descends from, answers `baseUnreachable`: the hook reports it stale once (the daemon replaces it with this thread's start commit) and measures again. A git check that merely failed answers null — never replace a baseline over a timeout, which would restart the series. A pull does not move the basis, so commits a pull brings in count toward it. It is mounted from `Chats`, not the shell (a thread's folder is on the run rows that screen holds), and is silent on a remote device so a phone never measures the Mac's folders. Before the daemon stops — a quit, and a restart from Settings — main asks each window to post what it still holds (`main/line-measurement-flush.ts` → `flushWindowsThen`, bounded at 30s for a quit and 10s for a restart): the shell answers (`renderer/stats/line-flush.ts`), and the hook registers the measurements it has started, so the stop waits on reads actually in flight and nothing else.

**On a phone the app is PAGES under a bottom tab bar, not columns in drawers** (below `sm`, i.e. the LAN gateway in a phone browser; the Electron window's `minWidth` is 960). `components/bottom-tab-bar.tsx` draws the rail's own `NAV_ITEMS` as icons and replaces the rail there. Chats is three pages, decided inside `Chats` because the screen stays mounted for its live room: the chat LIST (no thread, `mobileComposeOpen` false), the new-chat COMPOSER (the list's `+`), and an open THREAD. **The tab bar is on every phone page**, including under a thread. A CHAT page — a thread or the composer — also carries a ‹ back button at the title band's leading edge; the Settings section page has none. The other way back to a tab's first page is that tab pressed again: Chats from a thread or the composer (`phoneHomeSignal`, bumped by `App`), Settings from a section. `Chats` reports a detail page through `onPhoneDetailChange`, which only sets the title. Leaving a thread CLOSES it (`deactivateRun`). Settings is two pages, the section list and a section, with the open flag owned by `App` beside `settingsSection` so a jump from Chats lands in the section. The PLATFORM's back (iOS Safari's edge swipe, Android's back button) does the same: each detail page holds one browser history entry while open (`components/use-phone-back-entry.ts`), and popping it runs the page's back; the ‹ button and the tab re-press both pop it through `history.back()` rather than closing directly, so every way back runs one `onBack` once. The entries are MARKED in `history.state` (a token on the entry under the page, the page's own entry naming it and its owner), which is why the shell's hash sync passes `history.state` through `replaceState` rather than `null`: a pop counts as back only when it lands on the token, so a link pasted into the tab is not read as one. The push waits a microtask, because a page that opens in the same commit as a view switch (the composer's "Manage fast actions" jump) would otherwise push before the shell's hash write. A page closed another way (a tab switch, a deleted thread, a rotation past `sm`) leaves its entry behind rather than popping it (popping would race that hash write and navigate off the tab just chosen); reopened on that entry, the same kind of page ADOPTS it instead of pushing another, so dead back presses never pile up. The only drawer is the run-details panel (`MobileDrawer`, opened by its band button). There are no app swipe gestures.

**The periods, and what a ONE-DAY range costs.** `Today` leads them (`use-stats.ts` `STATS_PERIODS`). `days: 1` is a calendar day, not a rolling 24 hours: the lower bound stays a local midnight. A line and an area are drawn BETWEEN points, so a single point renders as bare axes that read as "no data" — hence `loneDot`, a marker offered only at exactly one point and never as a general option (at 30 points markers bead over the curve). `dayRangeTitle` reads LOCAL days for both ends, because every bucket on the page is a local one (`usage-fold.ts` `localDateKey`); never read the UTC day out of the ISO bounds (`iso.slice(0, 10)`), which is off by a day east and west of Greenwich. The suite's pinned `America/Los_Angeles` can only tell the west-of-Greenwich case apart, which is what its test asserts.

**One line under a control, not a paragraph about it.** A Settings note says **what flipping this does and the one consequence you could not guess** — the cost (extra tools in every prompt), the restart, the security caveat (an open inspector port runs code for any local process). Leave out rationale, mechanism nobody acts on, enumerations the label already implies, and anything a neighbouring element (a badge, a label) already says.

**A full-screen view scrolls its PANE; the centred reading column is what the pane scrolls** — two elements, never one. The outer pane is the `overflow-y-auto` container and spans the view, so the scrollbar sits at the window edge; the inner `mx-auto max-w-2xl` column caps the width. One `<div>` doing both draws the scrollbar floating inside the pane. `Stats` is the house pattern; `Settings` and `Onboarding` follow it. The outer pane also carries `scrollbar-gutter: stable`, so with macOS "always show scrollbars" the centred column does not shift when content grows past one screen. On `Onboarding` the inner column keeps `min-h-full`, because its footer is `mt-auto` and would otherwise ride up under the last card. The window itself never scrolls (`html, body, #root { overflow: clip }`). **jsdom computes no layout**, so specs in this app pin the DOM fact that DECIDES a layout — which element scrolls and caps the width, document order, the class carrying it — never a measured position; the paragraphs below name only their specific pin.

**The Stats page reads top-down as headline → figures → charts → breakdowns** — the measured figures sit directly under the headline whose token count they split. The spec pins that order off DOCUMENT POSITION, which is what grid order is made of.

**Every figure sits in a RULED SURFACE, and there are never four boxes where one will do** (`stats/stat-card.tsx` — `StatGrid` + `StatCell`). Each grid is one surface, and its rules are the container's own `bg-border` background showing through a `gap-px` — NEVER `divide-x`: Tailwind's divide utilities border every child but the first IN DOCUMENT ORDER, so on a wrapping grid the second row's first cell wears a rule opening onto nothing, while a one-pixel gap is correct on every row and clips to the enclosure's radius. The summary is a four-cell grid (Spent · Cost per turn · Turns · Agent time) with TYPE carrying the emphasis (`StatCell`'s `size`), never a spanning hero cell (it has to be re-spanned at every breakpoint and lands as a half-width orphan at the one nobody checked). Figures in the summary are not repeated in the detail grid, whose cell count must divide by both 3 and 2 so no breakpoint leaves a ragged tail; it is one subject — where the tokens went. The breakdowns are COLUMNS of one surface, not a grid of cards, which would stretch every card to the tallest.

**Colour on the Stats page names the QUANTITY, and a ranked list is not a category.** Charts: money is `--chart-1` and tokens are `--chart-3`/`--chart-4` (`charts/chart-theme.tsx` `SERIES`) — one quantity, one colour, everywhere on the page. The daily chart's hue follows its metric switch, and its gradient `id` is keyed by metric or the fill keeps the previous one's stops. Breakdown bars are one hue stepped by RANK (`breakdown-card.tsx` `RANK_OPACITY`), never a categorical ramp (each column would restart it, so one colour would mean unrelated things); a ranked row carries its own label, so colour encodes only its order. The ramp FLOORS high, because it compounds with the 2% width floor: the faintest rank is usually the narrowest, and a row that spent money must stay visible.

**Number formatting** (`chats/agent-activity.ts`, shared with the transcript, and `stats-format.ts`). `formatTokens` has a billion step; `formatUsd` and `formatCount` group digits. `formatUsd` is pinned to `en-US`, unlike the day labels beside it, because the `$` is hardcoded and the daemon records USD alone — a machine-locale number would pair a dollar sign with `21.547,80`. `formatPercent` never rounds UP to a whole the rate did not reach (99.999% must not print as `100%`, a claim that no prompt token was ever a cache miss).

**The window draws its own title bar** — ONE band across the whole window (`components/title-bar.tsx`), ABOVE the columns, so no column border crosses it (do not go back to one header row per column). `titleBarStyle: 'hiddenInset'` + `trafficLightPosition` in `main/index.ts` remove the system's strip while KEEPING the window buttons; `frame: false` would take the buttons with it. **What is in it is decided by what each thing is ABOUT.** The band carries the window's own business: a title centred over the window (the open thread's name, reported up by `Chats` via `onTitleChange`), and on the right the daemon status + version and the update control (`components/update-control.tsx`). The debug-log trigger does not belong in it: ⌥⌘L (`App.tsx`) is the only way in, and Settings' Diagnostics section names the chord. The rail keeps what is about the rail — the app mark and the width toggle, on its own top row — and has no footer: it is navigation and nothing else. Only the collapsed STATE is the shell's (`components/use-sidebar-collapsed.ts`) — the button and the column it resizes are two components, and two `useState`s over one setting would be two answers to one question.

Three obligations come with the space. **Room**: the buttons' footprint is MEASURED, not assumed — `TRAFFIC_LIGHT_INSET` / `TRAFFIC_LIGHT_WIDTH` / `TRAFFIC_LIGHT_GAP` / `TITLEBAR_CONTENT_INSET` in `src/shared/contracts.ts`, the one module main and the renderer share, because main POSITIONS the buttons and the renderer RESERVES room for them and a copy on each side drifts in silence. The gap is explicit because clearing the buttons by arithmetic alone sits too tight. Re-measure before editing those numbers: open a `hiddenInset` window at a known position, `screencapture -R` its bounds and find the coloured discs (button size and spacing changed in macOS 26). `trafficLightPosition`'s `y` and the bar's `h-11` are one piece of arithmetic ((44 − 13.5) / 2 ≈ 15) and move together. **Alignment**: the title is centred on the WINDOW, and nothing between the bar's edges may displace that centre — a flex `gap` on the row shifts every child after it, so spacing belongs to the children and a spec pins the absence. Do not reintroduce a divider between the leading columns and the content pane (it puts back the break the single band removed), nor centring over the content pane via a `leadingWidth` prop (the title drifts whenever a column opens on the other side, e.g. the agents panel). **A drag handle**: with the system strip gone, a window with no `-webkit-app-region: drag` CANNOT BE MOVED, so `.app-drag` / `.app-no-drag` in `styles/global.css` mark it — and the title bar is the shell's ONLY drag region (column headers must not drag the window). **A control inside a drag region is INERT** (the compositor takes the press), so anything interactive in the bar carries `.app-no-drag`. `components/window-drag-strip.tsx` covers the two screens that render before the shell exists — Onboarding and the loading state.

**And the appearance has to be DECLARED** (`main/native-appearance.ts`, called first inside `whenReady`). Keeping the buttons means the OS draws them for the machine's appearance, and macOS tints an INACTIVE traffic light for it (near-white under Dark) — so an app whose painted theme disagrees with the declared appearance loses its buttons against its own ground (in either direction: light theme on a Dark Mac, dark theme on a Light one). The band's own colour is NOT the lever: recolouring leaves every other unpainted native surface (context menus, scrollbars, system dialogs) on the wrong appearance. The module sets `nativeTheme.themeSource` from `Settings.theme` (`'system'` or a theme id); that one write is the whole application of a theme (see *Design system*). Because the window's own `backgroundColor` is a construction option Electron reads once, the module also owns `watchSystemAppearance` (a `nativeTheme.on('updated')` listener that repaints it) and `paintWindows`. `applyTheme` is its only exported way to APPLY a theme — never export the bare OS write (`applyNativeAppearance` is gone for this reason): a caller taking it without the repaint leaves a dark window with a cream ground showing through every resize. `resolvedTheme` is the read-only sibling `createWindow` uses for the window's `backgroundColor` (`shared/themes.ts`, `ThemeDescriptor.windowBackground`), painted before any stylesheet exists.

### Terminal panel

`renderer/terminal/` — a panel docked across the bottom of the window (above the debug drawer, spanning every view), one tab per shell. The agents panel's folder-terminal button opens a TAB here in the chat's `cwd`, and ⌃` toggles the panel (first toggle starts a shell in the open chat's folder, else home). The `continue in your terminal` handoff (`openInTerminal`) is a different feature and still opens the external app.

- **Main owns the shells** (`main/terminal-sessions.ts`): node-pty is native and the renderer is sandboxed. Every session belongs to the WebContents that created it — only that one can write/resize/kill it or receive its output — and a window's shells are hung up on its `destroyed`, `render-process-gone` and main-frame navigation (a reload has no tabs left to show them), plus all of them at `before-quit`. No child journal is needed: the shell leads its own PTY session, so the kernel hangs it up when this process dies, SIGKILL included. The env drops only `GENIRO_`/`ELECTRON_`/`npm_` keys — it is the USER's shell, not an agent, so their own credentials stay.
- **The renderer mints the session id per MOUNT** of `terminal-view.tsx`, not per tab: it subscribes to `onTerminalData` before the shell prints, and a StrictMode double effect starts a second shell instead of colliding with the first one's hang-up. Output reaches views through ONE pair of IPC listeners dispatched by id (`terminal-events.ts`), not a pair per tab. It is FLOW-CONTROLLED: a view acknowledges each batch once xterm has DRAWN it (`terminalAck`), and main pauses reading a PTY whose unacknowledged output passes `FLOW_HIGH_WATER`, resuming at `FLOW_LOW_WATER` — so `yes` blocks the shell instead of queueing IPC without bound. A HIDDEN window acknowledges on receipt instead (and acks everything undrawn as it hides): Chromium throttles the timers xterm draws on, and draw-acks there would slow a build running behind another app to a crawl.
- **Lifecycle edges that look interchangeable are not.** A reload is caught on `did-navigate`, never `did-start-navigation`, which also fires for a navigation `will-navigate` then blocks (a link clicked in a markdown preview) and would hang up every shell under a page that went nowhere. The channels answer the window's top frame only. A shell killed by a signal reports exit code 0, so `signal` is what tells a kill from an exit. node-pty is imported on the first shell, so a native addon that fails to load costs the panel rather than the app's launch.
- **A tab can be NAMED and COLOURED**: its leading control (the terminal glyph, or the colour dot once one is set) opens a menu of the app's one palette (`components/ui/palette.ts`, the sidebar groups' colours), No colour and Rename; double-clicking the name is the quick path to the same field (Enter or blur saves, Escape cancels, a blank name gives the folder's name back). Both live on the tab in the reducer and nowhere else — a tab does not outlive the app, so neither does its label.
- **Hidden, never unmounted**: closing the panel only hides it (unmounting would end every shell and its scrollback); closing a TAB ends that shell. A shell that exits after the user typed or pasted into it closes its tab WHATEVER its code — a bare `exit` or ⌃D returns the last command's status, so a code of 1 is routine; a shell killed by a signal, one that never started, or one that exited before any input (a broken login rc) keeps its tab with the reason printed. "Input" is xterm's `onKey` plus paste, never `onData`, which also carries the terminal's replies to a prompt's startup queries. ⌃` and "+" use the open chat's folder only while the Chats view is on screen.
- xterm is lazy-loaded with the view and themed off the tokens (`terminal-theme.ts` reads the host's computed ground/ink and the `--ansi-*` palette), re-read when `<html data-theme>` changes.
- **Packaging**: node-pty is an app `dependency` (externalized by electron-vite) with an N-API prebuild — never add it to `rebuild:native`. `electron-builder.yml` unpacks `spawn-helper` from the asar (it is exec'd), and `build-mac.mjs` restores its exec bit in the app staging, since the signed bundle cannot be chmod'ed at runtime.

### Design system

The renderer is styled with **Tailwind CSS v4 (CSS-first `@theme`)** over a **token layer kept in lockstep with the sibling Geniro web app** — same warm cream/caramel palette, same shadcn/ui semantic-token vocabulary — so the desktop app and Geniro web look identical. Its structure is **authoritative**: every new screen builds from it rather than reinventing styles.

**A THEME is one CSS file plus one row.** `styles/themes/<id>.css` holds that theme's complete set of token VALUES, and `shared/themes.ts` holds every theme's IDENTITY — id, label, the light-or-dark ground it paints on, and the window background main needs before a stylesheet exists. Both are needed because no one language can hold both halves: a colour may not live outside CSS, while `BrowserWindow.backgroundColor` and `nativeTheme.themeSource` can only be set from TypeScript. Adding a theme is exactly those two edits; `styles/themes/theme-tokens.spec.ts` fails the build if a theme file omits a token another declares (it would silently fall through to light), and `shared/themes.spec.ts` fails it if a row and a file disagree.

**The choice is applied by MAIN, and there is no IPC channel for it.** `Settings.theme` (`'system'` | a theme id, default `'system'`) is read by `main/native-appearance.ts`, which sets `nativeTheme.themeSource`. That one write themes the OS chrome the app does not paint (traffic lights, context menus, scrollbars, system dialogs) AND drives the renderer's `prefers-color-scheme`, from which `renderer/theme/apply-theme.ts` resolves `<html data-theme>` before the first paint — so the page and the OS cannot disagree. A live macOS appearance change reaches the PAGE through that media query alone, but the window's `backgroundColor` is a construction option nothing re-reads, so main keeps a `nativeTheme.on('updated')` listener (`watchSystemAppearance`) that repaints it, and `applyTheme` is the one exported way to apply a theme, so no caller can take the OS write without the repaint. `@custom-variant dark` is re-keyed onto `data-theme` so a `dark:` utility follows the THEME rather than the OS appearance (Tailwind's default, `@media (prefers-color-scheme: dark)`, is wrong the moment a user pins Light on a dark-mode Mac).

```
apps/ui/src/renderer/
  styles/themes/<id>.css   — ONE file per theme: every token VALUE, and nothing else.
                             `light.css` also carries the bare `:root` arm, so a document
                             whose theme has not resolved yet still has a full palette.
  styles/global.css        — carries NO value of its own: the tailwind import, the theme
                             imports, `@theme inline` (pure indirection, written once for
                             every theme), base typography, and the vendor retints —
                             `.md-editor-surface` for @uiw/react-md-editor's GitHub-Primer
                             variables and `.react-flow` for @xyflow's `--xy-*` ones, both
                             unlayered + double-classed on purpose, since the vendor rules
                             they beat are themselves unlayered.
  theme/apply-theme.ts     — the ONE writer of `<html data-theme>`, plus the hooks a
                             component uses when it must name the theme (the md editor).
  components/
    ui/                    — token-driven primitives, shadcn-v4 flavour (data-slot, cva variants).
                             `select` is the app's ONE dropdown — a custom panel, never a
                             native <select>, whose OS menu ignores every token and cannot
                             render groups/icons/checkmarks/search or be asserted on.
    ...                    — app-level shared components composed from the primitives.
  chats/message-bubble.tsx — the transcript-row component (cva variants per item kind).
```

**Hard rules** are in `.claude/rules/renderer-design-system.md` (tokens — never hardcode a colour) and `.claude/rules/renderer-components.md` (never duplicate a component; the token → primitive → app-component layering; `cn()`/`cva`; no barrels). **Two mechanisms enforce them, not one.** The colour rule is an eslint `no-restricted-syntax` override scoped to `apps/ui/src/renderer/**` and `apps/ui/.storybook/**` (which renders the same components against the same tokens). It catches a colour inside a Tailwind arbitrary value (`bg-[#fff]`, `bg-[rgb(…)]`, likewise `rgba`/`hsl`/`hsla`/`oklch`/`oklab`, in string and template literals) and an exact `#hex` string literal; a bare `rgb()`/`hsl()`/`oklch()` string — e.g. in `style={{}}` — is NOT caught, so that case is review-only. The reuse rule is `components/catalog-coverage.spec.ts`, a filesystem-reading spec that fails the suite when a component has no co-located story, when a story outlives its component, or when either is filed outside its layer's namespace. It enforces DISCOVERABILITY, not de-duplication: it cannot see that two components do the same thing, only that both are in the catalog where the next person will find them before writing a third.

**The component catalog** is Storybook (`pnpm storybook`, from the root or `apps/ui`), and it is **development-only**: its packages are devDependencies that `pnpm deploy --prod` strips, `electron-builder.yml` ships `out/**` alone, and `build-storybook` writes to the gitignored `storybook-static/`. CI runs `pnpm build-storybook` because it is the ONLY gate that compiles the story files (`check-types` covers their types; the unit suite never renders them). The dev server binds `127.0.0.1` explicitly — Storybook's default is the wildcard address, which would serve the whole workspace over the LAN through Vite's `/@fs/` handler. It is reached from **View → Component Catalog**, a row `app-menu.ts` adds only when `ELECTRON_RENDERER_URL` is set (see *Main process*). `.storybook/preview.tsx` drives the app's OWN theme writer (`apply-theme.ts`) rather than setting `data-theme` itself — that module keeps the resolved theme in state `useThemeAppearance()` reads, so writing the attribute directly would leave that hook stale — and installs a typed `window.geniro` stub before any other import, since `main.tsx` reads the bridge at module scope. **Every new shared component needs a story in the same commit**; the coverage spec enforces it.

### Chats

`chats/` incl. `approval-card`; the composer's `/` skill autocomplete (`skill-menu`) and its chip row.

The chip row: `folder-select` and `config-dir-select` — both built on `directory-select`, the ONE directory chip (recents + the current value + a native-picker row), which keeps them from drifting apart; the config one adds a "Default profile" row, since the CLI's own is its normal state, and renders NOTHING for a CLI whose `GET /v1/capabilities` `configDirs[]` row names a reason — never a disabled chip, the same rule the effort chip follows. In an OPEN thread it is stated once, in the header beside the agent (`chat-header`), because it is fixed for the run's life and about what the conversation IS; a run on the default profile shows no chip at all. `branch-select` — git branches, only for a repo; `BranchSelect` SWITCHES the checkout. Its second export, `BranchValueSelect`, merely RECORDS a name for a saved run configuration and switches nothing — a separate component rather than a prop, since acting on the checkout is exactly wrong while describing a setup for later. `target-select` — which CLI or `wf:<slug>` a run points at, and the one place the "an agent this machine cannot run is shown-and-disabled, never hidden, and the current target is never refused" rule lives. `context-window-select` — which of the model's context-window sizes a turn runs at, offered wherever the effort chip is (the composer, an open thread's header row, a graph node's inspector, every template). Its rows are the CLI's own words fetched per (CLI, MODEL) through `use-agent-context-windows` — never a table here, and per model because which models carry the axis, and in what vocabulary, varies. With no model chosen there is nothing to list and the chip says so (unlike the effort chip, which falls back to the CLI-wide union; a union of window sizes would mean nothing). Choosing a MODEL clears the window everywhere it is stored — the composer's patch, the node inspector — since a size belongs to the model that offered it and `1m` on a model without the axis is refused per turn. **In the COMPOSER the model and everything it can be run with are ONE control** (`chats/model-settings-select.tsx`) — a chip naming the model, opening a panel whose labelled blocks are Effort, Context window, one per model parameter, and Model last; inside one panel each block says what it is in words, which a chip row has no room for. Do not go back to a row of separate chips. **It is TWO LEVELS**, never one flat list: the first level is one compact row per AXIS — its name, where it currently stands, and a chevron — and the second is that axis's values. Model is the last row and the only one whose second level carries a search field (a filter over the first level would hide the axes it exists to show). It is a `Select`, not a bespoke popover, so the search box, keyboard highlight, clipping escape and placement stay the primitive's; it needs `MenuItem.checked` (several independent choices cannot be marked from a single `value`) and `MenuItem.submenu` with the `side="right"` placement. The child panel is rendered INSIDE the parent's DOM on purpose: the outside-click guard asks `panel.contains(target)`, so a click two levels down must be a descendant or choosing a value would close the menu under itself (`position: fixed` still escapes the parent's scroller). It is a READOUT while the list is still loading. **The AXES have their own waiting state**: an axis with nothing in it is dropped, so a listing that has not arrived would look exactly like a model that offers nothing, and each listing is a real `cursor-agent acp` handshake (seconds when cold; single-flighted in `ModelVocabularyCache`). So the vocabulary hooks surface `useAgentVocabulary`'s `loading` alongside the listing, `Chats.tsx` ORs them into one `settingsLoading`, and the panel shows ONE disabled "Reading what this model offers…" row where the axes will land — one row rather than a skeleton per axis, because WHICH axes exist is itself the answer being waited for. The single-axis chips it composes over (`model-select`, `effort-select`, `context-window-select`, `model-parameter-select`) still serve the graph node inspector's label column, whose free-text model entry (`allowCustom`) this composite deliberately does not carry.

**A picker with nothing to pick is not drawn.** `EffortSelect` and `ContextWindowSelect` return null on an empty listing, and their `unavailableReason` / `unavailableKind` props are gone, so the row grows and shrinks with the model: `auto-smart` draws model + `Optimize For`, `claude-opus-5` draws model + effort + window + `Thinking` + `Fast`. An always-visible control for an absent axis (an inert `no effort control` word, a menu holding one `model default` row) is a dead control on most cursor models; this was reversed twice — do not reintroduce it. The daemon still answers why (`GET /v1/capabilities` `modelEfforts[]`); nothing renders it. Where a LABEL COLUMN is the layout rather than a chip row, the label goes with its control: the graph node inspector drops the whole `SettingRow`.

**Auto-compact is the one axis in that panel that belongs to no model** (`chats/auto-compact.ts`, `ModelSettingsSelect`'s `onAutoCompactChange`). It is offered for every CLI and every model — a share of the context window means the same thing everywhere — so it is present whenever the surface passes the callback, rather than appearing and disappearing with a listing. The thresholds are `AUTO_COMPACT_PERCENTS` (50–90) plus `off`; the daemon accepts any whole number from 10 to 95 (bounds twinned in `shared/contracts.ts`), so a stored value outside the list is still shown as selected. The new-chat pick is remembered as ONE `Settings.lastAutoCompactPercent`, not per CLI, and an open chat's row PATCHes the run like its neighbours. A workflow agent node offers the same choice as a labelled row of the builder's inspector (`chats/auto-compact-select.tsx`, the standalone form of that axis for a surface with a label column), stored on the node as `autoCompactPercent`; a stored value outside the list is added back as a row, since it is what runs. The compaction itself is the daemon's — see *AUTO-COMPACTION* in `apps/daemon/AGENTS.md`.

`model-parameter-select` — ONE chip per setting the model enumerates that geniro has no control of its own for, drawn wherever the effort and window chips are (composer, open thread, graph node). It knows nothing about any of them: the id, the label, the values and their labels all arrive from the CLI (`GET /v1/agents/model-parameters`, per (CLI, MODEL)) and the pick goes back verbatim, so the ROW ITSELF grows and shrinks with the model — `auto-smart` draws an `Optimize For` chip (Intelligence / Balance / Cost) and `gemini-3.1-pro` draws none. It carries no explanation: this app cannot say what `Fast` does, and the vendor's own word stands alone. The chip states the OUTCOME and the menu the CHOICE — with nothing picked the trigger reads what the CLI says the model is already on while `model default` stays the checked row. It names the PARAMETER beside the value (`Optimize For · Balance`), unlike its two neighbours, because this app does not know the axis: `1M` and `high` name themselves, while `Cost` or cursor's boolean `On`/`Off` mean nothing alone. `showAxisName={false}` drops it in the graph node inspector alone, where a label column carries the name. `withModelParameter` beside it is the one map edit every surface uses: a press is about one parameter while the run stores all of them, and the obvious inline spread writes `{id: undefined}`, which is not an absent key on a `record(string, string)` wire. `model-select` — the models the CLI ITSELF reports (via `GET /v1/agents/models`) + a "default model" row, hidden for a workflow target. `approval-mode-select` — offered for **every** CLI, each from its own `AdapterConfig.approval.modes` via `GET /v1/capabilities` (`approvals[]`), never from an allowlist of agent names. Reversed once — do not reintroduce. No unit test, deliberately (jsdom; `composer-rows.tsx` is untested for the same reason); verify in the running app.

**The run's FOLDER is in the HEADER, never the composer.** Three composer placements (beside Send, a row above the card, inside the card's top right) were each rejected — do not move it back. The composer holds the run's LIVE choices, so an unchangeable fact there always needs a band of its own; the header already carries the run's other life-long facts (the agent, the config directory) under the profile chip's rule — fixed for the run's life, about what the conversation IS — and its identity line already truncates the TITLE first. The composer keeps only controls that change something, and the queued strip sits directly on the card. The LANDING composer is different: there the folder is a live picker among the other run-identity chips, which belong above the card by the rule `composer-rows.tsx` states.

The figures END the row (the counters moved to the composer shelf, below). The identity popover uses `align="end"`, since a 24rem panel opening rightward from a trigger near the window's edge gets clamped by `Popover` away from its chip. Both groups carry a `data-slot` (`chat-header` / `chat-header-aside`), so the folder's position is pinnable from either side.

**The sidebar's PREVIEW line is kept current for a background thread by the client-wide `run_status` channel, not by its items — pushed for every message `threadPreviewOf` admits, from the one persist seam.** `persistItemAndEmit` (`v1/agents/utils/persist-item.ts`) announces `{status: null, preview}` right after it publishes a `message` row that is not a delegate's, not inside an agent-to-agent call and not blank — the twin of `ItemDao`'s list rule and this side's `previewsThread` — so the chat path and the graph executor cannot drift (a push only in `ChatService.persist` leaves a WORKFLOW's preview stale). Live items reach only the OPEN run's room, which is why `addItem` cannot keep a background thread's line current. The settle's `summary` is still read as a fallback when an announce carries no `preview`; only a non-empty string writes, since a turn that said nothing did not delete the last message (unlike the system notification, where `null` clears).

**An empty menu GROUP must not draw a block.** `Menu` drops a group with no rows on both the search and the unfiltered path (otherwise the next group's separating hairline sits under an empty box). A sentence explaining a group belongs in `MenuGroup.note` — prose, muted and wrapping — never in `label`'s 11px uppercase micro-label, and never only in a hover `title`.

**When a message queues — the table.** The whole decision is `followUpDelivery` / `parkedReason` in `chats/follow-up-delivery.ts`, read by the send path, the button, its hover sentence and the placeholder — so they cannot disagree about one press — and pinned row by row in its spec. One principle decides every row: **a message goes straight in when the agent will read it soon, and queues when the agent is busy with something that keeps it from reading until that thing ends.** A queued message can still be edited, reordered or withdrawn, and the strip's **Send now** pushes it into the turn anyway where the CLI has a mid-turn channel.

| # | What the thread is doing | Message | Why |
| --- | --- | --- | --- |
| 1 | Nothing — no turn in flight | **sends**, starts a turn | nothing to wait for |
| 2 | Earlier messages still in the queue | **queues** behind them (and kicks the drain if the agent is not working) | a queue the composer can jump is not a queue — FIFO |
| 3 | The agent producing its answer: thinking, writing, running a tool | **queues** | redirecting a turn in flight is the user's explicit choice (Send now), never a side effect of Enter |
| 4 | …including a tool call that BLOCKS on other work: a **sync sub-agent** (`Task` without `run_in_background`) or a long **foreground command** | **queues** | the agent cannot read anything until that call returns — minutes |
| 5 | Turn HELD: the reply is over, the process only waits for background sub-agents to report (`holdingFor`) | **sends** | stdin is idle; nothing to redirect |
| 6 | Sub-agents running **in the background** (`subagentsOut`), whatever else the agent does | **sends** | the agent is not waiting on them — Claude Code's own prompt is live in this state  — except an ACP agent running them as SUB-AGENT SESSIONS (cursor), whose held prompt would cancel them: the daemon refuses with RUN_BUSY and the message queues per row 10 |
| 7 | A **detached command** running (`shellsOpen`) | **sends** | same; the trade-off (a long-lived dev server keeps sending) is the user's choice |
| 8 | Workflow manager inside `await_agent` / a sync `call_agent` (`awaitingCalls`) | **sends** | unlike row 4, the daemon RELEASES that wait on a user message (`CallBroker.interruptWaits`), so it is read in seconds |
| 9 | Workflow manager has ended its turn while its calls run (`rootsWorking = 0`) | **sends**, starts the next pass | the manager is idle |
| 10 | The daemon answers RUN_BUSY where the renderer believed rule 1 | **queues** and kicks the drain | the daemon is the fact, the renderer's `streaming` a belief |

Rows 4 and 6 are the same unit seen twice, and what separates them is the CLI's own word, never a guess: claude's `task_started` carries `is_backgrounded` (false = "the spawning tool call blocking on it"), and a later move to the background — its auto-background timer, or a queued message it moved the work aside to deliver — arrives as `task_updated patch.is_backgrounded`. The daemon therefore announces a unit as background work (`subagent_info.backgroundOpen: true`, `shell_open`) only once it IS some (`background_work.foreground` / `backgrounded`, see `apps/daemon/AGENTS.md`). cursor tells the two apart (`cursor/task`'s `isBackground` → `backgroundOpen: null` for a foreground delegate).

**A WORKFLOW whose Manager has ended its turn takes a message at once, even while calls it started run on** (`RunWire.rootsWorking`, announced on `run_status`; `rootsIdle` in `use-chat-run.ts`, read by `Chats.tsx`'s send path, `activeRunHeld` and `queueMayDrainAfterReplay` through `workflowRootsIdle`). The run stays `running` while any call is out, so without this the composer would queue behind the whole call with nothing to drain it. The daemon counts the pass's DAG agents inside a turn — the Manager, and any node the walk has reached downstream of it, never a call — marking the Manager busy before a pass announces `running`, and going idle SILENTLY during a Stop (an idle announce is what drains the queue). The queue drains on the count's fall to 0, the row carries it for the replay paths, and a settled run drops its idle mark so the next pass queues normally.

**A HELD turn is not a working agent, and BOTH halves of the queue read it that way.** The daemon defers a turn's terminal event while a delegate it launched is still out (`holdingFor` on the run row and on every status announce) — the CLI's turn is over and it sits on an idle stdin so those delegates have somewhere to report. A message typed in that window sends straight in, and the messages queued BEFORE the hold began are released too, in the two places a hold can be learned: the live announce fires the drain on the TRANSITION into held (`use-chat-run.ts` — once per hold, never per report, or one turn would swallow the whole strip), and `queueMayDrainAfterReplay` counts a held run as drainable so opening or reconnecting to the chat does the same. A held run is the one case where a replay both re-arms the live row AND drains — which is why that pair is not an `if`/`else`: it is still `running` with no terminal row, so it answers the first branch and is owed the second anyway.

**The context readout's drill-downs are FOLDED, with each block's total on its header** (`9 servers · 113.2k`). They are open-ended lists (per deferred category, per instruction file, per MCP SERVER) that would otherwise push the headline readings out of sight; the fold is remembered per block (`usePersistedFlag`, since the panel is mounted afresh on every open). Spell both forms of each noun at the call site, never derive a plural with an `s` (the first block counts CATEGORIES). The breakdown, the plan limits and the thread totals stay open: they are what the panel is opened for. Each folded block is ONE LINE: the TITLE truncates (full text on the row's `title`) and the figure never gives way, since a half-shown number is worse than a shortened word.

**The landing card declares the viewport anchor, and the correction that keeps a panel on screen re-runs AFTER the placement lands.** The card's own `<section>` scrolls, and a box that scrolls vertically cannot keep `overflow-x: visible` (CSS forces both axes non-visible together), so an absolutely-placed panel inside it is cut on both edges. The container therefore declares `MenuAnchorContext` as `viewport` — the rule `Dialog` follows for its scrolling body — rather than each chip passing a prop. A floating menu is placed in TWO commits (one effect measures the trigger and sets the offset; only the next render moves the panel), so `Menu`'s overflow correction re-runs on `box`, and returns the SAME object when nothing moves so the loop settles. The open-chat composer needs neither: its section does not scroll.

**A geniro command QUEUES like anything else — the composer does not pre-empt the daemon's refusal.** `/compact` needs an idle run (it rewrites the turn and, on a CLI with no compaction of its own, replaces the session), and the daemon says so with the RUN_BUSY the queue is built on. The drain fires on a turn's TERMINAL ITEM and retries RUN_BUSY for ~4.5s, which covers the whole teardown (`TURN_END_EXIT_GRACE_MS` is 2s), so a queued command goes out on the first retry. Do not reintroduce a composer-side refusal (or `geniroCommandName`, its only helper).

**The queue's drag must ACCEPT the drop over the dragged row itself, or the browser snaps the drag image back** (`chats/queued-strip.tsx`). A drag whose last `dragover` was not `preventDefault`ed is an unsuccessful drop, and because this list rearranges live UNDER the pointer, the carried row is almost always the element beneath the cursor when the button comes up. So prevent the default FIRST and decide what to MOVE second — never return early on `draggingId === message.id` before preventing — the rule in both places that have it (the sidebar's sections too). The strip still refuses a drag it did not START (`draggingId === null`), since the sidebar's chat rows are draggable too. Pinned on `defaultPrevented` — the exact flag the browser branches on (jsdom runs no drag machinery); in the real renderer, separate `dragstart` from `dragover` across frames so React has committed the drag state.

**The queue survives a RELOAD** (`chats/queued-message-store.ts`): it is kept in localStorage beside memory, because the composer is cleared the moment a message is queued and a phone's browser discards a background tab routinely. Images that overrun the quota are dropped from the saved copy and the words kept.

**A send owns what it sends the moment it leaves, and a pasted picture is not staged until it has been READ.** The follow-up path clears the composer FIRST and puts anything unsent back where it came from (`restoreUnsent`: the composer if that thread is still on screen, else its saved draft, never over newer typing) — clearing after the POST returns lets a thread switch inside the await save in-flight images as the old thread's draft and restore a failure's text into the wrong thread. A paste is decoded and resized asynchronously, so `useAttachments` exposes `reading` and Send waits for it (the button says why on hover); each read carries its owning thread, so one landing after a switch goes to that thread's draft. The queue head whose POST is actually out reads `sending…` with Edit/Remove disabled (`postingIds`), and with no turn running the strip says the queue is waiting for the user rather than promising a send nothing will make — the Send button's label is derived from `followUpButton`, the same decision the press takes.

**The QUEUE is the order, not the composer.** A message goes behind whatever the user wrote earlier — `sendFollowUp` queues when the agent is working OR when this run's queue is not empty. Never decide on `streaming` alone: it is false in every window where the queue outlives its turn (after Stop, which deliberately leaves the queue standing; after a failed drain; while a drain's POST is in flight; on a run reopened before its drain ran), and the newest message would overtake the older ones. Queueing behind an idle run also KICKS the drain, because the automatic one fires on a turn's terminal item and there is no turn. Not while the agent is working: that drain would spend its whole RUN_BUSY backoff refusing and hold `drainingRef` against the drain the turn's own ending fires.

**A queued message's "send now" asks about the agents the message LANDS in** (`steerAgents` in `Chats.tsx`, `triggerFedAgentIds` in `chats/workflow-root.ts`). For a chat that is its one agent. A workflow run has no agent kind of its own, and the daemon hands a follow-up to every agent its trigger feeds, so those agents' CLIs are asked, off the run's own snapshot — never `activeRun.agentKind` alone, which is null for every workflow run. Every one must have the mid-turn channel, since the daemon refuses the whole delivery when any cannot take it.

Pasted-image attachments: `use-attachments` staging + `attachment-strip` thumbnails on the composer; `attachment-payload` + `message-attachments` in the transcript, fed by the `AttachmentLoaderContext` `Chats` provides so the memoized row shells need no new props.

**The composer's PAPERCLIP attaches by the same two rules, from a picker** (`chats/attach-files-button.tsx` → `chats/use-file-attach.ts`, at the start of `ComposerBottomRow`'s `leading` slot in both composers). It is a `<input type="file">` rather than the native dialog over IPC, because that is the one picker that works both in the window and in a phone's browser. A picked image the model accepts is STAGED like a paste (`useAttachments().addFiles`, which hands back what it cannot stage — another type, HEIC, or over the 5MB cap — instead of refusing it); every other file becomes its PATH, appended on a line of its own. On a phone there is no path, so the file is uploaded to the Mac (`POST /v1/chats/uploads`, 25MB, a 5-minute timeout rather than the client's 30s) and the stored copy's path goes in instead. An upload is routed to the draft it was picked FOR, like a paste's read, and Send waits for it (`attachBusy`, which also covers a paste still being read).

**A pasted file that is NOT an image is its PATH** (`chats/paste-file-paths.ts`). macOS writes a copied file to the pasteboard as a file URL PLUS a plain-text flavour holding only the file's NAME, and Chromium's default paste inserts that name (while `clipboardData.types` reports `["Files"]` alone). The path comes from `webUtils.getPathForFile` (Electron removed `File.path`), so `GeniroApi.filePath` is the ONE member of that interface the preload answers itself rather than over a channel (a `File` cannot be sent to main, and a paste handler must decide whether to swallow the event before it returns; `PreloadLocalMethod` excludes it from the `IPC` exhaustiveness check). Three rules. Images are LEFT OUT — they travel as bytes through `use-attachments` — and both readers are asked on every paste, since a clipboard can hold both kinds. The insertion is `execCommand('insertText')`, which lands at the CARET, keeps the field's undo stack and fires the `input` event a controlled value is written from; a state update would do none of the three. A paste it cannot replace is GIVEN BACK (a file with no path on disk, a field that refused the insertion) — the bare name is poor, losing the paste is worse. All three chat fields share it: both composers and the question card's answer field.

**Every one of those thumbnails OPENS** (`components/ui/image-viewer.tsx` → `ZoomableImage`, also under `markdown-image`): the transcript draws 128px `object-cover` squares that show only a screenshot's middle, and those bytes exist nowhere else in the app. One component across all three surfaces, over `Dialog` rather than beside it, so the modal contract is not written twice. Three details are load-bearing. It is **portalled**: it is the only dialog opened from deep inside a view, and `position: fixed` resolves against the nearest transformed ancestor. Its focus ring is **inset**, unlike every other control's — both thumbnail frames are `overflow-hidden` and would clip an outside ring. And its card is `w-fit`, overriding `Dialog`'s `w-full`, so a small image is not adrift in a 64rem card.

**And it ZOOMS**, on `react-zoom-pan-pinch` (MIT, no runtime dependencies) rather than a hand-rolled transform: the library keeps the point under the cursor fixed while the scale changes and clamps the pan to the scaled bounds — the two parts that are fiddly and invisible when wrong. `MIN_SCALE` IS fit-to-window (`limitToBounds` makes that true), so at rest the zoom-out and reset controls are DISABLED (a live control that does nothing reads as broken). The percentage reading IS the reset control; do not add a separate reset icon. Its spec stubs `ResizeObserver` (jsdom ships none) as `chart-block.spec.tsx` does for recharts, and since every box measures 0×0 there, no test asserts a SCALE — they pin the controls and the invariants around them. The composer's ✕ stays a SIBLING of the opener, never nested inside it — a nested button is invalid markup, and every attempt to remove an image would open it instead.

**The MARKDOWN export collapses base64 images and opens with a SUMMARY** (`chats/chat-markdown.ts`, over `chats/export-image-blocks.ts` and `chats/chat-export-summary.ts`). The JSON export is for a machine and is untouched; this is the one a person reads. The `json()` fallback dumps a payload whole, so a tool result carrying a picture would write megabyte-long base64 lines: `collapseImageBlocks` walks the payload and replaces a declared image block with `[image: image/png, 171 KB]` (the DECODED size), applied inside `json()` — the one door every dumped payload passes — so a screenshot cannot reach the file whichever row carries it, including a kind added later. Two block shapes: claude's `{type, source: {data, media_type}}` and ACP's `{type, mimeType, data}`. A long base64 string nothing DECLARED an image is left alone (it could be anything, and the reader would lose the only copy). The value is returned by IDENTITY when it holds no image, so an ordinary chat's export is byte-identical.

The SUMMARY states the figures a reader opens such a file for: which agent spent the money, how long each agent call took, which failed and how, how many times a window was compacted. `chatExportSummary` folds four tables out of rows the transcript already holds — `turn_complete` per node, the `call_started`/`call_result` pair (with the call's own cost summed from the `turn_complete` rows carrying its id), `error`, and a `system` row carrying the `compaction` MARKER, read through `compaction-payload.ts` rather than by matching a CLI's prose. It stores and computes nothing new. Three rules: a figure nothing measured is an em dash and never a zero (`$0.00` would claim a turn ran free); a call's outcome carries the WHOLE machine-prefixed one-liner, because the prefix is the diagnosis; and a section with no rows is omitted with its heading. Money and duration come from `agent-activity.ts` / `turn-duration.ts` — never a third money format.

**A workflow run's agents are read from the RUN, never from the library** (`GET /v1/workflows/runs/:runId/workflow`, read by the `wfNodes` effect in `Chats.tsx`). The run keeps a copy of the graph it started with (`Run.workflowSnapshot`), so editing a workflow changes neither an old run's agents panel nor what its follow-up message runs. A run made before copies existed is frozen from the library on its first read. The composer's trigger chip for a NEW run still reads the library, since that is the graph the next run will take.

**The agents panel is part of the chat screen, not a thing to summon** (`agents-panel.tsx`, rendered whenever a run is open — `showAgentsPanel` in `Chats.tsx` is just "is a chat open"). Do not reintroduce a show/hide toggle, a header button, or auto-opening on a published artifact. The header carries no counter; the running-sub-agents / open-tasks counts are composer-shelf chips (below). **Putting the panel away is the panel's OWN business, and it folds rather than vanishes**: a chevron in the heading and a `w-9` rail carrying the label sideways plus the control that opens it again (`collapsed` in `agents-panel.tsx`, remembered PER THREAD through `useThreadFlag`). A panel that vanished entirely would need a second control in the transcript header; the rail keeps the control on the column it acts on. It is remembered rather than component state because `Chats.tsx` remounts the panel per run on purpose (`key={activeRun?.id}`), and per thread rather than globally (see *Thread UI memory* below). **A thread nobody opened it in starts FOLDED**: the transcript is what a thread is opened to read; an unfold is remembered for that thread.

**Thread UI memory — what the reader folded is remembered per THREAD** (`chats/thread-ui-memory.ts`). `Chats.tsx` provides the open run's id on `ThreadUiMemoryContext`, and each fold reads its state for that run under a key naming the ROW it belongs to (`tools:<group id>`, `tool:<call id>`, `subagent:<block id>`, `thinking:<item id>`, …) — never an index, since the transcript window pages. `useThreadFlag` is the fixed-default shape, `useThreadOverride` the press-over-a-derived-default shape the self-opening folds use (a group holding a diff, the latest task card, a sub-agent block holding a card), and `useThreadFlags` serves the panel, which draws a variable number of folds per render. Only a PRESS writes, so a thread nobody touched shows every default. Storage is one localStorage entry per thread, capped at 200 threads and 500 folds a thread (least recently pressed forgotten first) and dropped on a permanent delete; outside the provider every hook is plain component state, which keeps a spec or a non-thread surface behaving as before. Deliberately NOT per thread: the context readout's drill-downs (they describe the window's categories, not the conversation) and the builder palette. **Inside a card, nothing folds either**: the delegate list and the task list are drawn open, delegates FIRST, and there is no button to reveal them (a `ListTree` toggle was removed — do not reintroduce it). ONE fold survives, over the FINISHED delegates — those rows are history that would bury the live ones — and it counts what it hides on its own row. The card list carries `data-slot="agent-cards"`, because it is not the only `ul` in the panel and `ul > li` reaches the thread rows too. The MCP listing is read only once the user opens an agent's MCP disclosure (`mcpOpen`), never because the panel is on screen, so an always-visible panel dials nobody's servers.

**A running call's callee can be messaged directly, from its call block** (`chats/call-message-box.tsx`, rendered by `CallBlock` while the call runs) — the composer of a workflow run reaches only the agents its trigger feeds. The box sends to `POST /v1/workflows/runs/:runId/nodes/:nodeId/calls/:callId/messages`, and the callee's answer still goes back to its CALLER — the box says so, and says BEFORE the press when that CLI's mid-turn channel INTERRUPTS its current step (`capabilities.followUps[].interrupts`, the same reading the composer's steer control uses); a CLI with no channel gets a disabled button carrying the daemon's sentence. It travels as `CallMessageChannelContext` through `ChatProviders`, provided for workflow runs alone. It offers what the composer offers minus the run's configuration: pasted images (`useAttachments`, as the question card uses it) and a QUEUE (`chats/use-call-message-queues.ts`, rendered by the composer's own `QueuedStrip`), with the button in the call block's footer (`BlockToolFooter`'s `action`). The queue does NOT hold messages until a turn ends the way the composer's does — a callee's only turn is the call, so held messages would never arrive — it keeps them in order (one POST at a time, the in-flight one out of the list so it cannot be edited after the daemon has it), retries `CALL_MESSAGE_REFUSED` on a short backoff, and on any other refusal STOPS with the daemon's sentence beside the messages it kept, never re-driving them on its own. It is keyed by the call block's id rather than by call id, because call ids restart with each pass of a run, and it lives in `Chats` so folding the card loses nothing. The message row sits inside the block as the user's own, and the folds that read a block tell it apart by `role === 'user'`: it is never the block's summary, never its result, and never clears its gone-quiet marker. The RESULT is taken only from rows written before the sub-turn's terminal status — a message delivered as the callee wraps up is answered off-turn, after the caller already had its result.

**A CALLED agent is drawn as its INSTANCES, each holding its own work** (`chats/agent-instances.ts` — the pure split; `InstanceBlock` in `agents-panel.tsx`). A workflow node can be called many times, and each `call_agent` thread is a conversation of its own running beside the others. **A call that CONTINUES an earlier call's thread is not another instance**: `call_agent`'s `thread` argument resumes that call's callee session, so it is ONE instance in the panel and ONE card in the transcript. Both surfaces read the chains through ONE rule (`resolveCallChains` in `transcript-groups.ts`, which joins a call only to a thread whose `call_started` came EARLIER in the window, so a root outside the window stays its own and no cycle can form) and name a conversation through `conversationHead` (its latest call) and `conversationRoot` (its first); `CallBlockEntry.callIds` / `AgentThread.callIds` hold every call and anything matching a call id to a block or an instance goes through them, both stay OPEN while ANY call is (`openCallIds`, since the daemon lets two calls continue one settled thread at once), spend sums the whole conversation, and the task lists are combined with the later call winning per task id. Never pool every instance's delegates, commands and checklists into one list: a card whose agent holds any call thread draws one block per call (and one for its OWN conversation only when something happened in it, its heading and terminal being the card's): the call's brief, its own context ring and terminal handoff, a line saying where it has got to and what that instance alone has spent (`callBlockLatest` / `callBlockUsage`, read off the transcript's own call block), and INSIDE it that conversation's sub-agents, running commands and task list. A block starts open only when it is the ONE instance at work, the reader's press outranking that default. A folded block counts what it holds on its second line (`InstanceCounts` — sub-agents, terminals, tasks done/total), so folding hides nothing silently. **Every block has the SAME anatomy, whatever it holds** (never a shape decided by the data, which makes shut blocks read as open): a disclosure, a heading stating the FIRST LINE of the call's brief with markdown markers stripped (`chats/brief-text.ts`; the call id lives only on the heading's hover), and a second line that is always drawn — where it has got to, else its status in words, plus its spend when measured. Opening one shows the REST of the brief — never the heading's line a second time — clamped, with a line that is only a URL drawn as one short link, above its delegates, commands and plan, and a `Hide details` control at the bottom of the body. An agent that was never called keeps the flat shape. **Every instance carries its OWN context ring, the main conversation included.** A main conversation exists only when the node ran a turn of its own: a `status` row carrying no `callId` (`AgentActivity.mainTurnStarts`) — never inferred from counting turn starts against call threads, which draws a phantom `Main conversation` when one call runs a second turn. The main instance's ring is folded from `turn_complete` rows with no `callId` (`mainContextTokens`), and the node's own live key outranks it in `callThreadsOf`. The CARD draws no ring of its own over more than one instance (each window differs); over a single conversation it still does. The panel draws the main block whenever it has a reading, not only when it holds delegates, commands or tasks. **A call OLDER than the loaded window is an instance too**, built in `callThreadsOf` from the daemon's per-call readings (`nodeReadings` → `calls`) and its list of the run's calls (`runState.calls`) for every call id the window does not name, ONE instance per conversation (chained by `thread` through `callChains`) — a call's `call_started` row is the only thing naming it in the transcript. Such an instance is titled by its brief from the daemon's call list, and its status comes from the call's block when the window holds any of its rows, else from that list.

**Each settled instance states where its prompt cache stands, beside its ring** (`chats/prompt-cache-badge.tsx`, on `ThreadRow`). The nodes route carries `promptCacheExpiresAt` per call and for the node's own conversation; `resolveConversationCacheExpiry` takes a conversation's newest call that states one. The badge counts the warm minutes down, reads `cold` once the cache lapses, and turns warning-toned when the lapsed conversation is over half its window — the same rule the daemon holds a calling agent to (`list_agent_threads`, `CACHE_EXPIRED`; the threshold is a TWIN, pinned by a spec that reads the daemon's source). Nothing is drawn while the instance works or when its CLI states no cache lifetime.

**The transcript is a WINDOW; its STRUCTURE and every readout beside it are not** (`chats/history-anchors.ts`, `chats/use-run-state.ts`, `Settings.historyPageSize`). A chat opens on its newest page (250–2,000 items, the user's pick; the daemon caps a page at 5,000) and pages older through `beforeSeq`. Two things keep that window from deciding anything but which rows are drawn. **Anchors**: `GET /v1/chats/:runId/items` answers `{items, anchors}`, the anchors being the rows OUTSIDE the page its rows refer to — every referenced call's `call_started`/`call_result` with the rest of its `thread` conversation, a delegate's launching call, reply and declarations, a reply's call, a dynamic workflow's first and newest announcement. They are held APART from `items` (every pager reads the window's first and last row and counts what came back), laid in only where the transcript is folded (`withAnchors` → `groupTranscript(…, {anchorIds})`), and never drawn as a row of their own. A live row naming structure nothing held can place asks for that row's anchors (`chats/use-live-anchor-asks.ts`, shared by the chat screen and the builder's dock so the two cannot disagree about which live rows need anchors); every place that REPLACES the anchors calls its `forget`, and a page that lands after a live row was answered MERGES rather than replaces, since that row's key stays asked. Anchors follow their rows: a read whose rows `addItem`'s away-from-tail guard refuses (a reconnect replay, a tail catch-up landing after a second jump) brings none, or a card would be drawn for work the window does not hold. Never rebuild a call heuristically from its later rows (it guesses `running` and draws ghost cards). A call's ending is whichever came first, its first terminal status row or the broker's settle envelope (`buildCallBlock`), and its RESULT falls back to the envelope's `result.text` when the answer message is above the window. **Run state**: `GET /v1/chats/:runId/state` is what the run holds as a whole — its open cards (`ApprovalRegistry`), every call, every delegate, running commands, dynamic workflows, artifact publishes, a chat's open-turn start. `useRunState` reads it on open, reconnect, a structural row or a status announce (never an activity phrase), so it stays live while the reader has jumped off the tail; the pinned card, needs-input (which also ORs `run.awaiting`), the Agents / Sub-agents / Terminals / Workflows chips, a card's sub-agent list and shells, the header clock and the artifacts list read it. The window's own reading WINS where it holds the same thing (it carries what the summary cannot: a delegate's conversation, a command's exit code), except open requests off the tail, where the window is history. A call or delegate the window does not hold is reached by jumping to its start row (`OFF_WINDOW_CALL_PREFIX`, `openSubagentById`). Worked time and tool count take the daemon's figure ALONE where it has one; the turn in flight is added on top by each card.

**The instance list is ONE ruled surface**, not a bordered box per instance. It sits under an `INSTANCES N · K running` micro-label, with the live instance alone tinted. What makes the split possible is the `callId` the executor stamps on every row a callee sub-turn streams: `ShellRun.callId`, `SubagentBlockEntry.callId` and the task fold (`taskListsByThread`, and the daemon's `RunTaskGroup.callId`) all read it, so a row is filed under its conversation rather than its node. Content whose call is not in the loaded window (the daemon folds every list the run wrote) becomes an INFERRED instance labelled with its call id, never poured into another one. The foreground-shell gate in `Chats.tsx` is per conversation as well: a settled call's unanswered command is dropped even while the node's other calls work on.

**Calls still out are the composer shelf's `Agents` chip, not a transcript row** (`RunningCallChips` in `chats/composer-shelf.tsx`, fed by `openCallBlocks` in `chats/transcript-groups.ts`). A callee inside an open call block gets no working row, because the block narrates it (`<callee> is thinking...`), and a caller's own working row no longer names what it waits on. Never time a wait from the agent's LAST row (it resets to `0s` after every tool call): the chip times each call from its start (the daemon's list of the run's calls, else the card's own `call_started` time), states the total wait in its panel, and a press reveals the newest call's card; each row reveals its own. It lists nothing once the run has settled.

**The THREAD's PULL REQUESTS are what the thread OPENED, and nothing else** (`chats/use-thread-pull-requests.ts` — the resolve; `chats/composer-shelf.tsx` — the chips; `main/github-prs.ts` `readPullRequestsByRef`). The daemon captures the pull requests a run opened out of its own transcript (see `apps/daemon/AGENTS.md`) and puts their identities on the run row; only GitHub knows what they currently ARE, so the renderer joins the two — one batched IPC call for every thread on screen, resolved by REPOSITORY (`gh pr list --repo`, with `gh pr view <url>` for anything older than that page) — one query per repository, not per thread. Addressing by URL is the whole point: it survives a branch switch and spans repositories, neither of which a query keyed on the folder's checked-out branch can do. A ref GitHub could not be asked about still draws a row that links to it — the thread demonstrably opened it, so an unanswerable lookup must cost the STATE and not the pull request.

**The capture runs when a TURN ENDS as well as on the chat listing, and the result is BROADCAST.** Capturing on `listChats` alone (one fetch per window) never sees a pull request opened during the session, and `run_status` alone carried none. `PullRequestCaptureService` therefore subscribes to the agent bus (a SUBSCRIBER, on the stats recorder's reasoning: both execution paths converge there, and no turn path should have to remember this) and announces on `RunStatusEvent.pullRequests` — the same seam `ChatTitleService` uses for a fact settled a moment after the turn ends. It announces only when the answer CHANGED, so a chat with none is silent — and from WHICHEVER pass found the change, the listing included: both passes share one marker, so a listing that ran between the `gh pr create` and the turn's end would otherwise capture it silently while the listing's own reply loses to `keepFresherRows` (the write moves no `updatedAt`). The announce carries `status: null`, since an event that never read the run must not assert whether it is still going. The renderer replaces the row's list wholesale rather than merging, the daemon's own pass having merged already.

It is drawn in three places, and it is the ONLY source any of them draws from: the panel lists them under **Opened by this thread** (what is still open in the open; merged and closed-unmerged folded together behind one control, shut by default, so the one in review is not buried under finished ones), the sidebar row names the thread's own newest RESOLVED one, and the shelf above the composer names the ones the thread is on. The repository is part of each name exactly when the thread spans more than one. **A row's STATE is its icon** — green merged, yellow open, grey draft, red closed (`lookOf` in `chats/pull-request-row.tsx`, tokens only) — and never a word beside the number; the word stays in the row's tooltip and in the icon's `sr-only` text, since colour is not a label.

**A WORKFLOW row RENAMES like any other**, on both surfaces — the hover pencil and the right-click menu. The title is the RUN's (`ChatTitleService` names workflow runs from their own conversation; the workflow's name is on the label chip), and the daemon's rename route is kind-blind.

**A row can be TINTED** (`Run.color`, the right-click menu's *Change colour* — the groups' palette colours plus *No colour*): the whole row takes that colour's token wash (`GROUP_ROW_TINT_CLASS` in `chats/run-group.ts`, over `PALETTE_ROW_CLASS`), with a stronger step on hover. The tint YIELDS to the active row's highlight, for the unseen wash's own reason — two backgrounds on one row read as a third state — and OUTRANKS that unseen wash, whose left bar still marks the row unread. Like a pin, the colour is the listing's to decide on a refetch (`keepFresherRows`), because the write does not move `updatedAt`.

**On the SIDEBAR row both facts are LABELS, not chips** (`chats/chat-list-item.tsx`, `data-slot="chat-row-labels"`; `PullRequestBadge` in `chats/pull-request-row.tsx`). The pull-request badge is the state glyph and the number only — the title and the state WORD live on its `title`, since the row already carries the thread's name and last message. **Labels rather than chips is a correctness point, not a style one**: the row is ONE activatable element, so nothing inside it can be a control — an anchor nested in one is invalid markup that also steals the row's own click — and a chip's affordance would promise a press nothing here can honour. The second label is the AGENT (`agentLabel`): `claude`, `cursor` or `graph`. A workflow has no single CLI, so the word is what the run IS and that reading WINS over any kind the row carries; the daemon's `cursor-agent` is shortened to one word; and a run that recorded no kind says `agent` rather than guessing. That mapping is deliberately NOT shared with the agents panel, which renders the exact kind in its own badge — a third caller is when it becomes shared.

**The composer SHELF** (`ComposerShelf`) is ONE LINE that never wraps. It names every pull request the thread has OPEN, up to `MAX_SHELF_PULL_REQUESTS`, newest first — and the newest single one when the thread has none open, which is what `currentThreadPullRequest` answers on its own. OPEN is what earns a chip (an open pull request is the only kind that is still work; a merged one has its row in the panel). Past the cap it hands the rest to a button, `All N`, which opens the RIGHT PANEL rather than growing the row; its count is what the THREAD opened, since the panel lists them all.

**Fitting them to the line takes TWO mechanisms, answering opposite situations.** A CROWDED row is handled by flex alone: every chip carries `min-w-0` and the default shrink while the terminals chip beside them is `shrink-0`, so the pull requests give up width first and the row fits by construction. A ROOMY row is what flex cannot do — several chips would each take a lone chip's full width — so `PULL_REQUEST_CHIP_WIDTH` caps them by COUNT (not linearly, because a number, a glyph and the padding are a fixed part of each chip). The `All N` button reaches two flags in different subtrees (`chats/panel-flags.ts` → `setPersistedFlag`), the panel's own collapse and the thread section's settled fold, because a panel revealed with its fold still shut answers with an empty section. It is a SHELF rather than a pull-request strip on purpose: anything the thread produces that is worth reaching without scrolling is another chip in that row, never another one-item band above the composer. Its height is RESERVED even when it holds nothing (`min-h-7`, the tallest thing it can hold): the transcript above is pinned to its tail, so a row appearing or vanishing (the Terminals chip comes and goes with nearly every command) would move every line in it. While a message is QUEUED the shelf rides at the head of the queue strip's header line instead (`QueuedStrip`'s `leading`, `ComposerShelf`'s `inline`), held at the same height, so no blank band opens between the queue and the composer. A thread that opened none gets NOTHING here.

**"Changed since this chat started" leaves out what a PULL brought in** (`main/git-changes.ts` `upstreamBaseSince`, `GitChanges.upstreamBase`, said in the dialog's header). The list is the working tree against the chat's start commit, and a checkout that pulled after the chat began still DESCENDS from that commit — so the branch-switch guard (`movedOffStart`) never fires and every file the pull touched would be listed as the chat's. The base is therefore the newest commit HEAD shares with the remote's default branch (`origin/HEAD`, else `origin/main`, else `origin/master`), used only when it lies at or past the start — a stale remote ref, or a chat begun on a branch already ahead of the remote, answers with an older commit that would put upstream's own work back in, and keeps the start. Deliberately, once the chat's own commits reach that branch they are history and drop out, the same reading `movedOffStart` takes of a checkout that left the start. **That is also why the header names the REF and claims no cause** (`GitUpstreamBase = { sha, ref }`, the ref as `git rev-parse --abbrev-ref` spells it): a pull and a merge of the chat's own commits move the base identically, and the default branch is not always `main`.

**There is no BRANCH query — the panel lists only what the thread opened.** A branch-scoped list (`gh pr list --head <branch>` per checkout) showed the thread's own pull request a second time, since it is on the thread's branch by construction, and whatever else the branch held was not this conversation's work. It was removed with its hook, rows and IPC channel; do not reintroduce a branch-scoped list.

**A tool group holding a FILE CHANGE opens itself, and so does the row carrying it** (`tool-group.tsx` → `showsFileChange`). A diff sits behind TWO folds — the group's chevron, then the row's — and is the one part of a turn that has to be checked by eye, so both give way together (opening the row inside a shut group renders the diff into a closed box). Only what starts open changes, not what is drawn. Three things it is not. It is not "open everything": reads, greps and command output stay folded, or they bury the diff. It is not keyed on the CALL's arguments alone — claude discloses its change there (`Edit`'s `old_string`/`new_string`, `Write`'s `content`) while an ACP agent discloses no arguments and returns `diffs` on the RESULT, so both sides are checked. And it is not seeded into `useState`, which reads its argument only at mount: a row mounts when the call streams in and its diff can arrive later, so the state is DERIVED with the user's own press layered over it as an override — the same shape as `TaskListCard`'s `latest`, for the same reason.

**The session picker searches EVERY profile at once, and searches them on the daemon** (`chats/session-search.ts`). A profile is an ACCOUNT, so asking only the composer's current config directory makes the other accounts' conversations absent with nothing saying so. The fan-out lives on THIS side because a profile is a directory recorded in `settings.json` (`configDirs` + `recentConfigDirs`, both keyed per CLI, and every named configuration in `configProfiles`), which the daemon never opens; each answer is COMPLETE for its own store. The CLI's own default (`null`) is always among them, and the rows are interleaved by WHEN, never grouped by account. **The profile is carried on the ROW**, and that is not a label: an id listed under one profile is not resumable under another, so `resumeSession` takes it from the row the user pressed. A profile that could not be read is NAMED in `partialReason` rather than dropped, and "this CLI cannot be asked" is shown only when nothing answered. The query itself is a question for the daemon (see `apps/daemon/AGENTS.md`) — no client-side filter — debounced by `SESSION_SEARCH_DEBOUNCE_MS` because the ask reads session files and, for cursor, spawns a process.

**A profile can be NAMED and COLOURED, and that list lives on the card of every CLI that can run under a config directory** (`settings/config-profiles.tsx`, `Settings.configProfiles`) — decided by each CLI's `configDirs[]` capability row rather than by name (not cursor's, whose row carries a reason: its config directory does not change the account). A `ConfigProfile` is `{ id, name, agent, dir, color }`: the DIRECTORY is the identity and the only field a run consumes, `agent` says which CLI's directory it is, and the name and colour are labelling over it — which is why two entries may not name one directory. A profile is offered to its own CLI ALONE, in every picker as on the card: a claude profile handed to codex as `CODEX_HOME` is a signed-out codex writing its files into the claude profile. The composer's current directory and its recents are per CLI for the same reason (`configDirs`, `recentConfigDirs`). It is rendered inside `AgentConfigList`'s `agentSettings[<cli>]`, the rule the agent options beside it follow, not as a Settings section of its own. Storage is a HAND-MANAGED list beside `runConfigs` and `fastActions`, through the same `salvageList` (entry-by-entry, unique ids, cap re-applied) — deliberately NOT folded into `recentConfigDirs`, an MRU of raw paths the app may re-sort, where these carry a name and a colour it must never evict. The COLOUR comes from the app's one palette (`components/ui/palette.ts`, the `--color-group-*` tokens the sidebar's groups use); `GROUP_DOT_CLASS` keeps its `Record<RunGroupColor, string>` TYPE in `chats/run-group.ts`, exhaustive over the generated union, so a colour added to the daemon's enum and missing from the palette fails type-checking. The palette's own union is spelled in `shared/contracts.ts` rather than derived from `RunGroupColor`: that file holds no daemon shapes, and a profile's colour never reaches the daemon.

**The COLOUR reaches the pickers, as a left border and nothing else.** `MenuItem.accent` carries a `ProfileColor` and `Menu` draws it as `border-l-2` from `PALETTE_BORDER_CLASS`, with the row's left padding pulled back by exactly the border's width so coloured and uncoloured labels stay aligned. A border rather than a second glyph: the row already leads with an icon saying what KIND of thing it is, an edge stripe costs the label no width, and it is how the sidebar draws a GROUP's colour. The row says BOTH, on two lines — the name, and the directory under it (`MenuItem.subLabel`); a colour is recognition, never a replacement for knowing which directory a row is, and an unnamed recent leads on its leaf. The shape is gated on the picker having a `named` group at all, so `FolderSelect` — which shares `DirectorySelect` and supplies no names — keeps its one-line rows, pinned by `chats/folder-select.spec.tsx`. `DirectorySelect` takes a map keyed by PATH rather than the configurations themselves — what a name or colour MEANS is the caller's.

**Where the name reaches**: both PICKERS — the new-thread one (`ConfigDirSelect` → `DirectorySelect`) and the in-thread one (`ModelSettingsSelect`), which offer the same directories and must describe them the same way. `ConfigDirSelect` always passes a `named` group, so every call site (the landing composer, the run-configuration editor, the graph builder's node inspector) draws the two-line row — an empty `configProfiles` means no NAMES, not a one-line shape. What the name does NOT reach: the composer's profile chip, the chat header's `Profile` row and the sidebar's rows, which name the config directory by PATH.

`session-picker` — the "Continue a session" dialog behind the sidebar's history control, which is a SEPARATE control from `+` on purpose: the `+` is a one-click new thread and must stay one, while this has a question attached to it. The saved run configurations hang off the `+` ITSELF (see *Run configurations*), which is a different question again — that menu picks a setup to start FROM, while this one picks a conversation to carry ON. TWO narrowing controls — which CLI, and free text (matched per-term by the DAEMON, across the title, the folder AND what was said) — is deliberately not three: a folder-scope filter was tried and removed, since it could only ever name the one folder the composer happened to point at, and the free-text search already matches paths across every folder at once. What that costs is that the row count cap (`SESSION_LIST_LIMIT`) becomes the only bound, so a listing that hits it now SAYS so in `partialReason` rather than passing a truncated list off as the whole. Each row states its path (elided from the front by the composer's own `shortenPath`, since CSS truncation eats the only end that identifies a directory) and the dialog is sized to fit one. Its agent is its OWN rather than the composer's, and the profiles it asks under are decided from that agent for the same reason: the composer's config directory belongs to whichever CLI the composer is pointed at, and sending a claude profile to cursor asked it to list conversations under a directory that is not its store — so `sessionProfiles` collapses to the CLI's own default for an agent that reads no config directory at all.

**Fast actions** (`chats/fast-action-bar.tsx` + `settings/fast-actions.tsx`, over `Settings.fastActions`) — the user's own buttons under the composer on the new-chat screen. One action is a NAME and a DESCRIPTION, and nothing else; pressing it writes the description into the message box. It sends nothing and it touches no chip, which is the whole feature: the same action works under whatever folder, agent and model the composer is already carrying, so one "review the diff and report findings" serves every repo.

An action never carries run setup (folder, branch, target, model, effort, approval mode, config directory) — it once did and was rejected: it made an action usable in one configuration and moved chips the user had just set by hand. Named new-chat setups are a separate feature, **Run configurations** (below). `chats/composer-values.ts` — `isChatApprovalMode`, `workflowSlugOf`, `targetAgentKind` — reads foreign strings from settings.json into the composer's own vocabulary, imported by `run-config.ts` rather than restated in it.

A press APPENDS to what is already in the box, separated by a blank line, rather than replacing it — the text there is the user's own typing, and a button that eats it is one nobody presses twice — and then puts the caret at the end. The caret is the reason the focus runs from an effect keyed on a press counter rather than inline: the textarea's DOM value is still the old one until React commits, so a `setSelectionRange` in the handler clamps to the wrong place.

The bar carries one more control, the SAME trip drawn two ways: alongside actions it is a ghost glyph; over an EMPTY set it is the bar's whole content, a muted `Add fast actions` spelled out in words — the new-chat screen is where a fast action is wanted, so the bar must not vanish until one is configured. The one case that draws nothing is a caller with no way to Settings (the harness). They are managed in **Settings → Fast actions** and nowhere else, a section of the Settings screen's left nav (`SettingsSection`). The editor is two fields, and the list re-reads whenever Chats becomes `active` again: the screen stays mounted across nav switches (that keeps its live room alive), so its one-shot settings read never runs twice, and an action added in Settings would otherwise not appear until the next launch.

The write path is `persistFastActions` in `Settings.tsx`, and it calls `window.geniro.updateSettings` DIRECTLY rather than the screen's own `persist` helper: that helper swallows a rejection into `setError`, so the rollback chained onto it could never fire, and the screen would keep listing an action settings.json does not have — after which every later save fails on the same entry, since the whole array is re-sent. The editor also refuses locally what the IPC schema would refuse anyway (empty name, empty description, over-long either, an entry past the cap), because that boundary throws on the WHOLE settings patch: without the guards the editor closes, the row shows from React state, and nothing is written. `readSettings` salvages the list ENTRY-BY-ENTRY (`salvageList`, shared with the run configurations) and re-applies the array cap there, for the reason it does with `cliPaths`: zod rejects an array wholesale on one bad element, and an action is hand-written and unrecoverable.

**Run configurations** (`chats/run-config.ts` + `chats/new-chat-button.tsx` + `chats/run-config-picker.tsx`, over `Settings.runConfigs`) — the user's named new-chat SETUPS: folder, branch, agent, model, effort, context window, model parameters, approval mode, config directory. Picking one seeds the new-chat screen and switches the folder's branch; it sends nothing and creates no run, so the user still writes the message.

**They are NOT fast actions, and the two must never be folded together again.** A configuration answers *where and with what does this chat run*; an action answers *what do I say*. Folding them once deleted the configurations — and, because dropping the settings key made the next settings write erase them, the user's saved configurations with them. **Dropping a settings key destroys the user's data**: `readSettings` keeps only keys the current schema knows and `writeSettings` rewrites the whole file. So a change that removes or renames a persisted settings key must migrate or export the data first — a code deletion is revertible from git, the user's data is not. The exceptions on record are under *Settings keys* below (the root `AGENTS.md`'s *Storage split* points there).

Two surfaces, ONE component and ONE key. `RunConfigPicker` renders as a Dialog off the chat sidebar's `+` (`NewChatButton` — a click is still the plain new thread; hovering opens the setups, plus `New configuration…` and `Manage configurations…`; a phone has no hover, so below `sm` a bookmark button beside the `+` opens the same menu), and with `asDialog={false}` the same list and editor are the Settings screen's **Run configurations** pane. `onApply` is what actually separates them and it is a real difference rather than a flag: the `+` is for USING a configuration so its rows start a chat, while the Settings pane is for KEEPING them and has no composer to seed — there its rows edit, and the accessible name says so rather than promising a launch.

Three things in the apply path are load-bearing. It builds the run from the APPLIED configuration and never from composer state, since the seeding it does first sets React state the same callback cannot see. It lands on the new-chat screen deliberately — that is the only view rendering both the seeded chips and the strip its branch refusal reports through. And a workflow target writes NONE of the per-CLI choices: those setters persist, `null` through them DELETES the remembered entry, so writing the blanks a workflow reports would erase the user's own claude model. The branch is a guarded `git switch` whose refusal is a partial success — the rest of the configuration still applied — so it reports in amber through `composerNotice` rather than as an error, and it offers no worktree redirect, because a configuration names a FOLDER as well as a branch and going elsewhere would run it where the user's own saved answer does not point.

**A question card's options are drawn from their ARITY, not from a single option style** (`components/ui/option-list.tsx`, driven by `approval-card`'s `optionArity`) — a pick-one and a pick-many card must not look identical. `many` is a checklist (square boxes, **stacked in a column**, since a checklist is read down its boxes); `one` is a radio list (round dots, **also one per line**). Those two carry no frame and no tinted fill — the indicator says "pickable" and, filled, "picked"; unframed options side by side run together as one ragged line. `none` — the answer-on-click card, one question taking one pick, where the press IS the submission — is framed buttons in a wrapping flow, the only arity that keeps an outline and shares a line, with **no indicator at all** (an empty box would promise a confirm step that does not exist) and a warning that the verdict is one-shot. The unchecked box is `border-muted-foreground/50`, NOT `border-input`, which vanishes at 16px against the page. They stay toggle `<button>`s rather than `role="radio"`/`role="checkbox"` — an ARIA radio group promises arrow-key navigation and a single tab stop, and a half-built one is worse than an honest list of buttons — so the arity reaches a screen reader through the group's own accessible name. Not built on `chip`, which is `whitespace-nowrap` by design, while an option label is routinely a full sentence. **An option's `preview` is drawn under the QUESTION and above the options** (`OptionPreviews`), on the open card as on the settled one: a preview is the explanation the choice rests on, read before choosing.

**The CONVERSATION TIMELINE is a VERTICAL timeline behind an icon in the AGENTS PANEL** (`chats/conversation-timeline.tsx`, fed by `chats/use-chat-timeline.ts` over `GET /v1/chats/:runId/timeline`). One node per user message, top to bottom in the transcript's own order, with that message beside each dot and — along the line running down to the next dot — what happened in between: the agent messages, the elapsed time, the tokens, the cost. Clicking a node calls `useTranscriptJump.jumpToSeq` and CLOSES the panel: the answer is the place, and a panel left open stands in front of the row it just landed on. `jumpToSeq` is reused as is, which is what makes a node older than the loaded window work at all, since that hook fetches the page around an off-screen seq before revealing it.

A horizontal strip above the transcript was rejected — it has one line of room for a message's words and shrinks the transcript on every thread; do not reintroduce it. The DAEMON half (route, fold, figures) is independent of the shape, which is the argument for keeping the fold there rather than in the component.

The trigger sits in the AGENTS PANEL's own control row, beside search, never in the chat header. That row also holds the other controls that act on the whole thread (its folder's terminal, its export), so they are one group; the header is readings alone. **Both are drawn on the FOLDED RAIL as well**, which is the load-bearing half: a panel that dropped them when it folded would put the only way to search or navigate a conversation behind unfolding a column first — the same rule, and the same spec shape, the terminal control already had. The panel takes the timeline as DATA rather than as a node: it draws the control twice at two sizes, so a pre-composed node could only be right in one of them, and how big a control in that column is is the column's own business. It is OMITTED, never disabled, when the thread has no user message.

Three things about the data are load-bearing. The nodes come from the DAEMON and never from `items`: a long chat opens on its newest `HISTORY_PAGE` items, so a local fold would draw the tail of a conversation and present it as the whole of it. It refreshes on three triggers, because three different things move it and none covers the others — `settledTurns` for a turn ENDING (when a stretch's spend stops changing), the newest loaded user `seq` for a message being SENT (without which the message currently being answered is missing for the whole of the turn, which is when someone looks), and the newest loaded agent `message`/`reasoning` `seq` for the work IN BETWEEN (a long turn moves neither of the first two). All three are monotonic within a thread and none moves when older history pages in, so scrolling up costs no fetch; the third fires once per paragraph the agent writes, never per token. Between reads the in-progress stretch's clock is the client's own (`now − createdAt`, never below the daemon's figure), since the daemon's elapsed time stops at the last row it read. And it is MEMOIZED like every other many-row component on this surface: `Chats` re-renders on every streamed token and this list is whole-thread by design.

**The NEWEST node is marked while the run works** (`inProgress`, from `isWorkingRunStatus(activeRunStatus)` — the reading the header's own `live` controls take): its dot is the accent with a pulse behind it and every finished stretch's dot is muted, so the stretch still being written does not read like one that is over.

The count on a segment is every non-user `message` AND every `reasoning` row in that stretch: the italic blocks the transcript draws between tool calls are `reasoning` rows, so counting `message` alone describes something other than what is on screen. **A delegate's output is included** — what separates a delegate's message from the main thread's is `payload.parentToolUseId`, and the daemon's spine projection deliberately carries no payload, so the exclusion every sibling fold applies is unreachable here without paying for the text column. It is answered by the WORDING rather than by a filter: a node says `3 messages` and never `3 replies`, and the hover detail says `sub-agents included`. A capped timeline also SAYS so, in the daemon's own sentence (`partialReason`), at the top — the end the conversation continues from.

It is a NAVIGATION surface and deliberately not a restatement of the rows beneath it (a timeline repeating the entries directly below itself was removed from `subagent-block.tsx` — do not reintroduce one): it is behind a control, it holds the WHOLE thread rather than the rows next to it, and its figures exist nowhere else on screen. A figure nothing measured is OMITTED rather than drawn as a zero, the daemon's own null-means-not-measured rule reaching the screen: a `$0.00` here would be a claim about money no CLI ever made.

`use-chat-run.ts` — the chat screen's run lifecycle, extracted out of `Chats.tsx`: the run list, which thread is open, the sidebar's `run_status` handling, and the join/leave of the open thread. **The per-run stream lives in `chats/use-run-stream.ts`, and the chat screen and the workflow dock both use it**: the rows and anchors of the window, the live-text plane, the expiry of requests, and the socket's reconnect replay. Each surface passes its own callbacks for what is particular to it — the sidebar row, the queue and the streaming flag here; the turn count and the run re-read in the dock — so one set of rules decides how a run's rows are merged, replayed and expired. The run-row fields a `run_status` announce sets the same way on both surfaces — status, awaiting, the hold, the two clocks and the task list — are read by one function, `chats/run-status-row.ts`. What each surface DRAWS from a run is shared the same way: the durable fold (`useDurableTranscript`), the ring's bookkeeping (`useContextRing`) and the metrics loader (`useChatMetricsLoader`) are each one hook both call, and the dock hands its transcript values to `ChatProviders` in one `transcript` object. The MESSAGE QUEUE is shared too (`chats/use-message-queue.ts`): the order, the pause, Send-now and the RUN_BUSY backoff are one set of rules, each surface supplying its turn start and firing the drain on its own turn ending. Only the chat screen keeps its queues across a reload — the store is one key, and two surfaces restoring it would each drain the other's runs. The dock drains only after the canvas has re-read what the turn wrote, because its send flushes the canvas first. **The `joinRun`/`leaveRun` pair of the open thread lives here, in `activateRun` and `deactivateRun`**, both halves — the activation swap AND the leave on run switch or delete — because ownership split across two files is how one of them comes to be missed. `use-chat-run.spec.tsx` drives it through a probe component against a fake client; the stream's own rules are pinned through both consumers' specs.

**The status vocabulary, in one table.** `RunStatusKind` (`chats/run-status.tsx`) is the ONE vocabulary every surface draws in — the sidebar row, the chat header, the agents panel's cards and thread rows, and every transcript block — and `RUN_STATUS_META` is the one glyph/tone/word for each of its members:

| kind | word on screen | glyph | what produced it |
| --- | --- | --- | --- |
| `pending` | pending | clock | the daemon's own column: the run exists, its first turn has not started |
| `running` | running | spinner | the agent is working — a live turn, or a delegate still producing rows, or the row says so |
| `held` | working | hourglass, **not** spinning | the daemon raised `turn_held`: the agent has said its piece and the process is alive only until the SUB-AGENTS it launched report back (`holdingFor > 0`) |
| `needs-input` | needs more info | question mark, warning-toned | an approval or question card is open (`run.awaiting`) — the one state that cannot advance without a human |
| `completed` | completed | check | the daemon's terminal status |
| `failed` | failed | ✗ | the daemon's terminal status |
| `cancelled` | cancelled | ⊘ | Stop, or a run that ended before the work finished |
| `skipped` | skipped | ⊖ | a workflow NODE only: something upstream of it failed |

The daemon persists only five of these (`RUN_STATUSES` in `runs.types.ts`, plus `skipped` for a node). `held` and `needs-input` are DERIVED here and never stored, which is why no run row ever carries them.

**No `idle`** — `pending` covers a node that has not started (it is what the node's own `node_state` row says), so `displayStatus` answers `pending` on both arms. Every other member is reachable, and no two describe one fact.

`displayRunStatus` decides between them in a fixed order, first match wins: **(1)** a card is open → `needs-input`; **(2)** the row says `failed`/`cancelled` → that, never overridden; **(3)** the run is held → `held`; **(4)** a delegate is still producing rows → `running`; **(5)** a live turn is streaming → `running`; **(6)** over a `completed` row, a background command or a background SUB-AGENT is still out → `held`; **(7)** otherwise the row.

**Rank 4 and rank 6 are two different delegates, and splitting them is what keeps both the badge and the notification honest.** A delegate WRITING rows is the run `running` — that is work happening, whatever the stale row says. One the CLI merely DECLARED out and has said nothing about since is `held`: the agent has stopped speaking, so a spinner would claim work it is doing. Cursor's background delegates are permanently the second kind (their steps never reach this wire at all), so collapsing the two put `running` over a finished agent AND swallowed its turn-end banner, since the notification rules fire on the transition into a settled status. Rank 6 is therefore withheld from `agentRunStatus`, the reading those rules watch, exactly as the background-command clause already was. `subagentSpokeSince` (`transcript-groups.ts`) is what separates them; it decides nothing about the WORK, which the daemon states (see *A background delegate's ending* in `apps/daemon/AGENTS.md`).

Rank 6's sub-agent half is **row-carried** (`RunDto.subagentsOut`, kept current by the `run_status` announce), like the shells beside it and for the identical reason: folded out of the OPEN thread's transcript it is knowable for one chat and no other, so the badge changed when the user looked away. `isWorkingRunStatus` is `running || held` and `isSettledRunStatus` is the four terminal ones — `pending`, `needs-input` and `held` are all states a run has yet to leave.

Two facts the table pins. **A detached shell does not hold a turn**: only a `background_work` unit of kind `agent` keeps a turn open (`spawn-cli.ts`'s `trackBackgroundWork`; claude distinguishes `task_type: local_agent` from the `local_bash` a delegate then runs), so a backgrounded command leaves its turn `completed` with the command still listed and running. **And an agent's own work IS `running`** — ranks 4 and 5 above. The hourglass appears only after the agent has stopped speaking, and its word is `working` rather than `waiting`; it deliberately does not spin, because that state can last many minutes.

**One state, one word — a block's lifecycle is translated, never printed.** `BlockStatus` (`block-shell.tsx`) is the transcript fold's own model (`running`/`done`/`error`/`stopped`) and never reaches the screen verbatim (a Stop-cut delegate must not read `error` beside surfaces reading `cancelled`): `RUN_STATUS_OF` translates both the GLYPH and the WORD, in both places one is written: the pill (`failed`, `cancelled`) and the `sr-only` span that carries the status for a screen reader when the mark is a glyph (`completed`). The kind is `held`, not `waiting`: that word already belongs to the sentence under a `needs-input` badge (`waiting for your answer`) and the sign-in flow's own `CliLoginStatus`.

**A settle no terminal item stands behind is flagged by the daemon** (`RunStatusEvent.noTerminalItem`). The open thread's working state is normally ended by its terminal ITEM, which lands before the settle announce — so a bare `completed` announce is not believed on its own (it may be stale). A lease expiring, the CLI session closing under an off-turn run, a woken workflow run settling, and a send that fails while a window shows the run working write no such row; their announce carries the flag, and `use-chat-run.ts` ends `streaming` on it and drains the queue (unless the settle is a Stop).

`settled-status.ts` — the ONE reading of "which run status does this terminal item imply", and the rule that goes with it: **only a LIVE terminal item mirrors its status onto the run row**, while a REPLAY takes one reading from its LAST item (`reconcileFromTail`). Every chat past its first turn replays a `turn_complete`, so mirroring each replayed row would write a past turn's ending onto a working run — and the next activation would read the row as settled and leave `streaming` false, taking the transcript's live row with it. The two live rows' clocks follow the same principle — both count from a timestamp derived from durable rows (`ChatHeader`'s `turnStartedAt`, the working row's `workingSince` from the last row its own thread put on screen, the thinking row's daemon-published `thinkingSince`), never from their own mount, or every remount restarts them. **A `turn_complete` the daemon stamped `insideTurn` is not a terminal item at all**: it is a background task's continuation finishing while the user's own turn was still owed its answer, so it ended nothing and the daemon writes no status for it; never mirror it (it would mark a working thread `completed` until the real ending).

**A null activity means "working, nothing named" — and BOTH surfaces have to read it that way** (`run-status.tsx` `STANDING_ACTIVITY`). The daemon announces `running Bash` on a tool call and null on its result (its `idleActivity`: "null leaves the run's own Working… standing"). The transcript's live row and the sidebar row both fall back to the ONE constant on null — a row gated on the phrase existing blanks out every time a tool returns, so the status blinks — and a second literal is how the two would come to disagree again. It applies only while the badge says `running`: a settled row showing it would claim the run was still going.

**The live plane's KEY for a 1:1 chat is the sentinel, never the owner key the daemon sends** (`chats/live-text.ts` `liveTextKey`). The daemon publishes `SINGLE_AGENT_NODE` — the literal `agent`, the pseudo-node a chat's rows are filed under — as the owner of a chat's live plane, while this side's sentinel is `CHAT_LIVE_KEY`, deliberately not that word, so a workflow node named `agent` cannot collide with it. Every reader with no event to derive a key from (`workingAgents`, `awaitingAnswer`, the context meter's live source) asks for the sentinel, and `withLiveText` suppresses the working fallback BY KEY, so keying deltas by the owner key draws `Thinking…` and `Working…` at once — and compiles fine (this file's TWIN PARSER block warns about exactly that). The discriminator is the NODE ID: a workflow node's delta always carries its id (`GraphExecutorService` passes `node.id`) while a chat's never does.

**`ThinkingRow` has TWO shapes, and which one it takes is a fact about the CLI, not a style choice** (`live-row.tsx`, fed by `LiveState.thinkingText`). With TEXT (cursor streams its reasoning; see `apps/daemon/AGENTS.md` for the live channel) the row is the same muted italic `reasoning` bubble the durable item becomes, so the words watched and the words that land are rendered one way, plus a spinner-and-clock line — without it a stretch that goes quiet is indistinguishable from one that finished. With NO text it is the one-line note `Thinking… 250 tokens`, all headless claude can offer since it redacts the block; the token count is never printed alongside the words, because the CLI that sends words reports no count and `0 tokens` is a figure nobody measured.

**A card being WRITTEN gets a placeholder shaped like the card that is coming** (`chats/composing-card.tsx`, the `composing` live row in `live-row.tsx`, fed by `RunDeltaEvent.composingTool` / `.composingBytes`). A host tool's ARGUMENT is its deliverable — `show_artifact` carries a whole HTML document — so the model spends the longest stretch of the turn serializing one, and the raw tool row is hidden by design (`chats/geniro-tool.ts`); the daemon's `tool_compose` channel makes the wait visible (see `apps/daemon/AGENTS.md`). It is a SKELETON of the card rather than a spinner, and the kind is the point — a page frame says an artifact is coming and will take a while, a row of tiles says a scorecard is seconds away. It draws only BOXES: a placeholder with invented numbers or lorem text would be indistinguishable from a real card. It carries the BYTES written rather than a clock (the work climbing is the only thing that tells a model still producing from one that stopped) and deliberately no progress bar, the final size being unknowable. **The words that introduced it stay on screen** — the row is attached AFTER the live text rather than instead of it. A kind this build does not recognise draws NOTHING rather than a generic box. `chats/geniro-tool.ts` is the one place tool names are matched: the fold hides a call that has already happened and this draws one still being written, and a second copy of the rule is how one of them would come to recognise a tool the other does not.

**The live rows are LEFT-ALIGNED, and their word ROTATES** (`MessageBubble`'s `live` variant; `chats/live-words.ts`). They are the agent's column still filling and are followed by the bubble they turn into, so they never wear the centred `note` chrome. A long wait in one fixed word reads as a frozen screen, so each row draws from a vocabulary (`THINKING_WORDS`, `WORKING_WORDS`, `COMPOSING_WORDS`), with three rules. **The FIRST word of every list is the plain one** — a row opens on `Thinking` / `Working` and only wanders once the wait is worth entertaining, so a short turn reads plainly and the status vocabulary stays honest (`WORKING_WORDS[0]` is TWINNED with `run-status.tsx`'s `STANDING_ACTIVITY`, pinned by `live-words.spec.ts`). **It is only ever the FALLBACK**: when the daemon says `running Bash` that phrase wins. And **each row takes its own PHASE as well as its own offset** — rows mount in one commit, so a shared period would change every word on the page (and play its 260ms fade) at the same instant. `prefers-reduced-motion` freezes all of it, the rule `.title-naming` already follows.

**A reasoning stretch is BOUNDED while it is written and FOLDED once it is not** (`chats/thinking-block.tsx` — `ThinkingScroller`, `ThinkingDisclosure`). LIVE it is capped at 300px and scrolls inside itself, pinned to the newest words. The follow gives way to the reader on the transcript's own rule (`nextFollowState`), never on "am I at the bottom" alone: growing content pushes the bottom away without anybody touching it, and reading that as intent would switch the follow off while streaming. FINISHED, the row folds behind its own first line — the only summary available that says what the agent was thinking ABOUT, the durable payload carrying the text and nothing else. A SHORT stretch is left unfolded. The fold is ONE component used by both durable renderings, which draw the body differently (the standalone bubble verbatim, a turn block as markdown) — hence `children` rather than a `text` the component renders.

**A delegate is named by its identity when nothing named it, and its launching call's reply is not its report** (`transcript-groups.ts` — `subagentTitle`, `subagentNamed`, `SubagentBlockEntry.resultIsOwn`). Three rules:

- **The generic title is the id's own tail** (`Sub-agent HvcbzU`), never a constant: only the launching call carries a description, so a delegate whose launch is outside the loaded window arrives with none, and the daemon's `subagent_info` declarations carry no `label`/`kind` to cover for it. The tail distinguishes rows and is honest about being an identity rather than a name. `subagentNamed` lets the dialog drop its `Sub-agent · ` prefix where the title already opens with it.
- **A launch acknowledgement is not the delegate's result.** A backgrounded delegate's call is answered within the second (claude's `Async agent launched successfully. …`) while the work runs on. `resultIsOwn` decides it STRUCTURALLY — did the delegate speak after its call was answered, and is its background unit still open — never by matching that sentence, which is one CLI's prose. The text is still shown, under `Reply to the launching call`, never under `RESULT FROM <name>`. For the same reason `This sub-agent has not done anything yet.` must not be gated on `returned || result !== null`, both of which an acknowledgement sets.
- **A `SendMessage` is not a delegation.** The daemon announces background work against the call that opened a unit, and resuming an already-running agent opens one — the phantom `spawn-cli.ts`'s own comment warns about. A launch admitted ONLY by that declaration, whose declaration describes nothing, contributes no block and no result: only the tool NAME (`isAgentToolName`) or a declaration that actually briefs the delegate (cursor's ACP path, whose frame carries no usable name) is evidence that the call was a delegation.

**A run settling is a MOMENT, not a flag** (`RunSettledContext` → `RunSettleAt`, read by `subagentBlockStatus`): a delegate that has produced rows SINCE the run row settled is still working, whatever that row says, so the settle only closes blocks whose last row precedes it (a bare boolean would paint every unreturned delegate `stopped` while it keeps working). Three states, not two: a settle whose timestamp will not parse is `'unknown'`, which keeps the conservative reading rather than putting every spinner back. The seq-based `SubagentBlockEntry.closed` outranks it — a turn-end ITEM after the delegate's last row is direct evidence that nothing more is coming. A tool group asks only `!== null`, since a tool call is one round trip and `pair.result` already answers "has it spoken since".

A code-review findings report the agent handed the APP to draw: `findings-payload.ts` — the twin parser, with NO fold, because a report arrives whole where a task list arrives as patches; `findings-block.tsx` — the `FindingsCard` the transcript shows, findings grouped under their file in the order the agent sent them (it was told most-severe first, so re-sorting would throw away the only ranking anybody has), a Confirmed / Plausible badge per row and the long half — the defect sentence and its failure scenario — behind a per-row disclosure. Two reports are two CARDS rather than one that rewrites itself: an agent that re-reports after fixing its findings is taking a step in the conversation, not correcting the card a reader has already scrolled past. The card carries no jump-to-file and no action buttons yet — both need surfaces the renderer does not have (an editor-open IPC, and a transcript block able to compose a new turn).

A CHART the agent handed the app to plot: `chart-payload.ts` — the twin parser, again with no fold; `chart-block.tsx` — the `ChartCard`, built on the **Stats page's own chart theme** (`stats/charts/chart-theme.tsx` → `categoryToken`, `AXIS`, `CHART_MARGIN`, `ChartTooltip`, `SeriesLegend`) rather than a second one, because a plot in a transcript and a plot on the Stats page are the same object drawn in two places. The parser's whole job is the POSITIONAL contract: series values are matched to `labels` BY INDEX, so it blanks an unreadable label instead of removing it and re-aligns every series to the label count — over rows written by older builds as much as new ones. `chartRows` then transposes into recharts' row-per-x shape keyed by POSITION (`s0`, `s1`, …), never by series name: a series legitimately named `x` would otherwise overwrite the axis column, and two series sharing a name — which a model does send, e.g. `p95` for two runs — would collapse into one curve. A `null` stays a gap (`connectNulls={false}`, and the tooltip SAYS unmeasured) because the alternative reading is a zero nobody measured. Plot height is fixed and small: it sits between two paragraphs of a conversation. The spec asserts only the chrome — heading, captions, legend, disclosure — since `ResponsiveContainer` measures 0×0 in jsdom, the same limit `stats/charts/time-charts.spec.ts` already records; it stubs `ResizeObserver`, which jsdom does not ship and recharts throws without.

A SCORECARD: `metrics-payload.ts` — the twin parser, again with no fold; `metrics-block.tsx` — the `MetricsCard`, a responsive grid of figures, ONE TILE each rather than columns in a shared box (columns have no edge to align against, so a figure carrying a note makes the row read as broken). Four decisions in it. It is **NOT behind a disclosure**, unlike the chart: a scorecard is two lines of large text read at a glance. The delta is coloured **by the stated sentiment, never by the sign** — `+4 pts` of coverage is good and `+90ms` of latency is bad (pinned). The parser resolves an absent or unknown sentiment to `neutral` so nothing downstream repeats the fallback, and it never coerces a number into a value (see the daemon's own note). The grid is `auto-fit`/`minmax` rather than a fixed column count, since the transcript narrows with the side panel; its track is **11rem**, what fits a figure AND its delta pill on one line. The note sits directly under its figure in normal flow, NOT pinned to the bottom of the stretched tile (one long note would float every other note away from its number). A tile label is **sentence case**, not the section caption's uppercase, so the two levels of hierarchy stay distinct.

A COMPARISON: `comparison-payload.ts` — the twin parser, which additionally resolves `recommendedIndex` (matched to a column BY NAME, case- and whitespace-insensitively, since `sqlite` in the recommendation and `SQLite` in the options agree); `comparison-block.tsx` — the `ComparisonCard`, options across the top and criteria down the side. It has to beat a markdown table, so it is built around what a table cannot hold. The verdict tint is on the **cell**, not on a glyph inside it — colour has to be the largest thing the eye gets. Neutral is UNtinted, not grey-tinted, so the two real verdicts keep their contrast. The recommendation marks its column at the head AND states its reason at the foot. An empty cell draws an em dash (a blank reads as a rendering failure). The table scrolls horizontally inside its own container, per the repo's wide-content rule, which is also why the option count is capped.

A GALLERY: `gallery-payload.ts` — the twin parser, which also accepts the bare-string and `src` entry forms for twin PARITY (a twin that accepts less than its writer can produce disagrees with it), though the daemon normalizes every entry before the row is written; `gallery-block.tsx` — the `GalleryCard`, a thumbnail grid whose tiles open the app's ONE image surface with prev/next wired up. It is the only card whose payload names FILES rather than carrying its own content. Each path is resolved through `LocalImageLoaderContext` (`chats/local-image-loader.ts`) — the same loader and token-gated route a markdown image uses — never a second fetch path. Loading is SEQUENTIAL and only while the card is open, and the resolved map is RELEASED when the card folds away: each picture is a `data:` URL held in memory (no thumbnail endpoint; the daemon's per-image ceiling is 20MB) and an unvirtualized transcript can hold several galleries. Reopening reads them again — bounded memory over a second round trip — and the spec pins the release by counting those reads. The FIRST scheme door is the shared `refusalFor` in `local-image-loader.ts`, the POLICY on what that loader may be asked for, so a remote path is refused here with its own sentence. A picture that could not be read is ONE dead tile saying so, never a dead card; with no loader in context every tile says that too rather than reading "loading…" for good. The grid is `auto-fill` with a floor, on the scorecard's reasoning. **It does NOT bring a lightbox of its own** — the prev/next arrows, the `3 of 8` readout and the arrow keys are optional props on `components/ui/image-viewer.tsx`, so the modal contract, portal, focus trap and zoom stay in one place. Stepping between pictures re-KEYS the zoom wrapper on the source, or each picture inherits the previous one's scale and offset. The arrows are withheld at the ends rather than wrapping, so a reader does not lose their place.

A DYNAMIC WORKFLOW card is the only one built from something other than a single row: `workflow-payload.ts` — the twin parser and the last-non-null merge, whose one deviation is that the agent ROSTER is taken WHOLE rather than merged, because the CLI re-sends the entire roster every time and index-merging two snapshots would resurrect an agent a later one dropped; `transcript-groups.ts`'s `buildWorkflowCards`, which runs after `buildSubagentBlocks` and pulls the launching tool pair OUT of its group exactly as a `Task` pair is pulled; and `workflow-block.tsx` — the `WorkflowCard`, collapsible and shut to start, whose HEADER carries the whole answer (`28 agents · 3 running · 1.2M tokens · 20m 34s`) and whose body opens onto the roster, phase-captioned, one row per agent with its model and what it spent. A CARD and not a block because a workflow's agents emit NOTHING onto this stream — there is a roster, not a conversation. A launch is recognised ONE way, by a `workflow_info` row naming the call, never by the tool's NAME: which calls launched a workflow is the adapter layer's fact, stated on the wire, so a second CLI growing an orchestrator is a daemon change alone. The header's clock counts from the launching call rather than from the CLI's own `duration_ms`, which rides the last roster sent and freezes between announcements. The rows are skipped OUTRIGHT in `groupTranscript`, beside `shell_info`: they render nothing there and land dozens of times mid-turn, so treated as the node "saying something" they would chop one turn's tools into one-call rows. `workflowCardsOf` is exported because a RUNNING workflow also gets a chip on the composer shelf (`composer-shelf.tsx`'s `ActiveWorkflowChips`, AFTER the pull-request chip so starting a workflow does not shift the durable chip) and a row in the side panel's `Workflows` section; pressing either takes the reader to the card (`Chats.tsx`'s `revealWorkflow`, arithmetic on the transcript scroller's own `scrollTop`, because `scrollIntoView` moves every scrollable ancestor and `revealWithinBox`'s `offsetTop` is measured against whichever ancestor is positioned). Three surfaces, ONE fold — a chip counting its own agents would drift from the card. The chip is drawn only while the workflow runs; the panel lists every one the run launched, newest first, and its row carries no running COUNT (the row is narrow and the spinner beside the name already says it). Both read `RunSettledContext` from the screen-wide `ChatProviders` the chat screen wraps around its whole tree, since each is a sibling of the transcript.

An ARTIFACT is the family's PAGE, and the only card whose body this app does not draw: `published-artifact.ts` — the twin parser plus `artifactPageUrl` (the query shape is half the wire contract; the host and port are `daemonBaseUrl`'s and are not re-derived) and `ArtifactUrlContext`, a context for `LocalImageLoaderContext`'s reason, every shell between `Chats` and a transcript row being memoized; `artifact-frame.tsx` — the frame itself; `artifact-block.tsx` — the transcript card; `artifact-dialog.tsx` — the full-screen popup; `use-run-artifacts.ts` — the panel's list. **The page is FRAMED, never inlined, and the sandbox is the whole security story.** `sandbox="allow-scripts"` WITHOUT `allow-same-origin` puts the agent's document in an OPAQUE origin — no reach into this app's DOM, its storage or the loopback token the renderer holds — and the document is SERVED by the daemon rather than put in an `<iframe srcdoc>`, because a srcdoc document INHERITS the embedder's CSP and this renderer's carries no `script-src`, so the agent's script would never run. `index.html`'s own policy has `frame-src 'self' http://127.0.0.1:*` for it — loopback for the window, `'self'` for a phone, where the daemon is reached through the gateway's (or a tunnel's) own origin — and the frame carries `referrerPolicy="no-referrer"`. **Two things cross that boundary and both are `postMessage`.** The host sends the resolved THEME tokens, read off the live document so the page is painted in the app's current theme, and the page reports its own HEIGHT, which is how an inline card sizes itself up to `MAX_INLINE_HEIGHT`. Each listener filters on `event.source` (the frame's own `contentWindow` one way, `parent` the other), since an opaque origin cannot be checked by origin string; the height report dedupes on the last value, or a page whose layout settles in steps emits a message per frame. **The frame is KEYED by `${artifactId}:${version}`**, so a republish remounts it rather than re-pointing a live one — a card silently showing the previous version of a revised page is the failure this feature exists to prevent. **The transcript card opens itself only for the NEWEST version of its id** (`open = override ?? latest`, over `useThreadOverride`): every version keeps its row, since each opens the page it announced, and a thread that revised a plan several times would otherwise mount every version live. The reader's press outranks that default and is remembered per thread. **And the PANEL's list comes from the DAEMON, never from a fold over `items`** (`useRunArtifacts` → `GET /v1/chats/:runId/artifacts`): a long thread opens on its newest `HISTORY_PAGE` items, so a local fold drops a page published earlier, and the panel is a page's only stable entry point once its card has scrolled away. ONE refresh trigger: nothing about a published page changes until it is republished, which writes another row, so the newest `show_artifact` seq covers every way the list can move. The hook carries the run it was read from and answers empty on a mismatch, or a thread switch lists the previous conversation's pages under the new thread's name. **And a page SAVES as one file** (`artifact-save.tsx` → `artifact-export.ts` → `GeniroApi.saveArtifact` → `main/save-artifact.ts`). It is one file by CONSTRUCTION: the page is served under a CSP whose only external subresources are libraries from a fixed list of public CDNs, so everything of its own it draws is already inside it. A page that loads a library needs the network to draw, saved or framed — the user's trade, made so pages can use ECharts, Mermaid or Tailwind. The raw reading carries the page RUNTIME (`geniro.chart` and the component kit, `apps/daemon/src/v1/agents/utils/artifact-runtime.ts`), since the agent's script calls it. What the renderer adds to the stored document is the THEME and the page's own POLICY: a file opened by a double-click has no host to hand it `--geniro-*` values, so the current theme's are baked in as a static `:root` block; and the daemon's `default-src 'none'` CSP is restated as a `<meta http-equiv>` (`ARTIFACT_FILE_CSP`, a twin of `artifact-page.ts` whose spec reads the daemon file so the two cannot drift), because a saved file loses the response header and could otherwise reach anything from a browser. The document is PARSED (`DOMParser`) and the charset, the policy and the theme are put at the START of its real `<head>` — never spliced before the first `</head>` in the text, which can sit inside a script — so the file is re-serialized, with a doctype, and the theme is a base the page's own styles override. `THEME_TOKENS` lives in `artifact-theme.ts`, shared by the frame and the export, so a saved page is themed like the one on screen; ONE saver serves both controls (the transcript heading's and the dialog's), since they are one act on one document. A CANCELLED panel leaves no trace, on `FileSaveResult`'s rule.

**A link in the page is the host's to open, never the frame's.** The frame's sandbox is `allow-scripts` alone, so nothing inside it can open a window. The wrapper script relays a click on an `<a href>` or `<area href>` to the host (a same-page `#anchor` still scrolls in place), which opens it in the user's browser at once (`linkToOpen`, then `window.open`) — no confirmation, by the user's decision, so the scheme is the only bound: a page's own script can post a link without a click, and it opens. Only `http:`, `https:` and `mailto:` are opened (`shared/link-schemes.ts`, read by both processes). The main process's `guardArtifactFrameNavigations` cancels any navigation of the frame away from the artifact's own route (a frame navigating itself to an external host blanks the card).

`isCardEntry` in **`transcript-groups.ts`** is the ONE predicate every reader of card entries goes through (entry owner, thread, `seq` fold, `lastRowAt`, tool count, the live-tail scan) — never spell a `'task-list' || 'findings' || …` chain, where a missed kind fails SILENTLY (a card left out of the `lastRowAt` fold just stops a spinner noticing work). Its union and its predicate must list the SAME kinds, which the compiler enforces, as it does the exhaustive `Record<CardEntry['type'], …>` maps (`entry-card.tsx`, `subagent-block.tsx`) and the render arms (`transcript-entry.tsx`, `turn-block.tsx`). `GENIRO_TOOL_NAMES` — the list that HIDES a host tool's own call row — is a plain string array the compiler cannot check: a card tool added to the daemon belongs in `GENIRO_TOOL_NAMES` as well as in the union.

**Each agent card also says what that agent has DONE — worked time and tool count, on their own line under the spend** (`agents-panel.tsx`'s `AgentSpend`, fed by `Chats.tsx`'s `workByAgent` side map, keyed by `AgentDisplay.id` exactly as `shellsByAgent` is) — what it COST and what it DID are two lines, not one list of four. The figures are DURABLE for BOTH run kinds, split as `contextTokens` is: a workflow node's on `node_state`, a 1:1 chat's on the RUN itself (`Run.workedMs` / `toolCalls`, written by `ChatService` at its own `turn_complete` and riding `RunWire`). The transcript fold stays underneath as the first-turn answer; alone, past `HISTORY_PAGE` items it would describe the loaded window rather than the conversation. Nothing refreshes a run row between full listings, so the SETTLE announce carries both figures (`RunStatusEvent.workedMs` / `.toolCalls`, read back by `writeRunStatus` and patched in `onRunStatus`) — the road `taskList` travels; on a settle alone (the only moment they change), and omitted when BOTH are null, which keeps every workflow run — whose figures live per node — off the field. The durable figure REPLACES the fold wherever it exists, and what the turn in flight has done is added on top — its time by each card (`openTurns`), its tool calls in `workByAgent` from the window's rows since that turn began. A NON-POSITIVE figure is not a measurement (`measured()`, the renderer twin of the daemon's `positive()`) — a zero draws no line, as on the spend line. The live half comes from `scanTurns`' open turns, which carry an `agentKey` so a fan-out's concurrent turns are separable, and both the header and the cards read ONE guarded list (`openTurnsShown` in `Chats.tsx`): `parkWhileHeld` applied, and withheld entirely on a settled run, or a card would out-count the header through a hold and a daemon that died mid-turn would leave every card ticking.

**A 1:1 chat's card states its SPEND from the daemon's thread totals** (`useChatTotals` → `GET /v1/chats/:runId/totals`, the same read the header's cost comes from and the figures the context readout's `This thread` line prints) — never a sum of the loaded transcript's `turn_complete` rows, which past `HISTORY_PAGE` items loses the oldest turns. The fold stays underneath for the moment before the totals read lands. A WORKFLOW node's card, each of its instances, and every call card read the same way off the nodes route (`GET /v1/workflows/runs/:runId/nodes`): the daemon sums every `turn_complete` the run wrote into `totals` (the node), `mainTotals` (its own conversation) and `calls[].totals` (each call, summed across a continued conversation by `resolveConversationSpend`), and the window's fold is only the fallback before that read lands. The route is re-read each time a turn settles. **What a turn still RUNNING has spent is added on top** (`withLiveCost` in `chats/call-context.ts`, over the live plane's `spentCostUsd`), since the recorded figures move only when a turn ENDS. The daemon's claude driver asks the CLI's own ledger (`get_usage`, the accumulator every `result` line's `total_cost_usd` is built from) what it has spent since its last `result`, and publishes 0 at that `result` ahead of the `turn_complete` that records the same money, so the sum never counts a dollar twice. The call card, each instance, each node card and the header all add it; cursor publishes none. A call card states its callee's OWN turns, not the nested calls drawn inside it. The ring's `604.9k of 1M` is a different quantity: what the context window holds right now, not what the thread has spent.

**A workflow node's LIVENESS falls back to its `node_state` row when the window holds none of its status history** (`withDurableNodeStatus` in `agent-activity.ts`, `withDurableOpenTurns` in `turn-duration.ts`, both fed by `useNodeDurableReadings`, which keeps `status` and `startedAt`). Both the card's status and the turn's open clock are read off `status` rows, and a node working one turn longer than `HISTORY_PAGE` items has its `running` row above the page (it would read `pending`, with no clock). The window WINS the moment it holds a status row for the node (one predicate, `windowHoldsStatus`, for both), which is what keeps a snapshot read on open and reconnect from going stale; a `running` row is ignored once the run row has settled; and a non-running row only fills in a node the window already knows or one of the workflow's own agents (`drawnNodeIds`), since an activity entry is what the panel draws a card from.

**An OPEN call card folds back from its FOOTER as well as its header** (`BlockCollapseContext` in `block-shell.tsx`, read by `BlockToolFooter`). A call card holding a long sub-turn puts its header a screen or more above its footer, so the footer leads with a `Collapse` control, and the fold scrolls the header back into view when it left it above the scroller. The footer is ONE type size throughout. The scroll correction runs in a LAYOUT effect after the fold commits — a frame callback reads the card while its body is still laid out and parks the header under the chat header. The reverse trip is on the HEADER: an open fold carries a worded `⌄ Jump to end` control (`data-slot="block-jump-to-end"`, the footer's `⌃ Collapse` turned around — worded, since an icon alone reads as a download button) that brings the card's bottom edge — its last message and the footer — to the scroller's bottom, and never scrolls up when that end is already on screen.

**A multi-agent turn block is TITLED** (`turn-block.tsx`, `data-slot="turn-block-header"`): the agent's name, `sub-agent` where it applies, and the time, as an uppercase eyebrow at the TOP of the card — the treatment the transcript's other agent cards wear, never a small caption under the card.

**A QUESTION card is drawn from the row's `questions`, never from a CLI's tool name or payload** (`readQuestions` in `approval-card.tsx`). Each adapter projects its own CLI's question request into ONE card shape before the row is written (`CardQuestion`, see *agent-adapters.md*), so this file holds one parser and names no CLI's question tool. A row with no card is offered as a permission, which is also what keeps a card from collecting an answer the daemon's answer-fold gate would refuse. A question marked `secret` masks its answer field and settles saying the answer was not saved — the daemon records none of a card's answers once any one question is secret, so the settled card has nothing to show and its note speaks for the whole card. The masked field's notice is a line UNDER it, linked as the field's description, rather than its placeholder, which is gone on the first keystroke and cut off at phone width.

**An approval card WARNS about characters that can hide how it reads, and gates Approve on the ones that can** (`chats/text-hazards.ts` + `PermissionCard` in `approval-card.tsx`). Three classes, from the stdlib rather than a vendored table: `bidi` (`\p{Bidi_Control}`, a superset of the obvious list), `invisible` (`[\p{Cf}\p{Default_Ignorable_Code_Point}\p{Cc}]` minus the bidi set, via the `/v` flag's set difference so nothing is reported twice), and `mixedScript` — a token mixing Latin with Cyrillic or Greek, found with `\p{Script_Extensions=…}` and NO confusables data. That last choice is deliberate: UTS #39 confusability is relational and an approval card has no comparison string, so a table would flag by possibility rather than by suspicion. Bidi and invisible GATE — Approve is disabled until an acknowledgement is ticked, and the tick resets when the card's content changes so it can never carry into different, unreviewed input; mixed-script annotates only. Deny is never gated: refusing a suspicious call stays one click. **The banner names each hit by class and CODEPOINT and never prints the character**, since a bidi override inside the warning would reorder the warning. What is SCANNED is the tool NAME, the compact `JSON.stringify(input)` and — separately — the DIFF body, joined by spaces. Compact rather than the pretty-printed `inputPreview` because pretty-printing inserts real newlines, which are `\p{Cc}`, so scanning it would gate every multi-field call on JSON's own formatting; the diff needs its own pass because that arm renders `new_string` RAW, where the JSON has escaped the C0 controls that matter most. **Every separator here is a SPACE.** Joining the parts with a newline would gate every card (a newline is `\p{Cc}`), and neutralizing the diff's own `\n\t\r` by REMOVAL glues the lines either side into one token, so a Cyrillic comment above a Latin line reads as a mixed-script hazard. A space is `\p{Zs}`, in none of the three classes, so it invents nothing either way.

**Ordinary emoji are exempt, and the exemption walks BACK over emoji suffixes rather than reading the adjacent codepoint.** `\p{Default_Ignorable_Code_Point}` covers VS16 and the ZWJ, so without it `⚠️` or `👩‍💻` in a proposed patch would disable Approve — and a warning that fires on routine text is one people learn to tick through. Variation selectors are subtracted from the class outright (they only ever follow a base character to pick its presentation); a ZWJ is exempted by CONTEXT, since the same codepoint between LETTERS splits a word into pieces that render as one and is a real hazard. Reading only the immediately-adjacent codepoint is not enough: in `👩🏽‍💻` the character before the joiner is U+1F3FD (`Emoji_Modifier`) and in `🏳️‍🌈` it is U+FE0F, neither of them `Extended_Pictographic`.

A PROPOSED PATCH needs no card of its own at all, and that is the point: the daemon files it as an ordinary `approval_request` carrying `toolName: 'propose_patch'`, so `approval-card.tsx` renders it and the existing verdict channel answers it. The one renderer change is in **`diff-view.tsx`** — `editDiffOf` recognises that tool name over `Edit`'s own field names (`old_string`→`new_string`), with the `old_string` made optional so a whole-file proposal falls through to `Write`'s additions-only shape. An `Edit` missing its `old_string` still answers null, deliberately: that arm belongs to the proposal alone, and letting a malformed edit through it would draw it as a confident file creation. The tool name is a bare literal with a TWIN comment, like the ones in `transcript-groups.ts`, because the name reaches here inside a `z.unknown()` payload and nothing generated spans that seam.

A PROPOSED PLAN rides the same `approval_request` row and does get a body of its own: **`plan-card.tsx`** — its twin parser (`readPlan`, defensive because the payload is `z.unknown()` on the wire) plus `PlanCard`, routed from `ApprovalCard` by the tool name and falling back to the PERMISSION body when nothing readable is there, exactly as a question row carrying no card does — a malformed call must stay answerable rather than draw an empty card. The steps are a real `<ol>` with drawn numbers: the order IS the plan, and the numbers are drawn rather than left to the list marker so they line up with a step whose text wraps. The card's own addition is the **note** — one optional textarea sent with either verdict, over the same `answer` field a question's reply uses, trimmed and sent as a one-argument verdict when empty so the daemon's note branch is never entered with a blank string. A settled card keeps the plan on screen with `✓ approved` / `✗ rejected` and the note under it, because the rest of the conversation refers back to the plan. `useOneShotVerdict` lives in **`use-one-shot-verdict.ts`** — the freeze-until-the-verdict-round-trips timing is one contract for every card body.

The agent's own task list: `task-payload.ts` — the twin parser plus the FOLD, since a patch names only what moved; `task-list.tsx` — the `TaskListCard` the transcript shows where the list moved, and the shared `TaskRows` the SIDE PANEL composes for the current list (`agents-panel.tsx`, BELOW that agent's delegates and, like them, not behind a disclosure). The panel and not a strip over the composer, because the list is the same kind of per-agent state as the delegate rows beside it — a sub-agent likewise has a block in the flow AND a row in the panel. A delegate's list stays in its own block, whose collapsed header carries its count, since the block is closed by default. **Only the LATEST card of a thread shows its rows**: an agent that says one sentence between two announcements gets a card on each side of it, and both printing the whole list duplicates it a paragraph apart. A superseded card folds to the line it already had, the count plus the task that was running then, which is the history the chronological placement is FOR without the repeated wall. The open state is DERIVED from `latest` with a manual override on top rather than seeded into `useState` — an initial value only applies at mount, so the card that was current when it appeared would stay expanded for good. **A card's words come from the DAEMON's fold when the window cannot supply them** (`withDurableTaskLists`, applied to the fold's output in `Chats.tsx`): a task's text is stated once, in the announcement that created it, so on a thread longer than `HISTORY_PAGE` the card would know its oldest tasks by number alone (`Task 1`, `Task 2`) while `Run.taskList` names them. The latest card takes that list's rows, order and total with its own statuses winning per task; an earlier card gains only its missing titles, being a snapshot. The COMPOSER SHELF's task chip says `done/total` through the same `TaskCount` (`composer-shelf.tsx`'s `TaskListChip`): a lone count of what is left cannot distinguish six-of-seven from six-of-sixty and only ever shrinks.

**In the PANEL the list is bounded and scrolls itself; in the transcript it is not** (`TaskScrollRows` vs `TaskRows`). The panel has ONE scroller over every agent card, so an unbounded list makes its own card that tall and pushes the next agent — and the artifacts under it — off the screen. The transcript keeps the unbounded rows on purpose — it is a document the reader scrolls, and a nested scroll box in it takes the wheel away from the page while the pointer is over the list. Two things make the bound safe rather than merely tidy. It FOLLOWS the running task (`revealWithinBox` in `scroll-to-bottom.ts`), or a long list would show the done rows and hide the one thing happening. And it moves only when that row has actually left the frame, so a reader who scrolled the box keeps their place. `scrollIntoView` is not an option for it, for the reason recorded beside `scrollToBottom`: it walks every scrollable ancestor, and this box sits inside the panel's scroller inside a shell that must never scroll.

**An `in_progress` row only SPINS while something is working through that list** (`taskCardIsLive`) — not after a turn ended mid-task, and not on historical cards. Two conditions, both needed: only a thread's LAST card can be live, and only while the run has not settled past it — read as a MOMENT, like `subagentBlockStatus`, so a card written after the settle (the CLI carrying on by itself) still spins.

**That moment is the run's own terminal ITEM, not merely its row's `updatedAt`** (`settled-status.ts` → `settleMomentOf`, which reads the last terminal item FIRST and the row's own timestamp only when no terminal item exists; `runStoppedAt` and `activeRunSettledAt` both take it): items never touch that column, so it is only as fresh as the last thing that DID write the row and can sit BEFORE the stop it describes — a task announcement can land inside that gap and read as work produced AFTER the settle, spinning on a run the user had just stopped. `subagentBlockStatus` reads the same moment. A stalled row keeps a glyph of its own rather than falling back to `pending`'s: the agent started that task and stopped there.

**What the agents are RUNNING on this machine** (`chats/shell-activity.ts` — the fold; `chats/shell-list.tsx` — the rows; an uncaptioned band per agent card, above that card's task list). The transcript's last tool row says nothing about whether a command has come back, so live commands are per-agent state in the panel, beside the delegates and the task list.

**ONE COMMAND IS ONE LINE, and every part of that line is spelled out.** The band has NO caption (finished commands are deliberately absent, so there is no `done/total` to state; the task band beside it keeps `Tasks`, since a task row is prose while a shell row leads with the terminal glyph and places itself). Each row leads with that glyph, not a spinner — every row is live by construction and the clock is already moving. The detached marker is the word `background` in a bordered tag, never `BG` jargon or bare muted text (which reads as part of the command or the duration), with the explanation on `title`. The clock is a right-aligned COLUMN (`min-w`, since nothing bounds how long a detached command may run), so a clock growing from `3s` to `1m 58s` does not push the tags of different rows to different x positions.

**And the glyph is lifted a pixel off the box centre (`-translate-y-px`) — an OPTICAL correction rather than a fudge.** `items-center` centres BOXES, and a line box reserves descender space a command like `sleep 400` mostly does not use, so the text's visible band sits above the box centre while a square glyph lands exactly on it. One pixel, not more: a command with descenders centres its ink lower, and a larger lift would leave the glyph visibly high against the letters. **A line-height change cannot do this** (here or on the shelf chip): shrinking a centred line box moves its top down by exactly half of what it takes off the leading, so the ink does not move. The `-translate-y-px` is pinned by a spec on the CLASS, and that pin is not a proxy — the class IS the whole of the correction.

Derived from the TRANSCRIPT, because a shell is only ever started by a tool call and only ever ended by one coming back — geniro spawns none of these itself, and the daemon declines ACP's `terminal/*` capability, so an ACP agent runs its own commands too and there is no process on this side to enumerate. A shell is an `execute` call by the one shared classifier (`tool-kind.ts`), so a CLI naming its shell tool anything at all is still recognised; a call that discloses no arguments — routine on cursor — is listed under its own title rather than dropped, since hiding it would answer "what is running" with silence on a whole CLI. Background commands are tracked through claude's own bookkeeping: `run_in_background` on the call, the `ID:` its launch replies with, then `BashOutput`'s `<status>`/`<exit_code>` and `KillShell`. A kill that FAILED is not a kill — the CLI answers a handle it cannot find with an error, and retiring the row off that reports a shell nothing stopped as stopped.

**Which tool calls were DETACHED is the daemon's answer, not a match on the CLI's English** (`shell_open` items, read by `shell-activity.ts` → `detachFromShellOpen`). The sidebar reads `Run.shellsOpen`, which the daemon counts off the CLI's own structured frames (`system/task_started` → `background_work` → `shell_open`), and the daemon writes the open as a row exactly as it writes the close, so the count and the list are two views of one set. A text match on the launch announcement deliberately MISSES (see `readLaunchHandle` below), so it cannot be the source. The row also brings in a command whose CLI LIED about finishing (cursor answers a backgrounded command `exitCode: 0` while it runs; see *A CLI that reports a backgrounded command FINISHED* in `apps/daemon/AGENTS.md`) with nothing on this side having to know. The strict match keeps one job: the handle a later `BashOutput` probe is addressed to. Three details. The row MARKS and never CREATES — an open for a call below the loaded window would otherwise put a command on screen with no name to draw. Nothing orders it against the launch's own reply, so the fold handles both orders: arriving first it is remembered so the reply's "no announcement means this is the output" arm cannot close it, arriving second it REOPENS the shell that arm just closed (`completed` being the only status reachable by then). And on the daemon side it is part of the predicate that decides whether an off-turn row means the run is working (`restatesRunAsWorking`): an OPEN is work beginning, but a backgrounded command deliberately does not hold a turn, so reading it as `running` would latch the spinner — a shell emits no further row until its close.

**A launch is recognised by the CLI's whole ANNOUNCEMENT, never by the characters `ID:`** (`shell-activity.ts` → `readLaunchHandle`). A FOREGROUND command's reply is its own OUTPUT, so a loose match (`\bID:\s*([^\s.]+)` anywhere) promotes any command that prints those characters into a detached shell, and a detached shell only ever ends on a probe, a kill or the daemon's `shell_info` — so it would stay listed as running forever. claude's launch wordings (a plain launch, one the user backgrounded, one that outran its timeout) all end `Output is being written to: <path>.`, so that whole shape is matched, anchored at the START of the reply (a command whose output quotes past launch replies must not match). The reply decides BOTH ways: a call that ASKED for the background and came back with plain output was never detached, so it closes. A miss costs one row that should have been listed; a false positive costs a row that can never be unlisted — keep the match strict. Background commands launched before the daemon's shell-settle channel existed have no ending in the transcript, so old conversations keep their stale rows.

**Only what is running — and how that is KNOWN differs by kind, which is the whole of the gate.** The finished ones are already in the transcript in full and in order, so repeating the last forty of them in a 280px column would bury the row this exists to show. A FOREGROUND command is read as running because its tool call has no reply, and that reading is only as good as the turn: a cancelled or abandoned one leaves a call that never comes back, and the row would stand for the rest of the session claiming a process that died with the turn. So those are gated on **`isSettledRunStatus`** — has this agent stopped for good. A DETACHED command is not read that way and is deliberately NOT gated: its call is answered within the second, its end is a durable `shell_info` row, and the daemon writes one for every shell still open when the CLI process dies — so its liveness is reported rather than inferred, and the run settling says nothing about it. Gating it too blanks the panel on exactly the case it exists for, since a backgrounded command does not hold the turn open (see `apps/daemon/AGENTS.md`): the agent finishes, the turn settles `completed`, and the `pnpm dev` runs on with nothing on screen. The whole rule lives in ONE place (`Chats.tsx`'s `shellsByAgent`), because the header's counter is the same reading over the same map and two copies is how a `2` up there comes to sit over three cards below.

**And it is the MAIN thread's shells alone.** In a 1:1 chat every row carries `nodeId: null`, so a delegate's commands would land in the SAME bucket as the agent's own and a fan-out's commands would swamp the list with nothing saying which thread launched them. A delegate's block holds its tool rows in full, its card in the agents panel is where its state is read, and the run row's own `shellsOpen` still counts every detached command whoever launched it. The drop is at the ITEM (`shell-activity.ts`, on `subagentIdOf`), before anything is indexed, which is what lets the daemon's `shell_open` / `shell_info` rows stay unguarded: each can only ever reach a shell this fold created, and for a delegate there is none.

**A detached command's END is a row the DAEMON writes** (`shell_info`, read by `shell-activity.ts`; see `apps/daemon/AGENTS.md` for the half that produces it). Its launching call is answered the moment the CLI accepts it, so the transcript otherwise holds a start and no end and the list would accumulate. The reader matches by launching call, else by the CLI's own work id (the settle names the call on one of its two channels and not the other), and it only ever coarsens a shell still believed to be RUNNING — one a `BashOutput` probe already settled knows how it ended, with an exit code. `shell_info` is also skipped OUTRIGHT by `groupTranscript`: it renders as nothing, and the fall-through treats any other kind as the node having said something and closes its open tool group.

**Clicking a row opens that command's own terminal** (`shell-output-dialog.tsx` over `GET /v1/chats/:runId/shell-output`). It is POLLED while the command runs and read once when it is finished — a bounded tail of one file, unlike the context breakdown next door, which is a multi-second round trip to the live CLI and so is fetched once per open. It follows the newest line unless the reader has scrolled up, says out loud when it is showing only the END of a longer output, and holds the command as a SNAPSHOT rather than following the live fold: a shell leaves the running list the moment it settles, so following it would close the dialog at exactly the moment the reader came to see how it ended.

**And it is drawn in the command's OWN colours** (`components/ui/ansi.ts` — the pure parser; `components/ui/ansi-text.tsx` — the one place a shell's escape sequences are rendered). Command output is not plain text: anything with `--color=always` or `FORCE_COLOR` emits SGR codes, and drawn verbatim the escape byte is INVISIBLE in HTML while its tail is not — a green `PASS` reaching the screen as `[32mPASS[0m`, corrupted rather than coloured. The parser also plays out what a terminal would have done with the rest: a line rewritten by a progress bar (`10%\r20%\r30%`) shows its last state instead of all three at once, and the sequences that cannot be honoured here — cursor moves, erase-line, window titles — are DROPPED rather than printed, which is the difference between a spinner's log being readable and being one `[2K` per tick.

Three rules it holds. **Every colour is a `--ansi-*` TOKEN**, aliasing the semantic and code palettes wherever one already carries the hue (red is `--destructive`, green `--success`, blue the highlighter's own `--code-variable`) — a terminal's own palette is built for a black background, and `#00ff00` on this cream card is unreadable; the one new literal is cyan, because nothing in the palette had one.

**The BRIGHT half (90–97) is the same eight NAMES carrying a flag, and the themes answer it differently** — `AnsiSpan.bright`, drawn as a `--ansi-bright-*` token, never as a lightened value the parser computed, because "brighter" is a fact about the ground. The dark theme lifts all eight in luminance with the hue held (each clearing AA on `--card`), while the light theme aliases the six CHROMATIC brights back onto their normal twin, since on cream a brighter ink is a fainter one. The GREYS do not alias on either theme: `ESC[90m` — the most common bright code in real output (git, npm, pnpm, cargo timestamps and secondary prose) — means DIM, so it must never map onto `--ansi-black` (which is `--foreground` on both themes); both themes put it on the palette's faintest ink, at the AA-large bar `--code-punctuation` documents. The four greys are four distinct steps on dark — bright-black (faintest), white (dim), black (default), bright-white (strongest); on light `--ansi-bright-white` and `--ansi-black` coincide. The 256-colour path follows the same layout, 8–15 being that palette's own bright eight in the same order.

And it is **deliberately partial** — no background fills (a per-span fill on cream is noise), no 24-bit colour (there is no token for an arbitrary value, so the run takes the surface's colour, with its parameters still consumed so the digits do not print). The copy control beside the output hands over `stripAnsi(text)`: the spans are for the eye, and what a reader pastes into a bug report must not carry the codes that coloured them.

**The count sits on the COMPOSER SHELF, as a chip** (`composer-shelf.tsx`'s `RunningShellChips`, `slot="running-shells"`), not in the chat header — the shelf is the row of what a thread is currently producing — holding `ShellRows` behind a hover-popover. The chip's three parts — a leading SPINNER as the mark, the word `Terminals`, a trailing muted count — are settled; the reasoning is written at `RunningShellChips`. It is **not drawn at zero**: a shelf is a row of what EXISTS, so it needs no "none" readout. **Its count is its rows, and the rows cover the whole run**: `withDurableShells` adds every command the daemon's run state lists that the loaded window started before, so the chip never layers the run's own `shellsOpen` over a shorter list (the sub-agents chip does the same through `withDurableDelegates`). `run.shellsOpen` and `run.subagentsOut` still drive the BADGE, and the `run_status` announce writes them onto the run row (`use-chat-run.ts`). **The liveness gate lives in `Chats.tsx`, at the one place both are fed from** — `shellsByAgent` is built from the fold, re-keyed to the panel's card ids and filtered to agents still working, and every count is a flatten of that same map; the panel renders exactly what it is given and invents no filter of its own.

**The SUB-AGENT count and the TASK list are chips on that same shelf** (`composer-shelf.tsx`'s `RunningSubagentChips` and `TaskListChip`, slots `running-subagents` / `open-tasks`), with the same `HoverPopover`, the same hover-then-pin, and the same panels — the delegate list, and `TaskScrollRows`, which bounds itself and follows the running row. `sidePanelLive` in `Chats.tsx` feeds all three chips from one reading, so the shelf and the agents panel cannot disagree about what is working. The sub-agent chip is **not drawn at zero**, on the shelf's rule. The task chip is the exception on the row and is drawn while `total > 0`: a finished checklist still answers "what did it do, and what did it leave", where a returned command and a finished delegate are history the transcript already holds. Its mark is the delegate glyph rather than a spinner: this list holds the FINISHED delegates too (every `Terminals` row, by contrast, is live by construction).

**The shelf's order is DURABLE → VOLATILE, left to right, and that is the whole rule**: pull requests, tasks, workflow, agents (open calls), sub-agents, terminals. A chip that comes and goes must never shift one that stays, so the ones that end within a turn go last. `SubagentRows` (`chats/subagent-list.tsx`) lists the LIVE delegates and counts the finished ones behind a fold, shut by default — the agents panel's answer; never sort running rows to the top instead (a fan-out's finished rows would still bury the live ones). SETTLED is `isSettledRunStatus` rather than `!== 'running'`, so a delegate that is `held`, `pending` or waiting on the user stays listed rather than hidden under `finished`. The fold is `useThreadFlag` (remembered per thread), because the popover's panel is mounted afresh on every hover. Its rows open the same sub-agent detail the panel's own rows do (`onOpen` → `setDetailSubagentId`), on the rule every list here follows — absent the callback they are plain text, never a row that merely looks clickable.

**The chips stay SEPARATE, and exactly ONE run of them is joined: the pull requests** (`chats/shelf-chip.ts` — `SHELF_CHIP_CLASS` for a standalone chip, `SHELF_GROUP_CLASS` + `SHELF_SEGMENT_CLASS` for the joined run). **Touching is a CLAIM that two things are one**, so it is made only where it is true: of a pull-request chip and the `All N` that counts it, not of a terminal and a task list (one segmented bar across the whole row was rejected). The group wears the same card a chip wears (a group of one is indistinguishable from a standalone chip, which is why `ThreadPullRequestChips` always renders it), `divide-x` separates its segments, and a segment carries no card of its own (its own hairline draws a second line beside the divider; its own radius leaves notches inside the run). `overflow-hidden` clips the end segments to the card's radius and does NOT clip the popovers, which are `anchor="viewport"` and therefore `fixed`. Two segment classes are OVERRIDES: `rounded-none` beats `HoverPopover`'s own `rounded-full` on its trigger (otherwise the counter fills as a lozenge inside a square segment), and `focus-visible:bg-sidebar-accent` is the keyboard indicator, since a focus RING is a box-shadow outside the element's box and `overflow-hidden` shaves it. **Both `All N` controls carry the glyph of what they count** — the pull-request mark, the workflow mark — so the control names its subject. The WORKFLOW `All N` stays a standalone chip.

**Under a SQUEEZE the row degrades by clipping, never by overlapping** — two separate rules for when the shelf runs short (a narrow window, a widened chat list, an open agents panel). `shrink-0` belongs on `HoverPopover`'s WRAPPER as well as on its trigger: the wrapper is what the shelf lays out, so with the class on the trigger alone the wrapper collapses while the button spills out of it and the next chip overlaps. And `SHELF_SEGMENT_CLASS` carries its own `overflow-hidden`, distinct from the group's: a pull-request chip is `[icon][number][title]` with the number deliberately `shrink-0` (it identifies the thing, so it never truncates), and without the segment's clip that unshrinkable content prints over the `All N` sibling beside it. A cut-off number reads as "there is more here"; overlapping glyphs read as a broken app. Both are pinned on the emitted CLASSES.

**While a turn runs there is ONE clock, and it is the worked total.** The header shows no raw wall clock for the running turn (`ElapsedTime` was removed — do not reintroduce it): on a first turn it repeats `worked`, and `worked` already moves every second. Settled, that slot says when the thread last spoke, so `completed · 4m · worked 1h 41m 5s / 5 turns` gives two different answers. `worked` PAUSES on an approval card by design; the card on screen says the thread is waiting.

**How long each turn WORKED** (`turn-duration.ts` — the twin parser over `usage.durationMs`/`apiMs`, the wall-clock fallback, `TurnDurationContext` and `formatDuration`; rendered on the `turn_complete` row beside its cost, and summed into the header as `worked 4m 12s / 6 turns`). Two clocks, and the CLI's own wins where it exists: claude's `result` line carries `duration_ms`/`duration_api_ms` (read by `readClaudeUsage`) and measures the agent WORKING, so it counts neither the first-prompt MCP-readiness hold nor a stretch parked on an approval card. ACP reports no timing and declares so rather than passing off the driver's wall clock as the agent's figure, so a cursor turn is measured from its durable rows MINUS the parked stretches (an `approval_request` and the `approval_verdict`/`unanswerable` closing it are both rows), which keeps the fallback meaning the same thing as the primary. The thread total is the SUM of its turns and never `updatedAt - createdAt` (a chat open for three days with five minutes of work spans `3d` and worked `5m`). `apiMs` can EXCEED `durationMs` on a turn served off a kept session, so the tooltip's API/own-work split is withheld on that reading rather than clamped to a fabricated `0s`.

**That middle source is only as fresh as the client keeps it** (`rememberRunContext` in `use-chat-run.ts`). The renderer's copy of the run row comes from `GET /v1/chats` at mount, and `run_status` carries status, activity, `updatedAt`, the preview and the title — no reading — so every live reading is mirrored onto the copy, and the fallback a settle drops into is the newest figure this client has seen (otherwise the ring freezes while the daemon's row moves). Guarded on the value CHANGING (the event fires many times a second, and an unconditional write would re-render the sidebar per delta) and on it being POSITIVE — "a reported 0 is not a measurement", so a settle that clears the figure cannot erase the last real one.

**The RING is drawn from three sources in strict recency order, and the middle one is the run ROW** (`chatContextFigures` in `chats/chat-context.ts`, which `Chats.tsx` and the workflow dock both call): the live delta for this turn's latest request, then `Run.contextTokens` — every reading the CLI reported, filed by the daemon as it arrives — then the last SETTLED turn of the loaded transcript. The live plane is ephemeral (a reload, a reconnect or a first open starts without one) and the transcript has nothing until the turn ends (e.g. a long turn after a `/compact`), so the row is the only thing a cold window can read. Read the live value directly rather than through `agents[0]`, which already collapses live onto transcript and would put the oldest source ahead of the row. `useContextReadings` stays the last fallback, for a switch whose refetch is still in flight.

**A WORKFLOW run's composer ring is its ROOT agent's**, and that is the one case where the ring is about a node rather than the run: a workflow's nodes each hold a window, so there is no run-level figure — except the root's, which is the node the user prompted and the one the run is a conversation with. `chatContext` resolves it through `wfNodes.rootId` (`rootAgentOf`, which needs a trigger EDGE into an agent, not merely an agent in the node list) and answers nulls for the four states where there is no single root — before the workflow fetch resolves, on a non-workflow run, on a graph with none, and on one with several — so the ring is withheld rather than drawn about no particular node. It renders beside the trigger chip, since the composer's per-CLI chip row is a chat's alone. A THIRD ring, the callee's, sits on the call block's summary band (`callBlockContext` in `transcript-groups.ts`), folded from that callee's own `turn_complete` rows: each side of a call holds its own window, so it is the one figure about a call the caller's ring cannot state.

**A WORKFLOW NODE's ring has the same shape one level down, and its middle sources are the durable rows** (`cardContextOf` in `Chats.tsx`, fed by `chats/use-node-context.ts`). First match wins: the node's own live delta; the newest CALL thread carrying a live one; the newest call thread carrying a DURABLE one (`call_context`, keyed `(runId, callId)`); `NodeState.contextTokens` / `contextWindowTokens`; the transcript's settled turn. The third rank applies ONLY to a node that runs nothing but calls — `node_state` is written on every reading while `call_context` is written only under a call, so for a node whose own DAG turn ran after its last call the node row holds the NEWER figure; `threadsOf` emits a `main` thread exactly when that turn happened, which is the test. The per-call rows also feed the sidebar's THREAD rows directly (`callThreadsOf`), so a node called several times draws one ring per call instead of one flickering between windows. They are fetched with `GET /v1/workflows/runs/:runId/nodes` on run OPEN and on RECONNECT, and on those two moments alone — everything in between arrives as a delta, which outranks them. Reconnect needs its own trigger (`reconnectNonce` on `use-chat-run.ts`) because a figure on a column is not a row: the reconnect item-delta replays what the socket missed, and a `node_state` column is not in it. The map is cleared on entry to the effect, so a run→run switch cannot leave the previous run's figures standing — two runs of one workflow share node ids.

**A COMPACTION invalidates every reading taken before it, and there are four places one survives.** This concerns the CLI whose compaction geniro performs ITSELF — cursor, which has none of its own (`AdapterConfig.geniroCommands`): the conversation is DISCARDED and a summary put aside for the turn that replaces it, so nothing measures the new one until the user's next message. The daemon clears the run row (`RunDao.forgetContext` — the count only, never the window, which belongs to the model) and stamps `conversationReplaced` on the compaction row; the renderer answers the other three. The transcript FOLD resets at that row (`endsContextHistory`, which also covers the CLI's own compaction marker — a figure the compaction reported about itself lands BELOW it and overwrites the null). The LIVE plane is cleared when the row arrives (it is dropped on a run switch, never on a settle, so it outlives the turn it was filled in), along with this window's mirrored copy of the run row. And the RECALL is not consulted while a transcript is loaded — a loaded transcript with no reading is an answer, while an empty one is the refetch the recall exists for. Only geniro's own compaction clears the live plane: a CLI that compacts for itself REPORTS what it left behind around its own marker. Between the compaction and the next message the ring is drawn EMPTY saying why (`ContextMeter`'s `awaitingReading`: `Conversation compacted — its new size is measured on the next message`), never withheld — the ring is what a user watches. It is muted rather than green, since a filled nought would claim a measured empty window, and it needs the WINDOW to be a gauge at all — which is why `chatContext` reads the denominator whether or not it has a count.

**What the context window actually HOLDS** (`context-panel.tsx` + `chat-metrics.ts`, opened by the `context-meter` ring) — the breakdown the CLI's own `/context` prints. Fetched from `GET /v1/chats/:runId/metrics` when the readout is OPENED and never polled — it is a multi-second question put to the user's own running agent — and re-fetched on every open rather than cached. The previous reading stays on screen while the SAME chat is re-read; a DIFFERENT chat starts blank, since a reading is carried with the run it was taken from and a mismatch reads as empty (the meter is not unmounted across a chat switch). One component, not a second meter: the panel is `children` the same `MeterReadout` renders, and the one-line summary steps aside only once a full breakdown has arrived. A CLI that counts tokens per REQUEST rather than per kind (codex) sends no categories, files and servers with `tokens: null`, and a `lastRequest` split: the bar is then one `In the window` segment, an unpriced row shows `—` (a server its tool count) and a folded block's header its count alone — never a `0` nobody measured — and the split is its own `Last request` line. Deferred categories are drawn in their OWN section rather than in the bar, because they sit outside the CLI's total and would overstate how full the window is. Category colours come from the avatar palette by POSITION in the CLI's own list, never by name (the CLI is free to invent a name). On a WORKFLOW run it is asked PER NODE (`GET /v1/chats/:runId/metrics?nodeId=`, `ContextMeter`'s `nodeId`, the panel's `metricsByNode`): a workflow run's nodes each hold their own process. The composer ring reads the root node and each agent card its own; the node is part of the readout's state key. Every readout branch must carry `nodeId`, including the filled ring's — `context-meter.spec.tsx` pins that branch. A node keeps its LAST reading the way a chat does (`NodeState.lastMetricsReading`, taken on the process's idle farewell and at turn end), so an idle Manager still shows its breakdown and plan limits, dated, while its callees work. **The panel is ordered by what a reader came for, not by where the figures came from**: the window headline, then the account's PLAN LIMITS, then the thread's totals, and only then the open-ended itemization (deferred rows, instruction files, one row per MCP server), which would otherwise push the limits below the 26rem scroll box. `Breakdown` renders the window itself and `ContextDetail` the itemization, so the two sit on opposite sides of the limits.

**The plan limits hold their place while they load, and say how old they are** (`context-panel.tsx`'s `Plan`; the daemon half is in `apps/daemon/AGENTS.md` → *Plan limits are the ACCOUNT's*). The section always ends up on screen in some form — limits, or the sentence why there are none — so a first open draws a `Plan limits · Loading…` placeholder (`plan-limits-loading`) under the breakdown's own `Reading the agent's context…`; a re-read keeps the figures with a spinner on the heading and `Updating…` at the foot. A reading older than a minute reads `Updated 5m ago` (`planTakenAt`), and an `estimated` one says the CLI's usage service did not answer.

**TWO money formats, and every dollar on screen comes from one of them** (`chats/agent-activity.ts`). They agree above a cent and differ only below it, where a bare 2-decimal rounding prints `$0.00` and claims a turn cost nothing: `formatUsd` answers with a BOUND (`<$0.01`) for aggregates in a column — the Stats breakdowns, the context meter's run total — where the reader compares rows; `formatExactUsd` answers with the VALUE (`$0.0034`) for a figure that stands alone — the thread header's cost, the `✓ done · 21s · $0.42` note under a finished turn. Never a third (no local `toFixed`, no second `formatUsd`). The spec pins the pair by asserting they AGREE at and above a cent.

**A badge that repeats the name beside it states no second fact.** The agents panel's card is `agent.name` + a muted badge carrying `agent.agent`; the badge is dropped when it equals the name (a 1:1 chat's card would read `claude … claude`). **The rule keys on "would this repeat the text beside it", never on "is this a workflow"**: `Chats.tsx`'s 1:1 branch sets BOTH fields from `activeRun.agentKind`, while its node branch sets `name` from `node.name ?? node.id` and `agent` from `node.agent`, so a named node keeps its badge. The spec pins all three shapes: no badge on the degenerate card, `cursor-agent` beside `Reviewer`, and `claude` still drawn beside `Orchestrator`, a NAMED node on the same CLI.

**Three things on this page that LOOK redundant and are not, so check here before cutting them.**

**The task list renders TWICE ON PURPOSE** — the transcript's inline card and the agents panel's `Tasks` section, both expanded and live (the same goes for sub-agent names). The user confirmed it is wanted: the transcript holds the list where the agent produced it, in conversation order; the panel pins the CURRENT state where it stays put while the transcript scrolls away. Do not resolve this into one surface.

**The composer shelf's `Tasks` / `Sub-agents` / `Terminals` chips** restate counts the agents panel also renders, deliberately: the shelf is the row of what a thread is producing right now, one line above where the user types, and its chips are hover-popovers rather than a third expanded copy — `RunningSubagentChips` takes its count as a PROP so there is one answer computed in one place.

**The chat-list row is four lines** because it carries four facts the user asked for (the PR label and the agent label among them) — do not reclaim height by deleting one.

**The tail is lost in TWO directions, and both need a watcher.** *Content grows* is covered by the commit-time effect (`[items, liveText]`) and by the `ResizeObserver` over the scroller's children. *The viewport shrinks* — the composer gaining a line, the attachment strip, an approval card, the fast-action bar — shortens the transcript while no row resizes, `scrollTop` never moves and neither items nor live text change, so nothing fires: the newest message sits below the fold with `aboveTail` still false, so "Latest" is not even drawn. So the observer watches the scroller ITSELF alongside its children — one `observe` call, and the reason it is not redundant.

**Opening a thread says it is loading** (`use-chat-run.ts` `loadingHistory`, drawn as `data-slot="thread-loading"`). The list is cleared at the switch and the newest page arrives a round trip later, so a blank pane would otherwise flash. Raised at the switch, cleared only by the fetch for the thread still open.

**An open workflow run's `/` menu lists the skills of the agents a follow-up lands in** (`skillTargets` in `Chats.tsx`, over `useAgentSkills`' `SkillTarget` pairs): every agent its trigger feeds, each under ITS node's config directory, since a workflow's agents name their own profiles. The daemon hands the text to the root verbatim, where claude expands it.

**A workflow row previews its ROOT conversation** (`chat-preview.ts` `previewsThread`, twin of `ItemDao`'s `NOT_IN_A_CALL`): a message written inside an agent call carries that call's `callId` and belongs to the callee, so it never becomes the sidebar line.

**ONE press of `Load earlier messages` pages until the transcript grows UPWARD** (`pageOlderUntilVisible` in `Chats.tsx`, bounded by `OLDER_PAGES_PER_PRESS`). One page is not one answer on a workflow run: every row a callee streams carries its call's id and is claimed by that call's block, so a page made entirely of them extends a card already on screen — usually a COLLAPSED one — and the top-level list is unchanged. The loop stops on the first page that puts an entry above the ones already drawn, comparing `transcriptEntryKey` of the top entry as last DRAWN (an effect-written ref — what the reader can see is only answerable after a commit) across a macrotask, so each prepend is committed before the next page is asked for. The pane-filling effect beside it re-runs per render and its guard is the pane's own height.

**An older page is prepended at most once** (`use-chat-run.ts` `loadOlder`). Its in-flight guard is released when the page ARRIVES, while `itemsRef` — where it reads the oldest row from — catches up only after React commits, so a scroll event in between would ask for the same page again and duplicate it. A load that sees the oldest row the previous one paged below continues from where that page ended (`lastOlderPageRef`), and the prepend keeps only rows still older than the oldest held.

**The history pager takes DIRECTION as well as position — a cost fix, not a tail fix.** `jumpToBottom` animates, so pressing "Latest" from inside the older-page zone fires `scroll` for every frame of the way down while the early frames are still under the threshold; without the direction check the pager fetches pages mid-flight and the caller's `scroller.scrollTop += …` (holding the reader's place) TERMINATES the smooth scroll. `shouldLoadOlder` (`chats/scroll-follow.ts`) therefore buys the fetch and the animation, not the destination (the press re-arms the follow either way). Ordering trap inside `onScroll`: the previous-`scrollTop` ref is overwritten mid-handler, so it is read ONCE up front — passing the ref to the second reader hands it `scrollTop === previous`, which reads as "did not move" and silently disables the guard.

### Workflows

**Workflow vs graph** — the noun rule is in the root `AGENTS.md`'s *Coding conventions*. In the renderer: the screen directory is `workflows/` (screens are named for what the user sees — `chats/`, `settings/`, `stats/`) holding `Workflows.tsx`, the `AppView` member is `'workflows'`, entity names are `Workflow*` (`WorkflowCard`, the generated `WorkflowsApi`), and `graph` survives only where the DAG itself is the subject (`graph-doc.ts`, `graph-edge.tsx`, `node-validate.ts`, the page subtitle *"Compose a team of agents as a graph"*). **The daemon's `v1/graphs/` deliberately keeps its name**: it is the graph ENGINE — `graph-executor`, `graph-order`, `graph-validate` — no user reads it, and the workflow store inside it is already `WorkflowStoreService`.

**The library is a CARD GRID, two per line.** `Workflows.tsx`'s `<ul>` is `grid grid-cols-1 sm:grid-cols-2`, with `items-start` rather than the default stretch (a stretched shorter card leaves its footer dangling in blank space), and the description gets `line-clamp-3` — it is the field that tells two workflows apart, so it must not be truncated to one line. Each card is the real `ui/card.tsx` `Card` (name in `CardTitle`, description in `CardDescription`, the agent tally + node/edge counts + updated time in a `CardFooter`), never a hand-rolled look-alike.

**It takes `NavListItem` for its activation, not its own.** Never a `div` with `role="button"`, a hand-rolled Enter/Space handler and a nested delete button (which ARIA forbids, and which needs an event dam so delete does not also open the builder). `NavListItem` layers a REAL `<button>` under the content, so keyboard activation is the platform's and the delete control is that button's SIBLING. It is used with `active={false}` throughout and its own sidebar dress neutralized (`bg-transparent`, no padding, `rounded-xl` to match the card's corners), so the nested `Card` is the only thing painting a border/radius/shadow. The spec pins the structure, not the keystroke (jsdom synthesizes no click from a keydown): `tagName === 'BUTTON'` and "the activation button contains no interactive descendant" both fail on a revert.

**A COUNT beside a graph is read as a count OF the graph, so it must be one.** The node cards' collapsed ports block counts the edges ACTUALLY attached to each side, off `useEdges` (`node-ports.tsx`) — never `rules.length`, the connection rules the node KIND accepts, which reads like a live figure and cannot change. ZERO is the case worth showing (a leaf agent reads `0 outputs`). The palette's category headers carry no count (it would be how many TYPES the drawer offers, beside a canvas holding a different number).

**Collapsed, that block is a caption, not a panel**: one caption-height row with no fill, padding following the state. Satisfied sides are muted, and the destructive tint is spent on the ONE state worth spotting across a canvas — a side missing a wire it requires. EXPANDED is where "what can connect here" belongs, with rows labelled per rule.

**A selected card is ONE thick edge, and nothing may straddle the silhouette that edge redraws.** The selection ring is FLUSH — never `ring-offset-2`, which draws the silhouette three times (border, a stripe of page background, ring) and reads as two outlines; same-hue strokes with no gap merge into one heavier edge. The ports toggle sits INSIDE the card, between the two port captions, never pinned half outside the bottom border, where its own fill punches a hole through the selection ring — the fix is position, not layering. Both are pinned on the emitted CLASSES, where the class IS the mechanism.

**EVERY wire is drawn by `graph-edge.tsx`, and the ranking matches what the wires MEAN.** The data wire ORDERS THE RUN, while `call` and `instruction` "order nothing", so data is solid, the heaviest stroke, arrow-headed, and NEUTRAL (`--color-foreground` at 0.7 — strong enough to outrank the full-chroma annotation dashes; not 1, the page's text weight, which out-shouts the node cards). Neutral rather than the brand accent deliberately: the annotations are already caramel and amber. Never leave a kind on React Flow's default edge. `flowEdgeType` emits a `type` for EVERY kind, while `flowEdgeKind` must keep reading an ABSENT type as `data`, since edges persisted earlier carry none (its own spec case). `EDGE_TYPES` is keyed by the whole `EdgeKind` union, so a kind without a component is a compile error rather than a silent revert to the default.

**The palette shows everything at once — a few tiles, no folds** (no collapsed accordion blocks; `node-palette.spec.tsx` records why, so a fold is not reintroduced as "consistency"). **The agent is ONE tile whatever the CLI** (`node-palette.tsx`): a tile per CLI makes the CLI a drag-time choice that cannot be changed. The node's CLI is the first row of its settings card (`CLI for this node`), and switching it starts the node from that CLI's defaults — model, effort, context window, model parameters and profile belong to the CLI that offered them. A new node starts on the CLI last chosen there (`defaultNodeAgent` / `rememberNodeAgent`, browser storage), else the first the daemon lists. **Never pair a `line-clamp-*` with a `display` utility**: `line-clamp` works by setting `display: -webkit-box`, which a `block` beside it cancels.

**`ConfirmButton` arms ITSELF to destructive, so a caller naming that variant deletes the guard**: a resting destructive button is the loudest thing on the page, and arming it would then change nothing but the word. The variant is `Exclude<…, 'destructive'>` at the type level, since the mistake is invisible in review and no spec renders the builder's delete control. `confirm-button.spec.tsx` pins the behaviour that exclusion protects: arming must change the CLASS, not only the label.

**An INSTRUCTION block is a node that never runs.** The palette's third category (`instruction-node.tsx`, wired with the `instruction` edge kind) drops a free-text block onto the canvas; its text is appended to the turn of every agent it is wired to, ranked after the user's global custom instructions and before that node's own `role` (root `AGENTS.md` → *Agent instructions*). It has no status chip and no `node_state` row — the daemon writes neither, because `pending` is a promise that something will happen to it — so nothing about it settles, fails, or appears in the run order. Its text refuses control characters, through the same schema as the settings box (no length limit). Every agent-node field that reaches a CLI's argv refuses a NUL (`id`, `name`, `model`, `effort`, `contextWindow`, `description`, `role`, `configDir`), since a NUL makes node's `spawn` throw on every run of that node — a NUL and nothing wider, because the same schema READS the library's YAML and every run's graph copy, and refusing a pasted ESC or form-feed (which argv takes fine) would make a working workflow fail to load. The builder autosaves the whole workflow in one PUT, so `node-validate.ts` mirrors that rule and the card names the offending field; without the mirror one bad field stops every later edit to that workflow from persisting. The two dashed non-data wires — `call` and `instruction` — share `graph-edge.tsx` (which draws data wires too) with a per-kind variant, because the back-edge routing is the fiddly half and a second copy is how two kinds would come to disagree about where a wire goes.

`workflows/` React Flow canvas. **A node's pickers are only as trustworthy as the list behind them, and the list arrives late.** The inspector fetches the SELECTED node's CLI vocabulary, so a node of another CLI can mount against the previous node's list — and act on it (writing one CLI's model onto another CLI's node, which then runs on a model nothing on screen names). So `useAgentVocabulary` resolves DURING RENDER off its own cache, never from an effect-set state: an effect is always one commit late, and that commit is the one a child mounts in. Free-text mode (deciding a stored model is off-list) waits for a NON-EMPTY list — an empty list makes every stored model look off-list and shows `Custom…` over a text input for good. There is no model adopt (see the settings band below).

The **canvas** carries the same lateness in geometry: React Flow defers the initial `fitView` until nodes are measured, so on a workflow created moments ago it fires when the FIRST node lands and scales that one node to fill the pane — hence `INITIAL_FIT`'s `maxZoom: 1`, capping the AUTOMATIC fit only; the Controls' own fit button stays uncapped. A toolbar add also PANS to what it just added (adds stack right of the rightmost node and would otherwise land off screen); a drop is exempt, having landed where the user aimed.

**What the builder must never lose.** Each rule is pinned in `Workflows.spec.tsx`, which drives the REAL React Flow (never mock it: a mock makes node state and keyboard handling untestable).
- **Closing the chat dock HIDES it** (`workflow-chat-panel.tsx`'s `hidden`), never unmounts it: unmounted mid-turn, `chatWorking` stays true for good, and autosave is paused while the agent works, so every later edit would silently never be written. A turn that ends while hidden still clears the flag and re-reads the canvas, and that re-read compares the file against the LAST LOAD OR SAVE rather than against the canvas, or edits held back during the turn are thrown away even when the agent changed nothing. While paused over edits the status bar says so (`use-autosave.ts`'s `paused`).
- **Delete/Backspace act only while the screen is on view** (`deleteKeyCode` is null otherwise). React Flow listens on the whole `document`, and this screen stays mounted when hidden, so Backspace elsewhere would delete the selected node of a workflow nobody is looking at, and autosave would write it. `addNode` selects the new node ON THE CANVAS, not only in the inspector, so Backspace deletes the node the user just added.
- **Leaving waits for the canvas to reach disk.** `flush` waits out a write in flight, writes again if the canvas moved on, and says whether it worked; a failed leave stays in the builder with the reason and a "Leave without saving?" way out. A save or re-read answer that lands after another workflow was opened is dropped — otherwise a late answer for A resets the open slug to A under B's canvas, and the next autosave writes B into A.
- **A wire to a missing node is dropped on open and named** (`toFlow`), since the daemon refuses such a graph on every save and the wire would be invisible to delete. The canvas also refuses a DATA wire that would close a loop (`canvasAcceptsConnection` / `closesDataCycle` in `node-schema.ts`); call wires may still loop.
- **Deleting a workflow from the builder fully leaves it**, so the next one opens without the previous chat dock.

- **The dock catches up after the socket reconnects** (the replay is `use-run-stream.ts`'s, which `use-workflow-chat.ts` reads the rows through and then re-reads the run). It reads back the rows past the newest one held when the socket DROPPED (not when it returned: the room is re-joined first, and a live row landing in between would move the cursor past what was missed), ends the turn on a terminal tail, then re-reads the run, since a settle with no terminal row was announced only on the socket — otherwise a turn that ended offline leaves the dock working, with autosave paused, for good. A turn ending delivered by both the socket and the replay is counted once, by row id, because each count re-reads the canvas.
- **The dock holds anchors like the chat screen does** (`use-workflow-chat.ts`): its opened page's anchors apart from its rows, a reconnect read-back's merged in (another run's dropped), and its live rows asking through the same `useLiveAnchorAsks`. Its page stays `WORKFLOW_CHAT_PAGE` (120) rather than the user's page size — a dock is a side panel, not the transcript.
- **A card raised while the dock is hidden MARKS the toggle** (`data-slot="chat-awaiting-mark"`, and the toggle's name and tooltip say the agent is waiting for an answer). It rides `RunDto.awaiting`, which `use-workflow-chat.ts` keeps current off `run_status` on `use-chat-run.ts`'s three-state rule (absent asserts nothing, `null` clears) — including on an announce whose status is null.

**A node's AGENT POOL is edited under its settings card** (`workflows/agent-pool-editor.tsx`): members 2, 3, … — the card above is member 1 — each with its own CLI, profile, approval mode, model, effort, context window, the model's other settings, auto-compact threshold and its OWN MCP switches (`mcpDisabled`, over a listing fetched under that member's own CLI and profile — never member 1's list), reorderable (rows keyed by an id that moves with the member, so a row's fetched lists and open picker go with it) and removable, capped at the daemon's `MAX_AGENT_POOL_EXTRA_MEMBERS` (a twin constant). A member's approval shows the node's until one is picked, and a new member starts at the node's auto-compact threshold (unset afterwards means never). Switching a member's CLI starts it from that CLI's defaults — approval included — keeping only the threshold, and a model change clears the window and parameters through the same `modelChangePatch` the card uses. A member whose CLI does not offer the approval mode it runs is flagged, since such a call may stop to ask. A pool is ONE label wherever a node's CLI is named — `claude +1`, every member (CLI · model · profile) listed on hover (`components/agent-pool-label.tsx`, on the canvas card and the agents panel's card). `node-validate.ts` names a member whose field carries a NUL. In a RUN, each call INSTANCE in the agents panel names the member it runs on (`AgentThread.member`, `instance-member`), and a call card's CLI badge does the same rather than naming the node's own CLI: `call_started` carries the member it starts on, each hand-off `system` row the member it moved to, and `call_result` the one that answered (`CallBlockEntry.member`, resolved through `TranscriptNodeMeta.pool`; off the window, `RunCallState.member`). A hand-off above the loaded page arrives as an ANCHOR (`ItemDao.callHandOffRows`) and is read for its member without being drawn — without it a call running on member 2 would be badged with member 1's CLI until it settled. Every member's MCP servers are reachable: the agents panel card's MCP dialog carries a member switch (opening on the member the live call runs on) and each member's switches and Sign in are addressed to THAT member's CLI and profile; the builder's per-member MCP chip signs in through the builder's one `useCliLogin`, the panel and busy row shown only in the member that started it. The run-time semantics are the daemon's (`apps/daemon/AGENTS.md`, the call runtime's *agent POOL* paragraph).

**The inspector's per-run settings are the COMPOSER's chips, in one band**: `chats/model-select`, `chats/effort-select`, `chats/approval-mode-select` and `chats/config-dir-select` — never builder-only look-alikes — wrapped in one bordered card under a single `Agent settings` label, with approval beside the model it belongs to. The card is not decoration: the chips are `ghost` (flat until hovered), and on the inspector's tinted ground a bare row of them reads as loose text.

Two behaviours follow the composer. There is no `workflows/model-select.tsx`: its free-text entry is `ModelSelect`'s `allowCustom` (the builder's case — a workflow runs for months, so naming a model the CLI does not enumerate is worth a field), and with it the chip's `default model` row, so "let the CLI decide" is an answer the builder can store. There is therefore NO model adopt — force-setting the first alias on a model-less node would overwrite that answer. Effort likewise has no adopt: an unset level is a real answer. And the **approval** modes come from the daemon's `approvals[]` — the capability the composer's chip reads — never a hardcoded list; `plan` is filtered out, being a `ChatApprovalMode` the workflow schema has no value for, so it cannot build a node the daemon refuses on save.

**MCP is behind a chip, but the READ is not.** The listing opens `components/mcp-dialog-button.tsx` (shared with the Agents panel, one component with an `icon`/`chip` trigger) rather than standing open in the panel. It deliberately does NOT gate the fetch on the press, the way the Agents panel does: `useNodeMcp`'s daemon refusal is the ONLY thing that can tell the user their config-directory path is wrong — claude CREATES a directory it cannot find and then reports "Not logged in" about it — so the read stays on selection and its 4xx renders under the chips, with the MCP chip suppressed while it stands. That error is routinely ONE unbroken token (the daemon's uniform shape carries the percent-encoded query string), hence `break-words`, or it runs past the 300px panel's right edge.

**A node's MCP switches are its OWN, and they write nothing the CLI keeps** (`workflows/node-mcp-switches.ts`, read by the inspector's MCP dialog and by each pool member's). Every row the profile loads carries a switch that edits the node's `mcpDisabled` (a pool member's own, for a member — member 1's list names another profile's servers), autosaved like every other node field; the daemon hands that list to the CLI for each of the node's turns (`AgentTurnInput.mcpDisabled`, see `apps/daemon/AGENTS.md`) and writes no config of the CLI's, so nothing changes in the user's terminal or in a chat. `withNodeSwitches` owns three things on a row and leaves the rest the CLI's answer: `disabled` is the node's choice; the lock is the daemon's per-row `turnToggleUnavailableReason` (codex's plugin servers, which only the whole plugin turns off) or, for a server the PROFILE itself has off, the sentence that a node can only switch servers off; and Approve is replaced by a sentence, since approving is per folder and the builder has none. A name the node switched off that the profile does NOT list (a run folder's project server, a server removed since) is SHOWN as an `off` row rather than dropped — the daemon still applies it to any server of that name a run loads, and a list the reader cannot see is one they cannot clear — but not while the listing is still dialling. Switching a node's or a member's CLI clears its list, since server names belong to that CLI's profile; changing only the profile keeps it, the stale names then showing as those `off` rows. `node-validate.ts` mirrors the daemon's refusal (empty, over 256 characters, any control character, more than 100 names). The run view's agents panel is untouched: its switches are the folder's, in the CLI's own config, and it does not show a node's own list.

### Settings

`settings/`, `notifications/` (the renderer half of the notifications module — see *System notifications* below), `autogenerated/` the generated daemon client + every daemon wire type (`pnpm generate:api`), `daemon-api.ts` which binds it to a launch handle, `daemon-client.ts` the WS client.

**Settings keys (`settings.json`).** `main/settings.ts` owns the file in the Electron userData dir; `shared/contracts.ts` holds its `Settings` shape (no daemon shapes — values whose vocabulary belongs to the daemon stay opaque strings on the Electron side, and the renderer validates them against the generated enum before they reach a run).
- **Composer memory** — `lastChatTarget`, `lastApprovalMode`, and `lastModels` / `lastEfforts` keyed PER CLI (the CLIs have disjoint model and effort vocabularies). `configDirs` + `recentConfigDirs` (the optional agent config directory, beside `projectFolder` / `recentFolders`) are ALSO per CLI, since the directories are not interchangeable — a claude profile handed to codex as `CODEX_HOME` is a signed-out codex writing into the claude profile. A file holding the older single `configDir`, flat recents or agent-less profiles is carried over on read, filed under the CLI whose `main/agents/` descriptor declares `ownsUnscopedConfigDirs` (claude).
- **Three hand-managed lists, three different features** — `fastActions` (a name and a description; see *Fast actions*), `runConfigs` (named new-chat setups; see *Run configurations*) and `configProfiles` (named agent config directories with a colour and their CLI, `agent`). Never fold any two together. Nothing adds or evicts an entry and the order is the user's, preserved on read rather than re-sorted like `recentFolders` / `recentConfigDirs`. `readSettings` salvages all three ENTRY-BY-ENTRY (`salvageList`, twinned with `salvageCliRecord`) and re-applies the array cap there: zod rejects an array wholesale on one bad element, and each entry is hand-written and unrecoverable.
- `agentOptions` — each CLI's own on/off switches (`{<cli>: {<optionId>: on}}`), whose ids, labels and defaults the daemon publishes on `GET /v1/capabilities` (`options[]`, from `AdapterConfig.options`); sent whole on chat create, workflow start and task-run start and snapshotted onto `Run.agentOptions`, so an open conversation keeps its switches (see *Agent options*).
- `notificationsEnabled` — ONE switch for both notification kinds (a question and a turn ending are the same interruption seen from two sides).
- `archiveRetentionDays` — `null` by default, because it arms a background sweep that PERMANENTLY deletes chats that many days after they were archived (no trash). A number of days, not a boolean. The daemon owns only the destruction (`POST /v1/chats/sweep-archived`) and learns the window from the client, since it never opens this file.
- `customInstructions` — the user's standing instructions to every agent (see *Custom instructions* below and the root `AGENTS.md` → *Agent instructions*).
- `theme` — `'system'` or a theme id, read by MAIN before a window exists (`native-appearance.ts` → `nativeTheme.themeSource`, `createWindow` → `backgroundColor`; see *Design system*). It is ENUMERATED in `settingsPatchSchema`, since a theme is a file this repo ships; a value from a newer build falls back to `'system'` rather than to a blank window.

**Removing a key from this schema DESTROYS what it held** — `readSettings` keeps only keys the schema knows and `writeSettings` rewrites the whole file — so any change that drops or renames a key migrates or exports the data first. A file that does not PARSE reads as the defaults, so `writeSettings` first copies an unparseable file aside to `settings.json.corrupt-<timestamp>` (0600, once per corruption) and refuses to write over one it cannot even read. **The exceptions on record are two clean breaks** with no carry-over; the next break migrates or exports first. What an agent must still know about them: a run made before `agentOptions` (which replaced `cursorMaxMode` and `claudeBrowserTools`, with the run and `node_state` columns that became `agentOptions` and `polled*`) holds none and runs each option at its default, and the chat settings PATCH carries no `agentOptions`; polled spend is re-priced from the account's last thirty days (`ACCOUNT_LOOKBACK_MS`); and a question card stored before its row carried `questions` renders as a plain permission body, Approve on one delivering the empty-answer placeholder.

`handoff-open.ts` — the ONE resolve-then-open-a-terminal helper, with ONE call site, in `chats/Chats.tsx`: handing a thread's conversation to the user's own terminal APP. A plain shell in a chat's folder is not this helper's: that opens a tab of the in-app terminal panel (*Terminal panel* above). Settings does not use it.

**Plugin servers are a group of their own in the MCP dialog, with an Add on each** (`components/mcp-plugin-list.tsx`, rendered by `mcp-section.tsx` as `From plugins`). Cursor's plugins load MCP servers in Cursor's own app that the sessions geniro runs never see, so the listing carries them as `plugins[]` beside the server rows, never AS rows — a row promises the agent a tool it will not have. The daemon's `interactiveOnlyNote` becomes the group's caption, the group opens itself while any server is not yet in the config, and Add copies one into the CLI's own `mcp.json` (`useAgentMcp().addPluginServer` → `POST /v1/agents/mcp/plugin-servers`), asking first for the plugin's declared variables — a list (`select`) where the manifest gives one. The daemon's refusal is shown beside that form rather than in the toggle strip. The graph builder's inspector passes no handler, so there the group is read-only: its listing is taken in no folder.

**Every MCP dialog carries an Add, which adds a server to the listing's PROFILE or edits its servers as JSON** (`components/mcp-add-dialog.tsx` over the pure `components/mcp-server-form.ts`; bound per surface by `chats/mcp-config-actions.ts`). It is drawn by `McpSection`'s header (`data-slot="mcp-add-server"`) wherever the caller passes `McpDialogButton` a `configActions` — the agents panel's card (the pool member the dialog's switch names), the builder's node inspector and each pool member's chip — and absent anywhere else. Both modes write at USER scope, the profile the rows came from (a CLI and its config directory), never a folder, and never a node's own `mcpDisabled`. **Add a server** is a form — name, then a command with one argument per line and `KEY=value` env, or a URL with `Name: value` headers — kept disabled with the reason until it is valid; the daemon runs the CLI's own `mcp add` where there is one. **Edit JSON** opens the profile's server map exactly as the CLI keeps it (claude's `mcpServers`, cursor's `mcp.json`, codex's `[mcp_servers]` read as JSON), names the file, parses as the user types, and saves the whole map at the version it was opened at — a document that moved since is refused with the daemon's sentence and the edit kept. It reads on entering the mode through a REF to the actions, since every caller binds them inline and an effect keyed on that object would re-read and reset the edit on each render. A write calls the listing's `onRefresh`, the daemon having already dropped its cached readings; a new OAuth server then shows under Needs sign-in with the ordinary Sign in. The editor shows the user their own credentials — it is their file — and keeps no copy anywhere.

**A Sign in press is answered by the BUTTON, not by the daemon's reply.** `useCliLogin.start`/`startMcp` set `login` only once `POST /v1/auth/login` returns, and the daemon holds that reply until the CLI prints its URL (`URL_WAIT_MS`, seconds) while a browser tab opens behind the window; the progress panel cannot exist yet, because there is no session to render. `CliLoginController.starting` fills exactly that window, set SYNCHRONOUSLY before the await (anything derived after it lands inside the gap it exists to cover) and cleared in a `finally`, so a REFUSED start does not leave a spinner over a sign-in that never began. Both buttons read it — the account card's (`agent-config-list`, `signingIn: CliKind | null`) and the MCP row's (`mcp-section`, `signingIn: string | null`) — and both go `disabled` as well as spinning, which is not cosmetic: a second press opens a second browser challenge and invalidates the first, the same reason the account card withholds its button entirely once the panel owns the flow. The flag is the CALLER's on both, because the controller is: one sign-in runs at a time across the screen, so a copy kept per section would let two of them each believe they own it.

**A server sign-in is settled by the DAEMON seeing the server connect, not by the CLI exiting** (`verifying` in `LoginStatusSchema`, drawn by `cli-login-progress.tsx` as "Finish signing in in your browser — checking the connection…"). claude's claude.ai connectors exit about a second after opening the browser, before anything is authorized, so a settle at exit is premature, and the renderer must not poll the listing itself. The daemon re-checks the one server with backoff and answers `succeeded` ("Signed in — connected") or an honest `failed`; `verifying` is not over, so the controller's poll simply keeps going, and `onSettled` does one narrow re-read of that row when it ends.

**Signing in never opens a terminal, on any surface.** `use-cli-login.ts` is the one controller — start, poll, submit a pasted code, cancel — over the daemon's `/v1/auth/login` (the account) and `/v1/auth/mcp-login` (one server), and `components/cli-login-progress.tsx` is the one panel that renders it. Every surface shares both — the Settings account card, the Agents panel's MCP dialog, and the transcript's own failure row. Never hand a sign-in invocation to a shell: nothing in the app watches that window, so a finished browser round-trip would change nothing on screen.

Two things about `Chats` in particular. It holds ONE controller instance for both of its flows, for the reason the hook holds a single sign-in at all — two browser challenges open at once are indistinguishable in the browser, and the second reads as the first having failed — so `onSettled` is handed the sign-in that settled and dispatches on `server` (a server's outcome is re-read from the LISTING, an account's from the CLI's own status; neither from an exit code). And the two panels render in different places for the same reason: the MCP one belongs in the dialog it was pressed in, while the account one is pinned above the composer rather than drawn on the error row that started it — that row is somewhere in a scrollback the user is free to leave, and claude's flow asks for a pasted code, which is unusable off-screen.

**An agent-specific setting lives in that agent's CARD**, never in a page section of its own (`AgentConfigListProps.agentSettings`), so everything a reader can change about a CLI is in the card named for it. A card reads top-to-bottom as which binary → how it behaves → whose account. The nodes are passed IN rather than built by the list, which is the rule the daemon's adapters follow as well — that component knows how to draw a card, not what is true of claude — and it is what keeps ONBOARDING, which shares the list, free of settings that belong to a running app: it passes none. Every such setting sits behind a disclosure, which is why the Settings spec opens a card before looking for one.

**Agent options** — each CLI's own on/off switches, stored as `Settings.agentOptions` (`{<cli>: {<optionId>: on}}`) and drawn in that CLI's card from the rows the daemon publishes on `GET /v1/capabilities` (`options[]` — id, label, description, default, all from the adapter's `AdapterConfig.options`), so no card and no setting names a CLI's switch. Examples: claude's browser tools (off by default) and cursor's Max Mode (on by default — it is a switch only because Cursor bills Max Mode at the model's API rate plus 20% on legacy request-based plans; off, a model runs at a smaller context window than in cursor's own CLI). The whole map rides chat create, session import, workflow-run start and task-run start beside `customInstructions`, read at the moment the run is created, and is SNAPSHOTTED onto the run, so a switch applies to the next chat and an open conversation never changes posture mid-thread. An option the map does not mention runs at its own default.

**Appearance** — one `Select` in General, offering System plus a row per theme, built from `shared/themes.ts` so a theme added there appears with no edit to this screen. A pick does two things and they are not the same write: `persist({ theme })`, after which MAIN re-applies `nativeTheme.themeSource` and the renderer's media query repaints on its own; and `setThemePreference`, which is what makes the change immediate for a theme whose name the media query cannot report (it can only answer light-or-dark). The screen guards the mount read with its own `themeDirtyRef`, like every other field here, and — unlike `customInstructions` beside it — applies NO `??` default: `readSettings` merges `DEFAULT_SETTINGS` on every path, so `theme` is always present and a fallback would be unreachable. `customInstructions` earns its `?? ''` because its `.length` is read on the very next render.

**Custom instructions** — the Settings section holding the user's standing instructions to every agent (`Settings.customInstructions`, an `ExpandableTextarea` since it is a prompt-length field). Saving goes through `use-debounced-persist.ts`, which is where the debounce, the latest-value ref, the unmount flush and the dirty guard live once rather than per field: an UNSAVABLE value (one carrying control characters `settingsPatchSchema` refuses — there is no length limit) is held on screen and never written, and the timer handle is NULLED rather than merely cleared — otherwise a legal edit followed by an unsavable one flushes the unsavable text on unmount. The section says so beside the field. It also carries **Remove from existing chats** (`POST /v1/chats/forget-custom-instructions`), the purge for text already snapshotted onto earlier runs — a press, never a consequence of clearing the box, since it discards the per-run snapshot guarantee. It is read at the MOMENT a run is created (`currentRunSettings()` in `chats/Chats.tsx`, used by chat create, session import and workflow-run start) rather than cached in component state — `Chats` stays mounted across nav switches, so a cached copy would start a chat on text Settings had already replaced. The section also PREVIEWS geniro's own host preamble, read from `GET /v1/capabilities` (`hostPreamble`) rather than restated here, and renders nothing at all until that read lands: an empty box captioned "geniro already tells every agent this" would state that the app sends nothing, which is the opposite of true. See the root `AGENTS.md` → *Agent instructions* for what the preamble claims and why it must contradict the CLI's own prompt by name.

### macOS packaging

**macOS packaging**: `pnpm --filter @geniro/ui build:mac` runs `scripts/build-mac.mjs` — two self-contained `pnpm deploy` stagings (shell app + daemon under `Resources/daemon`), each `pnpm --filter <pkg> --config.inject-workspace-packages=true deploy --prod <dir>`; Electron-ABI rebuild of better-sqlite3 in the daemon staging; `.icns` generated from `resources/icon.png`; signing (below); no `publish` feed; DMG + zip into `release/dist/`. Never pass `--legacy` to that deploy: the legacy deploy ignores the lockfile and RE-RESOLVES every `^`/`~` range against the registry, so a release ships dependency versions no build, test or CI run ever executed (one such release shipped a daemon that never finished booting); the modern deploy copies the workspace's own installed tree and needs `inject-workspace-packages`, passed per invocation. The Homebrew cask + install script strip the quarantine bit so the un-notarized app launches. The packaged app presents as **"Geniro"** on every macOS surface (menu bar, Dock, About, Finder) via electron-builder `productName`.

**The build is signed so that macOS can tell one release from the next.** Every privacy grant is recorded against the app's DESIGNATED REQUIREMENT, and re-asked the moment a running build stops satisfying the requirement its grant was recorded under. An ad-hoc signature's requirement is `cdhash H"…"`, the hash of its own bytes, so every ad-hoc release — reinstall or self-update — re-asks for every permission. `scripts/make-signing-identity.mjs` creates the one **self-signed** certificate every release is signed with (free — no Apple account; the requirement is evaluated against the certificate embedded IN the app), and `GENIRO_SIGN_IDENTITY` names it to `build-mac.mjs`. Three things hang together there and are one branch for that reason (`.claude/rules/packaging-config.md`): the identity, `forceCodeSigning` — without which electron-builder answers a missing identity with a WARNING and an unsigned artifact that installs perfectly and silently resets every user's permissions — and a read-back of the packaged bundle's own requirement, asserted against the arm that was taken. Still **not notarized**: a self-signed certificate is not a Developer ID, so Gatekeeper's verdict is unchanged and the quarantine stripping stays. A local build with no `GENIRO_SIGN_IDENTITY` is ad-hoc, and says so.

**A grant made under an ad-hoc build is dead, and it looks granted.** TCC stores the requirement alongside the decision, so a row recorded against an ad-hoc build keeps its `cdhash` forever while every signed build fails it: the switch in System Settings stays ON and access is refused anyway, and Screen Recording never re-prompts. Electron's `systemPreferences.getMediaAccessStatus('screen')` just says `denied`. Diagnose from `tccd`'s own log while reproducing the refusal (`/usr/bin/log stream --level debug --process tccd` — `log` is a zsh BUILTIN, so the absolute path is required):

```
Failed to match existing code requirement for subject io.geniro.desktop and service kTCCServiceScreenCapture
For io.geniro.desktop: matches platform requirements: No
Service kTCCServiceScreenCapture does not allow prompting; returning denied.
```

The fix is one-time and belongs on the machine, not in this repo: `tccutil reset <Service> io.geniro.desktop`, then RELAUNCH the app (a running process does not see the new decision); the next request records a requirement that names the certificate and survives every later release. Stale rows are per SERVICE and cannot be enumerated (the user TCC.db will not open) — each is found only by provoking that service (Screen Recording and Accessibility are the usual ones). The requester is often not the app's own code: a CLI agent running `screencapture` is attributed to the process tree's responsible app, which is Geniro.

**A lost FOLDER grant looks like a crash, not a permission error.** `realpath`, `stat` and `access(R_OK)` succeed on a TCC-denied folder and only opening it fails with `EPERM`, and claude started in such a folder exits in milliseconds with `error: An unknown error occurred (Unexpected)`. So `resolveValidDirectory` OPENS the folder and refuses with `FOLDER_NOT_READABLE` naming System Settings → Privacy & Security, and the `Info.plist` carries the folder purpose strings (`extendInfo` in `electron-builder.yml`). The repair is on the machine: allow Geniro under Files and Folders (or Full Disk Access), or `tccutil reset SystemPolicyDesktopFolder io.geniro.desktop` and relaunch.

### App updates

**App updates** — the app notices a new release, says so, and applies it on one click.

**electron-updater is not used.** Its macOS path is Squirrel.Mac; what replaces it already verifies its own downloads and handles what Squirrel does not know about here (a translocated or read-only install is answered with `brew upgrade`, not a button that fails at the last step). It is `scripts/install.sh`'s own sequence moved in-process — resolve the release, download the `-mac.zip`, verify it against the published `SHA256SUMS.txt`, stage it beside the app, strip quarantine, and put it in place when the app quits — split across three files by what each can be tested without: `updater.ts` is the feed alone (no filesystem), `update-installer.ts` is the stage and the swap alone (no policy), `update-service.ts` is the policy alone (every dependency injected, so its specs need neither network nor bundle).

The rules the code exists to hold:

- **The running bundle is never replaced while the app runs — an install STAGES, and the quit applies.** After `app.asar` is swapped under a live window, the renderer reads the NEW archive at the OLD archive's offsets (lazily-imported chunks throw `SyntaxError`s), while main is fine because it holds the archive through an fd; the daemon has the same exposure through anything it requires lazily from `Resources/daemon`. So `stageUpdate` unpacks the verified release and copies it to `<bundle>.new-<pid>` BESIDE the app (same volume, so applying it is a rename), and `applyStagedUpdate` runs from `will-quit` in `index.ts` — after every window has closed and the daemon has stopped — as two renames and no copy. The Restart button is only a relaunch; its quit takes the same path, and so does any other quit.
- **An automatic check is SILENT unless something changed.** The renderer's subscriber (`useUpdateState`) sits in `App`, at the root, so every push re-renders the whole tree. `checking` draws nothing (`footerUpdate` maps it to `{kind:'none'}`); scheduled callers use `check({ announce: false })` (a check the USER pressed still announces — the Settings button reads "Checking…" and disables itself off that phase); and `emit` compares the merged state against the previous one and broadcasts only on a real difference, since the patch is a fresh object every time.
- **Every deletion runs with `process.noAsar` raised — under Electron, `fs.rm({recursive})` does not delete an `app.asar`, it walks INTO it and never returns.** Electron's `asar-fs-wrapper` patches `lstat`/`readdir`/`internalModuleStat` so an archive reads as a directory, and `fs.rm` descends into tens of thousands of virtual entries — it neither fails nor finishes, so an install whose cleanup hits one never resolves. `withoutAsar` wraps every `rm` in `update-installer.ts` and REFCOUNTS, because `process.noAsar` is one global flag and the sweep deletes concurrently — a naive set-and-restore re-enables asar under trees still being walked. The UI suite runs under node, where the bug cannot show, so the spec pins the FLAG.
- **`ready` is an ENDING that a check may not undo.** The version compared against is the RUNNING app's, and staging a release does not change it — the relaunch does. So `check()` returns early on `ready` without asking the feed (otherwise every check re-discovers the staged release, turns Restart back into Update, and re-downloads it); a newer release is picked up after the restart.
- **A release is not a release until its macOS archive is attached, and the check reads the release LIST.** The workflow's `create-release` cuts a **draft**, and `build-app` publishes it (`gh release edit --draft=false --latest`) as its LAST step, after the upload; a draft is invisible to `/releases/latest`, the release list, `scripts/install.sh` and Homebrew, and a failed or cancelled build leaves a draft rather than a broken release. Defence in depth on the updater side: `fetchLatestRelease` reads `/releases?per_page=10` and returns the newest release carrying an archive, filtering drafts and pre-releases itself and ordering by parsed VERSION rather than the feed's tag-date order, so it cannot disagree with `isNewerVersion`. Only a page with no installable release at all is an error the user sees, and that error NAMES the tag when there is one.

  **Offering the newest good one is not the same as being up to date.** With the newest tag unarchived, the newest INSTALLABLE release can be the running build, so `fetchLatestRelease` answers BOTH questions off the one page — `release`, the newest it can install, and `published`, the newest tag at all (`readPublishedVersion`, kept separate from `readRelease`; drafts and pre-releases excluded from both, or a nightly would leave every stable install permanently "behind"). The phase stays `up-to-date` (nothing is downloadable, so no Update button) and carries a MESSAGE naming the pending version, which Settings renders after the status line; an EQUAL tag stays silent (pinned).
- **A release with no `SHA256SUMS.txt` is REFUSED, never warned about.** The build is not notarized, so the published digest is the only link between the release that was built and the code about to execute as the user. `install.sh` degrades to TLS-only with a warning because a human is watching it; nobody watches this. A build job that stops emitting the file disables updating rather than weakening it.
- **The old bundle is moved aside, never deleted first.** The first rename is the commit point; a failure of the second renames it back, so a swap that fails at quit costs the new version rather than the user's installed app. The backup is removed last and only on success.
- **`canInstall` is asked of the filesystem, per use.** An app installed by another account, on a read-only volume, or running TRANSLOCATED (macOS's read-only synthetic mount for a quarantined copy, where a "successful" update writes to a volume that vanishes at quit) gets the `brew upgrade --cask geniro` sentence instead of a button. It is still TOLD, in the window: `footerUpdate` returns a `readout` for that case, which the title bar's update control (`components/update-control.tsx`) draws as a non-pressable glyph carrying the sentence on hover.
- **Main owns the state; the renderer reports presses.** One `UpdateState` is pushed at every window, so the title bar's update control (`renderer/updates/update-status.ts` → `footerUpdate`, read by `App`) and the Settings section are two renderings of one download rather than two pollers — the same split as notifications. There is no DISMISSAL: the offer lives in the title bar at the size of a control, with nothing to wave away.
- **A phase that stops moving becomes an `error`, and abandoning it means CANCELLING it.** Main owns the state, so a wedged phase survives a renderer reload. Each non-terminal phase carries a deadline (`checking` 60s, `installing` 10min, both flat since neither reports progress; `downloading` a 3-minute STALL budget re-armed by every progress callback, so a slow transfer takes as long as it takes). The re-arm reads the RAW callback, never the published `progress` (a server with no content-length leaves `fraction` null). When one trips, an `attempt` counter is bumped, so the hung call cannot write `ready` over the failure already shown, AND an `AbortController` fires, so the abandoned work really stops — otherwise a retry could run a second `ditto` into one bundle. `install()` accepts `error` as well as `available` when a release is held: the title bar's Retry control IS that call.
- **The debris sweep is at LAUNCH, because the install's own cleanup is allowed to fail.** `stageUpdate` discards its scratch in a `finally` and `applyStagedUpdate` its backup on the way out, both best-effort (a cleanup that throws would report a completed update as failed, and macOS holds freshly written bundles open). `sweepUpdateDebris` runs from `main()`, ungated by the auto-check setting, matching only the names this code writes — `update-*` under the work dir, `<the app's own name>.old-*` and `.new-*` beside the bundle (never this launch's own staging), which `Geniro.app` itself cannot match.
- **A failure names the phase that FAILED, and one function composes the sentence.** `UpdateState.failedPhase` is DERIVED inside `emit` from the phase the service was in (never passed by each error site), and the lead reads "The update check failed." / "The download failed." / "The update could not be installed." accordingly. `updateStatusText` is the one composition, used by both the title bar's hover and the Settings line. It joins an error with a COLON, because main writes those messages as fragments meant to follow a lead; never capitalize the fragment (it carries acronyms, shell commands and absolute paths).
- **Main's update failures go to the daemon's log, never to stdout** (a packaged Finder launch discards main's stdout). `UpdateService` takes an injected `UpdateLog` (wired in `index.ts` to `reportMainLog`, which buffers until the daemon exists) and writes the check failure, the install start and end (`update-install-started` / `update-installed` — a start with no matching end is a hung install), the install failure, every watchdog trip and the launch sweep into the `ui` channel, where the debug panel shows them.

Nothing installs unasked: the check is automatic (launch + every 5min, gated on the `checkForUpdates` setting, which re-arms the schedule the moment it is flipped), the download is not. The Homebrew cask carries `auto_updates true` so `brew upgrade` stops reinstalling over an app that has already updated itself.

### System notifications

**System notifications** — a macOS banner when an agent stops to ask something and when a thread's turn ends. **One module, split across the two processes by what each can answer**: `renderer/notifications/` decides WHEN (`run-notifications.ts` — pure rules over the DISPLAY statuses the sidebar badges show, never the daemon's row, so a banner and the row it sends you to cannot describe one run differently; `use-run-notifications.ts` — the thin React binding, mounted from `Chats`, which stays mounted across nav switches so a thread finishing while the user is in Settings still reports), and `main/notifications/` decides WHETHER and does the posting. Whether it becomes a banner is read from `notificationsEnabled` at the moment of the post rather than cached in the renderer, so a flipped switch takes effect on the very next question. Three rules, each a defect if dropped: a run **seen for the first time never notifies** (the chat list loads with every past thread already finished); a turn the user **cancelled** is not announced (`failed` IS, since nobody asked for it); and the chat the user is **already looking at** is skipped only while the window has focus AND the Chats view is on screen (suppression is about watching, not about which chat is open). The sidebar's unseen mark still skips the open chat on any screen, since a mark on it would be one nothing clears. Clicking a banner raises the window in main — a renderer in a hidden window cannot show itself — and sends the run back over `onNotificationActivated`, which `App` reads for the view and `Chats` for the thread. `notifier.ts` is the only file that touches a notification API, and it uses Electron's own `Notification`, never `node-notifier`: that posts through a bundled `terminal-notifier.app`, so the banner (and the per-app switch in System Settings) is attributed to the helper, it ships a nested Mach-O binary into an app with no Developer ID, and its click cannot raise this window. No banner renders on a Mac while the display is shared or recorded (`dndMirrored: true` in `com.apple.ncprefs` suppresses every app's) — that is macOS, not this code.

**A turn that finishes with a command still running is announced PROVISIONALLY, and the banner is withdrawn if the run goes back to work** (`endingIsProvisional` in `run-notifications.ts`, applied by `use-run-notifications.ts`; withdrawn through `retractNotification` → `NotificationService.retract`, which closes the banner and so removes it from Notification Centre too). Nothing on the wire tells "waiting on its own background command" from "finished, and left a dev server up": claude reports `idle` right after launching the command, then later a continuation whose result says `origin: task-notification`. Do not guess with a timer or a launch-time window. Both are announced at the ending, the body says so ("… (1 command still running)"), and what the run does NEXT settles it: a settled run going back to work — the CLI's continuation, or the user's own message — withdraws the banner, and the continuation's ending is announced like any other. The AGENT can say it in its own words: its `notify_user` call arrives as `RunStatusEvent.notify`, `use-chat-run` queues it as an `AgentNotice` with a growing id (so a re-render cannot post it twice), and it is posted as its own banner in place of the plain ending. A `failed` ending and a question are never provisional. The sidebar's unseen mark (`use-unseen-runs.ts`) is unaffected.

**Two things the notification rules are fed that the sidebar does not show.** The OPEN thread's ending reaches the renderer as its terminal ITEM before the settle announce that carries its `housekeeping` flag and closing words, so `use-chat-run.ts` marks a run going back to work as `settleOwed`, and `use-run-notifications.ts` (`settling`) HOLDS its turn-end until that settle — or a listing that reports it settled, which covers a missed announce — then posts or drops it by that settle's own flag (a quiet `/compact` turn is not announced, and a real turn is not worded from the previous one's summary); a question is never held, and a held ending is dropped if the run goes back to work. And the rules and the unseen marks read `runs + offScopeRuns`: a row the current archive SCOPE leaves out is kept (not under `Show all`, never once this window saw it deleted) and patched by the same announces, because both hooks read "absent" as "deleted". What remains out of reach is a run this window has never listed at all.

### Sidebar

**The UNREAD mark is the DAEMON's, so every device shows the same one** (`chats/unread.ts`, `chats/use-unseen-runs.ts`; the daemon half is `POST /v1/chats/:runId/seen` in `apps/daemon/AGENTS.md`). A row is unread while its `attentionAt` (stamped when the run finished, failed or asked something) is later than its `seenAt` (stamped when any device opened it); both ride `RunDto` and the `run_status` broadcast, and a row only ever moves them FORWARD (`laterInstant`). Never compute it per window from received broadcasts. The open thread counts as looked at only while somebody can SEE it — Chats on screen and the window visible AND focused (`useWindowWatched`) — and that is also when the look is reported (`markRunSeen` in `use-chat-run.ts`: an optimistic catch-up to the row's own `attentionAt`, then the POST): on opening a thread, on coming back to the window, and on a fresh mark arriving while watched. A thread left open on a desktop nobody is at therefore stays unread on the phone. A thread's turn-end BANNER stays per device (`use-run-notifications.ts`); composer drafts and the message QUEUE are per device too (localStorage).

**The ARCHIVE is the sidebar's other axis, and it replaced Delete as the row action** (`chats/chat-scope-filter.tsx` over the shared `components/ui/menu.tsx`; `chatScope` / `showScope` / `addRun` / `placeRun` / `dropRun` in `use-chat-run.ts`). A thread is SHELVED rather than destroyed: an icon in the sidebar header's control row picks how much of the archive the list covers (`GET /v1/chats?scope=`), and the one-way delete lives in the archive alone — a live row offers Archive, an archived row offers Unarchive and Delete permanently. **Workflow rows archive too**, with their Delete behind the archive like the chats'; both halves of the listing take the same scope (`workflowApi.listWorkflowRuns({ scope })`), since a scope is about how much of the shelf to show, never about the run kind. What stays per-kind is the dialog's WORDS (`archiveDialogCopy`): a workflow run is stopped as a RUN — every agent still working in it — where a chat's cancel is one turn.

**Three scopes, not two, and an ICON rather than a band.** A labelled run of options is a band of chrome that a list filter in a 260px column does not earn (the general rule is in `.claude/rules/renderer-components.md`). A BOOLEAN could name only two of the three answers, and the one it cannot is `Show all` — a shelved thread found IN PLACE beside the live ones. `active` is the default and the only scope that hides anything.

Four things about it are load-bearing, and the first two are the disjoint-listing rule and its LIMIT. `refreshRuns` carries a GENERATION and drops a resolved fetch that is no longer the current one: the active fetch runs the pull-request capture pass over every run, so it is routinely still in flight when the user reaches the archive, and landing it there would fill the archive with rows that do not belong. `addRun` leaves the shelf instead of prepending, since a new run is never archived — but only from `archived`, because `all` holds it. **And `placeRun` is where the rule stops**: archive and unarchive re-file a row rather than dropping it, keeping it where the current scope still holds it (under `Show all` a thread must not vanish on being archived). `dropRun` is for the permanent delete alone. The ROW's own actions are read off `run.archivedAt`, never off the scope: under `Show all` both kinds are listed together.

Two consequences of the third scope. A scope switch **keeps the open thread** when the new scope still lists it; a thread the new scope does NOT hold is closed, because it would otherwise render with its row absent from `runs`, losing the header (title, status, Stop) and leaving the archived-composer gate reading `undefined`. And the rows on screen are **not blanked** during a switch: the active listing's first capture sweep takes seconds, and an empty sidebar for that long is worse than stale rows.

The fourth is that **an archived chat is inert**. The daemon refuses `POST :runId/messages` with `RUN_ARCHIVED`, so the composer of an open archived thread is disabled with a placeholder saying so, and the shelf above it carries the one control that undoes that. It is read off the ROW (`activeRun.archivedAt`) rather than off the scope. Archiving a RUNNING chat asks first, because it cancels the turn — the one irreversible thing archiving does; a settled chat is filed away in a single press.

**Sidebar groups** (`chats/run-group.ts`, `chats/group-header.tsx`, and the `run_groups` rows behind them) — the folders a user files their threads into, with a colour, a fold, an order, a live "is anything in here working" reading, and an optional rule that files new chats by the folder they start in.

**A WORKFLOW claim outranks every folder claim** (`RunGroupsService.resolveAutoGroupId`, whose own doc block says so). A group may name a workflow by slug (`autoWorkflowId`) as well as a folder, and a run of that workflow is filed there before any folder rule is consulted — a workflow run's `cwd` is whatever one of its nodes named, so the folder says nothing about what the run IS. Everything below is the folder half.

**The auto-file rule matches a folder AND everything inside it, most specific first.** When two groups both claim a run the longer `autoCwd` wins (so a group on `~/work` and one on `~/work/app` can coexist); sidebar order breaks a genuine tie. Containment is SEGMENT-wise (`utils/path-within.ts`) — a plain `startsWith` would file `/work/app-old` into the group that claimed `/work/app`. Both sides are canonicalized at the moment they are CHOSEN (`autoCwd` when it is set, `cwd` when the chat is created), so no read path touches the filesystem, and a rule pointing at a folder that does not exist is refused rather than stored. Adding a rule deliberately does NOT sweep up existing chats in that directory — it says where the next one lands, and must not undo the user's own filing.

**Deleting a group releases its chats**; it never takes them with it. The release runs BEFORE the row is dropped, since the reverse order leaves a window in which a run points at a group that no longer exists and a crash inside it makes that permanent.

**Everything moves by dragging, and the DROP ZONE is the whole section.** A header dragged over another group REORDERS, and the list rearranges under the cursor — the daemon is told once, at `dragend`, because the intermediate arrangements are not decisions. A chat dragged into a section FILES ITSELF there; there is no "move to group" row menu. The section — header, rail, rows and the space between them — is one `li` carrying the `dragover`/`drop` pair (a target on the header alone leaves an expanded group's BODY inert); `dragover` bubbles, so one handler covers every child, and an empty group is dropped onto through the same section. One piece of drag state carries the KIND, because the same header is a drop target for both gestures and they do different things. A drop that changes nothing writes nothing. Neither a group nor a chat is draggable while its name is being edited (a text field inside a draggable element cannot be selected with the mouse). The row menus stay (they are the keyboard path, and the only one that can reach `New group…`).

**A group header reads its state from the BADGES its rows are showing, never from the daemon's `status` column** (`runGroupSummary` over `sidebarRunStatus`). The column and the badge disagree in exactly the cases that matter — a live turn under a stale `completed`, a run parked on a question — so a header computed from the row would contradict its own children. `needsInput` is reported ALONGSIDE `busy` rather than folded into it, so a collapsed group never hides the one state that cannot advance without the user.

**A group's chats are enclosed** — indented, hung off a rail in the group's own colour (`GROUP_RAIL_CLASS`) — so an expanded group does not run straight into the next. The section's bottom padding is PERMANENT rather than part of the drop highlight (adding it only while a drag hovers would shift every row at the moment the user is aiming). The highlight is `muted` and a hairline — never `accent` (reads as a coloured state) or a 2px ring (reads as an error). An EMPTY group draws no rail; its header is the drop target either way. The count sits against the name it counts, not pushed right by `flex-1`. Colours are NAMES on the wire and tokens in the renderer (`--group-*`, aliases of the avatar hues so a group dot and an agent avatar cannot drift into two different blues).

**A group's options are a PANEL, not a row list** (`Popover`, `anchor="viewport"`). The auto-file rule is a stated section: a caption in words, the path as a label, and two small buttons that say which is which (choose another, remove) — never a menu row labelled with the path whose action reopens the picker. `anchor="viewport"` measures the trigger and places the panel `fixed`, the only way out of the chat list's scroll container (never cap the panel's width to fit the clip instead). The colour rows stay a `Menu` on the DOT, so the panel's own rows — the delete among them — are not scrolled out of sight.

**Deleting a group asks first**, in a dialog that leads with what is NOT deleted ("Its 2 chats are kept — they move to Ungrouped with all their history"). Nothing is destroyed; the confirm exists because *delete* reads as final, and the menu row says so too (`Delete group · keeps chats`).

### Daemon supervision

`DaemonSupervisor.start()` reuses a still-healthy daemon left by a prior UI instance (pid + `/health/check` + identity + bundled `version` + the pidfile's `entry` stamp), sweeps stale pidfiles, and only tears down the process it owns. **The `entry` stamp is what makes "is this the current build" answerable at all**: `version` is the package version and is identical across every rebuild, so without the stamp a rebuilt daemon is adopted over and the app serves the previous compile. A daemon started from the SAME entry path whose mtime/size have moved is a rebuild and is replaced; one from a DIFFERENT path (`pnpm daemon:dev` on TypeScript source) is left alone; one reporting NO stamp predates the check and is replaced. The other half is in `turbo.json`, where the `dev` task carries `dependsOn: ["^build"]` — `dist/main.js` is produced by `pnpm build` alone and never by `electron-vite dev` — and the `@geniro/daemon` dependency in `apps/ui/package.json` (which imports nothing) exists solely to give turbo that ordering edge. **That edge only exists when the launch goes THROUGH turbo**, which is why the root `dev` script is `turbo run dev --filter=@geniro/ui` and must never be "simplified" to `pnpm --filter @geniro/ui dev`: pnpm runs `electron-vite dev` directly and the app launches whatever compile is on disk — which the `entry` stamp cannot catch, since a `dist/` nobody rebuilt is stale before any daemon starts. The supervisor also passes `GENIRO_IDLE_EXIT_MS` to every daemon it spawns: a daemon it does NOT own (left by a force-quit or a crash) is one it can never stop, so the daemon must be able to stop itself. On macOS `window-all-closed` does not quit, so the app can outlive its daemon's idle window — `app.on('activate')` re-ensures the daemon (`ensureDaemon()`, the one path both launch and reactivation take) before the window can talk to a dead handle. **And on darwin ⌘W HIDES the window rather than destroying it** (`createWindow`'s `close` handler, gated on `isQuitting`, which `before-quit` sets first): every notification is decided in the renderer (`use-run-notifications.ts`), so a destroyed window would silence every banner. `activate` shows the hidden window again instead of creating a second one.

**A daemon the app OWNS is brought back when it dies, and one nobody can start is never a dead end.** An unexpected exit of an owned daemon respawns it with a capped backoff (1s → 30s, then Retry is the way back; a daemon that served a minute earns a fresh budget), while every exit the app asked for — stop, restart, quit, and the daemon's own IDLE exit, which arrives as a SIGTERM Nest re-raises — is left alone. A CRASH arrives the same way (the crash guards SIGTERM the daemon so its hooks run), so it first leaves its pid in `<userData>/daemon-crashed` and the supervisor respawns an exit whose mark names that daemon (`consumeCrashMark`). Before every signal it sends a daemon it has seen serving, and when it respawns one that crashed, it writes WHY to `<userData>/daemon-stop-cause` (`writeStopCause`: `quit`, `self-update` — set by the update's relaunch through `createUpdateService`'s `beforeRelaunch` — `restart` or `crash`), which the next daemon's boot reconcile reads to decide whether a card that stop cut off may be continued unattended (see `apps/daemon/AGENTS.md`). Retry calls the `ensureDaemon` IPC (allowed for a phone, with the token blanked, since it only starts a daemon where none answers). `start()` joins an in-flight restart instead of racing it (racing would adopt the restart's own child as not-owned, which then outlives quit), and a pidfile whose pid is ALIVE but proven to be a different process (start-time mismatch) is swept rather than refused on every launch. `stop()`'s wait for a start is bounded, and `login-shell-path.ts` spawns the interactive shell with stdin on `/dev/null` and SIGKILLs it at its deadline — a `.zshrc` that reads stdin would otherwise hang daemon start and ⌘Q, since an interactive zsh ignores the SIGTERM `execFile`'s timeout sends. `before-quit` runs its steps through `quit-teardown.ts`, each isolated, with `app.quit()` in a `finally`, so one step throwing cannot swallow every later ⌘Q.

### Security

**`SAFE_CONFIG` is a repository's drivers emptied, not a list of names** (`git-safe-config.ts`). Refusing `core.fsmonitor` by name alone leaves the repo's own `filter.<name>.clean` drivers running on an ordinary `status`/`diff`, so drawing the branch chip for a cloned repository would run its code. Every read-side git call reads the repository's `filter.*` config and empties each driver (`clean`, `smudge`, `process`, and `required=false` so an LFS-style required filter does not fail the read), passes `--ignore-submodules=dirty` (a checked-out submodule's own config runs otherwise), and refuses a repository whose driver name git cannot address by `-c`. Drivers from the user's GLOBAL config (git-lfs lives there) still run, and actions the user presses — switch, pull, stash, the worktree rescue commit — keep the repository's filters and hooks exactly as their terminal would. Reads also run with `core.hooksPath=/dev/null`, so a repository's own `post-index-change` hook never runs on a read. A task worktree is committed and removed only while its HEAD is the task's own branch with no rebase, merge, cherry-pick or revert half done; a detached HEAD's commits are reachable from nothing once the worktree's reflog goes with it, so such a worktree is KEPT.

**The renderer has no network outside loopback and the fixed artifact library CDNs, WebRTC included** (`network-lockdown.ts`). An artifact page is agent-authored script in a sandboxed frame under `ARTIFACT_PAGE_CSP`, whose `connect-src` is shut, but CSP does not govern `RTCPeerConnection` (STUN/TURN to an arbitrary host). The lockdown is three measures because each alone leaks: `disable_non_proxied_udp` on every WebContents, a black-hole SOCKS proxy on the default session with loopback direct, and a process-wide `host-resolver-rules` mapping every name but `localhost`/`127.0.0.1` to NOTFOUND. Nothing the app does needs Chromium DNS — the window loads a file or the local dev server, the updater uses Node's fetch, links open in the user's browser — with ONE exception: an artifact page loads its libraries and fonts from the fixed CDNs its CSP admits, so those hosts (`ARTIFACT_CDN_HOSTS`) are excluded by EXACT name from the resolver rules and bypass the black-hole proxy, and `network-lockdown.spec.ts` reads the daemon's `ARTIFACT_PAGE_CSP` to keep the two lists identical. Anything else added later that loads a remote host THROUGH Chromium will fail to resolve, deliberately.
