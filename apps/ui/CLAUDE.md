### Main process

`src/main/` — `index.ts` (app lifecycle), `daemon-supervisor.ts` (spawn/adopt/health-poll/orphan-sweep), `daemon-pidfile.ts` (reads + validates the daemon's pidfile), `settings.ts` (`settings.json`), `purge-legacy-secret.ts` (deletes the one Keychain entry earlier versions wrote — see *Storage split* in the root `CLAUDE.md`), `cli-detect.ts` (per-CLI binary + version, plus whether the CLI reports itself signed in, for a CLI that can be asked — `loggedIn` is three-state, and `null` means UNKNOWN rather than signed-out, because a failed probe must not tell a signed-in user to sign in; the answer is read from the CLI's own STRUCTURED reply (`cursor-agent status --format json` → `isAuthenticated`), because its human output has a third `partially-authenticated` state that matched neither wording and read as ready), `probe-env.ts` (the main-side twin of the daemon's `child-env.ts`: a probe child gets its OWN agent's credentials and never the other's — `detectClis` runs an authenticated `status` call, so it must not hold a rival agent's token; `neutralEnv()` beside it applies the same rule to a child that is not one of the agents at all — `gh` makes an authenticated call to GitHub and owns nothing on the list, so it keeps nothing), `git-info.ts` (the composer's branch chip: repo/branch/branches/dirty, plus a branch switch GUARDED by a re-read dirty check — and `git switch`, never `git checkout`, which would resolve a branch name as a pathspec and restore a file instead; plus `pullBranch`, the "bring this branch up to date and keep my changes" the refusal now offers: stash → `git pull --ff-only` → stash pop. `--ff-only` because a fast-forward is the only pull that cannot leave a repository in a state the user then has to resolve — no merge commit they did not ask for, no half-finished rebase — and what to do about a divergence is not a decision a button in a chat composer gets to take. The stash goes back on EVERY path INCLUDING a failed pull: hiding the user's work and then failing before restoring it looks exactly like the edits were destroyed. Whether the tip is THIS pull's entry is decided by `pullStashIsOurs` — the stash ref having MOVED *and* the tip's subject ending with `geniro: pull`. Neither alone: git's own prose is locale-dependent, a push on a tree that is not really dirty exits 0 having created nothing (reachable, since a failed `git status` reads as dirty) so a leftover entry still carries the message, and a concurrent `git stash` moves the ref. A failed push aborts the pull rather than running it unprotected. `BranchSwitchResult.dirty` is what tells the renderer the refusal is the guard working rather than a failure — it drives the amber tone and the Pull offer. `BranchSwitchResult.worktree` is the second such field, and it OUTRANKS the dirty guard: git will not check one branch out into two worktrees, so committing or pulling cannot help and the Pull offer would be a control with no way to work. It is decided from `git worktree list --porcelain` (also read into `GitInfo.worktrees`, which is what marks those rows in the picker) rather than from git's own `fatal: '<branch>' is already used by worktree at …`, which is translated prose — the same rule `pullStashIsOurs` follows. The renderer answers it with the one thing that CAN work: an offer to point the run at the worktree that already holds the branch. Not on the saved-configuration path, which names a folder of its own — there the sentence states the path and stops), `github-prs.ts` (the **pull requests** the chat surfaces name — `gh pr list` in the run's folder, parsed into `PullRequestsResult`. Its own file rather than more of `git-info.ts`: that one reads local refs on a 5s budget, this one is a network client on a 15s one. ONE query per folder, head-filtered: `--state all --head <branch>`. A thread is one folder on one branch and every surface is scoped to that, so the repo's other branches are never fetched — asking for the repo's `--state open` and `--state closed` lists was the first shape and was rejected in use ("i need to show prs only related to current thread"): three round trips to collect fifty rows that were then filtered down to one and, because a `--limit` has to be applied somewhere, needing this same head query underneath them anyway so the branch's own pull request survived the truncation. `--state all` because a branch's HISTORY is the point — the merged pull request under the open one that replaced it, which is the ticket's own "merged PRs should be collapsed"; each row carries its own state, which is what separates them again on screen. A detached HEAD spawns NOTHING, the branch being the query's own argument. The folder's `origin` OWNER rides along (`readOriginOwner`, parsed from the remote URL and never asked of `gh`, which answers for the BASE repo — on a fork clone with an `upstream` remote that is the upstream owner, the opposite of what is needed); the fork MATCH itself stays in the renderer, because `--head` matches a branch NAME and a stranger's fork branch is routinely called `main`. It FAILS CLOSED: every failure — no `gh`, a logged-out `gh`, a folder that is not a GitHub checkout, the query erroring — is ONE outcome, the empty list, and every surface then draws nothing rather than an error strip about a CLI the user may have no intention of installing. There is deliberately no "did it work" flag on the wire, and the reason is written at the guard in `github-prs.ts`: a half-answer reads as confident and wrong rather than as partial), `resolve-binary.ts` (the PATH ∪ well-known-dirs lookup `cli-detect.ts` used to keep to itself, extracted when `github-prs.ts` needed it: a packaged app launched from Finder runs under launchd's `/usr/bin:/bin:/usr/sbin:/sbin`, where `git` resolves and a Homebrew `gh` does not — so a bare-name spawn works in `pnpm dev` and is ENOENT in every shipped build, silently, because a swallowed spawn error is indistinguishable from "no pull requests"), `ipc.ts`, `ipc-schemas.ts` (the zod shapes every IPC argument is validated against before main acts on it — the renderer is the untrusted side of that boundary), `context-menu.ts` (the right-click menu, which Electron does NOT provide: a packaged app has none at all unless it builds one, so every right-click did nothing anywhere until this existed), `navigation-policy.ts` (keeps the top frame on the renderer document — `URL.origin` cannot decide it in a packaged build, where every `file:` URL has the opaque origin `null`), `native-appearance.ts` (tells macOS which appearance the app is painting, from the stored theme — the ONE write that themes both the OS chrome and, through `prefers-color-scheme`, the page; see the traffic-light paragraph below), `open-terminal.ts` (the handoff OUT of geniro: a 0700 `.command` script and `open`, so LaunchServices routes it to whatever terminal the user actually set), `reveal-path.ts` (shows the daemon's log in Finder — it REVEALS rather than opens, so a path it is talked into taking cannot become a program that runs), `daemon-ready-notify.ts` (pushes the freshly started daemon's handle to the renderer, tolerating a window destroyed between the daemon becoming healthy and the send), `window-diagnostics.ts` (what the MAIN process saw happen to a window, written into the daemon's log — the `ui` channel carries only what the RENDERER catches, so a window that never ran the renderer could report nothing at all), `app-menu.ts` (the macOS menu bar: Electron's own default, restated through role menus, with **Toggle Developer Tools** hidden — reported out of the menu bar, and hidden rather than deleted so ⌥⌘I stays bound; verified against the RUNNING app by dumping `Menu.getApplicationMenu()` over `electron --inspect`, which is also the only way to read that menu at all, and rows of geniro's own — one always, one only in development. Always: **Clear Agent Cache**, beside the two Reloads because it is the same act one layer down — Reload drops what the WINDOW holds, this drops what the DAEMON holds about the CLIs. ASKED FOR as "на мыши нужно сделать сброс кэша… как дополнительную функцию". It carries no accelerator (every other row here has the platform's own, and an invented chord for a maintenance action is one pressed by accident) and it does the work in the RENDERER, over `IPC.onClearAgentCaches` to the FOCUSED window: the renderer is what holds the daemon client. **It clears and then RELOADS**, which is the renderer's whole half of the press — `useAgentVocabulary` caches per hook INSTANCE (the composer holds three, the graph inspector three more, a component not yet mounted none), so there is no one cache to empty and a reload drops all of them with the rest of the window. The reload also REPLACED a confirmation strip this first shipped with, on the report "нам не нужно вот это добавлять… просто должен перезагружать": a reload is its own confirmation, and it costs the composer's unsent text, which is the trade the row is understood to make. A first attempt at the same problem — a `vocabulary-epoch` number folded into the cache key — is gone with the strip: a reload makes it dead code. ORDER is load-bearing and so is the failure arm: the reload happens only AFTER the daemon has answered (reloading first refills from a daemon that has not cleared yet) and never on a failure (a reload after one hides it behind a window that looks like it worked), which instead goes to the daemon's log where every other renderer failure goes. Verified by clicking the real macOS menu row through System Events — the daemon logged `cleared 2 cached CLI answer(s) on request`. And in DEVELOPMENT only: **Component Catalog**, which opens Storybook in the user's browser. Gated on `isDev` — `Boolean(process.env.ELECTRON_RENDERER_URL)`, passed IN to `installApplicationMenu` so the template stays a pure function of its arguments and both arms are spec-testable — and OMITTED rather than disabled when false, because a greyed row states that a feature exists and is unavailable, which is true for a developer and simply wrong for a user. The row PROBES before it opens: this app neither starts nor supervises that dev server, so "nothing is listening" is the common case on a fresh `pnpm dev`, and a browser tab reading ERR_CONNECTION_REFUSED names no way forward where a dialog saying `pnpm storybook` does. Spawning Storybook instead was considered and rejected — a long-lived child this process would then own the lifecycle of, for a convenience one sentence buys. The port is a TWIN with `apps/ui/package.json`'s `storybook` script, and `app-menu.spec.ts` reads that script to check the two agree, since a package script is not importable), `updates` (**app self-update** — `updater.ts` reads the GitHub Releases feed, `update-installer.ts` downloads/verifies/swaps the bundle, `update-service.ts` owns the one state and the schedule; see *App updates* below), `login-shell-path.ts` (packaged Finder launches inherit launchd's minimal PATH — resolve the login-shell PATH for the daemon), `notifications/` (**system notifications** — `notifier.ts`, the ONE file that touches a notification API, and `notifications.service.ts` over it).

`src/shared/contracts.ts` holds the Electron-internal contracts only — IPC/Settings/CLI + `DaemonHandle` — shared across main/preload/renderer; it deliberately holds **no daemon wire types** (those are generated, see *The daemon API client* in the root `CLAUDE.md`). `src/preload/index.ts` exposes a typed `window.geniro` via `contextBridge`.

### Renderer shell

`src/renderer/` — React app: `App.tsx`, `onboarding/`, then the feature directories below (`chats/`, `workflows/`, `stats/`, `settings/`), plus `autogenerated/`, `daemon-api.ts` and `daemon-client.ts` (see *Settings* below for those). `stats/` is what the app has SPENT — totals, a per-day series and per-agent/model/project breakdowns over the daemon's usage ledger, drawn with **recharts** under `stats/charts/`, whose `chart-theme.tsx` is the one place the series colours and axis styling are read off the design tokens. (This line used to claim token-driven `components/ui/{bar,donut}-chart.tsx` primitives "rather than a charting dependency" — neither file exists and recharts is a direct dependency.)

**The periods, and what a ONE-DAY range costs.** `Today` leads them (`use-stats.ts` `STATS_PERIODS`) — reported as "we need to add today", and the narrowest window before it was a week, in which today is one column of seven and the headline figure is six other days. `days: 1` is a calendar day and not a rolling 24 hours: the lower bound stays a local midnight, so the period does not slide backwards into yesterday as the afternoon wears on. It made two existing holes routine, both of which a fresh install's first day could already reach on ANY period (the daemon clamps a range to what its ledger holds). A line and an area are drawn BETWEEN points, so a single day rendered as bare axes — read as "no data" about a day that may well have cost money — hence `loneDot`, a marker offered only at exactly one point and never as a general option, since at 30 points the same markers are a beaded string over the curve whose shape is the thing being read. And the span under the title dashed a date to itself. Fixing that surfaced a genuine timezone bug in the line it replaced: the header read the UTC day out of the ISO bounds (`iso.slice(0, 10)`) while every bucket on the page is a LOCAL one (`usage-fold.ts` `localDateKey`). One bug with two faces — east of Greenwich a local midnight is the previous UTC day (measured at UTC+5: "August 20 – August 21" over a chart holding one column, Aug 21), west of it a local evening is the next one, and since `to` is always *now* every period opened after ~16:00 local claimed to run a day past its last column. `dayRangeTitle` reads local days for both ends; the suite's pinned `America/Los_Angeles` can only tell the second face apart, which is what its test asserts.

**One line under a control, not a paragraph about it.** Reported against Settings as "we have too much text here - let's remove most": every section carried two or three muted paragraphs and the screen read as documentation with switches in it — measured at 302 words across 9 notes, over a 1210px page. Now 147 words across 5, and the whole tail from Notifications to Diagnostics fits one screen. The rule the cut followed, worth keeping for the next section anyone adds: a note says **what flipping this does and the one consequence you could not guess** — the cost (`22 extra tools in every prompt, paid for on each`), the restart, the security caveat (`while the port is open any process on this machine can run code inside it`). What went was rationale ("so a run parked on a question does not sit unanswered while you are in another app"), mechanism nobody acts on (the update's checksum verification), enumerations the label already implies (listing the browser tools under "Let claude drive your browser"), and anything a neighbouring element already says — Diagnostics' "On by default in development and off in the installed app" was sitting next to a badge reading `default for the installed app`. The cut also stranded `Remove from existing chats` on a row of its own, since it had been pushed right by `ml-auto` against a paragraph that no longer existed; it now shares the note's row, and the two `ErrorText` states moved to their own full-width line, which is where a sentence like "Contains invisible control characters — not saved…" needs to be anyway.

**A full-screen view scrolls its PANE; the centred reading column is what the pane scrolls** — two elements, never one. Reported as "scroll should be for all page, not just in the middle", against `Settings` (and, unreported but identical, `Onboarding`), where a single `<div>` was both the `mx-auto max-w-2xl` column and the `overflow-y-auto` container: the scrollbar was therefore drawn at the COLUMN's right edge, floating inside the pane with dead page background either side of it. Measured in a 1200px window, its right edge sat at x=1025 — 175px short of the window edge every other scrollbar on the machine lives at. `Stats` was already built the right way, so this is the house pattern rather than a new one. The outer pane also carries `scrollbar-gutter: stable`: the reporter runs macOS with "always show scrollbars", which is why the bar is visible in the screenshot at all, and without the gutter a real 15px bar shifts the centred column sideways by half its width the moment content grows past one screen. On `Onboarding` the inner column additionally keeps `min-h-full`, because its footer is `mt-auto` and would otherwise ride up under the last card once both CLIs are already installed. The pins are STRUCTURAL — jsdom computes no layout, so the scrollbar's position is unobservable there, but "which element scrolls, and is it the one that caps the width" is the DOM fact that decides that position and the one that regressed. None of this touches `7569b86`'s `html, body, #root { overflow: clip }`: the window still does not scroll, and the report was never asking it to.

**The page reads top-down as headline → figures → charts → breakdowns.** Reported as "and move those to the top": the measured figures were the LAST section, three sections and a scroll below the headline whose own token count they split, so "what did this cost" was answered in two places with a page between them. They now sit directly under it, and the section order is otherwise unchanged. The spec pins that order off DOCUMENT POSITION rather than a class name — jsdom computes no layout, so where a card lands is unobservable there, while which of two nodes comes first is exactly what grid order is made of.

**Every figure sits in a RULED SURFACE, and there are never four boxes where one will do** (`stats/stat-card.tsx` — `StatGrid` + `StatCell`). The page was a hero `Card`, eight figure `Card`s, a chart `Card`, four breakdown `Card`s and two more chart `Card`s: one border radius, one border colour and one shadow, fifteen times, with nothing telling a reader which of them was the answer. The grids are one surface each now, and the rules are the container's own background showing through a `gap-px`, NEVER `divide-x` — Tailwind's divide utilities border every child but the first IN DOCUMENT ORDER, so on a wrapping grid the second row's first cell wears a left rule opening onto nothing, while a one-pixel gap over a `bg-border` ground is correct on every row by construction and clips to the enclosure's radius. Three consequences worth knowing. The HERO card is gone: it spent its right two thirds on nothing — "SPENT" at the far left, two small figures pinned to the far right — and is now a four-cell summary (Spent · Cost per turn · Turns · Agent time) with TYPE carrying the emphasis (`StatCell`'s `size`), because a spanning hero cell has to be re-spanned at every breakpoint and lands as a half-width orphan at the one nobody checked. Cost per turn and Agent time were MOVED up out of the grid rather than repeated, which is what leaves the detail grid at SIX — the count that divides by both 3 and 2, so there is no breakpoint with a ragged tail, where eight had one at every breakpoint but four — and makes it one subject, where the tokens went, instead of the mixed bag it was. And the four breakdowns are COLUMNS of one surface: a grid of cards stretches every one to the tallest, so the workflow breakdown, which routinely holds one row, was a 345px box with 300px of nothing in it and the agent one beside it was another. The air is unavoidable while the columns are ranked lists of different lengths; drawing four boxes around it is not.

**Colour on this page names the QUANTITY, and a ranked list is not a category.** Two separate corrections, one rule. The CHARTS: money is `--chart-1` and tokens are `--chart-3`/`--chart-4` (`charts/chart-theme.tsx` `SERIES`), because the daily spend area was caramel while the cumulative spend line a scroll below it was teal — one quantity in two colours, on a page where a repeated colour is exactly what a reader takes to mean something. The daily chart's own hue follows its metric switch for the same reason, and its gradient `id` is keyed by metric or the fill would keep the previous one's stops after the switch. The BREAKDOWN bars went the other way, from a categorical ramp to one hue stepped by RANK (`breakdown-card.tsx` `RANK_OPACITY`): each of the four columns restarted that ramp at index 0, so "the second bar is teal" held in three columns about three unrelated dimensions at once. A ranked row carries its own label on its own line, so colour identifies nothing here and is free to encode the one thing the rows share — their order. The ramp FLOORS high, because it compounds with the 2% width floor: the faintest rank is routinely also the narrowest, so a ramp fading toward transparent would undo, by opacity, the guarantee that a row which spent money can be seen to have spent it.

**Two figures on it were WRONG, and both were formatting rather than arithmetic.** Measured against a real 26-day ledger. `formatTokens` had no billion step, so 16.6e9 cache-read tokens rendered as `16603.4M` — five significant digits under a suffix that had stopped compacting, printed as the largest figure on the page. And `formatUsd` did not group, so a lifetime total was `$21547.80`, seven digits the reader counts in threes to place. Both live in `chats/agent-activity.ts` and are shared with the transcript, where neither branch is reachable — a turn costs tens of dollars and moves millions of tokens — so the fix is strictly additive there. `formatUsd` is pinned to `en-US` unlike the day labels beside it, because the `$` is hardcoded and the daemon records USD alone: a machine-locale number would pair a dollar sign with `21.547,80`. Two smaller ones in `stats-format.ts` for the same reason: `formatCount` groups the turn count, which was the last `String(n)` on the page, and `formatPercent` refuses to round UP to a whole the rate did not reach — 16.6e9 / (16.6e9 + 155e3) is 99.999%, which `Math.round` printed as `100%`, a claim that not one prompt token in the period was ever a cache miss, and the kind of figure a reader stops trusting the whole page over.

**The window draws its own title bar** — ONE band across the whole window (`components/title-bar.tsx`), above the columns. `titleBarStyle: 'hiddenInset'` + `trafficLightPosition` in `main/index.ts` remove the system's strip while KEEPING the window buttons, so the app owes the OS no controls of its own; `frame: false` would take the buttons with it. The strip held the word "Geniro" and nothing else directly above a row of ours that already named the open chat. It was then rebuilt a SECOND time: the title bar had been three rows, one per column (the rail's top row, the chat list's header, the transcript's), all `h-11` and so aligned — but two vertical column borders ran straight through the band, so what the eye read was three column headings rather than a title bar ("это криво… у нас этот header всё ещё должен выглядеть как header", against Cursor's). Being ABOVE the columns is the fix: their borders start under it, so nothing crosses the band. **What is in it is decided by what each thing is ABOUT.** The band carries the window's own business — a title centred over the CONTENT pane (the open thread's name, reported up by `Chats` via `onTitleChange`, since the bar spans the window and the name has to travel up from the view that knows it), and on the right the daemon status + version and the update control (`components/update-control.tsx`). It carried a THIRD control, the debug-log trigger, and that one was reported and removed: an unlabelled `>_` opening a developer panel, sitting in the one band every user sees beside a health readout and an update offer. ⌥⌘L is now the only way in (`App.tsx`), which is the point — the drawer is a developer's answer to "what just happened", and Settings' Diagnostics section names the chord so it stays findable where somebody would look. The rail keeps what is about the rail: the app mark and the width toggle, on its own top row. Both of those went up and came straight back — the toggle acts on that column rather than on the window ("давай её в само меню оставим там же, где она и была"), and the mark belongs to the app. The rail's FOOTER is gone with the status: collapsed, it had shrunk to one green pip alone under a rule ("вот эта точка выглядит одна-одиноко"), so the rail is navigation and nothing else now. Only the collapsed STATE is the shell's (`components/use-sidebar-collapsed.ts`) — the button and the column it resizes are two components, and two `useState`s over one setting would be two answers to one question.

Three obligations come with the space. **Room**: the buttons' footprint is MEASURED, not assumed — `TRAFFIC_LIGHT_INSET` / `TRAFFIC_LIGHT_WIDTH` / `TRAFFIC_LIGHT_GAP` / `TITLEBAR_CONTENT_INSET` in `src/shared/contracts.ts`, the one module main and the renderer share, because main POSITIONS the buttons and the renderer RESERVES room for them and a copy on each side drifts in silence. It was a hand-written 52px (12px buttons 20px apart, right for years of macOS); on macOS 26 they are 13.5px and 23px apart — a 59.5px group — so every reservation was ~8px short and the green button was drawn over the column beside the rail. Clearing them by arithmetic ALONE is still not enough ("очень мало отступа между иконкой и кнопками"), hence the explicit gap. Re-measure before editing those numbers: open a `hiddenInset` window at a known position, `screencapture -R` its bounds and find the coloured discs. `trafficLightPosition`'s `y` and the bar's `h-11` are one piece of arithmetic ((44 − 13.5) / 2 ≈ 15) and move together. **Alignment**: the title is centred on the WINDOW, and nothing between the bar's edges may displace that centre — a flex `gap` on the row shifts every child after it by its own width (measured 8px out when the bar carried one), which is why spacing belongs to the children and a spec pins the absence. Two other arrangements were tried and reverted, both reported: a visible divider on the boundary between the leading columns and the content pane ("давай всё-таки вот эту линию из хедра вообще уберём" — a rule through the band puts back exactly the break that splitting it into three column headings had caused), and centring the title over the CONTENT pane by adding the column widths into a `leadingWidth` prop. That second one is right until a column opens on the OTHER side: with the agents panel out, the midpoint of everything right of the chat list sits well right of the transcript and the title drifts with it (measured 1322px into a 2000px window — "он не посередине"). Bounding both sides would mean the panel reporting its width up on every frame of a resize drag. **A drag handle**: with the system strip gone a window with no `-webkit-app-region: drag` anywhere CANNOT BE MOVED ("я перетаскивать за него вообще не могу окно"), so `.app-drag` / `.app-no-drag` in `styles/global.css` mark it — and the title bar is the shell's ONLY drag region. The column headers gave theirs up with the restructure: dragging the transcript's chip row moved the window, which is surprising once a real title bar exists. **A control inside a drag region is INERT** (the compositor takes the press and the click never reaches React), so anything interactive in the bar carries `.app-no-drag`. `components/window-drag-strip.tsx` still covers the two screens that render before the shell exists — Onboarding and the loading state.

**And the appearance has to be DECLARED** (`main/native-appearance.ts`, called first inside `whenReady`). Keeping the buttons means the OS keeps drawing them, and it draws them for whatever appearance the machine is set to — while `styles/global.css` ships one light-only palette and never said so. On a Mac in Dark mode that showed up in the one place nobody can miss: macOS tints an INACTIVE traffic light for the appearance — near-white under Dark, grey under Light — so an unfocused window painted three white discs onto the title bar's own `#fdfcfa` and the buttons vanished ("когда у меня окно не в фокусе, я вообще в принципе не вижу трех кнопочек… они должны быть серенькими, точно так же, как на других приложениях мака"). Measured on macOS 26: fill `#ffffff` on `#fdfcfa`, a 1.02:1 ratio, against `#dad9d7` once `nativeTheme.themeSource = 'light'`. The band's own colour is NOT the lever, and probing settled it — three `hiddenInset` windows over the same near-white ground, with and without `trafficLightPosition`, all vanished under Dark and all came back under `'light'`; recolouring would have bought back three buttons and left every other unpainted native surface (the context menu, scrollbars, system dialogs) dark against a light app. It was `'light'` for exactly as long as the palette was light-only, and the dark theme is what changed that line. It now takes the user's stored `Settings.theme` — `'system'` or a theme id — and that ONE write is the whole application of a theme: it decides what the OS draws for every surface the app does not paint, AND Electron drives the renderer's `prefers-color-scheme` from it, which is what `renderer/theme/apply-theme.ts` resolves `<html data-theme>` from. So there is no theme IPC channel and no push event; the page and the OS chrome cannot disagree. Switching the Mac's appearance under `System` repaints the PAGE off that media query alone — but not the window's own `backgroundColor`, which is a construction option Electron reads once, so the module also owns `watchSystemAppearance` (a `nativeTheme.on('updated')` listener that repaints it) and `paintWindows`. `applyTheme` is the module's only exported way to APPLY a theme, and `applyNativeAppearance` is gone as an export for that reason: a caller reaching the OS write without the repaint is exactly the defect that shipped in the first cut, leaving a dark window with a cream ground showing through every resize. `resolvedTheme` is the read-only sibling `createWindow` uses, since its window does not exist yet. The traffic-light failure is now symmetric rather than retired — a light-mode machine running the dark theme would hit the mirror image of it — which is why the declaration matters more than before, not less. `createWindow` also reads the resolved theme back for the window's own `backgroundColor` (`shared/themes.ts`, `ThemeDescriptor.windowBackground`), since that is painted before any stylesheet exists.

### Chats

`chats/` incl. `approval-card`; the composer's `/` skill autocomplete (`skill-menu`) and its chip row.

The chip row: `folder-select` and `config-dir-select` — both built on `directory-select`, the ONE directory chip (recents + the current value + a native-picker row), which is also what keeps them from drifting apart; the config one adds a "Default profile" row, since the CLI's own is its normal state, and renders NOTHING for a CLI whose `GET /v1/capabilities` `configDirs[]` row names a reason — never a disabled chip, the same rule the effort chip follows. **And it ZOOMS**, which for a release it did not — "zoomable" meant only "opens full-screen", so a screenshot too small to read at fit size could not be read at all. It rides `react-zoom-pan-pinch` (MIT, no runtime dependencies) rather than a hand-rolled transform, and the reason is what the library actually buys: not the `scale`, which is a line of state, but keeping the point under the cursor fixed while the scale changes and clamping the pan to the scaled bounds — the two parts that are fiddly to get right and invisible when wrong. `MIN_SCALE` IS fit-to-window (`limitToBounds` is what makes that true), so at rest the zoom-out and reset controls are DISABLED: a live control that does nothing when pressed reads as broken. The reading IS the reset control — a percentage the user can read and a button they can press are the same affordance here, and a separate reset icon would need a label explaining which of the two it undoes. The second label is the AGENT (`agentLabel`), and it says `claude`, `cursor` or `graph`: a workflow has no single CLI, since its agents are per node, so the honest word is what the run IS and that reading WINS over any kind the row carries; the daemon spells the second CLI `cursor-agent`, which is the binary's name where the label has room for one word; and a run that recorded no kind says `agent` rather than guessing. **The shelf replaced the single pull-request LINE above the composer** (`ComposerShelf`), and it is ONE LINE that never wraps. It names every pull request the thread has OPEN, up to `MAX_SHELF_PULL_REQUESTS` (three), newest first — and the newest single one when the thread has none open, which is what `currentThreadPullRequest` answers on its own. It named exactly ONE for a release, right for a thread whose work is one branch and wrong for the case reported against it ("in case if we have few opened PRS - all of them, but maximum 3"): several reviews out at once, only the newest reachable from here. Past the three it hands the rest to a button, `All N`, which opens the RIGHT PANEL rather than growing the row: thirty-one chips would push the textarea most of the way up the pane, and the count on that button is what the THREAD opened rather than what is hidden, since the panel behind it lists them all.

**Fitting them to the line takes TWO mechanisms, answering opposite situations** ("we always should fit all available chips to one line"). A CROWDED row is handled by flex alone: every chip carries `min-w-0` and the default shrink while the terminals chip beside them is `shrink-0`, so the pull requests give up width first and the row fits by construction. What flex cannot do is the ROOMY row, where three chips would each take a lone chip's full width and press the rest of the shelf against the edge — so `PULL_REQUEST_CHIP_WIDTH` caps them by COUNT (14 → 11 → 9rem). The steps are not linear because a chip is not all title: a number, a glyph and the padding are fixed at about 5rem, so what is left is a readable title, a recognisable one, and a hint — the right shape for a row whose leftmost chip is the one the thread is most likely on. That button reaches two flags in different subtrees (`chats/panel-flags.ts` → `setPersistedFlag`), the panel's own collapse and the thread section's settled fold, because a panel revealed with its fold still shut answers "all 31" with an empty section. It is a SHELF rather than a pull-request strip on purpose: what belongs there is whatever the thread has produced that is worth reaching without scrolling, and anything added later is another chip in that row rather than another one-item band above the composer, which is how the area became a stack of them in the first place. It draws nothing when it holds nothing (`empty:hidden`), so a thread that produced none costs no space — and a thread that opened none gets NOTHING here, which is the fix for a one-message chat that displayed a pull request it had never opened.

**The branch query is the SECOND source, and it no longer claims what it finds as the thread's** — three places, off ONE read per checkout (`chats/use-pull-requests.ts` — the cache; `chats/pull-request.ts` — the folds; `chats/pull-request-row.tsx` — the rows). Scope is the thread throughout — `threadPullRequests` is the ONE filter every surface goes through (branch match, plus the fork check below), and the repo-wide panel this first shipped with was rejected in use: on a busy repo it put fifty of other people's pull requests under a thread whose subject is one branch. The panel lists the branch's own under the artifacts, NAMED as the branch's (open expanded; merged and closed-unmerged folded together, shut by default and remembered through `usePersistedFlag` since the panel is keyed by run id) — and that captioned section is now the only surface it reaches. The sidebar row and the shelf above the composer name what the THREAD opened and nothing else: a checkout routinely sits on a branch whose pull request somebody else opened, so the fallback had two unrelated conversations in one folder both claiming `#75`, and a chat one message old showing a pull request it had never opened. **The hook takes a LIST of folders rather than one**, and that is the whole design: the sidebar draws a row per thread, threads routinely share a checkout, and a per-row read would spawn one `gh` process — a network round trip — per row to answer one question. So `Chats.tsx` passes every distinct `run.cwd` (sorted, because the sidebar reorders itself as runs report activity and an unsorted list would look like a new set of folders), reads are SEQUENTIAL, and each surface is handed what it needs as a plain prop. **"Current PR" is a live match, never stored**: no branch column was added to `Run` — it is the pull request whose head branch is the folder's checked-out branch, with an open one outranking a settled one from the same branch (reusing a branch after its PR merged is routine). A fork pull request matches only when its head repository's owner IS this folder's `origin` owner — that is the fork-clone case, where the user's own PR comes back cross-repository; a stranger's fails, which is the point, since fork branch names are routinely `main` or `patch-1` and matching on the name alone would let a thread claim someone else's work and offer to open it. A fork pull request that cannot be matched at all — a deleted head repository, an unknown `origin` owner — is excluded rather than guessed at, which is the one place a surface shows less than the branch query returned. Three things re-read it: the first paint, window focus (bounded to the folders on screen, with an in-flight guard AND a five-minute per-folder freshness floor — the started-set only grows, and alt-tabbing is this app's normal rhythm, so without both an ordinary session spends a burst of authenticated GitHub traffic every few seconds), and an explicit `refresh(dir)` after an in-app branch move, which focus cannot see because the window never lost it and which deliberately ignores the floor, being asked for precisely because something changed. A read carries a per-folder generation and is DROPPED if a newer one for that folder was issued while it was in flight — last to resolve is not last to be asked for, and without it a focus sweep still running when the user switches branches reinstates the pre-switch answer.

**A tool group holding a FILE CHANGE opens itself, and so does the row carrying it** (`tool-group.tsx` → `showsFileChange`). REPORTED as "I wanna see all file edits, so it should be automatically open, like claude cli… no need to change design, but it should be visible", and the shape of the defect is that there were TWO folds in front of a diff — the group's chevron, then the row's — so the one part of a turn that has to be checked by eye was the part hidden hardest. Nothing about what is DRAWN changes; only what starts open. Both folds give way together, since opening the row inside a shut group renders the diff into a closed box. Three things it is not: it is not "open everything" — a turn's reads, greps and command output are the material the agent worked FROM, and unfolding those would bury the diff in the wall the fold exists to prevent (measured on the author's longest thread: 50 of 104 groups opened, 121 of 432 rows, so the fold still carries 311 one-liners and 54 whole groups). It is not keyed on the CALL's arguments alone — claude discloses its change there (`Edit`'s `old_string`/`new_string`, `Write`'s `content`) while an ACP agent discloses no arguments at all and returns `diffs` on the RESULT, so either side alone opens one CLI's diffs and none of the other's. And it is not seeded into `useState`, which reads its argument only at mount: a row is mounted the moment the call streams in and its diff can arrive later, so the state is DERIVED with the user's own press layered over it as an override — the same shape as `TaskListCard`'s `latest`, and for the same reason.

**The session picker searches EVERY profile at once, and searches them on the daemon** (`chats/session-search.ts`). Two reports, one dialog. "i can see only one claude profile there - it should search by ALL profiles": a profile is an ACCOUNT, and the picker asked the single config directory the composer happened to hold, so the other subscription's conversations were not hard to find but absent, with nothing on screen saying a second store existed. The fan-out lives on THIS side rather than in the daemon because of where the knowledge is — a profile is a directory somebody chose, recorded in `settings.json` (`configDir` + `recentConfigDirs`), and the daemon never opens that file; there is no registry of profiles on disk for it to enumerate. It is also honest folding rather than the kind the daemon exists to prevent: each answer is COMPLETE for its own store. The CLI's own default (`null`) is always among them — it is the account a user has without ever choosing one — and the rows are interleaved by WHEN, never grouped by account, since nobody remembers which subscription they were signed into. **The profile is carried on the ROW**, and that is not a label: an id listed under one profile is not resumable under another, so `resumeSession` takes it from the row the user pressed. A profile that could not be read is NAMED in `partialReason` rather than dropped, and "this CLI cannot be asked" survives only when nothing answered — over a list full of rows it is simply false. The other half, `filterSessions`, is gone: the query is a question for the daemon (see `apps/daemon/CLAUDE.md`), debounced by `SESSION_SEARCH_DEBOUNCE_MS` because the ask reads session files and, for cursor, spawns a process.

**A profile can be NAMED and COLOURED, and that list lives on the claude card** (`settings/config-profiles.tsx`, `Settings.configProfiles`). Until it existed the app could only ever point a run at a config directory BY PATH, so a user with three accounts picked between `/Users/x/.claude-work`, `/Users/x/.claude-personal` and `/Users/x/.claude-lab` by reading their tails. A `ConfigProfile` is `{ id, name, dir, color }`, the DIRECTORY is the identity and the only field a run consumes, and the other two are labelling over it — which is why two entries may not name one directory: that would be two names for one account with nothing able to say which a run was using. It is rendered inside `AgentConfigList`'s `agentSettings.claude` rather than as a Settings section of its own — asked for there ("should be in claude settings menu"), and it is the rule the browser-tools switch beside it already follows; claude ALONE because the config directory only changes the account for claude, which the daemon says itself and `configDirReasonFor` already acts on. Storage is the third HAND-MANAGED list beside `runConfigs` and `fastActions`, through the same `salvageList` (entry-by-entry, unique ids, cap re-applied) — deliberately NOT folded into `recentConfigDirs`, which is an MRU of raw paths the app is free to re-sort, where these carry a name and a colour it must never evict. The COLOUR comes from the app’s one palette (`components/ui/palette.ts`, the eight `--color-group-*` tokens the sidebar's groups use), which moved out of `chats/run-group.ts` when this became its second caller; `GROUP_DOT_CLASS` keeps its `Record<RunGroupColor, string>` TYPE there, and that type is the point — it is exhaustive over the generated union, so a colour added to the daemon's enum and missing from the palette still fails type-checking. The palette's own union is spelled in `shared/contracts.ts` rather than derived from `RunGroupColor`, and that is forced rather than chosen: that file is Electron-internal and holds no daemon shapes, while a profile's colour never reaches the daemon at all.

**The COLOUR reaches the pickers, as a left border and nothing else** — asked for in those words ("там должен быть просто левый бордер вот этого же цвета"). `MenuItem.accent` carries a `ProfileColor` and `Menu` draws it as `border-l-2` from `PALETTE_BORDER_CLASS`, with the row's left padding pulled back by exactly the border's width: without that a coloured row's label sits 2px right of its uncoloured neighbours', which on a list where only some directories are named reads as two indents rather than one list. A border rather than a second glyph, because the row already leads with an icon saying what KIND of thing it is, and an edge stripe is read by position while costing the label no width — it is also how the sidebar draws a GROUP's colour, so a named configuration and a chat group wear theirs the same way. The row still says the PATH: a colour is recognition, not a replacement for knowing which directory it is, and a list where some rows said a name and others a path would read as two kinds of thing. `DirectorySelect` takes a `ReadonlyMap<path, ProfileColor>` rather than the configurations themselves — it knows about directories and nothing else, and what a colour MEANS is the caller's.

**What the name does NOT yet reach**: the composer's profile chip, the chat header's `Profile` row and the sidebar's rows all still name the config directory by PATH, and `ConfigDirSelect`'s `configProfiles` defaults to empty so the graph builder's node inspector and the run-configuration editor render exactly what they rendered before. The colour is wired where a directory is CHOSEN; the name is not wired anywhere.

`session-picker` — the "Continue a session" dialog behind the sidebar's history control, which is a SEPARATE control from `+` on purpose: the `+` is a one-click new thread and must stay one, while this has a question attached to it. The saved run configurations hang off the `+` ITSELF (see *Run configurations*), which is a different question again — that menu picks a setup to start FROM, while this one picks a conversation to carry ON. TWO narrowing controls — which CLI, and free text (matched per-term by the DAEMON, across the title, the folder AND what was said) — is deliberately not three: a folder-scope filter was tried and removed, since it could only ever name the one folder the composer happened to point at, and the free-text search already matches paths across every folder at once. What that costs is that the row count cap (`SESSION_LIST_LIMIT`) becomes the only bound, so a listing that hits it now SAYS so in `partialReason` rather than passing a truncated list off as the whole. Each row states its path (elided from the front by the composer's own `shortenPath`, since CSS truncation eats the only end that identifies a directory) and the dialog is sized to fit one. Its agent is its OWN rather than the composer's, and the profiles it asks under are decided from that agent for the same reason: the composer's config directory belongs to whichever CLI the composer is pointed at, and sending a claude profile to cursor asked it to list conversations under a directory that is not its store — so `sessionProfiles` collapses to the CLI's own default for an agent that reads no config directory at all.

**Fast actions** (`chats/fast-action-bar.tsx` + `settings/fast-actions.tsx`, over `Settings.fastActions`) — the user's own buttons under the composer on the new-chat screen. One action is a NAME and a DESCRIPTION, and nothing else; pressing it writes the description into the message box. It sends nothing and it touches no chip, which is the whole feature: the same action works under whatever folder, agent and model the composer is already carrying, so one "review the diff and report findings" serves every repo.

That smallness is the SECOND shape of this. The first bundled a whole new-chat setup into each action — folder, branch, target, model, effort, approval mode, config directory, and the message it sent on press — and was reported wrong on both counts ("на самом деле Fast Action у них просто должно быть имя и description… Ты их можешь использовать как кнопки на любой конфигурации"): it made an action usable in exactly one configuration, and it gave the run's setup a second, invisible source that moved chips the user had just set by hand. Cutting an action down to those two fields also, wrongly, deleted **Run configurations** — a separate feature that had nothing to do with it. That is documented in its own section below, along with what it cost. `chats/composer-values.ts` dates from that change and stays: `isChatApprovalMode`, `workflowSlugOf`, `targetAgentKind` — reading foreign strings from settings.json into the composer's own vocabulary, imported by `run-config.ts` rather than restated in it.

A press APPENDS to what is already in the box, separated by a blank line, rather than replacing it — the text there is the user's own typing, and a button that eats it is one nobody presses twice — and then puts the caret at the end. The caret is the reason the focus runs from an effect keyed on a press counter rather than inline: the textarea's DOM value is still the old one until React commits, so a `setSelectionRange` in the handler clamps to the wrong place.

The bar carries one more control, and it is the SAME trip drawn two ways: alongside actions it is a ghost glyph, because the buttons beside it already say what the bar is; over an EMPTY set it is the bar's whole content, a muted `Add fast actions` spelled out in words. That empty state is the correction to what shipped first — the bar drew nothing at all with no actions, on the reasoning that a manage button over an empty set costs space for a feature nobody has configured, and it was REPORTED straight back ("если fast actions вообще нет, я при создании чата внизу должен видеть кнопочку типа «Добавить fast actions»"): the new-chat screen is the one place a fast action is wanted, so a feature invisible until it is already configured can only be found by somebody who went hunting through Settings for it. The one case that still draws nothing is a caller with no way to Settings (the harness) — an invitation to a screen nobody can open is a button that does nothing. They are managed in **Settings → Fast actions** and nowhere else, which is a screen with a left nav (`SettingsSection`, `general | fast-actions`) rather than the dialog off the `+` this started as. The editor is two fields, and the list re-reads whenever Chats becomes `active` again: the screen stays mounted across nav switches — that is what keeps its live room alive — so its one-shot settings read never runs twice, and an action added in Settings would otherwise not appear until the next launch.

The write path is `persistFastActions` in `Settings.tsx`, and it calls `window.geniro.updateSettings` DIRECTLY rather than the screen's own `persist` helper: that helper swallows a rejection into `setError`, so the rollback chained onto it could never fire, and the screen would keep listing an action settings.json does not have — after which every later save fails on the same entry, since the whole array is re-sent. The editor also refuses locally what the IPC schema would refuse anyway (empty name, empty description, over-long either, a 51st entry), because that boundary throws on the WHOLE settings patch: without the guards the editor closes, the row shows from React state, and nothing is written. `readSettings` salvages the list ENTRY-BY-ENTRY (`salvageList`, shared with the run configurations) and re-applies the array cap there, for the reason it does with `cliPaths`: zod rejects an array wholesale on one bad element, and an action is hand-written and unrecoverable.

**Run configurations** (`chats/run-config.ts` + `chats/new-chat-button.tsx` + `chats/run-config-picker.tsx`, over `Settings.runConfigs`) — the user's named new-chat SETUPS: folder, branch, agent, model, effort, context window, model parameters, approval mode, config directory. Picking one seeds the new-chat screen and switches the folder's branch; it sends nothing and creates no run, so the user still writes the message.

**They are NOT fast actions, and the two must never be folded together again.** A configuration answers *where and with what does this chat run*; an action answers *what do I say*. That distinction was lost once, and the cost is the reason this paragraph is long: PR #78 read a report about what a fast action should BE ("просто должно быть имя и description") as licence to delete the configurations outright — 3,514 lines, the feature, its UI, its schema and its tests. It was rejected flatly on discovery ("Кто их удалил? Они не должны были удаляться. Я не давал таких инструкций… это вообще в принципе разные вещи") and restored. **Dropping the settings key also destroyed the user's data**: `readSettings` keeps only keys the current schema knows and `writeSettings` rewrites the whole file, so the first settings write after the key vanished silently erased six saved configurations, with no backup and no Time Machine on that machine. They were reconstructed out of old Claude Code session transcripts, which is luck and not a recovery path. The rule that follows: a change that removes or renames a persisted settings key must migrate or export the data first — a code deletion is revertible from git, the user's data is not.

Two surfaces, ONE component and ONE key. `RunConfigPicker` renders as a Dialog off the chat sidebar's `+` (`NewChatButton` — a click is still the plain new thread; hovering opens the setups, plus `New configuration…` and `Manage configurations…`), and with `asDialog={false}` the same list and editor are the Settings screen's **Run configurations** pane. `onApply` is what actually separates them and it is a real difference rather than a flag: the `+` is for USING a configuration so its rows start a chat, while the Settings pane is for KEEPING them and has no composer to seed — there its rows edit, and the accessible name says so rather than promising a launch.

Three things in the apply path are load-bearing. It builds the run from the APPLIED configuration and never from composer state, since the seeding it does first sets React state the same callback cannot see. It lands on the new-chat screen deliberately — that is the only view rendering both the seeded chips and the strip its branch refusal reports through. And a workflow target writes NONE of the per-CLI choices: those setters persist, `null` through them DELETES the remembered entry, so writing the blanks a workflow reports would erase the user's own claude model. The branch is a guarded `git switch` whose refusal is a partial success — the rest of the configuration still applied — so it reports in amber through `composerNotice` rather than as an error, and it offers no worktree redirect, because a configuration names a FOLDER as well as a branch and going elsewhere would run it where the user's own saved answer does not point.

**A question card's options are drawn from their ARITY, not from a single option style** (`components/ui/option-list.tsx`, driven by `approval-card`'s `optionArity`). Reported as "more beautiful, more compact — and for cases where we can select few options design should be different": every option was an outline `Button`, so a pick-one and a pick-many card were pixel-identical and the only thing separating them was a grey line of prose above them, which is precisely the sentence nobody reads before clicking. Three arities now, and each is drawn as the thing it is — `many` a checklist (square boxes, **stacked in a column**, because a checklist is read down its boxes and a wrapping flow puts every box at a different x), `one` a radio row (round dots, flowing, so six short options take one line), and `none` — the answer-on-click card, one question taking one pick, where the press IS the submission — **no indicator at all**, since an empty box there promises a staging step that does not exist and sends the user looking for the button that confirms it. That third case gets the warning the other two do not need: the verdict is one-shot, so a mis-click cannot be taken back. The unchecked box is `border-muted-foreground/50` and NOT `border-input`, which is tuned to recede against page cream and at 16px simply vanished. They stay toggle `<button>`s rather than `role="radio"`/`role="checkbox"` — an ARIA radio group promises arrow-key navigation and a single tab stop, and a half-built one is worse for a keyboard user than an honest list of buttons — so the arity reaches a screen reader through the group's own accessible name instead of through a shape it cannot see. Not built on `chip`, which is `whitespace-nowrap` by design: an option label is routinely a full sentence, and the reported card's were.

`use-chat-run.ts` — the run and websocket lifecycle, extracted out of `Chats.tsx`: the run list, which thread is open, the live-text plane, and every `DaemonClient` subscription (`onItem` / `onLiveText` / `onRunStatus` / `onDisconnect` / `onReconnect` / `onVerdictAck`) with the reconnect replay that follows them. **The `joinRun`/`leaveRun` pair lives here in full**, both halves — the activation swap AND the leave on run switch or delete — because ownership split across two files is how one of them comes to be missed. It is also what made the streaming plane testable without mounting the screen: `use-chat-run.spec.tsx` drives it through a probe component against a fake client, where before, every assertion about it had to go through a 9,000-line `Chats.spec.tsx`.

**The status vocabulary, in one table.** ASKED FOR as "давай мы как-то стандартизируем статусы… распиши мне вообще табличку статусов вот этих. Как это вообще работает? Что за кондишены такие?". `RunStatusKind` (`chats/run-status.tsx`) is the ONE vocabulary every surface draws in — the sidebar row, the chat header, the agents panel's cards and thread rows, and every transcript block — and `RUN_STATUS_META` is the one glyph/tone/word for each of its members:

| kind | word on screen | glyph | what produced it |
| --- | --- | --- | --- |
| `pending` | pending | clock | the daemon's own column: the run exists, its first turn has not started |
| `running` | running | spinner | the agent is working — a live turn, or a delegate still producing rows, or the row says so |
| `held` | working | hourglass, **not** spinning | the daemon raised `turn_held`: the agent has said its piece and the process is alive only until the SUB-AGENTS it launched report back (`holdingFor > 0`) |
| `needs-input` | needs more info | question mark, warning-toned | an approval or question card is open (`run.awaiting`) — the one state that cannot advance without a human |
| `completed` | completed | check | the daemon's terminal status |
| `failed` | failed | ✗ | the daemon's terminal status |
| `cancelled` | cancelled | ⊘ | Stop, or a run that ended before the work finished |
| `skipped` | skipped | ⊖ | a workflow NODE only: something upstream of it failed |

The daemon persists only five of these (`RUN_STATUSES` in `runs.types.ts`, plus `skipped` for a node). `held` and `needs-input` are DERIVED here and never stored, which is why no run row ever carries them.

**There were NINE, and the ninth was a duplicate.** Asked to re-check whether every status is needed and behaves, one did not survive: `idle` meant "has not started yet", which is what `pending` already means and what the node's own `node_state` row literally says while it holds. `displayStatus` answered `idle` for a node with no activity and `pending` the moment any status item existed — one unchanged node, two words, decided by a row nobody had looked at. It is gone, and `displayStatus` answers `pending` on both arms. Every other member earns its place: each is reachable, and no two describe one fact. `held` was DRIVEN in the dev app to confirm it, not read off the code — a delegate launched with `run_in_background` and the turn ended on the spot: the header, the sidebar row and the agent card all read `⌛ working · waiting on 1 sub-agent` together.

`displayRunStatus` decides between them in a fixed order, first match wins: **(1)** a card is open → `needs-input`; **(2)** the row says `failed`/`cancelled` → that, never overridden; **(3)** the run is held → `held`; **(4)** a delegate is still producing rows → `running`; **(5)** a live turn is streaming → `running`; **(6)** over a `completed` row, a background command or a background SUB-AGENT is still out → `held`; **(7)** otherwise the row.

**Rank 4 and rank 6 are two different delegates, and splitting them is what keeps both the badge and the notification honest.** A delegate WRITING rows is the run `running` — that is work happening, whatever the stale row says. One the CLI merely DECLARED out and has said nothing about since is `held`: the agent has stopped speaking, so a spinner would claim work it is doing. Cursor's background delegates are permanently the second kind (their steps never reach this wire at all), so collapsing the two put `running` over a finished agent AND swallowed its turn-end banner, since the notification rules fire on the transition into a settled status. Rank 6 is therefore withheld from `agentRunStatus`, the reading those rules watch, exactly as the background-command clause already was. `subagentSpokeSince` (`transcript-groups.ts`) is what separates them; it no longer decides anything about the WORK, which the daemon now states (see *A background delegate's ending* in `apps/daemon/CLAUDE.md`).

Rank 6's sub-agent half is **row-carried** (`RunDto.subagentsOut`, kept current by the `run_status` announce), like the shells beside it and for the identical reason: folded out of the OPEN thread's transcript it is knowable for one chat and no other, so the badge changed when the user looked away. `isWorkingRunStatus` is `running || held` and `isSettledRunStatus` is the four terminal ones — `pending`, `needs-input` and `held` are all states a run has yet to leave.

Two corrections the table exists to make, both measured rather than reasoned. **A detached shell does not hold a turn.** The guess in the report was that the hourglass means "some long-running terminal is open"; it is the reverse — only a `background_work` unit of kind `agent` keeps a turn open (`spawn-cli.ts`'s `trackBackgroundWork`, and claude distinguishes `task_type: local_agent` from the `local_bash` a delegate then runs). Driven live in the dev app: a backgrounded `sleep 180` settled its turn at `completed · worked 5.1s` with the command still listed and running. **And an agent's own work IS `running`** — ranks 4 and 5 above. The hourglass appears only after the agent has stopped speaking, and its word is already `working` rather than `waiting`; it deliberately does not spin, because that state routinely lasts twenty minutes.

**One state, one word — a block's lifecycle is translated, never printed.** `BlockStatus` (`block-shell.tsx`) is the transcript fold's own model (`running`/`done`/`error`/`stopped`) and used to reach the screen verbatim, so a delegate cut off by Stop wore a red `error` pill three lines under a header, a sidebar row and an agent card all reading `cancelled` — one event spelled two ways on one screen, which is the whole of the standardization report. `RUN_STATUS_OF` already translated it for the GLYPH; it now translates the WORD too, in both places one is written: the pill (`failed`, `cancelled`) and the `sr-only` span that carries the status for a screen reader when the mark is a glyph (`completed`). The kind was also renamed `waiting` → `held`, since that one word had been doing three jobs — this key, the sentence under a `needs-input` badge (`waiting for your answer`), and the sign-in flow's own `CliLoginStatus`.

`settled-status.ts` — the ONE reading of "which run status does this terminal item imply", and the rule that goes with it: **only a LIVE terminal item mirrors its status onto the run row**, while a REPLAY takes one reading from its LAST item (`reconcileFromTail`). Every chat past its first turn replays a `turn_complete`, so mirroring each replayed row wrote a past turn's ending onto a run that was working — measured on the real app as a chat reading `running · Working… 3m 39s` and then, after switching to another chat and back, `completed` with no live row, while the daemon still said `running`. The wrong value outlived the visit, which is the second half: the next activation read the row as settled and left `streaming` false, taking the transcript's live row with it. The two live rows' clocks follow the same principle — both count from a timestamp derived from durable rows (`ChatHeader`'s `turnStartedAt`, the working row's `workingSince` from the last row its own thread put on screen, the thinking row's daemon-published `thinkingSince`), never from their own mount, or every remount restarts them.

**A null activity means "working, nothing named" — and BOTH surfaces have to read it that way** (`run-status.tsx` `STANDING_ACTIVITY`). REPORTED as the status on a thread blinking: "справа от него то появляется, то исчезает… там всегда должен быть последний его статус". The daemon announces `running Bash` on a tool call and null on its result, and says at its own `idleActivity` that "null leaves the run's own Working… standing" — which was true of ONE of the two consumers. The transcript's live row carried that fallback; the sidebar row was gated on the phrase EXISTING and drew nothing, so it erased the phrase every time a tool returned. Measured on a real four-tool turn: 132 sampled frames in the standing state against 2 naming a tool, so the row was blank for essentially the whole turn and flashed a tool name for a moment — which is what a blink looks like from the other side. The fix is the fallback, in ONE constant both read, because the defect was two renderings of one null disagreeing about what it meant and a second literal is how they would come to disagree again. It applies only while the badge says `running`: a settled row showing it would claim the run was still going, which is worse than the blink.

**The live plane's KEY for a 1:1 chat is the sentinel, and reading the owner key the daemon sends is how the two came to draw two rows at once** (`chats/live-text.ts` `liveTextKey`). The daemon publishes `SINGLE_AGENT_NODE` — the literal `agent`, the pseudo-node a chat's rows are filed under — as the owner of a chat's live plane, while this side renamed its own sentinel away from that very word to stop a workflow node named `agent` colliding with it (`CHAT_LIVE_KEY`). Nothing failed to compile, which is exactly what that file's TWIN PARSER block warns about: a chat's deltas landed under `agent`, and every reader that has no event to derive a key from — `workingAgents`, `awaitingAnswer`, the context meter's live source — went on asking for the sentinel. REPORTED as a chat showing `Thinking… 250 tokens · 3s` and `Working… · 5s` at the same time, and reproduced in the running app: `withLiveText` suppresses the working fallback for an agent that already has a live row, BY KEY, and the two keys could never match. The discriminator is the NODE ID rather than the owner key's value — a workflow node's delta always carries its id (`GraphExecutorService` passes `node.id`) while a chat's never does — so the collision the sentinel exists for is still answered. Verified live: `Working…· 5s` and then `Thinking… · 1s`, never both.

**`ThinkingRow` has TWO shapes, and which one it takes is a fact about the CLI, not a style choice** (`live-row.tsx`, fed by `LiveState.thinkingText`). Reported as a cursor chat sitting on `Working…` for three minutes with nothing happening — cursor streams its reasoning the whole time, and until the daemon gained a live channel for it (see `apps/daemon/CLAUDE.md`) none of it reached the screen. With TEXT the row is the same muted italic `reasoning` bubble the durable item becomes, so the words a user watches appear and the words that land are one thing rendered one way, plus a spinner-and-clock line the durable row does not need — without it a stretch that goes quiet is indistinguishable from one that finished. With NO text it stays the one-line note it has always been, `Thinking… 250 tokens`, which is all headless claude can offer since it redacts the block; the token count is never printed alongside the words, because the CLI that sends words reports no count and `0 tokens` is a figure nobody measured.

**A reasoning stretch is BOUNDED while it is written and FOLDED once it is not** (`chats/thinking-block.tsx` — `ThinkingScroller`, `ThinkingDisclosure`). REPORTED against a cursor turn as "вот этот thinking-блок очень большой… должно иметь какую-то максимальную высоту, например 300 px… и потом это должно быть collapsed, как только он закончил". Cursor streams its whole chain of thought, so the row grew to thousands of words in both states, and the two states need opposite answers. LIVE it is capped at 300px and scrolls inside itself, pinned to the newest words — a fixed box that did not follow would show the paragraph the agent wrote a minute ago, motionless under a spinner. The follow gives way to the reader on the transcript's own rule (`nextFollowState`), which is why "am I at the bottom" cannot decide it alone: content that grows pushes the bottom away without anybody touching it, and reading that as intent would switch the follow off during the very streaming it exists for. FINISHED, the words stop being something to watch and become something to be able to check, so the row folds behind its own first line — the only summary available here that says what the agent was thinking ABOUT, the durable payload carrying the text and nothing else. A SHORT stretch is left alone: folding two sentences into a preview plus a chevron hides nothing and charges a click. The fold is ONE component used by both durable renderings, which draw the body differently and always have (the standalone bubble prints it verbatim, a turn block prints it as markdown) — hence `children` rather than a `text` the component renders, so neither call site has to give up its own idiom to share the disclosure. Measured in the running app: the finished stretch 15px collapsed, the live box 300px with `scrollHeight 975 / scrollTop 675` — pinned to the end.

**A delegate is named by its identity when nothing named it, and its launching call's reply is not its report** (`transcript-groups.ts` — `subagentTitle`, `subagentNamed`, `SubagentBlockEntry.resultIsOwn`). Reported as "i see wrong agent names and popup", over a panel listing one `Review: optimizations` above seven identical `sub-agent` rows and a dialog headed `Sub-agent · sub-agent` whose entire body was `{"success":true,"message":"Resuming agent ad31fec"…}` beside `Working… 2m 29s`. Three separate defects behind it, each measured on the user's own `geniro.db` rather than reasoned about:

- **The generic title was a CONSTANT**, so every unnamed delegate was the same row and "which spinner is which piece of work" had no answer on screen. Only the launching call ever carries a description, so any delegate whose launch is outside the loaded window arrives with none — and the daemon's `subagent_info` cannot cover for it: all 76 declarations on that ledger carry `label: null, kind: null` and speak only about `backgroundOpen`. The fallback is now the id's own tail (`Sub-agent HvcbzU`), which distinguishes rows and is honest about being an identity rather than a name. `subagentNamed` exists so the dialog can drop its `Sub-agent · ` prefix where the title already opens with it — the stutter that was reported.
- **A launch acknowledgement was rendered as the delegate's result.** A backgrounded delegate's call is answered within the second and the work runs on; 23 of the 39 delegation calls on that ledger were answered with `Async agent launched successfully. (This tool result is internal metadata — never quote or paste any part of it, including the agentId below, into a user-facing reply.)`, printed under `RESULT FROM <name>`. `resultIsOwn` decides it STRUCTURALLY — did the delegate speak after its call was answered, and is its background unit still open — never by matching that sentence, which is one CLI's prose. The text is still shown, under `Reply to the launching call`: it is the user's own agent's tool result and the transcript shows those everywhere; what was wrong was the claim about whose answer it is.
- **A `SendMessage` is not a delegation.** The daemon announces background work against the call that opened a unit, and resuming an already-running agent opens one — so the fold adopted a message-send as a delegate launch, giving a block with no name, no prompt, no conversation and a routing receipt where its result should be. Exactly the phantom `spawn-cli.ts`'s own comment warns about. A launch admitted ONLY by that declaration, and whose declaration describes nothing, can no longer contribute a result: the two admission routes are not equally strong, and only the tool NAME (`AGENT_TOOLS`) or a declaration that actually briefs the delegate (cursor's ACP path, whose frame carries no usable name) is evidence that the call was a delegation at all.

Also fixed by the second point: `This sub-agent has not done anything yet.` was gated on `returned || result !== null`, both of which an acknowledgement sets — so the one line explaining an empty thread went missing on precisely the delegates whose thread is empty for that reason.

**A run settling is a MOMENT, not a flag** (`RunSettledContext` → `RunSettleAt`, read by `subagentBlockStatus`): a delegate that has produced rows SINCE the run row settled is still working, whatever that row says, so the settle only closes blocks whose last row precedes it. As a bare boolean it painted every unreturned delegate in the chat `stopped` at once, when a delegate could still be producing rows well after the run row had settled — the reported symptom being "I can see stopped status - but it's incorrect, in fact they continue working". Three states and not two, because a settle whose timestamp will not parse is not the same as no settle: `'unknown'` keeps the old conservative reading rather than silently putting every spinner back. The seq-based `SubagentBlockEntry.closed` is untouched and outranks it — a turn-end ITEM after the delegate's last row is direct evidence that nothing more is coming. A tool group asks only `!== null`, since a tool call is one round trip and "has it spoken since" is the question `pair.result` already answers.

A code-review findings report the agent handed the APP to draw: `findings-payload.ts` — the twin parser, with NO fold, because a report arrives whole where a task list arrives as patches; `findings-block.tsx` — the `FindingsCard` the transcript shows, findings grouped under their file in the order the agent sent them (it was told most-severe first, so re-sorting would throw away the only ranking anybody has), a Confirmed / Plausible badge per row and the long half — the defect sentence and its failure scenario — behind a per-row disclosure. Two reports are two CARDS rather than one that rewrites itself: an agent that re-reports after fixing its findings is taking a step in the conversation, not correcting the card a reader has already scrolled past. The card carries no jump-to-file and no action buttons yet — both need surfaces the renderer does not have (an editor-open IPC, and a transcript block able to compose a new turn).

A CHART the agent handed the app to plot: `chart-payload.ts` — the twin parser, again with no fold; `chart-block.tsx` — the `ChartCard`, built on the **Stats page's own chart theme** (`stats/charts/chart-theme.tsx` → `categoryToken`, `AXIS`, `CHART_MARGIN`, `ChartTooltip`, `SeriesLegend`) rather than a second one, because a plot in a transcript and a plot on the Stats page are the same object drawn in two places. The parser's whole job is the POSITIONAL contract: series values are matched to `labels` BY INDEX, so it blanks an unreadable label instead of removing it and re-aligns every series to the label count — over rows written by older builds as much as new ones. `chartRows` then transposes into recharts' row-per-x shape keyed by POSITION (`s0`, `s1`, …), never by series name: a series legitimately named `x` would otherwise overwrite the axis column, and two series sharing a name — which a model does send, e.g. `p95` for two runs — would collapse into one curve. A `null` stays a gap (`connectNulls={false}`, and the tooltip SAYS unmeasured) because the alternative reading is a zero nobody measured. Plot height is fixed and small: it sits between two paragraphs of a conversation. The spec asserts only the chrome — heading, captions, legend, disclosure — since `ResponsiveContainer` measures 0×0 in jsdom, the same limit `stats/charts/time-charts.spec.ts` already records; it stubs `ResizeObserver`, which jsdom does not ship and recharts throws without.

A SCORECARD: `metrics-payload.ts` — the twin parser, again with no fold; `metrics-block.tsx` — the `MetricsCard`, a responsive grid of figures, ONE TILE each rather than columns in a shared box (columns have no edge to align against, so a figure carrying a note grew taller than its neighbours and the row read as broken instead of as one item having more to say). Four decisions in it. It is **NOT behind a disclosure**, unlike the chart beside it: a chart is 190px of plot that would push the reply off screen and so earns a fold, while a scorecard is two lines of large text that exists to be read at a glance, and a card you must open before glancing at is a link to one. And the delta is coloured **by the stated sentiment, never by the sign** — `+4 pts` of coverage is good news and `+90ms` of latency is bad, both start with a plus, and a card reading the sign would paint one of them wrong (pinned). The parser resolves an absent or unknown sentiment to `neutral` so nothing downstream repeats the fallback, and it never coerces a number into a value — see the daemon's own note on why that would be the renderer's fault looking like the model's. The grid is `auto-fit`/`minmax` rather than a fixed column count: the transcript narrows with the side panel, and four columns in a 300px pane truncate every figure the card exists to show. Its track is **11rem**, which is what fits a figure AND its delta pill on one line — measured at 9rem with five figures, `1.2 MB` plus `−120 kB` overran by a few pixels, so that one delta dropped below its number while the four beside it stayed inline, and the row read as a mistake rather than as a layout. The note sits directly under its figure in normal flow, NOT pinned to the bottom of the stretched tile: bottom-pinning looked tidier in the abstract and read as broken with five figures on screen, since one long note set the row height and every other note floated a centimetre below the number it belongs to. A tile label is **sentence case**, not the section caption's uppercase — both are small muted text a line apart, and styling them alike collapsed two levels of hierarchy into one (a card headed `TYPESCRIPT FILES IN SANDBOX/` over a tile labelled `TYPESCRIPT FILES` read as the same caption printed twice).

A COMPARISON: `comparison-payload.ts` — the twin parser, which additionally resolves `recommendedIndex` (matched to a column BY NAME, case- and whitespace-insensitively, since a model writing `sqlite` in the recommendation and `SQLite` in the options is agreeing with itself and an exact match would silently drop the highlight); `comparison-block.tsx` — the `ComparisonCard`, options across the top and criteria down the side. This is the one card in the family that has to beat MARKDOWN, since a markdown table renders perfectly well here — so the layout is built around the two things a table cannot hold. The verdict tint is on the **cell**, not on a glyph inside it: the whole point is that the winning column looks greener from a metre away, and colour has to be the largest thing the eye gets rather than a mark it must find first. Neutral is UNtinted, not grey-tinted — a wash over every cell would destroy the contrast the two real verdicts carry. The recommendation marks its column at the head AND states its reason at the foot: only the head would leave a verdict with no argument, only the foot would leave the reader matching a name back to a column. An empty cell draws an em dash, because a blank reads as a rendering failure while a dash says "nothing here", which is what the daemon's blank means. The table scrolls horizontally inside its own container, per the repo's wide-content rule, and that is also why the option cap is four.

A GALLERY: `gallery-payload.ts` — the twin parser, which also accepts the bare-string and `src` entry forms for twin PARITY rather than for back-compatibility: nothing persisted arrives that way (the daemon normalizes every entry before the row is written), but a twin that accepts less than its writer can produce is a twin that disagrees, and the pair is only checkable against each other while they agree; `gallery-block.tsx` — the `GalleryCard`, a thumbnail grid whose tiles open the app's ONE image surface with prev/next wired up. It is the only card in the family whose payload names FILES rather than carrying its own content, and everything particular about it follows from that. Each path is resolved through `LocalImageLoaderContext` (`chats/local-image-loader.ts`) — the same loader a markdown image uses, over the same token-gated route — rather than a second fetch path, so "how does a local picture reach the screen" keeps one answer. That context started life inside `markdown-image.tsx` and moved out when the gallery became its second consumer: it is now how ANY local picture reaches the screen, not a markdown detail. Loading is SEQUENTIAL and only while the card is open, and the resolved map is RELEASED when the card folds away — each picture is a `data:` URL held in memory (the full-screen viewer needs the same bytes the tile shows; there is no thumbnail endpoint and the daemon's per-image ceiling is 20MB), and an unvirtualized transcript can hold several galleries at once, so a folded card keeping 24 of them is memory nobody can see being spent. Reopening therefore reads them again — the deliberate trade, bounded memory over a second round trip, and the spec pins the release by counting those reads. The FIRST scheme door is the shared `refusalFor`, which lives in `local-image-loader.ts` beside the context it gates — it is the POLICY on what that loader may be asked for, so a remote path is refused here with its own sentence rather than reaching the daemon's second door and coming back as a generic failure. A picture that could not be read is ONE dead tile saying so, never a dead card — the agent produced the rest, and refusing to draw them would hide the work over one moved file; with no loader in context at all every tile says that too, rather than reading "loading…" for good. The grid is `auto-fill` with a floor rather than a fixed column count, on the scorecard's reasoning: the transcript narrows when the agents panel opens. **It does NOT bring a lightbox of its own** — the prev/next arrows, the `3 of 8` readout and the arrow keys are optional props on `components/ui/image-viewer.tsx`, so the modal contract, the portal, the focus trap and the zoom all stay where they already lived; a second modal here is exactly what that component's own doc block exists to prevent. Stepping between pictures re-KEYS the zoom wrapper on the source, or each new picture would inherit the previous one's scale and offset. The arrows are withheld at the ends rather than wrapping: a set has a first and a last picture, and looping silently makes a reader stepping through lose their place in it.

A DYNAMIC WORKFLOW is the seventh card, and the only one built from something other than a single row: `workflow-payload.ts` — the twin parser and the last-non-null merge, whose one deviation is that the agent ROSTER is taken WHOLE rather than merged, because the CLI re-sends the entire roster every time it sends one and index-merging two snapshots would resurrect an agent a later one had dropped; `transcript-groups.ts`'s `buildWorkflowCards`, which runs after `buildSubagentBlocks` and pulls the launching tool pair OUT of its group exactly as a `Task` pair is pulled; and `workflow-block.tsx` — the `WorkflowCard`, collapsible and shut to start, whose HEADER carries the whole answer (`28 agents · 3 running · 1.2M tokens · 20m 34s`) and whose body opens onto the roster, phase-captioned, one row per agent with its model and what it spent. A CARD and not a block, and that is a fact about the CLI rather than a layout choice: a workflow's agents emit NOTHING onto this stream, so there are no rows to enclose — where a sub-agent block has a conversation, this has a roster. A launch is recognised ONE way, by a `workflow_info` row naming the call, never by the tool's NAME: which calls launched a workflow is the adapter layer's fact and it is stated on the wire, so a second CLI growing an orchestrator is a daemon change alone. The header's clock counts from the launching call rather than from the CLI's own `duration_ms`, which rides the last roster sent and therefore freezes between announcements — the opaque tool row this replaced had a clock that did not, and losing it would have been a regression inside an improvement. The rows are also skipped OUTRIGHT in `groupTranscript`, beside `shell_info`: they render nothing there and land dozens of times mid-turn, so treated as the node "saying something" they would chop one turn's tools into a column of one-call rows. The card is not the only view of that reading, which is why `workflowCardsOf` is exported: a RUNNING workflow also gets a chip on the composer shelf (`composer-shelf.tsx`'s `ActiveWorkflowChips`, beside the pull-request chip and after it — prepending would shift the durable chip every time a workflow starts) and a row in the side panel's `Workflows` section, and pressing either takes the reader to the card (`Chats.tsx`'s `revealWorkflow`, arithmetic on the transcript scroller's own `scrollTop` because `scrollIntoView` moves every scrollable ancestor and `revealWithinBox`'s `offsetTop` is measured against whichever ancestor happens to be positioned). Three surfaces, ONE fold — a chip that counted its own agents would sooner or later say `3 running` beside a card saying two. The chip is drawn only while the workflow runs, so it appears and disappears with the work; the panel lists every one the run launched, newest first, and drops the running COUNT from its row because the row is a quarter of the card's width and the spinner beside the name already says it — without that the name truncated to `sh…`. Both are wrapped in `RunSettledContext.Provider` at their call sites: each is a sibling subtree of the transcript and inherits none of its context, the same trap the sub-agent detail dialog fell into.

`isCardEntry` in **`transcript-groups.ts`** arrived with it, and is the reason adding it was cheap. Six readers — entry owner, thread, `seq` fold, `lastRowAt`, tool count, and the live-tail scan — each spelled the same `'task-list' || 'findings' || 'chart'` chain, so a fourth card kind was six edits and every miss was SILENT: a card left out of the `lastRowAt` fold does not fail, it just stops a spinner noticing that work happened. One predicate made the fifth card one line. Its union and its predicate must list the SAME kinds, and the COMPILER enforces that: the fifth card went in with `comparison` added to the predicate alone, and five call sites stopped compiling because a `ComparisonEntry` reached a branch expecting `.entries`. That is the trade — six silent misses became one loud one. Confirmed again by the gallery: adding `GalleryEntry` to the union broke exactly the two render arms (`transcript-entry.tsx`, `turn-block.tsx`) and nothing else, because the six readers all go through the predicate.

**Each agent card also says what that agent has DONE — worked time and tool count, on their own line under the spend** (`agents-panel.tsx`'s `AgentSpend`, fed by `Chats.tsx`'s `workByAgent` side map, keyed by `AgentDisplay.id` exactly as `shellsByAgent` is). Its own line rather than more of the spend, because one answers what the agent COST and the other what it DID, and four figures separated by the same dot read as one list of four. The figures are DURABLE for BOTH run kinds, and which row holds them is the split `contextTokens` already follows: a workflow node's on `node_state`, a 1:1 chat's on the RUN itself (`Run.workedMs` / `toolCalls`, written by `ChatService` at its own `turn_complete` and riding `RunWire`, so the renderer needs no second fetch — it already holds the run). The transcript fold stays underneath as the first-turn answer, before either row has been written; without the rows it would be the ONLY answer, and past `HISTORY_PAGE` items it describes the loaded window rather than the conversation, with nothing on screen marking the difference. **Keeping the CHAT's copy current took a wire field**, and its absence was a real defect rather than a theoretical one: nothing refreshes a run row between full listings, so the figures froze at the moment the window fetched the run — and since a durable total outranks the fold on any chat past `HISTORY_PAGE` items, the card's clock climbed through a turn and then dropped back by the whole of it the instant that turn settled, over a tool count that never moved at all. A total cannot be derived from the event that moved it (unlike `status`, or a `title`), so the SETTLE announce now carries both (`RunStatusEvent.workedMs` / `.toolCalls`, read back by `writeRunStatus` and patched in `onRunStatus`) — the same road `taskList` travels, for the same reason. On a settle alone, because that is the only moment they change and an activity announce fires on every tool call; and omitted entirely when BOTH are null, since these columns only ever grow, which is what keeps every workflow run — whose figures live per node — off the field. The durable snapshot is still merged as the LARGER of the two rather than replacing the fold, for two now-different reasons: `useNodeDurableReadings` fetches on run open and reconnect and never again, and even a live chat row moves only at the settle, so mid-turn the fold is the fresher of the pair. A NON-POSITIVE figure is not a measurement (`measured()`, the renderer twin of the daemon's `positive()`) — a zero draws no line, on the same rule the spend line follows. The live half comes from `scanTurns`' open turns, which now carry an `agentKey` so a fan-out's concurrent turns are separable, and both the header and the cards read ONE guarded list (`openTurnsShown` in `Chats.tsx`): `parkWhileHeld` applied, and withheld entirely on a settled run, or a card would out-count the header through a hold and a daemon that died mid-turn would leave every card ticking for days.

**An approval card WARNS about characters that can hide how it reads, and gates Approve on the ones that can** (`chats/text-hazards.ts` + `PermissionCard` in `approval-card.tsx`). Three classes, from the stdlib rather than a vendored table: `bidi` (`\p{Bidi_Control}` — 12 codepoints on Unicode 16, a superset of the obvious list), `invisible` (`[\p{Cf}\p{Default_Ignorable_Code_Point}\p{Cc}]` minus the bidi set, via the `/v` flag's set difference so nothing is reported twice), and `mixedScript` — a token mixing Latin with Cyrillic or Greek, found with `\p{Script_Extensions=…}` and NO confusables data. That last choice is deliberate: UTS #39 confusability is relational and an approval card has no comparison string, so a table would flag by possibility rather than by suspicion. Bidi and invisible GATE — Approve is disabled until an acknowledgement is ticked, and the tick resets when the card's content changes so it can never carry into different, unreviewed input; mixed-script annotates only. Deny is never gated: refusing a suspicious call stays one click. **The banner names each hit by class and CODEPOINT and never prints the character**, since a bidi override inside the warning would reorder the warning. What is SCANNED is the tool NAME, the compact `JSON.stringify(input)` and — separately — the DIFF body, joined by spaces. Compact rather than the pretty-printed `inputPreview` because pretty-printing inserts real newlines, which are `\p{Cc}`, so scanning it would gate every multi-field call on JSON's own formatting; the diff needs its own pass because that arm renders `new_string` RAW, where the JSON has escaped the C0 controls that matter most. **Every separator here is a SPACE, and both halves of that were paid for.** Joining the three parts with a newline gated every card ever drawn, a newline being `\p{Cc}`; and neutralizing the diff's own `\n\t\r` by REMOVAL glued the lines either side into one token, so a Cyrillic comment above an unindented Latin line became `Проверкаexport` and was reported as a look-alike hazard naming plain `U+0065`. A space is `\p{Zs}`, in none of the three classes, so it invents nothing either way.

**Ordinary emoji are exempt, and the exemption walks BACK over emoji suffixes rather than reading the adjacent codepoint.** `\p{Default_Ignorable_Code_Point}` covers VS16 and the ZWJ, so without it `⚠️` or `👩‍💻` in a proposed patch disabled Approve behind the red banner — and a warning that fires on routine text is one people learn to tick through, which costs more than it protects. Variation selectors are subtracted from the class outright (they only ever follow a base character to pick its presentation); a ZWJ is exempted by CONTEXT, since the same codepoint between LETTERS splits a word into pieces that render as one and is a real hazard. Reading the immediately-adjacent codepoint was not enough: in `👩🏽‍💻` the character before the joiner is U+1F3FD (`Emoji_Modifier`) and in `🏳️‍🌈` it is U+FE0F, neither of them `Extended_Pictographic` — so the two commonest emoji shapes on the planet gated while the unmodified `👩‍💻` beside them passed.

A PROPOSED PATCH needs no card of its own at all, and that is the point: the daemon files it as an ordinary `approval_request` carrying `toolName: 'propose_patch'`, so `approval-card.tsx` renders it and the existing verdict channel answers it. The one renderer change is four lines in **`diff-view.tsx`** — `editDiffOf` recognises that tool name over `Edit`'s own field names (`old_string`→`new_string`), with the `old_string` made optional so a whole-file proposal falls through to `Write`'s additions-only shape. An `Edit` missing its `old_string` still answers null, deliberately: that arm belongs to the proposal alone, and letting a malformed edit through it would draw it as a confident file creation. The tool name is a bare literal with a TWIN comment, like the ones in `transcript-groups.ts`, because the name reaches here inside a `z.unknown()` payload and nothing generated spans that seam.

A PROPOSED PLAN rides the same `approval_request` row and does get a body of its own: **`plan-card.tsx`** — its twin parser (`readPlan`, defensive because the payload is `z.unknown()` on the wire) plus `PlanCard`, routed from `ApprovalCard` by the tool name and falling back to the PERMISSION body when nothing readable is there, exactly as an `AskUserQuestion` whose payload parses to nothing does — a malformed call must stay answerable rather than draw an empty card. The steps are a real `<ol>` with drawn numbers: the order IS the plan, and the numbers are drawn rather than left to the list marker so they line up with a step whose text wraps. The card's own addition is the **note** — one optional textarea sent with either verdict, over the same `answer` field a question's reply uses, trimmed and sent as a one-argument verdict when empty so the daemon's note branch is never entered with a blank string. A settled card keeps the plan on screen with `✓ approved` / `✗ rejected` and the note under it, because the rest of the conversation refers back to the plan. `useOneShotVerdict` moved to **`use-one-shot-verdict.ts`** when this third body wanted it — the freeze-until-the-verdict-round-trips timing is one contract for all three cards, and leaving it private to `approval-card.tsx` would have made that file the others' dependency for no reason but where it was written first.

The agent's own task list: `task-payload.ts` — the twin parser plus the FOLD, since a patch names only what moved; `task-list.tsx` — the `TaskListCard` the transcript shows where the list moved, and the shared `TaskRows` the SIDE PANEL composes for the current list (`agents-panel.tsx`, BELOW that agent's delegates and, like them, not behind a disclosure). A delegate's list stays in its own block, whose collapsed header carries its count, since the block is closed by default. **Only the LATEST card of a thread shows its rows**: an agent that says one sentence between two announcements gets a card on each side of it, and both used to print the whole list — eight rows, then eight rows again with one more spinner, a paragraph apart (the reported "Todo is duplicating"). The open state is DERIVED from `latest` with a manual override on top rather than seeded into `useState` — an initial value only applies at mount, so the card that was current when it appeared would stay expanded for good and the duplication returns on the next announcement. The COMPOSER SHELF's task chip says `done/total` through the same `TaskCount` (`composer-shelf.tsx`'s `TaskListChip`, which was the chat header's readout until the move below): a lone count of what is left cannot distinguish six-of-seven from six-of-sixty and only ever shrinks.

**In the PANEL the list is bounded and scrolls itself; in the transcript it is not** (`TaskScrollRows` vs `TaskRows`). Reported as "also we need scroll for tasks list" against a thirteen-task card, and the shape of it is that the list never overflowed anything: the panel has ONE scroller over every agent card, so a long list simply makes its own card that tall and pushes the next agent — and the artifacts under it — off the screen. Measured on the reporter's own CI243 thread, a SIX-task list: the agent card 439px → 326px, the task section 325px → 212px, and it now stays there whatever the length. The transcript keeps the unbounded rows on purpose — it is a document the reader scrolls, and a nested scroll box in it takes the wheel away from the page while the pointer is over the list. Two things make the bound safe rather than merely tidy. It FOLLOWS the running task (`revealWithinBox` in `scroll-to-bottom.ts`), or a list of thirteen with the sixth in progress would show the five that are done and hide the one thing happening — a worse answer than the tall card. And it moves only when that row has actually left the frame, so a reader who scrolled the box keeps their place. `scrollIntoView` is not an option for it, for the reason recorded beside `scrollToBottom`: it walks every scrollable ancestor, and this box sits inside the panel's scroller inside a shell whose window scroll was itself a shipped bug.

**An `in_progress` row only SPINS while something is working through that list** (`taskCardIsLive`): a turn that ended mid-task left a spinner running for good — the reported "finished one task, still in progress for some reason" — and every historical card animated its own in-progress task besides, so a three-step job showed three spinners for one running task. Two conditions, both needed: only a thread's LAST card can be live, and only while the run has not settled past it — read as a MOMENT, like `subagentBlockStatus`, so a card written after the settle (the CLI carrying on by itself) still spins.

**That moment is the run's own terminal ITEM, not merely its row's `updatedAt`** (`settled-status.ts` → `lastTerminalItemAt`, whose later-of-the-two both `runStoppedAt` and `activeRunSettledAt` now take): items never touch that column, so it is only as fresh as the last thing that DID write the row and can sit BEFORE the stop it describes — a task announcement can land inside that gap and read as work produced AFTER the settle, spinning on a run the user had just stopped. The same gap sat under every `subagentBlockStatus` reading. A stalled row keeps a glyph of its own rather than falling back to `pending`'s: the agent started that task and stopped there.

**What the agents are RUNNING on this machine** (`chats/shell-activity.ts` — the fold; `chats/shell-list.tsx` — the rows; an uncaptioned band per agent card, above that card's task list). Every other coding CLI puts its live commands on its own screen, and this app had them nowhere: the only record of a shell in flight was the last tool row in the transcript, which says nothing about whether it has come back. The panel is where the ask put it, beside the delegates and the task list — per-agent state a reader opens this column to read.

**ONE COMMAND IS ONE LINE, and every part of that line is spelled out.** REPORTED against a card showing a single `sleep 240` — "this one looks wrong - not in one line. Also not understandable what is BG" — and it was two separate faults meeting on the same row. The band carried a caption, `1 shell running`, so the commonest case spent a whole line counting the single line beneath it; the caption is GONE, and nothing was lost with it, since the finished commands are deliberately absent so there was never a `done/total` to state (the task band beside it keeps its own caption, because a task row is prose and needs the word `Tasks` to be placed, while a shell row leads with the terminal glyph and places itself). That glyph REPLACED a per-row spinner: every row here is live by construction, so the spinner was one mark repeated N times, and the clock beside it is already moving. And the detached marker, `BG`, is now the word `background` in a bordered tag — two letters of shell jargon, set in the same muted grey as the clock, made the one row carrying an explanation the one nobody could decode; a tag rather than more muted text, because a bare word between a command and a duration reads as part of one of them, with the sentence it has no room for on `title`. The clock is a right-aligned COLUMN (`min-w`, so nothing bounds how long a detached command may run): left to size itself it swings from `3s` to `1m 58s` and pushes everything before it sideways, so two rows of one list carried their tags at two different x positions — measured in the running app at 1217px for both once fixed.

**And the glyph is lifted a pixel off the box centre, which is an OPTICAL correction rather than a fudge.** REPORTED as "it should be on the same line, now icon a bit more down". `items-center` centres BOXES, and a line box is not symmetric about its ink: it reserves descender space below the baseline that a command like `sleep 400` mostly does not use, so the text's visible band sits ABOVE the box centre while a square glyph lands exactly on it. Measured off the rendered pixels, the glyph's ink centred **3.5 device px below the digits'**; after `-translate-y-px` it is 1.5. A PIXEL rather than the full 3.5, because the two ends of the string disagree — `sleep` has a descender, so the whole command's ink centres only 1 device px above the glyph, and closing the gap to the cap band alone would leave the glyph visibly high against the letters. Between the two is where it reads as one line (verified: +3.5 → +1.5 against the digits, +1.0 → −0.5 against the whole command). **A line-height change cannot do this**, which is worth writing down because it is the obvious first idea and was tried twice — here and on the shelf chip: shrinking a centred line box moves its top down by exactly half of what it takes off the leading, so the ink does not move at all. The `-translate-y-px` is pinned by a spec on the CLASS, jsdom computing no layout, and that pin is not a proxy — the class IS the whole of the correction.

Derived from the TRANSCRIPT, because a shell is only ever started by a tool call and only ever ended by one coming back — geniro spawns none of these itself, and the daemon declines ACP's `terminal/*` capability, so an ACP agent runs its own commands too and there is no process on this side to enumerate. A shell is an `execute` call by the one shared classifier (`tool-kind.ts`), so a CLI naming its shell tool anything at all is still recognised; a call that discloses no arguments — routine on cursor — is listed under its own title rather than dropped, since hiding it would answer "what is running" with silence on one of the two CLIs. Background commands are tracked through claude's own bookkeeping: `run_in_background` on the call, the `ID:` its launch replies with, then `BashOutput`'s `<status>`/`<exit_code>` and `KillShell`. A kill that FAILED is not a kill — the CLI answers a handle it cannot find with an error, and retiring the row off that reports a shell nothing stopped as stopped.

**Which tool calls were DETACHED is the daemon's answer, not a match on the CLI's English** (`shell_open` items, read by `shell-activity.ts` → `detachFromShellOpen`). REPORTED as a sidebar row reading `working · waiting on background work` beside a header counting zero shells — one question with two answers, and the two answers had two sources. The sidebar reads `Run.shellsOpen`, which the daemon counts off the CLI's own structured frames (`system/task_started` → `background_work` → `shell_open`); this fold could only recognise a detachment by matching the announcement the CLI writes back to a detached launch, and that match is deliberately strict (see `readLaunchHandle` below — a loose one promotes any command whose OUTPUT quotes the sentence into a shell nothing can ever close). So it MISSES BY DESIGN, and every miss put the count over the list. The daemon now writes the open as a row, exactly as it already wrote the close, so the count and the list are two views of one set — and that row is also how a command whose CLI LIED about finishing reaches this list at all (cursor answers a backgrounded command `exitCode: 0` while it runs; the daemon asks the process table instead, see *A CLI that reports a backgrounded command FINISHED* in `apps/daemon/CLAUDE.md`), which nothing on this side has to know about: it is the same row, the same count and the same chip — and the strict match keeps its remaining job, which is the only one it was ever uniquely good for: the handle a later `BashOutput` probe is addressed to. Three details. The row MARKS and never CREATES — an open for a call below the loaded window would otherwise put a command on screen with no name to draw. Nothing orders it against the launch's own reply, so the fold handles both orders: arriving first it is remembered so the reply's "no announcement means this is the output" arm cannot close it, arriving second it REOPENS the shell that arm just closed (`completed` being the only status reachable by then, since a probe is addressed to a handle nothing has named yet). And on the daemon side it had to join the predicate that decides whether an off-turn row means the run is working (`restatesRunAsWorking`, renamed from `closesWork` when it stopped being only about closes): an OPEN really is work beginning, but a backgrounded command deliberately does not hold a turn, so reading it as `running` would latch the spinner from the other end — a shell emits no further row until its close.

**A launch is recognised by the CLI's whole ANNOUNCEMENT, never by the characters `ID:`** (`shell-activity.ts` → `readLaunchHandle`). REPORTED as "я вижу, что thread completed, хотя на самом деле нет, и есть три терминала" beside "эти шелл команды вообще стейлд, то есть они на самом деле выполнились" — and the second report is the true one: the thread had finished and the panel was lying. The reader matched `\bID:\s*([^\s.]+)` anywhere in a tool reply, and a FOREGROUND command's reply is its own OUTPUT — so any command printing those two characters (a `git show` of Go source with a struct field, a JSON blob, a doc listing) was promoted to a detached shell, and a detached shell only ever ends on a probe, a kill or the daemon's `shell_info`, none of which is coming for a command that already exited. It was therefore listed as running for the life of the transcript, and counted in the header. Measured on the reporter's own `geniro.db`, run `d64593d0`: **11 phantoms out of 690 shells**, with handles `row`, `spec`, `resp`, `"foryou",`, the oldest running for a day and a half. The three real wordings are ONE ternary in the shipped 2.1.237 binary (a plain launch, one the user backgrounded, one that outran its timeout) and every arm ends `Output is being written to: <path>.`, so that whole shape is what is matched — which also fixes a quieter bug, the middle arm's `(ID: x)` having captured `x)` into the handle, where no later probe could match it. It is anchored at the START of the reply, a guard that earned itself within a day: a `sqlite3` query printing past launch replies and a `grep` over the CLI binary each produced a phantom in the session that wrote this, one carrying the literal handle `${e}`. And the reply now decides BOTH ways — a call that ASKED for the background and came back with plain output was never detached, so it closes instead of stranding a row with no handle to be matched by. The old doc justified the loose match by saying a miss is survivable; it is, and that is the argument for tightening: a miss costs one row that should have been listed, a false positive costs a row that can never be unlisted. What this does NOT fix is history — the daemon's shell-settle channel first wrote a row on 2026-08-24 21:46, and the 95 background commands launched before it have no ending in the transcript at all, so old conversations keep their stale rows.

**Only what is running — and how that is KNOWN differs by kind, which is the whole of the gate.** The finished ones are already in the transcript in full and in order, so repeating the last forty of them in a 280px column would bury the row this exists to show. A FOREGROUND command is read as running because its tool call has no reply, and that reading is only as good as the turn: a cancelled or abandoned one leaves a call that never comes back, and the row would stand for the rest of the session claiming a process that died with the turn. So those are gated on **`isSettledRunStatus`** — has this agent stopped for good. A DETACHED command is not read that way and is deliberately NOT gated: its call is answered within the second, its end is a durable `shell_info` row, and the daemon writes one for every shell still open when the CLI process dies — so its liveness is reported rather than inferred, and the run settling says nothing about it. Gating it too made the panel go blank on exactly the case it exists for, since a backgrounded command no longer holds the turn open (see `apps/daemon/CLAUDE.md`): the agent finishes, the turn settles `completed`, and the `pnpm dev` runs on with nothing on screen. The whole rule lives in ONE place (`Chats.tsx`'s `shellsByAgent`), because the header's counter is the same reading over the same map and two copies is how a `2` up there comes to sit over three cards below.

**And it is the MAIN thread's shells alone — a REVERSAL of what shipped first.** A delegate's `pnpm build` is still a process on the user's machine, which is why it was originally in; that reading is true of one delegate and false of a fan-out. REPORTED as "we should not show terminals from subagents", over a review with ten reviewers out at once: in a 1:1 chat every row carries `nodeId: null`, so a delegate's commands land in the SAME bucket as the agent's own and the `Terminals` chip counts them together with nothing on the row saying which thread launched it — the commands the reader opened the chip for were then the minority of a list they could not filter by eye. Nothing is lost that is not answered better elsewhere: a delegate's block holds its tool rows in full, its card in the agents panel is where its state is read, and the run row's own `shellsOpen` still counts every detached command whoever launched it, so a fan-out holding the turn open is still SAID on the surface that says it. The drop is at the ITEM (`shell-activity.ts`, on `subagentIdOf`), before anything is indexed, which is what lets the daemon's `shell_open` / `shell_info` rows stay unguarded: each can only ever reach a shell this fold created, and for a delegate there is none.

**A detached command's END is a row the DAEMON writes** (`shell_info`, read by `shell-activity.ts`; see `apps/daemon/CLAUDE.md` for the half that produces it). Its launching call is answered the moment the CLI accepts it, so the transcript otherwise holds a start and no end — which is what made the list ACCUMULATE: measured on a live 45-second `sleep`, the completion reached the model out of band and the conversation as a sentence the agent wrote, so every background command a session launched stayed listed until its turn ended. The reader matches by launching call, else by the CLI's own work id (the settle names the call on one of its two channels and not the other), and it only ever coarsens a shell still believed to be RUNNING — one a `BashOutput` probe already settled knows how it ended, with an exit code, and that is the better answer. `shell_info` is also skipped OUTRIGHT by `groupTranscript`: it renders as nothing, and the fall-through treats any other kind as the node having said something and closes its open tool group, so a burst of background commands would chop one turn's tools into a run of one-call rows for rows nobody can see.

**Clicking a row opens that command's own terminal** (`shell-output-dialog.tsx` over `GET /v1/chats/:runId/shell-output`). It is POLLED while the command runs and read once when it is finished — a bounded tail of one file, unlike the context breakdown next door, which is a multi-second round trip to the live CLI and so is fetched once per open. It follows the newest line unless the reader has scrolled up, says out loud when it is showing only the END of a longer output, and holds the command as a SNAPSHOT rather than following the live fold: a shell leaves the running list the moment it settles, so following it would close the dialog at exactly the moment the reader came to see how it ended.

**And it is drawn in the command's OWN colours** (`components/ui/ansi.ts` — the pure parser; `components/ui/ansi-text.tsx` — the one place a shell's escape sequences are rendered). Command output is not plain text: anything with `--color=always` or `FORCE_COLOR` emits SGR codes, and drawn verbatim the escape byte is INVISIBLE in HTML while its tail is not — a green `PASS` reaching the screen as `[32mPASS[0m`, corrupted rather than coloured. The parser also plays out what a terminal would have done with the rest: a line rewritten by a progress bar (`10%\r20%\r30%`) shows its last state instead of all three at once, and the sequences that cannot be honoured here — cursor moves, erase-line, window titles — are DROPPED rather than printed, which is the difference between a spinner's log being readable and being one `[2K` per tick.

Three rules it holds. **Every colour is a `--ansi-*` TOKEN**, aliasing the semantic and code palettes wherever one already carries the hue (red is `--destructive`, green `--success`, blue the highlighter's own `--code-variable`) — a terminal's own palette is built for a black background, and `#00ff00` on this cream card is unreadable; the one new literal is cyan, because nothing in the palette had one.

**The BRIGHT half (90–97) is the same eight NAMES carrying a flag, and the themes answer it differently** — `AnsiSpan.bright`, drawn as a `--ansi-bright-*` token, never as a lightened value the parser computed. Putting the decision in CSS is the whole point, because "brighter" is a fact about the ground: the dark theme lifts all eight about 15% in luminance with the hue held (each clearing AA on `--card` by 7.4–10.4:1, a visible step above its normal), while the light theme aliases the six CHROMATIC brights back onto their normal twin, since on cream a brighter ink is a fainter one and the weight `ESC[1m` carries says the same thing legibly. The GREYS do not alias on either theme, and that was a real defect rather than an unexploited option: `ESC[90m` is by far the most common bright code in real output — git, npm, pnpm and cargo all reach for it for timestamps and secondary prose — it means DIM, and mapping it onto `--ansi-black` (which is `--foreground` on both themes, since a literal black would be invisible on dark) was drawing it at full strength, the exact opposite of what the program asked for. Both themes now put it on the palette's faintest ink, at the AA-large bar `--code-punctuation` already documents. The four greys sort into four distinct steps on dark — bright-black (faintest), white (dim), black (default), bright-white (strongest); on light `--ansi-bright-white` and `--ansi-black` do coincide, and there is nowhere else for either to go. The 256-colour path follows the same layout for free, 8–15 being that palette's own bright eight in the same order.

And it is **deliberately partial** — no background fills (a per-span fill on cream is noise), no 24-bit colour (there is no token for an arbitrary value, so the run takes the surface's colour, with its parameters still consumed so the digits do not print). The copy control beside the output hands over `stripAnsi(text)`: the spans are for the eye, and what a reader pastes into a bug report must not carry the codes that coloured them.

**The count also sits on the COMPOSER SHELF, as a chip** (`composer-shelf.tsx`'s `RunningShellChips`, `slot="running-shells"`) — moved there from the chat header on request ("я хочу перенести наши терминалы все над текст-эрией"), holding the same `ShellRows` behind the same hover-popover the header used. It was the header's counter for one release, beside the delegates', and that arrangement is where the ask began ("количество активных шелов рядом с количеством активных субагентов"); what changed is only the anchor, since the shelf is the row of what a thread is currently producing and a running command is the most immediate of those. The chip's own three parts — a leading SPINNER as the mark, the word `Terminals`, a trailing muted count — were reported twice before they settled, and the reasoning is written at `RunningShellChips`. Unlike the header counter it replaced it is **not drawn at zero**: a fixed row of readouts needs "none" told apart from "no such readout", and a shelf makes that distinction for itself, being a row of what EXISTS. That is also what left `ShellRows`' empty-case sentence unreachable — the chip returns null on an empty list and the panel band is not rendered at all — so it is dead code awaiting a caller or a deletion, deliberately left rather than removed in a change about something else. **The liveness gate lives in `Chats.tsx`, at the one place both are fed from** — `shellsByAgent` is built from the fold, re-keyed to the panel's card ids and filtered to agents still working, and the header's count is a flatten of that same map. Two copies of the rule is how a `2` in the header comes to sit over three cards below it; the panel therefore renders exactly what it is given and invents no filter of its own.

**The SUB-AGENT count and the TASK list are chips on that same shelf** (`composer-shelf.tsx`'s `RunningSubagentChips` and `TaskListChip`, slots `running-subagents` / `open-tasks`), moved off the chat header on the ask that followed the terminals one ("move subagents to down chips as well, with todo list"). The move is an ANCHOR change and nothing else: the same `HoverPopover`, the same hover-then-pin, the same panels — the delegate list, and `TaskScrollRows`, which already bounds itself and follows the running row. `sidePanelLive` in `Chats.tsx` still feeds all three chips from one reading, so the shelf and the agents panel cannot disagree about what is working. Two things did change with the anchor. The sub-agent chip is **no longer drawn at zero**, reversing the header's own rule ("здесь должна быть всегда иконка саб-эйджентов, даже если их ноль") — and reversing it is right, because that rule existed to keep "none" distinguishable from "no such readout" on a FIXED row, which a shelf does for itself, being a row of what exists. The task chip is the exception on the row and keeps the header's `total > 0`: a finished checklist still answers "what did it do, and what did it leave", where a returned command and a finished delegate are history the transcript already holds. Its mark is the delegate glyph rather than a spinner, unlike its neighbour's — that spinner was asked for by name and is honest there (every `Terminals` row is live by construction), while this list holds the FINISHED delegates too, and two spinners on one row is noise besides.

**The shelf's order is DURABLE → VOLATILE, left to right, and that is the whole rule**: pull requests, tasks, workflow, sub-agents, terminals. A chip that comes and goes must never shift one that stays, so the ones that end within a turn go last — which is also why the task chip sits second rather than out by the terminals it used to stand beside in the header. `SubagentRows` (`chats/subagent-list.tsx`, lifted out of `chat-header.tsx` with the count) lists the LIVE delegates and counts the finished ones behind a fold, shut by default — the same answer the agents panel gives, and a REVERSAL of what shipped here first. The rows arrive in the panel's order, which groups them under the agent that launched each, so a fan-out that spawned forty and finished thirty-eight buries its two live ones in the middle of a scrolling popover; this list used to answer that by sorting the running rows to the top, on the stated reasoning that a popover cannot fold. It can — the panel is pinned and its rows already carry buttons — and sorting is the weaker fix, which is what came back ("completed subagents should be collapsed") over a box six running and four finished deep, every row past the sixth being work that is over. SETTLED is `isSettledRunStatus` rather than `!== 'running'`, so a delegate that is `held`, `pending` or waiting on the user stays listed: hiding the one row that cannot advance without them behind a control captioned `finished` is exactly the wrong place for it. The fold is `usePersistedFlag`, because the popover's panel is mounted afresh on every hover and component state would forget the choice between two glances at the same list. Its rows open the same sub-agent detail the panel's own rows do (`onOpen` → `setDetailSubagentId`), on the rule every list here follows — absent the callback they are plain text, never a row that merely looks clickable.

**The chips stay SEPARATE, and exactly ONE run of them is joined: the pull requests** (`chats/shelf-chip.ts` — `SHELF_CHIP_CLASS` for a standalone chip, `SHELF_GROUP_CLASS` + `SHELF_SEGMENT_CLASS` for the joined run). Reported first as "let's join all chips somehow to prs. like it should be more understandable", which was read as "join every chip" and shipped as one segmented bar across the whole row — rejected on sight: "but chips still should be separate, as before. What i told - ts only for prs". The rule that survives both rounds is that **touching is a CLAIM that two things are one**, so it may only be made where it is true: it is true of `#76` and the `All 4` that counts it, false of a terminal and a task list. The defect the first report named was real and narrow — `All 4` standing apart as a fifth identical pill read as a peer of `Tasks 2/6`, because nothing said which items belonged together. So the group wears the same card a chip wears (a group of one is indistinguishable from a standalone chip, which is why `ThreadPullRequestChips` always renders it — no branch, nothing to keep in step), `divide-x` separates its segments, and a segment carries no card of its own: one with its own hairline draws a second line beside the divider, one with its own radius leaves notches of the group's background inside the run. `overflow-hidden` clips the end segments to the card's radius and does NOT clip the popovers, which are `anchor="viewport"` and therefore `fixed`. Two segment classes are OVERRIDES and both are invisible until you look: `rounded-none` beats `HoverPopover`'s own `rounded-full` on its trigger (a standalone chip's `rounded-lg` wins that merge; a segment with no radius at all does not, and the counter fills as a lozenge inside a square segment), and `focus-visible:bg-sidebar-accent` is the keyboard indicator, since a focus RING is a box-shadow outside the element's box and `overflow-hidden` shaves it. **Both `All N` controls gained the glyph of what they count** — the pull-request mark, the workflow mark — which is separable from the joining and is the half that carries the meaning: it was the one item on the shelf naming no subject, and the hardest to guess, being a control rather than a reading. The WORKFLOW `All N` is deliberately still a standalone chip: the same argument applies to it, but the joining was asked for on the pull requests alone.

**Under a SQUEEZE the row degrades by clipping, never by overlapping** — two separate fixes, both invisible until the shelf runs short (a narrow window, a widened chat list, an open agents panel). First, `shrink-0` belongs on `HoverPopover`'s WRAPPER as well as on its trigger: the wrapper is what the shelf lays out and the trigger is a flex child of it, so with the class on the trigger alone the wrapper collapsed while the button inside refused to — the button spilled out of its own box and the next chip was placed against the collapsed one. Reported as "terminals chip have some problems with margin" and measured at a 430px shelf: the sub-agents span ran 725–810 against its own button's 725–837, with the terminals span beginning at 816, i.e. 21px INSIDE its neighbour. The gap does not shrink there; it vanishes and the chips overlap. Second, `SHELF_SEGMENT_CLASS` carries its own `overflow-hidden`, which is a different clip from the group's: a pull-request chip is `[icon][number][title]` with the number deliberately `shrink-0` (it identifies the thing, so it must never truncate), and that unshrinkable content printed over the `All 4` beside it — the group's clip cannot help, the two being siblings inside it. A cut-off number reads as "there is more here"; overlapping glyphs read as a broken app. Both are pinned on the emitted CLASSES rather than on geometry, since jsdom computes no layout and the overlap itself is unobservable there.

**While a turn runs there is ONE clock, and it is the worked total.** REPORTED against a header reading `running · 21s · worked 21s`: "у нас сейчас два раза показывается таймер… нам нужен только таймер, сколько он в целом работал". The first figure was this turn's raw wall clock (`ElapsedTime`, now deleted with its `turnStartedAt` prop and the `Chats.tsx` memo behind it), and on a thread's first turn the two are the same number printed twice. Only the RUNNING half went: settled, that slot still says when the thread last spoke, and `completed · 4m · worked 1h 41m 5s / 5 turns` is two different answers rather than one of them repeated. The reason a wall clock was there at all is answered by what replaces it — the relative time reads "just now" for a whole turn, which is why it cannot be shown while running, and `worked` moves every second, which is what the relative time could not do. One thing is genuinely lost: `worked` PAUSES on an approval card by design, so a thread parked ten minutes now shows the seconds it worked rather than the minutes it waited — the card itself is on screen saying so.

**How long each turn WORKED** (`turn-duration.ts` — the twin parser over `usage.durationMs`/`apiMs`, the wall-clock fallback, `TurnDurationContext` and `formatDuration`; rendered on the `turn_complete` row beside the cost it already carried, and summed into the header as `worked 4m 12s / 6 turns`). The app showed how long AGO a thread last spoke and never how long it worked: the header clock and the working row are live-only and both vanish at the settle, while a sub-agent block has said `took 13s` since M3 — so a delegate was better instrumented than the agent that launched it. Two clocks, and the CLI's own wins where it exists: claude's `result` line carries `duration_ms`/`duration_api_ms` (probed 2026-08-14; every timing field was being dropped by `readClaudeUsage`, which read only `total_cost_usd` beside them) and measures the agent WORKING, so it counts neither the first-prompt MCP-readiness hold nor a stretch parked on an approval card. ACP reports no timing at all and declares so rather than passing off the driver's own wall clock as the agent's figure, so a cursor turn is measured from its durable rows — MINUS the parked stretches, which is what keeps the fallback meaning the same thing as the primary: an `approval_request` and the `approval_verdict`/`unanswerable` closing it are both rows, so the wait is readable, and without the subtraction a turn blocked half an hour on a question card would report the lunch break as work. The thread total is the SUM of its turns and never `updatedAt - createdAt`, which is the plausible-looking wrong number — a chat left open across three days with five minutes of work in it spans `3d` and worked `5m`, and both are now on the header at once. `apiMs` can EXCEED `durationMs` on a turn served off a kept session, so the tooltip's API/own-work split is withheld on that reading rather than clamped to a fabricated `0s`.

**That middle source is only as fresh as the client keeps it** (`rememberRunContext` in `use-chat-run.ts`). The row outranks the transcript because the daemon's row moves with every reading while the transcript carries a figure per SETTLED turn — but the copy in the renderer was whatever `GET /v1/chats` answered at mount, and nothing refreshed it: `run_status` carries status, activity, `updatedAt`, the preview and the title, and no reading. So the ring sat on a frozen number for the life of the window while the daemon's row went on moving. REPORTED as "прыгнул кружочек с контекстом. Он показывал 50%. Как только я на него навёл, он начал показывать правильную цифру: 70%" — the ring on the frozen copy, the readout asking the live CLI; the daemon's row for that chat held 740,515 of 1,000,000 at that moment. Every live reading is now mirrored onto the copy, so the fallback a settle drops into is the newest figure this client has actually seen rather than an old one. Guarded on the value CHANGING (the event fires many times a second, and an unconditional write would re-render the sidebar per delta) and on it being POSITIVE — the same "a reported 0 is not a measurement" rule the live plane and the transcript fold already apply, so a settle that clears the figure cannot erase the last real one.

**The RING is drawn from three sources in strict recency order, and the middle one is the run ROW** (`chatContext` in `Chats.tsx`): the live delta for this turn's latest request, then `Run.contextTokens` — every reading the CLI reported, filed by the daemon as it arrives — then the last SETTLED turn of the loaded transcript. REPORTED as a ring reading `2%` beside a panel reading `46%`, on a chat whose last settled turn had ended directly after a `/compact`: the transcript's newest figure was 16.7k of 1M and the hour of work since had regrown the window to 462k with nothing settled to record it. The live plane HAD that figure and is ephemeral — a reload, a reconnect or a first open starts without one — and the transcript cannot have it at all until the turn ends, so the row is the only thing a cold window can read. Reading the live value directly rather than through `agents[0]` is what makes the order true: that field already collapses live onto transcript, which would put the oldest source ahead of the row. `useContextReadings` stays the last fallback, for the one stretch the row cannot cover — a switch whose refetch is still in flight.

**A WORKFLOW run's composer ring is its ROOT agent's**, and that is the one case where the ring is about a node rather than the run: a workflow's nodes each hold a window, so there is no run-level figure — except the root's, which is the node the user prompted and the one the run is a conversation with. `chatContext` resolves it through `wfNodes.rootId` (`rootAgentOf`, which needs a trigger EDGE into an agent, not merely an agent in the node list) and answers nulls for the four states where there is no single root — before the workflow fetch resolves, on a non-workflow run, on a graph with none, and on one with several — so the ring is withheld rather than drawn about no particular node. It renders beside the trigger chip, since the composer's per-CLI chip row is a chat's alone. A THIRD ring, the callee's, sits on the call block's summary band (`callBlockContext` in `transcript-groups.ts`), folded from that callee's own `turn_complete` rows: each side of a call holds its own window, so it is the one figure about a call the caller's ring cannot state.

**A WORKFLOW NODE's ring has the same shape one level down, and its middle sources are the durable rows** (`cardContextOf` in `Chats.tsx`, fed by `chats/use-node-context.ts`). FIVE ranks, first match wins: the node's own live delta; the newest CALL thread carrying a live one; the newest call thread carrying a DURABLE one (`call_context`, keyed `(runId, callId)`); `NodeState.contextTokens` / `contextWindowTokens`; the transcript's settled turn. The third rank applies ONLY to a node that runs nothing but calls — `node_state` is written on every reading while `call_context` is written only under a call, so for a node whose own DAG turn ran after its last call the node row holds the NEWER figure and rank 3 would hand back a staler one; `threadsOf` emits a `main` thread exactly when that turn happened, which is the test. The per-call rows also feed the sidebar's THREAD rows directly (`callThreadsOf`), which is what makes a node called several times draw one ring per call instead of one flickering between windows. The daemon has filed those columns since the per-node ring existed; nothing READ them until this hook, so a workflow node's ring simply went blank on a reload and stayed blank while a node parked in `await_agent` emitted nothing for minutes. They are fetched with `GET /v1/workflows/runs/:runId/nodes` on run OPEN and again on RECONNECT, and on those two moments alone — everything in between arrives as a delta, which outranks them. Reconnect needs its own trigger (`reconnectNonce` on `use-chat-run.ts`) precisely because a figure on a column is not a row: the reconnect item-delta replays what the socket missed, and a `node_state` column is not in it. The map is cleared on entry to the effect, so a run→run switch cannot leave the previous run's figures standing — two runs of one workflow share node ids, which is the same mismatch this section's own rule forbids for the metrics panel.

**A COMPACTION invalidates every reading taken before it, and there are four places one survives.** REPORTED as "после компакта кружочек не обновляется. Он все еще так же заполнен с контекстом", and it is a defect of the CLI whose compaction geniro performs ITSELF — cursor, which has none of its own (`AdapterConfig.geniroCommands`). There, the conversation is DISCARDED and a summary is put aside for the turn that replaces it, so nothing measures the new one until the user sends the next message; every source the ring reads went on holding the old figure. Reproduced in the dev app: a cursor chat at `Context 10% full — 101.5k of 1M` read exactly that directly under its own row saying `everything before it is no longer in its context`. The daemon clears the run row (`RunDao.forgetContext` — the count only, never the window, which belongs to the model) and stamps `conversationReplaced` on the compaction row; the renderer then answers the other three, and each needed its own: the transcript FOLD resets at that row (`endsContextHistory`, which also covers the CLI's own compaction marker — a figure the compaction reported about itself lands BELOW it and overwrites the null), the LIVE plane is cleared when the row arrives (it is dropped on a run switch, never on a settle, so it outlives the turn it was filled in) along with this window's mirrored copy of the run row, and the RECALL is not consulted at all while a transcript is loaded — a loaded transcript with no reading is an answer, while an empty one is the refetch the recall exists for. Only geniro's own compaction clears the live plane: a CLI that compacts for itself REPORTS what it left behind, and that reading arrives around its own marker rather than safely after it. What the user sees between the compaction and their next message is an EMPTY ring saying why (`ContextMeter`'s `awaitingReading`), not the absence of one: withholding it was the first cut of this fix and came straight back — "я на втором скриншоте у тебя сейчас вообще кружочку не вижу!" — on the same reading the effort and context-window chips are drawn by, and worse here, because the ring is the one thing on that row a user watches climb. It is muted rather than green, since a filled nought would claim an empty window nobody has measured, and it needs the WINDOW to be a gauge at all — which is why `chatContext` now reads the denominator whether or not it has a count. Verified end to end on cursor: `101.5k` → an empty ring reading `Conversation compacted — its new size is measured on the next message` → `64.5k` on the next turn.

**What the context window actually HOLDS** (`context-panel.tsx` + `chat-metrics.ts`, opened by the existing `context-meter` ring). The ring answered "how much room is left" and nothing about what filled it, which is the whole of the report: a user pointing at `9%` and asking for the statistics their own CLI's `/context` prints. Fetched from `GET /v1/chats/:runId/metrics` when the readout is OPENED and never polled — it is a multi-second question put to the user's own running agent — and re-fetched on every open rather than cached, since the window is exactly what changes between two glances at it; the previous reading stays on screen while the SAME chat is re-read, so the re-fetch costs no blank panel — a DIFFERENT chat starts blank instead, since a reading is carried with the run it was taken from and a mismatch reads as empty (the meter is not unmounted across a chat switch, so the alternative was the previous chat's window, totals and spend sitting under the new chat's name). One component still, not a second meter: the panel is `children` the same `MeterReadout` renders, and the one-line summary steps aside only once a full breakdown has arrived (it states the same used/window pair, and two renderings of one figure inches apart is what the readout was already criticised for). Deferred categories are drawn in their OWN section rather than in the bar, because they sit outside the CLI's total — one live reading had 274k deferred against a 98k total, which in one bar reports a window nearly four times fuller than it is. Category colours come from the avatar palette by POSITION in the CLI's own list, never by name: the names belong to the CLI and it is free to invent one, which a name-keyed map would leave uncoloured or, worse, silently give a neighbour's colour. Offered for a CHAT only — a workflow run's nodes each hold their own process, so `metricsRunId` is null there and the panel is never shown under a name it does not describe. **The panel is ordered by what a reader came for, not by where the figures came from**: the window headline, then the account's PLAN LIMITS, then the thread's totals, and only then the itemization (deferred rows, instruction files, one row per MCP server). Those last three are open-ended, and with a dozen servers they run longer than the 26rem scroll box — which is what put the plan limits a screen and a half below the fold, with the popover's own bottom edge reading as the end of the content ("the weekly-limits feature — I open it on claude and see nothing"). `Breakdown` therefore renders the window itself and `ContextDetail` the itemization, so the two can sit on opposite sides of the limits.

**TWO money formats, and every dollar on screen comes from one of them** (`chats/agent-activity.ts`). They agree above a cent and differ only below it, where a bare 2-decimal rounding prints `$0.00` and claims a turn cost nothing: `formatUsd` answers with a BOUND (`<$0.01`) for aggregates in a column — the Stats breakdowns, the context meter's run total — where every figure is the same width and the reader is comparing rows; `formatExactUsd` answers with the VALUE (`$0.0034`) for a figure that stands alone and IS the point — the thread header's cost, the `✓ done · 21s · $0.42` note under a finished turn. There were THREE before, the third being a bare `toFixed(4)` in `transcript-item.tsx` with no rule behind it, which rendered a 42-cent turn as `$0.4200` two hundred pixels under a header writing `$0.42` — one number, two notations, one screen. The header's own local copy (a second function also called `formatUsd`, differing again) is gone with it. The spec pins the pair by asserting they AGREE at and above a cent, which is where every figure a reader could see twice actually lives.

**A badge that repeats the name beside it states no second fact.** The agents panel's card is `agent.name` + a muted badge carrying `agent.agent` — which is news on a workflow card (`Reviewer` · `claude`) and nothing at all on a 1:1 chat, where the agent IS named after its CLI: that card read `claude … claude`, the same word twice on one row, on the most common chat in the app. The badge is dropped when it equals the name. **The rule keys on "would this repeat the text beside it", never on "is this a workflow"**, and that distinction is the whole of it: `Chats.tsx`'s 1:1 branch sets BOTH fields from `activeRun.agentKind`, so they are the same string by construction, while its node branch sets `name` from `node.name ?? node.id` and `agent` from `node.agent` — separate fields of the graph, which is why a named node keeps its badge. Queried during review as exactly that ("it's not gonna work if I have an agent name in case we running workflow?"), so the spec pins all three shapes: no badge on the degenerate card, `cursor-agent` beside `Reviewer`, and — the case where the two candidate rules disagree — `claude` still drawn beside `Orchestrator`, a NAMED node on the same CLI as the doubled card.

**Three things on this page that LOOK redundant and are not, so check here before cutting them.**

**The task list renders TWICE ON PURPOSE** — the transcript's inline card and the agents panel's `Tasks 2/6` section, both expanded, both live, the same six rows and the same spinner on the same in-progress row at the same instant. Raised as a possible defect (measured: 2 live copies of one task line on screen, and 2 of each sub-agent name) and CONFIRMED as wanted: "twice render for todo list it fine". They answer different questions from different places — the transcript holds the list where the agent produced it, in the order the conversation happened; the panel pins the CURRENT state where it stays put while the transcript scrolls away from it. Do not resolve this into one surface.

**The composer shelf's `Tasks 2/6` / `Sub-agents 3` / `Terminals 1` chips** restate counts the agents panel also renders, and that is deliberate and requested: the shelf is the row of what a thread is producing right now, one line above where the user is typing, and its chips are hover-popovers rather than a third expanded copy — `RunningSubagentChips` takes its count as a PROP precisely so there is one answer computed in one place (`composer-shelf.tsx` carries the reports verbatim).

**The chat-list row is four lines** because it carries four requested facts: the PR label and the agent label were asked for by name ("make chip with current pr in threads list smaller… also add second label there - agent type"), and the status/time line has its own recorded history about wrapping. Measured at 86px a row — heavy for a 237px rail, and not something to reclaim by deleting a fact the user asked to see.

**The tail is lost in TWO directions and only one of them had a watcher — the SHRINKING viewport is what "it doesn't autoscroll, even if i click latest" actually was.** *Content grows* is the familiar half, covered by the commit-time effect (`[items, liveText]`) and by the `ResizeObserver` over the scroller's children. *The viewport shrinks* had nothing: everything below the transcript in the column is content-sized — the composer gaining a line, the attachment strip, an approval card, the fast-action bar — and each shortens the transcript by its own height while no row resizes, `scrollTop` never moves, and neither items nor live text change. So nothing fires at all. MEASURED in the running app, one composer growing by six lines: the viewport lost 73px, `scrollTop` moved 0, and the newest message sat 73px below the fold with `aboveTail` still false — which is the second half of the report, because a false `aboveTail` means "Latest" is not even DRAWN. With the scroller in the watch set, the same gesture moves `scrollTop` by exactly the 73px lost and the distance stays 0. The next streamed token re-followed and hid the whole thing again, which is what made it intermittent. So the observer watches the scroller ITSELF alongside its children — one `observe` call, and the reason it is not redundant.

**The history pager takes DIRECTION as well as position, and that is a cost fix rather than the tail fix — worth stating because the opposite is the natural assumption.** `jumpToBottom` animates, so pressing "Latest" from inside the older-page zone fires `scroll` for every frame of the way down, the early frames are still under the threshold, and the pager fired mid-flight; the caller then held the reader's place with `scroller.scrollTop += …`, a write that TERMINATES a smooth scroll. Measured on a 9,000-item thread, ONE press: 147,312px of transcript — two full pages, ~2,000 items off the daemon — fetched during a single animation, and the scroll replaced by a teleport (the guarded build animates 93k → 28k → 9k → 1.7k → 0; the unguarded one reads 0 at the first sample). It did NOT strand the reader: the press re-arms the follow, so the growth it caused re-followed the tail and the viewport still ended at the bottom. `shouldLoadOlder` (`chats/scroll-follow.ts`) therefore buys the fetch and the animation, not the destination. Note the ordering trap inside `onScroll`: the previous-`scrollTop` ref is overwritten mid-handler, so it is read ONCE up front — passing the ref to the second reader hands it `scrollTop === previous`, which reads as "did not move" and silently disables the guard.

Both were measured by driving the running app over CDP, and the harness has one trap worth recording: **an occluded Electron window delivers no `scroll` events and throttles `ResizeObserver`, so every number taken against one is meaningless.** A first pass reported both fixes passing while `document.visibilityState` was `hidden` — the scroll listener had never run at all, `aboveTail` never flipped, and the pager never fired, so the runs proved nothing they appeared to. Assert `visibilityState === 'visible'` (re-raise the window with `osascript -e 'tell application "Electron" to activate'`) before believing any scroll measurement. `Input.dispatchMouseEvent` with `mouseWheel` never acks under Electron and hangs the driver; stepped `scrollTop` writes emit real `scroll` events once the window is visible, and are what these measurements use.

### Workflows

**One noun for the thing, one for its shape: a WORKFLOW is what the user makes, names, opens and runs; a GRAPH is the DAG inside it.** The two were used interchangeably and the seam showed on screen — the nav rail said `Graphs` and the page it opened said `Workflows`, over a directory called `graphs/` whose every export was named `Workflow*`. The rule settles each case rather than picking a favourite: everything the user reads says workflow, and so does the entity in code (`Workflow`, `WorkflowRow`, `WorkflowsApi` — which is also what the daemon's generated client has always called it, and regenerating that vocabulary is not on the table). `graph` survives wherever the DAG itself is the subject: `graph-doc.ts`, `graph-edge.tsx`, `node-validate.ts`, and the page's own subtitle, *"Compose a team of agents as a graph"* — which is the rule in one sentence. So the screen directory is `workflows/` (screens are named for what the user sees — `chats/`, `settings/`, `stats/`) holding `Workflows.tsx`, and the `AppView` member is `'workflows'`. **The daemon's `v1/graphs/` deliberately keeps its name**: it is the graph ENGINE — `graph-executor`, `graph-order`, `graph-validate` — no user reads it, and the workflow store inside it is already `WorkflowStoreService`.

**The library is a LIST, because the one field that tells two workflows apart was the one being clipped.** Measured before the change: four 289px tiles laid across a 1190px page, 175px of content in an 812px pane, each clamping its description to two lines (`min-h-[2.5em]`, so a one-line blurb sat over its own blank line) while `claude ×2 · cursor-agent ×2 · 6 nodes · 8 edges` — near-identical down a library — took the room. Full-width rows hand the description that width and demote the rest to a right rail whose columns are FIXED tracks (`136px`/`84px`, plus `176px` for the agent tally at `xl`) so the figures line up down the page; each row is its own grid, so an `auto` track would align with nothing. Two consequences worth keeping. A `hidden` cell is not laid out at all, so the tracks a breakpoint declares must be exactly the cells it shows — get those out of step and the shape figures slide under the timestamp. And the agent tally is one truncating line of text rather than a `Badge` each: at 176px two badges wrapped, which grew the row and pulled the name off the figures beside it. The container is `gap-px` over a `bg-border` fill, the same construction as the Stats page's `StatGrid`.

**And the row took `NavListItem` rather than keeping its own activation.** The tile was a `div` wearing `role="button"` with a hand-rolled Enter/Space keydown handler and a nested delete button — which ARIA forbids, and which needed an event dam (`stopPropagation` on a wrapper `span`) to stop a delete click from also opening the builder of the workflow being removed. `NavListItem` layers a REAL `<button>` under the content instead, so keyboard activation is the platform's and the delete control is that button's SIBLING: the dam is gone because there is no longer a path to dam. It is used against its grain in one respect — `active={false}` throughout, and the sidebar dress overridden to `rounded-none bg-card` — which is the right trade, since what the library needs from it is the a11y structure and nothing else. The spec pins the structure, not the keystroke: jsdom synthesizes no click from a keydown, so a keyboard assertion there could only re-test jsdom, while `tagName === 'BUTTON'` and "the activation button contains no interactive descendant" both fail on a revert.

**A COUNT beside a graph is read as a count OF the graph, so it had better be one.** Two places printed a number that was a constant, and both sat centimetres from a canvas holding a different number of the same noun. The node cards' collapsed ports block printed `rules.length` under the word `connections` (`node-ports.tsx`) — how many connection RULES the node KIND accepts — so every agent card on every workflow read `inputs 4 connections · outputs 2 connections`, identically, whether it was wired to six nodes or to none. It looked like a live reading and could not change. It now counts the edges ACTUALLY attached to each side, off `useEdges`, which is the thing a reader was trying to learn from it and is worth keeping precisely because ZERO is the case the eye misses on a busy canvas (a leaf agent reads `0 outputs`; the four captions on the dev-team graph sum to its 8 edges). The palette's category headers had the same shape — `Agents 2` was how many agent TYPES the drawer offers, beside a canvas holding four agent nodes — and there the fix is deletion, since opening the block shows one or two tiles anyway.

**And that block was a caption pretending to be a panel.** Measured before the change: a flat **53px** on every card whatever its kind — 41% of a trigger's whole height, 31% of an agent's — spent on two filled two-line pills that restated, on a canvas, what the wires already draw. Collapsed it is now one caption-height row (23px; the trigger card went 128px → 99px) with no fill, and the padding follows the state rather than being sized for the taller of the two. Tone went with the fill: the satisfied sides are muted and the destructive tint is spent on the ONE state worth spotting across a canvas — a side missing a wire it requires. EXPANDED is untouched, because that is the surface where "what can connect here" belongs and its rows are already labelled per rule.

**A selected card is ONE thick edge, and nothing may straddle the silhouette that edge redraws.** REPORTED against a selected instruction block as looking wrong, and it was two faults meeting on the same outline. `ring-offset-2` drew the card's silhouette THREE times — a 1px border, a 2px stripe of page background, then the 2px ring — so what should read as a heavier edge read as two outlines with canvas trapped between them; same-hue strokes with no gap merge into one, which is the whole effect wanted, so the ring is FLUSH now. **EVERY wire is drawn by `graph-edge.tsx`, and the ranking matches what the wires MEAN.** REPORTED as "why do arrows have different design? I see one gray arrow" — and the grey one was the spine. `Workflows.tsx` used to say it outright: *"Data edges keep React Flow's default"*, so the wire that ORDERS THE RUN was an unstyled library hairline with no arrowhead, while `call` and `instruction` — which, per their own doc comment, "order nothing" — had custom tones, dashes, arrowheads and hover chips. **The palette shows everything at once — it holds FOUR tiles.** One trigger, two agents, one instruction block, and they sat behind three accordion blocks that were collapsed by default: reaching any single item cost a click that could only ever reveal one or two. **An INSTRUCTION block is a node that never runs.** The palette's third category (`instruction-node.tsx`, wired with the `instruction` edge kind) drops a free-text block onto the canvas; its text is appended to the turn of every agent it is wired to, ranked after the user's global custom instructions and before that node's own `role` (root `CLAUDE.md` → *Agent instructions*). The two dashed non-data wires — `call` and `instruction` — share ONE component with a per-kind variant (`annotation-edge.tsx`, formerly `call-edge.tsx`), because the back-edge routing is the fiddly half and a second copy is how the two would come to disagree about where a wire goes.

`workflows/` React Flow canvas. **A node's pickers are only as trustworthy as the list behind them, and the list arrives late.** The inspector fetches the SELECTED node's CLI vocabulary, so a node of the other CLI mounts against the previous one's — and the model chip acted on it twice, adopting the first alias for a model-less node and deciding whether a stored model is off-list. Two of those merges changed BEHAVIOUR, both in the direction of the composer. `workflows/model-select.tsx` is **gone**; its free-text entry survives as `ModelSelect`'s `allowCustom` (the builder's case, not the composer's — a workflow runs for months, so naming a model the CLI does not enumerate is worth a field there), and with it the chip's `default model` row. The builder could not previously express that answer at all. ### Settings

`settings/`, `notifications/` (the renderer half of the notifications module — see *System notifications* below), `autogenerated/` the generated daemon client + every daemon wire type (`pnpm generate:api`), `daemon-api.ts` which binds it to a launch handle, `daemon-client.ts` the WS client.

`handoff-open.ts` the ONE resolve-then-open-a-terminal helper, used from the chat surface — ONE call site left, in `chats/Chats.tsx`: handing a thread's conversation to the user's own terminal, which is the only thing on this surface a terminal is still FOR. Settings does not use it.

**A Sign in press is answered by the BUTTON, not by the daemon's reply.** REPORTED as "I press Sign In and there is no loader, nothing — the page opens and the button still sits in the same state". `useCliLogin.start`/`startMcp` set `login` only once `POST /v1/auth/login` returns, and the daemon holds that reply until the CLI prints its URL (`URL_WAIT_MS`) — measured at **4001ms** in the running app, driving the real dialog. For those four seconds a browser tab opens behind the window and nothing on screen moves: the progress panel cannot exist yet, because there is no session to render. `CliLoginController.starting` fills exactly that window, set SYNCHRONOUSLY before the await (anything derived after it lands inside the gap it exists to cover) and cleared in a `finally`, so a REFUSED start does not leave a spinner over a sign-in that never began. Both buttons read it — the account card's (`agent-config-list`, `signingIn: CliKind | null`) and the MCP row's (`mcp-section`, `signingIn: string | null`) — and both go `disabled` as well as spinning, which is not cosmetic: a second press opens a second browser challenge and invalidates the first, the same reason the account card withholds its button entirely once the panel owns the flow. The flag is the CALLER's on both, because the controller is: one sign-in runs at a time across the screen, so a copy kept per section would let two of them each believe they own it.

**And the listing is re-read on focus-return while a server sign-in is in flight** (`Chats.tsx`). The settle stays the primary mechanism, but the daemon calls a sign-in settled when the CLI PROCESS EXITS — so a CLI that lingers after the browser round-trip leaves the row stale for as long as it lingers, which is the other half of the same report ("the status updated only after 30 seconds, probably"; detection itself was measured at ~1.3s, so it was never the probe). Focus-return is when the answer may have changed, since leaving for a browser tab and coming back is the shape of the flow — the same backstop Settings already runs for the ACCOUNT probe. Bounded to a sign-in actually being in flight rather than armed on every focus: re-dialling a folder's servers launches each one and is measured in seconds.

**Signing in never opens a terminal, on any surface.** `use-cli-login.ts` is the one controller — start, poll, submit a pasted code, cancel — over the daemon's `/v1/auth/login` (the account) and `/v1/auth/mcp-login` (one server), and `components/cli-login-progress.tsx` is the one panel that renders it. Three call sites now share both: the Settings account card, the Agents panel's MCP dialog, and the transcript's own failure row. That last one was REPORTED as *"after click on sign in - it will open terminal. and after redirect and auth nothing will happens"* — it was the last caller still resolving the invocation and handing it to a shell, which put the only surface that knows how a sign-in is going outside the app entirely: nothing here was watching that window, so a finished browser round-trip changed nothing on screen and the failed turn sat looking exactly as it had.

Two things about `Chats` in particular. It holds ONE controller instance for both of its flows, for the reason the hook holds a single sign-in at all — two browser challenges open at once are indistinguishable in the browser, and the second reads as the first having failed — so `onSettled` is handed the sign-in that settled and dispatches on `server` (a server's outcome is re-read from the LISTING, an account's from the CLI's own status; neither from an exit code). And the two panels render in different places for the same reason: the MCP one belongs in the dialog it was pressed in, while the account one is pinned above the composer rather than drawn on the error row that started it — that row is somewhere in a scrollback the user is free to leave, and claude's flow asks for a pasted code, which is unusable off-screen.

**An agent-specific setting lives in that agent's CARD**, never in a page section of its own (`AgentConfigListProps.agentSettings`). REPORTED as "все специфические, именно к агентам специфичные настройки должны быть там": cursor's Max Mode and claude's browser tools each had a heading further down Settings, so what a reader could change about cursor was half in the card named cursor and half two screens below, under a heading that named a topic instead. A card now reads top-to-bottom as which binary → how it behaves → whose account. The nodes are passed IN rather than built by the list, which is the rule the daemon's adapters follow as well — that component knows how to draw a card, not what is true of claude — and it is what keeps ONBOARDING, which shares the list, free of settings that belong to a running app: it passes none. The cost is that every such setting sits behind a disclosure now, which is why the Settings spec opens a card before looking for one.

**Cursor Max Mode** — the switch behind `Settings.cursorMaxMode`, defaulting ON, drawn in the cursor-agent card. It rides chat create and workflow-run start beside `customInstructions` and is SNAPSHOTTED onto the run, so it applies to the next chat and an open conversation never changes window mid-thread. Its whole reason for being a switch is billing: Cursor charges Max Mode at the model's API rate plus 20% on legacy request-based plans, and nothing here can read which plan a user is on. The default is ON because the defect that produced the feature was a window too SMALL — `kimi-k3` running at 200k in geniro against cursor's own 1M. `false` is sent EXPLICITLY rather than omitted (`currentRunSettings` in `chats/Chats.tsx`): the daemon reads an absent field as the adapter's own default, so a decline and a silence must not look alike. See `apps/daemon/CLAUDE.md` for the measurements behind the flag itself.

**Appearance** — one `Select` in General, offering System plus a row per theme, built from `shared/themes.ts` so a theme added there appears with no edit to this screen. A pick does two things and they are not the same write: `persist({ theme })`, after which MAIN re-applies `nativeTheme.themeSource` and the renderer's media query repaints on its own; and `setThemePreference`, which is what makes the change immediate for a theme whose name the media query cannot report (it can only answer light-or-dark). **Custom instructions** — the Settings section holding the user's standing instructions to every agent (`Settings.customInstructions`, an `ExpandableTextarea` since it is a prompt-length field). Saving goes through `use-debounced-persist.ts`, which is where the debounce, the latest-value ref, the unmount flush and the dirty guard now live once rather than per field: an UNSAVABLE value (over the ceiling, or carrying control characters `settingsPatchSchema` refuses) is held on screen and never written, and the timer handle is NULLED rather than merely cleared — without that, a legal edit followed by an unsavable one still flushed the unsavable text on unmount. The section also PREVIEWS geniro's own host preamble, read from `GET /v1/capabilities` (`hostPreamble`) rather than restated here, and renders nothing at all until that read lands: an empty box captioned "geniro already tells every agent this" would state that the app sends nothing, which is the opposite of true. See the root `CLAUDE.md` → *Agent instructions* for what the preamble claims and why it must contradict the CLI's own prompt by name.

**macOS packaging (M4)**: `pnpm --filter @geniro/ui build:mac` runs `scripts/build-mac.mjs` — two self-contained `pnpm deploy --prod --legacy` stagings (shell app + daemon under `Resources/daemon`), Electron-ABI rebuild of better-sqlite3 in the daemon staging, `.icns` generated from `resources/icon.png`, signing (below), no `publish` feed; the Homebrew cask + install script strip the quarantine bit so the un-notarized app launches, DMG + zip into `release/dist/`. The packaged app presents as **"Geniro"** on every macOS surface (menu bar, Dock, About, Finder) via electron-builder `productName`.

**The build is signed so that macOS can tell one release from the next.** Every privacy grant is recorded against the app's DESIGNATED REQUIREMENT — the signature's answer to "which code is this app" — and re-asked the moment a running build stops satisfying the requirement its grant was recorded under. An ad-hoc signature has no certificate to name, so its requirement is `cdhash H"…"`, the hash of its own bytes; measured on the shipped 1.46.2 bundle, and confirmed against the predicate macOS evaluates by cross-checking two builds of one probe app (`codesign --verify -R "=<v1's requirement>" v2.app` → failed). That is the whole of the reported "every reinstall asks for all the permissions again", and it applied to the self-update as much as to a reinstall. `scripts/make-signing-identity.mjs` creates the one **self-signed** certificate every release is signed with (free — no Apple account; the users' Macs never see it, since the requirement is evaluated against the certificate embedded IN the app), and `GENIRO_SIGN_IDENTITY` names it to `build-mac.mjs`. Three things hang together there and are one branch for that reason (`.claude/rules/packaging-config.md`): the identity, `forceCodeSigning` — without which electron-builder answers a missing identity with a WARNING and an unsigned artifact, the one failure that packages and installs perfectly and silently resets every user's permissions — and a read-back of the packaged bundle's own requirement, asserted against the arm that was taken. Still **not notarized**: a self-signed certificate is not a Developer ID, so Gatekeeper's verdict is unchanged and the quarantine stripping stays. A local build with no `GENIRO_SIGN_IDENTITY` is ad-hoc as before, and says so.

**A grant made BEFORE that change is dead, and it does not look dead — it looks granted.** TCC stores the requirement alongside the decision, so a row recorded against an ad-hoc build keeps its `cdhash` forever while every signed build since fails it. The row stays in System Settings under the app's name with its switch ON, and access is refused anyway; Screen Recording in particular never re-prompts for allow/deny, so the app only ever gets the "grant access in Privacy & Security settings" dialog, pointing at the switch that is already on. REPORTED as exactly that dead end, and it is invisible from inside the app — Electron's `systemPreferences.getMediaAccessStatus('screen')` says `denied`, which is true and says nothing about why. The one place the answer exists is `tccd`'s own log, captured while reproducing the refusal (`/usr/bin/log stream --level debug --process tccd`, then trigger it — note `log` is a zsh BUILTIN, so the absolute path is required):

```
Failed to match existing code requirement for subject io.geniro.desktop and service kTCCServiceScreenCapture
For io.geniro.desktop: matches platform requirements: No
Service kTCCServiceScreenCapture does not allow prompting; returning denied.
```

The fix is one-time and belongs on the machine, not in this repo: `tccutil reset <Service> io.geniro.desktop` drops the stale row so the next request records a fresh requirement — which now names the certificate and therefore survives every later release. Confirmed by re-running the probe after the reset: the `Failed to match` line is gone and tccd writes a fresh record for the current binary.

**It is per-SERVICE, so finding the rest means provoking each one.** A stale row is only discovered when something asks, and the ask is what puts the line in the log — there is no way to enumerate them (the user TCC.db refuses to open even to a process running as its owner). Measured on the reporter's machine, one probe per service from a shell inside the app's process tree: `kTCCServiceScreenCapture` and `kTCCServiceAccessibility` were both stale, `SystemPolicyDocumentsFolder` and `SystemPolicyDownloadsFolder` came back `Allowed (User Consent)` with their requirements matching, and `SystemPolicyAllFiles` was plainly never granted (`Denied (Service Policy)`). So it is not "everything from before the change is dead" — only the rows old enough to predate it. The Accessibility one had already been written down as an environment fact ("osascript has no assistive access here") in a memory note, which is what a stale grant looks like from the outside: a capability that is simply, permanently missing. Two things about re-granting it afterwards: the app has to be RELAUNCHED before a running process sees the new decision, and the requester is usually not this app at all — a CLI agent running `screencapture` is attributed to whatever is responsible for its process tree, which is Geniro. The app's own code touches no screen-capture API.

**App updates** — the app notices a new release, says so, and applies it on one click.

**electron-updater is not used here — a signing fact that has since become a choice.** Its macOS path is Squirrel.Mac, which validates a downloaded bundle against the RUNNING app's designated requirement; while the build was ad-hoc that requirement was a `cdhash` no later build could ever match, so the door was shut. The release certificate (see *macOS packaging* above) reopened it — the requirement now names the certificate and holds across releases — and the door stays shut anyway, because what was built in its place already verifies its own downloads and handles what Squirrel does not know about here (a translocated or read-only install is answered with `brew upgrade`, not a button that fails at the last step). What replaces it is `scripts/install.sh`'s own sequence moved in-process — resolve the release, download the `-mac.zip`, verify it against the published `SHA256SUMS.txt`, `ditto` it into place, strip quarantine, relaunch — split across three files by what each can be tested without: `updater.ts` is the feed alone (no filesystem), `update-installer.ts` is the swap alone (no policy), `update-service.ts` is the policy alone (every dependency injected, so its specs need neither network nor bundle).

Twelve rules the code exists to hold:

- **An automatic check is SILENT unless something changed.** REPORTED as the app appearing to re-render itself every so often, and it was the only event on that cadence — the debug log for the session held no daemon restart and no second `renderer-loaded`, so the window was not reloading. What it was: a scheduled check pushed `checking` and then its outcome at every window, and the renderer's subscriber (`useUpdateState`) sits in `App`, at the root — so the entire tree, transcript included, re-rendered twice every five minutes to display nothing. `checking` draws nothing at all (`footerUpdate` maps it to `{kind:'none'}`), and the outcome on an up-to-date app is the sentence already on screen. Two halves: `check({ announce: false })` for the scheduled callers, since there is no press to acknowledge — a check the USER pressed still announces, because the Settings button reads "Checking…" and disables itself off that phase — and `emit` compares the merged state against the previous one and broadcasts only on a real difference, because the patch is a fresh object every time and `setState` on a new identity re-renders whether or not the value differs.

- **Every deletion runs with `process.noAsar` raised — under Electron, `fs.rm({recursive})` does not delete an `app.asar`, it walks INTO it and never returns.** MEASURED on electron 42.5.1 against node 24.14.0, one 111KB archive: node stats it as a file and finishes in **1ms**; electron stats it as a DIRECTORY and is **still running at 30s**. Electron's `asar-fs-wrapper` is why — it patches `lstat`/`readdir`/`internalModuleStat` so a path inside an archive resolves (which is what makes `require('…/app.asar/main.js')` work), and `fs.rm` believes the directory answer, descending into tens of thousands of virtual entries it then retries unlinking. It does not fail; it does not finish. REPORTED as an update that installs endlessly with a loader that never ends: the bundle swap had already SUCCEEDED and the app on disk was the new version, but `installUpdate`'s `finally` cleanup never returned, so the install never resolved, the phase never left `installing`, and the log carried `update-install-started` with no matching `update-installed`. The same call in the launch sweep is why a user's `Geniro.app.old-*` sat eroded to exactly its two `.asar` files with the RUNNING app still holding fds on them. `withoutAsar` wraps every `rm` in this file and REFCOUNTS, because `process.noAsar` is one global flag and the sweep deletes concurrently — a naive set-and-restore lets the first tree to finish re-enable asar under the ones still being walked. Verified end-to-end on the real 118MB archive under electron: **45,002ms and still running** before, **2ms** after. Nothing in the UI suite can see this — it runs under node, where both arms are the 1ms row — so the spec pins the FLAG, which behaves identically in both runtimes.
- **`ready` is an ENDING that a check may not undo.** The version this service compares against is the RUNNING app's, and a bundle swap does not change it — the relaunch does. So every automatic check after a finished install re-discovered the release already sitting on disk and put the app back to `available`: the Restart button became an Update button, pressing it downloaded and swapped in the identical release, and the cycle repeated every five minutes until the user restarted by hand. `check()` returns early on `ready` without even asking the feed — there is nothing an answer could change while a bundle is already staged, and a newer release is picked up by the first check after the restart.

- **A release is not a release until its macOS archive is attached — and the check reads the release LIST, so that one release which is not can never be the whole answer.** Both halves address the same measured window, from opposite ends. The workflow publishes the release ~14 seconds into a run whose macOS build takes another ~3–4 minutes, so for those minutes `/releases/latest` answered with a release carrying no assets at all, and an app polling every 5 minutes reliably looked inside it: REPORTED on v1.48.4 as `The update could not be installed. release v1.48.4 publishes no macOS archive`, in red, about a build that was still running. The workflow half is the root fix — `create-release` now cuts a **draft**, and `build-app` publishes it (`gh release edit --draft=false --latest`) as its LAST step, after the upload. A draft is invisible to `/releases/latest`, to the release list, to `scripts/install.sh` and to Homebrew, so the window closes for every consumer at once rather than each learning to survive it, and the two paths that used to publish a permanently broken release — a build job that errors, and a run cancelled by `cancel-in-progress` between the jobs — now leave a draft for a maintainer instead. The updater half is defence in depth, since a build CAN genuinely fail: `fetchLatestRelease` reads `/releases?per_page=10` and returns the newest release carrying an archive, filtering drafts and pre-releases itself (the filtering `/releases/latest` used to do) and ordering by parsed VERSION rather than by the feed's tag-date order, so it cannot disagree with `isNewerVersion` about which release is newer. One bad release is then answered by offering the newest good one; only a page with no installable release at all is an error the user is shown — and that error now NAMES the tag when there is one, because "no release carries an archive" and "1.5.0's archive is still uploading" send a reader to different places.

  **Offering the newest good one is not the same as being up to date, and saying so was the third face of this bug.** With the newest tag unarchived, the newest INSTALLABLE release is an older one — often the running build itself — so `!isNewerVersion(release.version, current)` held and the app answered `up-to-date` while a newer version sat on the releases page: REPORTED as "terminal not saying truth — there is a new version". `fetchLatestRelease` therefore answers BOTH questions off the one page — `release`, the newest it can install, and `published`, the newest tag at all (`readPublishedVersion`, split out of `readRelease` so the two stay separable; drafts and pre-releases are excluded from both, or a nightly would leave every stable install permanently "behind"). The phase stays `up-to-date` — nothing is downloadable, and a phase that offers an Update button would put a control on screen with nothing behind it — and carries a MESSAGE naming the pending version, which Settings already renders after the status line. Verified against the live feed on 2026-08-21: ten releases, every one archived, newest published `1.48.5` = newest installable, so the healthy case adds no message (its own test pins that an EQUAL tag stays silent).
- **A release with no `SHA256SUMS.txt` is REFUSED, never warned about.** The build is signed but not notarized, so Gatekeeper validates nothing it will act on and the running app validates nothing about its replacement, so the published digest is the only link between the release that was built and the code about to execute as the user. `install.sh` degrades to TLS-only with a warning because a human is watching it; nobody is watching this. The release workflow therefore publishes that file as a first-class artifact — a build job that stops emitting it silently disables updating rather than weakening it.
- **The old bundle is moved aside, never deleted first.** The rename is the commit point; a failed copy renames it back, so an update that dies mid-`ditto` costs a message rather than the user's installed app. The backup is removed last and only on success.
- **`canInstall` is asked of the filesystem, per use.** An app installed by another account, on a read-only volume, or running TRANSLOCATED (macOS's read-only synthetic mount for a quarantined copy — where a "successful" update writes to a volume that vanishes at quit) gets the `brew upgrade --cask geniro` sentence instead of a button that would fail at the last step. It is still TOLD, in the window: `footerUpdate` returns a `readout` for that case and the rail draws it as a non-pressable glyph carrying the sentence on hover, because the alternative — drawing nothing — left that user's only channel behind a nav click into Settings.
- **Main owns the state; the renderer reports presses.** One `UpdateState` is pushed at every window, so the nav rail's version row (`renderer/updates/update-status.ts` → `footerUpdate`, read by `App`) and the Settings section are two renderings of one download rather than two pollers free to disagree — the same split as notifications. There is no DISMISSAL: the offer lives in the status row now, at the size of the row, so there is nothing to wave away and nothing interrupting a view to be waved away from.
- **A phase that stops moving becomes an `error`, and abandoning it means CANCELLING it.** REPORTED: an install sat on one non-terminal phase and never left it — and because main owns the state, reloading the renderer only re-read the same wedged value, so the only recourse was quitting the app, which nothing tells the user. Every RECOGNISED failure already landed in `error`; what was missing was a bound on the ones nobody recognised. Each non-terminal phase now carries a deadline (`checking` 60s, `installing` 10min, both flat totals since neither reports progress; `downloading` a 3-minute STALL budget re-armed by every progress callback, so a slow 150MB transfer takes as long as it takes while one that never starts still gives up). The re-arm reads the RAW callback, never the published `progress` — a server that declares no content-length leaves `fraction` null for the whole transfer. Two things happen when one trips, and the second is the one that is easy to miss: an `attempt` counter is bumped, so the hung call cannot write `ready` over the failure the user has already been shown, AND an `AbortController` is fired, so the abandoned work really stops. Ignoring it is not enough — the user can retry the moment the app frees up, and an abandoned attempt still inside `swapBundle` would be a second `ditto` writing one bundle. `install()` therefore accepts `error` as well as `available` when a release is held: the rail's Retry control IS that call, and a guard accepting `available` alone made the button do nothing but restate its own refusal.
- **The debris sweep is at LAUNCH, precisely because the install's own cleanup is allowed to fail.** REPORTED: ~224MB of dead trees — two scratch directories under `updates/` and two `Geniro.app.old-*` backups beside the app — from updates that had SUCCEEDED days earlier, each eroded down to the `Contents/Resources` the removal had not finished emptying — which the asar rule above later explained: the removal deleted every ordinary file and then disappeared into the archive. Neither is a missing step (`installUpdate` discards its scratch in a `finally`, `swapBundle` its backup on the way out); both are deliberately best-effort, since a cleanup that throws once reported a completed update as a failed one, and a freshly-written bundle is exactly what macOS holds open behind them. So the guarantee cannot live inside the install at all. `sweepUpdateDebris` runs from `main()`, ungated by the auto-check setting (a user who switched checks off still has the leftovers), matching only the two names this code writes — `update-*` under the work dir, `<the app's own name>.old-*` beside the bundle, which `Geniro.app` itself cannot match.
- **A failure names the phase that FAILED, and one surface composes the sentence.** `error` is an ending, so it erases what died: every failure read "The update could not be installed.", which was REPORTED against a DOWNLOAD that never moved a byte — an app that had installed nothing being told the install had failed, and the log for those two days holds 32 failed CHECKS reported the same way. `UpdateState.failedPhase` carries it, DERIVED inside `emit` from the phase the service was in rather than passed by each of the five error sites, and the lead reads "The update check failed." / "The download failed." / "The update could not be installed." accordingly. The other half of the same report was the JOIN: `${line} ${message}` produced "The update could not be installed. the update made no progress for 3 minutes", a lowercase fragment after a full stop — and it was written out twice, in the rail's hover title and in the Settings line, so neither was fixable alone. `updateStatusText` is now the one composition. It joins an error with a COLON, because main writes those messages as fragments meant to follow a lead while every other phase's is a whole sentence; capitalizing the fragment instead was tried and produced "Ipc broke" out of a real error string, since these carry acronyms, shell commands and absolute paths.
- **Main's update failures go to the daemon's log, never to stdout.** A packaged Finder launch discards main's stdout, so when the wedge above was investigated there was no record of it anywhere on the machine — the gap was itself part of the bug. `UpdateService` takes an injected `UpdateLog` (wired in `index.ts` to `reportMainLog`, which buffers until the daemon exists) and writes the check failure, the install start, the install failure, every watchdog trip and the launch sweep into the same `ui` channel as the renderer's own errors, where the debug panel shows them and the user can paste them into a report.

Nothing installs unasked: the check is automatic (launch + every 5min, gated on the `checkForUpdates` setting, which re-arms the schedule the moment it is flipped rather than at the next launch), the download is not. The Homebrew cask carries `auto_updates true` so `brew upgrade` stops reinstalling over an app that has already updated itself.

**System notifications** — a macOS banner when an agent stops to ask something and when a thread's turn ends, so a run parked on a question does not sit unanswered while the user is in another app. **One module, split across the two processes by what each can answer**: `renderer/notifications/` decides WHEN (`run-notifications.ts` — pure rules over the DISPLAY statuses the sidebar badges show, never the daemon's row, so a banner and the row it sends you to cannot describe one run differently; `use-run-notifications.ts` — the thin React binding, mounted from `Chats`, which the shell keeps mounted across nav switches so a thread finishing while the user is in Settings still reports), and `main/notifications/` decides WHETHER and does the posting. Whether it becomes a banner is read from `notificationsEnabled` at the moment of the post rather than cached in the renderer, so a flipped switch takes effect on the very next question; keeping the gate in the one process that can post one makes that true by construction. Three rules the diff enforces, each a defect if dropped: a run **seen for the first time never notifies** (the chat list loads with every past thread already finished — otherwise the app opens with a banner per conversation in the history), a turn the user **cancelled** is not announced (telling somebody what they just did with Stop is the notification everyone switches the feature off over — `failed` IS announced, since nobody asked for it), and the chat the user is **already looking at** is skipped, but only while the window has focus (suppression is about watching, not about which chat is open — without both halves a user who leaves the app sitting on a running chat is told nothing at all). Clicking a banner raises the window in main — a renderer in a hidden window cannot show itself — and sends the run back over `onNotificationActivated`, which `App` reads for the view and `Chats` for the thread. `notifier.ts` is the only file that touches a notification API, and Electron's own `Notification` IS the ready-made library here: an npm package (`node-notifier`) posts through a bundled `terminal-notifier.app`, so the banner is attributed to that helper rather than to Geniro (and the per-app switch in System Settings then names the helper), it ships a nested Mach-O binary into an app that is signed with no Developer ID and no notarization, and its click cannot reach into this process to raise the window. **Measured 2026-08-15**: `Notification.isSupported()` is true and the service posts/suppresses correctly, but no banner renders on a Mac while the display is being shared or recorded — `dndMirrored: true` in `com.apple.ncprefs` suppresses every app's, which an `osascript display notification` control probe confirms is not specific to this code.

**The ARCHIVE is the sidebar's other axis, and it replaced Delete as the row action** (`chats/chat-scope-filter.tsx` over the shared `components/ui/menu.tsx`; `chatScope` / `showScope` / `addRun` / `placeRun` / `dropRun` in `use-chat-run.ts`). A thread is SHELVED rather than destroyed: an icon in the sidebar header's control row picks how much of the archive the list covers (`GET /v1/chats?scope=`), and the one-way delete lives in the archive alone — a live chat row offers Archive, an archived row offers Unarchive and Delete permanently. **Workflow rows archive too**, and their Delete moved behind the archive with the chats'. They were excluded for a release — the handler withheld, the listing skipped under `Archived only` — on the reading that a workflow run had no archive; that left a finished run with destroying it as the only way off the desk, REPORTED against a completed `Dev Team Manifest` row. Both halves of the listing now take the same scope (`workflowApi.listWorkflowRuns({ scope })`), since a scope is a question about how much of the shelf to show and never about the run kind. The Delete moving is the same rule one step on: it was on the desk only because that row had no shelf to put a one-way door behind, and leaving it there once it had one would mean the gesture that destroys a run's history stayed one hover-click away on exactly one kind of row. What stays per-kind is the dialog's WORDS (`archiveDialogCopy`): a workflow run is stopped as a RUN — every agent still working in it — where a chat's cancel is one turn.

**Three scopes, not two, and an ICON rather than a band.** The first cut was a two-option segmented control in a row of its own under the heading, and both halves came back: "у нас не должно быть этого элемента интерфейса… всегда там должна быть отдельная маленькая иконка, там же, где сверху другие три иконки для фильтрации. Там есть «Показывать все» и «Показывать только архив»". The shape complaint is the general rule now recorded in `.claude/rules/renderer-components.md` — a labelled run of options is a band of chrome, which a page's own subject switch earns and a list filter in a 260px column does not. The count is the sharper half: a BOOLEAN can only ever name two of the three answers, and the one it cannot name is `Show all` — the reading a user takes when they want a shelved thread found IN PLACE, beside the live ones, rather than on a shelf of its own. That is also the original ask ("фильтр, чтобы показывать архивированные треды тоже") read literally. `active` is the default and the only scope that hides anything, which is what makes archiving worth doing.

Four things about it are load-bearing, and the first two are the disjoint-listing rule and its LIMIT. `refreshRuns` carries a GENERATION and drops a resolved fetch that is no longer the current one: the active fetch runs the pull-request capture pass over every run, so it is routinely still in flight when the user reaches the archive, and landing it there would fill the archive with rows that do not belong. `addRun` leaves the shelf instead of prepending, since a new run is never archived — but only from `archived`, because `all` holds it perfectly well. **And `placeRun` is where the rule stops**: archive and unarchive both re-file a row rather than dropping it, keeping it where the current scope still holds it, because under `Show all` a thread that vanishes on being archived breaks the one promise that scope makes. `dropRun` survives for the permanent delete alone — a run that no longer exists. The same limit reaches the ROW's own actions, which are read off `run.archivedAt` and never off the scope: under `Show all` both kinds are listed together, so a view-wide flag would offer Unarchive on a live thread and Archive on a shelved one in the same list.

Two consequences of the third scope worth stating. A scope switch **keeps the open thread** when the new scope still lists it — closing unconditionally was right while the filter had two disjoint sides, and under `Show all` it would shut a conversation to show a list that still contains it; a thread the new scope does NOT hold is still closed, because it would otherwise render on with its row absent from `runs`, taking the header (title, status, Stop) with it and leaving the archived-composer gate reading `undefined` on a composer the daemon then refuses. And the rows on screen are **no longer blanked** during a switch: that was right while a row's actions came from the view, and what it cost is not a flicker — the active listing's first capture sweep is seconds, and an empty sidebar under "Loading chats…" for that long is the worse of the two.

The fourth is that **an archived chat is inert**. The daemon refuses `POST :runId/messages` with `RUN_ARCHIVED`, so the composer of an open archived thread is disabled with a placeholder saying so, and the shelf above it carries the one control that can undo that. It is read off the ROW (`activeRun.archivedAt`) rather than off the scope — the question is about this conversation, not this view — which is also the renderer consumer that keeps the wire field honest. Archiving a RUNNING chat asks first, because that is the one irreversible thing archiving does: it cancels the turn. A settled chat is filed away in a single press.

**Sidebar groups** (`chats/run-group.ts`, `chats/group-header.tsx`, and the `run_groups` rows behind them) — the folders a user files their threads into, with a colour, a fold, an order, a live "is anything in here working" reading, and an optional rule that files new chats by the folder they start in.

**A WORKFLOW claim outranks every folder claim** (`RunGroupsService.resolveAutoGroupId`, whose own doc block says so). A group may name a workflow by slug (`autoWorkflowId`) as well as a folder, and a run of that workflow is filed there before any folder rule is consulted — because a workflow run's `cwd` is whatever one of its nodes happened to name, so the folder says nothing about what the run IS. Everything below is the folder half, which decides among folder claims once no workflow has claimed the run.

**The auto-file rule matches a folder AND everything inside it, most specific first.** A user who points a group at a project means the project — its `apps/`, its `packages/` — so exact-match-only would silently never fire for the very chats the rule was made for. When two groups both claim a run the longer `autoCwd` wins, which is the only reading under which a group on `~/work` and one on `~/work/app` can usefully coexist; sidebar order breaks a genuine tie, so the answer is deterministic. Containment is SEGMENT-wise (`utils/path-within.ts`) — a plain `startsWith` files every chat opened in `/work/app-old` into the group that claimed `/work/app`. Both sides are canonicalized at the moment they are CHOSEN (`autoCwd` when it is set, `cwd` when the chat is created), so no read path touches the filesystem, and a rule pointing at a folder that does not exist is refused rather than stored: a rule that can never fire is indistinguishable from a feature that does not work. Adding a rule deliberately does NOT sweep up the chats that already exist in that directory — it says where the next one lands, and retroactively moving conversations the user filed by hand would undo their own arrangement without asking.

**Deleting a group releases its chats**; it never takes them with it. The release runs BEFORE the row is dropped, since the reverse order leaves a window in which a run points at a group that no longer exists and a crash inside it makes that permanent. It is the one destructive-looking action in the app that is deliberately NOT behind a confirm dialog — nothing is destroyed — and the menu row says so at the moment the user is deciding (`Delete group · keeps chats`).

**Everything moves by dragging, and the DROP ZONE is the whole section.** A header dragged over another group REORDERS, and the list rearranges under the cursor rather than jumping when the button comes up — the daemon is told once, at `dragend`, because the intermediate arrangements are not decisions. A chat dragged into a section FILES ITSELF there — the only way, since the row's "move to group" menu is gone: filing is one gesture where the menu was a click, a read and a second click. The section — header, rail, rows and the space between them — is one `li` carrying the `dragover`/`drop` pair, because hanging the target off the header alone left the BODY of an expanded group inert: a chat dragged into it lit nothing up and landed nowhere, which is most of what the eye actually aims at. `dragover` bubbles, so one handler covers every child and the rows need none of their own; an empty group has no rows to aim at and is dropped onto through the same section. One piece of drag state carries the KIND for exactly that reason: the same header is a drop target for both gestures and they do different things, which cannot be told apart by guessing from an id. A drop that changes nothing writes nothing. Neither a group nor a chat is draggable while its name is being edited — a text field inside a draggable element cannot be selected with the mouse, because the drag starts instead. The row menus stay (they are the keyboard path, and the only one that can reach `New group…`).

**A group header reads its state from the BADGES its rows are showing, never from the daemon's `status` column** (`runGroupSummary` over `sidebarRunStatus`). The column and the badge disagree in exactly the cases that matter — a live turn under a stale `completed`, a run parked on a question — so a header computed from the row would contradict its own children. `needsInput` is reported ALONGSIDE `busy` rather than folded into it, because a collapsed group would otherwise hide the one state that cannot advance without the user, which is the failure this whole feature would introduce if a header only ever said "something is running".

**A group's chats are enclosed** — indented, hung off a rail in the group's own colour (`GROUP_RAIL_CLASS`) — because without it an expanded group ran straight into the next and the list read as flat. The section's bottom padding is PERMANENT rather than part of the drop highlight: it is what keeps the rail from running flush into the edge below it, and adding it only while a drag hovers would shift every row down at the moment the user is aiming at one. The highlight itself is `muted` and a hairline — `accent` is the palette's warm caramel and read as a coloured state rather than as a destination, and a 2px ring on a block this size in a 260px sidebar reads as an error. An EMPTY group draws no rail (the container exists to enclose rows, and with none it rendered as a 4px orphan tick); its header is the drop target either way. The count sits against the name it counts rather than being pushed to the far right by `flex-1`, where it read as an unrelated second column. Colours are NAMES on the wire and tokens in the renderer (`--group-*`, aliases of the avatar hues so a group dot and an agent avatar cannot drift into two different blues) — a hex could not legally be used at the call site, since the renderer's eslint config makes a colour literal an error.

**A group's options are a PANEL, not a row list** (`Popover`, `anchor="viewport"`). The auto-file rule was a menu row whose label was the folder path and whose action was "open the picker" — so choosing the same folder again looked like nothing happening, and nothing anywhere said what the rule DID. It is now a stated section: a caption in words, the path as a label, and the two things that can be done to it as two small buttons that say which is which (choose another, remove). `anchor="viewport"` measures the trigger and places the panel `fixed`, which is the only way out of the chat list's scroll container — the earlier fix capped the panel's WIDTH to fit inside that clip instead, at 257px in a 235px slot. The colour rows stay a `Menu` on the DOT, because fourteen rows in one panel scrolled its last four — the delete among them — out of sight.

**Deleting a group asks first**, in a dialog that leads with what is NOT deleted ("Its 2 chats are kept — they move to Ungrouped with all their history"). Nothing is destroyed, so the confirm is not there to prevent loss; it is there because *delete* is a word a user reads as final, and a menu row's hint is not where that difference can be stated.

`DaemonSupervisor.start()` reuses a still-healthy daemon left by a prior UI instance (pid + `/health/check` + identity + bundled `version` + the pidfile's `entry` stamp), sweeps stale pidfiles, and only tears down the process it owns. **The `entry` stamp is what makes "is this the current build" answerable at all**: `version` is the package version and is identical across every rebuild, so before it a rebuilt daemon was adopted over and the app went on serving the previous compile — measured as a `pnpm dev` daemon four days old with a whole module missing, which is how instrumentation written to diagnose a bug came never to run. A daemon started from the SAME entry path whose mtime/size have moved is a rebuild and is replaced; one from a DIFFERENT path (`pnpm daemon:dev` on TypeScript source) is a different thing and is left alone; one reporting NO stamp predates the check and is replaced. The other half of that fix is in `turbo.json`, where the `dev` task carries `dependsOn: ["^build"]` — `dist/main.js` is produced by `pnpm build` alone and never by `electron-vite dev`, so without it launching the app ran whatever compile happened to be on disk, and the `@geniro/daemon` dependency in `apps/ui/package.json` (which imports nothing) exists solely to give turbo that ordering edge. **That edge only exists when the launch goes THROUGH turbo**, which is why the root `dev` script is `turbo run dev --filter=@geniro/ui` and must never be "simplified" back to `pnpm --filter @geniro/ui dev`: pnpm runs `electron-vite dev` directly, turbo never enters the picture, and every word above about the ordering silently stops being true. It was `pnpm --filter` for months, and the symptom is exactly the one the `entry` stamp was written to catch and cannot — the stamp only decides whether to REPLACE a running daemon, and a `dist/` nobody rebuilt is stale before any daemon starts — which is why it also passes `GENIRO_IDLE_EXIT_MS` to every daemon it spawns: a daemon it does NOT own (left by a force-quit or a crash) is one it can never stop, so the daemon has to be able to stop itself. The macOS counterpart is on the UI side: `window-all-closed` does not quit on darwin, so a closed window can outlive its daemon's idle window — `app.on('activate')` therefore re-ensures the daemon (`ensureDaemon()`, the one path both launch and reactivation take) before the reopened window can talk to a handle that no longer answers.
