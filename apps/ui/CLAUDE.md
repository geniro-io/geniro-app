### Main process

`src/main/` — `index.ts` (app lifecycle), `daemon-supervisor.ts` (spawn/adopt/health-poll/orphan-sweep), `daemon-pidfile.ts` (reads + validates the daemon's pidfile), `settings.ts` (`settings.json`), `purge-legacy-secret.ts` (deletes the one Keychain entry earlier versions wrote — see *Storage split* in the root `CLAUDE.md`), `cli-detect.ts` (per-CLI binary + version, plus whether the CLI reports itself signed in, for a CLI that can be asked — `loggedIn` is three-state, and `null` means UNKNOWN rather than signed-out, because a failed probe must not tell a signed-in user to sign in; the answer is read from the CLI's own STRUCTURED reply (`cursor-agent status --format json` → `isAuthenticated`), because its human output has a third `partially-authenticated` state that matched neither wording and read as ready), `probe-env.ts` (the main-side twin of the daemon's `child-env.ts`: a probe child gets its OWN agent's credentials and never the other's — `detectClis` runs an authenticated `status` call, so it must not hold a rival agent's token; `neutralEnv()` beside it applies the same rule to a child that is not one of the agents at all — `gh` makes an authenticated call to GitHub and owns nothing on the list, so it keeps nothing), `git-info.ts` (the composer's branch chip: repo/branch/branches/dirty, plus a branch switch GUARDED by a re-read dirty check — and `git switch`, never `git checkout`, which would resolve a branch name as a pathspec and restore a file instead; plus `pullBranch`, the "bring this branch up to date and keep my changes" the refusal now offers: stash → `git pull --ff-only` → stash pop. `--ff-only` because a fast-forward is the only pull that cannot leave a repository in a state the user then has to resolve — no merge commit they did not ask for, no half-finished rebase — and what to do about a divergence is not a decision a button in a chat composer gets to take. The stash goes back on EVERY path INCLUDING a failed pull: hiding the user's work and then failing before restoring it looks exactly like the edits were destroyed. Whether the tip is THIS pull's entry is decided by `pullStashIsOurs` — the stash ref having MOVED *and* the tip's subject ending with `geniro: pull`. Neither alone: git's own prose is locale-dependent, a push on a tree that is not really dirty exits 0 having created nothing (reachable, since a failed `git status` reads as dirty) so a leftover entry still carries the message, and a concurrent `git stash` moves the ref. A failed push aborts the pull rather than running it unprotected. `BranchSwitchResult.dirty` is what tells the renderer the refusal is the guard working rather than a failure — it drives the amber tone and the Pull offer. `BranchSwitchResult.worktree` is the second such field, and it OUTRANKS the dirty guard: git will not check one branch out into two worktrees, so committing or pulling cannot help and the Pull offer would be a control with no way to work. It is decided from `git worktree list --porcelain` (also read into `GitInfo.worktrees`, which is what marks those rows in the picker) rather than from git's own `fatal: '<branch>' is already used by worktree at …`, which is translated prose — the same rule `pullStashIsOurs` follows. The renderer answers it with the one thing that CAN work: an offer to point the run at the worktree that already holds the branch. Not on the saved-configuration path, which names a folder of its own — there the sentence states the path and stops), `github-prs.ts` (the **pull requests** the chat surfaces name — `gh pr list` in the run's folder, parsed into `PullRequestsResult`. Its own file rather than more of `git-info.ts`: that one reads local refs on a 5s budget, this one is a network client on a 15s one. ONE query per folder, head-filtered: `--state all --head <branch>`. A thread is one folder on one branch and every surface is scoped to that, so the repo's other branches are never fetched — asking for the repo's `--state open` and `--state closed` lists was the first shape and was rejected in use ("i need to show prs only related to current thread"): three round trips to collect fifty rows that were then filtered down to one and, because a `--limit` has to be applied somewhere, needing this same head query underneath them anyway so the branch's own pull request survived the truncation. `--state all` because a branch's HISTORY is the point — the merged pull request under the open one that replaced it, which is the ticket's own "merged PRs should be collapsed"; each row carries its own state, which is what separates them again on screen. A detached HEAD spawns NOTHING, the branch being the query's own argument. The folder's `origin` OWNER rides along (`readOriginOwner`, parsed from the remote URL and never asked of `gh`, which answers for the BASE repo — on a fork clone with an `upstream` remote that is the upstream owner, the opposite of what is needed); the fork MATCH itself stays in the renderer, because `--head` matches a branch NAME and a stranger's fork branch is routinely called `main`. It FAILS CLOSED: every failure — no `gh`, a logged-out `gh`, a folder that is not a GitHub checkout, the query erroring — is ONE outcome, the empty list, and every surface then draws nothing rather than an error strip about a CLI the user may have no intention of installing. There is deliberately no "did it work" flag on the wire, and the reason is written at the guard in `github-prs.ts`: a half-answer reads as confident and wrong rather than as partial), `resolve-binary.ts` (the PATH ∪ well-known-dirs lookup `cli-detect.ts` used to keep to itself, extracted when `github-prs.ts` needed it: a packaged app launched from Finder runs under launchd's `/usr/bin:/bin:/usr/sbin:/sbin`, where `git` resolves and a Homebrew `gh` does not — so a bare-name spawn works in `pnpm dev` and is ENOENT in every shipped build, silently, because a swallowed spawn error is indistinguishable from "no pull requests"), `ipc.ts`, `ipc-schemas.ts` (the zod shapes every IPC argument is validated against before main acts on it — the renderer is the untrusted side of that boundary), `context-menu.ts` (the right-click menu, which Electron does NOT provide: a packaged app has none at all unless it builds one, so every right-click did nothing anywhere until this existed), `navigation-policy.ts` (keeps the top frame on the renderer document — `URL.origin` cannot decide it in a packaged build, where every `file:` URL has the opaque origin `null`), `native-appearance.ts` (tells macOS the app is light, because its CSS already is — see the traffic-light paragraph below), `open-terminal.ts` (the handoff OUT of geniro: a 0700 `.command` script and `open`, so LaunchServices routes it to whatever terminal the user actually set), `reveal-path.ts` (shows the daemon's log in Finder — it REVEALS rather than opens, so a path it is talked into taking cannot become a program that runs), `daemon-ready-notify.ts` (pushes the freshly started daemon's handle to the renderer, tolerating a window destroyed between the daemon becoming healthy and the send), `window-diagnostics.ts` (what the MAIN process saw happen to a window, written into the daemon's log — the `ui` channel carries only what the RENDERER catches, so a window that never ran the renderer could report nothing at all), `app-menu.ts` (the macOS menu bar: Electron's own default, restated through role menus, with **Toggle Developer Tools** hidden — reported out of the menu bar, and hidden rather than deleted so ⌥⌘I stays bound; verified against the RUNNING app by dumping `Menu.getApplicationMenu()` over `electron --inspect`, which is also the only way to read that menu at all, and one row of geniro's own: **Clear Agent Cache**, beside the two Reloads because it is the same act one layer down — Reload drops what the WINDOW holds, this drops what the DAEMON holds about the CLIs. ASKED FOR as "на мыши нужно сделать сброс кэша… как дополнительную функцию". It carries no accelerator (every other row here has the platform's own, and an invented chord for a maintenance action is one pressed by accident) and it does the work in the RENDERER, over `IPC.onClearAgentCaches` to the FOCUSED window: the renderer is what holds the daemon client. **It clears and then RELOADS**, which is the renderer's whole half of the press — `useAgentVocabulary` caches per hook INSTANCE (the composer holds three, the graph inspector three more, a component not yet mounted none), so there is no one cache to empty and a reload drops all of them with the rest of the window. The reload also REPLACED a confirmation strip this first shipped with, on the report "нам не нужно вот это добавлять… просто должен перезагружать": a reload is its own confirmation, and it costs the composer's unsent text, which is the trade the row is understood to make. A first attempt at the same problem — a `vocabulary-epoch` number folded into the cache key — is gone with the strip: a reload makes it dead code. ORDER is load-bearing and so is the failure arm: the reload happens only AFTER the daemon has answered (reloading first refills from a daemon that has not cleared yet) and never on a failure (a reload after one hides it behind a window that looks like it worked), which instead goes to the daemon's log where every other renderer failure goes. Verified by clicking the real macOS menu row through System Events — the daemon logged `cleared 2 cached CLI answer(s) on request`), `updates` (**app self-update** — `updater.ts` reads the GitHub Releases feed, `update-installer.ts` downloads/verifies/swaps the bundle, `update-service.ts` owns the one state and the schedule; see *App updates* below), `login-shell-path.ts` (packaged Finder launches inherit launchd's minimal PATH — resolve the login-shell PATH for the daemon), `notifications/` (**system notifications** — `notifier.ts`, the ONE file that touches a notification API, and `notifications.service.ts` over it).

`src/shared/contracts.ts` holds the Electron-internal contracts only — IPC/Settings/CLI + `DaemonHandle` — shared across main/preload/renderer; it deliberately holds **no daemon wire types** (those are generated, see *The daemon API client* in the root `CLAUDE.md`). `src/preload/index.ts` exposes a typed `window.geniro` via `contextBridge`.

### Renderer shell

`src/renderer/` — React app: `App.tsx`, `onboarding/`, then the feature directories below (`chats/`, `graphs/`, `stats/`, `settings/`), plus `autogenerated/`, `daemon-api.ts` and `daemon-client.ts` (see *Settings* below for those). `stats/` is what the app has SPENT — totals, a per-day series and per-agent/model/project breakdowns over the daemon's usage ledger, drawn with **recharts** under `stats/charts/`, whose `chart-theme.tsx` is the one place the series colours and axis styling are read off the design tokens. (This line used to claim token-driven `components/ui/{bar,donut}-chart.tsx` primitives "rather than a charting dependency" — neither file exists and recharts is a direct dependency.)

**The periods, and what a ONE-DAY range costs.** `Today` leads them (`use-stats.ts` `STATS_PERIODS`) — reported as "we need to add today", and the narrowest window before it was a week, in which today is one column of seven and the headline figure is six other days. `days: 1` is a calendar day and not a rolling 24 hours: the lower bound stays a local midnight, so the period does not slide backwards into yesterday as the afternoon wears on. It made two existing holes routine, both of which a fresh install's first day could already reach on ANY period (the daemon clamps a range to what its ledger holds). A line and an area are drawn BETWEEN points, so a single day rendered as bare axes — read as "no data" about a day that may well have cost money — hence `loneDot`, a marker offered only at exactly one point and never as a general option, since at 30 points the same markers are a beaded string over the curve whose shape is the thing being read. And the span under the title dashed a date to itself. Fixing that surfaced a genuine timezone bug in the line it replaced: the header read the UTC day out of the ISO bounds (`iso.slice(0, 10)`) while every bucket on the page is a LOCAL one (`usage-fold.ts` `localDateKey`). One bug with two faces — east of Greenwich a local midnight is the previous UTC day (measured at UTC+5: "August 20 – August 21" over a chart holding one column, Aug 21), west of it a local evening is the next one, and since `to` is always *now* every period opened after ~16:00 local claimed to run a day past its last column. `dayRangeTitle` reads local days for both ends; the suite's pinned `America/Los_Angeles` can only tell the second face apart, which is what its test asserts.

**One line under a control, not a paragraph about it.** Reported against Settings as "we have too much text here - let's remove most": every section carried two or three muted paragraphs and the screen read as documentation with switches in it — measured at 302 words across 9 notes, over a 1210px page. Now 147 words across 5, and the whole tail from Notifications to Diagnostics fits one screen. The rule the cut followed, worth keeping for the next section anyone adds: a note says **what flipping this does and the one consequence you could not guess** — the cost (`22 extra tools in every prompt, paid for on each`), the restart, the security caveat (`while the port is open any process on this machine can run code inside it`). What went was rationale ("so a run parked on a question does not sit unanswered while you are in another app"), mechanism nobody acts on (the update's checksum verification), enumerations the label already implies (listing the browser tools under "Let claude drive your browser"), and anything a neighbouring element already says — Diagnostics' "On by default in development and off in the installed app" was sitting next to a badge reading `default for the installed app`. The cut also stranded `Remove from existing chats` on a row of its own, since it had been pushed right by `ml-auto` against a paragraph that no longer existed; it now shares the note's row, and the two `ErrorText` states moved to their own full-width line, which is where a sentence like "Contains invisible control characters — not saved…" needs to be anyway.

**A full-screen view scrolls its PANE; the centred reading column is what the pane scrolls** — two elements, never one. Reported as "scroll should be for all page, not just in the middle", against `Settings` (and, unreported but identical, `Onboarding`), where a single `<div>` was both the `mx-auto max-w-2xl` column and the `overflow-y-auto` container: the scrollbar was therefore drawn at the COLUMN's right edge, floating inside the pane with dead page background either side of it. Measured in a 1200px window, its right edge sat at x=1025 — 175px short of the window edge every other scrollbar on the machine lives at. `Stats` was already built the right way, so this is the house pattern rather than a new one. The outer pane also carries `scrollbar-gutter: stable`: the reporter runs macOS with "always show scrollbars", which is why the bar is visible in the screenshot at all, and without the gutter a real 15px bar shifts the centred column sideways by half its width the moment content grows past one screen. On `Onboarding` the inner column additionally keeps `min-h-full`, because its footer is `mt-auto` and would otherwise ride up under the last card once both CLIs are already installed. The pins are STRUCTURAL — jsdom computes no layout, so the scrollbar's position is unobservable there, but "which element scrolls, and is it the one that caps the width" is the DOM fact that decides that position and the one that regressed. None of this touches `7569b86`'s `html, body, #root { overflow: clip }`: the window still does not scroll, and the report was never asking it to.

**The page reads top-down as headline → figures → charts → breakdowns.** Reported as "and move those to the top": the eight `StatCard`s were the LAST section, three sections and a scroll below the `HeroStat` whose own token count they split, so "what did this cost" was answered in two places with a page between them. They now sit directly under it, and the section order is otherwise unchanged. The grid went `2 → lg:4`, from `2 / lg:3 / xl:6`, for two reasons that both belong to being at the top: eight cards over six columns is a row of six above a row of two with four empty cells trailing — survivable at the foot of a page, broken at the head of one — and three columns is the same ragged tail one breakpoint down, so 2 and 4 are the only counts that divide eight. Four only from `lg` because the widest thing these cards hold is a duration: measured at 900px, `Agent time` truncated to `15h 4…`, which on a page whose whole job is reporting figures is the one thing a cell must not do. The spec pins the order off DOCUMENT POSITION rather than a class name — jsdom computes no layout, so where a card lands is unobservable there, while which of two nodes comes first is exactly what grid order is made of.

**The window draws its own title bar** — ONE band across the whole window (`components/title-bar.tsx`), above the columns. `titleBarStyle: 'hiddenInset'` + `trafficLightPosition` in `main/index.ts` remove the system's strip while KEEPING the window buttons, so the app owes the OS no controls of its own; `frame: false` would take the buttons with it. The strip held the word "Geniro" and nothing else directly above a row of ours that already named the open chat. It was then rebuilt a SECOND time: the title bar had been three rows, one per column (the rail's top row, the chat list's header, the transcript's), all `h-11` and so aligned — but two vertical column borders ran straight through the band, so what the eye read was three column headings rather than a title bar ("это криво… у нас этот header всё ещё должен выглядеть как header", against Cursor's). Being ABOVE the columns is the fix: their borders start under it, so nothing crosses the band. **What is in it is decided by what each thing is ABOUT.** The band carries the window's own business — a title centred over the CONTENT pane (the open thread's name, reported up by `Chats` via `onTitleChange`, since the bar spans the window and the name has to travel up from the view that knows it), and on the right the daemon status + version and the update control (`components/update-control.tsx`). It carried a THIRD control, the debug-log trigger, and that one was reported and removed: an unlabelled `>_` opening a developer panel, sitting in the one band every user sees beside a health readout and an update offer. ⌥⌘L is now the only way in (`App.tsx`), which is the point — the drawer is a developer's answer to "what just happened", and Settings' Diagnostics section names the chord so it stays findable where somebody would look. The rail keeps what is about the rail: the app mark and the width toggle, on its own top row. Both of those went up and came straight back — the toggle acts on that column rather than on the window ("давай её в само меню оставим там же, где она и была"), and the mark belongs to the app. The rail's FOOTER is gone with the status: collapsed, it had shrunk to one green pip alone under a rule ("вот эта точка выглядит одна-одиноко"), so the rail is navigation and nothing else now. Only the collapsed STATE is the shell's (`components/use-sidebar-collapsed.ts`) — the button and the column it resizes are two components, and two `useState`s over one setting would be two answers to one question.

Three obligations come with the space. **Room**: the buttons' footprint is MEASURED, not assumed — `TRAFFIC_LIGHT_INSET` / `TRAFFIC_LIGHT_WIDTH` / `TRAFFIC_LIGHT_GAP` / `TITLEBAR_CONTENT_INSET` in `src/shared/contracts.ts`, the one module main and the renderer share, because main POSITIONS the buttons and the renderer RESERVES room for them and a copy on each side drifts in silence. It was a hand-written 52px (12px buttons 20px apart, right for years of macOS); on macOS 26 they are 13.5px and 23px apart — a 59.5px group — so every reservation was ~8px short and the green button was drawn over the column beside the rail. Clearing them by arithmetic ALONE is still not enough ("очень мало отступа между иконкой и кнопками"), hence the explicit gap. Re-measure before editing those numbers: open a `hiddenInset` window at a known position, `screencapture -R` its bounds and find the coloured discs. `trafficLightPosition`'s `y` and the bar's `h-11` are one piece of arithmetic ((44 − 13.5) / 2 ≈ 15) and move together. **Alignment**: the title is centred on the WINDOW, and nothing between the bar's edges may displace that centre — a flex `gap` on the row shifts every child after it by its own width (measured 8px out when the bar carried one), which is why spacing belongs to the children and a spec pins the absence. Two other arrangements were tried and reverted, both reported: a visible divider on the boundary between the leading columns and the content pane ("давай всё-таки вот эту линию из хедра вообще уберём" — a rule through the band puts back exactly the break that splitting it into three column headings had caused), and centring the title over the CONTENT pane by adding the column widths into a `leadingWidth` prop. That second one is right until a column opens on the OTHER side: with the agents panel out, the midpoint of everything right of the chat list sits well right of the transcript and the title drifts with it (measured 1322px into a 2000px window — "он не посередине"). Bounding both sides would mean the panel reporting its width up on every frame of a resize drag. **A drag handle**: with the system strip gone a window with no `-webkit-app-region: drag` anywhere CANNOT BE MOVED ("я перетаскивать за него вообще не могу окно"), so `.app-drag` / `.app-no-drag` in `styles/global.css` mark it — and the title bar is the shell's ONLY drag region. The column headers gave theirs up with the restructure: dragging the transcript's chip row moved the window, which is surprising once a real title bar exists. **A control inside a drag region is INERT** (the compositor takes the press and the click never reaches React), so anything interactive in the bar carries `.app-no-drag`. `components/window-drag-strip.tsx` still covers the two screens that render before the shell exists — Onboarding and the loading state.

**And the appearance has to be DECLARED** (`main/native-appearance.ts`, called first inside `whenReady`). Keeping the buttons means the OS keeps drawing them, and it draws them for whatever appearance the machine is set to — while `styles/global.css` ships one light-only palette and never said so. On a Mac in Dark mode that showed up in the one place nobody can miss: macOS tints an INACTIVE traffic light for the appearance — near-white under Dark, grey under Light — so an unfocused window painted three white discs onto the title bar's own `#fdfcfa` and the buttons vanished ("когда у меня окно не в фокусе, я вообще в принципе не вижу трех кнопочек… они должны быть серенькими, точно так же, как на других приложениях мака"). Measured on macOS 26: fill `#ffffff` on `#fdfcfa`, a 1.02:1 ratio, against `#dad9d7` once `nativeTheme.themeSource = 'light'`. The band's own colour is NOT the lever, and probing settled it — three `hiddenInset` windows over the same near-white ground, with and without `trafficLightPosition`, all vanished under Dark and all came back under `'light'`; recolouring would have bought back three buttons and left every other unpainted native surface (the context menu, scrollbars, system dialogs) dark against a light app. `'light'` rather than `'system'` for exactly as long as the palette is light-only — a dark theme is what changes that line, not a preference.

### Chats

`chats/` incl. `approval-card`; the composer's `/` skill autocomplete (`skill-menu`) and its chip row.

The chip row: `folder-select` and `config-dir-select` — both built on `directory-select`, the ONE directory chip (recents + the current value + a native-picker row), which is also what keeps them from drifting apart; the config one adds a "Default profile" row, since the CLI's own is its normal state, and renders NOTHING for a CLI whose `GET /v1/capabilities` `configDirs[]` row names a reason — never a disabled chip, the same rule the effort chip follows. In an OPEN thread it is stated once, in the header beside the agent (`chat-header`), because it is the same kind of fact — fixed for the run's life, and about what the conversation IS rather than where the next message goes; a run on the default profile shows no chip at all. `branch-select` — git branches, only for a repo; it exports TWO chips, `BranchSelect` which SWITCHES the checkout and `BranchValueSelect` which merely RECORDS a name for a saved run configuration (and so carries a "whatever is checked out" sentinel row the live one must never have). `target-select` — which CLI or `wf:<slug>` a run points at, shared by the composer and the configuration editor, and the one place the "an agent this machine cannot run is shown-and-disabled, never hidden, and the current target is never refused" rule lives. `context-window-select` — which of the model's context-window sizes a turn runs at, offered wherever the effort chip is (the composer, an open thread's header row, a saved run configuration, a graph node's inspector) because that is what was asked for: "я должен быть способен его выбрать везде, то есть во всех предустановленных template, когда я начинаю чат в крафт билдере и везде". Its rows are the CLI's own words fetched per (CLI, MODEL) through `use-agent-context-windows` — never a table here, and per model because twelve of a cursor account's thirty-four models carry the axis with three different vocabularies between them. With no model chosen there is nothing to list and the chip says so, which is the one way it differs from the effort chip: that one falls back to the CLI-wide union, and a union of window sizes would mean nothing. Choosing a MODEL clears the window everywhere it is stored — the composer's patch, the configuration editor, the node inspector — since a size belongs to the model that offered it and `1m` on a model without the axis is refused per turn, for months, in a workflow. **In the COMPOSER the model and everything it can be run with are ONE control** (`chats/model-settings-select.tsx`) — a chip naming the model, opening a panel whose labelled blocks are Effort, Context window, one per model parameter, and Model last. It replaced a row of separate chips that was correct and then grew: on `claude-opus-5` through cursor it was five pickers wide, REPORTED as "сейчас очень много опций… в курсоре фактически не на каждую опцию отдельный select, а поповер, когда мы выбираем модель, уже там все эти опции". The second half of that report is the other half of the fix — inside one panel each block carries a label, so a setting says what it is in words instead of through an icon the composer row had no room to explain. **It is TWO LEVELS**, and that is the second round of the same report: the first attempt put every axis's values in one flat panel, which on `claude-opus-5` was five blocks of values followed by thirty-four model rows, and came back as "сейчас у нас один огромный большой список. У нас должно быть двух-уровневое меню" with a screenshot of Cursor's own picker. So the first level is one compact row per AXIS — its name, where it currently stands, and a chevron — and the second is that axis's values. Stating the current value on the row is what makes a level worth more than a heading: five settings readable at a glance where five chips could only be read one hover at a time. Model is the last row and the only one whose second level carries a search field (thirty-four rows is where typing beats scrolling; five is not, and a filter over the first level would hide the axes it exists to show). It is a `Select`, not a bespoke popover, which is what keeps the search box, the keyboard highlight, the clipping escape and the placement the primitive's; it needed exactly two things from `menu.tsx` — `MenuItem.checked`, because a menu holding several independent choices cannot mark them from a single `value`, and `MenuItem.submenu` with the `side="right"` placement that goes with it. The child panel is rendered INSIDE the parent's DOM on purpose: the outside-click guard asks `panel.contains(target)`, so a click two levels down must be a descendant or choosing a value would close the menu under itself — `position: fixed` still escapes the parent's scroller, so being a descendant costs no clipping. It is a READOUT while the list is still loading, kept from the model chip it replaced. **And the AXES have their own waiting state**, which is a second and separate thing: an axis with nothing in it is dropped, so a listing that has not arrived yet was drawn exactly like a model that offers nothing — and the wait is not a frame, since each of the three listings is answered by a real `cursor-agent acp` handshake. Reported as "я выбрал GPT 5.5… и он мне вообще не пишет никаких дополнительных параметров к этой модели, хотя должен": measured against a cold dev daemon, one cold model costs 6.1–6.8s and all three listings together 6.2s wall (so the single-flight in `ModelVocabularyCache` is working), against 0.0s warm — after which Effort, Context window and Fast appear together. So the three vocabulary hooks now surface `useAgentVocabulary`'s `loading` alongside the listing, `Chats.tsx` ORs them into one `settingsLoading`, and the panel shows one disabled "Reading what this model offers…" row where the axes will land. ONE row rather than a skeleton per axis because WHICH axes exist is itself the answer being waited for. The four single-axis chips it composes over (`model-select`, `effort-select`, `context-window-select`, `model-parameter-select`) still serve the two surfaces that are NOT a chip row — the run-configuration editor's label column and the graph node inspector, whose free-text model entry (`allowCustom`) this composite deliberately does not carry.

**A picker with nothing to pick is not drawn — none of the three, and that is the settled answer after two rounds of arguing about how to draw it instead.** The effort chip carried an inert `no effort control` word and the context chip a live picker whose menu held one `model default` row; both were attempts to keep an absence visible, on the reasoning that a control which vanishes is indistinguishable from a broken one. That reasoning came from a report about an axis that SHOULD have existed and did not (cursor's effort, before the ACP handshake declared its parameterized model picker), and the fix for that was making the axis reachable. **The THREAD's PULL REQUESTS, in three places, off ONE read per checkout** (`chats/use-pull-requests.ts` — the cache; `chats/pull-request.ts` — the folds; `chats/pull-request-row.tsx` — the rows). Scope is the thread throughout — `threadPullRequests` is the ONE filter every surface goes through (branch match, plus the fork check below), and the repo-wide panel this first shipped with was rejected in use: on a busy repo it put fifty of other people's pull requests under a thread whose subject is one branch. Three things re-read it: the first paint, window focus (bounded to the folders on screen, with an in-flight guard AND a five-minute per-folder freshness floor — the started-set only grows, and alt-tabbing is this app's normal rhythm, so without both an ordinary session spends a burst of authenticated GitHub traffic every few seconds), and an explicit `refresh(dir)` after an in-app branch move, which focus cannot see because the window never lost it and which deliberately ignores the floor, being asked for precisely because something changed. Chips are right under a message box, where they read as a sentence about the next turn; here seven of them wrapped onto a second line whose contents moved as the target changed, so the same setting sat somewhere different each time the dialog opened. A fixed label column gives every setting one address and nothing can wrap, because the control's cell truncates instead.

Three rules the code holds, each a defect if dropped. **Applying returns to the new-chat view first** (`newChat()`): it is what the feature promises, and it is the only view that renders both the seeded chips and the error strip the branch refusal reports through — the picker is reachable from the sidebar with a thread open, where the notice would otherwise go nowhere. **A workflow configuration must NOT write the per-CLI choices** (`AppliedRunConfig.isWorkflow`): `applyRunConfig` reports `agentKind: 'claude'` for a `wf:` target because a workflow has no CLI of its own, and the composer's model/effort setters PERSIST — so writing their nulls through deletes the user's remembered claude model, which the configuration never spoke about. **The branch is re-read after the switch** (`useGitInfo().refresh`): the hook's own read fires only when the FOLDER changes, so a configuration naming the folder already selected would leave the chip — and any configuration later saved from it — on the pre-switch branch. The editor composes the composer's own chips rather than new pickers, and asks its vocabulary about the CONFIGURATION's agent, never the composer's — the same rule, and the same past bug, as `session-picker`'s config directory.
**A question card's options are drawn from their ARITY, not from a single option style** (`components/ui/option-list.tsx`, driven by `approval-card`'s `optionArity`). Reported as "more beautiful, more compact — and for cases where we can select few options design should be different": every option was an outline `Button`, so a pick-one and a pick-many card were pixel-identical and the only thing separating them was a grey line of prose above them, which is precisely the sentence nobody reads before clicking. Three arities now, and each is drawn as the thing it is — `many` a checklist (square boxes, **stacked in a column**, because a checklist is read down its boxes and a wrapping flow puts every box at a different x), `one` a radio row (round dots, flowing, so six short options take one line), and `none` — the answer-on-click card, one question taking one pick, where the press IS the submission — **no indicator at all**, since an empty box there promises a staging step that does not exist and sends the user looking for the button that confirms it. That third case gets the warning the other two do not need: the verdict is one-shot, so a mis-click cannot be taken back. The unchecked box is `border-muted-foreground/50` and NOT `border-input`, which is tuned to recede against page cream and at 16px simply vanished. They stay toggle `<button>`s rather than `role="radio"`/`role="checkbox"` — an ARIA radio group promises arrow-key navigation and a single tab stop, and a half-built one is worse for a keyboard user than an honest list of buttons — so the arity reaches a screen reader through the group's own accessible name instead of through a shape it cannot see. Not built on `chip`, which is `whitespace-nowrap` by design: an option label is routinely a full sentence, and the reported card's were.

`use-chat-run.ts` — the run and websocket lifecycle, extracted out of `Chats.tsx`: the run list, which thread is open, the live-text plane, and every `DaemonClient` subscription (`onItem` / `onLiveText` / `onRunStatus` / `onDisconnect` / `onReconnect` / `onVerdictAck`) with the reconnect replay that follows them. **The `joinRun`/`leaveRun` pair lives here in full**, both halves — the activation swap AND the leave on run switch or delete — because ownership split across two files is how one of them comes to be missed. It is also what made the streaming plane testable without mounting the screen: `use-chat-run.spec.tsx` drives it through a probe component against a fake client, where before, every assertion about it had to go through a 9,000-line `Chats.spec.tsx`.

**The status vocabulary, in one table.** ASKED FOR as "давай мы как-то стандартизируем статусы… распиши мне вообще табличку статусов вот этих. Как это вообще работает? Что за кондишены такие?". `RunStatusKind` (`chats/run-status.tsx`) is the ONE vocabulary every surface draws in — the sidebar row, the chat header, the agents panel's cards and thread rows, and every transcript block — and `RUN_STATUS_META` is the one glyph/tone/word for each of its members:

| kind | word on screen | glyph | what produced it |
| --- | --- | --- | --- |
| `pending` | pending | clock | the daemon's own column: the run exists, its first turn has not started |
| `running` | running | spinner | the agent is working — a live turn, or a delegate still producing rows, or the row says so |
| `held` | working | hourglass, **not** spinning | the daemon raised `turn_held`: the agent has said its piece and the process is alive only until the SUB-AGENTS it launched report back (`holdingFor > 0`) |
| `needs-input` | needs more info | question mark, warning-toned | an approval or question card is open (`run.awaiting`) — the one state that cannot advance without a human |
| `completed` | completed | check | the daemon's terminal status |
| `failed` | failed | ✗ | the daemon's terminal status |
| `cancelled` | cancelled | ⊘ | Stop, or a run that ended before the work finished |
| `skipped` | skipped | ⊖ | a workflow NODE only: something upstream of it failed |

The daemon persists only five of these (`RUN_STATUSES` in `runs.types.ts`, plus `skipped` for a node). `held` and `needs-input` are DERIVED here and never stored, which is why no run row ever carries them.

**There were NINE, and the ninth was a duplicate.** Asked to re-check whether every status is needed and behaves, one did not survive: `idle` meant "has not started yet", which is what `pending` already means and what the node's own `node_state` row literally says while it holds. `displayStatus` answered `idle` for a node with no activity and `pending` the moment any status item existed — one unchanged node, two words, decided by a row nobody had looked at. It is gone, and `displayStatus` answers `pending` on both arms. Every other member earns its place: each is reachable, and no two describe one fact. `held` was DRIVEN in the dev app to confirm it, not read off the code — a delegate launched with `run_in_background` and the turn ended on the spot: the header, the sidebar row and the agent card all read `⌛ working · waiting on 1 sub-agent` together.

`displayRunStatus` decides between them in a fixed order, first match wins: **(1)** a card is open → `needs-input`; **(2)** the row says `failed`/`cancelled` → that, never overridden; **(3)** the run is held → `held`; **(4)** a delegate is still producing rows → `running`; **(5)** a live turn is streaming → `running`; **(6)** otherwise the row. `isWorkingRunStatus` is `running || held` and `isSettledRunStatus` is the four terminal ones — `pending`, `needs-input` and `held` are all states a run has yet to leave.

Two corrections the table exists to make, both measured rather than reasoned. **A detached shell does not hold a turn.** The guess in the report was that the hourglass means "some long-running terminal is open"; it is the reverse — only a `background_work` unit of kind `agent` keeps a turn open (`spawn-cli.ts`'s `trackBackgroundWork`, and claude distinguishes `task_type: local_agent` from the `local_bash` a delegate then runs). Driven live in the dev app: a backgrounded `sleep 180` settled its turn at `completed · worked 5.1s` with the command still listed and running. **And an agent's own work IS `running`** — ranks 4 and 5 above. The hourglass appears only after the agent has stopped speaking, and its word is already `working` rather than `waiting`; it deliberately does not spin, because that state routinely lasts twenty minutes.

**One state, one word — a block's lifecycle is translated, never printed.** `BlockStatus` (`block-shell.tsx`) is the transcript fold's own model (`running`/`done`/`error`/`stopped`) and used to reach the screen verbatim, so a delegate cut off by Stop wore a red `error` pill three lines under a header, a sidebar row and an agent card all reading `cancelled` — one event spelled two ways on one screen, which is the whole of the standardization report. `RUN_STATUS_OF` already translated it for the GLYPH; it now translates the WORD too, in both places one is written: the pill (`failed`, `cancelled`) and the `sr-only` span that carries the status for a screen reader when the mark is a glyph (`completed`). The kind was also renamed `waiting` → `held`, since that one word had been doing three jobs — this key, the sentence under a `needs-input` badge (`waiting for your answer`), and the sign-in flow's own `CliLoginStatus`.

`settled-status.ts` — the ONE reading of "which run status does this terminal item imply", and the rule that goes with it: **only a LIVE terminal item mirrors its status onto the run row**, while a REPLAY takes one reading from its LAST item (`reconcileFromTail`). Every chat past its first turn replays a `turn_complete`, so mirroring each replayed row wrote a past turn's ending onto a run that was working — measured on the real app as a chat reading `running · Working… 3m 39s` and then, after switching to another chat and back, `completed` with no live row, while the daemon still said `running`. The wrong value outlived the visit, which is the second half: the next activation read the row as settled and left `streaming` false, taking the transcript's live row with it. The two live rows' clocks follow the same principle — both count from a timestamp derived from durable rows (`ChatHeader`'s `turnStartedAt`, the working row's `workingSince` from the last row its own thread put on screen, the thinking row's daemon-published `thinkingSince`), never from their own mount, or every remount restarts them.

**A null activity means "working, nothing named" — and BOTH surfaces have to read it that way** (`run-status.tsx` `STANDING_ACTIVITY`). REPORTED as the status on a thread blinking: "справа от него то появляется, то исчезает… там всегда должен быть последний его статус". The daemon announces `running Bash` on a tool call and null on its result, and says at its own `idleActivity` that "null leaves the run's own Working… standing" — which was true of ONE of the two consumers. The transcript's live row carried that fallback; the sidebar row was gated on the phrase EXISTING and drew nothing, so it erased the phrase every time a tool returned. Measured on a real four-tool turn: 132 sampled frames in the standing state against 2 naming a tool, so the row was blank for essentially the whole turn and flashed a tool name for a moment — which is what a blink looks like from the other side. The fix is the fallback, in ONE constant both read, because the defect was two renderings of one null disagreeing about what it meant and a second literal is how they would come to disagree again. It applies only while the badge says `running`: a settled row showing it would claim the run was still going, which is worse than the blink.

**`ThinkingRow` has TWO shapes, and which one it takes is a fact about the CLI, not a style choice** (`live-row.tsx`, fed by `LiveState.thinkingText`). Reported as a cursor chat sitting on `Working…` for three minutes with nothing happening — cursor streams its reasoning the whole time, and until the daemon gained a live channel for it (see `apps/daemon/CLAUDE.md`) none of it reached the screen. With TEXT the row is the same muted italic `reasoning` bubble the durable item becomes, so the words a user watches appear and the words that land are one thing rendered one way, plus a spinner-and-clock line the durable row does not need — without it a stretch that goes quiet is indistinguishable from one that finished. With NO text it stays the one-line note it has always been, `Thinking… 250 tokens`, which is all headless claude can offer since it redacts the block; the token count is never printed alongside the words, because the CLI that sends words reports no count and `0 tokens` is a figure nobody measured.

**A reasoning stretch is BOUNDED while it is written and FOLDED once it is not** (`chats/thinking-block.tsx` — `ThinkingScroller`, `ThinkingDisclosure`). REPORTED against a cursor turn as "вот этот thinking-блок очень большой… должно иметь какую-то максимальную высоту, например 300 px… и потом это должно быть collapsed, как только он закончил". Cursor streams its whole chain of thought, so the row grew to thousands of words in both states, and the two states need opposite answers. LIVE it is capped at 300px and scrolls inside itself, pinned to the newest words — a fixed box that did not follow would show the paragraph the agent wrote a minute ago, motionless under a spinner. The follow gives way to the reader on the transcript's own rule (`nextFollowState`), which is why "am I at the bottom" cannot decide it alone: content that grows pushes the bottom away without anybody touching it, and reading that as intent would switch the follow off during the very streaming it exists for. FINISHED, the words stop being something to watch and become something to be able to check, so the row folds behind its own first line — the only summary available here that says what the agent was thinking ABOUT, the durable payload carrying the text and nothing else. A SHORT stretch is left alone: folding two sentences into a preview plus a chevron hides nothing and charges a click. The fold is ONE component used by both durable renderings, which draw the body differently and always have (the standalone bubble prints it verbatim, a turn block prints it as markdown) — hence `children` rather than a `text` the component renders, so neither call site has to give up its own idiom to share the disclosure. Measured in the running app: the finished stretch 15px collapsed, the live box 300px with `scrollHeight 975 / scrollTop 675` — pinned to the end.

**A delegate is named by its identity when nothing named it, and its launching call's reply is not its report** (`transcript-groups.ts` — `subagentTitle`, `subagentNamed`, `SubagentBlockEntry.resultIsOwn`). Reported as "i see wrong agent names and popup", over a panel listing one `Review: optimizations` above seven identical `sub-agent` rows and a dialog headed `Sub-agent · sub-agent` whose entire body was `{"success":true,"message":"Resuming agent ad31fec"…}` beside `Working… 2m 29s`. Three separate defects behind it, each measured on the user's own `geniro.db` rather than reasoned about:

- **The generic title was a CONSTANT**, so every unnamed delegate was the same row and "which spinner is which piece of work" had no answer on screen. Only the launching call ever carries a description, so any delegate whose launch is outside the loaded window arrives with none — and the daemon's `subagent_info` cannot cover for it: all 76 declarations on that ledger carry `label: null, kind: null` and speak only about `backgroundOpen`. The fallback is now the id's own tail (`Sub-agent HvcbzU`), which distinguishes rows and is honest about being an identity rather than a name. `subagentNamed` exists so the dialog can drop its `Sub-agent · ` prefix where the title already opens with it — the stutter that was reported.
- **A launch acknowledgement was rendered as the delegate's result.** A backgrounded delegate's call is answered within the second and the work runs on; 23 of the 39 delegation calls on that ledger were answered with `Async agent launched successfully. (This tool result is internal metadata — never quote or paste any part of it, including the agentId below, into a user-facing reply.)`, printed under `RESULT FROM <name>`. `resultIsOwn` decides it STRUCTURALLY — did the delegate speak after its call was answered, and is its background unit still open — never by matching that sentence, which is one CLI's prose. The text is still shown, under `Reply to the launching call`: it is the user's own agent's tool result and the transcript shows those everywhere; what was wrong was the claim about whose answer it is.
- **A `SendMessage` is not a delegation.** The daemon announces background work against the call that opened a unit, and resuming an already-running agent opens one — so the fold adopted a message-send as a delegate launch, giving a block with no name, no prompt, no conversation and a routing receipt where its result should be. Exactly the phantom `spawn-cli.ts`'s own comment warns about. A launch admitted ONLY by that declaration, and whose declaration describes nothing, can no longer contribute a result: the two admission routes are not equally strong, and only the tool NAME (`AGENT_TOOLS`) or a declaration that actually briefs the delegate (cursor's ACP path, whose frame carries no usable name) is evidence that the call was a delegation at all.

Also fixed by the second point: `This sub-agent has not done anything yet.` was gated on `returned || result !== null`, both of which an acknowledgement sets — so the one line explaining an empty thread went missing on precisely the delegates whose thread is empty for that reason.

**A run settling is a MOMENT, not a flag** (`RunSettledContext` → `RunSettleAt`, read by `subagentBlockStatus`): a delegate that has produced rows SINCE the run row settled is still working, whatever that row says, so the settle only closes blocks whose last row precedes it. As a bare boolean it painted every unreturned delegate in the chat `stopped` at once, when a delegate could still be producing rows well after the run row had settled — the reported symptom being "I can see stopped status - but it's incorrect, in fact they continue working". Three states and not two, because a settle whose timestamp will not parse is not the same as no settle: `'unknown'` keeps the old conservative reading rather than silently putting every spinner back. The seq-based `SubagentBlockEntry.closed` is untouched and outranks it — a turn-end ITEM after the delegate's last row is direct evidence that nothing more is coming. A tool group asks only `!== null`, since a tool call is one round trip and "has it spoken since" is the question `pair.result` already answers.

The agent's own task list: `task-payload.ts` — the twin parser plus the FOLD, since a patch names only what moved; `task-list.tsx` — the `TaskListCard` the transcript shows where the list moved, and the shared `TaskRows` the SIDE PANEL composes for the current list (`agents-panel.tsx`, BELOW that agent's delegates and, like them, not behind a disclosure). The panel and not a strip over the composer, because the list is the same kind of per-agent state as the delegate rows beside it — a sub-agent likewise has a block in the flow AND a row in the panel. A delegate's list stays in its own block, whose collapsed header carries its count, since the block is closed by default. **Only the LATEST card of a thread shows its rows**: an agent that says one sentence between two announcements gets a card on each side of it, and both used to print the whole list — eight rows, then eight rows again with one more spinner, a paragraph apart (the reported "Todo is duplicating"). A superseded card folds to the line it already had, the count plus the task that was running then, which is the history the chronological placement is FOR without the repeated wall. The open state is DERIVED from `latest` with a manual override on top rather than seeded into `useState` — an initial value only applies at mount, so the card that was current when it appeared would stay expanded for good and the duplication returns on the next announcement. The header's own task readout says `done/total` through the same `TaskCount` (`chat-header.tsx`, `tasks` prop): a lone count of what is left cannot distinguish six-of-seven from six-of-sixty and only ever shrinks.

**In the PANEL the list is bounded and scrolls itself; in the transcript it is not** (`TaskScrollRows` vs `TaskRows`). Reported as "also we need scroll for tasks list" against a thirteen-task card, and the shape of it is that the list never overflowed anything: the panel has ONE scroller over every agent card, so a long list simply makes its own card that tall and pushes the next agent — and the artifacts under it — off the screen. Measured on the reporter's own CI243 thread, a SIX-task list: the agent card 439px → 326px, the task section 325px → 212px, and it now stays there whatever the length. The transcript keeps the unbounded rows on purpose — it is a document the reader scrolls, and a nested scroll box in it takes the wheel away from the page while the pointer is over the list. Two things make the bound safe rather than merely tidy. It FOLLOWS the running task (`revealWithinBox` in `scroll-to-bottom.ts`), or a list of thirteen with the sixth in progress would show the five that are done and hide the one thing happening — a worse answer than the tall card. And it moves only when that row has actually left the frame, so a reader who scrolled the box keeps their place. `scrollIntoView` is not an option for it, for the reason recorded beside `scrollToBottom`: it walks every scrollable ancestor, and this box sits inside the panel's scroller inside a shell whose window scroll was itself a shipped bug.

**An `in_progress` row only SPINS while something is working through that list** (`taskCardIsLive`): a turn that ended mid-task left a spinner running for good — the reported "finished one task, still in progress for some reason" — and every historical card animated its own in-progress task besides, so a three-step job showed three spinners for one running task. Two conditions, both needed: only a thread's LAST card can be live, and only while the run has not settled past it — read as a MOMENT, like `subagentBlockStatus`, so a card written after the settle (the CLI carrying on by itself) still spins.

**That moment is the run's own terminal ITEM, not merely its row's `updatedAt`** (`settled-status.ts` → `lastTerminalItemAt`, whose later-of-the-two both `runStoppedAt` and `activeRunSettledAt` now take): items never touch that column, so it is only as fresh as the last thing that DID write the row and can sit BEFORE the stop it describes — a task announcement can land inside that gap and read as work produced AFTER the settle, spinning on a run the user had just stopped. The same gap sat under every `subagentBlockStatus` reading. A stalled row keeps a glyph of its own rather than falling back to `pending`'s: the agent started that task and stopped there.

**What the agents are RUNNING on this machine** (`chats/shell-activity.ts` — the fold; `chats/shell-list.tsx` — the rows; a `Shells` section per agent card, above that card's task list). Every other coding CLI puts its live commands on its own screen, and this app had them nowhere: the only record of a shell in flight was the last tool row in the transcript, which says nothing about whether it has come back. The panel is where the ask put it, beside the delegates and the task list — per-agent state a reader opens this column to read.

Derived from the TRANSCRIPT, because a shell is only ever started by a tool call and only ever ended by one coming back — geniro spawns none of these itself, and the daemon declines ACP's `terminal/*` capability, so an ACP agent runs its own commands too and there is no process on this side to enumerate. A shell is an `execute` call by the one shared classifier (`tool-kind.ts`), so a CLI naming its shell tool anything at all is still recognised; a call that discloses no arguments — routine on cursor — is listed under its own title rather than dropped, since hiding it would answer "what is running" with silence on one of the two CLIs. Background commands are tracked through claude's own bookkeeping: `run_in_background` on the call, the `ID:` its launch replies with, then `BashOutput`'s `<status>`/`<exit_code>` and `KillShell`. A kill that FAILED is not a kill — the CLI answers a handle it cannot find with an error, and retiring the row off that reports a shell nothing stopped as stopped.

**A launch is recognised by the CLI's whole ANNOUNCEMENT, never by the characters `ID:`** (`shell-activity.ts` → `readLaunchHandle`). REPORTED as "я вижу, что thread completed, хотя на самом деле нет, и есть три терминала" beside "эти шелл команды вообще стейлд, то есть они на самом деле выполнились" — and the second report is the true one: the thread had finished and the panel was lying. The reader matched `\bID:\s*([^\s.]+)` anywhere in a tool reply, and a FOREGROUND command's reply is its own OUTPUT — so any command printing those two characters (a `git show` of Go source with a struct field, a JSON blob, a doc listing) was promoted to a detached shell, and a detached shell only ever ends on a probe, a kill or the daemon's `shell_info`, none of which is coming for a command that already exited. It was therefore listed as running for the life of the transcript, and counted in the header. Measured on the reporter's own `geniro.db`, run `d64593d0`: **11 phantoms out of 690 shells**, with handles `row`, `spec`, `resp`, `"foryou",`, the oldest running for a day and a half. The three real wordings are ONE ternary in the shipped 2.1.237 binary (a plain launch, one the user backgrounded, one that outran its timeout) and every arm ends `Output is being written to: <path>.`, so that whole shape is what is matched — which also fixes a quieter bug, the middle arm's `(ID: x)` having captured `x)` into the handle, where no later probe could match it. It is anchored at the START of the reply, a guard that earned itself within a day: a `sqlite3` query printing past launch replies and a `grep` over the CLI binary each produced a phantom in the session that wrote this, one carrying the literal handle `${e}`. And the reply now decides BOTH ways — a call that ASKED for the background and came back with plain output was never detached, so it closes instead of stranding a row with no handle to be matched by. The old doc justified the loose match by saying a miss is survivable; it is, and that is the argument for tightening: a miss costs one row that should have been listed, a false positive costs a row that can never be unlisted. What this does NOT fix is history — the daemon's shell-settle channel first wrote a row on 2026-08-24 21:46, and the 95 background commands launched before it have no ending in the transcript at all, so old conversations keep their stale rows.

**Only what is running — and how that is KNOWN differs by kind, which is the whole of the gate.** The finished ones are already in the transcript in full and in order, so repeating the last forty of them in a 280px column would bury the row this exists to show. A FOREGROUND command is read as running because its tool call has no reply, and that reading is only as good as the turn: a cancelled or abandoned one leaves a call that never comes back, and the row would stand for the rest of the session claiming a process that died with the turn. So those are gated on **`isSettledRunStatus`** — has this agent stopped for good. A DETACHED command is not read that way and is deliberately NOT gated: its call is answered within the second, its end is a durable `shell_info` row, and the daemon writes one for every shell still open when the CLI process dies — so its liveness is reported rather than inferred, and the run settling says nothing about it. Gating it too made the panel go blank on exactly the case it exists for, since a backgrounded command no longer holds the turn open (see `apps/daemon/CLAUDE.md`): the agent finishes, the turn settles `completed`, and the `pnpm dev` runs on with nothing on screen. The whole rule lives in ONE place (`Chats.tsx`'s `shellsByAgent`), because the header's counter is the same reading over the same map and two copies is how a `2` up there comes to sit over three cards below.

**A detached command's END is a row the DAEMON writes** (`shell_info`, read by `shell-activity.ts`; see `apps/daemon/CLAUDE.md` for the half that produces it). Its launching call is answered the moment the CLI accepts it, so the transcript otherwise holds a start and no end — which is what made the list ACCUMULATE: measured on a live 45-second `sleep`, the completion reached the model out of band and the conversation as a sentence the agent wrote, so every background command a session launched stayed listed until its turn ended. The reader matches by launching call, else by the CLI's own work id (the settle names the call on one of its two channels and not the other), and it only ever coarsens a shell still believed to be RUNNING — one a `BashOutput` probe already settled knows how it ended, with an exit code, and that is the better answer. `shell_info` is also skipped OUTRIGHT by `groupTranscript`: it renders as nothing, and the fall-through treats any other kind as the node having said something and closes its open tool group, so a burst of background commands would chop one turn's tools into a run of one-call rows for rows nobody can see.

**Clicking a row opens that command's own terminal** (`shell-output-dialog.tsx` over `GET /v1/chats/:runId/shell-output`). It is POLLED while the command runs and read once when it is finished — a bounded tail of one file, unlike the context breakdown next door, which is a multi-second round trip to the live CLI and so is fetched once per open. It follows the newest line unless the reader has scrolled up, says out loud when it is showing only the END of a longer output, and holds the command as a SNAPSHOT rather than following the live fold: a shell leaves the running list the moment it settles, so following it would close the dialog at exactly the moment the reader came to see how it ended.

**And it is drawn in the command's OWN colours** (`components/ui/ansi.ts` — the pure parser; `components/ui/ansi-text.tsx` — the one place a shell's escape sequences are rendered). Command output is not plain text: anything with `--color=always` or `FORCE_COLOR` emits SGR codes, and drawn verbatim the escape byte is INVISIBLE in HTML while its tail is not — a green `PASS` reaching the screen as `[32mPASS[0m`, corrupted rather than coloured. The parser also plays out what a terminal would have done with the rest: a line rewritten by a progress bar (`10%\r20%\r30%`) shows its last state instead of all three at once, and the sequences that cannot be honoured here — cursor moves, erase-line, window titles — are DROPPED rather than printed, which is the difference between a spinner's log being readable and being one `[2K` per tick.

Three rules it holds. **Every colour is a `--ansi-*` TOKEN**, aliasing the semantic and code palettes wherever one already carries the hue (red is `--destructive`, green `--success`, blue the highlighter's own `--code-variable`) — a terminal's own palette is built for a black background, and `#00ff00` on this cream card is unreadable; the one new literal is cyan, because nothing in the palette had one. **The BRIGHT half (90–97) maps to the same eight**: on a light background a brighter ink is a fainter one, and the weight `ESC[1m` asks for says the same thing legibly. And it is **deliberately partial** — no background fills (a per-span fill on cream is noise), no 24-bit colour (there is no token for an arbitrary value, so the run takes the surface's colour, with its parameters still consumed so the digits do not print). The copy control beside the output hands over `stripAnsi(text)`: the spans are for the eye, and what a reader pastes into a bug report must not carry the codes that coloured them.

**The count also sits in the header, beside the delegates'** (`chat-header.tsx`, `slot="running-shells"`) — asked for as "количество активных шелов рядом с количеством активных субагентов", and the two are the pair a reader scans: how many agents are working, and how many commands they have open. Drawn at ZERO like the sub-agent counter it sits next to, and for that counter's own recorded reason — one that appears only when something is running answers "is anything running" with the same blank space as a header that has no such readout. It holds the commands themselves behind it (`ShellRows`, which is why that component grew an empty-case sentence; the panel's section never reaches it, drawing nothing at all instead). **The liveness gate lives in `Chats.tsx`, at the one place both are fed from** — `shellsByAgent` is built from the fold, re-keyed to the panel's card ids and filtered to agents still working, and the header's count is a flatten of that same map. Two copies of the rule is how a `2` in the header comes to sit over three cards below it; the panel therefore renders exactly what it is given and invents no filter of its own.

**While a turn runs there is ONE clock, and it is the worked total.** REPORTED against a header reading `running · 21s · worked 21s`: "у нас сейчас два раза показывается таймер… нам нужен только таймер, сколько он в целом работал". The first figure was this turn's raw wall clock (`ElapsedTime`, now deleted with its `turnStartedAt` prop and the `Chats.tsx` memo behind it), and on a thread's first turn the two are the same number printed twice. Only the RUNNING half went: settled, that slot still says when the thread last spoke, and `completed · 4m · worked 1h 41m 5s / 5 turns` is two different answers rather than one of them repeated. The reason a wall clock was there at all is answered by what replaces it — the relative time reads "just now" for a whole turn, which is why it cannot be shown while running, and `worked` moves every second, which is what the relative time could not do. One thing is genuinely lost: `worked` PAUSES on an approval card by design, so a thread parked ten minutes now shows the seconds it worked rather than the minutes it waited — the card itself is on screen saying so.

**How long each turn WORKED** (`turn-duration.ts` — the twin parser over `usage.durationMs`/`apiMs`, the wall-clock fallback, `TurnDurationContext` and `formatDuration`; rendered on the `turn_complete` row beside the cost it already carried, and summed into the header as `worked 4m 12s / 6 turns`). The app showed how long AGO a thread last spoke and never how long it worked: the header clock and the working row are live-only and both vanish at the settle, while a sub-agent block has said `took 13s` since M3 — so a delegate was better instrumented than the agent that launched it. Two clocks, and the CLI's own wins where it exists: claude's `result` line carries `duration_ms`/`duration_api_ms` (probed 2026-08-14; every timing field was being dropped by `readClaudeUsage`, which read only `total_cost_usd` beside them) and measures the agent WORKING, so it counts neither the first-prompt MCP-readiness hold nor a stretch parked on an approval card. ACP reports no timing at all and declares so rather than passing off the driver's own wall clock as the agent's figure, so a cursor turn is measured from its durable rows — MINUS the parked stretches, which is what keeps the fallback meaning the same thing as the primary: an `approval_request` and the `approval_verdict`/`unanswerable` closing it are both rows, so the wait is readable, and without the subtraction a turn blocked half an hour on a question card would report the lunch break as work. The thread total is the SUM of its turns and never `updatedAt - createdAt`, which is the plausible-looking wrong number — a chat left open across three days with five minutes of work in it spans `3d` and worked `5m`, and both are now on the header at once. `apiMs` can EXCEED `durationMs` on a turn served off a kept session, so the tooltip's API/own-work split is withheld on that reading rather than clamped to a fabricated `0s`.

**That middle source is only as fresh as the client keeps it** (`rememberRunContext` in `use-chat-run.ts`). The row outranks the transcript because the daemon's row moves with every reading while the transcript carries a figure per SETTLED turn — but the copy in the renderer was whatever `GET /v1/chats` answered at mount, and nothing refreshed it: `run_status` carries status, activity, `updatedAt`, the preview and the title, and no reading. So the ring sat on a frozen number for the life of the window while the daemon's row went on moving. REPORTED as "прыгнул кружочек с контекстом. Он показывал 50%. Как только я на него навёл, он начал показывать правильную цифру: 70%" — the ring on the frozen copy, the readout asking the live CLI; the daemon's row for that chat held 740,515 of 1,000,000 at that moment. Every live reading is now mirrored onto the copy, so the fallback a settle drops into is the newest figure this client has actually seen rather than an old one. Guarded on the value CHANGING (the event fires many times a second, and an unconditional write would re-render the sidebar per delta) and on it being POSITIVE — the same "a reported 0 is not a measurement" rule the live plane and the transcript fold already apply, so a settle that clears the figure cannot erase the last real one.

**The RING is drawn from three sources in strict recency order, and the middle one is the run ROW** (`chatContext` in `Chats.tsx`): the live delta for this turn's latest request, then `Run.contextTokens` — every reading the CLI reported, filed by the daemon as it arrives — then the last SETTLED turn of the loaded transcript. REPORTED as a ring reading `2%` beside a panel reading `46%`, on a chat whose last settled turn had ended directly after a `/compact`: the transcript's newest figure was 16.7k of 1M and the hour of work since had regrown the window to 462k with nothing settled to record it. The live plane HAD that figure and is ephemeral — a reload, a reconnect or a first open starts without one — and the transcript cannot have it at all until the turn ends, so the row is the only thing a cold window can read. Reading the live value directly rather than through `agents[0]` is what makes the order true: that field already collapses live onto transcript, which would put the oldest source ahead of the row. `useContextReadings` stays the last fallback, for the one stretch the row cannot cover — a switch whose refetch is still in flight.

**A COMPACTION invalidates every reading taken before it, and there are four places one survives.** REPORTED as "после компакта кружочек не обновляется. Он все еще так же заполнен с контекстом", and it is a defect of the CLI whose compaction geniro performs ITSELF — cursor, which has none of its own (`AdapterConfig.geniroCommands`). There, the conversation is DISCARDED and a summary is put aside for the turn that replaces it, so nothing measures the new one until the user sends the next message; every source the ring reads went on holding the old figure. Reproduced in the dev app: a cursor chat at `Context 10% full — 101.5k of 1M` read exactly that directly under its own row saying `everything before it is no longer in its context`. The daemon clears the run row (`RunDao.forgetContext` — the count only, never the window, which belongs to the model) and stamps `conversationReplaced` on the compaction row; the renderer then answers the other three, and each needed its own: the transcript FOLD resets at that row (`endsContextHistory`, which also covers the CLI's own compaction marker — a figure the compaction reported about itself lands BELOW it and overwrites the null), the LIVE plane is cleared when the row arrives (it is dropped on a run switch, never on a settle, so it outlives the turn it was filled in) along with this window's mirrored copy of the run row, and the RECALL is not consulted at all while a transcript is loaded — a loaded transcript with no reading is an answer, while an empty one is the refetch the recall exists for. Only geniro's own compaction clears the live plane: a CLI that compacts for itself REPORTS what it left behind, and that reading arrives around its own marker rather than safely after it. What the user sees between the compaction and their next message is an EMPTY ring saying why (`ContextMeter`'s `awaitingReading`), not the absence of one: withholding it was the first cut of this fix and came straight back — "я на втором скриншоте у тебя сейчас вообще кружочку не вижу!" — on the same reading the effort and context-window chips are drawn by, and worse here, because the ring is the one thing on that row a user watches climb. It is muted rather than green, since a filled nought would claim an empty window nobody has measured, and it needs the WINDOW to be a gauge at all — which is why `chatContext` now reads the denominator whether or not it has a count. Verified end to end on cursor: `101.5k` → an empty ring reading `Conversation compacted — its new size is measured on the next message` → `64.5k` on the next turn.

**What the context window actually HOLDS** (`context-panel.tsx` + `chat-metrics.ts`, opened by the existing `context-meter` ring). The ring answered "how much room is left" and nothing about what filled it, which is the whole of the report: a user pointing at `9%` and asking for the statistics their own CLI's `/context` prints. Fetched from `GET /v1/chats/:runId/metrics` when the readout is OPENED and never polled — it is a multi-second question put to the user's own running agent — and re-fetched on every open rather than cached, since the window is exactly what changes between two glances at it; the previous reading stays on screen while the SAME chat is re-read, so the re-fetch costs no blank panel — a DIFFERENT chat starts blank instead, since a reading is carried with the run it was taken from and a mismatch reads as empty (the meter is not unmounted across a chat switch, so the alternative was the previous chat's window, totals and spend sitting under the new chat's name). One component still, not a second meter: the panel is `children` the same `MeterReadout` renders, and the one-line summary steps aside only once a full breakdown has arrived (it states the same used/window pair, and two renderings of one figure inches apart is what the readout was already criticised for). Deferred categories are drawn in their OWN section rather than in the bar, because they sit outside the CLI's total — one live reading had 274k deferred against a 98k total, which in one bar reports a window nearly four times fuller than it is. Category colours come from the avatar palette by POSITION in the CLI's own list, never by name: the names belong to the CLI and it is free to invent one, which a name-keyed map would leave uncoloured or, worse, silently give a neighbour's colour. Offered for a CHAT only — a workflow run's nodes each hold their own process, so `metricsRunId` is null there and the panel is never shown under a name it does not describe. **The panel is ordered by what a reader came for, not by where the figures came from**: the window headline, then the account's PLAN LIMITS, then the thread's totals, and only then the itemization (deferred rows, instruction files, one row per MCP server). Those last three are open-ended, and with a dozen servers they run longer than the 26rem scroll box — which is what put the plan limits a screen and a half below the fold, with the popover's own bottom edge reading as the end of the content ("the weekly-limits feature — I open it on claude and see nothing"). `Breakdown` therefore renders the window itself and `ContextDetail` the itemization, so the two can sit on opposite sides of the limits.

### Graphs

**An INSTRUCTION block is a node that never runs.** The palette's third category (`instruction-node.tsx`, wired with the `instruction` edge kind) drops a free-text block onto the canvas; its text is appended to the turn of every agent it is wired to, ranked after the user's global custom instructions and before that node's own `role` (root `CLAUDE.md` → *Agent instructions*). It has no status chip and no `node_state` row — the daemon writes neither, because `pending` is a promise that something will happen to it — so nothing about it ever settles, fails, or appears in the run order. It is also the FIRST node field whose CONTENT the daemon can refuse (bounded by the same schema as the settings box), and the builder autosaves the whole workflow in one PUT, so `node-validate.ts` mirrors that bound: without the mirror one over-long block stops every later edit to that workflow from persisting at all. The two dashed non-data wires — `call` and `instruction` — share ONE component with a per-kind variant (`annotation-edge.tsx`, formerly `call-edge.tsx`), because the back-edge routing is the fiddly half and a second copy is how the two would come to disagree about where a wire goes.

`graphs/` React Flow canvas. **A node's pickers are only as trustworthy as the list behind them, and the list arrives late.** The inspector fetches the SELECTED node's CLI vocabulary, so a node of the other CLI mounts against the previous one's — and the model chip acted on it twice, adopting the first alias for a model-less node and deciding whether a stored model is off-list. Measured 2026-08-15 in the real builder: adding a cursor node while a claude node was selected wrote claude's `claude-fable-5[1m]` onto the cursor node, into the workflow YAML and then into the run — whose own transcript recorded `agent does not offer the model 'claude-fable-5' — this turn runs on the agent's current model instead`, so the node ran on a model nothing on screen named. Both directions reproduced (a claude node stamped `auto-smart`), deterministically, with both lists already cached. The fix is in `useAgentVocabulary`, which now resolves DURING RENDER off its own cache rather than from an effect-set state: an effect is always one commit late, and that commit is the one a child mounts in. The adopt is since gone entirely (see the settings band below), but the second use remains and is decided the same way: free-text mode waits for a NON-EMPTY list, which ended the visible half of this — every re-opened node showing its model as `Custom…` over a text input, permanently, because an empty list makes every stored model look off-list.

The **canvas** carries the same lateness in geometry: React Flow defers the initial `fitView` until nodes are measured, so on a workflow created moments ago it fired when the FIRST node landed and scaled that one node to fill the pane — `scale(1)` empty, `scale(3.42)` the instant a node was added — hence `INITIAL_FIT`'s `maxZoom: 1`, capping the AUTOMATIC fit only; the Controls' own fit button is asking to fill the screen and stays uncapped. A toolbar add also PANS to what it just added: adds stack 260px right of the rightmost node, so the fourth click put its node past the edge and the builder read as having stopped adding them — a drop is exempt, having landed where the user aimed.

**The inspector's per-run settings are the COMPOSER's chips, in one band.** Model, effort, approval and config directory each name the same thing the composer names, and each had grown its own control here: two selects, a bordered chevron and a bare path `Input`, spread down the panel with Description and Role standing between the model and the approval it belongs beside — reported as "effort select and model should be same design as when we create chat … approval should be near by … config directory should be the same setting". They are now `chats/model-select`, `chats/effort-select`, `chats/approval-mode-select` and `chats/config-dir-select`, wrapped in one bordered card under a single `Agent settings` label. The card is not decoration: the chips are `ghost` — flat until hovered — and on the inspector's own tinted ground a bare row of them read as loose text.

Two of those merges changed BEHAVIOUR, both in the direction of the composer. `graphs/model-select.tsx` is **gone**; its free-text entry survives as `ModelSelect`'s `allowCustom` (the builder's case, not the composer's — a workflow runs for months, so naming a model the CLI does not enumerate is worth a field there), and with it the chip's `default model` row. That row is why the ADOPT had to go: it force-set the first alias on any model-less node, so the instant a user picked "let the CLI decide" it wrote `opus` straight back. The builder could not previously express that answer at all. And the **approval** modes now come from the daemon's `approvals[]` — the same capability the composer's chip reads — instead of a hardcoded three; `plan` is filtered out, being a `ChatApprovalMode` the workflow schema has no value for, so it cannot build a node the daemon refuses on save. Unlike Model, effort still has no adopt, for the reason the default row exists: an unset level means "let the CLI decide", which is a real answer.

**MCP is behind a chip, but the READ is not.** The listing used to stand open in the panel — a header, a hint, up to ten server rows and a paragraph of connection-failure text under each broken one — which is what "we should have a button there to show mcp, not just inline" was about; it now opens `components/mcp-dialog-button.tsx` (extracted from the Agents panel, one component with an `icon`/`chip` trigger). What it deliberately does NOT do is gate the fetch on the press, the way the Agents panel does: `useNodeMcp`'s daemon refusal is the ONLY thing that can tell the user their config-directory path is wrong — claude CREATES a directory it cannot find and then reports "Not logged in" about it — so the read stays on selection and its 4xx renders under the chips, with the MCP chip suppressed while it stands. That error is also the one string in the panel that is routinely ONE unbroken token (the daemon's uniform shape carries the percent-encoded query string), hence `break-words`: unwrapped it did not widen the 300px panel, it ran out past its right edge.

### Settings

`settings/`, `notifications/` (the renderer half of the notifications module — see *System notifications* below), `autogenerated/` the generated daemon client + every daemon wire type (`pnpm generate:api`), `daemon-api.ts` which binds it to a launch handle, `daemon-client.ts` the WS client.

`handoff-open.ts` the ONE resolve-then-open-a-terminal helper, used from the chat surface — ONE call site left, in `chats/Chats.tsx`: handing a thread's conversation to the user's own terminal, which is the only thing on this surface a terminal is still FOR. Settings does not use it.

**A Sign in press is answered by the BUTTON, not by the daemon's reply.** REPORTED as "I press Sign In and there is no loader, nothing — the page opens and the button still sits in the same state". `useCliLogin.start`/`startMcp` set `login` only once `POST /v1/auth/login` returns, and the daemon holds that reply until the CLI prints its URL (`URL_WAIT_MS`) — measured at **4001ms** in the running app, driving the real dialog. For those four seconds a browser tab opens behind the window and nothing on screen moves: the progress panel cannot exist yet, because there is no session to render. `CliLoginController.starting` fills exactly that window, set SYNCHRONOUSLY before the await (anything derived after it lands inside the gap it exists to cover) and cleared in a `finally`, so a REFUSED start does not leave a spinner over a sign-in that never began. Both buttons read it — the account card's (`agent-config-list`, `signingIn: CliKind | null`) and the MCP row's (`mcp-section`, `signingIn: string | null`) — and both go `disabled` as well as spinning, which is not cosmetic: a second press opens a second browser challenge and invalidates the first, the same reason the account card withholds its button entirely once the panel owns the flow. The flag is the CALLER's on both, because the controller is: one sign-in runs at a time across the screen, so a copy kept per section would let two of them each believe they own it.

**And the listing is re-read on focus-return while a server sign-in is in flight** (`Chats.tsx`). The settle stays the primary mechanism, but the daemon calls a sign-in settled when the CLI PROCESS EXITS — so a CLI that lingers after the browser round-trip leaves the row stale for as long as it lingers, which is the other half of the same report ("the status updated only after 30 seconds, probably"; detection itself was measured at ~1.3s, so it was never the probe). Focus-return is when the answer may have changed, since leaving for a browser tab and coming back is the shape of the flow — the same backstop Settings already runs for the ACCOUNT probe. Bounded to a sign-in actually being in flight rather than armed on every focus: re-dialling a folder's servers launches each one and is measured in seconds.

**Signing in never opens a terminal, on any surface.** `use-cli-login.ts` is the one controller — start, poll, submit a pasted code, cancel — over the daemon's `/v1/auth/login` (the account) and `/v1/auth/mcp-login` (one server), and `components/cli-login-progress.tsx` is the one panel that renders it. Three call sites now share both: the Settings account card, the Agents panel's MCP dialog, and the transcript's own failure row. That last one was REPORTED as *"after click on sign in - it will open terminal. and after redirect and auth nothing will happens"* — it was the last caller still resolving the invocation and handing it to a shell, which put the only surface that knows how a sign-in is going outside the app entirely: nothing here was watching that window, so a finished browser round-trip changed nothing on screen and the failed turn sat looking exactly as it had.

Two things about `Chats` in particular. It holds ONE controller instance for both of its flows, for the reason the hook holds a single sign-in at all — two browser challenges open at once are indistinguishable in the browser, and the second reads as the first having failed — so `onSettled` is handed the sign-in that settled and dispatches on `server` (a server's outcome is re-read from the LISTING, an account's from the CLI's own status; neither from an exit code). And the two panels render in different places for the same reason: the MCP one belongs in the dialog it was pressed in, while the account one is pinned above the composer rather than drawn on the error row that started it — that row is somewhere in a scrollback the user is free to leave, and claude's flow asks for a pasted code, which is unusable off-screen.

**An agent-specific setting lives in that agent's CARD**, never in a page section of its own (`AgentConfigListProps.agentSettings`). REPORTED as "все специфические, именно к агентам специфичные настройки должны быть там": cursor's Max Mode and claude's browser tools each had a heading further down Settings, so what a reader could change about cursor was half in the card named cursor and half two screens below, under a heading that named a topic instead. A card now reads top-to-bottom as which binary → how it behaves → whose account. The nodes are passed IN rather than built by the list, which is the rule the daemon's adapters follow as well — that component knows how to draw a card, not what is true of claude — and it is what keeps ONBOARDING, which shares the list, free of settings that belong to a running app: it passes none. The cost is that every such setting sits behind a disclosure now, which is why the Settings spec opens a card before looking for one.

**Cursor Max Mode** — the switch behind `Settings.cursorMaxMode`, defaulting ON, drawn in the cursor-agent card. It rides chat create and workflow-run start beside `customInstructions` and is SNAPSHOTTED onto the run, so it applies to the next chat and an open conversation never changes window mid-thread. Its whole reason for being a switch is billing: Cursor charges Max Mode at the model's API rate plus 20% on legacy request-based plans, and nothing here can read which plan a user is on. The default is ON because the defect that produced the feature was a window too SMALL — `kimi-k3` running at 200k in geniro against cursor's own 1M. `false` is sent EXPLICITLY rather than omitted (`currentRunSettings` in `chats/Chats.tsx`): the daemon reads an absent field as the adapter's own default, so a decline and a silence must not look alike. See `apps/daemon/CLAUDE.md` for the measurements behind the flag itself.

**Custom instructions** — the Settings section holding the user's standing instructions to every agent (`Settings.customInstructions`, an `ExpandableTextarea` since it is a prompt-length field). Saving goes through `use-debounced-persist.ts`, which is where the debounce, the latest-value ref, the unmount flush and the dirty guard now live once rather than per field: an UNSAVABLE value (over the ceiling, or carrying control characters `settingsPatchSchema` refuses) is held on screen and never written, and the timer handle is NULLED rather than merely cleared — without that, a legal edit followed by an unsavable one still flushed the unsavable text on unmount. The section states which of the two rules is refusing. It also carries **Remove from existing chats** (`POST /v1/chats/forget-custom-instructions`), the purge for text already snapshotted onto earlier runs — a press, never a consequence of clearing the box, since it discards the per-run snapshot guarantee. It is read at the MOMENT a run is created (`currentCustomInstructions()` in `chats/Chats.tsx`, used by chat create, session import and workflow-run start) rather than cached in component state — `Chats` stays mounted across nav switches, so a cached copy would start a chat on text Settings had already replaced. The section also PREVIEWS geniro's own host preamble, read from `GET /v1/capabilities` (`hostPreamble`) rather than restated here, and renders nothing at all until that read lands: an empty box captioned "geniro already tells every agent this" would state that the app sends nothing, which is the opposite of true. See the root `CLAUDE.md` → *Agent instructions* for what the preamble claims and why it must contradict the CLI's own prompt by name.

**macOS packaging (M4)**: `pnpm --filter @geniro/ui build:mac` runs `scripts/build-mac.mjs` — two self-contained `pnpm deploy --prod --legacy` stagings (shell app + daemon under `Resources/daemon`), Electron-ABI rebuild of better-sqlite3 in the daemon staging, `.icns` generated from `resources/icon.png`, signing (below), no `publish` feed; the Homebrew cask + install script strip the quarantine bit so the un-notarized app launches, DMG + zip into `release/dist/`. The packaged app presents as **"Geniro"** on every macOS surface (menu bar, Dock, About, Finder) via electron-builder `productName`.

**The build is signed so that macOS can tell one release from the next.** Every privacy grant is recorded against the app's DESIGNATED REQUIREMENT — the signature's answer to "which code is this app" — and re-asked the moment a running build stops satisfying the requirement its grant was recorded under. An ad-hoc signature has no certificate to name, so its requirement is `cdhash H"…"`, the hash of its own bytes; measured on the shipped 1.46.2 bundle, and confirmed against the predicate macOS evaluates by cross-checking two builds of one probe app (`codesign --verify -R "=<v1's requirement>" v2.app` → failed). That is the whole of the reported "every reinstall asks for all the permissions again", and it applied to the self-update as much as to a reinstall. `scripts/make-signing-identity.mjs` creates the one **self-signed** certificate every release is signed with (free — no Apple account; the users' Macs never see it, since the requirement is evaluated against the certificate embedded IN the app), and `GENIRO_SIGN_IDENTITY` names it to `build-mac.mjs`. Three things hang together there and are one branch for that reason (`.claude/rules/packaging-config.md`): the identity, `forceCodeSigning` — without which electron-builder answers a missing identity with a WARNING and an unsigned artifact, the one failure that packages and installs perfectly and silently resets every user's permissions — and a read-back of the packaged bundle's own requirement, asserted against the arm that was taken. Still **not notarized**: a self-signed certificate is not a Developer ID, so Gatekeeper's verdict is unchanged and the quarantine stripping stays. A local build with no `GENIRO_SIGN_IDENTITY` is ad-hoc as before, and says so.

**A grant made BEFORE that change is dead, and it does not look dead — it looks granted.** TCC stores the requirement alongside the decision, so a row recorded against an ad-hoc build keeps its `cdhash` forever while every signed build since fails it. The row stays in System Settings under the app's name with its switch ON, and access is refused anyway; Screen Recording in particular never re-prompts for allow/deny, so the app only ever gets the "grant access in Privacy & Security settings" dialog, pointing at the switch that is already on. REPORTED as exactly that dead end, and it is invisible from inside the app — Electron's `systemPreferences.getMediaAccessStatus('screen')` says `denied`, which is true and says nothing about why. The one place the answer exists is `tccd`'s own log, captured while reproducing the refusal (`/usr/bin/log stream --level debug --process tccd`, then trigger it — note `log` is a zsh BUILTIN, so the absolute path is required):

```
Failed to match existing code requirement for subject io.geniro.desktop and service kTCCServiceScreenCapture
For io.geniro.desktop: matches platform requirements: No
Service kTCCServiceScreenCapture does not allow prompting; returning denied.
```

The fix is one-time and belongs on the machine, not in this repo: `tccutil reset <Service> io.geniro.desktop` drops the stale row so the next request records a fresh requirement — which now names the certificate and therefore survives every later release. Confirmed by re-running the probe after the reset: the `Failed to match` line is gone and tccd writes a fresh record for the current binary.

**It is per-SERVICE, so finding the rest means provoking each one.** A stale row is only discovered when something asks, and the ask is what puts the line in the log — there is no way to enumerate them (the user TCC.db refuses to open even to a process running as its owner). Measured on the reporter's machine, one probe per service from a shell inside the app's process tree: `kTCCServiceScreenCapture` and `kTCCServiceAccessibility` were both stale, `SystemPolicyDocumentsFolder` and `SystemPolicyDownloadsFolder` came back `Allowed (User Consent)` with their requirements matching, and `SystemPolicyAllFiles` was plainly never granted (`Denied (Service Policy)`). So it is not "everything from before the change is dead" — only the rows old enough to predate it. The Accessibility one had already been written down as an environment fact ("osascript has no assistive access here") in a memory note, which is what a stale grant looks like from the outside: a capability that is simply, permanently missing. Two things about re-granting it afterwards: the app has to be RELAUNCHED before a running process sees the new decision, and the requester is usually not this app at all — a CLI agent running `screencapture` is attributed to whatever is responsible for its process tree, which is Geniro. The app's own code touches no screen-capture API.

**App updates** — the app notices a new release, says so, and applies it on one click.

**electron-updater is not used here — a signing fact that has since become a choice.** Its macOS path is Squirrel.Mac, which validates a downloaded bundle against the RUNNING app's designated requirement; while the build was ad-hoc that requirement was a `cdhash` no later build could ever match, so the door was shut. The release certificate (see *macOS packaging* above) reopened it — the requirement now names the certificate and holds across releases — and the door stays shut anyway, because what was built in its place already verifies its own downloads and handles what Squirrel does not know about here (a translocated or read-only install is answered with `brew upgrade`, not a button that fails at the last step). What replaces it is `scripts/install.sh`'s own sequence moved in-process — resolve the release, download the `-mac.zip`, verify it against the published `SHA256SUMS.txt`, `ditto` it into place, strip quarantine, relaunch — split across three files by what each can be tested without: `updater.ts` is the feed alone (no filesystem), `update-installer.ts` is the swap alone (no policy), `update-service.ts` is the policy alone (every dependency injected, so its specs need neither network nor bundle).

Twelve rules the code exists to hold:

- **An automatic check is SILENT unless something changed.** REPORTED as the app appearing to re-render itself every so often, and it was the only event on that cadence — the debug log for the session held no daemon restart and no second `renderer-loaded`, so the window was not reloading. What it was: a scheduled check pushed `checking` and then its outcome at every window, and the renderer's subscriber (`useUpdateState`) sits in `App`, at the root — so the entire tree, transcript included, re-rendered twice every five minutes to display nothing. `checking` draws nothing at all (`footerUpdate` maps it to `{kind:'none'}`), and the outcome on an up-to-date app is the sentence already on screen. Two halves: `check({ announce: false })` for the scheduled callers, since there is no press to acknowledge — a check the USER pressed still announces, because the Settings button reads "Checking…" and disables itself off that phase — and `emit` compares the merged state against the previous one and broadcasts only on a real difference, because the patch is a fresh object every time and `setState` on a new identity re-renders whether or not the value differs.

- **Every deletion runs with `process.noAsar` raised — under Electron, `fs.rm({recursive})` does not delete an `app.asar`, it walks INTO it and never returns.** MEASURED on electron 42.5.1 against node 24.14.0, one 111KB archive: node stats it as a file and finishes in **1ms**; electron stats it as a DIRECTORY and is **still running at 30s**. Electron's `asar-fs-wrapper` is why — it patches `lstat`/`readdir`/`internalModuleStat` so a path inside an archive resolves (which is what makes `require('…/app.asar/main.js')` work), and `fs.rm` believes the directory answer, descending into tens of thousands of virtual entries it then retries unlinking. It does not fail; it does not finish. REPORTED as an update that installs endlessly with a loader that never ends: the bundle swap had already SUCCEEDED and the app on disk was the new version, but `installUpdate`'s `finally` cleanup never returned, so the install never resolved, the phase never left `installing`, and the log carried `update-install-started` with no matching `update-installed`. The same call in the launch sweep is why a user's `Geniro.app.old-*` sat eroded to exactly its two `.asar` files with the RUNNING app still holding fds on them. `withoutAsar` wraps every `rm` in this file and REFCOUNTS, because `process.noAsar` is one global flag and the sweep deletes concurrently — a naive set-and-restore lets the first tree to finish re-enable asar under the ones still being walked. Verified end-to-end on the real 118MB archive under electron: **45,002ms and still running** before, **2ms** after. Nothing in the UI suite can see this — it runs under node, where both arms are the 1ms row — so the spec pins the FLAG, which behaves identically in both runtimes.
- **`ready` is an ENDING that a check may not undo.** The version this service compares against is the RUNNING app's, and a bundle swap does not change it — the relaunch does. So every automatic check after a finished install re-discovered the release already sitting on disk and put the app back to `available`: the Restart button became an Update button, pressing it downloaded and swapped in the identical release, and the cycle repeated every five minutes until the user restarted by hand. `check()` returns early on `ready` without even asking the feed — there is nothing an answer could change while a bundle is already staged, and a newer release is picked up by the first check after the restart.

- **A release is not a release until its macOS archive is attached — and the check reads the release LIST, so that one release which is not can never be the whole answer.** Both halves address the same measured window, from opposite ends. The workflow publishes the release ~14 seconds into a run whose macOS build takes another ~3–4 minutes, so for those minutes `/releases/latest` answered with a release carrying no assets at all, and an app polling every 5 minutes reliably looked inside it: REPORTED on v1.48.4 as `The update could not be installed. release v1.48.4 publishes no macOS archive`, in red, about a build that was still running. The workflow half is the root fix — `create-release` now cuts a **draft**, and `build-app` publishes it (`gh release edit --draft=false --latest`) as its LAST step, after the upload. A draft is invisible to `/releases/latest`, to the release list, to `scripts/install.sh` and to Homebrew, so the window closes for every consumer at once rather than each learning to survive it, and the two paths that used to publish a permanently broken release — a build job that errors, and a run cancelled by `cancel-in-progress` between the jobs — now leave a draft for a maintainer instead. The updater half is defence in depth, since a build CAN genuinely fail: `fetchLatestRelease` reads `/releases?per_page=10` and returns the newest release carrying an archive, filtering drafts and pre-releases itself (the filtering `/releases/latest` used to do) and ordering by parsed VERSION rather than by the feed's tag-date order, so it cannot disagree with `isNewerVersion` about which release is newer. One bad release is then answered by offering the newest good one; only a page with no installable release at all is an error the user is shown — and that error now NAMES the tag when there is one, because "no release carries an archive" and "1.5.0's archive is still uploading" send a reader to different places.

  **Offering the newest good one is not the same as being up to date, and saying so was the third face of this bug.** With the newest tag unarchived, the newest INSTALLABLE release is an older one — often the running build itself — so `!isNewerVersion(release.version, current)` held and the app answered `up-to-date` while a newer version sat on the releases page: REPORTED as "terminal not saying truth — there is a new version". `fetchLatestRelease` therefore answers BOTH questions off the one page — `release`, the newest it can install, and `published`, the newest tag at all (`readPublishedVersion`, split out of `readRelease` so the two stay separable; drafts and pre-releases are excluded from both, or a nightly would leave every stable install permanently "behind"). The phase stays `up-to-date` — nothing is downloadable, and a phase that offers an Update button would put a control on screen with nothing behind it — and carries a MESSAGE naming the pending version, which Settings already renders after the status line. Verified against the live feed on 2026-08-21: ten releases, every one archived, newest published `1.48.5` = newest installable, so the healthy case adds no message (its own test pins that an EQUAL tag stays silent).
- **A release with no `SHA256SUMS.txt` is REFUSED, never warned about.** The build is signed but not notarized, so Gatekeeper validates nothing it will act on and the running app validates nothing about its replacement, so the published digest is the only link between the release that was built and the code about to execute as the user. `install.sh` degrades to TLS-only with a warning because a human is watching it; nobody is watching this. The release workflow therefore publishes that file as a first-class artifact — a build job that stops emitting it silently disables updating rather than weakening it.
- **The old bundle is moved aside, never deleted first.** The rename is the commit point; a failed copy renames it back, so an update that dies mid-`ditto` costs a message rather than the user's installed app. The backup is removed last and only on success.
- **`canInstall` is asked of the filesystem, per use.** An app installed by another account, on a read-only volume, or running TRANSLOCATED (macOS's read-only synthetic mount for a quarantined copy — where a "successful" update writes to a volume that vanishes at quit) gets the `brew upgrade --cask geniro` sentence instead of a button that would fail at the last step. It is still TOLD, in the window: `footerUpdate` returns a `readout` for that case and the rail draws it as a non-pressable glyph carrying the sentence on hover, because the alternative — drawing nothing — left that user's only channel behind a nav click into Settings.
- **Main owns the state; the renderer reports presses.** One `UpdateState` is pushed at every window, so the nav rail's version row (`renderer/updates/update-status.ts` → `footerUpdate`, read by `App`) and the Settings section are two renderings of one download rather than two pollers free to disagree — the same split as notifications. There is no DISMISSAL: the offer lives in the status row now, at the size of the row, so there is nothing to wave away and nothing interrupting a view to be waved away from.
- **A phase that stops moving becomes an `error`, and abandoning it means CANCELLING it.** REPORTED: an install sat on one non-terminal phase and never left it — and because main owns the state, reloading the renderer only re-read the same wedged value, so the only recourse was quitting the app, which nothing tells the user. Every RECOGNISED failure already landed in `error`; what was missing was a bound on the ones nobody recognised. Each non-terminal phase now carries a deadline (`checking` 60s, `installing` 10min, both flat totals since neither reports progress; `downloading` a 3-minute STALL budget re-armed by every progress callback, so a slow 150MB transfer takes as long as it takes while one that never starts still gives up). The re-arm reads the RAW callback, never the published `progress` — a server that declares no content-length leaves `fraction` null for the whole transfer. Two things happen when one trips, and the second is the one that is easy to miss: an `attempt` counter is bumped, so the hung call cannot write `ready` over the failure the user has already been shown, AND an `AbortController` is fired, so the abandoned work really stops. Ignoring it is not enough — the user can retry the moment the app frees up, and an abandoned attempt still inside `swapBundle` would be a second `ditto` writing one bundle. `install()` therefore accepts `error` as well as `available` when a release is held: the rail's Retry control IS that call, and a guard accepting `available` alone made the button do nothing but restate its own refusal.
- **The debris sweep is at LAUNCH, precisely because the install's own cleanup is allowed to fail.** REPORTED: ~224MB of dead trees — two scratch directories under `updates/` and two `Geniro.app.old-*` backups beside the app — from updates that had SUCCEEDED days earlier, each eroded down to the `Contents/Resources` the removal had not finished emptying — which the asar rule above later explained: the removal deleted every ordinary file and then disappeared into the archive. Neither is a missing step (`installUpdate` discards its scratch in a `finally`, `swapBundle` its backup on the way out); both are deliberately best-effort, since a cleanup that throws once reported a completed update as a failed one, and a freshly-written bundle is exactly what macOS holds open behind them. So the guarantee cannot live inside the install at all. `sweepUpdateDebris` runs from `main()`, ungated by the auto-check setting (a user who switched checks off still has the leftovers), matching only the two names this code writes — `update-*` under the work dir, `<the app's own name>.old-*` beside the bundle, which `Geniro.app` itself cannot match.
- **A failure names the phase that FAILED, and one surface composes the sentence.** `error` is an ending, so it erases what died: every failure read "The update could not be installed.", which was REPORTED against a DOWNLOAD that never moved a byte — an app that had installed nothing being told the install had failed, and the log for those two days holds 32 failed CHECKS reported the same way. `UpdateState.failedPhase` carries it, DERIVED inside `emit` from the phase the service was in rather than passed by each of the five error sites, and the lead reads "The update check failed." / "The download failed." / "The update could not be installed." accordingly. The other half of the same report was the JOIN: `${line} ${message}` produced "The update could not be installed. the update made no progress for 3 minutes", a lowercase fragment after a full stop — and it was written out twice, in the rail's hover title and in the Settings line, so neither was fixable alone. `updateStatusText` is now the one composition. It joins an error with a COLON, because main writes those messages as fragments meant to follow a lead while every other phase's is a whole sentence; capitalizing the fragment instead was tried and produced "Ipc broke" out of a real error string, since these carry acronyms, shell commands and absolute paths.
- **Main's update failures go to the daemon's log, never to stdout.** A packaged Finder launch discards main's stdout, so when the wedge above was investigated there was no record of it anywhere on the machine — the gap was itself part of the bug. `UpdateService` takes an injected `UpdateLog` (wired in `index.ts` to `reportMainLog`, which buffers until the daemon exists) and writes the check failure, the install start, the install failure, every watchdog trip and the launch sweep into the same `ui` channel as the renderer's own errors, where the debug panel shows them and the user can paste them into a report.

Nothing installs unasked: the check is automatic (launch + every 5min, gated on the `checkForUpdates` setting, which re-arms the schedule the moment it is flipped rather than at the next launch), the download is not. The Homebrew cask carries `auto_updates true` so `brew upgrade` stops reinstalling over an app that has already updated itself.

**System notifications** — a macOS banner when an agent stops to ask something and when a thread's turn ends, so a run parked on a question does not sit unanswered while the user is in another app. **One module, split across the two processes by what each can answer**: `renderer/notifications/` decides WHEN (`run-notifications.ts` — pure rules over the DISPLAY statuses the sidebar badges show, never the daemon's row, so a banner and the row it sends you to cannot describe one run differently; `use-run-notifications.ts` — the thin React binding, mounted from `Chats`, which the shell keeps mounted across nav switches so a thread finishing while the user is in Settings still reports), and `main/notifications/` decides WHETHER and does the posting. Whether it becomes a banner is read from `notificationsEnabled` at the moment of the post rather than cached in the renderer, so a flipped switch takes effect on the very next question; keeping the gate in the one process that can post one makes that true by construction. Three rules the diff enforces, each a defect if dropped: a run **seen for the first time never notifies** (the chat list loads with every past thread already finished — otherwise the app opens with a banner per conversation in the history), a turn the user **cancelled** is not announced (telling somebody what they just did with Stop is the notification everyone switches the feature off over — `failed` IS announced, since nobody asked for it), and the chat the user is **already looking at** is skipped, but only while the window has focus (suppression is about watching, not about which chat is open — without both halves a user who leaves the app sitting on a running chat is told nothing at all). Clicking a banner raises the window in main — a renderer in a hidden window cannot show itself — and sends the run back over `onNotificationActivated`, which `App` reads for the view and `Chats` for the thread. `notifier.ts` is the only file that touches a notification API, and Electron's own `Notification` IS the ready-made library here: an npm package (`node-notifier`) posts through a bundled `terminal-notifier.app`, so the banner is attributed to that helper rather than to Geniro (and the per-app switch in System Settings then names the helper), it ships a nested Mach-O binary into an app that is signed with no Developer ID and no notarization, and its click cannot reach into this process to raise the window. **Measured 2026-08-15**: `Notification.isSupported()` is true and the service posts/suppresses correctly, but no banner renders on a Mac while the display is being shared or recorded — `dndMirrored: true` in `com.apple.ncprefs` suppresses every app's, which an `osascript display notification` control probe confirms is not specific to this code.

**Sidebar groups** (`chats/run-group.ts`, `chats/group-header.tsx`, and the `run_groups` rows behind them) — the folders a user files their threads into, with a colour, a fold, an order, a live "is anything in here working" reading, and an optional rule that files new chats by the folder they start in.

**The auto-file rule matches a folder AND everything inside it, most specific first** (`RunGroupsService.resolveAutoGroupId`). A user who points a group at a project means the project — its `apps/`, its `packages/` — so exact-match-only would silently never fire for the very chats the rule was made for. When two groups both claim a run the longer `autoCwd` wins, which is the only reading under which a group on `~/work` and one on `~/work/app` can usefully coexist; sidebar order breaks a genuine tie, so the answer is deterministic. Containment is SEGMENT-wise (`utils/path-within.ts`) — a plain `startsWith` files every chat opened in `/work/app-old` into the group that claimed `/work/app`. Both sides are canonicalized at the moment they are CHOSEN (`autoCwd` when it is set, `cwd` when the chat is created), so no read path touches the filesystem, and a rule pointing at a folder that does not exist is refused rather than stored: a rule that can never fire is indistinguishable from a feature that does not work. Adding a rule deliberately does NOT sweep up the chats that already exist in that directory — it says where the next one lands, and retroactively moving conversations the user filed by hand would undo their own arrangement without asking.

**Deleting a group releases its chats**; it never takes them with it. The release runs BEFORE the row is dropped, since the reverse order leaves a window in which a run points at a group that no longer exists and a crash inside it makes that permanent. It is the one destructive-looking action in the app that is deliberately NOT behind a confirm dialog — nothing is destroyed — and the menu row says so at the moment the user is deciding (`Delete group · keeps chats`).

**Everything moves by dragging, and the DROP ZONE is the whole section.** A header dragged over another group REORDERS, and the list rearranges under the cursor rather than jumping when the button comes up — the daemon is told once, at `dragend`, because the intermediate arrangements are not decisions. A chat dragged into a section FILES ITSELF there — the only way, since the row's "move to group" menu is gone: filing is one gesture where the menu was a click, a read and a second click. The section — header, rail, rows and the space between them — is one `li` carrying the `dragover`/`drop` pair, because hanging the target off the header alone left the BODY of an expanded group inert: a chat dragged into it lit nothing up and landed nowhere, which is most of what the eye actually aims at. `dragover` bubbles, so one handler covers every child and the rows need none of their own; an empty group has no rows to aim at and is dropped onto through the same section. One piece of drag state carries the KIND for exactly that reason: the same header is a drop target for both gestures and they do different things, which cannot be told apart by guessing from an id. A drop that changes nothing writes nothing. Neither a group nor a chat is draggable while its name is being edited — a text field inside a draggable element cannot be selected with the mouse, because the drag starts instead. The row menus stay (they are the keyboard path, and the only one that can reach `New group…`).

**A group header reads its state from the BADGES its rows are showing, never from the daemon's `status` column** (`runGroupSummary` over `sidebarRunStatus`). The column and the badge disagree in exactly the cases that matter — a live turn under a stale `completed`, a run parked on a question — so a header computed from the row would contradict its own children. `needsInput` is reported ALONGSIDE `busy` rather than folded into it, because a collapsed group would otherwise hide the one state that cannot advance without the user, which is the failure this whole feature would introduce if a header only ever said "something is running".

**A group's chats are enclosed** — indented, hung off a rail in the group's own colour (`GROUP_RAIL_CLASS`) — because without it an expanded group ran straight into the next and the list read as flat. The section's bottom padding is PERMANENT rather than part of the drop highlight: it is what keeps the rail from running flush into the edge below it, and adding it only while a drag hovers would shift every row down at the moment the user is aiming at one. The highlight itself is `muted` and a hairline — `accent` is the palette's warm caramel and read as a coloured state rather than as a destination, and a 2px ring on a block this size in a 260px sidebar reads as an error. An EMPTY group draws no rail (the container exists to enclose rows, and with none it rendered as a 4px orphan tick); its header is the drop target either way. The count sits against the name it counts rather than being pushed to the far right by `flex-1`, where it read as an unrelated second column. Colours are NAMES on the wire and tokens in the renderer (`--group-*`, aliases of the avatar hues so a group dot and an agent avatar cannot drift into two different blues) — a hex could not legally be used at the call site, since the renderer's eslint config makes a colour literal an error.

**A group's options are a PANEL, not a row list** (`Popover`, `anchor="viewport"`). The auto-file rule was a menu row whose label was the folder path and whose action was "open the picker" — so choosing the same folder again looked like nothing happening, and nothing anywhere said what the rule DID. It is now a stated section: a caption in words, the path as a label, and the two things that can be done to it as two small buttons that say which is which (choose another, remove). `anchor="viewport"` measures the trigger and places the panel `fixed`, which is the only way out of the chat list's scroll container — the earlier fix capped the panel's WIDTH to fit inside that clip instead, at 257px in a 235px slot. The colour rows stay a `Menu` on the DOT, because fourteen rows in one panel scrolled its last four — the delete among them — out of sight.

**Deleting a group asks first**, in a dialog that leads with what is NOT deleted ("Its 2 chats are kept — they move to Ungrouped with all their history"). Nothing is destroyed, so the confirm is not there to prevent loss; it is there because *delete* is a word a user reads as final, and a menu row's hint is not where that difference can be stated.

`DaemonSupervisor.start()` reuses a still-healthy daemon left by a prior UI instance (pid + `/health/check` + identity + bundled `version` + the pidfile's `entry` stamp), sweeps stale pidfiles, and only tears down the process it owns. **The `entry` stamp is what makes "is this the current build" answerable at all**: `version` is the package version and is identical across every rebuild, so before it a rebuilt daemon was adopted over and the app went on serving the previous compile — measured as a `pnpm dev` daemon four days old with a whole module missing, which is how instrumentation written to diagnose a bug came never to run. A daemon started from the SAME entry path whose mtime/size have moved is a rebuild and is replaced; one from a DIFFERENT path (`pnpm daemon:dev` on TypeScript source) is a different thing and is left alone; one reporting NO stamp predates the check and is replaced. The other half of that fix is in `turbo.json`, where the `dev` task carries `dependsOn: ["^build"]` — `dist/main.js` is produced by `pnpm build` alone and never by `electron-vite dev`, so without it launching the app ran whatever compile happened to be on disk, and the `@geniro/daemon` dependency in `apps/ui/package.json` (which imports nothing) exists solely to give turbo that ordering edge. **That edge only exists when the launch goes THROUGH turbo**, which is why the root `dev` script is `turbo run dev --filter=@geniro/ui` and must never be "simplified" back to `pnpm --filter @geniro/ui dev`: pnpm runs `electron-vite dev` directly, turbo never enters the picture, and every word above about the ordering silently stops being true. It was `pnpm --filter` for months, and the symptom is exactly the one the `entry` stamp was written to catch and cannot — the stamp only decides whether to REPLACE a running daemon, and a `dist/` nobody rebuilt is stale before any daemon starts — which is why it also passes `GENIRO_IDLE_EXIT_MS` to every daemon it spawns: a daemon it does NOT own (left by a force-quit or a crash) is one it can never stop, so the daemon has to be able to stop itself. The macOS counterpart is on the UI side: `window-all-closed` does not quit on darwin, so a closed window can outlive its daemon's idle window — `app.on('activate')` therefore re-ensures the daemon (`ensureDaemon()`, the one path both launch and reactivation take) before the reopened window can talk to a handle that no longer answers.
